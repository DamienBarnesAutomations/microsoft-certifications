## Card 1: Automate Database Deployment

### Deployment Models in Azure
- **Declarative (ARM/Bicep):** Specify *what* to create; Azure Resource Manager orchestrates creation order.
- **Imperative (PowerShell/Azure CLI):** Specify *how* to create — sequence of commands.
- **Azure portal:** Graphical interface for ARM — every deployment can be exported as ARM template.

### ARM Templates (JSON)
- Declarative JSON documents describing resources in a resource group.
- **Benefits:** Repeatable (idempotent), Orchestrated (dependencies), Modular (split/combine), Exportable (from portal).
- **Authoring:** VS Code with ARM Tools extension, Visual Studio.
- **Deployment scopes:** Resource group, Subscription, Management Group, Tenant.
- **Deploy with PowerShell:** `New-AzResourceGroupDeployment -ResourceGroupName X -TemplateUri Y -parameters @{}`
- **Deploy with Azure CLI:** `az deployment group create --resource-group X --template-file path/template.json`
- Remote linked templates with relative path: use SAS token in query-string.

### Bicep
- Declarative DSL for Azure resources — transpiles to ARM JSON.
- **Benefits:** Concise syntax (~60% less verbose than JSON), full resource/API version support (no waiting for tool updates), easy to learn.
- `param` / `var` / `resource` keywords. `parent:` for nested resources.
- Deploy: `New-AzResourceGroupDeployment -ResourceGroupName X -TemplateFile ./main.bicep`
- **Azure CLI limitation:** Currently doesn't support deploying remote Bicep files directly — must transpile to JSON first.

### PowerShell for SQL Deployment
- **Az.Sql module:** Subset of Az module for managing Azure SQL resources.
- Verb-noun syntax: `Get-AzSqlServer`, `New-AzSqlDatabase`, `New-AzSqlInstance`.
- Supports: creating/modifying resources, deploying ARM templates, querying status.
- Environments: PowerShellGet, Azure Cloud Shell, Docker container.
- `New-AzSqlInstance` parameters: `-LicenseType`, `-StorageSizeInGB`, `-VCore`, `-Edition`, `-ComputeGeneration`.

### Azure CLI for SQL Deployment
- Cross-platform (Linux, macOS, Windows). Cloud Shell or Docker support.
- Syntax: `az <reference> <command> --parameter value`.
- `az sql server create --name X --resource-group Y --admin-user Z --admin-password W`
- `az sql server firewall-rule create` to configure firewalls.
- **PowerShell vs CLI:** PowerShell uses verb-noun; CLI uses reference-command pattern.
  - Sign in: `Connect-AzAccount` (PS) vs `az login` (CLI)
  - List subscriptions: `Get-AzSubscription` vs `az account list`
  - Create SQL server: `New-AzSqlServer` vs `az sql server create`

### Azure DevOps / CI/CD
- **CI:** Small frequent changes to code, automated build/test.
- **CD:** Automated delivery to infrastructure.
- **Azure Pipelines:** Deploy ARM templates via PowerShell scripts or dedicated tasks.

### Exam Gotchas
- ARM templates are **idempotent** — same template can be deployed repeatedly.
- Bicep transpiles to ARM JSON; not a general-purpose language.
- Azure CLI cannot deploy remote Bicep files directly — must transpile to JSON first.
- PowerShell Az.Sql module is a subset of Az module.
- `New-AzSqlInstance` requires SubnetId for Managed Instance.
- Bicep is ~60% less verbose than equivalent JSON.
- Resource group deployment vs Subscription vs Management Group vs Tenant scope.

## Card 2: Create and Manage SQL Agent Jobs

### Maintenance Plan Activities
- **Check Database Integrity:** DBCC CHECKDB — checks logical and physical consistency. Run regularly; align with backup retention window.
- **Shrink Database:** Reduces file size by moving data — NOT recommended for regular maintenance (causes severe index fragmentation, I/O intensive).
- **Reorganize/Rebuild Index:** Based on fragmentation level. Rebuild also updates statistics.
- **Update Statistics:** Crucial for query optimizer. Default sampling usually sufficient.
- **Backup Database:** Full, Differential, Transaction Log.
  - Full + Differential + Log backups define RPO.
  - Restore flow: Full → most recent Differential → Log backups since that differential.
- **Cleanup History:** Removes old backup/restore/job history from msdb.
- **Maintenance Cleanup Task:** Removes old backup files and text reports from disk. Only removes files in specified folders (not subfolders).

### Best Practices
- Create separate plans per task type (e.g., system DB backup vs user DB backup).
- **Backup retention > consistency check window** — ensure you can recover if corruption is found.
- Stagger intensive operations (backups, index maintenance, CHECKDB) across week.
- Maintenance Plans are stored as Integration Services (SSIS) packages.

### Proxy Accounts
- Stored credentials for SQL Server Agent to run job steps as a designated user.
- Used when job steps need granular security rights (e.g., backup to network share without giving service account access).
- Login info stored as credential in SQL Server instance.

### Job Schedules
- Jobs and schedules have **many-to-many relationship** (each job can have multiple schedules; each schedule can be assigned to multiple jobs).
- Stored in **msdb** system database.
- Maintenance Plan Wizard doesn't create independent schedules.

### Multiserver Environment
- **Primary server:** Stores master copy of jobs, distributes to target servers.
- **Target servers:** Periodically connect to primary to update job schedules.
- Define job once, deploy across enterprise.

### Operators, Notifications & Alerts
- **Operators:** Aliases for individuals/groups (typically email distribution groups). Defined by name and contact info.
- **Notifications:** Per-job settings for completion/success/failure. Best practice: notify only on failure.
- **Alerts:** Proactive monitoring based on:
  1. SQL Server error log (error numbers, severity levels ≥ 16)
  2. Performance conditions (CPU > 90% for 5 min, low Page Life Expectancy)
  3. WMI events
- Alert responses: notify operator (email) or execute another SQL Agent job.
- Requires **Database Mail** to send emails.

### Exam Gotchas
- Shrink Database NOT recommended for regular maintenance — causes fragmentation.
- Consistency check window must be less than backup retention period.
- Proxy accounts = stored credentials for specific job steps.
- Jobs ↔ Schedules = many-to-many. Stored in msdb.
- Alerts can respond: notify operator OR execute job.
- Operators should use email distribution groups for redundancy.
- Maintenance Plans are SSIS packages.
- DBCC CHECKDB is the only way to check entire database for corruption.

## Card 3: Manage Azure PaaS Tasks Using Automation

### Elastic Jobs (Azure SQL Database)
- Scheduled T-SQL execution across multiple databases — similar to SQL Agent but T-SQL only.
- **Components:**
  - **Elastic Job Agent:** Azure resource for running/managing jobs.
  - **Job Database:** Dedicated database (S1 or higher recommended).
  - **Target Group:** Collection of servers, elastic pools, or single databases.
  - **Job:** One or more T-SQL scripts (job steps).
- **Target types:**
  - Server/Elastic Pool: need credential in **master** database to enumerate databases.
  - Single database: only database-level credential needed.
- **Credentials:** Least privileges necessary to perform job step.
- **Idempotent scripts required** — same script can run multiple times without errors.
- cmdlets: `New-AzSqlElasticJobTargetGroup`, `Add-AzSqlElasticJobTarget`, `New-AzSqlElasticJob`, `Add-AzSqlElasticJobStep`, `Start-AzSqlElasticJob`.
- **Use cases:** Schema changes, data movement, telemetry collection, maintenance across many databases.
- **Monitoring:** Azure portal, PowerShell (`Get-AzSqlElasticJobExecution`), T-SQL (`jobs.job_executions` view).
- Automatic retry on failure.

### Azure Automation
- Process automation, configuration management, RBAC/Entra ID integration.
- **Components:**
  - **Runbooks:** PowerShell or Python scripts (Graphical, PowerShell Workflow, PowerShell, Python).
  - **Modules:** Import required PowerShell modules (e.g., Az.SQL, Az.Accounts).
  - **Credentials:** Store sensitive info for runbook use.
  - **Schedules:** Trigger runbooks at specific times.
- **System-managed identity:** Use `Connect-AzAccount -Identity` in runbooks. Must enable appropriate RBAC.
- **Hybrid runbooks:** Manage on-premises or Azure VMs (e.g., start VM, backup SQL, shut down).
- **Runbooks are restartable** — if interrupted, restart from beginning.
- **PowerShell runbooks** most common for Azure SQL management.
- **Activity log:** Records who/what started a runbook. Query via `Get-AzLog`.

### Azure Policy
- Governance for Azure resources: region limitations, naming standards, resource sizes.
- Applied at: Management Groups, Subscriptions, Resource Groups.
- Can be grouped into **initiatives** for broader application.
- **Resource tags:** Key-value pairs. Up to **15 tags** per resource.
  - View in portal, filter with PowerShell/Azure CLI (like WHERE clause).
  - Included in billing info — useful for cost center chargebacks.
  - **Stored as plain text** — never store sensitive values.
- Tags can be applied at subscription, resource group, or individual resource level.

### Logic Apps
- Cloud-based platform for automated workflows — prebuilt connectors (SQL Server, Office 365, etc.).
- **SQL Server Connector:** Supported editions: SQL Server, Azure SQL DB, Azure SQL MI.
- **Triggers:** `When an item is created` (returns only 1 row). Must add other actions to process data.
- **Actions:** Get row, Insert row, Delete data, Run stored procedure, Execute Query.
- **Built-in connector (Standard workflows):** No triggers, only Execute Query action.
- **Connection string:** Available in Azure portal under database connection strings.
- **Use cases:** Send email on file upload, route customer orders, move files from SFTP to Storage, monitor tweets.

### Monitoring Automated Tasks
- **Runbook monitoring:** Check progress via database/storage account/shared file. Runbook should check last action before proceeding.
- **Alerts:** Metric alerts on runbook execution (e.g., Total Jobs > 10). Define action groups (email, webhook, runbook trigger).
- **Activity log:** Who started a runbook. `Get-AzLog` with filter for `Microsoft.Automation/automationAccounts/jobs/write`.
- **Log Analytics:** Forward diagnostic logs from Automation Account to Log Analytics workspace. Requires Diagnostic settings configuration first.
- **Elastic Jobs:** Executions logged, automatic retry. Monitor via portal, PowerShell, or T-SQL (`jobs.job_executions`).

### Exam Gotchas
- Elastic Jobs are **T-SQL only** — unlike SQL Agent. Available for Azure SQL DB.
- Elastic Jobs auto-retry on failure. Scripts must be idempotent.
- Job database for Elastic Jobs: S1 or higher recommended.
- Target server/elastic pool needs credential in **master** database.
- Azure Automation runbooks restart from beginning if interrupted.
- **System-managed identity** (`Connect-AzAccount -Identity`) needs RBAC permissions on Automation account.
- Tags: up to **15** per resource. Stored as **plain text** — no sensitive values.
- Azure Policy for governance (regions, naming, sizes). Can block deployment.
- Azure CLI cannot deploy remote Bicep files — must transpile to JSON.
- Logic Apps SQL connector: triggers return only 1 row. Built-in connector has no triggers.
- Runbooks use modules — import Az.SQL for SQL cmdlets.
- Log Analytics for Automation requires **Diagnostic settings** to be configured first.
