# Module 6: High Availability, Disaster Recovery & Backup/Restore

---

## Card 1: HADR Strategies & Options

### RTO and RPO
- **RTO (Recovery Time Objective):** Max time to bring resources online after outage. Defined at component + application level; overall RTO = slowest component.
- **RPO (Recovery Point Objective):** Max acceptable data loss (point in time to recover to). Driven by business requirements, not technology.
- Cost of downtime should justify HADR investment. RTO/RPO documented and periodically revised.
- Separate RTO/RPO for HA (local, seconds) vs DR (cross-region, hours).

### IaaS HADR Features
| Feature | Protection Level | Description |
|---------|-----------------|-------------|
| **Always On FCI** | Instance | Shared storage, full stop/start on failover, no data loss, requires WSFC/Pacemaker, AD DS + DNS. SQL Std = 2 nodes. |
| **Always On AG** | Database | Database-level, each replica has own copy, no shared storage, listener abstraction. Std = 1 DB, 2 replicas. Ent = multi-DB, 9 replicas. |
| **Log Shipping** | Database | Backup/copy/restore, simplest method, no native abstraction, some data loss on unplanned failover. |

### Azure IaaS Availability Features
- **Availability Sets:** Anti-affinity within single datacenter. 3 fault domains (FD) + up to 20 update domains (UD). 99.95% SLA. Cannot combine with AZ.
- **Availability Zones:** Separate datacenters within region, 3 zones. 99.99% SLA. Round-trip latency typically <1ms. Cannot combine with AS.
- **Azure Site Recovery:** VM-level replication to another region. Crash-consistent every 5 min. App-consistent configurable. RTO ~2 hours. Use for DR when SQL features not deployable.

### PaaS HADR (SQL DB & MI)
- **Built-in HA:** 99.99% SLA. ADR (Accelerated Database Recovery) on by default, can't be disabled. Auto page repair.
- **Active Geo-Replication (SQL DB only):** Async readable secondary in another region. Manual failover. Same service tier required. Cross-subscription available programmatically.
- **Auto-Failover Groups (SQL DB & MI):** AG-like listeners (read-write + read-only). Automatic failover (can disable). GracePeriodWithDataLossHours (default 1 hour). MI supports only one failover group. Seeding creates database on secondary.

### Hybrid Solutions
- IaaS-based (PaaS limited). AG secondary replica in Azure. Requires AD DS + DNS + sufficient bandwidth (ExpressRoute or S2S VPN).
- Transactional replication from on-prem publisher to MI subscriber (not reverse).

### Exam Gotchas
- FCI = instance-level, full stop/start, **no data loss**, requires shared storage + AD DS + DNS.
- AG = database-level, **no shared storage**, listener abstraction, secondary replicas readable (Enterprise).
- Availability Sets and Availability Zones **cannot be combined**.
- Azure Site Recovery is **not SQL Server-aware** — may not meet RPO for transactional DBs.
- Active Geo-Replication: SQL DB only. SQL MI must use auto-failover groups.
- MI supports **one auto-failover group** only.
- GracePeriodWithDataLossHours default = 1 hour. Higher value = less data loss but longer wait.
- DB state cannot be set to OFFLINE or EMERGENCY in PaaS.
- ADR is **on by default and cannot be turned off** in Azure SQL.
- Read-only listener disabled by default after failover — configurable.
- Cross-subscription geo-replication: programmatic only.

## Card 2: Implement IaaS & PaaS HADR

### WSFC in Azure
- **Cloud witness** recommended (WS 2016+), especially multi-region/hybrid.
- **DTC/MSDTC** requires shared disk if AG/FCI uses it.
- **Workgroup Cluster** (WS 2016+): AG only (no FCI), no AD DS needed, DNS required.
- **IP address:** Must be configured in Azure, not inside VM. Inside VM shows DHCP — expected.
- **Create WSFC:** Use PowerShell `New-Cluster` with `-StaticAddress` (wizard fails for FCIs/AGs due to DHCP).
- **Distributed Network Name (DNN):** Default in WS 2019+ for WSFC name. Replaces VNN for FCI — no Azure Load Balancer needed.
- `Test-Cluster` validates configuration. Warnings acceptable if expected; errors must be resolved.

### AG Configuration in Azure
- **Enable:** `Enable-SqlAlwaysOn` or SQL Server Configuration Manager — requires SQL restart.
- **Internal Load Balancer (ILB):** Required for listener connectivity. Standard LB needed for Availability Zones. Each listener IP needs unique **probe port** (high port like 59999).
- Multi-subnet AG: ILB per subnet/region.
- **Distributed AG** (Enterprise, SQL 2016+): AG of AGs. Global primary + forwarder. No WSFC needed between AGs. Each AG maintains own quorum/witness.

### Azure Site Recovery Details
- **Mobility extension** installed on VM. Changes sent continuously.
- Crash-consistent: every 5 min. App-consistent: configurable (VSS snapshots — can freeze SQL I/O).
- Multi-VM consistency: groups VMs for shared recovery points — affects performance.
- **Test failover** without impacting production.
- After failover, replica VMs are **not protected** — must be reprotected.
- Can protect against ransomware (roll back to pre-infection point).

### Monitoring Availability
- **Azure Status:** Dashboard of service problems in all global regions. RSS feed available.
- **Azure Service Health:** Problems, planned maintenance, advisories, history. Alerts via email/SMS.
- **Resource Health:** View reasons for instance/database unavailability (Azure portal or REST API).
- `sys.dm_database_replica_states`: Check replica status for BC service tier.
- `az sql mi list` / `az sql db list`: CLI status.
- `Get-AzSQLDatabase`: PowerShell status.
- **System Center Management Pack** for Azure SQL monitoring.

### Exam Gotchas
- WSFC wizard **cannot be used** in Azure for FCIs/AGs (use PowerShell `New-Cluster`).
- DNN replaces VNN for FCI in WS 2019+ — **no Load Balancer needed** for FCI with DNN.
- ILB required for AG listener. Standard LB required for Availability Zones.
- Probe port: unique high port per listener IP. Must configure after listener creation.
- Distributed AG = AG of AGs. No WSFC between them. Enterprise only, SQL 2016+.
- ASR mobility extension on VM. Crash-consistent = 5 min. App-consistent = configurable.
- Multi-VM consistency affects performance — only enable if VMs must restore together.
- ASR failover: replica VMs **unprotected** after failover — must reprotect.
- Warnings in cluster validation acceptable if expected; errors must all be resolved.

## Card 3: Back Up and Restore Databases

### Backup Types (IaaS)
- **Full:** Copies all pages. Restores to backup point alone. With NORECOVERY/STANDBY allows more backups.
- **Differential:** Pages changed since last full backup. Requires matching full backup.
- **Transaction Log:** Granular PITR, clears log, manages log size. Can be every 30s. Requires FULL recovery model.
- **Recovery Models:** FULL (all backup types), BULK_LOGGED (minimal logging for bulk ops), SIMPLE (no log backups, no PITR). FULL is default for most production DBs.
- **COPY_ONLY:** Independent of log chain — doesn't break sequence of differential/log backups.

### Backup to URL (IaaS)
- Requires Azure Storage account + container.
- Path: `https://ACCOUNTNAME.blob.core.windows.net/ContainerName/File.bak`.
- **Authentication:** Storage account + access key (page blob) or **Shared Access Signature** (block blob — preferred from SQL 2016+, cheaper, better security).
- Block blob only from SQL 2016+.
- **Automated backups** via SQL Server IaaS Agent Extension: configures backup schedule + retention. Windows-only. **Do not** combine with instance-level log backups (breaks log chain).

### Azure Backup for SQL VM
- SQL Server-aware (application-consistent VSS backups). Restores full VM.
- If snapshot delays cause failures: set `USEVSSCOPYBACKUP` registry key.
- **Best practice:** Use only one backup method for IaaS. Combining guest-level + Azure-level log backups breaks the log chain.

### Backup/Restore for PaaS (SQL DB & MI)
- **Automatic backups:** Full weekly + Differential every 12h + Log every 5-10 min. RA-GRS blobs (paired region).
- **PITR retention:** Default 7 days, configurable up to 35 days. LTR up to 10 years.
- **Restore:** Creates a **new database** (cannot restore over existing). Deleted database can be restored to last available point.
- **Server deletion:** All backups deleted with server, **no recovery possible**.
- **MI-only:** COPY_ONLY backup to URL (`BACKUP DATABASE ... TO URL ... WITH COPY_ONLY`). T-SQL RESTORE from URL. Cannot restore MI backups to SQL DB.
- **ADR:** Enabled by default, cannot be disabled. Speeds recovery of long-running transactions.

### Exam Gotchas
- Restore PaaS database = **new database** (cannot overwrite existing). Must drop or rename first.
- Server deletion = all backups gone permanently (PaaS).
- COPY_ONLY backup: **MI only** (not SQL DB). Must be COPY_ONLY since MI manages log chain.
- ADR on by default in all Azure SQL — **cannot be disabled**.
- Block blob only from SQL 2016+ (use SAS). Page blob with access key deprecated.
- SIMPLE recovery model = no log backups, no PITR.
- Automated backups (IaaS Agent) = Windows-only. Don't combine with instance-level log backups.
- PaaS PITR: default 7 days, max 35 days. LTR up to 10 years.
- System databases: master/msdb — don't restore across instances.
- Restore flow: Full → most recent Diff → Logs since Diff (requires NORECOVERY).
