## Card 1: Query Performance Optimization

### Query Processing & Execution Plans
- SQL Server uses a **cost-based query optimizer** — calculates cost for multiple plans using statistics, selects lowest cost.
- **Query processing flow:** Parse → Algebrizer (binding) → Check plan cache (by `query_hash`) → Optimize → Execute.
- **Plan cache** stores execution plans; identified by hash of T-SQL text. Memory grant allocated based on row estimates.
- **Three plan types:**
  - **Estimated:** Generated by optimizer, no execution. `SET SHOWPLAN_ALL ON`. No results returned.
  - **Actual:** Includes runtime stats (actual row counts, CPU, duration). `SET STATISTICS PROFILE ON`. Query executes.
  - **Live Query Statistics:** Animated, refreshes every second, shows row flow through operators. Graphical only.
- Execution plan flow: **right to left, top to bottom**. Arrow width = estimated rows. Operator cost is % of total.

### Lightweight Query Profiling
- Legacy profiling: up to **75% overhead**. Lightweight profiling: max **~2% overhead**.
- Enabled by default in SQL Server 2019, Azure SQL DB, Azure SQL MI.
- Use `OPTION(USE HINT ('QUERY_PLAN_PROFILE'))` for query-level profiling.
- `LAST_QUERY_PLAN_STATS` DB scoped config or trace flag 2451 to capture last actual plan via `sys.dm_exec_query_plan_stats`.

### Query Store
- Per-database feature, **enabled by default in Azure SQL DB**.
- Three stores: **Plan store**, **Runtime stats store**, **Wait stats store**.
- Enable: `ALTER DATABASE ... SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE)`.
- Key views: Regressed Queries, Overall Resource Consumption, Top Resource Consuming Queries, Queries With Forced Plans, Queries With High Variation, Query Wait Statistics, Tracking Query.
- Plan forcing via SSMS or `sp_query_store_force_plan @query_id, @plan_id`.
- Automatic plan correction (`FORCE_LAST_GOOD_PLAN`): enabled by default for new Azure SQL DB.

### SARGability & Anti-Patterns
- **SARGable predicates** allow index seeks. Non-SARGable: `LIKE '%term'`, functions on columns (`LEFT(city,1) = 'M'`), implicit conversions.
- **Missing indexes:** Look for Clustered Index Scan or Nonclustered Index Seek + Key Lookup in plan.
- Missing index DMV: `sys.dm_db_missing_index_details`.
- **Parameter sniffing:** First parameter value shapes the plan. Solutions: `RECOMPILE` hint, `OPTIMIZE FOR UNKNOWN`, conditional recompile.

### Blocking, Locking & Deadlocking
- **Lock escalation:** >5,000 rows on a single object → single table lock.
- **Deadlocking:** Two transactions each hold locks the other needs. SQL Server kills the **deadlock victim** (least work to roll back).
- Deadlocks recorded in `system_health` extended event session (enabled by default).
- Row versioning isolation levels prevent readers from blocking writers.

### Exam Gotchas
- Estimated plans do NOT execute the query. Actual plans execute and show runtime stats.
- Live Query Statistics is **graphical only** (animated). Refreshes every 1 second.
- Lightweight profiling: ~2% overhead vs legacy 75%. Default in SQL 2019+ and Azure SQL.
- Lock escalation threshold: **5,000 rows** on a single object.
- Deadlock victim = transaction with **least work to roll back**.
- `QUERY_PLAN_PROFILE` hint generates a `query_plan_profile` extended event.
- Query Store enabled by default in Azure SQL DB. Must enable in SQL Server.
- `sys.dm_db_resource_stats` for Azure SQL DB — snapshot every **15 seconds**.
- Missing index DMVs are starting points — don't create all suggested indexes blindly.

## Card 2: Performance-based Database Design

### Normalization
| Form | Requirement |
|------|-------------|
| **1NF** | Separate table per entity, eliminate repeating groups, primary key |
| **2NF** | All attributes depend on **complete** composite key (not partial) |
| **3NF** | No transitive dependencies (nonkey columns don't depend on other nonkey columns) |
| **Denormalization** | Tradeoff: fewer joins (better read performance) vs update anomalies |

### Star vs Snowflake Schema
- **Star schema:** Denormalized dimensions, central fact table. Fewer joins, faster queries. Preferred for data warehouses.
- **Snowflake schema:** Normalized dimensions. Saves storage but requires more joins (complexity/performance tradeoff).

### Data Type Selection
- Choose smallest appropriate data type to reduce storage and improve query performance.
- **Implicit conversions** can cause index scans instead of seeks — costly.
- Explicit conversion via `CAST` or `CONVERT` gives you control. Some conversions are not possible (date → bit).

### Index Design
| Index Type | Characteristics |
|------------|----------------|
| **Clustered** | Sorted order (logical), table data itself, one per table. Keep key narrow, unique, frequently used for sorting. |
| **Nonclustered** | Separate structure, key + pointer to row. Can add included columns to cover queries. Multiple per table. |
| **Filtered** | `WHERE` clause on index, ideal for columns where many rows share same value (bit columns). |
| **Unique** | No duplicate key values. Auto-created for PRIMARY KEY and UNIQUE constraints. |
| **Columnstore** | Column-based storage, batch execution mode (~900 rows at a time). Best for analytic/aggregation queries. Bulk load min: **102,400 rows** into compressed rowgroups. Smaller loads go to **delta store** (b-tree), moved async by **tuple mover**. Nonclustered columstore for unsupported types (XML, CLR, sql_variant). |

### Columnstore Details
- **Rowgroups:** 102,400 to ~1,024,000 rows each. Fuller rowgroups = more efficient scans.
- **Delta store:** B-tree structure for small loads (<102,400 rows). Affects read performance.
- **Tuple mover:** Async process moves delta store to compressed columnstore.
- `REORGANIZE` with `COMPRESS_ALL_ROW_GROUPS` forces delta into columnstore.
- Batch mode: up to **5x performance improvement** for analytical queries.
- Augment with b-tree nonclustered index for singleton lookups.

### Indexing Best Practices
- Understand workload (read vs write heavy). Fewer indexes for heavy writes.
- Evaluate existing usage: `sys.dm_db_index_operational_stats`, `sys.dm_db_index_usage_stats`.
- Leading column should be **selective** and used in WHERE clauses.
- Equality columns before inequality columns in composite index.
- Test in nonproduction — account for hardware differences.
- Save index code in source control before dropping.
- **Resumable index** (SQL 2017+): Pause/resume online index operations. Check status via `sys.index_resumable_operations`. Only supported with **ONLINE** operations.

### Exam Gotchas
- Clustered index = table data; only one per table. Heap = no clustered index.
- Columnstore bulk load minimum: **102,400 rows**. Below that goes to delta store.
- Resumable index only supported with **ONLINE=ON**.
- Nonclustered columnstore needed for unsupported types (XML, CLR, sql_variant, ntext, text, image).
- Batch mode processes ~900 rows at a time. Up to 5x improvement for analytical queries.
- `sys.index_resumable_operations` shows current execution status of resumable index builds.
- Filtered indexes are ideal for bit columns with skewed distribution (e.g., `WHERE CurrentFlag = 1`).

## Card 3: Evaluate Performance Improvements

### Wait Statistics
- Three types:
  - **Resource waits:** Thread waiting for resource in use (locks, latches, disk I/O).
  - **Queue waits:** Thread idle, waiting for work (deadlock monitoring, cleanup).
  - **External waits:** Waiting on external process (linked server, network).
- Query: `sys.dm_os_wait_stats` (SQL Server/MI), `sys.dm_db_wait_stats` (Azure SQL DB).
- `sys.dm_exec_session_wait_stats` — active session waits.
- Data persisted from instance startup; can be cleared.

### Common Wait Types
| Wait Type | Indication |
|-----------|------------|
| `RESOURCE_SEMAPHORE` | Queries waiting for memory — excessive memory grants, out-of-date stats, missing indexes |
| `LCK_M_X` | Blocking — change to READ COMMITTED SNAPSHOT, optimize indexes, improve transaction management |
| `PAGEIOLATCH_SH` | Storage performance issues or missing indexes (scanning too much data) |
| `SOS_SCHEDULER_YIELD` | High CPU utilization — large scans, missing indexes |
| `CXPACKET` | Parallelism configuration — lower MAXDOP, increase cost threshold for parallelism |
| `PAGEIOLATCH_UP` (on 2:1:1) | TempDB contention — add TempDB files (one per core, up to 8) |
| `LOG_RATE_GOVERNOR` | Azure SQL DB log rate governance |
| `POOL_LOG_RATE_GOVERNOR` | Elastic Pool log rate governance |
| `INSTANCE_LOG_GOVERNOR` | SQL MI log rate governance |
| `HADR_SYNC_COMMIT` | Business Critical tier — expected, uses AG technology |
| RBIO* waits | Hyperscale page server reads |

### Index Tuning Approach
1. Evaluate existing usage: `sys.dm_db_index_operational_stats`, `sys.dm_db_index_usage_stats`
2. Eliminate unused/duplicate indexes (carefully — some used monthly/quarterly)
3. Review expensive queries via Query Store or Extended Events
4. Create indexes in nonproduction, test, account for hardware differences
5. Implement via change control. Save index code before dropping

### Query Hints
| Hint | Purpose |
|------|---------|
| `MAXDOP <n>` | Overrides server/DB max degree of parallelism |
| `RECOMPILE` | New plan each execution, not cached |
| `OPTIMIZE FOR (@var = value)` | Use specified value for plan compilation |
| `OPTIMIZE FOR UNKNOWN` | Don't sniff parameters, use histogram averages |
| `FAST <n>` | Optimize for first `n` rows |
| `{LOOP\|MERGE\|HASH} JOIN` | Force specific join type |
| `USE PLAN` | Use specified XML plan |

### Query Store Hints
- Shape query plans **without modifying application code**.
- Use `sp_query_store_set_hints @query_id, @query_hints`.
- Identify `query_id` via Query Store catalog views or Query Performance Insight.
- Use cases: recompile, limit MAXDOP, force hash join, use compat level 110 for specific query.

### Performance Scenarios (Running vs Waiting)
- **Running (High CPU):** Use Query Store → Top Consuming Resources, `sys.dm_exec_requests` (state=RUNNABLE, wait=SOS_SCHEDULER_YIELD), `sys.dm_exec_query_stats`, `sys.dm_exec_procedure_stats`.
- **Waiting:** Use `sys.dm_os_wait_stats`, `sys.dm_exec_requests` (specific wait types), `sys.dm_os_waiting_tasks`, Query Store wait reports.

### Azure SQL-Specific DMVs
| DMV | Purpose |
|-----|---------|
| `sys.dm_db_resource_stats` | Azure SQL DB — CPU, memory, I/O every **15 seconds** |
| `sys.server_resource_stats` | SQL MI — same behavior as above |
| `sys.dm_user_db_resource_governance` | Azure SQL DB — actual config/capacity settings |
| `sys.dm_instance_resource_governance` | SQL MI — same as above for MI |

### Exam Gotchas
- `sys.dm_db_resource_stats` snapshots every **15 seconds** (Azure SQL DB only).
- `sys.server_resource_stats` for SQL Managed Instance.
- `CXPACKET` can indicate poor parallelism config — before SQL 2019, MAXDOP default = all CPUs, cost threshold = 5.
- `PAGEIOLATCH_UP` on page 2:1:1 = TempDB PFS page contention — add files.
- Query Store hints (`sp_query_store_set_hints`) do NOT require modifying application code.
- Wait stats from instance startup; `sys.dm_os_waiting_tasks` shows live waits.
- `HADR_SYNC_COMMIT` is normal for Business Critical tier (uses AG technology).
- Log governance wait types: `LOG_RATE_GOVERNOR` (SQL DB), `POOL_LOG_RATE_GOVERNOR` (elastic pool), `INSTANCE_LOG_GOVERNOR` (MI).
