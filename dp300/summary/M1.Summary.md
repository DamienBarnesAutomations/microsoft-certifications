# Module 1: Azure SQL Platform Options, Deployment & Migration

---

## Card 1: Azure SQL Platform Options (IaaS vs PaaS)

### What It Is
Microsoft offers three primary SQL Server-based options in Azure, spanning Infrastructure as a Service (IaaS) and Platform as a Service (PaaS). The choice depends on control needs, compatibility requirements, and management overhead tolerance.

### IaaS: SQL Server on Azure VM
Full control over OS and SQL Server — you manage patching, configuration, and backups. Best for:
- Applications requiring older SQL Server versions for vendor support
- Need for additional SQL Server services (SSIS, SSRS, SSAS) on the same machine
- Applications incompatible with PaaS (requires CLR, cross-database queries, or OS-level access)
- SQL Server IaaS Agent Extension provides automated backup, patching, Key Vault integration, Defender for Cloud, and view disk utilization
- **Licensing:** Pay-as-you-go (PAYG) via Marketplace images, Bring Your Own License (BYOL), Azure Hybrid Benefit (AHB) for existing SA licenses, Reserved Instances (1-3 year commitment)
- **VM Families:** General Purpose (balanced), Compute Optimized (high CPU), Memory Optimized (database workloads, up to 4 TB RAM), Storage Optimized (NVMe, ephemeral), GPU, FPGA Accelerated, High Performance Compute
- **Storage:** Premium SSD or Ultra Disk for data/log files (5-10ms latency); Standard for backups; separate pools for data files (read-cache on), log files (no cache), TempDB (temporary disk or own pool)
- **HA:** Availability Zones (99.99%, 3 zones per region), Availability Sets (99.95%, spread across racks), Always On Availability Groups (up to 9 replicas, sync/async, unit=DB group), Failover Cluster Instance (unit=instance, requires shared storage)
- **DR:** Native backups to URL, Azure Backup, Azure Site Recovery

### PaaS: Azure SQL Database
Fully managed database service — no OS/SQL patching, automated backups, built-in HA. Best for:
- New cloud-native application development
- Intermittent/unpredictable usage (serverless tier)
- Simplified deployment and management
- Scaling needs up to 100 TB (Hyperscale)
- **Purchasing Models:** DTU (bundled compute+storage, Basic/Standard/Premium tiers), vCore (decoupled compute/storage, General Purpose/Business Critical/Hyperscale)
- **Deployment:** Single database (dedicated resources) or Elastic Pool (shared resources across databases, cost-effective for multitenant)
- **Serverless:** Autoscaling compute, autopause (1hr-7day delay), billed per second; only storage billed when paused; available in General Purpose and Hyperscale (auto-pause only in GP)
- **Backups:** Automated — Full (weekly), Differential (12h), Log (5-10 min); retention 7-35 days (default 7); LTR up to 10 years; geo-redundant by default (RA-GRS); manual COPY_ONLY backup NOT supported
- **Restore:** PITR (1-35 day window), geo-restore; cannot restore over existing DB; no T-SQL RESTORE command
- **Geo-replication:** Up to 4 readable async secondaries; failover groups provide read-write and read-only listener endpoints

### PaaS: Azure SQL Managed Instance
Full SQL Server instance in PaaS form — near 100% compatibility with on-premises SQL Server. Best for:
- Lift-and-shift migrations without application changes
- Need for instance-scoped features (SQL Agent, CLR, cross-database queries, system DBs, Service Broker)
- Up to 100 databases per instance
- **Service Tiers:** General Purpose (standard storage, higher latency), Business Critical (local SSD, lowest latency, In-Memory OLTP, readable secondary)
- **Network:** Deployed in dedicated VNet subnet; private IP only (requires VPN/ExpressRoute for on-premises); public endpoint optional (port 3342, requires SoD between DBA and NetAdmin)
- **Managed Instance Link:** Distributed Availability Group (DAG) — per-database replication between on-prem SQL Server and MI; one-way (2016/2019) or two-way (2022); supports DR, read-scale, automated backups; cutover in seconds
- **Instance Pools:** Pre-provision resources for smaller instances; fast deployment (~10 min); cost-efficient
- **Backups:** Same schedule as SQL DB; supports COPY_ONLY backups to URL; can RESTORE T-SQL (from URL only)
- **HA/DR:** Built-in 99.99% SLA; auto-failover groups (entire instance, one secondary in paired region); DNS zone matching required

### Decision Factors
| Factor | IaaS (VM) | SQL Database | SQL Managed Instance |
|--------|-----------|-------------|---------------------|
| Control | Full OS+SQL | DB only | Instance level |
| Compatibility | Full SQL Server | ~95% (no Agent, CLR) | ~100% |
| Management | You patch OS+SQL | Fully managed | Fully managed |
| Migration | Lift-and-shift | May need app changes | Lift-and-shift |
| Best for | Legacy apps, full control | New apps, simple migration | Existing apps, minimal change |

### Exam Gotchas
- **SQL Database and SQL Managed Instance share the same base code** but differ in instance-scoped features (Agent, CLR, cross-DB queries are MI-only)
- **SQL Database does NOT support:** SQL Agent (use elastic jobs), T-SQL RESTORE, COPY_ONLY backups, cross-database queries natively (use elastic query), Machine Learning Services
- **Managed Instance does NOT support:** DTU purchasing model, elastic pools, elastic jobs, Hyperscale tier
- **Serverless autopause:** min 60 min, max 7 days; can be disabled; only GP tier supports auto-pause
- **Hyperscale:** 100 TB+ max, fast backups (file snapshots), independent compute/storage scaling, read-scale replicas (ApplicationIntent=ReadOnly), CANNOT revert to standard tier
- **Elastic pools:** for multitenant SaaS with low avg utilization; resources shared; monitor for noisy neighbors
- **Azure Hybrid Benefit (AHB):** 1 EA core = 1 vCore Business Critical, or 8 vCores General Purpose; 1 Std core = 1 vCore General Purpose; up to 40% savings
- **Reserved Instances:** 1-3 year commitment, monthly billing, no upfront required
- **Availability Zones vs Sets:** Zones = different data centers (99.99%), Sets = different racks (99.95%)
- **Always On AG unit of failover = database group; FCI unit = entire instance**

## Card 2: IaaS Deployment (SQL Server on Azure VM)

### What It Is
SQL Server running on Azure Virtual Machines provides the most control and the highest compatibility with on-premises SQL Server deployments. The Azure platform manages the hypervisor and hardware, while you manage the VM, OS, SQL Server, and all configuration.

### SQL Server IaaS Agent Extension
Automatically installed when deploying from Azure Marketplace. Provides:
- Automated Backup (configure scheduling, retention)
- Automated Patching (maintenance windows)
- Azure Key Vault Integration (for encryption keys)
- Microsoft Defender for Cloud integration
- View Disk Utilization in portal
- Flexible Licensing (toggle between PAYG and BYOL/AHB without redeployment)
- Flexible Version/ Edition change
- SQL Best Practices Assessment

### Storage Best Practices
| Component | Recommendation |
|-----------|---------------|
| Data files | Premium SSD or Ultra Disk; separate pool with read-caching enabled |
| Transaction log | Separate pool from data files; NO read-caching |
| TempDB | Temporary disk (D:) for low latency, or own pool |
| Backups | Can use Standard storage |
| OS disk | Minimum needed; no database files here |
- Premium SSD: 5-10ms latency; Ultra Disk: sub-ms (1-2ms real-world)
- Use Storage Spaces to pool disks for increased IOPS and capacity
- Data compression: Page compression (72% fewer reads shown), Row compression (basic), Columnstore archival (XPRESS, for cold data)
- Table partitioning: partition function → partition scheme → table; enables partition elimination and targeted maintenance

### High Availability & Disaster Recovery
| Feature | Scope | Type | Distance | Notes |
|---------|-------|------|----------|-------|
| Availability Set | Single region | HA (racks) | Same DC | 99.95%, spread across fault/update domains |
| Availability Zone | Single region | HA (DCs) | Same region | 99.99%, 3 zones per region |
| Always On AG | Multi-VM | HA+DR | Same region or cross-region | Up to 9 replicas; sync (low latency) or async (geo); unit=DB group |
| FCI | Multi-VM | HA only | Single region | Unit=instance; requires shared storage (S2D or file share) |
| Azure Site Recovery | VM-level | DR | Cross-region | Block-level replication; RTO=RPO; best for stateless |
| Native Backups | DB-level | DR | Any | To URL (Blob Storage), GRS/RA-GRS for geo-redundancy |

### Licensing Options
| Model | Description |
|-------|-------------|
| PAYG | Deploy Marketplace image; pay per minute for SQL Server license + VM cost |
| BYOL | Existing SA license; deploy blank VM + manual SQL install or Deploy with AHB option |
| Azure Hybrid Benefit (AHB) | Apply existing Windows Server + SQL Server SA licenses to reduce costs |
| Reserved Instance | 1 or 3 year commitment; significant savings over PAYG; monthly billing |

### Exam Gotchas
- **Ephemeral storage** (temporary disk D:\) is NOT durable — data lost on reboot/maintenance; use only for TempDB, page files, swap
- **Ultra Disk** requires special configuration (different from Premium SSD deployment)
- **Always On AG synchronous commit** requires low latency between replicas (same region); cross-region = async
- **FCI is NOT a DR solution** — it provides HA only within a single region; needs AG or log shipping for DR
- **Azure Site Recovery for SQL Server** results in higher RPO (potential data loss); not recommended for transactional DBs without supplementary measures
- **Storage Spaces** pools disks to increase IOPS/striping; essential for production SQL Server workloads
- **Page compression** is superset of row compression — prefix + dictionary compression applied after row compression
- **sp_estimate_data_compression_savings** estimates space savings before implementing (does not support columnstore before SQL 2019)
- **Query Store, instant file initialization, lock pages in memory, optimized for adhoc workloads** — all recommended production settings

## Card 3: PaaS Deployment — Azure SQL Database

### What It Is
Azure SQL Database is a fully managed PaaS relational database service built on the SQL Server engine. It provides automatic backups, patching, high availability, and built-in intelligence. Available in single database and elastic pool deployment models with DTU or vCore purchasing.

### Purchasing & Service Tiers

**DTU Model** (bundled compute+storage):
- Basic: Light workloads, 2 GB max
- Standard: Moderate workloads, 250 GB max (S0-S3)
- Premium: Intensive workloads, 4 TB max (P1-P15), local SSD, In-Memory OLTP

**vCore Model** (decoupled compute/storage):
| Tier | Max Size | Storage | Latency | Compute | Features |
|------|----------|---------|---------|---------|----------|
| General Purpose | 4 TB | Premium storage (remote) | Higher | Provisioned or Serverless | Standard HA |
| Business Critical | 4 TB | Local SSD | Lowest | Provisioned | In-Memory OLTP, readable replica |
| Hyperscale | 100 TB+ | Premium storage | Varies | Provisioned | Fast snapshots, read-scale, unlimited size |

### Serverless Compute
- Autoscales between min/max vCores (min 0.5, max 16)
- Autopause delay: 1 hour to 7 days (or disabled)
- Billed per second for compute; only storage when paused
- Resume triggered by first connection attempt
- NOT compatible with: geo-replication, LTR backup, elastic jobs job DB, SQL Data Sync sync DB
- Auto-pause only available in General Purpose tier

### Deployment Models
| Model | Description | Best For |
|-------|-------------|----------|
| Single Database | Each DB has dedicated resources | Isolated apps, predictable workloads |
| Elastic Pool | Shared resource pool across DBs | Multitenant SaaS, low avg utilization |

### Backup & Restore
- **Automatic:** Full (weekly), Differential (12h), Log (5-10 min)
- **Default retention:** 7 days (configurable 1-35 days for vCore)
- **LTR:** Up to 10 years (disabled by default, weekly/monthly/yearly)
- **Geo-redundant:** RA-GRS by default; geo-restore to any Azure region
- **PITR:** Restore to any point within retention window; to same server only
- **Cannot restore over existing DB** — must drop or rename first
- **No T-SQL RESTORE** command (use portal, PowerShell, CLI, REST API)
- **No manual COPY_ONLY backups** (Managed Instance only)

### Geo-Replication & Failover Groups
- **Geo-replication:** Up to 4 readable async secondaries (same or different region); manual failover only
- **Failover Groups:** Built on geo-replication; provides read-write and read-only listener endpoints (no connection string changes on failover); automatic/manual failover

### Elastic Features
- **Elastic Query:** Run T-SQL across multiple databases (three/four-part names); supports vertical partitioning (different schemas) and horizontal partitioning/sharding (same schema)
- **Elastic Jobs:** SQL Agent replacement for SQL Database; runs T-SQL across multiple targets (databases, pools, shard maps); cross-subscription/region; parallel execution
- **Elastic Pools:** Shared resource pool; min/max DTU or vCore per database; scale pool up/down with slider; monitor per-DB utilization for noisy neighbors

### Automatic Tuning
- ML-based identification of index opportunities
- Creates indexes, drops unused/duplicate indexes, forces last good execution plan
- Tests indexes on a DB copy first before applying

### Hyperscale Details
- Independent scaling of compute and storage (storage auto-grows, no max)
- Instant backups (file snapshots) — not dependent on data size
- Fast restores in minutes regardless of size
- Multiple read-scale replicas (ApplicationIntent=ReadOnly)
- CANNOT revert to standard service tier after conversion
- Rapid scale up/down (seconds/minutes, not dependent on data volume)

### Exam Gotchas
- **Default backup retention:** 7 days; can increase to 35 days for vCore
- **Hyperscale CANNOT be reverted** to General Purpose or Business Critical
- **Serverless pause only in GP tier** — Hyperscale serverless exists but auto-pause is GP-only
- **Elastic jobs replace SQL Agent** for SQL Database; Managed Instance still has SQL Agent
- **Automatic tuning is enabled at server level** and inherited by databases; can disable per database
- **DTU model is simpler but less flexible** — storage bound to compute; vCore decouples them
- **Read-scale replicas in Business Critical:** one free readable secondary; Hyperscale can have more
- **Scaling operation ends with brief connection interruption** — implement retry logic
- **Firewall rules at server level** — can also set at database level with contained DB users

## Card 4: PaaS Deployment — Azure SQL Managed Instance

### What It Is
Azure SQL Managed Instance is a fully managed SQL Server instance in the cloud, offering near 100% compatibility with on-premises SQL Server. It provides the benefits of PaaS (auto backups, patching, HA) while preserving instance-scoped features needed for most existing applications.

### Key Features vs SQL Database
| Feature | SQL Database | SQL Managed Instance |
|---------|-------------|---------------------|
| SQL Agent | ❌ (elastic jobs) | ✅ |
| CLR | ❌ | ✅ |
| Cross-DB queries | ❌ (elastic query) | ✅ |
| System DB access | ❌ | ✅ (tempdb, msdb) |
| T-SQL RESTORE | ❌ | ✅ (from URL) |
| COPY_ONLY backup | ❌ | ✅ |
| Service Broker | ❌ | ✅ |
| Max databases | N/A | 100 |
| Max storage | 100 TB (Hyperscale) | 16 TB (BC) / 8 TB (GP) |
| DTU model | ✅ | ❌ |
| Elastic pools | ✅ | ❌ |
| Hyperscale | ✅ | ❌ |

### Service Tiers
| Tier | Storage | Latency | HA | Additional Features |
|------|---------|---------|-----|-------------------|
| General Purpose | Premium storage (remote) | Higher | Storage replication | Cost-effective |
| Business Critical | Local SSD | Lowest | Always On AG replicas | In-Memory OLTP, readable replica |

### Network & Connectivity
- **Deployed in dedicated VNet subnet** — private IP only by default
- **Public endpoint optional** — enable via PowerShell (DBA) + open port 3342 on NSG (NetAdmin); Separation of Duties required
- **On-premises connection:** VPN Gateway (P2S or S2S) or ExpressRoute
- **DNS Zone required** — must match between primary and secondary in failover groups

### Managed Instance Link
- Based on **Distributed Availability Groups (DAG)**
- **One link per database** (can have multiple links per instance)
- **One-way replication:** SQL Server 2016/2019
- **Two-way replication:** SQL Server 2022 (online failover, offline failback currently)
- **Hybrid uses:** DR (failover to cloud), offload read-only workloads, automated backups in Azure
- **Cutover in seconds** — best for minimal downtime scenarios
- **No SQL version/edition restrictions beyond 2016+ Enterprise/Standard/Developer

### Instance Pools
- Pre-provision compute resources shared across multiple instances
- Fast deployment (up to 10 min)
- All instances share same VM
- Cost-efficient for migrating small SQL Server instances

### Backups (Managed Instance Specific)
- Same automatic schedule as SQL Database (full weekly, diff 12h, log 5-10 min)
- **Supports COPY_ONLY backup to URL** (SQL Database does not)
- **Supports T-SQL RESTORE** from URL (but not local storage)
- Cannot overwrite existing database during restore
- Must disable TDE for user-initiated COPY_ONLY backups
- Restore supports: FILELISTONLY, HEADERONLY, LABELONLY, VERIFYONLY
- Cannot restore: backups with multiple log files, multiple backup sets, or In-Memory/FILESTREAM

### HA & DR
- **Built-in HA:** 99.99% SLA
- **General Purpose:** Storage replication-based HA
- **Business Critical:** Always On Availability Group replicas
- **Auto-failover groups:** Entire instance failover; single secondary in paired Azure region; read-write and read-only listener endpoints
- DNS zone must match between primary and secondary instances

### Exam Gotchas
- **SQL Agent exists in Managed Instance** — elastic jobs are NOT available
- **COPY_ONLY backup to URL** is NOT supported by SQL Database; Managed Instance only
- **T-SQL RESTORE** is available only in Managed Instance (not SQL Database)
- **Public endpoint port:** 3342 (not the standard 1433)
- **Instance pools** share same VM across multiple instances — good for small DB consolidation
- **Link feature uses DAG** (not log shipping); one link per database
- **DTU model is NOT supported** by Managed Instance — vCore only
- **Failover groups require matching DNS zones** between primary and secondary
- **Cross-DB queries work natively** in Managed Instance; SQL Database needs elastic query
- **Elastic pools do not exist in Managed Instance** — each instance has dedicated resources

## Card 5: Migration to Azure SQL

### What It Is
Migrating SQL Server workloads to Azure involves choosing between offline methods (downtime acceptable) and online methods (minimal downtime). The right migration path depends on your target platform (SQL Database vs Managed Instance) and business requirements for downtime tolerance.

### Assessment
Before migrating, assess source databases for compatibility:
- **Azure Migrate** — discovery and assessment tool
- **Data Migration Assistant (DMA)** — identify feature parity and blocking issues
- **Azure Arc-enabled SQL Server** — automatic weekly assessment; also supports trigger-on-demand; generates readiness reports with right-sized target recommendations

### Migration Modes

| Mode | Description | Downtime | Tools |
|------|-------------|----------|-------|
| Offline | DB is unavailable during migration | Full downtime | DMS, BACPAC, bcp, ADF, native backup/restore |
| Online | DB remains available during sync | Minimal | Transactional replication, Managed Instance link, LRS |

### Migration to Azure SQL Database

| Tool | Mode | Notes |
|------|------|-------|
| Azure Database Migration Service (DMS) | Offline | Use Azure CLI or PowerShell; supports table selection; recommended for large migrations |
| Transactional replication | Online | Only online method for SQL DB; push subscriber only; configure from SSMS/T-SQL (not portal) |
| BACPAC (SqlPackage) | Offline | Compressed file (metadata + data); faster than portal import; scale up target tier during import |
| BCP (Bulk Copy Program) | Offline | Table-level export/import; good for partial migration |
| Azure Data Factory | Offline | For data migration rather than full DB migration |
| Import Wizard (portal) | Offline | Simple UI; slower than SqlPackage |

**Key SQL Database Migration Considerations:**
- Schema must be deployed to target before data migration (DMS can handle this)
- Scale up target SKU during migration, scale down after
- Enable retry logic in applications (transient errors, min 5s first retry, exponential backoff to 60s max)
- If a SELECT fails with transient error, retry in a new connection
- Transactional replication is the ONLY online method for SQL Database
- Replication components: Publisher, Subscriber, Distributor, Article, Publication, Subscription

### Migration to Azure SQL Managed Instance

| Tool | Mode | Notes |
|------|------|-------|
| Managed Instance Link | Online | DAG-based; seconds cutover; SQL 2016+; best for business-critical; supports reverse migration |
| Log Replay Service (LRS) | Online | Log shipping tech; more control; 30-day limit; useful when DMS can't be used |
| Azure Arc | Online or Offline | Portal-based; unified assessment → target → migrate → monitor; built-in Copilot |
| Native backup/restore | Offline | Backup to URL, restore to MI; COPY_ONLY for user backups |
| Transactional replication | Online | MI can be publisher, distributor, or subscriber |
| BACPAC (SqlPackage) | Offline | NOT supported via portal; use SqlPackage utility directly |

**Choosing Between Link and LRS:**
| Factor | Managed Instance Link | LRS |
|--------|---------------------|-----|
| Cutover downtime | Seconds | Longer |
| Read during migration | ✅ | ❌ (restoring state) |
| SQL version | 2016+ | 2012+ |
| SQL edition | Enterprise, Standard, Developer | All editions |
| Network | VPN/private endpoint | Public endpoint OK |
| Duration | Unlimited | Max 30 days |
| Reverse migration | ✅ | ❌ |

### Performance Recommendations for Migration
- Monitor and mitigate source data file I/O latency
- Scale up target (Business Critical Gen5 8 vCore or Hyperscale recommended)
- Ensure adequate network bandwidth for max log ingestion rate
- Choose highest service tier during migration, scale down after
- Minimize distance between BACPAC files and target region
- Disable auto update/auto create statistics during migration
- Partition tables and indexes; drop indexed views; recreate after migration
- Rarely queried historical data → separate DB + elastic queries
- For DMS: up to 10 concurrent DB migrations per self-hosted IR; scale out IR for more concurrency

### Connectivity for Hybrid Scenarios
| Method | Security | Latency | Cost |
|--------|----------|---------|------|
| Point-to-Site VPN | Encrypted | Moderate | Low |
| Site-to-Site VPN | Encrypted | Moderate | Moderate |
| ExpressRoute | Private, not over internet | Lowest | Highest |

### Exam Gotchas
- **Transactional replication is the ONLY online migration for SQL Database** — all other methods are offline
- **Managed Instance Link uses DAG** (not log shipping like LRS)
- **LRS has a 30-day limit** — the job is automatically canceled after 30 days
- **COPY_ONLY backup only on Managed Instance**, not SQL Database
- **BACPAC import via portal NOT supported for Managed Instance** — use SqlPackage CLI
- **Remove database before restore** — cannot restore over existing DB in either SQL DB or MI
- **Link does NOT support Filestream/Filetable** — must verify source compatibility first
- **DMS recommended for large migrations** — use Azure CLI for automation and CI/CD integration
- **Migration statuses:** Preparing for copy → Copying → Copy finished → Rebuilding indexes → Succeeded
- **Retry logic required:** first retry after 5s, exponential backoff to 60s; new connection for SELECT retries
- **Azure Arc migration discovery runs automatically every weekend**; can trigger manually
