## Card 1: Performance Monitoring & Tuning

### Monitoring Tools
- **Azure Monitor:** Collects standard metrics (CPU, network, disk R/W) from Azure resources. Active data retained for **93 days**. Can archive to Azure Storage.
- **Azure Monitor Insights:** Extra data points (storage latency, available memory, disk capacity). Data stored in **Log Analytics workspace** (queried via KQL).
- **Performance Monitor (Perfmon):** Native Windows tool for OS and SQL Server counters. Can forward to Azure Monitor.
- **SQL VM Resource Provider:** View database/log file space, manage automated patching and storage configuration. Available for Marketplace-deployed SQL VMs.

### Critical Metrics
| Counter | What It Tells You |
|---------|------------------|
| `Processor(_Total)\% Processor Time` | Overall CPU utilization |
| `PhysicalDisk(_Total)\Avg. Disk sec/Read` and `Write` | Storage latency (should be <20ms, Premium SSD <10ms) |
| `System\Processor Queue Length` | CPU pressure if >0 |
| `SQLServer:Buffer Manager\Page life expectancy` | How long pages stay in memory; sudden drops indicate issues |
| `SQLServer:SQL Statistics\Batch Requests/sec` | How consistently busy the server is |
| `SQLServer:SQL Statistics\SQL Compilations/sec` | Plan compilation rate; recompiles may indicate memory pressure |
| `Paging File(_Total)\% Usage` | Should be near 0 for properly configured SQL Server |
| **Wait statistics** (`sys.dm_os_wait_stats`) | Identify bottlenecks by wait type |

### Metric Alerts
- **Static alerts:** Fixed threshold (e.g., CPU > 80%).
- **Dynamic Thresholds:** Learn historical behavior, detect seasonality, alert on abnormal patterns.
- **Action groups:** Automation Runbook, Azure Function, Email/SMS/Push/Voice, ITSM, Logic App, Webhook, Secure Webhook.

### Extended Events
- Lightweight monitoring system, successor to SQL Server Profiler.
- **Channels:** Admin (admin actions), Operational (common diagnostics), Analytic (high-volume performance), Debug (Microsoft support only).
- **Target types:**
  - Event Counter (synchronous) — counts occurrences, low overhead
  - Event File (asynchronous) — persists to file/blob
  - Ring Buffer (asynchronous) — in-memory, circular, not persisted
  - ETW (synchronous) — correlates SQL Server with Windows OS events
  - Histogram (asynchronous) — counts by event column/action
  - Event Pairing (asynchronous) — matches paired events (lock acquire/release)
- Filters apply to **a single field on a single event** — need separate filters per event.
- Can create sessions via SSMS wizard, templates, or T-SQL `CREATE EVENT SESSION`.
- Causality tracking adds GUID + sequence number to trace event order.

### Query Performance Insight
- Found in Azure SQL Database under Intelligent Performance.
- Filters: Long Running Queries, Top Resource Consuming Queries, Custom.
- Metrics: CPU, Data IO, Log IO, memory.
- Query IDs correlate to Query Store for deeper analysis.
- Does NOT show execution plans — use Query Store for that.

### Database Watcher (Preview)
- Designed specifically for Azure SQL Database and SQL Managed Instance.
- Collects monitoring data into a central data store (Azure Data Explorer or Real-Time Analytics in Fabric).
- Configurable targets, datasets, frequency, retention.
- Low latency: data collection/ingestion within seconds.
- Supports parameterized templates for common alert rules + custom alerts.

### Exam Gotchas
- Azure Monitor retains metrics for **93 days**; can archive to Azure Storage.
- `db_backupoperator` has no effect in Azure SQL Database.
- Extended Events filters apply to **a single field on a single event** — must configure per event.
- Most Extended Events targets are **asynchronous**; Event Counter and ETW are **synchronous**.
- Query Performance Insight does NOT show execution plans — use Query Store.
- Database Watcher stores data in Azure Data Explorer or Real-Time Analytics (Fabric).
- Wait statistics are available across all Azure SQL platforms.

## Card 2: Resource Configuration (Storage, VM, TempDB, Resource Governor)

### Azure Storage Types
- **Blob Storage:** Object-based, cold/hot/archive tiers. Used for SQL Server backups (BACKUP TO URL).
- **File Storage:** File share mountable inside VM. Used for FCI shared storage.
- **Disk Storage (Managed Disks):** Block storage for data/log files.

### Managed Disk Types
| Type | Use Case | Latency |
|------|----------|---------|
| Ultra Disk | Mission-critical, sub-ms latency needed | Sub-millisecond |
| Premium SSD | Most production workloads | Single-digit ms |
| Standard SSD | Dev/test, light IO | Predictable |
| Standard HDD | Backups, infrequent access | Highest |

### Storage Best Practices for SQL Server VMs
- Separate volumes for data files (read-caching ON) and log files (NO caching).
- Plan for **extra 20% IOPS/throughput** for workload peaks.
- Use **D: drive (local SSD)** for TempDB (recreated on restart, no data loss risk).
- Enable **instant file initialization**.
- Move trace/error log directories to data disks.
- **Striping with Storage Spaces:** Sums IOPS and volume across disks; do NOT configure redundancy (Azure provides 3x replication).
- Ultra Disk can scale IOPS, throughput, and max size independently on a single disk (no striping needed).

### Constrained Cores
- Reduce vCPU count while keeping full memory, storage, and I/O bandwidth.
- Good for workloads that need high memory but aren't CPU-intensive.
- Reduces SQL Server licensing costs.

### VM Resizing
- Requires restart. May require deallocation depending on source/target type.

### TempDB Configuration
- **Proportional fill:** SQL Server distributes data across files based on file size (not equally).
- **SQL Server:** Configures up to 8 files during setup; for high workloads, match number of CPUs.
- **Azure SQL Database:** Files scale with vCores (2 vCores = 4 files), max 16. NOT configurable via T-SQL. Maximum size scaled per vCores.
- **SQL Managed Instance:** Always 12 files, independent of vCores.
- TempDB always on local SSD in Azure SQL — I/O shouldn't be an issue.
- `MIXED_PAGE_ALLOCATION` = OFF, `AUTOGROW_ALL_FILES` = ON (default, not configurable).
- TempDB metadata optimization (SQL Server 2019) NOT available in Azure SQL.

### MAXDOP Configuration
- Higher MAXDOP = more parallel threads = faster but more memory pressure.
- Lower MAXDOP = less memory pressure, better storage efficiency.
- Configure via: `ALTER DATABASE SCOPED CONFIGURATION`, `sp_configure` (MI only), query hints, Resource Governor (MI only).

### Resource Governor
- Granular control over CPU, physical I/O, and memory for application requests.
- Available in SQL Server and Azure SQL Managed Instance. NOT available in Azure SQL Database.
- Components:
  - **Resource pools:** Represent physical resources. `internal` (can't restrict) and `default` pools always exist. Set min/max CPU%, memory%, IOPs per volume, NUMA affinity.
  - **Workload groups:** Container for session requests classified by classifier function. Associated with one resource pool.
  - **Classifier function:** Runs at connection time, returns workload group name. Returns NULL/default/nonexistent → goes to default group.
- Change to resource pools only affects **new sessions**, not in-progress ones (except external pools for ML Services).
- All pool settings except min/max CPU% are **hard limits**. Min/max CPU% only applies during contention.

### Exam Gotchas
- **Ultra Disk** scales IOPS/throughput/size independently — no striping needed.
- **Premium SSD** benefits from striping via Storage Spaces; don't configure redundancy (Azure handles it).
- Constrained cores reduce vCPU count while keeping full memory/I/O — reduces licensing cost.
- TempDB files in Azure SQL DB scale with vCores (max 16), MI always has 12.
- TempDB metadata optimization (SQL Server 2019) is NOT available in Azure SQL.
- Resource Governor is NOT available in Azure SQL Database — only SQL Server and Managed Instance.
- Resource pool changes only affect NEW sessions (except external pools).
- Classifier function runs at **connection time** — test for efficiency.
- MAXDOP can be configured via DB scoped config, sp_configure (MI), query hints, or Resource Governor (MI).

## Card 3: Database Optimization (Indexes, Statistics, Automatic Tuning, IQP)

### Index Maintenance
- **Fragmentation** occurs when logical page ordering doesn't match physical ordering.
- **Reorganize** (online, defrags leaf level, compacts per fillfactor): 5-30% fragmentation.
- **Rebuild** (online or offline, drops and recreates): >30% fragmentation. Online requires more space. Resumable rebuild available since SQL Server 2017.
- Rebuild updates statistics; reorganize does NOT.
- DMV for B-tree: `sys.dm_db_index_physical_stats`. For columnstore: `sys.dm_db_column_store_row_group_physical_stats`.

### Statistics
- Stored as BLOBs in user database. Contain data distribution info for cardinality estimation.
- **AUTO_CREATE_STATISTICS** = ON by default; query optimizer creates stats for indexed columns and query predicate columns.
- Consider creating manual statistics when: DTA suggests, query predicate has multiple columns not in same index, query selects subset of data, missing statistics detected.
- To view last updated: `sys.stats` + `sys.dm_db_stats_properties`.

### Maintenance Automation
| Platform | Tools |
|----------|-------|
| SQL Server on Azure VM | SQL Agent, Windows Task Scheduler |
| Azure SQL DB | Azure Automation runbooks, SQL Agent from Azure VM (remote), Elastic Jobs |
| Azure SQL MI | SQL Agent |

### Database Scoped Configuration
- `ALTER DATABASE SCOPED CONFIGURATION`: MAXDOP, Legacy Cardinality Estimation, Last Query Plan Stats (compat level 150 only), Optimize for Ad Hoc Workloads.
- `ALTER DATABASE`: Recovery model, automatic tuning, auto create/update stats, Query Store, snapshot isolation.
- **Compatibility level** controls query optimizer behavior. IQP features require compat level 140 or 150.

### Automatic Tuning (Azure SQL Database)
- **Automatic plan correction (`FORCE_LAST_GOOD_PLAN`):** When enabled, engine forces last known good plan when plan regression is detected. Plan reverts after 15 executions if not better. Check via `sys.dm_db_tuning_recommendations` and `sys.database_automatic_tuning_options`. Query Store must be enabled and in Read-Write mode.
- **Automatic index management:** Azure SQL DB only. Creates/drops indexes based on learned workload. Monitors resources to avoid degradation. If dropped index hurts performance, it's automatically recreated.
- Conditions for auto-plan correction: previous plan had higher error rate, estimated CPU gain >10 seconds, forced plan performs better.

### Intelligent Query Processing (Compat Level 150)
| Feature | Description |
|---------|-------------|
| **Adaptive Joins** | Defer join type (hash vs nested loops) based on actual rows, batch mode only |
| **Interleaved Execution** | MSTVFs get actual row count before plan compilation (vs fixed 1/100 rows) |
| **Memory Grant Feedback** | Adjusts memory grant up/down based on actual usage to avoid spills or overallocation |
| **Table Variable Deferred Compilation** | TVFs get actual row count at first compilation (vs fixed 1 row) |
| **Batch Mode on Rowstore** | Batch processing without columnstore dependency — benefits CPU-heavy queries |
| **Scalar UDF Inlining** | Scalar functions transformed into subqueries for parallelism and proper costing |
| **Approximate Count Distinct** | `APPROX_COUNT_DISTINCT` — faster with ~2% error rate at 97% confidence |

### Exam Gotchas
- Rebuild updates statistics; reorganize does NOT.
- Resumable rebuild: SQL Server 2017+. MAXDOP control on resumable: SQL Server 2019+.
- Rebuild can be online or offline. Online requires more space.
- Automatic plan correction forces plan after 15 executions of better query. Check regression threshold: 10 seconds CPU gain.
- Automatic index management is Azure SQL DB only (not on-premises, not MI by default).
- Query Store must be in **Read-Write** mode for auto-tuning ALTER to succeed.
- Adaptive joins only work in **batch execution mode**.
- Scalar UDF inlining converts UDFs to scalar subqueries — enables parallelism.
- Approximate Count Distinct guarantees 2% error rate at 97% confidence.
- Legacy CE can be set per database via `ALTER DATABASE SCOPED CONFIGURATION` — still allows IQP features at compat level 140/150.
