# Module 2: Authentication, Authorization, Encryption & Compliance

---

## Card 1: Authentication & Authorization

### Authentication Options
- **SQL Server Authentication:** Login/password stored in SQL Server. Supported by all Azure SQL offerings.
- **Microsoft Entra ID Authentication:** More secure, simplifies user management. Supports MFA (push notification, text, access code). Use Universal Authentication with MFA in SSMS. Best practice: make the Microsoft Entra admin a **group**, not a single user, so access isn't dependent on one login.
- **Windows Authentication:** Only on SQL Server and SQL Server on Azure VM (not SQL Database or Managed Instance).

### RBAC (Azure Resource Level)
- **SQL DB Contributor:** Create/manage databases but CANNOT read data.
- **SQL Security Manager:** Manage security policies (auditing) but CANNOT access data.
- **SQL Server Contributor:** Manage servers and databases but CANNOT access data.
- RBAC is decoupled from database-level SQL permissions.

### Security Principals
- **Logins:** Server-level principals stored in `master` database. Available in SQL Server and SQL Managed Instance. New logins can be added but new server roles cannot be created in Azure SQL Database.
- **Users:** Database-level principals. Can be mapped to a login or created as contained users (recommended for Azure SQL Database). Contained users only have access to that specific database.
- **Schemas:** Namespace for objects. Every user has a default schema (defaults to `dbo`). Best practice: specify schema name when accessing objects (`SELECT FROM SalesSchema.customers`).

### Built-in Database Roles
| Role | Permission |
|------|-----------|
| db_owner | Full admin within database |
| db_accessadmin | Create other users |
| db_backupoperator | Backup DB (SQL Server/MI only, not Azure SQL DB) |
| db_datareader | Read all tables/views |
| db_datawriter | INSERT, UPDATE, DELETE all tables/views |
| db_ddladmin | Create/modify objects (not data) |
| db_denydatareader | DENY read (overrides grants) |
| db_denydatawriter | DENY write (overrides grants) |
| db_securityadmin | Grant permissions to others |
| public | Default role for all users (no permissions by default) |

### Azure SQL Database-Specific Master DB Roles
- **loginmanager:** Create logins for the server (equivalent to `securityadmin` fixed server role)
- **dbmanager:** Create/delete databases (equivalent to `dbcreator` fixed server role)

### Server-Level Roles (SQL Server / SQL Managed Instance)
- sysadmin, serveradmin, securityadmin (treat as sysadmin), processadmin, setupadmin, bulkadmin, diskadmin, dbcreator

### Object Permissions
- **DML:** SELECT, INSERT, UPDATE, DELETE on tables/views
- **Other:** CONTROL (full rights), REFERENCES (view FK), EXECUTE (procedures/functions), ALTER (change definition), VIEW DEFINITION, VIEW CHANGE TRACKING
- **DENY always overrides GRANT** — if both are applied, DENY wins

### Ownership Chains
- If a stored procedure has the same owner as the tables it accesses, the user only needs EXECUTE on the procedure — they inherit access to the tables during execution.
- **Dynamic SQL breaks ownership chains** — the user must have direct permissions on the objects accessed by dynamic SQL because it executes outside the stored procedure's context.

### Application Roles
- Activated by the user supplying the preconfigured password (not by membership).
- Permissions apply until the role is deactivated.

### Transient Faults & Retry Logic
- Transient faults occur during reconfiguration (planned/unplanned), usually <60 seconds.
- Retry: first retry after **5 seconds minimum**, exponential backoff up to **60 seconds maximum**.
- **SELECT failures: retry in a new connection** — do not retry in the same connection.

### Exam Gotchas
- Contained database users are the recommended pattern for Azure SQL Database (not logins in master).
- `db_backupoperator` has no effect in Azure SQL Database — only in SQL Server and SQL Managed Instance.
- `securityadmin` server role should be treated as equivalent to `sysadmin` because it can grant itself permissions.
- Dynamic SQL breaks ownership chains — users need direct table permissions.
- DENY always overrides GRANT, regardless of order.
- RBAC roles (SQL DB Contributor, etc.) manage Azure resource operations, not database access.

## Card 2: Data Encryption (TDE, Always Encrypted, TLS)

### Transparent Data Encryption (TDE)
- Encrypts data at rest at the **page level** — data encrypted when written to disk, decrypted when read into memory.
- **Does NOT encrypt at column or table level** — authorized users can still read data.
- Protects against: restoring backups to unsecured servers, copying database/log files.
- **Azure SQL DB:** Automatically enabled for databases created after May 2017.
- **Azure SQL MI:** Automatically enabled for databases created after February 2019.
- On-premises/VM: Must manually create master key → certificate → database encryption key → enable encryption.
- **Service-managed key** (Microsoft-provided) vs **Customer-managed key** (BYOK via Azure Key Vault).
- If customer-managed key is removed from AKV, database connections are closed and access is denied.
- Certificate used by TDE must be manually backed up — if lost, backups cannot be restored.
- For Always On AG: the certificate must be restored to all replicas.
- Automatic key rotation: server checks AKV for new key versions every 60 minutes.

### Always Encrypted
- Encrypts data **within the client application** — protection from high-privileged users (DBAs, cloud admins).
- Uses two keys: **Column Master Key (CMK)** and **Column Encryption Key (CEK)**.
- Keys stored in key store (Windows Certificate Store, Azure Key Vault, HSM). **Never generate keys on the database server.**
- **Deterministic encryption:** Same value always encrypts to same ciphertext — supports equality, joins, grouping, indexing.
- **Randomized encryption:** More secure — same value encrypts differently each time — only supports returning in results. Cannot change encryption type after creation.
- Application needs: Always Encrypted driver + `Column Encryption Setting=enabled` in connection string.
- `SqlCommandColumnEncryptionSetting` can minimize metadata lookups in .NET applications.

### Secure Enclaves
- Secured region of memory within SQL Server process — trusted execution environment.
- Enables pattern matching, comparison operations, and indexing on **randomized encrypted** columns (overcoming the limitation).
- Appears as a black box — no data/code visible even with a debugger.

### TLS/Encrypted Connections
- Transport Layer Security encrypts data in transit.
- Certificate requirements: local certificate store, SQL Server service account must have access, within valid period.
- Configure via SQL Server Configuration Manager: Certificate tab → select cert, Flags tab → ForceEncryption = Yes.
- Test via SSMS: Connection Properties → Encrypt connection.

### SQL Injection
- Caused by poor coding practices — dynamically generated SQL accepting user input.
- Prevent by: validating input matches expected data type, using parameterized queries, inspecting parameters.
- Advanced Threat Protection can provide an extra layer when code cannot be fixed.

### Azure Key Vault Integration
- Stores secrets, certificates, keys. Has its own RBAC policies separate from Azure subscription.
- SQL Server supports AKV for TDE, Backup Encryption, and Always Encrypted.
- Configuration: create credential mapped to login → create asymmetric key in AKV → create asymmetric key in DB using `FROM PROVIDER`.

### Exam Gotchas
- TDE encrypts at the **page level**, not column level. Always Encrypted encrypts **in the client application**.
- TDE is **auto-enabled** for Azure SQL DB (post-May 2017) and Azure SQL MI (post-Feb 2019).
- **Customer-managed key removal closes all database connections** and denies access.
- Always Encrypted keys must **never be generated on the database server** — use client-side or AKV.
- Deterministic encryption supports equality, joins, grouping, indexing. Randomized does not — only return in results.
- **Dynamic SQL breaks ownership chains** — users need direct permissions on objects accessed via dynamic SQL.
- For TLS: missing service account access to certificate causes SQL Server restart to **fail**.
- AKV has its own RBAC — subscription admin does NOT automatically have AKV access.

## Card 3: Firewall, Network Security & Private Link

### Firewall Rules
- **Two levels:**
  - **Server-level:** Allow connections to all databases on the server. Configured via Azure portal or `sp_set_firewall_rule` in master.
  - **Database-level:** Grant/block specific IPs per database. Configured via `sp_set_database_firewall_rule` T-SQL only (in user database).
- **Connection flow:** Check database-level rule first → if no match, check server-level rules. If neither exists, SSMS prompts to create a rule.
- **Allow Azure Services:** Counts as a single firewall rule when enabled.

### Virtual Network Endpoints
- Allow traffic from a specific Azure VNet. Apply at server level only.
- Service endpoint applies to **one region** only (the endpoint's region).
- VNet must have outbound access to the database's public IP via service tags.

### Private Link
- Connect to Azure SQL Database using a **private endpoint** — traffic goes entirely over Azure backbone network, not public internet.
- Provides private IP on your VNet. Supports ExpressRoute connections.
- Benefits: cross-region private connectivity, protection against data leakage.

### Exam Gotchas
- Server-level firewall rules can be configured via portal or T-SQL (`sp_set_firewall_rule` in master).
- Database-level firewall rules are **T-SQL only** (`sp_set_database_firewall_rule` in user database).
- Firewall checks database-level rules **first**, then server-level.
- VNet service endpoints apply to only **one region**.
- Private Link provides a private IP on VNet and keeps traffic off the public internet.

## Card 4: Compliance Controls (Auditing, Data Classification, Masking, RLS)

### Data Classification
- Performed **per column** using sensitivity labels and information types.
- Stored in `sys.sensitivity_classifications` catalog view (available SQL Server 2019+, Azure SQL DB, SQL MI).
- Classification engine scans database and recommends classifications based on column **names** — a column named `column1` containing emails would NOT be auto-detected.
- Configure via: Azure portal (Data Discovery & Classification), SSMS sensitivity wizard, or T-SQL `ADD SENSITIVITY CLASSIFICATION TO ... WITH (LABEL='PII', INFORMATION_TYPE='Email')`.
- Customize taxonomy in Microsoft Defender for Cloud — only users with admin rights on the **root management group** can create/manage sensitivity labels.

### Server & Database Audit
- Tracks database events to: Azure Storage account, Log Analytics workspace, or Event Hubs.
- **Server-level** policy covers all existing and new databases. **Database-level** for specific exceptions.
- Best practice: enable only server-level unless a specific database needs different settings.
- **Default auditing action groups:** BATCH_COMPLETED_GROUP, SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP, FAILED_DATABASE_AUTHENTICATION_GROUP.
- **Read-Only replicas are automatically audited** when server auditing is enabled.
- Audit log includes `data_sensitivity_information` field when combined with data classification.
- Auditing may skip events during high activity or network load (optimized for availability/performance).

### Dynamic Data Masking
- Obfuscates data at the **presentation layer** — unmasked data always visible to high-privileged users.
- **Masking functions:**
  - `default()` — XXXX for strings, 0 for numbers, 01.01.1900 for dates
  - `partial(0,"XXXX-XXXX-XXXX-",4)` — credit card format
  - `email()` — aXXX@XXXXXXX.com
  - `random(1, 12)` — random number
  - `partial(1,"XXXXXXX",0)` — custom string
- **UNMASK** permission required to see unmasked data.
- **SELECT INTO / INSERT INTO** from masked columns copies masked data.
- **Export** by user without UNMASK creates masked data in the file.
- Masked data can be identified via **inference** — should be combined with other security features.
- Configure via Azure portal or T-SQL `ALTER TABLE ... ADD MASKED WITH (FUNCTION = '...')`.

### Row-Level Security (RLS)
- Restricts rows based on group membership or authorization context — equivalent to a WHERE clause.
- Uses an **inline table-valued function** with `SCHEMABINDING` + a **security policy**.
- **Filter predicates:** Restrict SELECT, UPDATE, DELETE (INSERT is not applicable for filters).
- **Block predicates:** Restrict AFTER INSERT, AFTER UPDATE, BEFORE UPDATE, BEFORE DELETE.
- Create flow: Create users → Create inline TVF → Create security policy → Assign predicate.
- Risk of **side-channel attacks** via divide-by-zero errors — limit unplanned queries.
- Best practices: separate schema for predicates, avoid type conversions, avoid excessive joins/recursion.

### Exam Gotchas
- Data classification is based on column **names** — automated recommendations may miss poorly named columns.
- Only users with admin rights on the **root management group** can create/manage sensitivity labels.
- **Best practice:** enable only server-level auditing unless a specific database needs different settings.
- Dynamic Data Masking works at the **presentation layer** — data is still stored unencrypted; high-privileged users with UNMASK see real data.
- RLS requires: inline TVF with `SCHEMABINDING` + `CREATE SECURITY POLICY`.
- RLS filter predicates affect SELECT, UPDATE, DELETE. Block predicates affect INSERT and UPDATE.
- Side-channel attacks are possible with RLS — limit unplanned queries.
- `db_backupoperator` has no effect in Azure SQL Database.

## Card 5: Microsoft Defender for SQL, Ledger & Microsoft Purview

### Microsoft Defender for SQL
- Includes **SQL vulnerability assessment** + **Advanced Threat Protection**.
- **Vulnerability Assessment:** Knowledge base of security rules, flags misconfigurations, excessive permissions, exposed sensitive data. Must enable at subscription level (recommended). Requires a storage account.
- **Advanced Threat Protection alerts:**
  - Vulnerability to SQL injection (detects vulnerable T-SQL)
  - Potential SQL injection (active attack detected)
  - Access from unusual location / unusual Azure data center
  - Access from unfamiliar principal
  - Access from potentially harmful application
  - Brute force SQL credentials
- To manage settings: must be in SQL security manager role, or database/server admin role.
- Recommended audit action groups: BATCH_COMPLETED_GROUP, SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP, FAILED_DATABASE_AUTHENTICATION_GROUP.

### Ledger
- Provides **tamper-evidence** capabilities — cryptographically attest that data hasn't been tampered with.
- Each transaction is cryptographically hashed (SHA-256) and linked like a blockchain.
- **Updatable ledger tables:** For apps that issue INSERT, UPDATE, DELETE — tracks history using system-versioned history table.
- **Append-only ledger tables:** For insert-only apps (accounting, SIEM) — blocks all UPDATE/DELETE at the API level.
- **Enable ledger only during database creation** — cannot modify after creation.
- Setting: "Enable for all future tables in this database" makes all future tables ledger tables (default to updatable if not specified).
- Can also enable per-table using `LEDGER = ON` in `CREATE TABLE`.

### Microsoft Purview
- Unified data governance service — automated data discovery, classification, and lineage.
- Creates a holistic map of data across on-premises, multicloud, and SaaS.
- **Scanning authentication methods:**
  - System-assigned managed identity (recommended) — cannot be used with self-hosted IR
  - User-assigned managed identity (preview) — cannot be used with self-hosted IR
  - Service Principal (has expiration date)
  - SQL Authentication
- **Self-hosted IR:** Must use service principal or SQL authentication (managed identities don't work).
- **Firewall options:** Allow Azure connections, self-hosted IR, managed virtual network.
- **Required roles:** Data Source Administrator + Data Reader to register and manage sources.
- **Data lineage:** Extracted from stored procedure executions. Supports lineage extraction toggle in scan setup. Runs incremental scans every 6 hours.
- Requirements: Azure subscription, ability to create Purview resources, access to data sources.

### Exam Gotchas
- **Ledger can only be enabled during database creation** — cannot be added later.
- Append-only ledger tables block UPDATE and DELETE at the API level.
- Updatable ledger tables use system-versioned history for tracking changes.
- **Managed identities (system/user-assigned) do NOT work with self-hosted integration runtime** for Purview scanning — use service principal or SQL authentication.
- Vulnerability assessment requires enabling Microsoft Defender for SQL at the **subscription level**.
- Advanced Threat Protection recommended audit groups: BATCH_COMPLETED, SUCCESSFUL_DATABASE_AUTHENTICATION, FAILED_DATABASE_AUTHENTICATION.
- Purview lineage extraction runs incremental scans every **6 hours**.
- Data Source Administrator + Data Reader roles are required for Purview source registration.
