# Configure and manage automation of tasks

## Manage schedules for regular maintenance jobs

Regular SQL Server maintenance covers four recurring activities: database and transaction log backups, database consistency checks, index maintenance, and statistics updates. Consistency checks run through DBCC CHECKDB, the only mechanism that validates the logical and physical integrity of every page in a database. Because index maintenance and consistency checks are both I/O-intensive, production systems typically spread these operations across the week rather than running everything nightly, often scheduling the heaviest work for weekend hours. Backup strategy is commonly staggered: one full backup per week supplemented by differential and transaction log backups so recovery can hit a specific point in time. For example, a full backup on Sunday plus a nightly differential means restoring to Thursday at noon requires the Sunday full, Wednesday's differential, and the transaction log backups from Wednesday's differential through Thursday noon.

SQL Server Maintenance Plans give you a built-in workflow for these tasks, built as SQL Server Integration Services packages and scheduled through SQL Server Agent jobs. Many DBAs also use open-source maintenance scripts for more flexibility. The Maintenance Plan Wizard in SSMS walks through naming the plan, choosing a run-as account (usually the SQL Server Agent service account, though a proxy account is needed when a step requires access the Agent account doesn't have, such as a backup destination on a restricted file share), and selecting tasks. A proxy account stores credentials the Agent uses to run specific job steps as a designated user with only the rights that step needs.

The available maintenance tasks are:
- Check database integrity – runs DBCC CHECKDB; schedule it to align with your backup retention window so a consistency check always runs before older backups are discarded, since a backup operation does not itself detect corruption.
- Shrink database – reclaims free space from a database or log file; not recommended as a routine task because it causes severe index fragmentation and is heavily I/O and CPU intensive.
- Reorganize/Rebuild index – checks fragmentation level and reorganizes or rebuilds based on a user-defined threshold; rebuilding an index also refreshes its statistics.
- Update statistics – refreshes column and index statistics used by the query optimizer; you choose which tables/indexes and what sampling percentage or row count to scan, though the default sampling rate is usually adequate.
- Cleanup history – deletes backup/restore and SQL Server Agent job history from msdb, helping control msdb's size.
- Execute SQL Server Agent job – runs another user-defined Agent job as a step.
- Backup Database (Full/Differential/Log) – full backups capture the entire database as a restore baseline; differential backups capture changed pages since the last full; transaction log backups capture active log pages and define your recovery point objective. Transaction log backups cannot be performed on databases in the SIMPLE recovery model.
- Maintenance Cleanup Tasks – deletes old maintenance-plan report and backup files, but only within the folders you specify; subfolders must be listed explicitly or they're skipped.

Each task can be scoped to system databases, user databases, or a custom database list. Best practice is a separate maintenance plan per task type (and sometimes per database) rather than combining everything into one plan — for example, a plan for system database backups, a separate one for user databases, and possibly a dedicated plan for a particularly large database. Maintenance plans also help prune the msdb database itself and can be configured to delete old backup files from disk to control backup volume size.

Job schedules live in the msdb system database, and jobs and schedules have a many-to-many relationship — one job can carry multiple schedules, and one schedule can be attached to multiple jobs. The Maintenance Plan Wizard is an exception: it only creates a dedicated schedule per plan rather than letting you attach a reusable, independent schedule. Schedules can recur hourly, daily, or weekly.

In a multiserver environment, SQL Server Agent supports designating one server as the primary server, which stores the master copy of jobs and pushes them to target servers; target servers periodically reconnect to the primary to pick up schedule updates. This lets you define a maintenance job once (for example, backups or index maintenance) and roll it out consistently across many servers in the enterprise.

Most SQL Server Agent functionality carries over to Azure SQL Managed Instance, though minor T-SQL differences between on-premises SQL Server and Managed Instance can affect job scripts written for one platform and moved to the other.

## Configure job alerts and notifications

Notifying operators about job failures or system errors is a core piece of SQL Server Agent automation, built around three objects: operators, notifications, and alerts. Delivery is typically done by email through SQL Server's Database Mail feature, which requires enabling a mail profile in SQL Server Agent's properties before any operator can receive email.

An operator is an alias — a name plus contact information, usually mapped to an email distribution group rather than an individual — configured to receive notifications of job completions or error-log alerts. Using a group address instead of a single person's address gives redundancy (no missed notification if one person is unavailable) and avoids maintenance churn when staff changes. Notifications are attached to individual SQL Server Agent jobs and can fire on completion, success, or failure; most DBAs configure notification on failure only, to avoid a flood of noise from routine successful runs. A notification always depends on an existing operator to send to.

Alerts provide proactive monitoring: the Agent reads the SQL Server error log and notifies an operator whenever it encounters an error number that has an alert defined against it. Beyond the error log, alerts can also be defined on SQL Server performance conditions (Windows Performance Monitor / perfmon metrics tracked inside the database engine, such as CPU utilization over 90% for five minutes or low Page Life Expectancy) and on WMI events. A single alert can cover one or more events. Common practice is to alert on all SQL Server errors of severity level 16 and higher, plus specific critical storage errors (823, 824, 825) or Availability Group failovers. Alerts are created from SSMS by right-clicking SQL Server Agent and choosing New | Alert.

When an alert condition fires, you have two response options: notify an operator by email (the most common response), or execute another SQL Server Agent job to remediate automatically — useful for well-understood conditions, such as running a job that performs a database consistency check in response to a storage error alert. Both notification paths route through the same SQL Server Agent subsystem.

## Troubleshoot SQL Server Agent jobs

Source coverage of Agent job troubleshooting specifically is limited to a few inline points rather than a dedicated troubleshooting workflow. The clearest exam-relevant trap is that Azure SQL Managed Instance supports most SQL Server Agent capabilities, but minor T-SQL differences between SQL Server and Managed Instance can break job scripts that were written for one platform and then ported to the other — a script that runs cleanly on-premises may need adjustment on Managed Instance. In multiserver topologies, target servers depend on periodically reconnecting to the primary server to receive schedule updates, so a target server that has fallen out of contact with the primary is a likely cause of jobs not running as expected on that target. Proxy account misconfiguration is another practical failure point: if a job step needs to access a resource (like a network file share for backups) that the SQL Server Agent service account can't reach, the step fails unless a proxy account with the correct credentials and permissions has been assigned to that step.

## Automate deployment by using Azure Resource Manager (ARM) and Bicep templates

ARM templates are JSON documents that declaratively describe the resources to deploy in an Azure resource group — you specify what should exist rather than the sequence of commands to create it, and the ARM framework figures out how. A template can define an entire dependent infrastructure stack (for example a VM plus its network and storage) in one document. Templates support orchestration, meaning ARM deploys interdependent resources in the correct order and, where possible, in parallel rather than serially for speed, and extensibility, meaning you can run PowerShell or Bash scripts against resources after deployment completes.

Benefits of ARM templates: they're idempotent and repeatable, so redeploying the same template throughout a development lifecycle produces a consistent result; they handle deployment orchestration automatically; they're modular and can be split or combined as needed; they're exportable — any resource created through the Azure portal can have its template exported via "Export template" in the resource group's Automation section, useful for disaster recovery and documentation; and they can be authored in Visual Studio Code (with the ARM Tools extension) or Visual Studio, both offering IntelliSense, syntax highlighting, and inline help.

A minimal ARM template to deploy a single Azure SQL Database defines parameters for server name, database name, location, admin login, and admin password (typed as `secureString`), then declares a `Microsoft.Sql/servers` resource and a `Microsoft.Sql/servers/databases` resource that `dependsOn` the server. Deployment scope options when deploying via PowerShell (or CLI) are resource group, subscription, management group (a collection of subscriptions under a shared template, common in large enterprises), or tenant. A template deploys from a URI with `New-AzResourceGroupDeployment -TemplateUri <url> ...` after creating the resource group with `New-AzResourceGroup`.

Bicep is a declarative, Azure-specific language (not a general-purpose language) for authoring the same infrastructure declarations with a more concise, readable syntax than the equivalent JSON. Its benefits: continuous full support for every resource type and API version the moment Azure introduces them, without waiting for tooling updates; simpler syntax than JSON for the same result; and a low barrier to entry, requiring no prior programming background. The VS Code Bicep extension adds IntelliSense and syntax validation. A Bicep file is deployed the same way as an ARM template — save it as `main.bicep`, create the resource group with `New-AzResourceGroup`, then run `New-AzResourceGroupDeployment -TemplateFile ./main.bicep ...`.

Because ARM/Bicep templates are infrastructure as code, they should live in source control just like application or database code, in addition to the versioning metadata (`contentVersion`) inside the template itself. In practice, DBAs rarely author templates from scratch — they typically start from a template exported via the Azure portal or from Microsoft's Azure Quickstart Templates on GitHub, where a "Deploy to Azure" button opens the portal, pre-loads the template, and only requires filling in details like resource group, location, and admin credentials before Review + create.

## Automate deployment by using Azure PowerShell

PowerShell is a cross-platform command shell built around cmdlets that operate on both text and .NET objects. Its practical advantages include command history, tab completion and command prediction, aliasing of commands and parameters, a pipeline for chaining commands together, and an in-console help system. The Az PowerShell module is the open-source core module providing cmdlets across almost all Azure services (for example, `Az.Compute` for virtual machines); it can create resources, retrieve status, modify existing resources, and deploy ARM templates, supporting both the declarative (template) and imperative (direct cmdlet) models.

`Az.Sql` is the subset of the Az module scoped to Azure SQL — it covers everything from creating databases to configuring geo-replication and other Azure SQL management tasks, and is usable from PowerShellGet, Azure Cloud Shell, or an Az PowerShell Docker container. All Az cmdlets follow the same verb-noun syntax: `<command-name> -<Required Parameter Name> <value> [-<Optional Parameter Name> <value>] [-<Optional Switch>]`. Representative examples: `Get-AzSqlServer -ResourceGroupName "ResourceGroup01" -ServerName "Server01"` retrieves server info; `New-AzSqlDatabase -ResourceGroupName "ResourceGroup01" -ServerName "Server01" -DatabaseName "Database01"` creates a database on an existing server; and `New-AzSqlInstance -Name managedInstance2 -ResourceGroupName ResourceGroup01 -Location westcentralus -AdministratorCredential (Get-Credential) -SubnetId "..." -LicenseType LicenseIncluded -StorageSizeInGB 1024 -VCore 16 -Edition "GeneralPurpose" -ComputeGeneration Gen4` provisions a SQL Managed Instance, requiring a subnet ID, license type, storage size, vCore count, edition, and compute generation. A variant of that same cmdlet can create a Managed Instance configured for Microsoft Entra-only authentication by supplying `-ExternalAdminName` and `-EnableActiveDirectoryOnlyAuthentication` instead of SQL admin credentials, and instance details (including the Entra administrator) can subsequently be retrieved with `Get-AzSqlInstance -ExpandActiveDirectoryAdministrator`.

## Automate deployment by using Azure CLI

Automating routine database tasks is treated as valuable regardless of organization size, for several concrete reasons: it gives granular control over applications and databases, scales more easily as the number of assets grows, lets scripts be reused for routine tasks, and simplifies troubleshooting when GUI tools aren't available. Azure CLI is a cross-platform command-line tool that can create and manage Azure resources interactively or via scripts, and it can be installed on Linux, macOS, or Windows, or run from a browser through Azure Cloud Shell or inside a Docker container. Its syntax pattern is reference name – command – parameter – parameter value, for example `az account set --subscription "my subscription name"`.

Azure CLI and Azure PowerShell are both cross-platform and can manage the same resources, but they differ in the shells they support:

| Shell Environment | Azure CLI | Azure PowerShell |
|---|---|---|
| Cmd | Yes | |
| Bash | Yes | |
| Windows PowerShell | Yes | Yes |
| PowerShell | Yes | Yes |

Azure CLI reads more like Bash scripting, a natural fit for Linux-oriented admins, while Azure PowerShell's verb-noun cmdlets suit those already comfortable with Windows tooling. A quick command comparison:

| Task | Azure CLI | Azure PowerShell |
|---|---|---|
| Sign in with web browser | `az login` | `Connect-AzAccount` |
| Get available subscriptions | `az account list` | `Get-AzSubscription` |
| Set subscription | `az account set --subscription` | `Set-AzContext -Subscription` |
| List all virtual machines | `az vm list` | `Get-AzVM` |
| Create a new SQL server | `az sql server create` | `New-AzSqlServer` |

Some commands for Azure Database for PostgreSQL and Azure Database for MySQL exist only in the CLI, not PowerShell. A typical CLI deployment of Azure SQL Database plus a firewall rule looks like:

```
az sql server create --name $server --resource-group $resourceGroup --location "$location" --admin-user $login --admin-password $password
az sql server firewall-rule create --resource-group $resourceGroup --server $server -n AllowYourIp --start-ip-address 0.0.0.0 --end-ip-address 0.0.0.0
```

For ARM template deployment, both tools support the same deployment scopes (resource group, subscription, management group, tenant), and templates are parameterized either inline or via a parameter file. PowerShell example: `New-AzResourceGroupDeployment -Name ExampleDeployment -ResourceGroupName ExampleResourceGroup -TemplateFile c:\MyTemplates\azuredeploy.json -TemplateParameterFile c:\MyTemplates\storage.parameters.json`. The CLI equivalent is `az deployment group create --resource-group ExampleResourceGroup --template-file '\path\template.json'`; template and parameter files can live in a Git repo, Azure Blob Storage, or any location reachable from the deploying machine. Remote linked templates stored in a storage account can be deployed with a SAS token passed via `--query-string`, e.g. `az deployment group create --name linkedTemplateWithRelativePath --resource-group myResourceGroup --template-uri "https://.../mainTemplate.json" --query-string $sasToken`. A notable CLI limitation: Azure CLI cannot deploy remote Bicep files directly — you must first convert the Bicep file to JSON with the Bicep CLI, then deploy the resulting JSON template from its remote location.

Two other Azure deployment surfaces round out the picture. The Azure portal is a graphical front end to ARM templates; anything you create through it can have its underlying ARM template exported from the resource group's Automation section, and the portal is generally the easiest entry point before teams move to more automated methods. Azure DevOps Services automates deployment through Azure Pipelines, either by invoking a PowerShell script or by defining pipeline tasks that stage artifacts (templates and secrets) and deploy them — this is the mechanism behind continuous integration (frequent small code changes checked into source control, with automated build/package/test) and continuous delivery (automated delivery of those changes to infrastructure), together making deployments consistent, rapid, and less error-prone.

## Create and configure elastic jobs

Elastic Jobs are the Azure SQL Database equivalent of SQL Server Agent job scheduling, since Azure SQL Database has neither the msdb database nor SQL Server Agent itself. An elastic job runs a set of T-SQL scripts against a collection of servers, elastic pools, or databases, either once or on a recurring schedule, and works across every Azure SQL Database service tier — unlike SQL Server Agent jobs, which remain available only on SQL Server and Azure SQL Managed Instance.

The Elastic Jobs architecture has four components: an elastic job agent (the Azure resource that runs and manages jobs), a job database (a dedicated database that stores job metadata — Microsoft recommends S1 or higher depending on job volume and frequency), a target group (the set of servers, elastic pools, and/or single databases a job runs against), and the job itself (one or more T-SQL scripts making up job steps). You can create the job agent through the Azure portal, PowerShell, or the REST API. If the target is a server or elastic pool, you must create a credential in the master database of that server/pool so the job agent can enumerate its databases; a single-database target only needs a database-level credential. Credentials should always be scoped to least privilege for the job step they support.

Target groups can be created with PowerShell, T-SQL, or Azure CLI — for example, `$serverGroup = $jobAgent | New-AzSqlElasticJobTargetGroup -Name 'MyServerGroup'` followed by `$serverGroup | Add-AzSqlElasticJobTarget -ServerName $targetServerName -RefreshCredentialName $masterCred.CredentialName` adds a target server to the group. Jobs and steps are created with `New-AzSqlElasticJob` (e.g., `-RunOnce` for a one-time job) and `Add-AzSqlElasticJobStep -Name "Step1" -TargetGroupName ... -CredentialName ... -CommandText $sqlText1`, then started with `Start-AzSqlElasticJob`. Because a job can rerun after a transient failure, the T-SQL it executes should be idempotent — safe to run repeatedly without erroring or producing unintended duplicate effects, for example guarding a `CREATE TABLE` with an `IF NOT EXISTS` check.

Typical elastic job use cases: running scheduled management tasks, deploying schema changes across many databases, moving data, collecting/aggregating data for reporting, loading data from Azure Blob Storage, running recurring jobs during off-peak hours across many databases, and processing per-database data (like telemetry) into a single aggregated destination table. The exam-relevant distinction: SQL Agent jobs give robust general-purpose scheduling on SQL Server and Managed Instance, while Elastic Jobs are the T-SQL-only equivalent purpose-built for Azure SQL Database and elastic pools.

## Create and configure database tasks by using automation

Beyond Elastic Jobs, Azure offers Azure Functions, Logic Apps, and Azure Automation as automation surfaces; Functions and Logic Apps are serverless workflow services (for example, a Logic App that writes to an Azure SQL Database table whenever a SharePoint list entry is created), while Azure Automation is the option offering the most control and granularity — it provides process automation, configuration management, full RBAC/Microsoft Entra ID integration, and the ability to manage both Azure and on-premises resources from one place. A distinctive Azure Automation capability is managing on-premises or IaaS VM resources directly: for instance, using hybrid runbooks to start a VM kept shut down for cost savings, run a SQL Server backup against it, then shut it down again. Azure Automation is also commonly used for periodic maintenance like purging stale data or reindexing a database.

Azure Automation's core components: runbooks (the unit of execution — graphical/PowerShell-based, plain PowerShell script, or Python; PowerShell runbooks are most common for Azure SQL work), modules (the execution context that must be imported before your runbook code can call its cmdlets — e.g., importing `Az.Accounts` and then `Az.SQL` before using `Get-AzSqlDatabase`), credentials (secure storage for secrets a runbook uses at runtime), and schedules (attached to a runbook to trigger it at a specific time).

Creating a runbook requires first creating an Automation account, then importing the needed modules under Shared Resources > Modules (Az.SQL depends on Az.Accounts, so import that first), optionally creating a stored credential, and then authoring the runbook itself under Process Automation > Runbooks, specifying a name, runbook type, and runtime version. Runbooks restart from the beginning if interrupted, so they must be written to tolerate being restarted safely after a transient failure. A representative PowerShell runbook logs in with the Automation account's system-assigned managed identity (`Connect-AzAccount -Identity`, which requires RBAC permissions granted to that identity or the runbook fails), retrieves database info via `Get-AzSQLDatabase`, pulls a stored credential with `Get-AutomationPSCredential`, and runs a query with `Invoke-Sqlcmd`. The portal's Test pane lets you validate runbook code inside the Automation execution context before relying on it, separating genuine PowerShell bugs from automation-context-specific issues.

Two governance features tie into automated database tasks: Azure Policy, which enforces rules (region restrictions, naming standards, resource sizing) at the management group, subscription, or resource group level and can be grouped into initiatives, and resource tagging, which stores key:value metadata (e.g., environment, cost center) that Policy can require and that PowerShell/CLI can filter on much like a SQL WHERE clause (`$rg | where-object {($_.tags['Use'] -ne 'Internal')}`). Azure supports up to 15 tags per resource, tags can be set via the portal, `New-AzTag`, or `az resource tag`, and tags feed into Azure billing breakdowns by cost center. Because tags are stored as plain text, sensitive values must never be placed in them — they can leak through cost reports, tag taxonomies, deployment histories, exported templates, and monitoring logs. Multiple subscriptions (grouped under a management group for unified policy/compliance) are commonly used to separate billing or isolate internal from customer-facing resources.

Azure Logic Apps is the workflow-automation platform for integrating apps, data, services, and systems, including B2B scenarios, using mostly prebuilt Microsoft-managed connectors so you focus on business logic rather than plumbing; when code is needed you can add Azure Functions snippets or inline code, and event-driven scenarios can route through Azure Event Grid. It's fully managed (serverless), so hosting, scaling, and monitoring are handled for you. Example automatable workflows: sending Office 365 email notifications on events like a new file upload, routing customer orders across on-prem and cloud systems, moving files from SFTP/FTP into Azure Storage, or monitoring social media sentiment and raising review tasks.

The SQL Server connector in Logic Apps lets a workflow trigger on database events or perform actions (get, insert, delete rows; run queries or stored procedures) against SQL Server, Azure SQL Database, or Azure SQL Managed Instance. Tables must already contain data for connector operations to return results. A typical Azure SQL connection string looks like `Server=tcp:{server-name}.database.windows.net,1433;Initial Catalog={database-name};Persist Security Info=False;User ID={user-name};Password={password};MultipleActiveResultSets=False;Encrypt=True;TrustServerCertificate=False;Connection Timeout=30;`, also retrievable from the database's Overview blade in the portal. The connector's availability varies by workflow type: Consumption workflows in multitenant Logic Apps get it only as a managed connector; Consumption workflows in an integration service environment (ISE) get both managed and ISE-native versions; Standard (single-tenant) workflows get both a managed connector and a built-in connector that runs in-process with the runtime — but the built-in version has no triggers and supports only one operation, Execute Query. Building a workflow in the portal means opening a blank workflow, searching "sql server" among triggers/actions (e.g., the "When an item is created" trigger or the "Get row" action, which returns exactly one row), configuring polling interval/frequency for triggers, and creating the SQL connection (server, database, credentials, auth type) on first use, then saving to auto-publish the live workflow.

## Configure alerts and notifications on database tasks

Azure Automation supports metric alert rules on runbook execution, configured from Create alert rule: you pick a signal (for example, Total Jobs), define signal logic (a static threshold, a comparison operator like "Greater than," an aggregation type such as Total, and a threshold value, e.g., greater than 10), and optionally scope the alert with a dimension so it only fires for a specific runbook and status — with no dimension specified, no filter is applied. Alerts are tied to an action group, a reusable bundle of response actions (email notifications, runbooks, webhooks, and more) shared across multiple alert rules; a common pattern is combining Azure Automation with an alert's action group so the alert itself triggers another Automation runbook to remediate. For Elastic Jobs, the built-in analog to alerting is the automatic retry of job executions on transient failure, which is a resiliency feature rather than a configurable notification — the source material doesn't describe a separate elastic-job alert/notification mechanism beyond monitoring execution status (covered below) and this automatic retry behavior.

## Troubleshoot automated database tasks

For Azure Automation runbooks, monitoring is central to troubleshooting: runbooks should be written modularly with restartable logic, and progress should be checked against a database, storage account, or shared file so the runbook can verify the last completed action before deciding whether to skip or continue subsequent steps. Execution history is visible in the portal under the automation account's Process Automation > Jobs page, showing whether a run completed and letting you drill into a specific job's details. The activity log for an Automation account records who or what started each runbook; the same information can be pulled programmatically by combining `Get-AzLog` (filtered to the `Microsoft.Automation/automationAccounts/jobs/write` action) with `Get-AzAutomationJob` to resolve which user or account triggered a given runbook run.

For deeper diagnostics, Azure Automation can forward runbook job status and job streams to a Log Analytics workspace (configured through the Automation account's Diagnostic settings) without needing a separate workspace-linking step. Once wired up, Log Analytics lets you view job status, write advanced Kusto queries across job history, trigger emails or alerts based on job status, and correlate data across multiple Automation jobs; the portal ships prebuilt query templates, such as one listing all completed jobs in the account.

Elastic Jobs log every execution automatically and retry failures transiently, and their execution can be inspected three ways: through the Elastic Job agent's Overview page in the portal; through PowerShell, using `$jobAgent | Get-AzSqlElasticJobExecution -Count 5` for recent runs, `$jobExecution | Get-AzSqlElasticJobStepExecution` for step-level detail, and `$jobExecution | Get-AzSqlElasticJobTargetExecution -Count 2` for per-target detail; or through T-SQL against the job database, querying the `jobs.job_executions` view — for example `SELECT * FROM jobs.job_executions ORDER BY start_time DESC;` for all executions, filtering by `WHERE job_name = 'MyJob'` for a specific job, or `WHERE is_active = 1` to see only currently running executions.
