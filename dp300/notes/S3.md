# Monitor, configure, and optimize database resources

## Prepare an operational performance baseline

A baseline is a collection of data measurements that establishes the normal state of an application or server's performance. Without a baseline, every issue encountered could be dismissed as "normal," since there's no reference point to say otherwise; with one, you can tell whether an ongoing condition is within expected parameters or has actually regressed. Baselines can be as simple as a chart of CPU utilization over time, or as complex as granular aggregations tied to specific application calls — the right granularity depends on how critical the database's performance is.

When SQL Server runs on an Azure virtual machine, correlating SQL Server's own performance with the performance of the underlying operating system is central to building a useful baseline. On Windows, this means using Performance Monitor (perfmon); on Linux, the equivalent requires installing InfluxDB, Collectd, and Grafana to collect and visualize comparable data. A representative sampling of perfmon counters used to build a SQL Server baseline includes:

- **Processor(_Total)% Processor Time** — overall CPU utilization across all processors; a good general workload indicator, especially combined with other counters to diagnose query performance problems.
- **Paging File(_Total)% Usage** — in a properly configured SQL Server, memory shouldn't page to disk; nonzero paging often indicates other services on the box are competing for memory.
- **PhysicalDisk(_Total)\Avg. Disk sec/Read and Avg. Disk sec/Write** — storage subsystem latency; values shouldn't normally exceed 20 ms, and with Premium Storage should stay under 10 ms.
- **System\Processor Queue Length** — the number of threads waiting for CPU time; a value greater than zero indicates CPU pressure and a workload that could benefit from more CPUs.
- **SQLServer:Buffer Manager\Page life expectancy** — how long SQL Server expects a page to remain in memory. There's no single "correct" value (the old rule of thumb of 300 seconds dates to the 32-bit era of far smaller RAM); what matters is monitoring the trend and investigating sudden drops, which can indicate poor query patterns, external memory pressure (e.g., a large SSIS package running), or benign causes like a consistency check on a large database.
- **SQLServer:SQL Statistics\Batch Requests/sec** — a measure of how consistently busy the server is over time; useful alongside % Processor Time to characterize workload.
- **SQLServer:SQL Statistics\SQL Compilations/sec and SQL Re-Compilations/sec** — track how often the engine has to compile or recompile plans because none exists in cache or an existing one was invalidated; high recompiles can point to RECOMPILE query hints, or memory pressure on the plan cache from too many ad-hoc queries.

Wait statistics, exposed via the DMV sys.dm_os_wait_stats, record what a thread was waiting on when it couldn't immediately execute, and are available across the whole Azure SQL platform. They're a critical baseline input for understanding both query-execution problems and hardware limitations — identifying the specific wait type and its accepted resolution is central to root-causing performance issues.

For SQL Server on Azure VMs, an alternate metric worth capturing for storage baselining is IOPs, measured with the SQL Server: Resource Pool Stats Disk Read and Write IO/sec counters, which show peak IOPs served — important because every Azure VM size caps IOPs, and your storage/VM design needs to comfortably clear the workload's peak without incurring latency.

## Determine sources for performance metrics

Different Azure SQL platforms expose performance data through different surfaces, and knowing which source to reach for is itself an exam-relevant skill.

For Azure Virtual Machines running SQL Server, deploying from Azure Marketplace installs an agent that feeds Azure Monitor a basic set of OS-level metrics (CPU usage, network utilization, disk read/write). These are host-level metrics, not SQL Server-specific ones — the metric namespace is the VM, not the database engine — so SQL Server-specific details still have to be gathered from inside the VM itself (perfmon, DMVs). Enabling Azure Monitor Insights on the VM extends the default metric set with extra data points like storage latency, available memory, and disk capacity; this data lands in an Azure Log Analytics workspace, queried with Kusto Query Language (KQL). VMs built from the SQL Server Marketplace images also get the SQL VM resource provider, reachable from the VM's Settings > SQL Server configuration blade, which shows database/log file space consumption and lets you manage automated patching and storage configuration; this can be manually installed for SQL Server deployments that weren't created from the Marketplace image.

At the OS level, Performance Monitor (perfmon) is the native Windows tool, operating on counters exposed both by the OS and by installed applications — SQL Server registers its own counter group when installed. Perfmon data can be stored and analyzed locally, or forwarded into Azure Monitor for a single cross-server view in larger estates.

Within the database engine, dynamic management views (DMVs) are a primary metrics source, exposing data not available anywhere else — for example, data and log file read/write latency lives only in sys.dm_os_volume_stats. Conversely, some OS metrics (like seconds per disk read/write for a volume) aren't exposed through SQL Server DMVs at all; combining OS and DMV sources helps determine whether an issue is a database-structure problem or a physical storage bottleneck.

Azure Monitor Metrics is the platform-wide metrics subsystem: it gathers metrics at regular intervals, retains active data for 93 days (older data can be archived to Azure Storage), supports alert rules (static thresholds or Dynamic Thresholds that learn a metric's historical/seasonal behavior), and can trigger action groups (notifications or automated responses such as an Automation Runbook, Azure Function, Logic App, or webhook).

For query-level metrics specifically, Query Performance Insight (in the Azure SQL Database blade's Intelligent Performance section) surfaces top resource-consuming or long-running queries without requiring manual tracing scripts, and its query IDs correlate directly to Query Store's query IDs for deeper follow-up. Database watcher (preview) is a newer, purpose-built monitoring solution for Azure SQL Database and Managed Instance that centralizes monitoring data from databases, elastic pools, and managed instances into a data store you control.

## Interpret performance metrics

Reading these metrics correctly means understanding what a given value or wait type implies about the underlying bottleneck, and cross-referencing multiple sources rather than any single counter in isolation.

CPU pressure shows up as System\Processor Queue Length values greater than zero, as high Processor(_Total)% Processor Time, and — inside the engine — as SOS_SCHEDULER_YIELD and CXPACKET wait types. CXPACKET waits specifically flag parallelism-related contention; before SQL Server 2019 the default MAXDOP used all available CPUs and the default cost threshold for parallelism was 5, causing even small queries to run in parallel and limiting throughput. Lowering MAXDOP and raising the cost threshold reduces CXPACKET waits, though a high occurrence can also simply reflect genuine CPU pressure resolved through index tuning rather than parallelism settings.

Storage-related pressure surfaces as elevated PhysicalDisk\Avg. Disk sec/Read or Avg. Disk sec/Write at the OS level, and as PAGEIOLATCH_SH waits inside the engine — the latter can indicate missing/ineffective indexes causing excessive scanning, or, when wait count is low but wait time is high, genuine storage latency (calculable from waiting_tasks_count and wait_time_ms in sys.dm_os_wait_stats). SQL Server logs a warning if any I/O takes longer than 15 seconds. PAGEIOLATCH_UP contention on pages 2:1:1 specifically flags tempdb PFS (Page Free Space) contention, typically from having too few tempdb data files (each data file has one PFS page per 64 MB); the fix is one tempdb file per core up to eight, all equally sized with matching autogrowth settings.

Memory pressure shows as RESOURCE_SEMAPHORE waits — queries waiting for a memory grant to become available — often driven by out-of-date statistics, missing indexes, or high concurrency demanding many large grants simultaneously; it manifests as long runtimes or timeouts.

Blocking pressure shows as LCK_M_X waits, addressed by moving to READ COMMITTED SNAPSHOT isolation, better indexing to shorten transaction duration, or tightened transaction management in T-SQL.

Wait statistics themselves are grouped into three families: resource waits (locks, latches, disk I/O — waiting on something another thread holds), queue waits (idle worker waiting for work, e.g. deadlock monitoring or deleted-record cleanup), and external waits (waiting on an outside process, e.g. a linked-server call or returning a large result set to a client). sys.dm_os_wait_stats (server-scoped; sys.dm_db_wait_stats for Azure SQL Database) aggregates waits since the last restart or last manual clear; sys.dm_exec_session_wait_stats shows active waiting sessions live.

Azure SQL introduces its own wait families worth recognizing: LOG_RATE_GOVERNOR (Azure SQL Database), POOL_LOG_RATE_GOVERNOR (elastic pools), and INSTANCE_LOG_GOVERNOR (Managed Instance) reflect transaction-log-rate throttling enforced to protect SLAs; HADR_THROTTLE_LOG_RATE* relates to Business Critical/geo-replication log-rate throttling. Business Critical tier databases, built on Always On availability group technology under the hood, can also show HADR_SYNC_COMMIT, HADR_DATABASE_FLOW_CONTROL, and HADR_THROTTLE_LOG_RATE_SEND_RECV — expected in that tier, but long durations there can flag I/O latency or a replica falling behind. Hyperscale introduces RBIO-prefixed wait types tied to its log-governance and page-server-read architecture. Worker-thread exhaustion appears as errors on new connections for Azure SQL Database (tier/size-based limits) or as THREADPOOL waits for Managed Instance (governed by max worker threads).

A standard troubleshooting heuristic is to first classify a problem as "Running" (high CPU — compilation or execution bound) versus "Waiting" (blocked on some resource: I/O, locks, latches, buffer pool, memory grants, plan cache eviction), then drill into the matching tool set (Query Store/sys.dm_exec_requests/sys.dm_exec_query_stats/sys.dm_exec_procedure_stats for Running; sys.dm_os_wait_stats/sys.dm_exec_requests/sys.dm_os_waiting_tasks/Query Store for Waiting).

## Configure and monitor activity and performance

Azure Monitor is the central place to configure ongoing activity and performance monitoring. Alert rules are created from the Azure Monitor blade and can be scoped three ways (illustrated with virtual machines, but generalizable): a list of resources in one region within a subscription; all resources of a type in one region across one or more resource groups; or all resources of a type in an entire subscription and region. The rule-creation flow is consistent regardless of scope: select New Alert Rule (resource/subscription/resource group pre-populate if launched from within a resource's own blade), add a Condition by picking the metric to alert on (e.g., Percentage CPU), and choose either a static threshold (e.g., alert if CPU exceeds 80% over a period) or a Dynamic Threshold that learns the metric's historical behavior — including seasonality — and alerts on abnormal deviation rather than a fixed number. Both alert types support Boolean comparison operators (greater than/less than) and aggregations (average, minimum, maximum, count, total).

An alert on its own only logs to storage unless paired with an action group, which is optional but defines the actual response: notification types include email/SMS/push/voice or emailing an Azure Resource Manager role; automation types include an Automation Runbook, Azure Function, Logic App, secure webhook, webhook, or ITSM integration.

Metrics are retained for 93 days in Azure Monitor before being purged, with archival to Azure Storage available for longer retention; the metrics dashboard supports flexible time-range filtering (last 30 minutes, last hour, last 4/12 hours, or a custom picker) for reviewing past behavior and diagnosing historical incidents.

Query Performance Insight, reached from the Intelligent Performance section of an Azure SQL Database's blade, gives a day-to-day activity view without manual scripting: it offers Resource Consuming Queries (top five by CPU, Data IO, or Log IO — CPU by default), Long Running Queries (top five by duration over the prior 24 hours, summed), and a Custom tab with more flexible drill-down across CPU, Log IO, Data IO, and memory (each metric's ceiling is set by the database's service tier and compute size). Drilling into an individual query surfaces its query ID, text, aggregation type, and time period; that same query ID correlates directly to Query Store for deeper plan-level analysis. Query Performance Insight itself does not show execution plans — you have to cross into Query Store for that.

## Monitor by using database watcher

Database watcher (in preview) is a monitoring solution purpose-built for Azure SQL Database and Azure SQL Managed Instance, giving comprehensive visibility into performance, configuration, and health across a whole SQL estate — databases, elastic pools, and managed instances together, rather than one resource at a time.

Its architecture centers on a central data store, provisioned inside your own Azure subscription, into which monitored resources continuously feed time-series monitoring data — that data store can be an Azure Data Explorer cluster (paid or the free tier) or a Real-Time Analytics database in Microsoft Fabric. Collection and ingestion happen within seconds, giving low-latency visibility, and the tool exposes configurable targets, datasets, collection frequency, and retention. Once data lands in the data store, it can be queried and analyzed directly with tools like Azure Data Explorer or Fabric Real-Time Analytics, or viewed through built-in Azure portal dashboards that provide a single-pane-of-glass view across the whole monitored estate, with drill-down into any individual resource. Database watcher also ships parameterized templates for common alert rules and supports building fully custom alerts.

To configure it: in the Azure portal, search "Database Watchers" and select Create; choose the subscription, resource group, name, and region; configure the data store on the Data store tab; choose the Azure SQL Database or Managed Instance targets to monitor on the SQL targets tab; then review and create.

## Monitor by using Extended Events

Extended Events is a lightweight, highly configurable event-monitoring engine available across SQL Server and Azure SQL, functionally a successor to SQL Server Profiler that adds far more event coverage while keeping collection overhead low. Typical use cases include troubleshooting blocking and deadlocking, identifying long-running queries, monitoring DDL operations, logging missing column statistics, observing memory pressure, and tracking long-running physical I/O. Filters can be applied per event/field to keep collection overhead down and focus on the problem at hand.

Events are grouped into four channels reflecting intended audience: **Admin** events target end users/administrators for well-understood, actionable problems (e.g., an XML deadlock report); **Operational** events support analysis/diagnostics of common problems and can trigger further action (e.g., an availability-group database changing state during failover); **Analytic** events are high-volume, performance-related events (e.g., tracing stored procedure or query execution); **Debug** events are undocumented and reserved for use under Microsoft support guidance. Events are organized into sessions, each of which can host many related events, and each session writes to a target — the place where the engine records occurrences. Common targets:

| Target | Description | Processing |
|---|---|---|
| Event Counter | Counts all events occurring during a session, without full data capture overhead | Synchronous |
| Event File | Writes session output from memory to a file on disk (blob storage for Azure SQL PaaS) | Asynchronous |
| Event Pairing | Flags events expected to occur in pairs (e.g., lock acquire/release) that fail to match | Asynchronous |
| Event Tracing for Windows (ETW) | Correlates SQL Server events with Windows OS event data | Synchronous |
| Histogram | Like Event Counter, but bucketed by a specific event column or action | Asynchronous |
| Ring Buffer | In-memory circular buffer; not persisted to disk, useful for live observation | Asynchronous |

Most targets process asynchronously (data written to memory, then flushed to disk later to reduce I/O overhead); ETW and Event Counter targets are the exceptions and process synchronously.

Sessions can be created through SSMS's New Session dialog (Management > Extended Events > Sessions > New Session) using built-in templates grouped as Locks and Blocks, Profiler Equivalents, Query Execution, and System Monitoring, or built manually by adding individual events (e.g., sp_statement_completed, sql_batch_completed, sql_statement_completed). Session options include starting automatically at server startup, starting immediately on creation, and enabling causality tracking (adds a GUID and sequence number to each event's output so you can reconstruct the order events occurred). Global fields (also called actions) let you attach extra common data to every captured event. Filters apply to a single field on a single event, so filtering out system connections (sqlserver.is_system = 0) across three events, for instance, requires three separate filters — one per event.

Sessions can also be scripted in T-SQL:

```sql
IF EXISTS (SELECT * FROM sys.server_event_sessions WHERE name='test_session')
    DROP EVENT session test_session ON SERVER;
GO

CREATE EVENT SESSION test_session
ON SERVER
    ADD EVENT sqlos.async_io_requested,
    ADD EVENT sqlserver.lock_acquired
    ADD TARGET package0.etw_classic_sync_target (SET default_etw_session_logfile_path = N'C:\demo\traces\sqletw.etl' )
    WITH (MAX_MEMORY=4MB, MAX_EVENT_SIZE=4MB);
GO
```

Sessions can be scoped to a server or a database, must be explicitly started (via ALTER ... SET STATE or through SSMS), and a catalog of available events, actions, and targets can be queried with:

```sql
SELECT obj.object_type, pkg.name AS [package_name], obj.name AS [object_name], obj.description AS [description]
FROM sys.dm_xe_objects AS obj
    INNER JOIN sys.dm_xe_packages AS pkg ON pkg.guid = obj.package_guid
WHERE obj.object_type in ('action', 'event', 'target')
ORDER BY obj.object_type, pkg.name, obj.name;
```

Extended Events, using sys.dm_tran_locks joined with sys.dm_exec_requests style approaches, is also called out specifically as a good ongoing tool for monitoring blocking problems given their sporadic, hard-to-catch-in-the-moment nature. Deadlocks specifically are recorded automatically in the system_health session, which is enabled by default.

## Configure Query Store

Query Store is a per-database feature that automatically captures the history of queries, their execution plans, and runtime statistics, purpose-built to simplify performance troubleshooting and query tuning, and it also surfaces database usage patterns and resource consumption over time.

It's structured as three internal stores: the **plan store** (estimated execution plan information), the **runtime stats store** (execution statistics), and the **wait stats store** (persisted wait statistics).

Query Store is enabled by default for Azure SQL databases. For SQL Server and Azure Synapse Analytics it must be turned on explicitly:

```sql
-- SQL Server
ALTER DATABASE <database_name> SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE);

-- Azure Synapse Analytics
ALTER DATABASE <database_name> SET QUERY_STORE = ON;
```

Internally, Query Store integrates with the query pipeline at multiple points, writing to disk asynchronously to minimize I/O overhead: on first execution, a query's text and initial estimated plan are captured; on recompile, any newly generated plan is persisted alongside prior plans, and execution stats per plan are tracked for comparison; during compile/recompile checks, Query Store checks whether a forced plan exists and, if the procedure cache's plan differs, triggers a recompile to use it; and on every execution, runtime statistics are aggregated into the store.

Configuration-relevant database-scoped settings tie back here too — recovery model, the automatic-tuning FORCE_LAST_GOOD_PLAN option, auto create/update statistics (including asynchronous statistics updates), and Query Store's own options are all set via ALTER DATABASE, distinct from the ALTER DATABASE SCOPED CONFIGURATION surface used for things like MAXDOP.

## Monitor by using Query Store

Once enabled, Query Store's views appear under the database's Query Store folder in SSMS Object Explorer (under System Views for Azure Synapse Analytics), each sharing a consistent pane layout: a query list, a plan-summary pane showing persisted plans over time for the selected query, and a graphical plan pane for the selected plan — with toolbar controls to force or unforce a plan directly from the UI. Plan forcing can also be done purely in T-SQL with `EXEC sp_query_store_force_plan @query_id=73, @plan_id=79`.

Common scenarios Query Store is used for: identifying and fixing regressions from inferior plan selection; identifying and tuning the highest resource-consuming queries; A/B testing the impact of database/application changes; verifying performance stability after a SQL Server upgrade; finding the most frequently run queries; auditing plan history for a given query; identifying and improving unplanned/ad-hoc workloads; understanding which wait categories dominate and which queries/plans drive them; and analyzing usage patterns (CPU/IO/memory) over time.

Specific views:

- **Regressed Queries** — surfaces queries whose execution metrics (duration, CPU time, row count, etc., with total/average/min/max/stddev statistics) have degraded over a chosen window, ranked top 25; lets you compare historical plans and force an earlier, better one. This matters because the plan cache only retains the most recent plan and can evict it under memory pressure, whereas Query Store retains multiple historical plans per query.
- **Overall Resource Consumption** — total resource consumption (execution count, duration, wait time, etc.) over a timeframe, with interactive charts that drill through to the contributing queries; useful when overall system resource contention is the concern (e.g., CPU pinned).
- **Top Resource Consuming Queries** — top 25 queries by a chosen metric/statistic/timeframe; useful for spotting unplanned workload patterns (e.g., ~90% of top consumers by execution count run only once).
- **Queries With Forced Plans** — lists queries with an active forced plan, so you can reassess whether the forced plan is still the right choice and unforce it if not.
- **Queries With High Variation** — surfaces queries with the highest variation/standard deviation for a chosen metric, useful for stabilizing unpredictable performers.
- **Query Wait Statistics** — analyzes the most active wait categories for the database (23 wait categories currently exist) as an interactive chart, drilling through to the queries contributing to a selected category; filterable by total/average/min/max/standard-deviation wait time.
- **Tracking Query** — full execution history for one specific query ID, with a checkmark flagging executions that used a forced plan; useful for confirming a forced plan's stability over time.

Automatic plan correction builds directly on Query Store data: once Query Store is enabled (SQL Server 2017+ or Azure SQL Database), the engine watches for plan regressions and surfaces recommendations in sys.dm_db_tuning_recommendations, including ready-to-run T-SQL to force the earlier good plan. If you trust the recommendations, you can let SQL Server force plans automatically via `ALTER DATABASE ... SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON)` (Query Store must be enabled and in READ_WRITE mode, or the statement fails), or through the Azure portal/REST APIs for Azure SQL Database specifically. Automatic plan-correction recommendations are always generated wherever Query Store runs; for new Azure SQL Database databases, FORCE_PLAN is enabled by default. Once forcing is active, the engine keeps watching: if the forced plan doesn't outperform the old one it's unforced and a fresh plan compiled; if it does keep outperforming, it stays forced until a recompile occurs; a forced plan otherwise reverts to the last known good plan after 15 executions if things go wrong.

Query Store also tracks per-query wait statistics, though at less granularity than the wait-stats DMVs, and provides Query Store hints — a way to reshape a query's plan without touching application code, useful when query text is hardcoded or generated. The workflow: find the query_id via the Query Store catalog views, built-in reports, or Query Performance Insight, then run `EXEC sys.sp_query_store_set_hints @query_id = 42, @query_hints = N'OPTION(RECOMPILE, MAXDOP 1)'`. Typical uses include forcing a recompile every execution, capping MAXDOP for a statistics-update operation, forcing a Hash join instead of Nested Loops, or pinning one query to an older compatibility level (e.g., 110) while the database itself runs a newer one.

## Identify and resolve session blocking

Locking underpins the atomicity, consistency, and isolation guarantees of the relational model; blocking occurs when one session holds a lock on a resource (row, page, table, database) and a second session requests an incompatible lock on that same resource. Locks are normally held briefly and released quickly — locking itself happens constantly and is healthy; it only becomes a problem when it isn't resolved promptly. SQL Server locks the smallest amount of data necessary for a given operation to maximize concurrency, but because every lock consumes memory, holding thousands of fine-grained locks isn't cost-free — if a single statement needs to lock more than 5,000 rows on one object, SQL Server escalates those row locks into a single table lock (lock escalation).

Two broad categories of blocking-driven performance problems exist: a process holding locks for an extended period before release (degrading concurrency for others), and a process that acquires locks and never releases them (requiring administrator intervention). Deadlocking is the specific case where two transactions each hold a lock the other needs and each waits on the other indefinitely; SQL Server detects this and kills one transaction (the "deadlock victim"), chosen as whichever has done the least work to roll back. Deadlocks are logged by default in the system_health Extended Events session.

The most common root cause of long-running blocking is a transaction that's simply never committed — Autocommit is the default mode (each statement is its own implicitly-committed transaction), but explicit `BEGIN TRANSACTION ... COMMIT TRANSACTION` blocks give developers finer control; forgetting the COMMIT leaves the transaction (and its locks) open indefinitely. Row versioning is the other main concurrency mechanism: when a row-versioning isolation level is enabled, the engine maintains prior row versions in tempdb so read queries don't block writers in mixed OLTP/reporting workloads.

To monitor open transactions awaiting commit or rollback, query sys.dm_tran_active_transactions joined to sys.dm_tran_session_transactions and sys.dm_exec_sessions (with sys.dm_exec_requests and sys.dm_exec_input_buffer for extra context) — this surfaces session ID, database, transaction begin time and duration, transaction type/state, and the originating login/host/program.

For ongoing blocking detection, sys.dm_tran_locks joined with sys.dm_exec_requests shows locks currently held per session, but Extended Events run continuously is described as a more effective monitoring approach given blocking's sporadic nature. Blocking problems generally trace back to either poor transactional design (missing COMMIT, oversized transactions, distributed transactions across linked servers) or long-running transactions caused by schema design gaps (e.g., an UPDATE against a column with no supporting index).

Isolation level choice directly governs how long locks are held (though it never changes the exclusive lock taken by the writer itself): **Read Uncommitted** allows dirty reads and is the lowest isolation level; **Read Committed** (SQL Server's default) reads only committed data and releases read locks immediately after the read; **Repeatable Read** holds both read and write locks until transaction end; **Serializable** is the strictest, holding all read/write locks until transaction end. Two additional row-versioning-based levels avoid locking on reads entirely: **Read Committed Snapshot**, which takes no row/page locks on reads and presents a snapshot as of query start (ideal for frequent reporting queries against an OLTP database, to keep reads from blocking writes), and **Snapshot**, which gives full transaction-level read consistency via row versioning but is vulnerable to update conflicts — if a snapshot transaction reads data another transaction has since modified, its own update is terminated and rolled back (a risk Read Committed Snapshot doesn't share). Isolation level is set per session with `SET TRANSACTION ISOLATION LEVEL { READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SNAPSHOT | SERIALIZABLE }` — there is no way to set a database- or user-wide default; it's always a session-level setting.

## Identify performance issues using dynamic management views (DMVs)

SQL Server ships several hundred dynamic management objects — views (DMVs) and functions (DMFs), though "DMV" is commonly used loosely for both — exposing internal state for monitoring health, diagnosing problems, and tuning performance. They're scoped either at the server level (requiring VIEW SERVER STATE permission) or the database level (requiring VIEW DATABASE STATE), and are named with the sys.dm_ prefix followed by functional area and specific object name. Broadly they fall into three categories: database-related, query-execution-related, and transaction-related objects. Azure SQL Database's DMV surface differs from on-premises SQL Server: some are server-scoped and simply don't apply to the Azure model (e.g., wait_stats is server-scoped and doesn't directly apply), while others are Azure-specific, like sys.dm_db_resource_stats, which has no on-prem equivalent.

Key DMVs by purpose:

- **sys.dm_os_wait_stats** (sys.dm_db_wait_stats for Azure SQL Database) — aggregate wait statistics since startup or last clear; **sys.dm_exec_session_wait_stats** — active session-level waits; **sys.dm_os_waiting_tasks** — live, per-task wait detail (versus the aggregated view in sys.dm_os_wait_stats).
- **sys.dm_db_index_physical_stats** — index fragmentation for b-tree indexes; **sys.dm_db_column_store_row_group_physical_stats** — the columnstore equivalent.
- **sys.dm_db_stats_properties** — last-updated date, row count, and rows sampled for statistics, used to spot stale statistics.
- **sys.dm_db_tuning_recommendations** — automatic-tuning/plan-regression recommendations (SQL Server 2017+ and Azure SQL Database); **sys.database_automatic_tuning_options** — which automatic tuning features are enabled/desired/actual, with reason codes.
- **sys.dm_db_missing_index_details** — recommended indexes the engine has flagged as missing; **sys.dm_db_index_usage_stats** and **sys.dm_db_index_operational_stats** — usage/operational stats for existing indexes, used to find unused or duplicate indexes worth dropping.
- **sys.dm_exec_cached_plans**, cross-applied with **sys.dm_exec_sql_text** and **sys.dm_exec_query_plan** (or, for last-actual-plan detail, **sys.dm_exec_query_plan_stats**) — inspecting cached plans and their text; on older SQL Server versions without Query Store, this combination is the fallback for plan investigation, though unlike Query Store it can't show how a plan changed over time.
- **sys.dm_exec_requests** — snapshot of currently executing requests, including wait type/state (e.g., filtering for RUNNABLE + SOS_SCHEDULER_YIELD to check CPU capacity); **sys.dm_exec_query_stats** — aggregated stats for cached query plans (unlike Query Store, only reflects what's currently cached); **sys.dm_exec_procedure_stats** — the same idea at the stored-procedure level.
- **sys.dm_tran_locks** — currently held locks, typically joined to sys.dm_exec_requests for blocking analysis; **sys.dm_tran_active_transactions** / **sys.dm_tran_session_transactions** — open-transaction tracking.
- **sys.dm_xe_objects** / **sys.dm_xe_packages** — catalog of available Extended Events events, actions, and targets.
- **sys.dm_db_resource_stats** (Azure SQL Database) and **sys.server_resource_stats** (Managed Instance) — CPU/memory/I/O resource usage snapshots taken every 15 seconds; **sys.dm_user_db_resource_governance** (Azure SQL Database) and **sys.dm_instance_resource_governance** (Managed Instance) — actual configuration/capacity settings enforced by resource governance for the database/pool or instance.

## Identify and implement index changes for queries

Index tuning starts from evaluating existing index usage with sys.dm_db_index_operational_stats and sys.dm_db_index_usage_stats, then carefully weighing the removal of unused or duplicate indexes — with the caveat that some indexes are only exercised by infrequent (monthly/quarterly/annual) processes and shouldn't be judged solely on recent usage; it can be reasonable to build such indexes shortly before the scheduled operation that needs them instead of maintaining them year-round. Expensive queries surfaced by Query Store or Extended Events should drive manually crafted indexes. New indexes should be built and validated in a nonproduction environment first, watching for hardware differences (memory, CPU count) between environments that could make the execution plan behave differently once in production, before rolling changes forward.

Column order in a composite index matters: the leading column drives the index's column statistics and largely determines whether the optimizer picks the index at all, so the leading column should ideally be selective and appear in the WHERE clause of many queries. Equality-comparison columns should precede inequality-comparison columns, and more selective columns should precede less selective ones. A change-control discipline is recommended — keeping index-creation scripts in source control before dropping an index so it can be quickly recreated if an infrequently run query later needs it.

Missing-index signals in an execution plan show up as a Clustered Index Scan, or as a Nonclustered Index Seek paired with a Key Lookup (indicating the existing nonclustered index doesn't cover all needed columns). sys.dm_db_missing_index_details reports the engine's own missing-index recommendations, but creating every suggested index without evaluating it in context isn't advisable — indexes cost write performance and storage, so gains must outweigh those costs.

Design-level indexing guidance: understand the workload (insert-heavy tables benefit less from extra indexes than read-heavy/data-warehouse tables); optimize around the most frequently executed queries; favor integer, unique, or non-null columns for index keys; keep nonclustered indexes on predicate/join columns as narrow as possible to limit maintenance overhead; and weigh table size (small-table scans are cheap; large-table scans are expensive, making indexes matter more there). Covering indexes — adding nonkey columns via the INCLUDE feature at the leaf level — eliminate Key Lookup operations by satisfying the whole query from the index alone. Filtered indexes target large tables where a big share of rows share one value in a column (e.g., `CREATE ... WHERE CurrentFlag = 1` to index only currently-employed rows efficiently), and indexes can also be created on views containing aggregations or joins.

Resumable index operations (introduced in SQL Server 2017, online-only) let an index build/rebuild be paused and resumed later — valuable both for controlling maintenance-window impact and for recovering from a large index build that would otherwise have to be killed and restarted from scratch if it needed to be interrupted:

```sql
CREATE INDEX IX_Customer_PersonID_ModifiedDate 
    ON Sales.Customer (PersonID, StoreID, TerritoryID, AccountNumber, ModifiedDate)
WITH (RESUMABLE=ON, ONLINE=ON)
GO

ALTER INDEX IX_Customer_PersonID_ModifiedDate ON Sales.Customer PAUSE
GO
```

Progress can be checked via sys.index_resumable_operations.

At the design level (relevant when index changes require schema-aware judgment), clustered index keys should be as narrow as possible and built on unique/high-distinct-value columns, ideally ones also used for frequent sequential access/sorting, since data stored in that clustered order avoids repeated sort costs. Only one clustered index can exist per table (a table without one is a heap, typically reserved for staging tables). Nonclustered indexes are separate structures pointing back to the underlying data row (or the clustering key), and multiple can exist per table; both clustered and nonclustered indexes can be declared unique (automatic for PRIMARY KEY/UNIQUE constraints). Columnstore indexes are a distinct family suited to large aggregation/analytic workloads: clustered columnstore indexes store the whole table in columnar form (unsorted); nonclustered columnstore indexes are used when a column's type isn't columnstore-eligible (XML, CLR, sql_variant, ntext, text, image) or to support hybrid transactional/analytical (HTAP) patterns via a filtered nonclustered columnstore index (commonly filtered on a date column) so inserts and reporting can run concurrently. Columnstore's per-column storage reduces I/O (only needed columns are scanned) and improves compression (similar values cluster together), and pairs with batch execution mode, processing roughly 900 rows at a time instead of row-by-row — batch mode on rowstore can approach columnstore-like gains for some analytic queries (up to ~5x), though it doesn't fully match columnstore read performance. Bulk loads of 102,400+ rows load directly into the columnstore (rowgroups can hold up to ~1,024,000 rows; fewer, fuller rowgroups mean fewer rowgroups to scan on SELECT); smaller loads land in a b-tree "delta store" first and get asynchronously moved into the columnstore by the tuple mover — open delta stores hurt read performance until compressed, which can be forced early with the COMPRESS_ALL_ROW_GROUPS reorganize option.

## Recommend query construct modifications based on resource usage

The most common driver of database performance problems is suboptimal query construction, which indirectly manifests as CPU, storage, and memory pressure (e.g., missing indexes forcing far more data to be read than necessary) — tuning the query pattern itself is recommended before chasing hardware upgrades. Relational engines perform best on set-based operations (INSERT/UPDATE/DELETE/SELECT manipulating whole sets); the alternative, row-based processing via cursors or WHILE loops, scales linearly with row count and becomes a bottleneck as data grows.

Recognized anti-patterns to flag and rewrite:

- **Cursors/WHILE loops** in place of set-based logic.
- **Multi-statement table-valued functions (MSTVFs)** — treated like tables by the optimizer but, lacking real statistics, historically used a fixed row-count estimate (one row pre-2017, or 100 in some versions), producing bad plans once actual row counts diverged; inline TVFs, by contrast, are treated like views and don't have this problem.
- **Scalar user-defined functions** — historically executed iteratively (effectively row-at-a-time), poorly costed in the plan, and blocked parallelism; Intelligent Query Processing's scalar UDF inlining (compatibility level 150) substantially improves this by transforming them into scalar subqueries.
- **Non-SARGable predicates** — a SARGable predicate ("Search ARGument") is shaped so the optimizer can use an index SEEK rather than a scan; leading-wildcard LIKE patterns (`LIKE '%SMITH%'`) and functions wrapped around a column (`WHERE CONVERT(CHAR(10), CreateDate, 121) = '2020-03-22'` or `WHERE LEFT(City,1) = 'M'`) are classic non-SARGable forms that force scans even when a supporting index exists; rewriting `LEFT(City,1)='M'` as `City LIKE 'M%'` (no leading wildcard) restores seek eligibility. Presence of a SARG doesn't guarantee a seek — the optimizer can still cost a scan as cheaper, particularly when the predicate matches a large fraction of the table — but absence of a SARG guarantees the optimizer won't even evaluate a seek.
- **Using the database as an application/service layer** — offloading JSON conversion, string manipulation, or heavy computation into T-SQL, or pulling entire result sets back to compute client-side, both drive excess CPU/IO; the database should be reserved for data access and set-based aggregation.

Missing indexes are flagged directly in execution plans (Clustered Index Scan; Nonclustered Index Seek + Key Lookup) and via sys.dm_db_missing_index_details, with sys.dm_db_index_usage_stats / sys.dm_db_index_operational_stats showing whether existing indexes are actually used.

Missing or stale statistics are another resource-usage driver: Azure SQL defaults to AUTO_UPDATE_STATISTICS = ON, but pre-SQL Server 2016 behavior didn't trigger an automatic update until roughly 20% of a table's rows had changed — trace flag 2371 (pre-2016) made that threshold scale dynamically down as tables grew; this dynamic behavior is now default in current SQL Server, Azure SQL Database, and Managed Instance. sys.dm_db_stats_properties reports the last update time and modification count since, to identify statistics needing a manual refresh.

Where the optimizer's cost-based choices are simply wrong for the data despite good statistics and indexing, options include query hints, trace flags, plan forcing, and (for genuinely hard cases) engaging Microsoft support. An OPTIMIZE FOR hint can steer the optimizer's cardinality assumptions for a specific variable value without affecting the actual value used at execution time:

```sql
DECLARE @city_name nvarchar(30) = 'Ascheim', @postal_code nvarchar(15) = 86171;
SELECT * FROM Person.Address
WHERE City = @city_name AND PostalCode = @postal_code
OPTION (OPTIMIZE FOR (@city_name = 'Seattle'));
```

Parameter sniffing — compiling a parameterized query's plan based on the parameter value supplied on first execution — is efficient in general (it avoids recompiling for every distinct value) but breaks down badly under data skew (e.g., a table where 99% of 10 million rows share one ID value and 1% are unique): whichever value happened to compile the cached plan drives performance for every subsequent call regardless of the actual value passed. Mitigations, each with a tradeoff: `RECOMPILE` hint or `WITH RECOMPILE` (always current parameter value, but recompiles every call, raising CPU cost); `OPTIMIZE FOR UNKNOWN` (compiles against the column's data-distribution histogram instead of sniffing a specific value — consistent but not necessarily optimal for any one value); or conditional logic in the procedure that only forces a RECOMPILE for known-troublesome parameter values, trading development effort and data-distribution awareness for a targeted fix.

Query hints in general (appended via OPTION) override the optimizer's own choice for a specific SELECT/INSERT/UPDATE/DELETE: `MAXDOP <n>` (overrides sp_configure's MAXDOP and also overrides Resource Governor), `RECOMPILE` (fresh temporary plan, discarded after use), `FAST <n>` (optimizes for fast retrieval of the first n rows — most effective at low n; cost rises as n grows), `OPTIMIZE FOR` (compile against a specified variable value), `USE PLAN` (force a specific XML plan), and `{ LOOP | MERGE | HASH } JOIN` (force a join strategy; if multiple join hints are given, the optimizer picks the cheapest among them). Hints can be combined, e.g. `OPTION (HASH GROUP, FAST 10)`. Because a permanent hint locks in behavior, Microsoft's own guidance is to avoid them in production where possible — they prevent otherwise-beneficial schema changes from helping the query, and they forgo automatic benefit from optimizer improvements in later SQL Server versions. Query Store hints (sp_query_store_set_hints) provide the same capability without editing application code at all, useful when the query text is hardcoded or generated and can't practically be changed.

## Review execution plans

SQL Server's query optimizer is cost-based: it estimates cost for a subset of the plan space (not an exhaustive search — complex queries can have thousands of theoretically possible plans) using statistics on the referenced columns and indexes, and picks the lowest-cost plan it evaluated via heuristics. Because the whole process depends on statistics accuracy, keeping statistics current is foundational to good plan choices, even though SQL Server updates them automatically as data changes.

Processing pipeline for a query: (1) parsing for syntax correctness, producing a parse tree; (2) binding by the Algebrizer, which validates object/column existence and resolves data types, producing a query processor tree; (3) plan-cache lookup by query_hash (a hash of the T-SQL text) — a match reuses the cached plan; (4) if no cached plan exists, the cost-based optimizer generates and evaluates candidate plans from available statistics, producing a query execution plan; (5) execution, using either the cached or newly generated plan, producing the result set.

Plans capture, among other metadata, estimated row counts per operator, the memory grant required for memory-intensive operators like joins or sorts, the database compatibility level, degree of parallelism, and supplied parameter values if parameterized. A poorly estimated row count (e.g., estimating 10 million rows when only 100 return) can produce an oversized memory grant, which risks a RESOURCE_SEMAPHORE wait (SQL Server defaults to waiting up to 25× the query's estimated cost in seconds, capped at 24 hours, before executing) or, if insufficient memory is actually available at execution time, a spill to tempdb — slower than an in-memory operation.

Three ways to view a plan: the **Estimated Execution Plan** (`SET SHOWPLAN_ALL ON`; generated purely from compile-time statistics, doesn't execute the query or return results, and remains in effect until turned off); the **Actual Execution Plan** (`SET STATISTICS PROFILE ON`; requires the query to run, and adds runtime context — actual vs. estimated row counts, execution warnings, actual degree of parallelism, elapsed/CPU time); and **Live Query Statistics**, an animated, graphical-only view refreshing every second that blends estimated and actual data and shows the live handoff of rows between operators as execution proceeds. In SSMS, Ctrl+L shows the estimated plan immediately for any highlighted (or whole) query; Ctrl+M requires executing the query to produce the actual plan. Both estimated-plan generation and actual-plan capture add overhead, so capturing plans in production should be done deliberately.

Reading a graphical plan: execution flows right-to-left and top-to-bottom, so the rightmost/bottommost operator runs first; each operator shows a cost percentage relative to total query cost (percentages are rounded, so an operator showing 0% still costs something, just under 0.5%); connecting-line thickness reflects estimated row volume flowing between operators, and an unusually thick line often flags a tuning opportunity. Hovering an operator shows a tooltip with cost/row estimates (and actual-vs-estimated comparisons for actual plans); right-clicking and choosing Properties opens the full property list in a separate pane, including the output column list — useful for spotting whether a covering nonclustered index could eliminate a Key Lookup or Clustered Index Scan.

Lightweight query profiling reduces the overhead ("observer overhead") of capturing an actual plan — legacy profiling could add up to 75% overhead, while lightweight profiling caps around 2%. It collects row-count and logical/physical I/O data per operator and introduces the query_thread_profile extended event. In its first release it required trace flag 7412 enabled globally; if not enabled globally, the query-level hint `OPTION(USE HINT('QUERY_PLAN_PROFILE'))` turns it on for a single query and emits a query_plan_profile extended event on completion. Lightweight profiling is on by default in SQL Server 2019+ and in Azure SQL Database/Managed Instance, and is independently controllable per database via the LIGHTWEIGHT_QUERY_PROFILING database-scoped configuration option. Related to this, sys.dm_exec_query_plan_stats returns the last known actual execution plan for a given plan handle — enabled globally with trace flag 2451, or per-database via the LAST_QUERY_PLAN_STATS database-scoped configuration option — letting you retrieve last-actual-run stats for any cached query cheaply, e.g. by cross-applying sys.dm_exec_cached_plans with sys.dm_exec_sql_text and sys.dm_exec_query_plan_stats.

Troubleshooting workflow for a problematic query generally splits into two cases: a query that consistently performs poorly (hardware constraints, poor query structure, compatibility-level effects, missing indexes, or bad optimizer plan choices), versus one that performs well sometimes and poorly other times (usually data skew interacting with a parameterized/sniffed plan, blocking, or hardware contention). Hardware-constraint symptoms are usually only visible under real production load rather than in an isolated single execution: CPU contention shows as elevated % Processor Time plus SOS_SCHEDULER_YIELD/CXPACKET waits; storage constraints show as elevated Disk Seconds/Read or Disk Seconds/Write at the OS level and PAGEIOLATCH_SH waits in the engine (with a 15-second threshold before SQL Server itself logs the I/O as slow).

## Implement index maintenance tasks

Index fragmentation happens as ordinary UPDATE/DELETE/INSERT activity causes the logical order of index pages to diverge from their physical order, forcing extra I/O to locate referenced data and degrading query performance. Two remediation operations exist: **reorganize**, an always-online operation that defragments the leaf level of an index (clustered or nonclustered) by physically reordering leaf pages to match logical order, compacting pages per the configured fill factor as it goes; and **rebuild**, which can run online or offline depending on the command/edition — an offline rebuild drops and recreates the index in place, while an online rebuild builds the new index in parallel to the existing one (requiring more space) before dropping the old one and renaming the new one into its place.

The standard guidance thresholds, evaluated against sys.dm_db_index_physical_stats (b-tree indexes) or sys.dm_db_column_store_row_group_physical_stats (columnstore indexes):

- Fragmentation between 5% and 30% → reorganize.
- Fragmentation above 30% → rebuild.

These are general recommendations, not hard rules — workload and data characteristics may call for more aggressive maintenance, or for deferring maintenance entirely on databases whose queries mostly perform seeks against specific pages. One side effect worth remembering: a rebuild also refreshes the index's statistics, while a reorganize does not.

Resumable rebuild (SQL Server 2017+) lets a rebuild be paused and resumed, controlling how long a single maintenance operation can monopolize the instance; SQL Server 2019 added the ability to also control MAXDOP for a resumable rebuild, giving more granular administrative control.

Automation differs by platform. SQL Server on an Azure VM has full access to SQL Server Agent or Windows Task Scheduler for custom maintenance jobs, letting administrators balance rebuild-versus-reorganize workloads for large databases. Azure SQL Managed Instance likewise has SQL Server Agent available. Azure SQL Database has neither SQL Server Agent nor Windows Task Scheduler, so index maintenance has to be driven through one of three alternatives: Azure Automation runbooks, a SQL Agent job on a separate SQL Server VM making a remote call, or Azure SQL elastic jobs.

## Implement statistics maintenance tasks

Statistics are stored as binary large objects (blobs) in the user database, capturing the distribution of data values across one or more columns of a table or indexed view. The query optimizer uses them to estimate cardinality (expected row counts returned), which in turn drives both the choice of execution plan and the choice of physical operation per step (e.g., index seek vs. scan) — accurate statistics are foundational to good plan selection.

To list user-defined statistics with their last-updated date:

```sql
SELECT sp.stats_id, name, last_updated, rows, rows_sampled
FROM sys.stats
    CROSS APPLY sys.dm_db_stats_properties(object_id, stats_id) AS sp
WHERE user_created = 1
```

With AUTO_CREATE_STATISTICS set to ON (the recommended default), the optimizer automatically creates statistics on indexed columns and on single columns referenced in query predicates. This covers most query plans adequately, but manual CREATE STATISTICS may still be warranted when: the Database Engine Tuning Advisor recommends it; a query predicate spans multiple columns not already covered by one index; a query selects from only a subset of the data; or a query is found to have missing statistics.

Statistics staleness is a recurring root cause of bad plans. Azure SQL defaults AUTO_UPDATE_STATISTICS to ON, but the pre-SQL Server 2016 default behavior didn't trigger a refresh until roughly 20% of a table's rows had been modified — for large tables this meant a lot of drift could accumulate before statistics caught up. Trace flag 2371 (pre-2016) made the modification threshold scale down dynamically as tables grew; this dynamic behavior is now the built-in default in current SQL Server, Azure SQL Database, and Azure SQL Managed Instance. sys.dm_db_stats_properties reports the last-updated time and modification count since that update, letting you target manual updates precisely where they're needed.

Automation for statistics maintenance follows the same platform split as index maintenance: SQL Server on an Azure VM or Managed Instance can use SQL Server Agent (or Windows Task Scheduler on the VM); Azure SQL Database, lacking both, relies on Azure Automation runbooks, a remote SQL Agent job from a VM, or Azure SQL elastic jobs.

## Configure database automatic tuning

Automatic tuning is a continuous monitoring/analysis feature that learns from ongoing workload behavior (via Query Store data) to identify and, optionally, self-correct performance issues. It matters because execution plans that were fine when created can degrade over time as schema, indexes, or the underlying data (and therefore statistics) evolve, leaving the compiled plan mismatched to current reality; automatic tuning also incorporates machine-learning-driven analysis of performance metrics to generate improvement suggestions or take autonomous corrective action. It works both on-premises and in the cloud for plan-regression detection; Azure SQL Database additionally supports automatic index tuning (creating or dropping indexes based on observed query performance).

**Automatic plan correction (FORCE_LAST_GOOD_PLAN):** using Query Store data, the engine detects when a plan has regressed and can automatically force the previously good plan. The conditions for automatic forcing to trigger: the previous (regressed) plan had a higher error rate than the recommended plan, the estimated CPU gain from switching was greater than 10 seconds, and the forced plan is confirmed to be performing better than the one it replaced. A forced plan reverts back to the last known good plan automatically after 15 executions if the query is later found to be underperforming again. Once forcing engages, the engine keeps monitoring: if the forced plan underperforms relative to the previous one, it's unforced and a new plan compiled; if it keeps outperforming, it remains forced until the next recompile. Enable it via:

```sql
ALTER DATABASE [WideWorldImporters] SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON);
```

— which requires Query Store to already be enabled and in Read-Write mode, or the ALTER statement fails. Recommendations (with ready-to-execute forcing statements) surface in sys.dm_db_tuning_recommendations (SQL Server 2017+ and Azure SQL Database); sys.database_automatic_tuning_options confirms which tuning features are actually enabled for a database, alongside desired/actual state and reason codes — also queryable directly:

```sql
SELECT name, desired_state_desc, actual_state_desc, reason_desc
FROM sys.database_automatic_tuning_options
```

**Automatic index management** (Azure SQL Database only — not available on-premises) learns from workload history and can automatically create or drop indexes to improve performance, surfaced through the Performance Recommendations page in the Azure portal. Index creation is resource-aware: the tuning engine monitors whether enough resources are available to build the index without degrading existing workloads and postpones the action if not. Safety is also built in: if a dropped index turns out to have hurt query performance, it's automatically recreated.

## Configure server settings for performance

Server- and instance-level performance configuration in this material centers primarily on virtual-machine and storage sizing rather than classic sp_configure server options (which appear mainly in the Resource Governor and MAXDOP contexts covered elsewhere).

Virtual machine sizing for SQL Server workloads should prioritize available memory and IOPs capacity. **Constrained cores** let you get a VM's full memory, storage, and I/O bandwidth while licensing (and paying for) a reduced vCPU count — Azure normally ties a fixed CPU-to-memory ratio per VM size, but SQL Server licensing is core-based, so constrained cores are valuable for memory/IO-heavy but not CPU-heavy workloads. Most production SQL Server workloads run comfortably on general purpose VM families; larger workloads needing more memory and/or CPU move to memory-optimized families. Resizing a VM requires a restart (typically fast), though switching between certain VM type families may require a deallocate-then-resize step, extending the outage to a few minutes.

Storage configuration best practices for SQL Server on Azure VMs: use a separate volume for data files versus the transaction log; enable read caching on the data-file volume but disable all caching on the log-file volume; provision roughly 20% extra IOPs/throughput headroom above measured peak workload needs; put tempdb on the local (D:) SSD, since tempdb is recreated on every restart and carries no data-loss risk there; enable instant file initialization to reduce file-growth overhead; move trace file and error log directories onto data disks; and for sub-millisecond latency requirements, choose Ultra disk over Premium SSD. The SQL Server VM resource-provider template in Azure Marketplace automates much of this (including creating storage pools and provisioning tempdb on local SSD via a startup task).

Beyond individual VM sizing, sys.dm_db_resource_stats (Azure SQL Database), sys.server_resource_stats (Managed Instance), sys.dm_user_db_resource_governance, and sys.dm_instance_resource_governance provide the server/instance-level resource-consumption and governance-configuration data needed to judge whether current server settings/sizing match the workload.

## Configure Resource Governor for performance

Resource Governor, introduced in SQL Server 2008 and available in SQL Server and Azure SQL Managed Instance, gives granular control over CPU, physical I/O, and memory for incoming connections — its primary use case is multitenant scenarios where several databases share one instance and performance needs to stay predictable across all tenants; a secondary use case is capping the resource footprint of maintenance operations (consistency checks, index rebuilds) so user queries retain enough resources during maintenance windows.

Three building blocks:

- **Resource pools** represent physical server resources. Two built-in pools always exist — **default** and **internal** — even with Resource Governor disabled; **internal** is reserved for critical engine functions and can't be restricted, while **default** (and any custom pools) can have limits configured: min/max CPU percent, a CPU percent cap, min/max memory percent, NUMA node affinity, and min/max IOPs per volume. All of these except min/max CPU percent are hard limits that can never be exceeded; min/max CPU percent only kicks in when there's actual CPU contention — e.g., a max of 70% still allows up to 100% usage when nothing else is competing for CPU, but caps at 70% once contention appears. Pool changes only affect new sessions, not ones already running — the one exception being external pools used for SQL Server Machine Learning Services, which can affect in-flight sessions.
- **Workload groups** are containers for classified session requests; again two built-ins exist (**default**, **internal**), each workload group maps to exactly one resource pool (though a pool can host multiple groups), and any connection not explicitly classified lands in the default group, using the default pool's resources.
- **The classifier function** runs once per new connection and returns the workload-group name to route that session into; returning NULL, "default", or a nonexistent group name routes the session to the default group. Because it runs on every connection, it needs to be efficient — an example classifying by login name:

```sql
CREATE FUNCTION dbo.RGClassifier()
RETURNS SYSNAME
WITH SCHEMABINDING
AS
BEGIN
DECLARE @WorkloadGroup AS SYSNAME
IF(SUSER_NAME() = 'ReportUser')
    SET @WorkloadGroup = 'ReportServerGroup'
ELSE IF (SUSER_NAME() = 'PrimaryUser')
    SET @WorkloadGroup = 'PrimaryServerGroup'
ELSE
    SET @WorkloadGroup = 'default'
RETURN @WorkloadGroup
END
```

More elaborate classifier logic is possible but should be checked for its own performance impact, since it executes on every new connection.

For SQL Managed Instance specifically, MAXDOP can additionally be configured through Resource Governor, on top of the ALTER DATABASE SCOPED CONFIGURATION and sp_configure mechanisms available elsewhere.

## Implement database-scoped configuration

Database-scoped configuration is the general trend of moving what used to be server-wide settings down to the database level, giving finer per-database control; many of these options tie into a database's compatibility level. Conceptually there are two syntactic families, with no functional significance to which family a given option belongs to: options set via **ALTER DATABASE SCOPED CONFIGURATION**, and options set via plain **ALTER DATABASE**.

Set through ALTER DATABASE: the recovery model (full vs. simple); the automatic-tuning FORCE_LAST_GOOD_PLAN option; auto-create/auto-update statistics (including whether statistics updates happen asynchronously); Query Store's own configuration; and snapshot isolation / read-committed-snapshot-isolation settings. (This is described as a subset, not an exhaustive list.)

Set through ALTER DATABASE SCOPED CONFIGURATION (or otherwise scoped to the database): MAXDOP, letting a database override the server's MAXDOP setting; Legacy Cardinality Estimation, letting a database opt back into the older cardinality estimator for queries that regress under the newer one — importantly, this can be combined with a newer compatibility level (140/150) so the database still benefits from Intelligent Query Processing even while using legacy cardinality estimation; Last Query Plan Stats (only active at compatibility level 150), which captures the last actual execution plan's stats; Optimize for Ad Hoc Workloads, which stores only a stub plan on first compile to shrink plan-cache footprint for workloads dominated by single-use ad hoc queries; and the lightweight-profiling-related settings LIGHTWEIGHT_QUERY_PROFILING and LAST_QUERY_PLAN_STATS, which can be toggled per database independent of the corresponding server-wide trace flags (7412 and 2451).

MAXDOP specifically deserves emphasis given how many mechanisms touch it: `ALTER DATABASE SCOPED CONFIGURATION` is supported for Azure SQL generally; the classic `sp_configure` "max degree of parallelism" server option is supported for SQL Managed Instance; MAXDOP query hints are fully supported everywhere; and for Managed Instance, MAXDOP can also be governed via Resource Governor. Raising MAXDOP lets more parallel threads work a single query (potentially faster) but at the cost of a larger memory grant, which can create memory pressure and, in columnstore-compression scenarios specifically, rowgroup trimming; lowering MAXDOP reduces memory pressure at the cost of per-query speed — the setting is a direct tradeoff between query speed and overall memory/storage efficiency.

Database compatibility level is the other major database-scoped setting: it governs optimizer behavior for that database and is commonly held back temporarily during a SQL Server version upgrade so existing queries keep the plans they had pre-upgrade; Microsoft supports running on an older compatibility level for an extended time, but recommends upgrading when feasible since most Intelligent Query Processing features require compatibility level 140 or 150 to activate (`ALTER DATABASE [WideWorldImportersDW] SET COMPATIBILITY_LEVEL = 150;`).

## Configure compute and storage resources for scaling

Azure SQL abstracts physical file placement away from the administrator — you can't put files on specific disks the way you could on-premises — but in exchange Azure SQL commits to specific I/O rate, IOPS, and latency guarantees at each service tier/compute size, so scaling those tiers is the primary lever instead of manual file placement.

For IOPS-bound workloads: confirm the chosen service tier/vCore level actually covers the workload's IOPS needs (measure on-premises IOPS before migrating, if migrating); restricted IOPS shows up as long I/O waits. In the vCore model, scaling up vCores, or moving to Business Critical or Hyperscale, addresses insufficient IOPS; in the DTU model, moving to Premium tier is the equivalent recommendation for production workloads. For latency-bound workloads: Business Critical or Hyperscale improve I/O latency for Azure SQL Database; for SQL Managed Instance, moving to Business Critical, or increasing file size/file count, improves latency; transaction log latency specifically may require batching into multistatement transactions rather than many small ones.

File-level scaling differs by platform. Azure SQL Database effectively has a single database file (Hyperscale typically uses several), with maximum size configured through the Azure interface and no ability to add more files. Azure SQL Managed Instance supports adding files and configuring their sizes (though not physical placement), and additionally supports user-defined filegroups for manageability. Proportional fill governs how writes are distributed across multiple files: SQL Server allocates new writes proportionally to each file's current size, so a very unevenly sized set of files (e.g., 10 GB and 1 GB) sees heavily skewed writes (~900 MB vs ~100 MB per 1 GB inserted) — in a write-heavy database like tempdb this uneven pattern can create a hotspot in the largest file.

Tempdb scaling specifically differs sharply between platforms. On-premises SQL Server auto-detects available CPUs at setup and creates up to eight evenly sized tempdb files, with trace flags 1117/1118 behaviors built permanently into the engine for tempdb (though only tempdb); administrators may add more files beyond eight for heavily tempdb-bound workloads, ideally matching CPU count. Tempdb data files are always placed on local SSD automatically in Azure SQL. Azure SQL Database scales tempdb file count with vCore count (2 vCores → 4 files) up to a maximum of 16 files, with file count not configurable via T-SQL (only via the deployment option) and max tempdb size scaled per vCore count; Managed Instance instead always provisions 12 tempdb files regardless of vCore count. MIXED_PAGE_ALLOCATION is fixed OFF and AUTOGROW_ALL_FILES fixed ON for tempdb and aren't configurable — these mirror the SQL Server-recommended defaults anyway. The SQL Server 2019 tempdb metadata optimization feature (targeting heavy latch contention) is not currently available in either Azure SQL Database or Managed Instance.

Underlying VM/disk-level scaling (for SQL Server on Azure VMs) uses Azure managed disks, which come in four performance tiers: **Ultra disk** (submillisecond latency, independently scalable IOPS/throughput/size on a single disk, best for mission-critical low-latency workloads); **Premium SSD** (single-digit-millisecond latency, high throughput, lower cost/more flexible than Ultra, and the only one of the four supporting read caching, stored on the local SSD to cut round trips for read-heavy workloads); **Standard SSD** (lightweight dev/test or low-IO web workloads needing predictable latency); and **Standard HDD** (infrequently accessed backups/file storage). Production SQL Server workloads typically run on Ultra, Premium SSD, or a mix. Where a single disk's IOPS/throughput ceiling isn't enough, Premium SSDs (not Ultra disk, which scales IOPS/throughput/size independently per disk already) can be striped across multiple disks using Windows Storage Spaces, with no redundancy configured in the pool (Azure already keeps three synchronous copies of each disk) — a pool of 10 P30 disks at 1 TB/5,000 IOPS each yields a combined 10 TB, 50,000-IOPS volume.

## Identify use cases for intelligent query processing (IQP) features

Intelligent Query Processing (IQP) is a family of optimizer improvements introduced across compatibility levels 140 and 150 that correct several long-standing anti-patterns (scalar UDFs, table variables) largely automatically, once a database is moved to compatibility level 150 (`ALTER DATABASE [WideWorldImportersDW] SET COMPATIBILITY_LEVEL = 150;`).

**Adaptive query processing** features, several enabled automatically under compatibility level 150 with no further changes required:

- **Adaptive joins** — defer the choice between a hash join and nested loops join until runtime, based on actual row counts flowing into the join; currently only available in batch execution mode.
- **Interleaved execution** — for multi-statement table-valued functions (MSTVFs): rather than relying on the old fixed row-count estimate (1 or 100 rows depending on version), the engine executes the MSTVF first to get an actual row count, then compiles the rest of the plan around that real number — directly fixing the classic MSTVF misestimation problem.
- **Memory grant feedback** — detects when the initial memory grant (computed from statistics-based row estimates) was badly wrong due to data skew, and adjusts the grant up or down on subsequent executions to avoid either a tempdb spill (grant too small) or reduced concurrency from over-allocation (grant too large).

**Table variable deferred compilation** addresses the same fixed-row-count problem for table variables (historically always estimated at one row): SQL Server 2019 analyzes the actual row count and compiles around it, similarly to interleaved execution for MSTVFs, except the correction happens at first compilation rather than dynamically mid-plan.

**Batch mode on rowstore** brings columnstore-style batch execution (processing rows in batches rather than one at a time) to rowstore tables, benefiting CPU-heavy calculation/aggregation queries by decoupling batch-mode processing from the requirement of having a columnstore index.

**Scalar UDF inlining** rewrites scalar user-defined functions — which previously executed iteratively, lacked proper cost estimation, and blocked parallelism — into scalar subqueries directly in the plan, in place of the old UDF operator, often yielding significant performance gains for queries that call scalar functions heavily.

**Approximate count distinct** targets the common data-warehouse pattern of counting distinct orders/users over a large table; it trades exactness for speed via a grouping-based approximation, guaranteeing a 2% error rate at a 97% confidence interval — appropriate for dashboards/reporting where an exact count isn't required but query latency matters.

Use-case takeaway: IQP is most valuable for workloads exhibiting the specific anti-patterns it targets — MSTVF- or table-variable-heavy code with unpredictable row counts, scalar-UDF-heavy queries, aggregation-heavy CPU-bound rowstore queries, data-skewed workloads causing bad memory grants, and large-table distinct-count aggregations — and requires no code rewriting to benefit from, only a compatibility-level bump to 150 (with the caveat that Legacy Cardinality Estimation can still be layered on top of compatibility level 150 for specific queries that regress under the newer cardinality estimator, without losing the rest of IQP's benefits).
