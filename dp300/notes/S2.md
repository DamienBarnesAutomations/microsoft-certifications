# Implement a secure environment

## Configure Microsoft Entra ID authentication for Azure SQL Database, Azure SQL Managed Instance, and SQL Server

On-premises SQL Server and SQL Server on Azure VMs support two authentication modes: SQL Server authentication, which stores login credentials inside SQL Server itself, and Windows Authentication, which relies on Active Directory (or, in Azure, Microsoft Entra ID — formerly Azure Active Directory). Azure SQL Database and Azure SQL Managed Instance replace Windows Authentication with Microsoft Entra authentication, since there's no on-premises Active Directory in the platform-as-a-service model. Microsoft Entra authentication reuses the same identity a user already has for the Azure portal or Microsoft 365, centralizes credential management (disabling a single Entra account revokes database access when someone leaves), and supports multifactor authentication (MFA) through push notifications in the Microsoft Authenticator app, text messages, or one-time access codes. Users enrolled in MFA must connect through SQL Server Management Studio using the "Universal Authentication with MFA" connection option rather than plain SQL login.

Microsoft Entra ID can be synchronized with an on-premises Active Directory so that the same credentials work consistently across both environments. A dedicated Microsoft Entra admin is set on the Azure SQL logical server (via the Azure portal, PowerShell, or Azure CLI only — never at the individual database level), and that admin effectively receives sysadmin-equivalent access across the server and every database it hosts. Best practice is to assign this admin role to a Microsoft Entra group rather than an individual account, so administrative access doesn't depend on one person's credentials remaining valid.

Separately from database-level authentication, all control-plane operations against Azure SQL Database (creating servers, configuring policies, etc.) are governed by Azure role-based access control (RBAC), which is decoupled from database security and scoped to subscription, resource group, or resource. RBAC governs what a principal can do through the Azure portal, Azure CLI, and Azure PowerShell, and lets organizations separate deployment/management duties from actual data access duties. Built-in RBAC roles reduce reliance on broad Owner/Contributor roles: SQL DB Contributor can create and manage databases but cannot connect to or read data in them; SQL Security Manager can manage security policies (such as auditing) but likewise has no data access; SQL Server Contributor can manage servers and databases without being able to access their contents. A typical pattern is a SQL Server Contributor deploying a server and then assigning a separate individual as the actual database admin — deployment and data access stay separated.

## Configure authentication for SQL on Azure VMs and Azure SQL Managed Instance

SQL Server running on an Azure VM behaves like on-premises SQL Server for authentication purposes: it supports both SQL Server authentication and Windows Authentication (domain-joined or Entra-synced), and administrators manage logins the same way they would on-premises, using CREATE LOGIN and Windows/Entra-integrated logins. Azure SQL Managed Instance sits between the two models — like SQL Server, it supports server-level logins and fixed server-level roles (sysadmin, serveradmin, securityadmin, processadmin, setupadmin, bulkadmin, diskadmin, dbcreator, public), and administrators can create new server-level logins, unlike in Azure SQL Database where new server roles cannot be created (only new logins can be added by administrators). Both SQL on Azure VMs and Managed Instance can also integrate with Azure Key Vault as an Enterprise Key Manager (EKM) to hold certificates and keys used for authentication-adjacent features such as Transparent Data Encryption, Backup Encryption, and Always Encrypted — this requires creating a SQL Server login and a mapped credential whose identity is the key vault name and whose secret is the key vault application ID, after which an asymmetric key created in Azure Key Vault can be mapped into the database with CREATE ASYMMETRIC KEY ... FROM PROVIDER.

## Configure security principals

Security principals are the entities — individuals or collections — that can request SQL Server resources and be granted permissions against them; they exist at either the server level or the database level, and their membership is either administrator-controlled or fixed by the platform. On Azure SQL Database, administrators can add new logins, but they cannot create new server-level roles.

Before principals, two supporting concepts matter: securables and schemas. Securables are the resources the authorization system protects (a table is a securable), and they're organized into three nested scopes — server, database, and schema — so access can be managed hierarchically rather than object-by-object. A schema groups objects into a namespace; every user has a default schema, and an unqualified reference such as `SELECT name FROM customers` is resolved first against the user's default schema, then against the built-in `dbo` schema, and if not found in either, the reference errors out. Best practice is to always schema-qualify object references (`SELECT name FROM SalesSchema.customers`). If a user has no default schema assigned, it defaults to `dbo`; when a user creates an object without specifying a schema, SQL Server tries to create it in that user's default schema, and fails if the user lacks permission to create objects there.

Logins are the principal used to connect to the instance (or server, in Azure SQL Database terms) and are stored at the instance level in the master database. Users are principals created at the database level and mapped to a login (or, for Entra/Windows identities, created directly as contained users). Contained users require the database to be configured for partial containment — enabled by default in Azure SQL Database, optional in SQL Server — and best practice for Azure SQL Database is to create users at the scope of the user database rather than master. A login only lets you connect; a mapped user in the target database is what authorization checks against, so both pieces are typically required outside of contained-user scenarios.

Database roles group permissions so they can be assigned collectively rather than per-user: create a role, add users as members, grant the role the needed permissions, and every member inherits them. Both built-in and custom roles exist; custom roles can be created at server or database level, but server roles can't be granted access to database objects directly, and server roles only exist in SQL Server and Azure SQL Managed Instance — never in Azure SQL Database. Application roles differ from database roles in that no user is made a member; instead, a user activates the role at runtime by supplying its preconfigured password, after which the role's permissions apply until deactivated.

SQL Server ships fixed database roles with predefined permissions in every database:

| Database role | Definition |
|---|---|
| db_accessadmin | Can create other users in the database; no access to schema or data. |
| db_backupoperator | Can back up the database in SQL Server/Managed Instance; confers no permission in Azure SQL Database. |
| db_datareader | Can read from every table and view in the database. |
| db_datawriter | Can INSERT, UPDATE, DELETE data in every table and view. |
| db_ddladmin | Can create/modify object definitions of any type; no data read/write access. |
| db_denydatareader | Blocks read access even if granted elsewhere. |
| db_denydatawriter | Blocks write access even if granted elsewhere. |
| db_securityadmin | Can grant access to other users, including to themselves — membership should be restricted to trusted users. |
| db_owner | Full administrative access by default; can still be blocked from data via deny roles — membership should be restricted to trusted users. |

Every database user is automatically a member of the `public` role, which by default has no permissions; granting permissions to `public` grants them to every user, including a guest account if enabled, so this should be done cautiously. Even privileged roles like db_owner can always see all data by default — Always Encrypted is the mechanism to shield sensitive columns from otherwise-privileged users.

For Azure SQL Database specifically, two virtual-master-database-only roles substitute for on-premises fixed server roles: `loginmanager` (create logins for the server, equivalent to the on-prem `securityadmin` server role) and `dbmanager` (create/delete databases on the server, equivalent to on-prem `dbcreator`). Azure SQL Database also exposes its own set of server-level roles: `MS_DatabaseConnector`, `MS_DatabaseManager`, `MS_DefinitionReader`, `MS_LoginManager`, `MS_SecurityDefinitionReader`, `MS_ServerStateReader`, and `MS_ServerStateManager`. On SQL Server and Azure SQL Managed Instance, the fixed server-level roles are sysadmin (any activity), serveradmin (server-wide config, can shut down the server), securityadmin (manage logins/passwords, grant/revoke server and database permissions — treat as equivalent to sysadmin), processadmin (kill processes), setupadmin (add/remove linked servers), bulkadmin (run BULK INSERT), diskadmin (manage backup devices), dbcreator (create/restore/alter/drop any database), and public (every login is a member; unlike other fixed server roles, permissions on public can be granted/denied/revoked).

## Create users from Microsoft Entra identities

A Microsoft Entra identity is turned into a database user with `CREATE USER [name@domain] FROM EXTERNAL PROVIDER;`, executed in the context of the target user database — the `FROM EXTERNAL PROVIDER` clause is what indicates the identity is resolved through Microsoft Entra ID rather than a local SQL login. This is the contained-user pattern: no separate server-level login is required first, because the Entra identity itself is the authentication source, and the resulting user only has access to the database in which it was created. This mirrors — but is distinct from — the SQL Server pattern where a login is created first in master (`CREATE LOGIN demo WITH PASSWORD = '...'`) and then a matching user is created in the target database with `CREATE USER demo FROM LOGIN demo`; logins authenticate to the server, but all authorization checks happen against the mapped user, so for Entra identities, the user creation step from an external provider does both jobs at once. Microsoft Purview's lineage-extraction scanning also relies on this pattern: a Purview managed identity is registered as a database user via `CREATE USER <purview-account> FROM EXTERNAL PROVIDER` and then added to `db_owner` with `sp_addrolemember` so it can query tables and metadata for scanning.

## Configure database and object-level permissions using graphical tools

The raw source material documents object-level permissions primarily through T-SQL rather than graphical tools, with one notable exception: the Always Encrypted Wizard in SQL Server Management Studio, reached by right-clicking a table in Object Explorer and selecting "Encrypt Columns...", which walks through column selection, encryption-type assignment, and master-key configuration without hand-writing T-SQL (it can also emit a PowerShell script instead of applying changes immediately). The Azure portal similarly exposes graphical panes for several security features covered elsewhere in this module — Transparent Data Encryption, Dynamic Data Masking, Data Discovery & Classification, and server/database Auditing are each configured from a "Security" section on the resource's blade. Beyond these specific panes, the source doesn't describe a dedicated graphical permissions-grant UI (an SSMS "Properties > Permissions" equivalent) distinct from the T-SQL GRANT/DENY/REVOKE statements detailed under least privilege and T-SQL authorization below.

## Apply the principle of least privilege for all securables

The principle is straightforward: users and applications should hold only the permissions required to complete their task, nothing broader. A common application of this is restricting an application's database access to EXECUTE on a defined set of stored procedures, with no direct table access at all — the application never needs raw SELECT/INSERT/UPDATE/DELETE rights if every data operation flows through procedures.

Ownership chaining is the mechanism that makes this pattern work without granting table-level rights directly: if a stored procedure and the table it accesses share the same owner, a user with only EXECUTE permission on the procedure can run it and have it read the table, inheriting access transiently and only for the duration of that execution — the user never gains standing rights to query the table directly. This chain breaks, however, when dynamic SQL is used inside the procedure (via `sp_executesql` or similar), because dynamic SQL executes outside the calling procedure's context; in that case the executing user's own permissions are checked against the underlying tables, and least-privilege design has to account for that by granting rights explicitly rather than relying on the chain. `EXECUTE AS <user>` (or `EXECUTE AS <login>`, available only in SQL Server and Managed Instance) temporarily switches the execution context to test or enforce narrower permission sets, and `REVERT` returns to the original context.

Because dynamic SQL is often the entry point for privilege escalation and injection risk, least-privilege design also means validating and constraining any user input that feeds into dynamically constructed statements, and being deliberate about which principal's permissions are in force when the dynamic SQL runs.

## Troubleshoot authentication and authorization issues

Connection failures can stem from reconfiguration, firewall rules, connection timeouts, incorrect login details, or the target Azure SQL Database/Managed Instance being over capacity. A specific category — transient faults — occurs when heavy workload increases cause Azure to dynamically reconfigure servers behind the scenes; the client briefly loses its connection, typically for under 60 seconds, during either a planned or unplanned reconfiguration event. Example transient error messages include "Cannot open database '%.*ls' requested by the login. The login failed," "Cannot process request. Not enough resources to process request," and "Cannot process request. Too many operations in progress for subscription '%ld'."

Monitoring guidance differs by failure type: for login failures, check the Azure Service Health dashboard for outages during the affected window; for resource-limit failures, monitor compute/storage consumption proactively and act before limits are hit; for authentication failures lasting longer than 60 seconds, or recurring more than once a day, file an Azure support request. Application-side, the recommended mitigation is retry logic rather than surfacing errors to the user — wait at least 5 seconds before the first retry, increase the delay exponentially on each subsequent attempt up to a 60-second cap, and always cap the total number of retries. A failed SELECT statement specifically should not be retried on the same connection — retry it on a new connection instead.

For the specific "Login failed for user '<name>'" error, the standard troubleshooting sequence is: check `sys.sql_logins` to see whether the login is disabled; if disabled, run `ALTER LOGIN <name> ENABLE;`; if the login doesn't exist at all, create it with `CREATE LOGIN`; connect to the target database and run `CREATE USER` to map a database user to that login; then either add the user to an appropriate role with `ALTER ROLE ... ADD MEMBER`, or grant object-level permissions directly with `GRANT`. Connection-string problems are also a common source of apparent auth failures, especially right after provisioning a database or making infrastructure changes — the Azure portal's "Connection strings" pane on the database blade provides the current string, which needs the password filled in (or server name updated) before being placed into the client application.

## Manage authentication and authorization by using T-SQL

Logins are created at the instance level (`CREATE LOGIN demo WITH PASSWORD = 'Pa55.w.rd'` in the context of master) and mapped to a database user with `CREATE USER demo FROM LOGIN demo`. Microsoft Entra identities skip the separate login step and are created directly as contained users with `CREATE USER [dba@contoso.com] FROM EXTERNAL PROVIDER;`. Database roles are created with `CREATE ROLE`, populated with `ALTER ROLE <role> ADD MEMBER <user>`, and granted rights with `GRANT <permissions> ON <securable> TO <role>` — for example, granting `SELECT, EXECUTE ON SCHEMA::Sales` to a `SalesReader` role lets every member select from any object and execute any procedure in that schema.

The four universal DML permissions — SELECT, INSERT, UPDATE, DELETE — apply to tables and views across all SQL Server platforms and can be GRANTed, DENYed, or REVOKEd. DENY always overrides a GRANT for the same principal and object: a user both granted and denied SELECT on a table will be denied. REVOKE removes a previously issued GRANT or DENY outright, restoring an unspecified state rather than the opposite permission. Additional table/view-scoped permissions include CONTROL (full rights, including the ability to delete the object), REFERENCES (view foreign keys), TAKE OWNERSHIP, VIEW CHANGE TRACKING, and VIEW DEFINITION. Functions and stored procedures support ALTER, CONTROL, EXECUTE, VIEW CHANGE TRACKING, and VIEW DEFINITION.

Column-level and schema-level scoping is possible by granting/denying/revoking against a narrower securable reference (e.g., `SCHEMA::Sales`), and row-level security (covered separately below) supplements this with predicate-based filtering. `EXECUTE AS USER = '<name>'` switches the session's execution context for testing permission boundaries, and dynamic SQL (`sp_executesql`, or building a T-SQL string programmatically as in `SELECT 'BACKUP DATABASE ' + name + ...  FROM sys.databases`) generates statements at runtime but, as noted above, executes outside any enclosing ownership chain, so permission checks apply to the executing principal directly rather than the calling procedure's owner.

## Implement transparent data encryption (TDE)

TDE encrypts an entire database at the page level: pages are encrypted as they're written to disk and decrypted when read into memory, so every data page at rest is protected, but TDE does not encrypt at the table or column level — anyone with appropriate permission to query the data sees it in plain text once it's in memory. TDE protects specifically against someone restoring a backup file or copying database/log files to an unsecured server; no decryption happens during backup, so the backup file itself stays encrypted. TDE uses AES or 3DES encryption and requires no application changes, and it factors into meeting various regulatory/compliance requirements around data at rest.

Databases created in Azure SQL Database after May 2017 have TDE enabled automatically (databases from before that date need it enabled manually); for Azure SQL Managed Instance, the cutoff is February 2019 for automatic enablement. By default, encryption uses a Microsoft-managed service key, but Azure also supports Bring Your Own Key (BYOK) — a customer-managed key generated outside Azure and uploaded to Azure Key Vault. If a customer-managed key is removed from Key Vault, active database connections are closed and further access is denied, giving the key-vault administrator an effective kill switch.

Enabling TDE manually in SQL Server is a four-step T-SQL sequence: create a master key in master (`CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<pwd>'`), create a certificate in master (`CREATE CERTIFICATE MyServerCert WITH SUBJECT = '...'`), create a database encryption key in the target database referencing that certificate (`CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256 ENCRYPTION BY SERVER CERTIFICATE MyServerCert`), and finally turn encryption on (`ALTER DATABASE <db> SET ENCRYPTION ON`). Once enabled, encrypting the existing database takes time proportional to its size, since every page must be read, encrypted, and rewritten; this background process runs at low priority to avoid starving I/O or CPU for normal workloads. The certificate used for TDE must be backed up manually and stored securely — losing it means a restored backup can't be decrypted and is effectively unusable. For an Always On Availability Group, the same certificate must be backed up and restored onto every secondary that will host a copy of the encrypted database.

Customer-managed keys (BYOK) via Azure Key Vault give full and granular control over the TDE protector's usage and management, transparency into that usage, the ability to separate duties between key management and data management within the organization, the ability for a key-vault administrator to revoke access and render the database inaccessible, centralized key management, and stronger customer trust since Key Vault is architected so Microsoft cannot see or extract the encryption keys. A user-assigned managed identity (UMI) can additionally be paired with customer-managed keys so that key-vault access can be pre-authorized for a logical server before the server or database even exists, the same UMI can be reused across multiple servers (avoiding per-server system-assigned identity setup), and CMK-at-creation-time can be enforced via a built-in Azure policy. Automatic key rotation is available for customer-managed TDE keys: the server periodically checks Key Vault for a new key version and, if found, rotates the TDE protector to the new version within 60 minutes. Azure Disk Encryption is a separate, complementary layer available for Azure VMs, and when combined with TDE gives data multiple layers of encryption protection.

## Implement object-level encryption

The raw source material's coverage of encryption below the whole-database level centers on column-level protection via Always Encrypted (detailed in its own section below) rather than describing legacy cell-level/symmetric-key encryption functions (ENCRYPTBYKEY/DECRYPTBYKEY-style object encryption) directly. What it does establish explicitly is the boundary that makes object-level encryption necessary in the first place: TDE only protects data at rest at the page level and grants no protection against a user with legitimate query permissions, or against a privileged role like db_owner, who by default can always see all data in the database regardless of TDE. Always Encrypted is the mechanism the source presents for closing that gap — encrypting specific columns so that even a high-privilege database principal (DBA, server admin, cloud admin) cannot see plaintext values without possessing the separate encryption keys, which live outside the database engine itself. Object-level (column) encryption is layered on top of TDE, not a replacement for it, and the two are complementary: TDE stops raw disk/backup exposure, column-level encryption stops exposure to anyone who can run a query.

## Configure server- and database-level firewall rules

Every Azure SQL Database maps to a Microsoft-hosted public IP address, and each Azure region exposes one or more public IPs that front the database gateway. All inbound connection attempts, whether from the internet or from within Azure, pass through a firewall before reaching the server or database. Azure SQL Database maintains two independent sets of firewall rules: server-level and database-level, both based on source IP address rather than SQL logins — a rule for one IP address permits every user connecting from that address (typically a company's shared outbound IP).

Server-level firewall rules apply to every database on the server and are configured through the Azure portal or by running `sp_set_firewall_rule` in the master database. The "Allow Azure services and resources to access this server" toggle counts as a single firewall rule when enabled. Database-level firewall rules restrict access to a specific database and can only be configured via T-SQL, using `sp_set_database_firewall_rule` from within the target user database. On connection, Azure SQL Database checks for a matching database-level rule for the named database first; if none exists, it falls back to checking server-level rules, which apply across all databases; a match at either level allows the connection. If neither level has a matching rule and the client is SQL Server Management Studio, the user is prompted to create one on the spot.

Virtual network (VNet) endpoints extend firewall control to allow traffic from a specific Azure Virtual Network; these rules apply at the server level only, are scoped to a single Azure region (the region of the underlying endpoint), and require the connecting VNet to have outbound access to the database's public IP — configurable via Azure SQL Database service tags. Private Link goes further, providing a private endpoint so that traffic to the database travels entirely over the Azure backbone network rather than the public internet, presenting a private IP address inside the customer's VNet. Private Link also supports connectivity over an Azure ExpressRoute circuit, offers cross-region private connectivity, and limits data-leakage risk by restricting connections to specific named resources rather than an open network path.

## Implement Always Encrypted

Always Encrypted encrypts data inside the client application before it ever reaches the database, protecting sensitive columns from malware and from high-privileged principals such as DBAs, server admins, and cloud admins who would otherwise always be able to see the data — encryption and decryption both happen transparently based on metadata about the column's encryption settings, so the application code itself doesn't need to change to encrypt or decrypt values. Three deployment scenarios are called out: client and data both on-premises (protecting against high-privileged external vendors managing the SQL Server), client on-premises with data in Azure (keys are kept in an on-premises key store so Microsoft cloud administrators have no path to the plaintext), and client and data both in Azure (Always Encrypted doesn't fully isolate data from cloud admins in this scenario, but the data is still encrypted at rest and in use within the database engine).

Always Encrypted is built on two key types: a column master key, which encrypts one or more column encryption keys, and a column encryption key, which performs the actual data encryption — each column can have its own key, or multiple columns can share one. Two encryption types are available per column, chosen at creation time and not changeable afterward: deterministic encryption, which always produces the same ciphertext for the same value, supporting equality/inequality comparisons, joins, grouping, and indexing on that column; and randomized encryption, which produces different ciphertext for the same value on each encryption, making it more secure against pattern inference but limiting the column to being returned in results only — no comparisons, joins, grouping, or indexing. Randomized encryption is recommended for columns with a small set of easily guessable values (e.g., a three-digit card verification code) where deterministic encryption's fixed mapping would be vulnerable to statistical inference.

Setup is typically done through the Always Encrypted Wizard in SQL Server Management Studio (right-click the table → Encrypt Columns...): select the columns and their encryption type, then configure the column master key. The column master key itself must be stored in an external key store — the Windows Certificate Store, Azure Key Vault, or a hardware security module — never generated or stored on the database server itself, since it could otherwise be extracted from server memory; the database engine only ever stores metadata pointing to where the key lives, never the key itself. For the strongest security posture, a third-party key store like Azure Key Vault is recommended. The wizard can either apply the change immediately or generate a PowerShell script for later execution.

Client-side, decrypting Always Encrypted columns requires an Always Encrypted-aware driver, access to the key store holding the relevant keys, and the connection string setting `Column Encryption Setting=enabled`, which triggers a metadata lookup for each referenced column; to minimize repeated lookups in .NET applications, `SqlCommandColumnEncryptionSetting` should be set on the `SqlConnection` object for each query submitted by the application.

## Implement Always Encrypted with VBS enclaves

Secure enclaves extend Always Encrypted by adding a protected region of memory inside the SQL Server process that functions as a trusted execution environment for operating on encrypted data. From SQL Server's own perspective this enclave is opaque — its data and code cannot be inspected, even with a debugger attached. The practical benefit is that secure enclaves lift some of randomized encryption's restrictions: with an enclave, pattern matching, comparison operations, and indexing become possible on randomized-encrypted columns, capabilities that are otherwise exclusive to deterministic encryption. This lets a column keep randomized encryption's stronger resistance to inference attacks while still supporting richer server-side query operations than randomized encryption alone would allow.

## Configure private links and service endpoints

Azure Private Link provisions a private endpoint for Azure SQL Database (and other PaaS services), routing traffic entirely across the Azure backbone network instead of the public internet and exposing a private IP address inside the customer's Virtual Network; it also supports connections carried over an Azure ExpressRoute circuit. Its stated benefits are cross-region private connectivity and reduced data-leakage risk, since connections are restricted to explicitly designated resources rather than any endpoint reachable over the network. Virtual network service endpoints are the related but distinct mechanism: they permit traffic from a specific VNet by adding a server-level firewall rule (not database-level), are bound to a single Azure region matching the endpoint, and depend on the connecting VNet having outbound network access to the database's public IP, which is configured using Azure SQL Database service tags. In short, service endpoints extend the IP-based firewall model to trust a VNet's identity, while Private Link removes the public IP path entirely in favor of a private one.

## Apply a data classification strategy

Data classification tags confidential columns in Microsoft SQL Server, Azure SQL Database, and Azure SQL Managed Instance so users and applications understand the sensitivity of what they're querying. Classification happens per column, not per table — a single table can mix public, confidential, and highly confidential columns. Originally implemented in SQL Server Management Studio using extended properties on objects, classification metadata has been stored since SQL Server 2019 in the catalog view `sys.sensitivity_classifications`. The Azure portal exposes this as "Data Discovery & Classification" under the Security section of a database's blade; its classification engine scans column names for patterns suggesting sensitive content (a column literally named `email` gets flagged automatically) and produces recommendations — but because detection is name-based, a column named `column1` holding email addresses would not be flagged. Classification can also be applied directly with T-SQL: `ADD SENSITIVITY CLASSIFICATION TO [Application].[People].[EmailAddress] WITH (LABEL='PII', INFORMATION_TYPE='Email')`. Knowing which columns are sensitive streamlines audits and highlights which columns are the best candidates for encryption (Always Encrypted, TDE) or masking.

Data Discovery & Classification is part of Microsoft Defender for Cloud, and its taxonomy of labels and information types is customizable per organization from the "Configure" option on the classification pane — the Information Protection page lets an admin define labels, rank them, and link them to information types, after which new patterns feed automatically into the discovery/scanning logic. Only users with administrative rights at the organization's root management group level can create or manage sensitivity labels.

Microsoft Purview extends classification beyond a single database into a governance layer across the entire data estate — on-premises, multicloud, and SaaS. It builds a unified, continuously updated map of data assets through automated scanning and classification, supports data curators managing and securing that estate, and helps data consumers locate trustworthy data. Concretely, Purview automates metadata discovery and classification across hybrid sources, applies both integrated and custom classification rules plus information-protection sensitivity labels, keeps labeling consistent across SQL Server, Azure, Microsoft 365, and Power BI, and integrates with other systems via the Apache Atlas API. Its Data Catalog makes assets discoverable using familiar business/technical search terms, replacing spreadsheet-based data dictionaries, and its Data Insights feature (preview) reports on the data domain's composition (by source type, classification, file size), scan pass/fail/cancel status, and glossary-term coverage gaps.

Prerequisites for using Purview against Azure SQL include an Azure subscription capable of creating resources (including a Purview account itself), access to the target data sources, a Reader role for Data Lake Storage scans, an identity capable of sampling tables for classification in Azure SQL, access to (or collaboration with) Microsoft Defender for Cloud for labeling, and Data Source Administrator plus Data Reader roles to register and manage a source in the governance portal. If the target SQL Server has a firewall, Purview scanning needs one of three paths in: allow Azure connections through the firewall directly, install a self-hosted integration runtime on a network-local machine (useful for closed/private-VNet environments), or use a managed virtual network tied to the Purview account for the Azure integration runtime. Supported scan authentication methods are system-assigned managed identity (recommended, created automatically with the Purview resource, but incompatible with a self-hosted integration runtime for Azure SQL), user-assigned managed identity (preview, same self-hosted-IR incompatibility), service principal (useful for temporary/expiring projects), and SQL authentication — a self-hosted integration runtime specifically requires falling back to service principal or SQL authentication, since managed identities don't work through it. Registering and scanning a source follows a fixed sequence in the Purview governance portal: build a collection hierarchy under Data Map > Collections, register the Azure SQL Database under the right collection, then create a scan specifying the database, credential, and scope, choosing a scan rule set (system default, existing custom, or a new inline rule set with selected classification rules), and setting a trigger before running it. Enabling the "lineage extraction" toggle on a scan additionally requires the Purview managed identity to be added to `db_owner` (`CREATE USER <purview-account> FROM EXTERNAL PROVIDER` plus `sp_addrolemember 'db_owner', <purview-account>`) and a master key created in the target database (`CREATE MASTER KEY`); once configured, an incremental lineage-extraction scan runs every 6 hours, deriving lineage from actual stored procedure executions, and results are browsable from an asset's Lineage tab or a stored procedure's Properties > Related assets / Run Overview.

## Configure server and database audits

Azure SQL auditing tracks database events and writes them to an audit log destination — an Azure Storage account, a Log Analytics workspace, or Event Hubs — supporting regulatory compliance, activity-pattern analysis, and detection of anomalies that might indicate a security violation. Audit policy can be defined at the server level or the database level. A server-level audit policy automatically covers every database on the server, both existing and future; if server auditing is enabled, a database is audited regardless of its own database-level auditing setting. Database-level auditing can still run alongside server-level auditing, but doing so is discouraged except for two specific cases: a database needs a different storage account, retention period, or Log Analytics workspace than the server policy uses, or a database needs audit coverage for different event types/categories than the rest of the server. Outside those cases, the recommendation is server-level auditing only, with database-level auditing left disabled everywhere.

The default SQL Database audit policy captures three action groups: `BATCH_COMPLETED_GROUP` (every query and stored procedure executed against the database), `SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP` (successful logins), and `FAILED_DATABASE_AUTHENTICATION_GROUP` (failed logins). Auditing for all databases on a server is enabled from the "Auditing" pane under the Security section of the server's blade, which is also where the log destination is set. Because the auditing service for SQL Database and Managed Instance is tuned for availability and performance, it may drop some audited events under very high activity or network load — audit completeness isn't absolute under load. Auditing on read-only replicas is enabled automatically.

Audit logs integrate with data classification through a `data_sensitivity_information` field added to the log, which records the sensitivity labels of any classified columns returned by an audited query, making it straightforward to track access specifically to sensitive data.

Microsoft Defender for SQL layers additional compliance-relevant monitoring on top of auditing: SQL vulnerability assessment scans the database against a knowledge base of security best-practice rules and flags misconfigurations, excessive permissions, and sensitive-data exposure, either via the portal or a periodic emailed summary; enabling recommendations requires turning on Microsoft Defender for SQL at the subscription level and providing a storage account. Advanced Threat Protection separately watches live connections and executed queries for malicious patterns, and surfaces alerts including vulnerability to SQL injection, an active SQL injection attempt in progress, access from an unusual geographic location, access from an unusual Azure datacenter, access from a principal that's never connected before, access from a known-harmful attack tool, and brute-force credential attempts (a spike in failed logins using different credentials). Advanced Threat Protection's investigative value increases substantially when auditing is also enabled (recommended action groups: `BATCH_COMPLETED_GROUP`, `SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP`, `FAILED_DATABASE_AUTHENTICATION_GROUP`), since audit logs supply the detail needed to trace an alert to its root cause. Managing Defender for SQL settings requires membership in the SQL security manager role or a database/server admin role, and it's turned on from the server blade's Microsoft Defender for Cloud pane by setting the server property to ON.

## Implement dynamic data masking

Dynamic Data Masking obfuscates column values at the presentation layer so that users without a need to see sensitive data can still query the column, just not its real contents — the underlying stored data is untouched, only what's returned to a masked user's session changes, and a high-privileged user always sees the real, unmasked value. Its main appeal is that it requires little to no modification of the application or schema to adopt. It can be configured through the Azure portal (the "Dynamic Data Masking" pane under a database's Security section) or through T-SQL by altering a column to add a masking function.

Five masking functions are supported:

| Masking function | Behavior | T-SQL example |
|---|---|---|
| Default | Fully masks the value with no exposed portion — `XXXX` for strings, `0` for numbers, `01.01.1900` for dates | `ALTER TABLE [Customer] ALTER COLUMN Address ADD MASKED WITH (FUNCTION = 'default()')` |
| Credit card | Shows only the final four characters in the standard card format | `ALTER TABLE [Customer] ALTER COLUMN Address ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)')` |
| Email | Exposes only the first character and the domain suffix, e.g. `aXXX@XXXXXXX.com` | `ALTER TABLE [Customer] ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()')` |
| Number | Substitutes a random number within a specified range, re-randomized on every query | `ALTER TABLE [Customer] ALTER COLUMN [Month] ADD MASKED WITH (FUNCTION = 'random(1, 12)')` |
| Custom string | Masks with a custom fill character, exposing a specified count of characters at either end (if the value is shorter than the exposed-character count, the whole value is masked) | `ALTER TABLE [Customer] ALTER COLUMN [PhoneNumber] ADD MASKED WITH (FUNCTION = 'partial(1,"XXXXXXX",0)')` |

A user is given the ability to see real values in a masked column via an explicit `UNMASK` grant. Because a determined user can sometimes infer unmasked values through inference attacks on query results, Microsoft's guidance is to pair Dynamic Data Masking with other controls — auditing, encryption, row-level security — rather than relying on masking alone, and to restrict masked users' ability to run arbitrary ad hoc queries. Good-fit use cases include masking data from application users with no direct database access, restricting sensitive columns from a subset of internal users, providing masked extracts to external vendors while preserving referential relationships between rows, and exporting a production database to a lower environment for development without exposing real values. Masking behavior carries through data movement: copying a masked column via `SELECT INTO`/`INSERT INTO` produces masked data in the destination table, and running SQL Server Import/Export as a non-UNMASK user produces an export file (and, if imported, a destination table) containing masked values rather than the originals.

## Implement ledger in Azure SQL

Ledger adds tamper-evidence to a database: every transaction is cryptographically hashed with SHA-256, and hashes are chained together in blockchain-like fashion, so tampering with any historical row becomes cryptographically detectable. This lets an organization prove to auditors, regulators, or business partners that the data hasn't been altered outside of the recorded transaction history, without giving up the performance, flexibility, and query power of ordinary Azure SQL Database.

Two ledger table types are supported. Updatable ledger tables support inserts, updates, and deletes, and use built-in system-versioning to retain a full history table capturing prior row versions — the fit for systems of record and transactional applications where auditable change history is required. Append-only ledger tables block all updates and deletes at the API level, which suits insert-only workloads such as accounting or SIEM-adjacent systems where records must never be altered once written, and the append-only restriction itself simplifies management as well as guaranteeing immutability. The stated benefits of Ledger are easing audits (documented, cryptographic proof of non-tampering during audit processes), building trust between multiple parties in a business process without the overhead of a full consensus network, and providing data integrity for off-chain storage tied to blockchain-style verification without sacrificing normal database query performance.

Ledger can only be turned on for a database at creation time — it cannot be enabled retroactively on an existing database. It's configured from the Security tab of the "Create SQL Database" flow in the Azure portal by selecting Ledger, then "Configure ledger," where checking "Enable for all future tables in this database" causes every new table in that database to default to being a ledger table (specifically an updatable ledger table) even without explicitly specifying `LEDGER = ON` in `CREATE TABLE` — meaning the entire database's data becomes subject to tamper-evidence by default. Leaving that box unchecked instead requires enabling ledger per table explicitly via T-SQL at table-creation time. A storage location for the database digests (the cryptographic proofs) must also be provided as part of enabling ledger.

## Implement row-level security

Row-level security (RLS) restricts which rows a principal can see or affect within a table, based on group membership or authorization context, without using encryption — conceptually it behaves like an automatically applied WHERE clause. Enforcement is handled by a security policy that invokes an inline table-valued function; the function's predicate evaluates per row against the querying user's identity or attributes, and can be as simple as `WHERE CustomerId = 29` or arbitrarily complex.

Two predicate types are supported. Filter predicates silently restrict which rows are visible/affected for SELECT, UPDATE, and DELETE (INSERT is not applicable to filter predicates) — a user simply never sees rows that fail the predicate. Block predicates instead actively prevent data-modification operations that would violate the predicate, evaluated at four points: AFTER INSERT (blocks inserting rows with values that violate the predicate), AFTER UPDATE (blocks updating rows to violate it), BEFORE UPDATE (blocks updating rows that already violate it), and BEFORE DELETE (blocks deleting rows that violate it).

Because enforcement lives at the database level rather than in application logic, adopting RLS typically requires minimal to no application changes, and users can query their own tables directly without the application needing to inject filtering logic. Implementation follows three steps: create the users or groups that need isolated access; create an inline table-valued function containing the filter predicate; and create a security policy on the target table that attaches that function. A representative multi-tenant example creates a `Sales` table with a `TenantName` column, creates one user per tenant plus a `TenantAdmin` user, grants all of them SELECT on the table, defines a schema-bound function `sec.tvf_SecurityPredicatebyTenant(@TenantName)` whose predicate is `WHERE @TenantName = USER_NAME() OR USER_NAME() = 'TenantAdmin'`, grants SELECT on that function to each user, and finally creates `CREATE SECURITY POLICY sec.SalesPolicy ADD FILTER PREDICATE sec.tvf_SecurityPredicatebyTenant(TenantName) ON [dbo].[Sales] WITH (STATE = ON)`. Under this policy, each tenant user sees only their own rows via ordinary `SELECT * FROM dbo.Sales`, `TenantAdmin` sees every row, and toggling the policy to `WITH (STATE = OFF)` removes filtering entirely, exposing all rows to all users again.

RLS carries a side-channel risk: an attacker can craft a WHERE clause designed to trigger an error (e.g., a divide-by-zero) only when a filtered condition is true, inferring hidden data from whether or not the query errors — mitigated by restricting users' ability to submit unplanned/ad hoc queries. Good-fit use cases include isolating departmental access at the row level, restricting each customer to only their own company's rows in a shared table, and enforcing row-level restrictions for regulatory compliance. Best practices are to keep predicate functions and security policies in a dedicated schema, avoid type conversions inside predicate functions, and avoid excessive joins or recursion inside predicate functions, both for performance and to reduce the attack surface for inference.
