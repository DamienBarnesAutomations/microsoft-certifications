# Plan and configure a high availability and disaster recovery (HA/DR) environment

## Recommend HA/DR strategy based on Recovery Point Objective/Recovery Time Objective (RPO/RTO) requirements

Recovery Time Objective (RTO) is the maximum amount of time available to bring resources back online after an outage; exceeding it can mean financial penalties or lost work. RTO can be stated for an entire solution or for individual components (a SQL Server instance, a specific database), and the overall RTO for an application is always governed by the slowest component to recover — if SQL Server itself comes back in five minutes but the application tier takes twenty, the effective RTO is twenty minutes. Recovery Point Objective (RPO) is the point in time to which a database must be recoverable, and it equates directly to the amount of data loss the business will tolerate. If a VM goes down at 10:00 AM and the stated RPO is 15 minutes, whatever mechanism is used to recover must be able to restore to 9:45 AM or later.

RTOs and RPOs are business decisions driven by the cost of downtime (for example, $10,000/hour or contractual fines), not purely technical ones, and they must be set through discussion among all stakeholders — "zero downtime, zero data loss" is rarely realistic, and the investment in an HADR solution should be proportional to what downtime actually costs. RPO in particular dictates the technical design: if transaction log backups only run every 30 minutes but the business demands an RPO of 15 minutes, the database can only ever be recovered to the last backup (up to 30 minutes old), so the backup cadence must be tightened, or the objective renegotiated. Similarly, if a backup takes three hours to copy but the RTO is two hours, the RTO will be missed and either the process or the target needs to change. RTO and RPO should be defined separately for high availability (HA) events, which are localized and typically recover in seconds (for example, an Availability Group failing over within a region), and for disaster recovery (DR) events, which can mean standing up an entirely new data center and take hours or longer. All RTO/RPO figures should be documented and revisited periodically, and only once they're defined should specific technologies be selected to meet them — the technology choice (AG vs. FCI, synchronous vs. asynchronous replication, backup frequency) is downstream of these numbers, not the starting point.

## Evaluate HA/DR for hybrid deployments

A hybrid architecture spans on-premises and Azure (or Azure and another public cloud). PaaS offerings are not natively hybrid-friendly because their HA/DR is built into the Azure infrastructure itself; the one notable exception is SQL Server transactional replication, which can publish from an on-premises (or other-cloud) instance to an Azure SQL Managed Instance subscriber, but not in the reverse direction. Because of this, hybrid HADR solutions are effectively always IaaS-based. The most common use of a hybrid topology is building disaster recovery for an on-premises system by adding an Azure-based secondary replica to an Availability Group — which also means the supporting infrastructure (Active Directory Domain Services and DNS) must exist in Azure as well as on-premises.

Networking is the most important consideration for any hybrid HADR design that extends into Azure: insufficient bandwidth can cause RTO/RPO to be missed outright. Azure ExpressRoute is the preferred fast networking option; if ExpressRoute isn't feasible, a secure site-to-site VPN should be used so Azure VMs act as an extension of the on-premises network — exposing IaaS VMs directly to the public internet is discouraged. A distributed availability group is well suited to hybrid scenarios because, unlike a traditional AG, it doesn't require a single Windows Server Failover Cluster (WSFC) spanning both locations — each side maintains its own cluster and its own quorum/witness, which is easier to achieve when on-premises and Azure networks aren't tightly coupled. A traditional AG stretched across on-premises and Azure (or across regions) instead requires all replica nodes to participate in the same WSFC, demanding good cross-site network connectivity and AD DS/DNS availability everywhere the cluster has nodes — the witness resource for that shared WSFC becomes a key design point. Beyond database-level HA/DR, Azure can also simply serve as an off-site or cold archival destination for on-premises database backups, which is a lightweight form of hybrid DR even without a live secondary.

## Evaluate Azure-specific HA/DR solutions

The choice between IaaS and PaaS fundamentally shapes what's available. With IaaS (SQL Server on an Azure VM), the administrator has a full menu of SQL Server HADR features and configures them directly; with PaaS (Azure SQL Database, Azure SQL Managed Instance), HADR is built into the service and largely just needs to be enabled, with far fewer configurable knobs.

For IaaS, SQL Server itself offers three main features, distinguished by what they protect:

| Feature | Protects |
|---|---|
| Always On Failover Cluster Instance (FCI) | Instance |
| Always On Availability Group (AG) | Database |
| Log Shipping | Database |

Instance-level protection (FCI) covers the entire SQL Server installation — binaries, logins, SQL Server Agent jobs, and all databases. Database-level protection (AG, log shipping) covers only what's inside the database or captured in its transaction log; anything else (Agent jobs, linked servers, instance-level logins) must be manually replicated to the secondary. Both FCIs and AGs require an underlying cluster — Windows Server Failover Cluster (WSFC) on Windows, Pacemaker on Linux.

On top of these SQL Server features, Azure provides three infrastructure-level options that are workload-agnostic (they don't know anything about SQL Server or transactions): Availability Sets, Availability Zones, and Azure Site Recovery.

Availability Sets protect against Azure host-level maintenance and single points of failure within one data center by splitting VMs across fault domains (groups of servers sharing power and network, up to three per data center, FD 0/1/2) and update domains (groups that get rebooted together), acting effectively as anti-affinity rules — two VMs in the same availability set or log-shipping pair are guaranteed never to run on the same physical server. Each application tier should get its own availability set (web tier, database tier, AD DS tier each separately). Availability Zones instead protect against data-center-level failure: an Azure region contains multiple physical data centers (zones) connected by low-latency links, and VMs can be deployed into Zone 1, 2, or 3 — zone numbers are only logical, so two subscribers' "Zone 1" VMs aren't necessarily in the same physical building. Round-trip latency between zones is typically under 1ms, which is low enough to support synchronous replication (for example, synchronous AG replicas). Availability Sets and Availability Zones are mutually exclusive — you pick one or the other — and neither protects against in-guest failures like an OS crash or a SQL Server crash, which is exactly what AGs, FCIs, or log shipping are for.

Azure Site Recovery (ASR) replicates an entire VM's disks from one Azure region to another for disaster recovery. It knows nothing about SQL Server transactions, so it may satisfy RTO but not necessarily RPO. ASR has a stated monthly RTO of two hours. It uses a Site Recovery Mobility extension on the VM, sends changes continually while replication is enabled, and generates crash-consistent recovery points every five minutes plus application-consistent recovery points per the configured replication policy (the "App consistent snapshot frequency" setting, which uses Volume Shadow Copy Service — lowering it too far can cause brief I/O freeze/thaw pauses that may interact badly with SQL Server, especially if an AG is also configured). Multiple VMs can be grouped for multi-VM consistency (shared crash/app-consistent recovery points across VMs) but this affects performance and should only be used when VMs truly must be restored together. ASR also has ransomware value — a VM can be rolled back to a point before infection, accepting some data loss in exchange for avoiding extended downtime. After an ASR failover, the replica VMs in the target region are not automatically protected going forward; they must be reprotected. A major operational benefit is that ASR DR drills can be tested without taking down production.

For PaaS, Azure SQL Database offers active geo-replication (Azure SQL Database only — not supported on Managed Instance) and both Azure SQL Database and Azure SQL Managed Instance support auto-failover groups. Azure SQL Database carries a 99.99% availability SLA; on a node-level failure, all committed transactions are already durably written to storage, so a new compute node is spun up and reattached to that storage automatically — applications must implement retry logic since in-flight connections and transactions are dropped during this process. Both services also support read replicas for offloading reporting workloads and for regional read availability. Neither service allows setting a database to OFFLINE or EMERGENCY state (OFFLINE doesn't apply since you can't attach/detach files yourself, and EMERGENCY-mode repair isn't needed since Azure manages the service); RESTRICTED_USER and dedicated admin connection (DAC) are still available. Accelerated Database Recovery (ADR) is built in and always on (can't be disabled) — it aggressively truncates the log and uses a persisted version store (PVS) to make transaction rollback near-instant and speed up database recovery generally, which is a meaningful contributor to the SLA. For consistency, Azure runs regular backup/restore integrity checks, detects lost writes and stale reads, supports DBCC CHECKDB (no-repair) manually, keeps CHECKSUM on by default, and performs automatic page repair with data-integrity alerting (silent repair if there's no impact, proactive notification if there is).

Common IaaS reference architectures worth knowing: a single-region AG for HA (multiple VM copies, good RTO/RPO, standardized app connectivity via the listener, no shared storage needed, better patching story than FCI); a single-region FCI using shared storage such as Storage Spaces Direct (still popular, meets HA RTO/RPO but not DR on its own, standardized connectivity via the FCI name); a multi-region or hybrid AG stretched across one WSFC (proven pattern, works on Standard or Enterprise Edition, extra data copies, handles both HA and DR with one feature, but requires AD DS/DNS everywhere and careful witness placement); a distributed AG, an Enterprise-only "AG of AGs" (the primary replica of the first AG is the global primary, the primary of the second AG is the forwarder that keeps its own secondary in sync) which avoids a single WSFC being a single point of failure, doesn't have one primary synchronizing every secondary, and supports failing back between locations; log shipping for DR (oldest HADR method, tolerant of unreliable networks, easy to administer, meets most DR RTO/RPO goals, good complement for protecting FCIs, but always assume some data loss); and Azure Site Recovery for DR when a SQL Server-native option isn't feasible (works for any workload in the VM, may meet RTO and possibly RPO, is a native Azure platform capability).

## Plan a testing procedure for an HA/DR solution

Regularly testing backups is called out explicitly as necessary to ensure they're actually reliable and will meet the stated RPO when needed — an untested backup strategy is not a trustworthy one. For Windows Server Failover Clusters, cluster validation is a mandatory, built-in battery of tests (run via Failover Cluster Manager or the `Test-Cluster` PowerShell cmdlet) that every node and, for FCIs, the shared storage must pass; results come back as error, warning, pass, or not applicable, and while warnings can be acceptable if expected for the environment, all errors must be resolved before the cluster is considered supported. Before configuring FCIs or AGs on top of a WSFC, the shared storage failover path itself should be tested — in Failover Cluster Manager, under Storage > Disks, each clustered disk can be right-clicked and moved to another node via "Move Available Storage" to confirm all nodes can actually take ownership of storage during a real failover. Once the load balancer for an AG listener is confirmed working, AG failover and listener connectivity should likewise be tested before go-live, since adding the probe port later requires bringing the listener's IP offline (and thus the AG) temporarily. Azure Site Recovery's standout testing advantage is that a full DR failover test can be run without taking production down, making it practical to rehearse the DR plan on a schedule rather than only discovering problems during a real disaster.

## Recommend a database backup and restore strategy

Even organizations that implement AGs or active geo-replication still need a solid, independent backup and recovery strategy — HA features are not a substitute for backups. SQL Server maintains both system databases (such as master and msdb, updated less frequently and generally not restored from one instance to another) and user databases (which hold application data and are the real focus of a backup plan). The three core backup types are full, differential, and transaction log. A full backup copies every page in the database and alone is enough to restore to the moment the backup finished. A differential backup captures only the pages changed since the last full backup. A transaction log backup both enables point-in-time recovery (to meet RPO) and truncates/manages the size of the transaction log; log backups can technically be taken as often as every 30 seconds, though that's rarely practical. Other backup types exist too: copy-only, file, filegroup, partial, and more. A differential or log backup can only be applied after a full restore if that restore used `WITH NORECOVERY` or `WITH STANDBY` — using neither triggers full recovery immediately and no further backups can be layered on afterward.

The database's recovery model governs what backup/restore options are even available: FULL, BULK_LOGGED, or SIMPLE. FULL permits every backup type including transaction log backups and full point-in-time recovery. SIMPLE does not allow transaction log backups at all, so a database in SIMPLE recovery cannot be restored to an arbitrary point in time — if the RPO is tight, SIMPLE will not meet it. Most production databases run in FULL or SIMPLE.

For Azure SQL Database and Azure SQL Managed Instance, backups are fully automatic and follow a fixed cadence: a full backup weekly, a differential every 12 hours, and transaction log backups every 5 to 10 minutes, all stored in read-access geo-redundant (RA-GRS) blobs replicated to an Azure-paired data center, so backups survive a single-datacenter outage. Retention policies can be configured per database to satisfy regulatory requirements. One important caveat: if the logical server hosting the database is deleted, all backups for every database on it are deleted at the same time and are unrecoverable — deleting just the database (server intact) still allows normal restore. Backups taken by Managed Instance cannot be restored onto SQL Database, and vice versa isn't implied to work either — they're separate backup ecosystems. A useful design question when building a strategy is simply whether the default 1–35 day retention window is long enough, or whether long-term retention is required.

## Perform a database backup by using native tools

For SQL Server on Azure VMs, Azure Backup can back up the entire VM (not just the databases), producing an application-aware / SQL-Server-aware, application-consistent backup that captures everything in the VM for full restoration — useful for scenarios like ransomware recovery even though it isn't ideal for every backup need. During this kind of backup, the SQL Server log will show a momentary I/O freeze and resume as the snapshot is taken. If snapshot delays are causing backup failures, the fix is setting `"USEVSSCOPYBACKUP"="TRUE"` under the registry key `HKEY_LOCAL_MACHINE\SOFTWARE\MICROSOFT\BCDRAGENT`.

Databases can also be backed up the traditional way, to disks attached to the VM or to a network share (including Azure Files), the same as on-premises — but backups must not be written to the VM's ephemeral/temporary storage, which is wiped on shutdown or restart, and it's good practice to copy backups to a second location so the primary backup isn't a single point of failure. Alternatively, the SQL Server IaaS Agent / resource provider can be configured to run automated backups against a storage account, which conveniently manages retention and covers both database and log backups from one place, helping guarantee RPO. Automated backups via the resource provider are Windows-only. Crucially, only one backup method should be used for a given database at a time — mixing automated backups and manual/in-guest log backups can break the log chain (each log backup clears the log, and a restore needs an unbroken chain of log backups), forcing an error-prone reassembly of backups taken from two different places during a restore.

On Azure SQL Managed Instance, in addition to the fully automatic managed backups, native manual backup is possible using the same backup-to-URL mechanism available in SQL Server, requiring credentials to the Azure Blob Storage container. Because Managed Instance maintains its own log chain automatically, manual backups on Managed Instance can only be taken as `COPY_ONLY`, for example:

```sql
BACKUP DATABASE contoso
TO URL = 'https://myacc.blob.core.windows.net/mycontainer/contoso.bak'
WITH COPY_ONLY
```

Azure SQL Database does not support this manual backup-to-URL feature at all — its backups are exclusively the automatic, Microsoft-managed ones.

## Perform a database restore by using native tools

While automated backups can be configured for IaaS SQL Server VMs, restores cannot be automated the same way — a restore must be performed manually using the restore-from-URL functionality inside SQL Server (via SSMS or T-SQL). In SQL Server Management Studio's restore wizard, selecting URL as the backup media type lets you restore directly from blob storage the same way you would restore from disk or a network share.

For Azure SQL Database and Azure SQL Managed Instance, "restore in place" is not supported — the target database name must not already exist before a restore is attempted; a restore always creates a new database rather than overwriting one in place. Both services also support restoring a deleted database: from the server's overview page in the Azure portal, the Deleted databases list shows each deleted database's deletion time and creation time (both in UTC); selecting one and supplying a new name restores it from backup to the point just before the `DROP DATABASE` occurred, via the "Create SQL Database - Restore database" page, which also shows the earliest available restore point.

## Perform a database restore to a point in time

On Azure SQL Database, a database can be restored to any specific point in time using the Azure portal, PowerShell, Azure CLI, or the REST API; the portal's restore page lets you pick the target timestamp directly. The point-in-time retention window defaults to 7 days and can be extended up to 35 days. As with all restores on this platform, point-in-time restore always creates a new database rather than restoring in place, so the target name must be free — and any point-in-time restore operation can be tracked afterward through the Azure Activity Log, since it registers as a database-creation event.

On IaaS SQL Server, point-in-time recovery is achieved manually through the full/differential/log backup chain: restore the full backup `WITH NORECOVERY` (or `WITH STANDBY`), then apply differential and/or log backups in sequence up to the desired point, with only the final restore operation allowed to complete recovery. Understanding transaction log internals is explicitly called out as important here, since it governs both how log backups behave and how granular the eventual point-in-time restore can be.

## Configure long-term backup retention

For Azure SQL Database and Managed Instance, standard backup retention covers point-in-time restore for 1 to 35 days (35 by default extendable, 7 by default for point-in-time restore specifically), which for many organizations is not enough for compliance or regulatory retention obligations — long-term retention policies can be configured per database to keep backups for far longer, and Azure SQL Database has built-in support for helping meet mandatory regulatory backup-retention requirements this way. Long-term backup retention history itself can be viewed via the Azure portal or CLI interfaces; on Managed Instance, Extended Events (XEvents) can additionally be used to track backup history, since no standard/classic backup history view is available on these PaaS platforms the way it is on-premises. A core planning question when designing any retention strategy is simply whether the default 1–35 day window is sufficient or whether a long-term policy needs to be layered on top.

## Backup and restore a database by using T-SQL

Backup-to-URL and restore-from-URL are configured and driven through T-SQL statements pointed at an Azure storage account/blob container rather than a local path. A transaction log backup to a URL looks like:

```sql
BACKUP LOG contoso
TO URL = 'https://myacc.blob.core.windows.net/mycontainer/contoso202003271200.trn'
```

Restoring a full backup without recovering the database (so later differential/log backups can still be applied) uses `WITH NORECOVERY`:

```sql
RESTORE DATABASE contoso
FROM URL = 'https://myacc.blob.core.windows.net/mycontainer/contoso20200327.bak'
WITH NORECOVERY
```

On Azure SQL Managed Instance, because the service maintains the log chain itself, manual T-SQL backups must include `WITH COPY_ONLY`:

```sql
BACKUP DATABASE contoso
TO URL = 'https://myacc.blob.core.windows.net/mycontainer/contoso.bak'
WITH COPY_ONLY
```

More generally, restoring a differential or log backup after a full restore requires the initial `RESTORE DATABASE` to specify `WITH NORECOVERY` or `WITH STANDBY` — using neither forces recovery immediately, after which no further backups can be layered on. Authentication to the storage account for these T-SQL operations is established through a SQL Server Credential, built either from the storage account name plus access key, or from a Shared Access Signature (SAS).

## Backup to and restore from cloud storage

For SQL Server on an Azure VM, backup-to-URL is effectively a "local" option since the VM and the storage account are both in Azure, even though the SQL Server engine itself has no awareness that it's running in Azure. It requires an Azure storage account, and inside that account, blobs are organized into containers with paths like `https://ACCOUNTNAME.blob.core.windows.net/ContainerName/MyDatabase.bak`; extra virtual folder names (FULL, DIFF, LOG) can be used under the container purely for organization. Authentication is established through a SQL Server Credential using either the storage account name + access key (stores backups as page blobs) or a Shared Access Signature (stores backups as block blobs). Starting with SQL Server 2016, only block blobs are supported for backup-to-URL, so a Shared Access Signature is the recommended and effectively required credential type going forward — it's also cheaper (block blobs cost less than page blobs) and gives finer-grained security control than an account key.

Azure SQL Managed Instance supports the same backup-to-URL / restore-from-URL mechanism as a manual, native option layered on top of its automatic managed backups, again needing credentials scoped to the blob container, and again restricted to `COPY_ONLY` backups since Managed Instance owns the log chain. Azure SQL Database has no equivalent manual cloud-storage backup path — its backups are exclusively the automatic RA-GRS ones Azure manages on your behalf, replicated to a paired data center for resilience against a single-datacenter outage.

## Configure active geo-replication

Active geo-replication is available for Azure SQL Database only — Azure SQL Managed Instance does not support it and must use auto-failover groups instead. It creates a readable secondary database replica in another region, kept asynchronously up to date; under the hood Azure actually uses Availability Groups to implement this, which explains why the terminology (primary/secondary logical servers, read-only databases) mirrors AG concepts. It exists to provide business continuity, letting the primary be failed over to a secondary region programmatically or manually during a major disaster. All databases participating in a geo-replication relationship must share the same service tier, and it's recommended (though not required) that the geo-secondary use the same compute size as the primary to avoid replication overhead/lag from a large write workload on an undersized secondary. Configuration is done from the database's blade in the Azure portal under Data management > Replicas > + Create replica; a manual failover afterward swaps roles, with the old secondary becoming the new primary and vice versa.

A cross-subscription geo-replica lets the secondary live in a different subscription than the primary — this configuration is only available programmatically (not through the portal).

## Configure Always On availability groups on SQL Managed Instance and Azure virtual machines

Availability Groups protect at the database level rather than the instance level. Introduced in SQL Server 2012 Enterprise Edition and extended to Standard Edition in SQL Server 2016 (Standard is limited to one database per AG and up to two replicas — one primary, one secondary; Enterprise supports multiple databases per AG and up to nine replicas — one primary, eight secondary). The primary replica holds the read/write copy; secondaries receive transactions synchronously or asynchronously and can, in Enterprise Edition, be made readable for offloading DBCC checks, backups, or reporting. Secondaries are initialized either from a database backup or via automatic seeding (which streams the backup directly to the secondary). AGs use a listener — a dedicated name and IP, functioning like an FCI's virtual name — for client abstraction, though direct connections to individual replicas remain possible. AGs need no shared storage, but that means storage cost scales linearly with replica count (a 1 TB primary needs 1 TB per replica, so five replicas means 5 TB total). Anything outside the database or its transaction log — Agent jobs, instance-level logins, linked servers — must be manually recreated on any new primary; using Windows Authentication or contained databases can reduce this burden.

On Azure VMs, an underlying WSFC (Pacemaker on Linux) is mandatory. Azure-specific WSFC considerations: the witness resource (disk, SMB 2.0+ file share, or cloud witness) maintains quorum, and a cloud witness (available since Windows Server 2016) is recommended especially for multi-region or hybrid topologies since it's fully Azure-based. Clustered Microsoft Distributed Transaction Coordinator (MSDTC), if an application needs it, requires shared disk even when the AG itself doesn't. AGs can be built without AD DS (using a Windows Server 2016+ Workgroup Cluster) but still need DNS; FCIs always require AD DS and DNS. The WSFC needs a unique name/CNO in AD DS, and a typical single-region Azure WSFC needs only one virtual NIC — the vNIC's IP must be set at the Azure level, not inside the guest (it appears as DHCP-assigned inside the VM, which is expected and any cluster-validation warning about it can be ignored). Because Azure gives no way to reserve that IP at the platform level, conflicts with other DHCP-issued addresses must be checked manually.

To enable clustering: `Install-WindowsFeature Failover-Clustering -IncludeManagementTools` on each node, then run cluster validation (via Failover Cluster Manager or `Test-Cluster`) — errors must always be fixed, warnings may be acceptable if expected (for AGs without shared storage, disk tests come back "not applicable" on Windows Server 2016+, but as a warning on Windows Server 2012 R2). Because of the DHCP IP issue, the WSFC itself must be created via PowerShell rather than the Failover Cluster Manager wizard for FCIs/AGs on Windows Server 2016 and earlier: `New-Cluster -Name MyWSFC -Node Node1,Node2,...,NodeN -StaticAddress w.x.y.z` for shared-storage configs (multiple `-StaticAddress` values for multi-subnet), add `-NoStorage` for AGs with no shared disk, and for a Workgroup Cluster add `-NoStorage -AdministrativeAccessPoint DNS`. A distributed network name (a name-only WSFC identity, with the IP tied to the underlying nodes rather than a dedicated cluster IP) is the default Azure creates automatically unless told otherwise; to force the traditional model instead, add `-ManagementPointNetwork Singleton`. Windows Server 2019 changed the Azure default to always use a distributed network name. Once validated and created, test that all nodes can take ownership of shared storage (Failover Cluster Manager > Storage > Disks > right-click > Move Available Storage > Select Node) before layering FCI/AG on top.

To actually configure the AG: enable the Always On Availability Groups feature per node (SQL Server Configuration Manager, or PowerShell `Enable-SqlAlwaysOn`), which requires restarting the SQL Server service. Create the AG using SSMS, T-SQL, or PowerShell exactly as on-premises. All VMs in the AG should use identical, appropriately-sized storage, and no permanent databases should sit on temporary storage. If a listener is created, it requires an Internal Load Balancer (ILB) — without it, only sessions connected directly to the primary-hosting VM can reach the listener. Either a Basic or Standard load balancer can be used, except Availability Zone deployments which require Standard. A single load balancer can host more than one IP/listener. Each listener IP needs a dedicated, high-numbered probe port (e.g., 59999) set via `Get-ClusterResource IPAddressResourceNameForListener | Set-ClusterParameter ProbePort PortNumber` — adding this later requires briefly taking the listener IP (and thus the AG) offline, so it should be set before production cutover. Multi-subnet AGs need a load balancer configured per subnet/region, each with its own probe port tied to that subnet's IP cluster resource. Connectivity can be validated with `Test-NetConnection NameOrIPAddress -Port PortNumber`, run from a machine other than the primary-hosting VM. Some environments also need the WSFC's own IP and administrative ports (such as 445) reachable through a load balancer for management purposes.

Distributed availability groups (an Enterprise-only "AG of AGs" introduced in SQL Server 2016) are configured the same in Azure as on-premises, except that the endpoint port for each AG (default 5022) must be added to each region's load balancer configuration. Distributed AGs need no WSFC or Pacemaker at all — the entire relationship is maintained within SQL Server itself, which makes them well suited to hybrid or multi-region deployments where a single shared cluster would be impractical.

On Azure SQL Managed Instance, Always On-style database-level HA is not configured as a classic AG at all — Managed Instance's equivalent capability is delivered through auto-failover groups (see below), since it doesn't expose the underlying WSFC to configure directly.

## Configure failover groups

Auto-failover groups work with both Azure SQL Database and Azure SQL Managed Instance (Managed Instance supports only one auto-failover group). A unique name is required within the `*.database.windows.net` domain. Failover groups provide two abstracted listener endpoints — one for read-write traffic, one for read-only traffic — and behind the scenes a failover updates DNS so clients keep using the same listener names without reconfiguration. The database (or databases — a group can hold one or more) is created automatically on the secondary through seeding, which can take time depending on database size and network speed, and both the primary and secondary databases share the same size and service tier.

Two policies control behavior: Automatic failover (on by default, can be disabled) determines whether the group switches regions on its own when a failure is detected; Read-Only availability (off after a failover by default, to protect the performance of the new primary) determines whether read-only traffic keeps flowing to a downed secondary's replacement immediately or waits. Manual failover is always possible even with automatic failover enabled. An unplanned/forced failover can lose data if the secondary wasn't fully caught up; `GracePeriodWithDataLossHours` (default one hour) controls how long Azure waits before forcing failover — raising it trades a longer wait for a better chance the secondary fully synchronizes first, which suits a tighter RPO tolerance for data loss but not for delay.

Compared with active geo-replication, failover groups differ in several concrete ways:

| Feature | Geo-replication | Failover groups |
|---|---|---|
| Automatic failover | No | Yes |
| Fail over multiple databases simultaneously | No | Yes |
| User must update connection string after failover | Yes | No |
| SQL Managed Instance support | No | Yes |
| Can be in same region as primary | Yes | No |
| Multiple replicas | Yes | No |
| Supports read-scale | Yes | Yes |

Both features can be configured with only a handful of clicks in the Azure portal or a few PowerShell/Azure CLI commands, a significant simplification compared with the planning and coordination an equivalent on-premises SQL Server HADR setup would require.

## Configure Always On Failover Cluster Instances on Azure virtual machines

An FCI is assigned at install time — a standalone instance cannot be converted into one afterward — and is given a unique name and IP distinct from the underlying cluster nodes and from the WSFC itself, so applications connect to the abstracted FCI identity without knowing which node is active. In Azure specifically, an Internal Load Balancer is required to make that FCI name/IP reachable (unlike on-premises, where the cluster's own virtual IP suffices). A failover is a full stop/start of the SQL Server instance on the target node: all connected sessions are dropped, and only applications built to recover from that disruption reconnect automatically. Recovery on the new node brings the instance back to a point consistent up to the moment of failure (rolling back any incomplete transactions), and because protection is instance-level, everything the business needs — logins, Agent jobs, etc. — is already present on the failover target.

FCIs keep a single copy of the database, which is also their single point of failure, so some form of shared storage is mandatory: Azure Premium File Share, iSCSI, Azure Shared Disk, Storage Spaces Direct (S2D), or a supported third-party clustering solution like SIOS DataKeeper. FCIs on SQL Server Standard Edition are capped at two nodes. AD DS and DNS are always required for an FCI, unlike AGs which can sometimes get by with a Workgroup Cluster. Windows Server's Storage Replica feature can add native disaster recovery to an FCI without needing a separate feature like log shipping or an AG.

FCIs support multi-subnet deployment, where each subnet gets its own virtual IP for the instance; on failover, DNS records for the virtual network name are updated to the new subnet's IP, and clients reconnect using the same name once DNS propagates — this removes the need for a stretched VLAN across subnets. The modern connection mechanism is the Distributed Network Name (DNN), which replaces the classic virtual network name (VNN) as the client connection point and removes the requirement for an Azure Load Balancer in front of it; the VNN still technically exists in the deployment, but clients target the DNN's DNS name instead.

Architecturally, FCIs remain a viable, popular HA choice in Azure even though they were originally designed to protect against physical hardware faults (disk, NIC failures) that are uncommon for a VM — the improving shared-storage story (Azure Shared Disk) makes them more practical, they meet most HA RTO/RPO goals (though they don't address DR on their own — pairing with log shipping is a classic complement), and they give applications a single, standardized connection point plus better behavior during patching than a bare standalone instance.

## Configure log shipping

Log shipping is one of the oldest SQL Server HADR mechanisms, built entirely on backup, copy, and restore, and it's still one of the simplest to reason about. It provides database-level protection (like AGs, it does not cover Agent jobs, linked servers, or instance-level logins — those must be handled manually), and unlike an AG it offers no native name abstraction: switching to the secondary means tolerating a name change unless mitigated with something like a DNS alias. The mechanics: take a full backup of the primary database, restore it onto a secondary server in a loading state (`WITH STANDBY` or `WITH NORECOVERY` — this is the "warm standby," and the restored copy is called the secondary database), then let SQL Server automatically and repeatedly back up the primary's transaction log, copy that log backup to the standby, and restore it there to keep the secondary caught up.

As an architecture, log shipping is primarily used for disaster recovery but can also improve local availability, is tolerant of unreliable networks, is easy to deploy and administer because it's just backup/copy/restore jobs, and generally meets DR-level RTO/RPO goals — though unless a switch to standby is carefully planned, some data loss should always be assumed since the unit of recovery granularity is a full transaction log backup interval. Log shipping is also a well-established complementary way to add disaster recovery on top of an FCI, since FCIs by themselves only address HA within a cluster.

## Monitor an HA/DR solution

Building the right HA/DR configuration starts with a set of planning questions worth revisiting continuously: is 1–35 days of standard backup enough, or is long-term retention needed; what are the RTO/RPO targets; what service tier does the SLA call for; are Availability Zones needed; is geo-replication or a failover group needed; and — often overlooked — is the application itself actually ready, with proper retry logic and with application/database placed close together to avoid added cross-region latency undermining the SLA.

Azure SQL exposes monitoring through the Azure portal, T-SQL, PowerShell, Azure CLI, and REST APIs. At the platform level, Azure Status is a global dashboard of ongoing service problems (with an RSS feed for change notifications), and Azure Service Health (in the portal) reports service issues, planned maintenance, health advisories, and history, with configurable email/SMS alerts. At the resource level, an Azure SQL Managed Instance's or database's Resource Health blade (portal or REST API) can reveal why it's currently unavailable; standard tools like SSMS and T-SQL queries also work against these platforms directly. CLI/PowerShell examples for status include `az sql mi list` (Managed Instance status), `az sql db list` (database status), and `Get-AzSQLDatabase` (all databases and their details on a server); REST APIs can retrieve the same information but are less convenient. For backup and restore history: standard backup history isn't exposed directly, but long-term retention backup history is visible via the portal or CLI, Managed Instance can additionally use Extended Events to track backup history, and any point-in-time restore (which always creates a new database) shows up in the Azure Activity Log as a create-database operation. Replica status for Business Critical tier deployments can be checked via the DMV `sys.dm_database_replica_states`. Finally, the System Center Management Pack for Azure SQL can monitor both Managed Instance and Azure SQL Database for organizations already standardized on System Center.

## Troubleshoot an HA/DR solution

Several concrete failure points and diagnostic paths recur across the HA/DR features. For WSFC-based solutions, quorum loss (loss of the witness resource) takes down the whole cluster along with any AG or FCI riding on it, so witness health is the first thing to check when a cluster-based solution goes dark; cluster validation results (errors vs. acceptable warnings) are the standard first diagnostic when a WSFC won't come up cleanly, and the shared-storage failover test (Move Available Storage in Failover Cluster Manager) isolates storage-access problems from clustering problems. AG listener connectivity failures are commonly a load-balancer or probe-port misconfiguration — each listener IP needs its own dedicated, correctly set probe port, and `Test-NetConnection NameOrIPAddress -Port PortNumber` run from outside the primary VM is the prescribed way to isolate whether the ILB, the probe port, or the SQL Server endpoint itself is at fault. If applications relying on MSDTC fail after an AG or FCI failover, the likely cause is that DTC wasn't clustered (which itself requires a shared disk even in an otherwise shared-storage-free AG).

For IaaS backup/restore problems, a broken log-restore chain is a classic self-inflicted issue caused by running both Azure-level automated backups and in-guest manual/native transaction log backups simultaneously — each clears the log independently, so the log chain needed for point-in-time restore gets fragmented across two backup histories and must be painstakingly reassembled; the fix is to standardize on exactly one backup method per database. Snapshot-related VM backup failures (Azure Backup interacting with SQL Server's VSS-based freeze/thaw) are addressed via the `USEVSSCOPYBACKUP` registry setting. For Azure Site Recovery, an overly aggressive app-consistent snapshot frequency can itself cause SQL Server I/O disruption due to the underlying VSS freeze/thaw, so if ASR appears to be interfering with SQL Server, the resolution is to relax that frequency or reconsider ASR in favor of a database-native option; also remember that after an ASR failover, the newly active replica VMs are unprotected until manually reprotected — a commonly missed step that leaves the environment without DR coverage for a second event. To determine why a Managed Instance or database-level failover happened at all, Azure Resource Health (portal or REST API) is the documented mechanism for identifying the root cause.
