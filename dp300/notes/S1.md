# Plan and implement data platform resources

## Recommend a database offering based on specific requirements

The three SQL platforms in scope are SQL Server on Azure Virtual Machines (IaaS), Azure SQL Managed Instance (PaaS), and Azure SQL Database (PaaS), plus on-premises SQL Server for hybrid scenarios. IaaS services consist of virtual machines, storage, and virtual networking, largely managed by the customer for patching and software; PaaS offloads a much larger share of management to the provider. In Azure SQL PaaS offerings the administrator is responsible for database management, user security, and data management, while Microsoft manages the OS and SQL Server software; IaaS is the most open-ended, with the customer responsible for OS patching, SQL Server install/configuration, and network/storage tuning.

SQL Server on an Azure VM is the right recommendation when an application needs an older SQL Server version for vendor support (Marketplace only carries images for currently supported versions, so older/extended-support versions require installing your own binaries), when other SQL Server services such as SSAS, SSIS, or SSRS need to run on the same box as the engine to maximize licensing, when the application requires direct OS access (not possible in PaaS), when it needs features like CLR or replication, or when it needs Active Directory (rather than Microsoft Entra ID) authentication. Azure SQL Database doesn't support cross-database querying, which is a common reason to choose either SQL Managed Instance or a VM instead.

Azure SQL Database is aimed at new application development: it gives the most deployment flexibility at scale and the lowest maintenance burden, but is scoped to single databases. It is the better recommendation when deployment/development simplicity matters, when usage is intermittent and unpredictable (serverless autoscale/autopause), when there's no usage history to size compute against beforehand, or when storage needs exceed what Managed Instance offers and consolidation isn't an option.

Azure SQL Managed Instance is recommended for lift-and-shift migrations that need near-100% SQL Server compatibility without redesigning the application: it supports SQL Agent (via msdb), cross-database queries, CLR, access to system databases, and up to 100 databases per instance, while still being fully managed PaaS (automatic backups, automatic patching, built-in HA). Historically, applications depending on instance-scoped features like SQL Agent jobs, cross-database joins, or SSIS could only move to Azure via IaaS, or via a full PaaS rewrite of Azure SQL Database to remove those dependencies — Managed Instance (code-named "cloud lifter") closes that gap.

Both SQL Database and SQL Managed Instance are purchased on the vCore model (compute and storage scaled independently); SQL Database additionally offers a DTU model (Basic/Standard/Premium) for simple, preconfigured sizing, but Managed Instance does not support DTU purchasing at all. Hybrid Benefit-style licensing (Azure Hybrid Benefit for SQL Server, License Mobility through Software Assurance) can reduce PaaS licensing cost by up to 30–40% for organizations with existing SQL Server Enterprise or Standard licenses under active Software Assurance.

## Choose an automated deployment method

All Azure resources are ultimately deployed through Azure Resource Manager. Resource Manager templates (ARM templates, JSON) are declarative — they define the desired end state and let the platform figure out how to get there — which is the recommended approach for large-scale, repeatable deployments. PowerShell and the Azure CLI are imperative, explicitly scripting each step, and are well suited to automation, CI/CD pipelines, and scripting repeatable one-off or scaled deployments. The Azure portal is the easiest way to get started but is not an easily repeatable process, so it's a poor choice for automation.

Microsoft publishes a GitHub repository, Azure-Quickstart-Templates, containing ready-made ARM templates you can reference directly in a deployment — for example, deploying a SQL logical server with `New-AzResourceGroupDeployment -TemplateUri "https://raw.githubusercontent.com/Azure/azure-quickstart-templates/master/101-sql-logical-server/azuredeploy.json"`. Typical PowerShell/CLI-based deployment of SQL Database involves scripting the resource group, the logical server with `New-AzSqlServer` / `az sql server create`, a firewall rule with `New-AzSqlServerFirewallRule` / `az sql server firewall-rule create`, and the database itself with `New-AzSqlDatabase` / `az sql db create` (specifying edition, family, and capacity, e.g. `--edition GeneralPurpose --family Gen4 --capacity 1`). The same pattern (portal, PowerShell, CLI, or ARM template) applies to virtual machines and to SQL Managed Instance deployments.

## Identify use cases for Azure Arc-enabled SQL services

Azure Arc extends Azure management capabilities to SQL Server instances running outside Azure — on-premises, in other clouds, or at the edge — without requiring you to move the databases into Azure. Once a SQL Server is Arc-enabled, you get a single, centralized inventory of registered SQL Server deployments in the Azure portal, along with automated policy application, compliance assessment, and real-time security alerts and vulnerability reporting for both the SQL Server instance and its host OS. Arc-enabled servers can also use Azure Monitor and Microsoft Defender for Cloud for enhanced security and performance monitoring, and support automated patching/updates, backup and restore, and disaster recovery capabilities normally associated with native Azure services, plus access to Azure's machine learning and AI capabilities against existing on-premises data.

Arc is also a first-class migration on-ramp: once a SQL Server instance is Arc-enabled, the Azure portal exposes an integrated assessment, target-selection, and migration experience for moving that instance's databases into Azure SQL Managed Instance, using either the Managed Instance Link or Log Replay Service under the hood. The workflow has four stages — assess source instance, select target, migrate data, monitor and cutover — and discovery/readiness reports are generated automatically every weekend (or on demand). Migration through Azure Arc supports SQL Server 2012 and later (exact minimum version depends on the chosen migration method), and Microsoft Copilot is integrated into the portal experience to help compare migration methods, interpret assessments, and monitor progress. Arc gives visibility across the whole estate: how many databases are migrated, in progress, and the recommended target configuration for each.

## Identify use cases for Azure SQL Database in Microsoft Fabric

SQL Database in Microsoft Fabric integrates SQL databases directly into the broader Fabric ecosystem, giving a unified platform for managing and analyzing data without moving it between separate systems. It supports both operational/transactional workloads and advanced analytics from the same data, which makes it a fit for organizations consolidating data infrastructure and wanting to streamline workflows and collaboration between data engineers, analysts, and data scientists rather than maintaining separate OLTP and analytics stores. The "Databases" workload in Fabric specifically targets these operational SQL scenarios, letting the same data be created and queried in a form optimized for each team's needs, with the security and scalability benefits already expected from Azure SQL.

## Plan for table partitioning

Table partitioning becomes a planning consideration once a table grows large enough to start compromising query performance — identifying candidate tables early, before problems appear, reduces future disruption. The main planning benefit is that filtering on the partition column limits access to a subset of the data rather than the whole table, and maintenance operations (compressing a specific partition, rebuilding a specific index partition) can be scoped to just the affected partitions instead of the whole table, shortening maintenance windows. This planning step precedes the actual implementation (filegroups, partition function, partition scheme, and the partitioned table itself), which is a distinct configuration task.

## Recommend a database sharding solution

Sharding in Azure SQL Database is implemented through elastic query, which supports two partitioning strategies. Horizontal partitioning (sharding proper) distributes rows across several scaled-out databases that all share the same schema, and supports either a single-tenant or a multi-tenant model — this is the pattern to recommend when a dataset or tenant base has grown beyond what a single database can efficiently hold, or when isolating tenants is a requirement. Vertical partitioning (also called cross-database queries) instead splits different schemas across databases — for example, one database for customer data and another for payment data — and elastic query lets you run a single T-SQL query that bridges both; this is the right recommendation when the goal is decomposing a monolithic schema by subject area rather than scaling out a single large table. Elastic query is a preview feature useful for applications using fixed three- or four-part names that can't be rewritten, and it also improves migration portability.

A related but distinct recommendation is the elastic pool: rather than sharding data, it pools compute/storage resources across many databases which each keep their own schema and data. Elastic pools are the right fit for a multi-tenant SaaS architecture with low average per-tenant utilization, where each tenant has its own database copy, since resources are shared cost-effectively across the pool rather than dedicated per tenant — but elastic pools should be monitored continually so that no single database's spikes starve the others sharing the pool.

## Deploy database offerings on selected platforms

Azure SQL Database can be deployed as a single database or into an elastic pool, via the Azure portal, PowerShell, Azure CLI, or ARM templates. Portal deployment asks for a resource group, database name, logical server (existing or new), whether to use an elastic pool, and compute + storage sizing (default Gen5, 2 vCore, 32 GB, with a Configure database link to change service tier/compute size — General Purpose defaults to Serverless, with Provisioned as the billed-hourly alternative). Elastic pools are created via "SQL elastic pools" in the portal, and existing databases are added to a pool through the pool's "+ Add databases" option; a pool's size (DTUs/vCores/storage), service tier, per-database resource limits, and database membership can all be changed after creation, with active connections dropped only while resizing completes.

Hyperscale is deployed the same way as a regular SQL Database, selecting the Hyperscale service tier under Configure database; note that once a database is converted to Hyperscale it cannot be converted back to a standard tier. SQL Server on an Azure VM is typically deployed from a preconfigured image in Azure Marketplace (e.g., SQL Server 2022 on Windows Server 2019), which installs the SQL Server IaaS Agent Extension as part of provisioning and exposes an OLTP- or Data-Warehouse-oriented preset along with storage, patching, and backup configuration during creation; portal deployment isn't easily repeatable, unlike ARM/PowerShell/CLI.

SQL Managed Instance is deployed choosing between the General Purpose and Business Critical vCore service tiers (Business Critical adds In-Memory OLTP and a readable secondary; both allow independent storage/compute sizing). Instance pools offer a fast (up to 10-minute), cost-efficient way to deploy several smaller managed instances that share the same underlying VM and a shared IP allocation, avoiding the extra governance overhead of consolidating many small workloads into one larger instance.

## Deploy hybrid SQL Server solutions

A hybrid SQL Server deployment combines on-premises (or other-cloud) infrastructure with an Azure IaaS component (commonly storage or SQL Server VMs) as a middle ground, rather than an all-or-nothing move to the cloud. The most common hybrid pattern is disaster recovery: local on-premises high availability continues for day-to-day operations, while Azure hosts the DR failover target in one or more regions — this is typically far cheaper than standing up a second physical data center. Another common pattern is backups: on-premises SQL Server backups can be written directly to Azure Storage via backup-to-URL or an Azure file share (SMB), protecting against local backup storage failure and letting backups be restored/tested against Azure VMs as part of DR drills; alternatively, user database data files themselves (not system databases) can be stored on Azure Storage while the SQL Server engine still runs on-premises, protecting against local storage failure — this pattern requires securing network communication, evaluating latency, and locking the storage account down with ACLs and Microsoft Entra ID.

Azure Arc-enabled SQL Server is the third hybrid pattern: it centralizes inventory, configuration assessment, usage, and security posture of every registered SQL Server (on-premises, other data centers, edge, multicloud) and surfaces recommendations, plus real-time security alerts and vulnerability reporting for the SQL Server and its host OS.

Any hybrid deployment requires core infrastructure — Active Directory and DNS — to exist both on-premises and in Azure, plus secure two-way connectivity, implemented as a site-to-site (S2S) VPN or a dedicated ExpressRoute circuit. ExpressRoute is more expensive but avoids the public internet entirely, giving the best security and lowest latency, at the cost of not working between different cloud providers in a multicloud scenario; latency tolerance should drive the choice between the two. Point-to-Site (P2S) VPN is a third connectivity option, useful for connecting individual client machines rather than an entire site.

## Apply patches and updates for hybrid and infrastructure as a service (IaaS) deployment

For SQL Server on an Azure VM, patching is a customer responsibility by default, but the SQL Server IaaS Agent Extension — installed automatically when a SQL Server VM is deployed from Azure Marketplace — provides automated patching (alongside automated backup, Key Vault integration, Defender for Cloud integration, disk-utilization visibility in the portal, flexible licensing, flexible version/edition changes, and a SQL best-practices assessment), substantially reducing the administrative burden versus a fully self-managed VM. Marketplace images are kept current only for supported SQL Server versions; if an older, extended-support version is required, you must supply and patch your own SQL Server binaries rather than relying on the Marketplace image.

By contrast, in the PaaS offerings (SQL Database, SQL Managed Instance) patching of the OS and SQL Server engine is fully handled by Microsoft as part of the managed service, and platform maintenance (Windows/SQL Server updates) generally occurs without visible application impact — though applications should still include retry logic for the rare connection interruption that can accompany a backend maintenance event or scaling operation. In hybrid Arc scenarios, applying consistent patch and update policy across on-premises SQL Server instances is one of the governance benefits Azure Arc adds on top of native Azure management tooling.

## Configure Azure SQL Database for scale and performance

SQL Database supports two purchasing models. DTU-based pricing bundles compute, storage, and I/O into a single Database Transaction Unit metric across three tiers — Basic, Standard, Premium — each with a fixed storage limit, backup retention, and cost; hitting the storage ceiling forces a DTU tier increase even if compute utilization is low. vCore-based pricing decouples compute and storage so each scales independently, across three tiers: General Purpose (budget-oriented, Azure premium storage, both Provisioned and Serverless compute, 4 TB max size), Business Critical (local SSD storage, lowest latency, In-Memory OLTP, a built-in read-only replica, 4 TB max size), and Hyperscale (Azure premium storage, up to 100 TB, unique scale-out architecture). A scaling operation that triggers an internal failover, or adding/removing a database from a pool, can cause a brief connection interruption, so applications need retry logic.

Serverless is a General Purpose/Hyperscale compute option (not its own tier) that autoscales between a configured minimum and maximum vCore count (as low as 0.5, up to 16 vCores) and autopauses the database after a configurable idle period — the autopause delay ranges from 60 minutes to 7 days, or can be disabled; while paused, only storage is billed, and the next connection attempt triggers an automatic resume (which produces a connection error the app should retry). Serverless is not compatible with features requiring an always-on background process: geo-replication, long-term backup retention, an elastic-jobs job database, and the Data Sync sync database.

Elastic pools share a single allocation of compute/storage across multiple databases (DTU- or vCore-based) and can be resized online — pool size, service tier, per-database resource limits, and pool membership can all change after creation; they are best suited to multi-tenant SaaS with low average utilization per tenant.

Hyperscale separates the query-processing engine from long-term storage/durability, giving it independently scalable compute and storage with no predefined maximum size; you're billed only for capacity actually used. Backups are file-snapshot based, effectively instantaneous regardless of data size, and restores complete in minutes rather than hours/days. Scale up/down changes primary compute (CPU/memory) independent of data volume since storage is shared; scale in/out provisions additional read-only compute replicas (which double as hot standbys) — connect to them by setting `ApplicationIntent=ReadOnly` in the connection string, which auto-routes to a read replica. Hyperscale also supports Row-Level Security and the same defense-in-depth security stack (IP/VNet firewall rules, SQL/Entra/Windows-for-Entra authentication, auditing, Advanced Threat Protection, TLS in transit, TDE at rest, Key Vault-managed keys, Always Encrypted, dynamic data masking) as other tiers.

Automatic tuning is a built-in, ML-driven feature that identifies expensive queries, forces the last known good execution plan, and creates or drops indexes based on observed query patterns — candidate indexes are validated against a copy of the database before being applied for real, and the feature is inherited from the parent logical server but can be disabled per database.

## Configure Azure SQL Managed Instance for scale and performance

SQL Managed Instance is purchased only on the vCore model — it does not support the DTU model at all. There are two service tiers, aligned with SQL Database's vCore tiers: General Purpose and Business Critical, the latter adding In-Memory OLTP and a readable secondary, with Always On Availability Groups underlying its higher resilience; both allow independent configuration of storage and compute. A single managed instance supports up to 100 databases and full access to system databases.

Instance pools give a fast (under 10 minutes), cost-efficient deployment option for migrating many smaller SQL Server instances without consolidating them into one larger instance (which would need extra governance/security planning); all instances in a pool share a VM, and total IP allocation is independent of instance count.

Hybrid licensing lets each core of Enterprise Edition with active Software Assurance convert to one Business Critical vCore or eight General Purpose vCores, and each Standard Edition core with active SA converts to one General Purpose vCore — potentially cutting total license cost by up to 40% since you then pay only for compute/storage, not SQL Server licensing.

Connections route through a highly available TDS gateway component rather than connecting directly to the instance. The Managed Instance Link (built on distributed availability groups) can also be used purely for scale/performance reasons — offloading read-only reporting workloads to a secondary replica hosted on Managed Instance — independent of its migration or DR use cases.

## Configure SQL Server on Azure Virtual Machines for scale and performance

VM sizing should match the workload to one of six VM families: General purpose (balanced CPU:memory, good for test/dev and small-to-medium DB servers), Compute optimized (high CPU:memory ratio, medium-traffic web/app servers, batch, non-GPU ML), Memory optimized (high memory:CPU ratio, up to 4 TB RAM, best fit for most database workloads), Storage optimized (fast ephemeral local NVMe, needs Always On Availability Groups or Log Shipping for data protection since local storage isn't durable), GPU (video/graphics or massively parallel ML), and FPGA-accelerated/High Performance Compute (compute-intensive or horizontally-scaled HPC with RDMA networking).

For storage, production SQL Server data and log files should only use Premium SSD or Ultra Disk. Azure managed disks offer 99.999% availability and up to 50,000 VM disks per subscription per region, and support two independent encryption layers (Server-side encryption at the storage-service layer, and Azure Disk Encryption via BitLocker/DM-Crypt inside the VM, both able to use a customer-managed key in Key Vault). Every VM has an OS disk (boot volume, C:\ or /dev/sda1) and a temporary disk (D:\ or /dev/sdb1) — the temporary disk must never hold database or log files since its contents are lost on maintenance or reboot. Additional managed data disks should be added and pooled (Storage Spaces on Windows, LVM on Linux) to increase available IOPS/capacity; data files should get their own pool with read caching, log files their own pool with no caching (log I/O doesn't benefit from caching), and tempdb can go on its own pool or on the VM's low-latency local temporary disk.

Disk type | Best for | Max size | Max throughput | Max IOPS
---|---|---|---|---
Ultra Disk | IO-intensive workloads | 65,536 GiB | 10,000 MB/s | 400,000
Premium SSD v2 | Performance-sensitive workloads | 65,536 GiB | 2,000 MB/s | 80,000
Premium SSD | Performance-sensitive workloads | 32,767 GiB | 900 MB/s | 20,000
Standard SSD | Lightweight workloads | 32,767 GiB | 750 MB/s | 6,000
Standard HDD | Backups, non-critical workloads | 32,767 GiB | 500 MB/s | 2,000

Properly configured Premium SSD delivers single-digit-millisecond latency (roughly 5–10 ms); Ultra Disk gets to sub-millisecond in theory and typically 1–2 ms in practice, and should be considered for mission-critical workloads needing latency below what Premium SSD delivers.

Beyond storage and sizing, a standard performance checklist for production SQL Server on Azure VMs includes: enabling backup compression; enabling instant file initialization for data files; limiting database autogrowth; disabling autoshrink/autoclose; moving all databases (including system databases) and the error log/trace directories onto data disks rather than the OS disk; setting a max server memory limit; enabling lock pages in memory; enabling "optimize for ad hoc workloads" for OLTP-heavy systems; enabling Query Store; scheduling SQL Server Agent jobs for DBCC CHECKDB, index reorganize/rebuild, and update statistics; and monitoring transaction log health and size. Data compression and table/index partitioning (covered separately) are also standard performance levers available on VM-hosted SQL Server, since they're identical to on-premises SQL Server features.

## Configure table partitioning

Implementing table partitioning is a four-step T-SQL process: create the filegroups that will hold the partitions, create a partition function that defines the boundary values/rule for how rows map to partitions based on a column, create a partition scheme that maps each partition produced by the function to a specific filegroup, and finally create (or alter) the table so that it's built on that partition scheme, keyed on the partitioning column. Example creating 13 monthly partitions for calendar year 2021:

```sql
-- Partition function
CREATE PARTITION FUNCTION PartitionByMonth (datetime2)
    AS RANGE RIGHT
    FOR VALUES ('20210101', '20210201', '20210301',
      '20210401', '20210501', '20210601', '20210701',
      '20210801', '20210901', '20211001', '20211101',
      '20211201');

-- Partition scheme assigns each partition to a filegroup
CREATE PARTITION SCHEME PartitionByMonthSch
    AS PARTITION PartitionByMonth
    TO (FILEGROUP1, FILEGROUP2, FILEGROUP3, FILEGROUP4,
        FILEGROUP5, FILEGROUP6, FILEGROUP7, FILEGROUP8,
        FILEGROUP9, FILEGROUP10, FILEGROUP11, FILEGROUP12,
        FILEGROUP13);

-- Partitioned table
CREATE TABLE Order ([Id] int PRIMARY KEY, OrderDate datetime2)
    ON PartitionByMonthSch (OrderDate);
```

Once partitioned, index and compression maintenance can target individual partitions (e.g., compressing or rebuilding just one partition) instead of the whole table, and queries filtered on the partitioning column only touch the relevant partitions.

## Configure data compression

SQL Server still stores compressed data on standard 8 KB pages, but compression packs more rows per page, so a query reads fewer pages — reducing physical I/O and letting more rows fit in the buffer pool for more efficient memory use. In one documented example, a query against a page-compressed table performed 72% fewer logical reads than the same query against the uncompressed table with identical indexes. The tradeoff is a small CPU overhead for compression/decompression, which is usually far outweighed by the I/O savings; database page compression is recommended where appropriate.

Compression is configured per object (table or index), and you can compress individual partitions within a partitioned table/index rather than the whole object. Use `sp_estimate_data_compression_savings` to estimate the space savings before committing to a compression change (prior to SQL Server 2019 this procedure didn't support columnstore or columnstore archival compression). Three compression types apply: row compression stores each column value in the minimum space it needs (variable-length storage for numeric types, variable-length format for fixed-length character strings) with fairly low overhead but a correspondingly smaller space reduction; page compression is a superset of row compression — every page is first row-compressed, then prefix compression removes redundant data within a column (replacing it with pointers to the page header) and dictionary compression replaces repeated values across the page with pointers, so the win scales with how much redundancy exists in the data; columnstore archival compression further compresses already-compressed columnstore objects using the Microsoft XPRESS algorithm, intended for infrequently-read data that must be retained for regulatory/business reasons, since decompression CPU cost usually outweighs the I/O benefit for actively queried data.

## Evaluate requirements for a migration

Evaluating a migration means weighing data recoverability, disaster recovery, security, and licensing/cost requirements against what each target platform offers, then matching the workload to Azure SQL Database, Azure SQL Managed Instance, or SQL Server on a VM. Azure SQL Database's baseline capability set for a migration decision includes: automatic backup, point-in-time restore, 7+ days of backup retention with optional long-term retention up to 10 years, a 99.99% availability SLA with three built-in secondary replicas and optional zone redundancy, geo-restore and active geo-replication for DR, dynamic scale-up/down plus scale-out via sharding and shared-resource elastic pools, Microsoft Entra authentication, Advanced Threat Protection, TDE by default, dynamic/static data masking, row-level security, Always Encrypted, and firewall allowlisting, alongside DTU pricing for predictable costs or vCore pricing (combinable with Azure Hybrid Benefit for up to ~30% savings).

Certain capabilities are exclusive to Azure SQL Database and should weigh into the decision when a workload can use them: Hyperscale (independently scalable compute/storage, up to 100 TB), serverless auto-scale/auto-pause, automatic index tuning (creates/validates/removes indexes automatically), elastic query (cross-database T-SQL bridging), elastic jobs (the SQL Agent replacement for SQL Database), and Query Performance Insights for identifying which queries to optimize. Conversely, requirements for instance-level features (SQL Agent via msdb, cross-database joins, CLR, up to 100 databases, near-100% on-premises compatibility) point toward SQL Managed Instance instead, and requirements for full OS access, legacy SQL Server versions, or co-located services like SSAS/SSIS/SSRS point toward a VM.

## Evaluate offline or online migration strategies

Migrations to Azure SQL targets are either offline (application experiences downtime during the cutover) or online (minimal to no downtime). For migrating to Azure SQL Database, the available tools split as: Azure Database Migration Service — offline (recommended for large migrations and the best overall experience); transactional replication — the only online option; Azure Migrate — offline (used for pre-migration assessment/compatibility checks); Import/Export via BACPAC — offline; bulk copy (bcp) — offline; Azure Data Factory — offline (better suited to partial/BI-oriented data movement than full database migration).

For migrating to SQL Managed Instance, Log Replay Service (LRS) and the Managed Instance Link are the two headline options, and the choice between them should be evaluated on several axes: minimum downtime (Link cuts over in seconds; LRS has a longer cutover, especially on Business Critical), ability to read data mid-migration (supported on Link; not available on LRS since the database is in restoring state), source SQL Server version (Link needs 2016+; LRS supports 2012+), SQL Server edition (Link needs Enterprise/Standard/Developer; LRS works with any edition), network requirements (Link needs a VPN or private endpoint; LRS works over a public endpoint by default), migration duration (Link is unlimited; LRS is capped at 30 days), and whether reverse migration/failback is needed (supported on Link, not on LRS). Native backup/restore and transactional replication are also available for Managed Instance migrations, and Azure Arc adds a portal-integrated assessment-and-migration path on top of both LRS and Link.

## Implement an online migration strategy

Transactional replication is the only fully online mechanism for migrating into Azure SQL Database, and it's also available for Managed Instance (which, unlike SQL Database, can act as publisher, distributor, or subscriber). It works by taking an initial snapshot of the publication's objects and data, then streaming subsequent changes at the Publisher to the target in near real time. The required roles are Publisher (source), Distributor (collects and routes changes), Subscriber (target), plus the logical objects Article (a replicated object, e.g. a table), Publication (a collection of articles), and Subscription (a Subscriber's request for a Publication). Configuration is done through SSMS or T-SQL against the publisher — it cannot be configured from the Azure portal — and replication into Azure SQL Database can only authenticate using SQL Server logins. A typical setup script sequence is: `sp_adddistributor` and `sp_adddistributiondb` to stand up the distribution database, `sp_adddistpublisher` and `sp_addsubscriber` to register the publisher and the Azure SQL Database subscriber, `sp_replicationdboption @optname = 'publish'` to enable replication on the source database, `sp_addlogreader_agent`/`sp_addqreader_agent` to add the log reader and queue reader agents, `sp_addpublication` and `sp_addpublication_snapshot` to define the publication, `sp_addarticle` to add each replicated table, and `sp_addsubscription`/`sp_addpushsubscription_agent` to create the push subscription into the target database. Once configured, the snapshot, log reader, and distribution agent jobs must be started to initiate replication, and — because replication administration isn't supported from the Azure SQL Database side — all monitoring (Snapshot Agent/Log Reader Agent status, synchronization status, agent job history) is done from SQL Server/SSMS, not the Azure portal. After the target is fully synchronized, cut connections over to the subscriber and then tear down the replication topology.

For Managed Instance specifically, the Managed Instance Link is the true online migration option, built on distributed availability groups (DAG), scoped one link per database (though multiple links can fan a single SQL Server instance out to one or more managed instances, or replicate the same database to several). One-way replication (SQL Server 2016/2019) replicates only from SQL Server to Managed Instance; two-way replication (SQL Server 2022) additionally supports manual failover and (offline) failback, with online failback in preview. Cutover with Link happens in seconds. Beyond migration, the same Link mechanism can offload read-only workloads to Azure, provide automated backups of the Azure-side secondary, and serve as an ongoing DR/business-continuity mechanism (fail over to Managed Instance, fail back once resolved). It's configured via the SSMS Link wizard or via T-SQL/PowerShell scripts (scripts are preferable for automation); features like file tables and FILESTREAM aren't supported on Managed Instance and will block enabling the Link.

## Implement an offline migration strategy

Azure Database Migration Service (ADMS) is the primary managed offline path, and it's automatable end-to-end through the `az datamigration` CLI extension (`az extension add --name datamigration`) or the equivalent PowerShell cmdlets, which is useful for CI/CD pipelines and migrating many databases at scale. Prerequisites are: Azure CLI with the datamigration extension, an ADMS instance provisioned in the subscription, the target Azure SQL Database already provisioned with schema deployed, and a self-hosted integration runtime configured for connectivity to the source. The typical flow is: create the service (`az datamigration sql-service create`), migrate the schema first (`az datamigration sql-server-schema --action MigrateSchema` with source/target connection strings), then start the data migration (`az datamigration sql-db create`, optionally scoped to specific tables via `--table-list`; empty tables are skipped automatically). A migration passes through the states Preparing for copy (disabling autostats/triggers/indexes on target) → Copying → Copy finished → Rebuilding indexes → Succeeded. Progress can be checked with `az datamigration sql-db show --expand MigrationStatusDetails`, blocked on with `az datamigration sql-db wait --created`, or stopped with `az datamigration sql-db cancel`, or monitored from the ADMS blade in the portal. Recommended performance practices: scale up the target SQL Database before migrating (Business Critical Gen5 8 vCore, or Hyperscale, to minimize log-file latency), ensure adequate network bandwidth for peak log ingestion, choose the highest service tier/compute for the migration window and scale down afterward, disable auto-update/auto-create statistics during migration, and run up to 10 concurrent migrations per self-hosted integration runtime (scale the runtime out, or add more runtime hosts, for more concurrency).

BACPAC-based offline migration packages both schema and data into a compressed file, importable from Azure Blob Storage or local storage. The Azure portal's "Import database" action on the target server (choosing storage account/container and BACPAC file, then destination size and credentials) is the simplest path, with progress visible under Import/Export history; for production-scale imports, the SqlPackage utility is faster, and running multiple SqlPackage processes in parallel against table subsets further speeds things up, e.g. `SqlPackage.exe /a:import /tcs:"..." /sf:AdventureWorks2019.bacpac /p:DatabaseEdition=Premium /p:DatabaseServiceObjective=P6` — scaling the target up for the duration of the import and back down afterward is recommended. `bcp` (Bulk Copy Program) exports/imports individual tables to/from flat files and is commonly used for partial, table-level offline data movement rather than whole-database migration; Azure Data Factory can similarly move and transform a subset of tables, and is more associated with BI-oriented workloads than full database migrations.

For SQL Managed Instance, Log Replay Service (LRS) is the primary controlled offline (or low-tolerance-downtime) option, using log-shipping technology and orchestrated via PowerShell, CLI, or API — useful when ADMS can't be used, when the environment can't install the DMS executable, lacks file access to backups, or can't open the necessary network ports. LRS has two modes: Autocomplete (finishes automatically once the last backup in the chain is restored — best for passive workloads, requires the whole backup chain up front) and Continuous (keeps scanning for and restoring new backup files, letting data catch up incrementally — best for active workloads). Regardless of mode, an LRS job auto-cancels after 30 days. Running LRS requires Subscription Owner, SQL Managed Instance Contributor, or a custom role with `Microsoft.Sql/managedInstances/databases/*`; it needs an Azure Blob Storage account as intermediary storage (with the MI subnet added to the storage account firewall via subnet delegation and service endpoint if the storage account is firewalled), and authenticates to that storage with either a SAS token or a managed identity, but not both simultaneously. Splitting full/differential backups into multiple files improves parallel read/write throughput; enabling backup compression speeds network transfer; and enabling CHECKSUM on backups, while not required, is strongly recommended because Managed Instance otherwise performs its own integrity check on restore, which slows the restore down.

## Implement a migration to Azure

Moving an on-premises or other-cloud SQL Server workload into Azure starts with choosing the target platform (VM/IaaS vs. SQL Database/Managed Instance PaaS) based on the requirements evaluation above, then executing whichever online/offline mechanism fits (ADMS, BACPAC/SqlPackage, bcp, Azure Data Factory, transactional replication, LRS, or Managed Instance Link, per the target). For VM-based (IaaS) migrations, deploying from an Azure Marketplace SQL Server image installs the SQL Server IaaS Agent Extension automatically, giving automated backup/patching and Key Vault/Defender integration out of the box; native backup-to-URL or Azure Backup for SQL Server VMs are the standard ways to move existing backups into the new environment. When the source SQL Server is Azure Arc-enabled, the Azure portal provides an integrated, guided migration experience directly to SQL Managed Instance (assess → select target → migrate → monitor/cutover), with Copilot assistance and automatic weekly readiness assessments, removing the need to separately script LRS or Link.

Regardless of the path, applications must be built (or updated) to tolerate transient connection failures during and after migration — implement retry logic with an increasing backoff, starting at a minimum 5-second wait on the first retry and increasing exponentially up to a maximum of 60 seconds; note that a failed `SELECT` should not be retried directly on the same connection but reissued on a new one.

## Implement a migration between Azure SQL services

Moving data between two Azure SQL targets (for example, VM to SQL Database, SQL Database to Managed Instance, or between two SQL Database instances) generally reuses the same tool set as an on-premises-to-Azure migration, since most tools (ADMS, BACPAC/SqlPackage, bcp, transactional replication, Azure Data Factory) work against any SQL endpoint, Azure-hosted or not. Geo-restore, which restores a geo-redundant backup into a different region, is one Azure-to-Azure movement mechanism specific to the PaaS backup architecture (available whenever backup storage redundancy is geo-redundant) and can be used to relocate a database to another Azure region without a full logical migration. The Managed Instance Link, similarly, isn't restricted to on-premises sources — it can replicate a database hosted "anywhere," including another Azure VM or another managed instance, which makes it usable for moving data between two Azure-hosted SQL services as well as for hybrid scenarios. Instance pools support this pattern too, by giving a landing zone to consolidate multiple smaller Azure-hosted or migrated SQL Server instances into a shared-resource footprint without merging them into one large managed instance.

## Implement Azure SQL Managed Instance database copy and move

Managed Instance supports a user-initiated copy-only backup to Azure Blob Storage — a capability SQL Database does not have — using `BACKUP DATABASE ... TO URL = '...' WITH COPY_ONLY`, and the corresponding `RESTORE DATABASE ... FROM URL = '...'` to bring it into another instance. Databases larger than 200 GB can use a striped backup by supplying multiple URL locations. Because Managed Instance databases are encrypted by default with Transparent Data Encryption using a Microsoft-managed key, TDE must be disabled on the specific database before a user-initiated copy-only backup can be taken; conversely, restoring an encrypted database requires access to the original certificate or asymmetric key, without which the restore cannot proceed.

Several hard constraints apply specifically to Managed Instance restores: you cannot overwrite an existing database — it must not exist (or must be dropped/renamed) before the restore; a Managed Instance backup can only be restored to another managed instance, never to a SQL Server VM or to Azure SQL Database; restoring between two managed instances requires both instances to be in the same Azure subscription and region; and you can restore individual databases only, never an entire managed instance in one operation. Because it's a genuine SQL Server engine, Managed Instance does support the T-SQL `RESTORE` command directly (unlike SQL Database), but only from a URL (no local drive access), and only with the options FILELISTONLY, HEADERONLY, LABELONLY, and VERIFYONLY alongside the database name; backup files containing multiple log files, multiple backup sets, or In-Memory/FILESTREAM data cannot be restored to Managed Instance at all. Restores can be initiated via the Azure portal, PowerShell, or Azure CLI. BACPAC-based copy is not supported natively through the Managed Instance portal experience — SqlPackage against a BACPAC file must be used as the workaround instead.

## Troubleshoot a migration

Migration status tracking is the first troubleshooting tool for ADMS: the states Preparing for copy, Copying, Copy finished, Rebuilding indexes, and Succeeded (surfaced via `az datamigration sql-db show --expand MigrationStatusDetails` or the portal) show exactly where a migration has stalled or failed, and errors encountered are returned in that same status payload. Known ADMS performance failure modes to watch for: migrations with a large number of tables run slowly because Azure Data Factory (which underlies ADMS) takes noticeable time just to start each activity, even against small tables; and tables containing large blob columns can fail outright due to timeout — these usually need to be handled separately (e.g., via bcp or a dedicated ADF pipeline) rather than folded into the bulk ADMS job.

For transactional replication, remember that replication administration and monitoring are not available from the Azure SQL Database side at all — troubleshooting must happen from SQL Server/SSMS: check whether the Snapshot Agent and Log Reader Agent are running (right-click the publication/subscription to view status or start them), check the Synchronization Status on the subscription, and if errors appear, check the SQL Server Agent job history for the underlying agent jobs.

For Log Replay Service, remember the 30-day hard limit — an LRS job that isn't completed within 30 days is automatically canceled, so a stalled LRS migration needs to be diagnosed (backup chain gaps, storage connectivity, RBAC permission issues, missing subnet delegation/service endpoint on the storage firewall) well before that deadline. Connection and retry issues are also a common post-migration symptom regardless of tool: implement exponential-backoff retry logic (starting at 5 seconds, doubling up to a 60-second cap) for transient errors, and never retry a failed `SELECT` on the same connection — open a new connection first, since the original may be in an indeterminate state.
