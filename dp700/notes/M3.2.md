# Real-Time Data Processing in Fabric

This module covers operational aspects of working with real-time data — streaming ingestion behaviours, Eventstream routing logic, and patterns for consuming real-time data alongside batch data.

---

## Streaming Concepts in Fabric

### Event Time vs Ingestion Time
- **Event time**: when the event actually occurred (embedded in the data payload)
- **Ingestion time**: when Fabric received and stored the event (`ingestion_time()` in KQL)

These differ when there is **latency between event generation and ingestion** (network delays, buffering). For real-time analytics, choosing which timestamp to filter on matters significantly:

```kql
// Using ingestion time (when Fabric received it)
Events | where ingestion_time() > ago(1h)

// Using event time (when it actually happened)
Events | where EventTimestamp > ago(1h)
```

> **Exam Tip:** Use **ingestion time** for operational queries ("what came in recently"). Use **event time** for business analytics ("what happened recently"). Late-arriving events can appear in queries based on ingestion time even if their event time is older.

### Late Arriving Data
Events may arrive out of order or delayed. KQL's `ingestion_time()` always reflects arrival order, not event order. For accurate time-window analysis, filter on event time and account for the expected latency window.

## Eventstream — Deep Dive

### Eventstream Processing Model

```
Source → [Transform] → [Route] → Destinations
```

An Eventstream is a **continuous, unbounded stream** — it has no defined start or end. It processes events one at a time (or in micro-batches) and routes them to destinations.

### Windowed Aggregation in Eventstream
Eventstream supports **tumbling window** aggregations:
- **Tumbling window**: fixed, non-overlapping time windows (e.g., aggregate every 5 minutes)
- Groups events by time bucket + grouping key
- Outputs one row per window per group

```
Input events with timestamps:
[09:00-09:05] → Window 1 (5-minute tumbling) → Aggregate → Output
[09:05-09:10] → Window 2                     → Aggregate → Output
```

### Eventstream Routing Conditions
You can route different events to different destinations based on field values:
```
Events where EventType == "error"   → Eventhouse errors table
Events where EventType == "warning" → Lakehouse warnings table
All events                          → Archive Lakehouse
```

## Ingesting into KQL Database Tables

### Direct Ingestion (Streaming)
Data flows from Eventstream → KQL table continuously with **seconds of latency**.

### Batch Ingestion into KQL
KQL databases can also accept batch ingestion via:
- **Pipeline Copy Data activity** → target is a KQL database table
- **One-click ingestion** from files (for bootstrapping historical data)

> **Exam Tip:** KQL databases are primarily designed for **streaming ingestion**, but they also support batch ingestion for historical backfill. The exam may ask you to choose the ingestion method — streaming via Eventstream for ongoing real-time data, batch via Pipeline for historical load.

### Table Ingestion Properties
Each KQL table can have an **ingestion batching policy** — controls how Eventstream batches events before writing to the table (trading latency for throughput):
- `MaximumBatchingTimeSpan`: default 5 minutes (maximum time to wait before flushing a batch)
- `MaximumNumberOfItems`: default 500,000 rows per batch
- `MaximumRawDataSizeMB`: default 1,024 MB per batch

Lowering `MaximumBatchingTimeSpan` reduces latency but increases write operations.

## KQL Database Table Management

### Creating Tables
```kql
.create table Events (
    Timestamp: datetime,
    EventType: string,
    UserID: long,
    DeviceID: string,
    Payload: dynamic
)
```

### Data Types
| KQL Type | Description |
|---|---|
| `datetime` | Date and time value |
| `timespan` | Duration (e.g., `1h`, `5m`, `30s`) |
| `string` | Text |
| `int` / `long` | 32-bit / 64-bit integer |
| `real` / `decimal` | Floating point / precise decimal |
| `bool` | Boolean |
| `dynamic` | JSON-like flexible type — arrays, objects |
| `guid` | Globally unique identifier |

> **Exam Tip:** `dynamic` is the most flexible KQL type — it stores JSON and supports array and object operations. Use it for variable-schema payloads like sensor readings or user events. Access nested fields with `.` notation: `Payload.temperature`.

### Updating Table Schemas
```kql
.alter table Events (Timestamp: datetime, EventType: string, NewColumn: real)
// Replaces the entire schema — use with caution
```

### Retention Policy
```kql
.alter table Events policy retention softdelete = 30d
// Data older than 30 days is automatically deleted
```

## Cross-Querying: KQL + Lakehouse

Fabric supports **cross-database and cross-workspace queries** in KQL:

```kql
// Query a Lakehouse table from a KQL Queryset
let lakedatahouse = external_table("silver_orders");
// Not a standard feature — cross-platform queries go via shortcuts

// More commonly: export KQL results to Lakehouse
.export to csv (
    h@"https://onelake.dfs.fabric.microsoft.com/workspace/lakehouse.Lakehouse/Files/exports/events.csv"
) <|
    Events | where EventDate > ago(7d)
```

Alternatively, use **OneLake shortcuts** to expose KQL database tables as readable files in a Lakehouse for Spark processing.

## Real-Time vs Batch: Choosing the Right Tool

| Requirement | Tool |
|---|---|
| Sub-second query latency on recent data | KQL Database + Eventhouse |
| Complex transformations on streaming data | Spark Structured Streaming (Notebook) |
| Simple routing: stream A → multiple destinations | Eventstream |
| Historical backfill of event data | Pipeline + KQL batch ingestion |
| Combining real-time and historical in one query | KQL with Lakehouse shortcut |

## Common Exam Traps

**"Eventstream only supports one output destination"** — False. Multiple destinations can be configured simultaneously.

**"Ingestion time and event time are always the same"** — False. They differ whenever there's any latency between the event happening and it being received by Fabric. Late-arriving events make this difference significant.

**"KQL databases are only for streaming data"** — False. They support batch ingestion too — useful for historical backfill alongside ongoing streaming.

**"`dynamic` fields are not queryable"** — False. Dynamic fields are fully queryable using dot notation and KQL's `parse`, `parse_json`, and `mv-expand` operators.
