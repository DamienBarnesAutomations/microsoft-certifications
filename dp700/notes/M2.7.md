# Organising a Fabric Lakehouse

This module covers best practices for structuring data within a Fabric lakehouse — folder organisation, naming conventions, the medallion architecture, and managing the lakehouse as a production asset.

---

## The Medallion Architecture

The standard layering pattern for lakehouse data. Each layer has a distinct purpose and quality standard:

### Bronze (Raw Layer)
- **Purpose**: Exact copy of source data, unmodified
- **Format**: Delta preferred, but CSV/JSON/Parquet also common
- **Characteristics**: Append-only, preserves original schema and values, never modified after write
- **Location**: `Tables/bronze_*` or `Files/raw/*`

### Silver (Cleansed Layer)
- **Purpose**: Validated, cleaned, conformed data
- **Format**: Delta (always)
- **Characteristics**: Nulls handled, types cast, duplicates removed, business rules applied, consistent naming
- **Location**: `Tables/silver_*`

### Gold (Curated Layer)
- **Purpose**: Business-ready aggregated or domain-specific data
- **Format**: Delta (always)
- **Characteristics**: Optimised for consumption (star schema, aggregated KPIs), directly backing semantic models or reports
- **Location**: `Tables/gold_*`

> **Exam Tip:** Bronze data should **never be modified**. If source data is corrected, re-ingest to Bronze and let the Silver transformation pipeline reprocess. Modifying Bronze removes your audit trail.

## Folder and Naming Conventions

### Recommended Table Naming
```
{layer}_{domain}_{entity}
e.g.:
bronze_sales_orders
silver_sales_orders
gold_sales_monthly_summary
```

### Files Section Organisation
```
Files/
├── raw/
│   ├── sales/
│   │   ├── 2024/
│   │   │   ├── 01/
│   │   │   │   └── orders_20240101.csv
├── staging/
│   └── ...
├── checkpoints/
│   └── streaming_events/
└── exports/
    └── reports/
```

## Managing Multiple Lakehouses

For larger teams or complex architectures, separate lakehouses by layer:

| Architecture | Lakehouses |
|---|---|
| Single lakehouse | `bronze_*`, `silver_*`, `gold_*` tables all in one lakehouse |
| Per-layer lakehouses | Bronze Lakehouse, Silver Lakehouse, Gold Lakehouse |
| Per-domain lakehouses | Sales Lakehouse, Finance Lakehouse, HR Lakehouse |

**Per-layer lakehouses** — cleaner access control (Bronze is ingestion-only, Gold is read-only for analysts), and each layer can have its own capacity allocation.

**Shortcuts between lakehouses** — Gold lakehouse can shortcut to Silver lakehouse tables, enabling zero-copy access without duplicating data between layers.

## Access Control in the Lakehouse

Lakehouses use **workspace roles** for broad access and **item-level permissions** for more granular control.

### Workspace Roles
| Role | Capabilities |
|---|---|
| Admin | Full control, manage workspace |
| Member | Create/edit/delete items, manage permissions |
| Contributor | Create/edit items, cannot manage permissions |
| Viewer | Read-only access to all items in workspace |

### Sharing a Lakehouse
You can share a specific lakehouse with external users without adding them to the workspace:
- Share the lakehouse → grants read access to the SQL Analytics Endpoint and/or OneLake files
- Optionally grant `ReadAll` (full OneLake file access) or `ReadData` (SQL endpoint only)

> **Exam Tip:** Workspace **Viewer** role gives read access to all items in the workspace. If you need to restrict access to only specific lakehouses, don't add users to the workspace — share only the specific lakehouse item.

## Table Management and Maintenance

### Scheduled Maintenance
Run these regularly on production lakehouses:
```sql
-- Compact small files
OPTIMIZE silver_orders;

-- Compact + Z-order by common filter columns
OPTIMIZE silver_orders ZORDER BY (CustomerID, OrderDate);

-- Remove old data files (7-day default retention)
VACUUM silver_orders;
```

Automate via a Fabric Pipeline with a Notebook activity running maintenance SQL on a schedule.

### Monitoring Table Health
```sql
-- Check file statistics
DESCRIBE DETAIL silver_orders;
-- Shows: numFiles, sizeInBytes, partitionColumns, location, format

-- View transaction history
DESCRIBE HISTORY silver_orders;
```

## Lakehouse vs Lakehouse (SQL) Endpoint Usage

The same Fabric lakehouse surfaces as two different experiences:

| Experience | Interface | Access Pattern |
|---|---|---|
| **Lakehouse** (Data Engineering) | Spark, Files browser, notebook | Read + Write via Spark |
| **SQL Analytics Endpoint** | T-SQL via SQL editor, Power BI | Read-only via SQL |

Both views see the same data in `Tables/`. Changes made via Spark appear immediately in the SQL endpoint (no sync delay — same underlying files).

## OneLake File Explorer

The **Microsoft OneLake File Explorer** is a Windows desktop application (like OneDrive) that mounts OneLake storage as a local drive. Data engineers can:
- Browse lakehouse files as if they were local files
- Copy files from local machine directly into lakehouse `Files/` section
- This is suitable for small, ad-hoc uploads — not for production ingestion

## Common Exam Traps

**"Bronze data should be cleaned before storing"** — No. Bronze is raw and unmodified. Cleaning happens at Silver. If Bronze is modified, you lose the ability to re-derive Silver from scratch.

**"Workspace Viewer role gives access to specific items only"** — False. Viewer gives read access to ALL items in the workspace. For item-level restriction, share the item directly rather than adding to workspace.

**"Changes made via Spark take time to appear in the SQL endpoint"** — False. The SQL endpoint reads the same Delta files that Spark writes to. There is no sync delay — the change is immediately visible (after the Spark write commits).

**"You can use OneLake File Explorer for production ingestion"** — No. It's suitable for manual, small-scale file uploads. Production ingestion should use Pipelines, Dataflows, or Spark.
