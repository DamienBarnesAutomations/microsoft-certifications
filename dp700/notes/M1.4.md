# Delta Lake Tables in Microsoft Fabric

**Delta Lake** is the default table format in Microsoft Fabric lakehouses. It sits on top of Parquet files and adds a **transaction log** that enables ACID transactions, versioning, schema enforcement, and time travel. Every Fabric lakehouse Table is a Delta table.

---

## What Delta Lake Adds to Parquet

| Feature | Plain Parquet | Delta Lake |
|---|---|---|
| ACID transactions | ❌ | ✅ |
| Schema enforcement | ❌ | ✅ |
| Time travel | ❌ | ✅ |
| Streaming + batch unified | ❌ | ✅ |
| `UPDATE` / `DELETE` / `MERGE` | ❌ | ✅ |
| Auto-compaction | ❌ | ✅ (configurable) |

The transaction log is stored in a `_delta_log/` folder alongside the Parquet files. Every operation (insert, update, delete, schema change) appends a JSON entry to this log.

---

## Creating Delta Tables

### From a DataFrame
```python
# Save as Delta (default format in Fabric lakehouses)
df.write.format("delta").saveAsTable("sales")

# Overwrite
df.write.format("delta").mode("overwrite").saveAsTable("sales")
```

### Using SQL
```sql
%%sql
CREATE TABLE products (
    ProductID INT,
    ProductName STRING,
    ListPrice FLOAT
)
USING DELTA;
```

### External Delta Table
```python
df.write.format("delta").save("Files/delta/sales")
# Table metadata not registered in catalog — access via path only
```

## Reading Delta Tables

```python
# Read as DataFrame from catalog
df = spark.read.format("delta").table("sales")

# Read from path (external)
df = spark.read.format("delta").load("Files/delta/sales")
```

## Time Travel

Delta Lake maintains the full history of changes. You can query any previous version.

```python
# Query by version number
df = spark.read.format("delta").option("versionAsOf", 2).table("sales")

# Query by timestamp
df = spark.read.format("delta").option("timestampAsOf", "2024-01-15").table("sales")
```

```sql
%%sql
-- SQL syntax for time travel
SELECT * FROM sales VERSION AS OF 2;
SELECT * FROM sales TIMESTAMP AS OF '2024-01-15';
```

### Restoring a Table
```sql
RESTORE TABLE sales TO VERSION AS OF 2;
RESTORE TABLE sales TO TIMESTAMP AS OF '2024-01-15';
```

> **Exam Tip:** `RESTORE` modifies the table **in place** — it does not create a new table. The restored state becomes the current version, and the restore itself is recorded as a new version in the log.

## VACUUM — Removing Old Files

Delta Lake retains old data files (Parquet files no longer referenced by the current snapshot) to support time travel. `VACUUM` physically deletes files older than the retention threshold.

```sql
VACUUM sales;                        -- Uses default retention (7 days)
VACUUM sales RETAIN 168 HOURS;       -- Explicit retention in hours
VACUUM sales RETAIN 0 HOURS DRY RUN; -- Preview what would be deleted
```

**Default retention: 7 days (168 hours)**

> **Exam Tip:** Running `VACUUM` with a retention period shorter than 7 days requires setting `spark.databricks.delta.retentionDurationCheck.enabled = false` to override the safety check. This is a deliberate guard — running VACUUM too aggressively breaks time travel for recent versions. This is a favourite exam gotcha.

> **Exam Tip:** After running `VACUUM`, time travel queries for versions older than the retention window will **fail** because the underlying Parquet files have been deleted.

## DESCRIBE HISTORY

View the full transaction log for a table:

```sql
DESCRIBE HISTORY sales;
```

Returns: version number, timestamp, operation (WRITE, UPDATE, DELETE, MERGE, RESTORE, VACUUM), operationParameters, and more.

## Schema Enforcement and Evolution

**Schema enforcement** (on by default): Delta rejects writes where the incoming data schema doesn't match the table schema. This prevents silent data corruption.

**Schema evolution**: Allows adding new columns to an existing Delta table on write.
```python
df.write.format("delta").option("mergeSchema", "true").mode("append").saveAsTable("sales")
```

To overwrite schema entirely:
```python
df.write.format("delta").option("overwriteSchema", "true").mode("overwrite").saveAsTable("sales")
```

> **Exam Tip:** `mergeSchema` only **adds** new columns; it won't change existing column types. Changing a column type requires `overwriteSchema` (which overwrites all data) or an explicit `ALTER TABLE` with a compatible cast.

## Optimisation Techniques

### OPTIMIZE (File Compaction)
Small files accumulate over time from streaming writes or many small inserts. `OPTIMIZE` merges them into larger files.

```sql
OPTIMIZE sales;
```

### Z-Ordering
Multi-dimensional clustering that co-locates related data within files, improving filter performance on the specified columns:

```sql
OPTIMIZE sales ZORDER BY (ProductCategory, SaleDate);
```

> **Exam Tip:** Z-ordering does **not** physically partition the data like `partitionBy` does. It co-locates data *within* files. Combine partitioning (for very high-selectivity filters like date) with Z-ordering (for secondary filters like category) for best results.

## Streaming with Delta Lake

Delta tables support both **batch** and **streaming** reads and writes in the same table — the "unified batch and streaming" capability.

```python
# Stream from a Delta table
streamDf = spark.readStream.format("delta").table("raw_events")

# Stream into a Delta table
streamDf.writeStream.format("delta").outputMode("append").option("checkpointLocation", "Files/checkpoints/events").table("processed_events")
```

The checkpoint location stores the streaming offset — if the stream restarts, it picks up from where it left off.

## Managed vs External Delta Tables

| | Managed | External |
|---|---|---|
| Data location | Lakehouse Tables/ folder | Any path (Files/ or external storage) |
| Drop table | Deletes data | Data remains |
| In Fabric catalog | Yes | Only if explicitly registered |
| Created by | `saveAsTable()` | `save()` to a path |

## Common Exam Traps

**"VACUUM with 0 hours retention is safe to run immediately"** — False. You must override the safety check with `retentionDurationCheck.enabled = false`. Even then, files modified in the last few hours may still be in use by concurrent queries.

**"Time travel works forever"** — Only for as long as the files exist. Once VACUUM removes them, older versions are inaccessible.

**"OPTIMIZE and VACUUM do the same thing"** — No. `OPTIMIZE` merges small files into larger ones (all still current). `VACUUM` deletes *old* files that are no longer referenced by any version within the retention window.

**"Z-ordering is the same as partitioning"** — No. Partitioning creates folder structure by column value (one folder per distinct value). Z-ordering rearranges data within files for better data skipping. Partitioning on high-cardinality columns creates too many small files; Z-ordering handles those columns better.

**"`mergeSchema` can change column types"** — False. It only adds new columns. Type changes require `overwriteSchema` or an ALTER TABLE.
