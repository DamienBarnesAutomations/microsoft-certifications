# Monitoring a Fabric Data Warehouse

Warehouse monitoring in Fabric uses three complementary tools: the **Fabric Capacity Metrics app** (cost/capacity), **Dynamic Management Views — DMVs** (current activity), and **Query Insights** (historical query analysis).

---

## Fabric Capacity Metrics App

An admin-installable app that provides capacity-wide utilisation telemetry across all Fabric workloads, including warehouses.

**What it shows:**
- CU (Capacity Unit) consumption over time, broken down by Fabric item type
- Throttling events (when your workload exceeds purchased capacity)
- Per-operation CU consumption

**How to filter to warehouse activity:**
In the app interface, filter by item type = "Warehouse" to isolate warehouse CU consumption from Spark, Dataflows, etc.

> **Exam Tip:** CU consumption in a warehouse is driven primarily by **data read/write operations** — queries scan Parquet files from OneLake, and each file read consumes CUs. Long-running or full-table-scan queries are the biggest CU consumers. The Capacity Metrics app is the only tool for tracking billing/cost impact.

## Dynamic Management Views (DMVs)

DMVs provide **real-time snapshots** of current sessions, connections, and running queries.

### The Three Warehouse DMVs

```sql
-- Active connections to the warehouse
SELECT * FROM sys.dm_exec_connections;

-- Authenticated sessions (users currently connected)
SELECT * FROM sys.dm_exec_sessions;

-- Currently running or queued requests
SELECT * FROM sys.dm_exec_requests;
```

### Schema Relationships
```
sys.dm_exec_connections ──┐
                           ├── joined on session_id
sys.dm_exec_sessions ──────┘
        │
        └── joined on session_id
sys.dm_exec_requests
```

### Useful Combined Query: Identify Long-Running Queries
```sql
SELECT
    sessions.session_id,
    sessions.login_name,
    connections.client_net_address,
    requests.command,
    requests.start_time,
    requests.total_elapsed_time
FROM sys.dm_exec_connections AS connections
INNER JOIN sys.dm_exec_sessions AS sessions
    ON connections.session_id = sessions.session_id
INNER JOIN sys.dm_exec_requests AS requests
    ON requests.session_id = sessions.session_id
WHERE requests.status = 'running'
    AND requests.database_id = DB_ID()
ORDER BY requests.total_elapsed_time DESC;
```

**Returns:** Active queries ordered by how long they've been running. The longest-running query is at the top — useful for identifying queries to kill or optimise.

> **Exam Tip:** DMVs show **current state only** — they show queries that are running *right now*. They do not store history. For historical analysis, use Query Insights views.

**Killing a session:**
```sql
KILL 126;  -- session_id from sys.dm_exec_sessions
```

## Query Insights Views

Query Insights is a set of **historical, aggregated query telemetry** views that persist query metadata after execution. Unlike DMVs, these survive session termination.

### The Three Query Insights Views

```sql
-- History of completed queries
queryinsights.exec_requests_history

-- Long-running queries (aggregated stats)
queryinsights.long_running_queries

-- Frequently executed queries
queryinsights.frequently_run_queries
```

### exec_requests_history — Recent Query History
```sql
SELECT start_time, login_name, command
FROM queryinsights.exec_requests_history
WHERE start_time >= DATEADD(MINUTE, -60, GETUTCDATE())
ORDER BY start_time DESC;
```

Returns each completed query with its text, user, start time, and duration.

### long_running_queries — Identify Slow Queries
```sql
SELECT last_run_command, number_of_runs, median_total_elapsed_time_ms, last_run_start_time
FROM queryinsights.long_running_queries
WHERE number_of_runs > 1
ORDER BY median_total_elapsed_time_ms DESC;
```

**Key columns:**
- `last_run_command` — parameterised query text
- `number_of_runs` — how many times executed
- `median_total_elapsed_time_ms` — median duration across all runs
- `last_run_start_time` — when it was last run

> **Exam Tip:** Query Insights **parameterises queries** for aggregation. `SELECT * FROM sales WHERE orderdate > '01/01/2023'` and `SELECT * FROM sales WHERE orderdate > '12/31/2021'` are treated as the **same query** because they differ only in the literal value. This means `number_of_runs` counts executions of the same logical query pattern, not exact SQL strings.

### frequently_run_queries — Usage Patterns
```sql
SELECT last_run_command, number_of_runs, number_of_successful_runs, number_of_failed_runs
FROM queryinsights.frequently_run_queries
ORDER BY number_of_runs DESC;
```

Use this to identify:
- Queries worth creating views or pre-aggregations for
- Queries with high failure rates (data quality issues, permission problems)

> **Exam Tip:** Query Insights data is **not real-time** — there is up to a **15-minute lag** before recent queries appear in these views. If a query just finished 2 minutes ago, it may not yet appear in `exec_requests_history`.

## Monitoring Strategy Summary

| Tool | What It Monitors | Time Scope | Who Uses It |
|---|---|---|---|
| Fabric Capacity Metrics App | CU consumption, throttling, cost | Historical (hours/days) | Admins |
| DMVs (`sys.dm_exec_*`) | Active connections, sessions, queries | Real-time (now) | DBAs, Admins |
| Query Insights | Completed query history, slow queries, frequent patterns | Historical (up to 15 min lag) | DBAs, Developers |

## Common Exam Traps

**"DMVs show historical query data"** — False. DMVs show current state only. Use Query Insights for history.

**"Query Insights reflects queries immediately after they complete"** — False. Up to 15 minutes of lag. Don't rely on it for real-time monitoring.

**"Killing a session in DMVs cancels the query immediately"** — `KILL` requests the session to terminate, but it may not be instant — the engine needs to roll back any in-progress transactions first.

**"Query Insights treats identical queries as separate records"** — False. Queries are parameterised and deduplicated — same logical query with different literal values is counted as one query pattern with multiple runs.

**"The Capacity Metrics app is part of the warehouse"** — No, it's a separately installed app at the capacity/admin level. It's not accessible from within a warehouse.
