# Data Modelling in a Fabric Warehouse

Dimensional modelling is the standard approach for analytical data in a Fabric Warehouse. This module covers star schema design, dimension table patterns, and how to structure data for BI consumption.

---

## Dimensional Modelling Fundamentals

### Star Schema
The primary modelling pattern for analytical warehouses:
- **Fact table**: measures/events (numeric, foreign keys, high row count)
- **Dimension tables**: descriptive context (names, categories, dates, geographies)
- Fact table joins to dimensions via **surrogate keys**

```
DimDate ──┐
DimProduct ─┼─► FactSales ◄─┬── DimCustomer
DimStore ──┘               └── DimPromotion
```

Direct joins between fact and dimension tables only — no joins between dimension tables. This is the "star" shape.

### Snowflake Schema
Dimensions are normalised into sub-dimensions:
```
DimProduct ──► DimCategory ──► DimDepartment
```

> **Exam Tip:** Star schema is **always preferred over snowflake** for analytical performance in Fabric. Snowflake schemas add joins, which increases query complexity and reduces performance. The exam often asks to choose between them — choose star.

## Fact Tables

### Characteristics
- One row per **business event or measurement** (sale, click, transaction)
- Contains **foreign keys** to all related dimensions
- Contains **measures** (numeric values to be aggregated: amount, quantity, duration)
- **High row count** — potentially billions of rows
- Minimal descriptive text (that belongs in dimensions)

### Types of Facts
| Type | Description | Example |
|---|---|---|
| **Transactional** | One row per event | Individual sales |
| **Periodic snapshot** | State at regular intervals | Account balance at month-end |
| **Accumulating snapshot** | One row per process instance, updated as it progresses | Order lifecycle (created, shipped, delivered dates) |

## Dimension Tables

### Characteristics
- Relatively **few rows** compared to fact tables
- **Wide** — many descriptive columns
- Contains **surrogate key** (auto-generated integer, not the source system's natural key)
- Contains **natural key** (the source system's original identifier, retained for traceability)

### Why Surrogate Keys?
- Natural keys may change in source systems (e.g., product code reused after deletion)
- Enables SCD Type 2 (multiple rows for same natural key, different time periods)
- Faster joins (integer vs string/composite key)
- Decouples warehouse from source system schema changes

### Dimension Table Structure
```sql
CREATE TABLE dbo.DimCustomer (
    CustomerKey     INT         NOT NULL,   -- Surrogate key (warehouse-generated)
    CustomerID      INT         NOT NULL,   -- Natural key (from source system)
    CustomerName    NVARCHAR(100),
    Email           NVARCHAR(200),
    City            NVARCHAR(100),
    Country         NVARCHAR(100),
    -- SCD Type 2 columns:
    ValidFrom       DATE        NOT NULL,
    ValidTo         DATE        NOT NULL,   -- '9999-12-31' for current row
    IsCurrent       BIT         NOT NULL    -- 1 for current, 0 for historical
);
```

## The Date Dimension

The date dimension is the most universal dimension — almost every fact table has a date. Always create it as a **pre-populated physical table**, not a calculated dimension.

```sql
CREATE TABLE dbo.DimDate (
    DateKey         INT         NOT NULL,   -- YYYYMMDD integer (e.g., 20240115)
    FullDate        DATE        NOT NULL,
    DayOfWeek       TINYINT     NOT NULL,
    DayName         VARCHAR(10) NOT NULL,
    DayOfMonth      TINYINT     NOT NULL,
    WeekOfYear      TINYINT     NOT NULL,
    MonthNumber     TINYINT     NOT NULL,
    MonthName       VARCHAR(10) NOT NULL,
    Quarter         TINYINT     NOT NULL,
    Year            SMALLINT    NOT NULL,
    IsWeekend       BIT         NOT NULL,
    IsHoliday       BIT         NOT NULL,
    FiscalYear      SMALLINT    NOT NULL,
    FiscalQuarter   TINYINT     NOT NULL
);
```

> **Exam Tip:** Always use a **DateKey (integer)** as the foreign key between fact and date dimension — not a DATE type column. Integer joins are faster than date type joins. The date dimension's primary key is the integer DateKey (e.g., 20240115).

## Slowly Changing Dimensions (SCD)

### SCD Type 1 — Overwrite
Update in place. No history preserved.
```sql
UPDATE dbo.DimCustomer
SET City = 'Chicago', Country = 'USA'
WHERE CustomerID = 1001 AND IsCurrent = 1;
```

### SCD Type 2 — Add History Row
Expire old row and insert new version:
```sql
-- Expire current row
UPDATE dbo.DimCustomer
SET ValidTo = CAST(GETUTCDATE() AS DATE), IsCurrent = 0
WHERE CustomerID = 1001 AND IsCurrent = 1;

-- Insert new version
INSERT INTO dbo.DimCustomer
    (CustomerKey, CustomerID, CustomerName, City, Country, ValidFrom, ValidTo, IsCurrent)
VALUES
    (NEXT VALUE FOR CustomerKeySequence, 1001, 'Alice Smith', 'Chicago', 'USA', CAST(GETUTCDATE() AS DATE), '9999-12-31', 1);
```

### SCD Type 3 — Previous Value Column
Add a column for the previous value only — preserves only one level of history:
```sql
ALTER TABLE dbo.DimCustomer ADD PreviousCity VARCHAR(100);

UPDATE dbo.DimCustomer
SET PreviousCity = City, City = 'Chicago'
WHERE CustomerID = 1001;
```

> **Exam Tip:** SCD Type 2 is the most commonly examined type. The exam may describe a scenario and ask which SCD type applies — "preserve full history of customer address changes" → Type 2. "Keep only current value" → Type 1. "Keep only one previous value" → Type 3.

## Factless Fact Tables

A fact table with no numeric measures — just dimension keys. Used to record events or coverage:
- **Event recording**: "Student attended course" (StudentKey, CourseKey, DateKey — no numeric measure)
- **Coverage**: "This product is available in this store on this date" (enables "which products had no sales today?" queries)

---

## Junk Dimensions

Low-cardinality flags and indicators that don't belong in their own dimension are combined into a single **junk dimension**:
- OrderType (Retail/Wholesale/Online)
- IsGift (Yes/No)
- IsReturn (Yes/No)
- PaymentMethod (Cash/Card/Invoice)

Rather than storing these in the fact table (causing fan-out with future additions), combine into DimTransactionType.

---

## Degenerate Dimensions

A **degenerate dimension** is a dimension key stored directly in the fact table with no corresponding dimension table:
- Order number, invoice number, transaction ID
- Contains no descriptive attributes — it's just an identifier

Since there's nothing to look up, no dimension table is needed. The key is stored directly in the fact table.

## Modelling for Power BI

When the Warehouse feeds Power BI:
- Power BI creates a **semantic model** on top of the Warehouse
- Relationships in Power BI are defined on the semantic model, not in the Warehouse
- **Star schema in the warehouse → star schema in the semantic model** — avoids complex DAX and slow queries
- Avoid many-to-many relationships where possible; use bridge tables instead

## Common Exam Traps

**"Snowflake schema performs better than star schema"** — False. Star schema performs better because it has fewer joins. Snowflake reduces storage at the cost of query performance.

**"Natural keys should be the primary key in dimension tables"** — False for SCD Type 2. Surrogate keys are used so that multiple versions of the same entity can coexist with unique keys.

**"Fact tables should contain descriptive attributes"** — False. Descriptive data belongs in dimensions. Storing it in facts violates dimensional modelling principles and causes update anomalies.

**"SCD Type 2 requires deleting old rows"** — False. Old rows are **kept** and marked with `IsCurrent = 0` and `ValidTo` date. Deleting them removes the history you're trying to preserve.

**"A date column in the fact table is sufficient — no date dimension needed"** — Not for analytical workloads. Without a date dimension, you can't filter by fiscal year, quarter, weekend/holiday, or other calendar attributes without complex DATEPART calculations on every query.
