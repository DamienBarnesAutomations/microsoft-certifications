# Loading Data into a Fabric Data Warehouse

This module focuses on the mechanics of getting data into a Fabric Warehouse — loading strategies, COPY INTO, staging patterns, and incremental load techniques.

---

## Load Approaches

| Approach | Tool | Best For |
|---|---|---|
| **COPY INTO** | T-SQL | Large bulk loads from Azure Storage (Parquet, CSV, ORC) |
| **Pipeline Copy Data** | Pipeline activity | Any supported source → Warehouse table |
| **Dataflow Gen2** | Power Query Online | Low-code ETL into Warehouse |
| **INSERT...SELECT** | T-SQL | Load from another table/view (cross-database) |
| **CTAS** | T-SQL | Create + populate table in one step |
| **Spark** | Spark notebook | Write DataFrame to Warehouse via JDBC or OneLake |

---

## COPY INTO — Bulk Load

The primary high-performance ingestion method for Fabric Warehouse:

```sql
COPY INTO dbo.FactSales
FROM 'https://mystorageaccount.blob.core.windows.net/container/sales/2024/*.parquet'
WITH (
    FILE_TYPE = 'PARQUET',
    CREDENTIAL = (IDENTITY = 'Managed Identity')
);
```

### Supported File Types
- **PARQUET** — preferred; best performance
- **CSV** — with optional delimiter, row terminator, quoting
- **ORC** — columnar format

### Authentication Options
- **Managed Identity** — recommended; no secrets required
- **SAS token** — `CREDENTIAL = (IDENTITY = 'Shared Access Signature', SECRET = 'sas_token')`
- **Storage account key** — `CREDENTIAL = (IDENTITY = 'Storage Account Key', SECRET = 'key')`

### CSV Options
```sql
COPY INTO dbo.StagingOrders
FROM 'https://storage.blob.core.windows.net/raw/orders.csv'
WITH (
    FILE_TYPE = 'CSV',
    FIELDTERMINATOR = ',',
    ROWTERMINATOR = '\n',
    FIRSTROW = 2,           -- Skip header row
    ENCODING = 'UTF8'
);
```

> **Exam Tip:** COPY INTO is **not transactional in the traditional sense** — partial loads can occur if the file load fails mid-way. Use staging tables + MERGE/INSERT pattern for idempotent, resumable loads.

## Staging Table Pattern

Load raw data into a staging table first, then merge into the target:

```sql
-- Step 1: Load raw data into staging (truncate first for idempotency)
TRUNCATE TABLE dbo.Staging_Sales;

COPY INTO dbo.Staging_Sales
FROM 'https://storage.blob.core.windows.net/raw/sales_*.parquet'
WITH (FILE_TYPE = 'PARQUET', CREDENTIAL = (IDENTITY = 'Managed Identity'));

-- Step 2: Merge from staging into fact table
MERGE INTO dbo.FactSales AS target
USING dbo.Staging_Sales AS source
ON target.SaleID = source.SaleID

WHEN MATCHED THEN UPDATE SET
    target.Amount = source.Amount,
    target.Quantity = source.Quantity

WHEN NOT MATCHED THEN INSERT (SaleID, ProductID, CustomerID, SaleDate, Amount, Quantity)
    VALUES (source.SaleID, source.ProductID, source.CustomerID, source.SaleDate, source.Amount, source.Quantity);
```

The staging pattern makes the load **idempotent**: truncate and reload staging, then merge — re-running produces the same result.

## CTAS (Create Table As Select)

Useful for creating derived or aggregated tables in one step:

```sql
CREATE TABLE dbo.MonthlyRevenue
AS
SELECT
    YEAR(SaleDate) AS SaleYear,
    MONTH(SaleDate) AS SaleMonth,
    ProductID,
    SUM(Amount) AS TotalRevenue,
    COUNT(*) AS TransactionCount
FROM dbo.FactSales
GROUP BY YEAR(SaleDate), MONTH(SaleDate), ProductID;
```

> **Exam Tip:** CTAS creates a **new table** — it cannot be used to update or replace an existing table. To refresh a CTAS-derived table: `DROP TABLE dbo.MonthlyRevenue; CREATE TABLE dbo.MonthlyRevenue AS SELECT ...`

## Incremental Load Patterns

### Watermark-Based Incremental Load

```sql
-- Get last loaded timestamp from control table
DECLARE @LastLoad DATETIME2;
SELECT @LastLoad = LastLoadTime FROM dbo.IngestionControl WHERE TableName = 'FactSales';

-- Load only new/modified records
INSERT INTO dbo.FactSales (SaleID, ProductID, CustomerID, SaleDate, Amount)
SELECT SaleID, ProductID, CustomerID, SaleDate, Amount
FROM dbo.Staging_Sales
WHERE ModifiedAt > @LastLoad;

-- Update control table
UPDATE dbo.IngestionControl
SET LastLoadTime = GETUTCDATE()
WHERE TableName = 'FactSales';
```

### Partition-Based Load
Load data by partition (date, region) — process one partition at a time:
1. DELETE rows for the target partition: `DELETE FROM dbo.FactSales WHERE YEAR(SaleDate) = 2024 AND MONTH(SaleDate) = 1`
2. INSERT the refreshed data for that partition

## MERGE in T-SQL (Warehouse)

```sql
MERGE INTO dbo.DimCustomer AS target
USING (
    SELECT CustomerID, Name, Email, City
    FROM dbo.Staging_Customers
) AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED AND (target.Name <> source.Name OR target.Email <> source.Email) THEN
    UPDATE SET target.Name = source.Name, target.Email = source.Email, target.LastModified = GETUTCDATE()

WHEN NOT MATCHED BY TARGET THEN
    INSERT (CustomerID, Name, Email, City, LastModified)
    VALUES (source.CustomerID, source.Name, source.Email, source.City, GETUTCDATE())

WHEN NOT MATCHED BY SOURCE THEN
    UPDATE SET target.IsActive = 0;  -- Soft delete records not in source
```

`WHEN NOT MATCHED BY SOURCE` handles records that exist in the target but not in the source (soft delete or mark as inactive).

## Loading Dimension Tables (Slowly Changing Dimensions)

### SCD Type 1 (Overwrite)
Simplest — just MERGE and overwrite changed values. No history.

### SCD Type 2 (History)
Add rows with date ranges instead of overwriting:

```sql
-- Expire old record
UPDATE dbo.DimCustomer
SET ValidTo = CAST(GETUTCDATE() AS DATE), IsCurrent = 0
WHERE CustomerID = @CustomerID AND IsCurrent = 1;

-- Insert new version
INSERT INTO dbo.DimCustomer (CustomerID, Name, Email, ValidFrom, ValidTo, IsCurrent)
VALUES (@CustomerID, @NewName, @NewEmail, CAST(GETUTCDATE() AS DATE), '9999-12-31', 1);
```

## Loading Fact Tables

Best practice for fact table loads:
1. Load into **staging** with COPY INTO
2. Validate data quality (null key columns, referential integrity)
3. **Reject bad rows** to an error table
4. Insert valid rows from staging into fact table
5. Log load metadata (rows loaded, start/end time, errors)

```sql
-- Insert valid rows only (where dimension keys exist)
INSERT INTO dbo.FactSales
SELECT s.SaleID, s.ProductID, s.CustomerID, s.SaleDate, s.Amount, s.Quantity
FROM dbo.Staging_Sales s
WHERE EXISTS (SELECT 1 FROM dbo.DimProduct p WHERE p.ProductID = s.ProductID)
  AND EXISTS (SELECT 1 FROM dbo.DimCustomer c WHERE c.CustomerID = s.CustomerID);
```

## Common Exam Traps

**"COPY INTO and INSERT INTO are equivalent for bulk loading"** — No. COPY INTO is a highly optimised bulk load that reads directly from storage in parallel. INSERT INTO processes row by row or in smaller batches. COPY INTO is orders of magnitude faster for large files.

**"CTAS updates an existing table"** — False. CTAS creates a new table. If a table with that name already exists, it will error (unless you DROP it first).

**"MERGE handles all scenarios automatically"** — Only if you write all three clauses. MERGE without `WHEN NOT MATCHED BY SOURCE` will never delete target rows that disappear from the source.

**"Staging tables are optional"** — Technically yes, but they're essential for idempotency, error handling, and data quality validation. Loading directly into production tables without a staging layer is risky.
