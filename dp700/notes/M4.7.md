# Optimising a Fabric Data Warehouse

Query performance in a Fabric Warehouse depends on statistics quality, query design, schema choices, and appropriate use of materialisation. This module covers the levers available for tuning.

---

## Statistics

The query optimiser in Fabric Warehouse uses **column statistics** to estimate row counts and choose the most efficient execution plan. Poor or stale statistics lead to bad plan choices.

### Auto-Created Statistics
Fabric Warehouse automatically creates statistics when a query references a column that has no statistics. This is transparent but can cause a one-time delay on the first query against a new column.

### Manual Statistics Management
```sql
-- Create statistics on a specific column
CREATE STATISTICS stats_CustomerID ON dbo.FactSales (CustomerID);

-- Update statistics (refresh after major data changes)
UPDATE STATISTICS dbo.FactSales;
UPDATE STATISTICS dbo.FactSales (CustomerID);  -- Specific column

-- View existing statistics
DBCC SHOW_STATISTICS('dbo.FactSales', 'stats_CustomerID');
```

### When to Update Statistics Manually
- After a bulk load adds a large percentage of new rows
- After deleting a large portion of the table
- When query performance degrades unexpectedly

> **Exam Tip:** Statistics become **stale** when data distribution changes significantly. The optimiser may continue using old stats from before a load. If a query suddenly performs worse after a large load, `UPDATE STATISTICS` is the first fix to try.

## Query Design for Performance

### Avoid SELECT *
```sql
-- Bad: reads all columns from storage
SELECT * FROM dbo.FactSales WHERE SaleDate = '2024-01-01';

-- Good: reads only required columns (columnar storage — unneeded columns are skipped)
SELECT SaleID, ProductID, Amount FROM dbo.FactSales WHERE SaleDate = '2024-01-01';
```

Since Fabric Warehouse stores data in **columnar Parquet format**, selecting fewer columns means fewer file reads — a direct performance improvement.

### Avoid Functions on Filtered Columns
```sql
-- Bad: function prevents column statistics from being used effectively
SELECT * FROM dbo.FactSales WHERE YEAR(SaleDate) = 2024;

-- Good: direct range filter — stats apply
SELECT * FROM dbo.FactSales WHERE SaleDate >= '2024-01-01' AND SaleDate < '2025-01-01';
```

Wrapping a column in a function means the optimiser can't use column-level statistics for that predicate.

### Materialise Expensive Aggregations with CTAS
If a complex aggregation is used repeatedly:
```sql
-- Run once: materialise the result
CREATE TABLE dbo.ProductMonthlyRevenue
AS
SELECT
    ProductID,
    YEAR(SaleDate) AS SaleYear,
    MONTH(SaleDate) AS SaleMonth,
    SUM(Amount) AS TotalRevenue
FROM dbo.FactSales
GROUP BY ProductID, YEAR(SaleDate), MONTH(SaleDate);

-- Downstream queries are fast
SELECT * FROM dbo.ProductMonthlyRevenue WHERE SaleYear = 2024;
```

## Result Set Caching

Fabric Warehouse automatically **caches query result sets**. If the exact same query is executed again and the underlying data hasn't changed, the cached result is returned instantly — no storage reads required.

> **Exam Tip:** Result set caching is **automatic and transparent** — you don't enable or configure it. It applies only when the **exact same query** (same SQL text, same parameters) is run against **unchanged underlying data**. If the data changes, the cache is invalidated. This is ideal for frequently-run reports with slowly-changing data.

## Workload Management and Concurrency

Fabric Warehouse uses **Capacity Units (CUs)** for billing and resource allocation. When multiple users run queries simultaneously:

- CU consumption adds up across all concurrent queries
- If total consumption exceeds purchased capacity, **throttling** occurs
- Throttled requests either queue or fail with a resource exhaustion error

### Reducing Concurrency Impact
- Schedule heavy ETL jobs during off-peak hours (lower concurrent user load)
- Use pre-materialised tables/views instead of having multiple users run the same expensive query
- Monitor via Capacity Metrics app to identify peak CU hours

## Partitioning (Limited in Fabric Warehouse)

Traditional table partitioning (range partitioning by date) has limited support compared to SQL Server. However, you can simulate partition-like behaviour for load management:

```sql
-- Pattern: partition by date in the load process
-- Delete and reload only the current partition (one month)
DELETE FROM dbo.FactSales WHERE SaleYear = 2024 AND SaleMonth = 1;
INSERT INTO dbo.FactSales
SELECT * FROM dbo.Staging_Sales WHERE SaleYear = 2024 AND SaleMonth = 1;
```

This avoids full-table reloads by scoping delete+insert to a date range.

## Optimising JOIN Performance

### Use Surrogate Keys for Joins
Integer surrogate keys join faster than string or composite natural keys. Always join fact to dimension on the integer surrogate key.

### Filter Before Joining
```sql
-- Good: filter first, then join (smaller dataset being joined)
WITH RecentSales AS (
    SELECT * FROM dbo.FactSales WHERE SaleDate >= '2024-01-01'
)
SELECT r.SaleID, c.CustomerName, r.Amount
FROM RecentSales r
JOIN dbo.DimCustomer c ON r.CustomerKey = c.CustomerKey;
```

### Avoid Cartesian Products
Ensure every JOIN has appropriate ON conditions. A missing ON clause in a multi-table join creates a Cartesian product — query returns rows * rows * rows.

## Distributed Query Execution

Fabric Warehouse is a **distributed MPP (Massively Parallel Processing)** system. Queries are broken into parallel operations executed across compute nodes. Actions that help the distributed engine:

- **Columnar reads**: SELECT only needed columns
- **Predicate pushdown**: place WHERE conditions early to filter at storage level
- **Statistics accuracy**: accurate stats → better parallel distribution of work

## Identifying Slow Queries to Optimise

Use Query Insights to find targets:
```sql
-- Top 10 slowest queries by median time
SELECT TOP 10 last_run_command, median_total_elapsed_time_ms, number_of_runs
FROM queryinsights.long_running_queries
ORDER BY median_total_elapsed_time_ms DESC;
```

Then analyse:
1. Is SELECT * being used? → Replace with specific columns
2. Are there function calls on filtered columns? → Rewrite as range filters
3. Are statistics up to date? → Run UPDATE STATISTICS
4. Is the same aggregation repeated frequently? → CTAS to materialise it

## Common Exam Traps

**"Result set caching requires configuration"** — False. It is automatic and transparent.

**"SELECT * has no performance impact in columnar storage"** — False. Columnar storage skips unread columns, so `SELECT *` forces reading all columns from storage — a significant overhead for wide tables.

**"Statistics are always kept current automatically"** — Auto-created, but not auto-updated after data changes. You must run `UPDATE STATISTICS` after large data changes.

**"Fabric Warehouse uses traditional SQL Server indexes for performance"** — False. No B-tree indexes. Performance relies on statistics, columnar storage, result set caching, and query design.

**"Throttling means queries fail permanently"** — No. Throttled queries may queue and eventually execute, or may fail with a timeout error. Throttling indicates purchased capacity is insufficient for current workload — either optimise queries, reduce concurrency, or upgrade capacity.
