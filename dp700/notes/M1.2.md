# Data Pipelines in Microsoft Fabric

A **Data Pipeline** in Microsoft Fabric is an orchestration tool built on the same engine as Azure Data Factory. It defines a sequence of **activities** that execute in order, with support for branching, looping, parameters, and scheduling. Pipelines do not process data themselves — they coordinate tools that do.

---

## Core Concepts

### Activities
Every step in a pipeline is an **activity**. Activities fall into two categories:

**Data transformation activities** — actually move or process data:
- **Copy Data** — moves data from source to destination with no transformation
- **Dataflow** — runs a Dataflows Gen2 job
- **Notebook** — executes a Spark notebook
- **Stored Procedure** — runs a SQL stored procedure
- **Delete Data** — removes data from a destination
- **Script** — runs arbitrary SQL

**Control flow activities** — manage execution logic:
- **If Condition** — branches based on a boolean expression
- **ForEach** — iterates over a collection
- **Until** — loops until a condition is true
- **Set Variable / Append Variable** — manage pipeline-scoped variables
- **Wait** — pauses execution for a specified duration
- **Fail** — explicitly fails the pipeline with a custom message

### Parameters
Pipelines can be **parameterized** — values passed at runtime rather than hardcoded. Parameters make pipelines reusable across environments (dev/test/prod) or dynamic based on trigger context (e.g., date ranges).

### Pipeline Runs
Each execution is a **pipeline run** with a unique run ID. Runs can be triggered:
- **Manually** (on-demand from the UI)
- **Scheduled** (time-based)
- **Event-based** (storage event triggers, not yet universally available in all Fabric regions)

Run history is accessible from the pipeline canvas or workspace monitor view.

## Copy Data Activity

The most common single-activity pipeline pattern. Copies data from a **source connector** to a **destination** without transformation.

**When to use Copy Data:**
- You want raw data in your lakehouse/warehouse without applying any logic
- The source is external (REST API, SFTP, on-premises SQL, etc.)
- You plan to transform *after* loading (ELT pattern)

**When NOT to use Copy Data:**
- You need to merge data from multiple sources
- You need to apply transformations during ingestion → use **Dataflow activity** instead

**Supported OneLake destinations:** Lakehouse (Files or Tables), Warehouse, SQL Database

> **Exam Tip:** Copy Data does **not** transform data. If the question involves any field mapping, filtering, or type conversion happening during the copy — that's a Dataflow, not a Copy Data activity.

---

## Activity Outcome Routing

Each activity has three outcome paths:
- **On Success** → next step runs if activity succeeded
- **On Failure** → alternative step (e.g., alert, cleanup)
- **On Completion** → runs regardless of success or failure

Chaining activities using these conditions allows sophisticated error handling without external logic.

---

## Pipeline Templates

Fabric ships pre-built **pipeline templates** for common scenarios (e.g., full load from SQL to lakehouse, incremental load patterns). Templates are a starting point — you customize them after selection. They don't lock you in to any particular structure.

---

## Validation and Monitoring

- **Validate** button checks pipeline configuration before running — catches missing connections, invalid expressions, misconfigured activities
- Pipeline monitor view shows run status, duration per activity, input/output, and error messages
- Individual activity runs can be **re-run** from a failed point without re-running the entire pipeline

---

## Pipelines vs Dataflows Gen2

| | Data Pipeline | Dataflows Gen2 |
|---|---|---|
| Primary purpose | Orchestration | Transformation + Load |
| Transforms data | Only via embedded Dataflow or Notebook activities | Yes — natively |
| Low-code | Yes (visual designer) | Yes (Power Query) |
| Scheduling | Yes | Yes |
| Can call the other | Pipeline can call a Dataflow | Dataflow cannot call a Pipeline |
| Retry policies | Yes | No |
| Parameterization | Yes | Limited |

## Common Exam Traps

**"A pipeline transforms data"** — Pipelines orchestrate; they delegate transformation to Dataflow, Notebook, or Stored Procedure activities. The pipeline itself is a coordinator.

**"Copy Data activity applies transformations during the copy"** — False. It copies as-is. Use Dataflow activity for transformation during load.

**"Pipelines require Fabric capacity"** — Yes. Like all Fabric items, pipelines require a Fabric capacity workspace.

**"You can run a pipeline from within a Dataflow"** — False. The dependency only goes one way: Pipelines can invoke Dataflows, not vice versa.

**"Activity failure always stops the pipeline"** — Not necessarily. If you configure an **On Failure** path, the pipeline continues on that branch. A pipeline only truly fails if no failure path is configured and an activity fails.
