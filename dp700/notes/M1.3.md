# Apache Spark in Microsoft Fabric

Apache Spark is the distributed processing engine underlying Microsoft Fabric's data engineering and data science workloads. In Fabric, Spark runs inside **lakehouses** and operates on data stored in **OneLake**.

---

## Spark Architecture in Fabric

### Cluster Structure
- **Head node**: hosts the **driver program** — coordinates the job, maintains the SparkContext, manages task distribution
- **Worker nodes**: host **executor processes** — perform actual computation on data partitions

Spark uses a "divide and conquer" approach: data is split into **partitions** distributed across worker nodes, processed in parallel, then results are collected.

### Spark Pools in Fabric
Fabric provides a **Starter Pool** in every workspace — pre-warmed nodes that start jobs quickly without provisioning delay.

**Custom Spark pools** can be created with specific node types and sizes. Key configuration options:
- **Node Family**: type of VM. **Memory Optimized** is recommended for most analytics workloads
- **Autoscale**: automatically adds/removes nodes based on load. Configure min/max node counts
- **Dynamic Allocation**: distributes executor processes across nodes based on data volume at runtime

> **Exam Tip:** Fabric admins can **disable the ability to customize Spark pool settings** at the capacity level. If a workspace admin can't change Spark settings, check capacity-level admin restrictions first.

Setting location: **Admin portal → Capacity settings → Data Engineering/Science Settings**

## Runtimes and Environments

### Runtimes
A **runtime** defines the versions of: Apache Spark, Delta Lake, Python, R, and Scala. Fabric supports multiple runtime versions simultaneously. The default runtime is set in workspace settings.

### Environments
An **Environment** is a workspace item that packages:
- A specific Spark runtime version
- Built-in libraries (always present)
- Additional libraries from **PyPI** (Python Package Index)
- Custom libraries (uploaded .whl or .jar files)
- Spark configuration property overrides
- Resource files

Multiple environments per workspace allows different workloads (e.g., ML vs. ETL) to use different library sets without conflict.

> **Exam Tip:** Environments are attached to a **specific Spark pool**. If a question asks how to ensure a notebook uses a specific Python library version, the answer is to create and attach a custom **Environment**, not to install the library in the notebook cell.

## Advanced Spark Configuration Options

### Native Execution Engine
A **vectorized processing engine** that runs Spark operations directly on lakehouse infrastructure, bypassing the standard JVM-based execution path. Delivers significant performance gains on **Parquet and Delta** files with large datasets.

Enable at the environment level by setting:
```
spark.native.enabled = true
spark.shuffle.manager = org.apache.spark.shuffle.sort.ColumnarShuffleManager
```
Or enable per-notebook:
```json
%%configure
{
  "conf": {
    "spark.native.enabled": "true",
    "spark.shuffle.manager": "org.apache.spark.shuffle.sort.ColumnarShuffleManager"
  }
}
```

### High Concurrency Mode
Allows **multiple users or notebooks to share a single Spark session**, reducing startup overhead. Key behaviours:
- Variable isolation is maintained between notebooks sharing a session
- Reduces the cost of spinning up new sessions for each user
- Can be enabled for both notebooks and Spark Job Definitions
- Configured in **Data Engineering/Science workspace settings**

### Automatic MLflow Logging
Fabric **implicitly logs ML experiment activity** via MLflow without requiring explicit logging code. Can be disabled in workspace settings if not needed.

## DataFrames — Core API

The primary data structure in Spark SQL. Similar to Pandas DataFrames but **distributed** across the cluster.

### Reading Data
```python
# Infer schema from CSV header row
df = spark.read.load('Files/data/products.csv', format='csv', header=True)

# Explicit schema — better performance, required when no header exists
from pyspark.sql.types import *
schema = StructType([
    StructField("ProductID", IntegerType()),
    StructField("ProductName", StringType()),
    StructField("ListPrice", FloatType())
])
df = spark.read.load('Files/data/products.csv', format='csv', schema=schema, header=False)
```

> **Exam Tip:** Specifying an **explicit schema** improves performance — Spark doesn't need to scan the data to infer types. On large datasets, schema inference is expensive.

### Common Transformations
```python
# Filter
df.where(df["Category"] == "Mountain Bikes")

# Select columns
df.select("ProductID", "ListPrice")

# Group and aggregate
df.groupBy("Category").count()

# Chain operations
df.select("ProductName", "Category", "ListPrice").where(df["Category"] == "Road Bikes")
```

### Saving DataFrames
```python
# Parquet — preferred format for analytical stores
df.write.mode("overwrite").parquet("Files/product_data/bikes.parquet")

# Partitioned output — improves query performance on large datasets
df.write.partitionBy("Category").mode("overwrite").parquet("Files/bike_data")
# Creates: Files/bike_data/Category=Mountain Bikes/ and Files/bike_data/Category=Road Bikes/
```

> **Exam Tip:** When reading a **partitioned folder**, the partition column is **omitted from the resulting DataFrame**. If you read `Files/bike_data/Category=Road Bikes`, there is no `Category` column in the output — the value is implied by the path.

## Spark SQL and the Spark Catalog

The **Spark Catalog** is a metastore for tables and views. It integrates with Fabric's lakehouse table storage.

### Temporary Views
```python
df.createOrReplaceTempView("products_view")
# View exists only for the current Spark session
```

### Managed Tables
```python
df.write.format("delta").saveAsTable("products")
# Data stored in the lakehouse Tables/ path
# Deleting the table ALSO deletes the data
```

### External Tables
```python
spark.catalog.createExternalTable("products_ext", path="Files/product_data/", source="parquet")
# Metadata in catalog, data stays in Files/
# Deleting the table does NOT delete the underlying data
```

> **Exam Tip:** **Managed vs External** is a classic exam distinction:
> - **Managed**: drop the table → data is deleted
> - **External**: drop the table → data stays
> Use External tables when the data lifecycle is managed independently of the catalog.

### Querying with SQL Magic
```sql
%%sql
SELECT Category, COUNT(ProductID) AS ProductCount
FROM products
GROUP BY Category
```

## Common Exam Traps

**"Spark DataFrames are the same as Pandas DataFrames"** — Similar API, but Spark DataFrames are distributed across a cluster. Pandas operates on a single machine. Converting a Spark DF to Pandas (`.toPandas()`) brings all data to the driver node — dangerous on large datasets.

**"The starter pool needs configuration before use"** — False. It's pre-warmed and ready to use immediately. Custom pools require more setup.

**"High Concurrency mode shares variables between notebooks"** — False. Variables are **isolated** even when sharing a session. That's the whole point — shared resources, isolated execution.

**"External tables are safer to drop"** — Depends on intent. Dropping an external table doesn't delete the data, which can leave orphaned files. The distinction is about data lifecycle ownership.

**"Partitioning always improves performance"** — Only when queries filter on the partition column. Partition on a column with too many distinct values (high cardinality) creates too many small files and *hurts* performance (the "small files problem").
