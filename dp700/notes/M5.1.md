# CI/CD in Microsoft Fabric

## CI/CD Overview

**Core Concept**
CI/CD (Continuous Integration / Continuous Delivery) is the practice of frequently merging code from multiple developers into a shared codebase, automatically validating it, and promoting it through structured environments (Development → Test → Production) to reduce bugs and delivery time.

**Three Distinct Stages**
- **Continuous Integration (CI):** Developers frequently commit to a shared branch. Automated build and test processes validate each commit. Conflicts are caught early when they are cheaper to fix.
- **Continuous Delivery (CD):** After CI passes, code is deployed to a staging environment for further automated testing before manual release to production.
- **Continuous Deployment:** Fully automated — code that passes all tests is released to production automatically with no manual step.

**How Fabric Implements CI/CD**
| Concern | Fabric Tool |
|---|---|
| Integration / version control | Git (GitHub or Azure DevOps) |
| Deployment / environment promotion | Deployment Pipelines |
| Automation of both | Fabric REST APIs |

## Git Integration

**Core Concept**
Git integration in Fabric provides version control for Fabric items. It is configured at the **workspace level** — not item level, not tenant level.

**Technical Specifications**
- Supported providers: **GitHub** and **Azure DevOps** only.
- Integration scope: **workspace level** — all versioned items in a workspace are tracked together.
- Fabric displays a **Git status column** in the workspace after connection showing sync state per item.
- A workspace connects to a **single Git branch** at a time.

**Git Status States**
| State | Meaning |
|---|---|
| **Synced** | Workspace item and Git branch are identical |
| **Conflict** | Changes exist in both workspace and Git — must be resolved manually |
| **Uncommitted** | Workspace has changes not yet pushed to Git |
| **Update Required** | Git branch has newer commits not yet pulled into workspace |

**Branching Workflow (Isolated Development)**
Best practice: never develop directly in the shared workspace connected to `main`. Instead:
1. Connect the **shared development workspace** to the `main` branch.
2. Developer selects **Source control → Branch out to new workspace** to create a personal branch + isolated workspace.
3. Developer makes changes in isolated workspace and commits to their personal branch.
4. Developer creates a **Pull Request (PR)** in GitHub/Azure DevOps to merge into `main`.
5. After merge, the shared development workspace prompts to **sync** the updated `main`.

**Client-Tool Workflow** (VS Code, Power BI Desktop)
1. Connect shared workspace to `main`.
2. Clone the repository locally.
3. Make changes locally, push to remote when ready.
4. Connect an isolated branch to a separate workspace for testing in Fabric.
5. Create PR to merge into `main`. Sync the shared workspace after merge.

## Deployment Pipelines

**Core Concept**
Deployment pipelines automate the promotion of Fabric items across environments (typically **Development → Test → Production**) by cloning content from one workspace-assigned stage to the next.

**Technical Specifications**
- Created from two entry points: **Workspaces icon → Deployment pipelines** or the **Create deployment pipeline** button at the top of a workspace.
- Each pipeline stage is assigned one Fabric workspace.
- Deploying clones all content from the source stage workspace into the target stage workspace.
- Does **not** require Git integration to function independently.

**Setup Steps**
1. Create pipeline, name it.
2. Define and name stages (e.g., Development, Test, Production).
3. Assign a workspace to each stage.
4. Use the **Deploy** button to promote content from one stage to the next.

**Combining Git + Deployment Pipelines (Recommended Pattern)**
- Connect **only the Development workspace** to Git.
- Use Git for version control and PR-based change management in Development.
- Use Deployment Pipelines to promote from Development → Test → Production.
- **Why:** Avoids Git sync conflicts that arise from connecting multiple stage workspaces to Git simultaneously.

## REST APIs for CI/CD Automation

**Core Concept**
Fabric REST APIs allow programmatic control of Git integration and deployment pipeline operations, enabling automation in CI/CD scripts and external orchestration tools.

**Git REST APIs**
| API | Purpose |
|---|---|
| `Commit` | Push workspace changes to the connected remote branch |
| `Update` | Pull remote branch commits into the workspace |
| `Status` | List items with uncommitted or incoming changes |

**Deployment Pipeline REST APIs**
| API | Purpose |
|---|---|
| `List Pipeline Stage Items` | Returns supported items from the workspace assigned to a pipeline stage |
| `Deploy Stage Content` | Triggers deployment from one pipeline stage to the next |

## Exam Gotchas & Distinctions

- **"Git integration is configured at the item level"** — False. It is at the **workspace level**. All items in a workspace are tracked together under one branch.
- **"Fabric supports any Git provider"** — False. Only **GitHub** and **Azure DevOps** are supported.
- **"Deployment pipelines require Git"** — False. They are independent tools. Git handles version control; pipelines handle environment promotion. They are complementary but neither requires the other.
- **"Continuous deployment = continuous delivery"** — They differ: delivery requires a manual release step; deployment is fully automatic after tests pass.
- **"All Fabric items can be versioned with Git"** — False. Eventhouses, KQL databases, and Activators are commonly cited as items **not supported** by Git integration.
- **"Connecting all three stage workspaces to Git is the recommended approach"** — False. The recommended pattern connects only the **Development** workspace to Git to avoid sync conflicts across stages.
