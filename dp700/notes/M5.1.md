# Continuous Integration and Continuous Delivery (CI/CD) in Microsoft Fabric

Lifecycle management in Fabric allows data engineers to version, test, and promote Fabric items (Notebooks, Dataflows Gen2, Reports, Semantic Models, Pipelines) across multiple environments.

---

## Source Control and Git Integration

Git integration in Fabric is configured at the **workspace level**.

### Core Architecture
- **Isolated Development**: Developers should work in separate, isolated workspaces rather than a shared workspace to prevent overwriting each other's live changes.
- **Git Provider Support**: Fabric natively integrates with **Azure DevOps** and **GitHub**.
- **Sync States**: After connecting a workspace to a Git branch, Fabric displays a **Git status** column:
  - **Synced**: Item is identical in workspace and Git.
  - **Conflict**: Changes exist in both the workspace and Git. Must be resolved.
  - **Uncommitted**: Local workspace changes not yet pushed to Git.
  - **Update Required**: Newer commits exist in the Git branch that must be pulled.

### Branching Workflows
1. **Branch Out**: From a shared development workspace connected to the `main` branch, a developer can select "Branch out to new workspace" to create a new branch and a dedicated workspace.
2. **Commit Changes**: Make updates in the web interface and commit them to the personal branch.
3. **Pull Request (PR)**: Create a PR in GitHub/DevOps to merge the feature branch into the `main` branch.
4. **Sync Main**: Once merged, other developers sync the updated `main` branch into their workspaces.

## Deployment Pipelines

Deployment pipelines automate the promotion of content through staging environments (typically **Development → Test → Production**).

### Configuration Steps
1. Create a deployment pipeline from the **Workspaces** section or from a workspace itself.
2. Define and name the pipeline stages.
3. Assign a Fabric workspace to each stage.
4. Promote content by selecting **Deploy** (clones items from source workspace to target workspace).

### Combining Git and Pipelines (Recommended Workflow)
- Connect **only the Development workspace** to Git (for version control, branching, and PR approvals).
- Use **Deployment Pipelines** to handle the movement of items from Development to Test, and Test to Production workspaces.
- This hybrid pattern avoids complex Git sync conflicts across multiple staging environments.

## Automating CI/CD with Fabric REST APIs

Fabric provides REST APIs to automate procedures programmatically:
- **Git APIs**:
  - `Commit`: Commit workspace changes to the remote branch.
  - `Update`: Pull remote commits into the workspace.
  - `Status`: Check for incoming or uncommitted changes.
- **Pipeline APIs**:
  - `List Pipeline Stage Items`: Retrieve supported items in a stage's workspace.
  - `Deploy Stage Content`: Trigger a deployment to the next stage programmatically.

## Common Exam Traps

- **"Git integration works at the tenant or item level"** — False. It is configured at the **workspace level**.
- **"All Fabric items support Git integration"** — False. Eventhouses/KQL databases and Activators are common examples of unsupported items.
- **"Deployment pipelines require Git to function"** — False. Pipelines can run independently, though combining them is a best practice.
