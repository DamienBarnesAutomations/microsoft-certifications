# Advanced Delta Lake — Merge, Streaming, and Optimisation

This module covers advanced Delta Lake capabilities: the MERGE operation, unified streaming/batch, and performance optimisation techniques beyond basic OPTIMIZE and VACUUM (covered in M1.4).

---

## MERGE (Upsert)

`MERGE INTO` is Delta Lake's implementation of an **upsert** — insert new rows, update existing rows, and optionally delete rows, all in a single atomic operation. This is the most powerful and exam-tested Delta operation.

```sql
%%sql
MERGE INTO silver_customers AS target
USING (SELECT * FROM staging_customers) AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED AND source.IsDeleted = true THEN DELETE
WHEN MATCHED THEN UPDATE SET
    target.CustomerName = source.CustomerName,
    target.Email = source.Email,
    target.UpdatedAt = source.UpdatedAt
WHEN NOT MATCHED THEN INSERT (CustomerID, CustomerName, Email, CreatedAt)
    VALUES (source.CustomerID, source.CustomerName, source.Email, source.CreatedAt);
```

### PySpark MERGE
```python
from delta.tables import DeltaTable

target = DeltaTable.forName(spark, "silver_customers")

target.alias("target").merge(
    staging_df.alias("source"),
    "target.CustomerID = source.CustomerID"
).whenMatchedDelete(condition="source.IsDeleted = true") \
 .whenMatchedUpdateAll() \
 .whenNotMatchedInsertAll() \
 .execute()
```

**MERGE clauses:**
- `WHEN MATCHED` — row exists in both target and source
- `WHEN NOT MATCHED` (or `WHEN NOT MATCHED BY TARGET`) — row exists in source but not target → INSERT
- `WHEN NOT MATCHED BY SOURCE` — row exists in target but not source → useful for deletes (Delta 2.0+)

> **Exam Tip:** `WHEN NOT MATCHED BY SOURCE` is the correct way to delete rows that disappeared from the source. Without this clause, a MERGE will never delete rows that no longer appear in the source feed — a common incorrect assumption.

## Delta Lake Streaming

Delta tables support **streaming reads and writes** natively. This enables a single table to serve both batch and streaming consumers without duplication.

### Streaming Write to Delta
```python
streamDf.writeStream \
    .format("delta") \
    .outputMode("append") \
    .option("checkpointLocation", "Files/checkpoints/events") \
    .table("streaming_events")
    # or .start("Files/delta/streaming_events")
```

**Output modes:**
| Mode | Behaviour | Use with Delta |
|---|---|---|
| `append` | Only new rows written each trigger | ✅ Most common for Delta |
| `complete` | Full result set written each trigger | ✅ With aggregations |
| `update` | Only changed rows | ✅ With stateful operations |

### Checkpoint Location
The checkpoint stores the **streaming offset** — the position in the source stream up to which data has been processed. If the stream restarts, it resumes from the last checkpoint position. Without a checkpoint, the stream restarts from the beginning.

> **Exam Tip:** The checkpoint location must be **unique per streaming query**. Two streaming queries writing to different tables must use different checkpoint paths. Reusing a checkpoint from a different query corrupts state.

### Streaming Read from Delta
```python
streamDf = spark.readStream.format("delta").table("bronze_events")
# Process and write to silver
(streamDf
    .filter(col("EventType") == "click")
    .writeStream
    .format("delta")
    .option("checkpointLocation", "Files/checkpoints/silver_clicks")
    .outputMode("append")
    .table("silver_clicks")
)
```

## Change Data Feed (CDF)

Delta Lake can emit a **change feed** — a record of every INSERT, UPDATE, and DELETE applied to a table. This enables downstream consumers to process only the changes since their last read (incremental processing).

### Enable CDF
```python
# Enable at table creation
df.write.format("delta") \
    .option("delta.enableChangeDataFeed", "true") \
    .saveAsTable("silver_customers")

# Enable on existing table
spark.sql("ALTER TABLE silver_customers SET TBLPROPERTIES (delta.enableChangeDataFeed = true)")
```

### Read the Change Feed
```python
changes = spark.read.format("delta") \
    .option("readChangeFeed", "true") \
    .option("startingVersion", 5) \
    .table("silver_customers")
```

CDF rows include an additional `_change_type` column: `insert`, `update_preimage`, `update_postimage`, `delete`.

> **Exam Tip:** CDF is **not enabled by default** — it must be explicitly turned on. Enabling CDF adds a small storage overhead because change records are retained. If a question asks how to process incremental changes from a Delta table into a downstream system without scanning the full table, the answer is CDF.

## Table Properties and Configuration

Delta tables have configurable properties set via `ALTER TABLE ... SET TBLPROPERTIES`:

| Property | Purpose |
|---|---|
| `delta.enableChangeDataFeed` | Enable Change Data Feed |
| `delta.autoOptimize.optimizeWrite` | Auto-compact small files on write |
| `delta.autoOptimize.autoCompact` | Run compaction in background after write |
| `delta.dataSkippingNumIndexedCols` | Number of columns with statistics for data skipping |
| `delta.logRetentionDuration` | How long to retain transaction log entries |
| `delta.deletedFileRetentionDuration` | How long to retain old data files (used by VACUUM) |

### Auto-Optimization
```sql
ALTER TABLE silver_sales SET TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true',
    'delta.autoOptimize.autoCompact' = 'true'
);
```

When `optimizeWrite` is enabled, Spark automatically determines the optimal file size during writes and coalesces partitions. Reduces manual OPTIMIZE runs.

## Data Skipping and Statistics

Delta Lake maintains **column statistics** (min, max, null count, distinct count) for the first N columns (default: 32) in each data file. When you apply a filter, Delta uses these statistics to **skip entire files** that cannot contain matching rows — without reading them.

Z-ordering (covered in M1.4) improves data skipping by co-locating similar values in fewer files.

> **Exam Tip:** Data skipping works automatically but only for columns that have statistics collected. If a query is slow on a specific column and Z-ordering/partitioning isn't the issue, check whether that column is within the `delta.dataSkippingNumIndexedCols` limit.

## Cloning Delta Tables

Delta Lake supports two types of clones:

```sql
-- Shallow clone: copies only metadata, points to original data files
CREATE TABLE silver_backup SHALLOW CLONE silver_sales;

-- Deep clone: copies both metadata and data files
CREATE TABLE silver_backup DEEP CLONE silver_sales;
```

| | Shallow Clone | Deep Clone |
|---|---|---|
| Data copied | ❌ (metadata only) | ✅ |
| Storage cost | Low | Same as full copy |
| Independent from source | ❌ (still references original files) | ✅ |
| Use case | Testing, quick snapshots | Full isolation, backup |

> **Exam Tip:** Shallow clones reference the original data files. If the original table runs VACUUM and removes old files, the shallow clone may break. Use deep clones when you need true independence.

## Common Exam Traps

**"MERGE handles deletes automatically when source rows disappear"** — Only with `WHEN NOT MATCHED BY SOURCE THEN DELETE`. Standard MERGE never deletes unless you explicitly include that clause.

**"Streaming checkpoints can be shared between queries"** — False. Each streaming query must have a unique checkpoint location.

**"CDF is enabled by default"** — False. Must be explicitly enabled via table property.

**"Shallow clone is a full independent copy"** — False. It references the original data files. Changes to the original or VACUUM on the original can break the clone.

**"OPTIMIZE permanently archives old versions"** — No. OPTIMIZE compacts current files. Old versions are only removed by VACUUM. After OPTIMIZE, the old small files still exist as historical versions until VACUUM removes them.
