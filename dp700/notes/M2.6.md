# Orchestrating Pipelines — Advanced Patterns

> **Note:** M2.6 in the raw source files is a near-duplicate of M1.2 (both cover Data Pipelines basics). This notes file focuses on **advanced pipeline orchestration topics** beyond the fundamentals covered in M1.2 — specifically parameterisation, error handling, monitoring, and pipeline design patterns.

---

## Pipeline Parameters vs Variables

| | Parameters | Variables |
|---|---|---|
| Scope | Passed in at runtime (external) | Internal to the pipeline run |
| Mutability | Immutable during a run | Mutable via Set Variable activity |
| Set by | Trigger, manual run, parent pipeline | Set Variable / Append Variable activity |
| Use case | Make pipeline reusable across envs | Track state within a run |

### Passing Parameters to Child Pipelines
When using **Execute Pipeline** activity (calling one pipeline from another):
- Parent pipeline passes parameters to child as explicit key-value pairs
- Child pipeline must declare those parameters in its definition
- Enables composable, reusable sub-pipelines

## Pipeline Expressions

Pipeline expressions use a JSON-based expression language (same as Azure Data Factory) enclosed in `@{ }`:

```
@pipeline().parameters.SourceFolder          # Access parameter
@variables('RunDate')                         # Access variable
@utcNow()                                     # Current UTC time
@formatDateTime(utcNow(), 'yyyy-MM-dd')       # Formatted date
@concat('Files/', pipeline().parameters.FolderName, '/output')
@activity('CopyData').output.rowsCopied       # Output of previous activity
@if(equals(variables('Status'), 'success'), 'done', 'retry')
```

> **Exam Tip:** Pipeline expressions are evaluated at **runtime**, not at design time. They are strings surrounded by `@{ }` in the UI, but in activity configurations that accept expressions, the entire value is the expression (no braces needed). This distinction catches many candidates.

## Error Handling and Retry Policies

Each activity can be configured with:
- **Retry count**: number of automatic retries on failure (0–10)
- **Retry interval**: seconds between retries
- **Timeout**: maximum duration for the activity before it's killed
- **On Failure / On Success / On Completion**: branching paths

### Pattern: Notify on Failure
```
Copy Data Activity
    → [On Failure] → Office 365 Outlook Activity (send email notification)
```

### Pattern: Conditional Branching
```
Get Metadata Activity (check if file exists)
    → [On Success] → If Condition Activity
        → [True] → Copy Data Activity
        → [False] → Wait Activity (retry later)
```

## Triggers

| Trigger Type | Description |
|---|---|
| **Schedule trigger** | Runs on a defined recurrence (e.g., daily at 2:00 AM UTC) |
| **Storage event trigger** | Fires when a blob is created/deleted in Azure Storage (not always available in all Fabric regions) |
| **Manual trigger** | On-demand from UI or API |
| **Tumbling window trigger** | Time-windowed, sequential, with dependency support — used for backfilling |

> **Exam Tip:** **Tumbling window triggers** are specifically designed for **backfill** scenarios — processing historical data windows sequentially. Schedule triggers fire independently even if the previous run is still going. Tumbling window triggers are sequential and can depend on other tumbling window triggers finishing first.

## Monitoring Pipelines

### Run Monitor
Access via: workspace → Monitor tab → Pipeline runs

Shows:
- Run start/end time, duration, status
- Per-activity run details (click into each activity)
- Input/output metadata (rows copied, bytes written)
- Error messages with error codes

### Programmatic Monitoring via REST API
You can call the Fabric REST API to query pipeline run status, useful for building custom dashboards or alerting systems.

## Pipeline Design Patterns

### Pattern: Metadata-Driven Pipeline
Instead of hardcoding source/destination details, store them in a control table. The pipeline loops over the table and processes each entry dynamically.

```
ForEach Activity
    → Lookup Activity (read config for current iteration)
    → Copy Data Activity (use Lookup output for source/dest)
```

Advantages: add new data sources by adding a row to the config table — no pipeline changes.

### Pattern: Full vs Incremental Load Switch
```
If Condition Activity (check LoadType parameter)
    → [Full Load branch] → Delete Data → Copy Data (full)
    → [Incremental branch] → Lookup (last watermark) → Copy Data (filtered)
```

### Pattern: Fan-Out (Parallel Processing)
```
ForEach Activity (with isSequential = false)
    → [Each iteration runs in parallel]
    → Process each partition/date/entity simultaneously
```

> **Exam Tip:** By default, `ForEach` runs **sequentially** (`isSequential = true`). Set `isSequential = false` to enable parallel execution. Max concurrency is configurable (default: 20). Parallel ForEach is ideal when processing independent partitions.

## Pipeline vs Dataflow vs Notebook — When to Orchestrate What

| Requirement | Tool |
|---|---|
| Schedule a Dataflow | Pipeline (Schedule trigger → Dataflow activity) or Dataflow's own schedule |
| Run a Notebook on a schedule | Pipeline (Schedule trigger → Notebook activity) |
| Retry a failed step automatically | Pipeline (retry policy on activity) |
| Loop over a list of files/tables | Pipeline (ForEach activity) |
| Branch based on a condition | Pipeline (If Condition activity) |
| Pure transformation, no orchestration needed | Dataflow Gen2 or Spark Notebook standalone |

## Common Exam Traps

**"ForEach always runs in parallel"** — False. Default is sequential. You must set `isSequential = false`.

**"Pipelines can be triggered by events from a Fabric lakehouse"** — Storage event triggers work with Azure Blob/ADLS, not directly from Fabric lakehouses. Fabric OneLake doesn't natively support event triggers in the same way.

**"Pipeline retry retries the entire pipeline"** — No. Retry is configured at the **activity level** and retries only that specific activity, not the whole pipeline from the start.

**"Tumbling window and schedule triggers are interchangeable"** — No. Schedule triggers fire independently on each recurrence. Tumbling window triggers are sequential, support dependencies, and support backfill processing of historical windows.
