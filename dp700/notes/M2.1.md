# Microsoft Fabric Lakehouses

A **Lakehouse** in Microsoft Fabric is a unified data store that combines the flexibility of a data lake (unstructured/semi-structured files in cloud storage) with the structured query capabilities of a data warehouse (SQL, schema, tables). It is built on top of **OneLake** and uses **Delta Lake** as its table format.

---

## Lakehouse Structure

Every lakehouse exposes two storage areas:

| Area | Path | Purpose |
|---|---|---|
| **Tables** | `Tables/` | Managed Delta Lake tables — queryable via SQL endpoint |
| **Files** | `Files/` | Raw files in any format (CSV, Parquet, JSON, images, etc.) |

Files stored in `Tables/` are automatically registered in the lakehouse's metadata catalog. Files stored in `Files/` are accessible via Spark but are **not** automatically queryable via SQL.

> **Exam Tip:** Only data in the `Tables/` section is accessible via the **SQL Analytics Endpoint**. If you write a file to `Files/products.csv`, it cannot be queried with `SELECT * FROM products` via T-SQL until it is promoted to a Delta table.

---

## OneLake — The Underlying Storage

All Fabric data (lakehouses, warehouses, KQL databases, etc.) is stored in **OneLake** — a single, tenant-wide data lake. OneLake uses **Azure Data Lake Storage Gen2** under the hood.

Key OneLake properties:
- One OneLake per Fabric tenant (not per workspace)
- Data is organised by workspace and item: `onelake://{workspace}/{item}.Lakehouse/Tables/`
- External tools and services can access OneLake via the **OneLake API** or **Azure Storage API**
- **Shortcuts** allow referencing data in other storage locations (ADLS Gen2, S3, GCS) without copying it

---

## Shortcuts

A **Shortcut** is a pointer to data stored outside the current lakehouse — either in another Fabric item or in external storage. The data is not copied; queries are executed against the original location.

**Supported shortcut targets:**
- Another Fabric lakehouse (within the same or different workspace)
- Azure Data Lake Storage Gen2
- Amazon S3
- Google Cloud Storage
- OneLake (another workspace)

**When to use shortcuts:**
- Avoid data duplication across workspaces
- Access external cloud storage without ETL
- Share data between teams without copying

> **Exam Tip:** Shortcuts appear in the lakehouse UI like regular folders, but writes to a shortcut go to the **original location**, not the lakehouse. Deleting a shortcut does not delete the original data. Compute costs for querying a shortcut may apply at the source location.

---

## SQL Analytics Endpoint

Every lakehouse automatically provides a **read-only SQL Analytics Endpoint** — a T-SQL interface over the Delta tables in the `Tables/` section. This endpoint:
- Is **read-only** (no INSERT, UPDATE, DELETE via SQL endpoint)
- Supports standard T-SQL SELECT syntax
- Is accessible from Power BI, SSMS, and other SQL clients
- Respects the same Delta table schema as Spark

> **Exam Tip:** The SQL Analytics Endpoint is **read-only**. If a question asks how to insert data into a lakehouse table via SQL, the answer involves using a **Warehouse** (not a Lakehouse), or using Spark/Pipelines to write to the lakehouse.

## Medallion Architecture in Fabric

The recommended pattern for organising lakehouse data:

| Layer | Purpose | Typical Format |
|---|---|---|
| **Bronze** | Raw ingested data, unmodified | Delta, CSV, Parquet |
| **Silver** | Cleaned, validated, conformed data | Delta |
| **Gold** | Aggregated, business-ready data | Delta |

Implementation options:
- **Multiple lakehouses** — one per layer (better isolation, clearer ownership)
- **Single lakehouse with folders** — simpler but less isolation
- **Shortcuts** — Gold lakehouse shortcuts to Silver lakehouse tables without copying

---

## Lakehouse vs Warehouse

| | Lakehouse | Warehouse |
|---|---|---|
| Storage | OneLake (Delta) | OneLake (Parquet + Delta) |
| Primary interface | Spark + SQL Analytics Endpoint | Full T-SQL (read + write) |
| SQL writes | ❌ (endpoint is read-only) | ✅ (INSERT, UPDATE, DELETE) |
| Unstructured files | ✅ (Files section) | ❌ |
| Schema flexibility | High (schemaless files + Delta) | Lower (enforced SQL schema) |
| Use case | Data engineering, ML, flexible exploration | BI reporting, structured analytics |

**Use Lakehouse over Warehouse when:**
- You need to store raw/unstructured files alongside tables
- Your primary processing is done with Spark
- You need schema flexibility (schemaless or semi-structured data)

**Use Warehouse over Lakehouse when:**
- Your team works primarily in T-SQL
- You need full DML (INSERT, UPDATE, DELETE) via SQL
- You are building a traditional relational model for BI

## Loading Data into a Lakehouse

Multiple methods:
1. **Dataflows Gen2** → transforms and writes to `Tables/`
2. **Copy Data activity** → writes files to `Files/` or tables to `Tables/`
3. **Spark notebooks** → `df.write.format("delta").saveAsTable(...)` writes to `Tables/`
4. **Shortcuts** → references external data without copying
5. **Upload** → drag-and-drop files into `Files/` from the Fabric UI (small files only)

## Common Exam Traps

**"The SQL endpoint on a lakehouse supports writes"** — False. It is read-only. Writes must go through Spark or Pipelines.

**"Files in the Files/ section are automatically queryable via SQL"** — False. Only Delta tables in `Tables/` are available via the SQL endpoint. You must convert raw files to Delta tables first.

**"A shortcut copies data to the lakehouse"** — False. It is a pointer. No data movement occurs.

**"Deleting a shortcut deletes the source data"** — False. Shortcuts are pointers only. Deleting the shortcut removes the pointer, not the data at the source.

**"Lakehouse and Warehouse are interchangeable"** — No. The key differentiator for the exam: if you need T-SQL DML writes → Warehouse. If you need unstructured file storage or Spark processing → Lakehouse.
