# Securing a Fabric Data Warehouse

Security in a Fabric Warehouse operates at multiple levels: workspace roles (coarse-grained), item-level sharing (mid-grained), and SQL object permissions (fine-grained). Understanding which layer controls what is critical for the exam.

---

## Security Layers

```
Tenant (Entra ID)
  └── Fabric Capacity
        └── Workspace (Workspace Roles)
              └── Warehouse Item (Item Sharing / Permissions)
                    └── SQL Objects (GRANT / DENY on tables, views, schemas)
```

---

## Workspace Roles

| Role | Warehouse Access |
|---|---|
| **Admin** | Full control — manage workspace, items, permissions |
| **Member** | Create, edit, delete warehouse items; can share and manage permissions |
| **Contributor** | Create, edit, delete items; **cannot** manage permissions or share |
| **Viewer** | Read-only — can query warehouse via SQL endpoint; cannot modify |

> **Exam Tip:** A **Viewer** can read all tables in a warehouse via the SQL endpoint. If you need to restrict Viewers to only specific tables, you cannot use workspace roles — you must use SQL object permissions (GRANT/DENY) or share the warehouse item with specific permissions.

---

## Item-Level Sharing

Sharing a warehouse item grants access to a specific user without adding them to the workspace. When sharing, you can grant:

| Permission | Description |
|---|---|
| **Read** (default) | Connect to the warehouse SQL endpoint, run SELECT on all tables |
| **ReadData** | Same as Read — query tables via SQL |
| **ReadAll** | Read access including OneLake file access (Parquet files directly) |
| **Build** | Create Power BI reports from the warehouse data |

> **Exam Tip:** Sharing a warehouse with **Read** permission gives read access to **all tables** in the warehouse. To restrict to specific tables, use SQL GRANT/DENY **after** sharing, or expose only a view and grant access to the view, not the underlying tables.

---

## SQL Object-Level Permissions

Fine-grained control using standard SQL DCL statements:

```sql
-- Grant SELECT on a specific table
GRANT SELECT ON dbo.FactSales TO [user@company.com];

-- Grant SELECT on a specific schema (all current and future tables)
GRANT SELECT ON SCHEMA::dbo TO [analyst@company.com];

-- Deny SELECT on sensitive table
DENY SELECT ON dbo.EmployeeSalaries TO [analyst@company.com];

-- Grant EXECUTE on a stored procedure
GRANT EXECUTE ON dbo.usp_RefreshDimProduct TO [etlservice@company.com];

-- Revoke a previously granted permission
REVOKE SELECT ON dbo.FactSales FROM [user@company.com];
```

**DENY takes precedence over GRANT** — if a user is both granted and denied a permission (e.g., through a role), the DENY wins.

### Using Roles for Permission Management
```sql
-- Create a role
CREATE ROLE ReportingAnalysts;

-- Grant the role access
GRANT SELECT ON SCHEMA::dbo TO ReportingAnalysts;
DENY SELECT ON dbo.SensitiveData TO ReportingAnalysts;

-- Add users to the role
ALTER ROLE ReportingAnalysts ADD MEMBER [alice@company.com];
ALTER ROLE ReportingAnalysts ADD MEMBER [bob@company.com];
```

## Column-Level Security

Restrict access to specific columns by not including them in a view or by using DENY on a column:

```sql
-- DENY SELECT on a specific column
DENY SELECT ON dbo.DimEmployee (Salary, SSN) TO [analyst@company.com];
```

Or create a view that excludes sensitive columns and grant access to the view only:
```sql
CREATE VIEW dbo.vw_EmployeePublic AS
SELECT EmployeeID, Name, Department, JobTitle
FROM dbo.DimEmployee;
-- Salary and SSN are excluded

GRANT SELECT ON dbo.vw_EmployeePublic TO [analyst@company.com];
DENY SELECT ON dbo.DimEmployee TO [analyst@company.com];
```

## Row-Level Security (RLS)

Fabric Warehouse does **not** natively support SQL Server-style RLS (`CREATE SECURITY POLICY`). To implement per-user row filtering:

**Option 1: View-based RLS**
```sql
CREATE VIEW dbo.vw_MySalesOrders AS
SELECT * FROM dbo.FactSales
WHERE SalesRepEmail = USER_NAME();  -- Filter based on current user
```

This works but requires each user to be explicitly granted access to the view, and USER_NAME() must return the user's identifier.

**Option 2: Semantic Model RLS**
The recommended approach: define RLS in the **Power BI semantic model** built on top of the warehouse. The semantic model's RLS applies when users access data through Power BI reports.

> **Exam Tip:** When the exam asks "how to implement row-level security in a Fabric Warehouse," the answer involves **semantic model RLS** for Power BI consumers, or view-based filtering for SQL users. Native SQL Server-style security policies are not supported.

## Service Principals

For automated access (pipelines, applications):
1. Register an app in **Entra ID** (formerly Azure AD)
2. Grant the service principal access to the workspace or warehouse item
3. Use the service principal's client ID and secret for authentication in pipelines/applications

Service principals bypass MFA and are suitable for unattended/automated processes.

## Dynamic Data Masking

Fabric Warehouse supports **Dynamic Data Masking (DDM)** — masks sensitive column data for users without unmasking permission, without changing the stored values:

```sql
-- Mask an email column
ALTER TABLE dbo.DimCustomer
ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()');
-- Output: aXXX@XXXX.com

-- Mask a credit card number
ALTER TABLE dbo.FactPayments
ALTER COLUMN CardNumber ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)');
-- Output: XXXX-XXXX-XXXX-1234

-- Grant UNMASK to privileged users
GRANT UNMASK ON dbo.DimCustomer TO [admin@company.com];
```

> **Exam Tip:** DDM does **not** prevent privileged users from seeing real values. Anyone with **UNMASK** permission or who can query via SELECT with elevated rights sees the real data. DDM only masks for non-privileged users. It is not a substitute for encryption or true access control.

---

## Encryption

- Data at rest: **AES-256 encryption** (handled by Azure storage layer automatically)
- Data in transit: **TLS 1.2** encryption for all connections
- No customer-managed key (CMK) option per warehouse — encryption is managed by Microsoft at the service level

---

## Common Exam Traps

**"Workspace Viewer role restricts access to specific tables"** — False. Viewer grants read access to all items in the workspace. Table-level restriction requires SQL GRANT/DENY.

**"GRANT always overrides DENY"** — False. DENY always wins over GRANT, regardless of role membership.

**"Dynamic Data Masking hides data from all users"** — False. Users with UNMASK permission see real data. DDM only applies to users without that permission.

**"Fabric Warehouse supports CREATE SECURITY POLICY for RLS"** — False. Use views or semantic model RLS instead.

**"Item sharing with Read permission gives access to specific tables only"** — False. Read permission gives access to all tables. Restrict further with SQL DENY on specific tables/columns.
