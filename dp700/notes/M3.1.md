# Real-Time Analytics in Microsoft Fabric — Eventhouse and KQL

Real-Time Analytics in Fabric is built around two core items: the **Eventhouse** (storage and query engine) and **Eventstream** (data ingestion). Together they form a complete real-time data platform optimised for time-series, log, and event data.

---

## Core Components

| Component | Purpose |
|---|---|
| **Eventhouse** | Container for KQL databases — stores and indexes time-series/event data |
| **KQL Database** | The actual database inside an Eventhouse — holds tables, functions, materialized views |
| **KQL Queryset** | A saved set of KQL queries (like a notebook but for KQL) |
| **Eventstream** | Managed streaming pipeline — routes events from sources to destinations |
| **Real-Time Dashboard** | Dashboard that auto-refreshes, backed by KQL queries |
| **Activator** | Event-driven alerting — triggers actions when conditions are met |

---

## Eventhouse vs Lakehouse

| | Eventhouse / KQL Database | Lakehouse |
|---|---|---|
| Optimised for | Time-series, logs, telemetry, streaming | Batch, structured analytics, ML |
| Query language | KQL (Kusto Query Language) | T-SQL (via endpoint) + Spark |
| Ingestion | Streaming (low latency) | Batch (pipeline, Dataflows, Spark) |
| Data retention | Configurable (hot vs cold) | OneLake (persistent) |
| Auto-indexing | ✅ (by ingestion time) | ❌ (manual partitioning/Z-order) |
| Schema | Flexible — infer on query | Defined at write time |

**Use Eventhouse over Lakehouse when:**
- Data arrives as a continuous stream of events
- Queries are time-bounded ("events in the last 30 minutes")
- You need sub-second query latency on recent data
- You're building IoT, click-stream, or log analytics

## KQL Database — Key Concepts

### Tables
KQL tables store data indexed by **ingestion time**. Each row gets an `ingestion_time()` value automatically.

```kql
// Query data ingested in the last hour
Events
| where ingestion_time() > ago(1h)
| take 100
```

### Hot vs Cold Cache
- **Hot cache**: data kept in fast SSD-backed memory for queries — faster, more expensive
- **Cold cache**: data spilled to cheaper storage (OneLake) — slower, cheaper

Hot cache size is configured per KQL database. Data older than the hot cache window is automatically moved to cold storage but remains queryable.

> **Exam Tip:** Hot cache affects **query performance**, not data availability. Data in cold cache is still queryable — it just takes longer to retrieve. Setting a shorter hot cache reduces cost but increases latency for historical queries.

## Eventstream

**Eventstream** is a managed, no-code streaming pipeline within Fabric. It captures events from sources and routes them to one or more destinations with optional transformation.

### Sources
- **Azure Event Hubs**
- **Azure IoT Hub**
- **Sample data** (for testing — built-in generators)
- **Custom endpoint** (push from any application)
- **Amazon Kinesis** (preview)

### Transformations (in Eventstream)
- Filter
- Aggregate (tumbling window)
- Union
- Expand (flatten JSON)
- Manage Fields (add/remove columns)

### Destinations
- **Eventhouse / KQL Database table**
- **Fabric Lakehouse** (Files or Tables)
- **Fabric Warehouse**
- **Activator** (trigger alerts based on stream conditions)
- **Custom endpoint** (forward to another system)

> **Exam Tip:** An Eventstream can have **multiple destinations** simultaneously — you can fan out a single stream to both an Eventhouse and a Lakehouse in the same Eventstream. Each destination receives the full (or filtered) stream independently.

---

## Eventstream vs Pipeline for Streaming

| | Eventstream | Spark Structured Streaming (via Pipeline/Notebook) |
|---|---|---|
| Coding required | None (visual) | PySpark code |
| Latency | Near-real-time | Near-real-time |
| Transformations | Basic (filter, aggregate, union) | Full Spark DataFrame API |
| Best for | Simple routing and fan-out | Complex transformations, ML inference |

## KQL — Essential Query Patterns

### Basic Structure
```kql
TableName
| operator1
| operator2
| operator3
```

KQL is **pipe-based** — output of each operator flows into the next.

### Common Operators

```kql
// Filter
Events | where EventType == "error" and Timestamp > ago(1h)

// Project (select columns)
Events | project Timestamp, UserID, EventType, Duration

// Extend (add computed column)
Events | extend DurationSec = Duration / 1000

// Summarize (aggregate)
Events | summarize EventCount = count(), AvgDuration = avg(Duration) by EventType

// Sort
Events | sort by Timestamp desc

// Top N
Events | top 10 by Duration desc

// Count
Events | count

// Distinct
Events | distinct EventType
```

### Time-Based Aggregation (Bin)
```kql
// Count events per hour
Events
| summarize Count = count() by bin(Timestamp, 1h)
| order by Timestamp asc
```

`bin()` rounds timestamp values to the nearest interval boundary — essential for time-series charting.

### arg_max — Latest Record per Group
```kql
// Get the most recent record for each device
Telemetry
| summarize arg_max(Timestamp, *) by DeviceID
// Returns all columns (*) for the row with the maximum Timestamp per DeviceID
```

> **Exam Tip:** `arg_max(ColumnToMaximise, ColumnsToReturn)` is the standard KQL pattern for "get the latest state per entity." It's used in nearly every Real-Time Analytics exam question involving current status or latest readings.

### Join in KQL
```kql
Devices
| join kind=inner (
    Alerts | where Severity == "High"
) on DeviceID
```

### Render (Visualisation)
```kql
Events
| summarize Count = count() by bin(Timestamp, 1h)
| render timechart
```

`render` is only valid in KQL Querysets and dashboards — not in exported results.

## Materialized Views

A **materialized view** in a KQL database is a pre-computed aggregation that is automatically updated as new data arrives. Querying a materialized view is faster than re-aggregating the full table on every query.

```kql
.create materialized-view HourlyEventCounts on table Events {
    Events
    | summarize Count = count() by EventType, bin(Timestamp, 1h)
}
```

> **Exam Tip:** Materialized views are **eventually consistent** — there may be a small lag between when new data arrives and when the view reflects it. For real-time queries on the very latest data, query the source table directly.

## Common Exam Traps

**"Eventhouse and Lakehouse serve the same purpose"** — No. Eventhouse is for real-time, time-series, high-frequency event data. Lakehouse is for batch, large-scale historical data. They complement each other.

**"Hot cache determines what data is queryable"** — False. Cold data is still queryable; hot cache only affects speed. Reducing hot cache doesn't make data unavailable.

**"An Eventstream can only route to one destination"** — False. Multiple destinations can be configured on a single Eventstream simultaneously.

**"`arg_max` returns the maximum value of a column"** — Not exactly. `arg_max(col, *)` returns ALL columns of the row where `col` is maximised. It's a "find the row" operation, not just a scalar maximum.

**"KQL `render` works in any context"** — False. `render` only works inside KQL Querysets and Real-Time Dashboards, not when calling KQL via REST API or when exporting results.
