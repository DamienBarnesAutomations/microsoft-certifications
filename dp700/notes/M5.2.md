# Monitoring in Microsoft Fabric

## Monitor Hub

**Core Concept**
Monitor Hub is Fabric's centralized monitoring interface — a single pane that aggregates activity status, history, and error details across all Fabric item types, replacing the need to open each item individually to check health.

**Technical Specifications**
- Accessed via **Monitor** in the Fabric left navigation pane.
- Retains job history for **30 days**. Long-term retention requires exporting logs to **Azure Log Analytics**.
- Users only see jobs for items they have **explicit permissions** to view — Workspace Viewers do not see all jobs.
- Supports **drill-down** into individual activity runs for error investigation.
- Available actions per activity (vary by item type): open the item, retry, view details, view historical runs.
- Filtering by: status, item type, start time, workspace, owner.

**Activity Types Visible in Monitor Hub**
| Activity | What to Monitor |
|---|---|
| **Data pipeline** | Success/failure, individual activity errors, compare duration to historical runs |
| **Dataflows Gen2** | Start/end times, status, duration, table load activity, error drill-down |
| **Semantic model refresh** | Refresh retries (indicate transient issues before classifying as failure) |
| **Spark jobs / Notebooks** | Job progress, task execution, resource usage, Spark logs across Notebooks, Spark Job Definitions, and Pipelines |
| **Eventstreams** | Streaming ingestion status, ingestion performance |

**Metadata Available per Activity**
- Status (success, failure, in-progress, cancelled)
- Start time, end time, duration
- Activity-specific statistics
- Error messages and drill-down links

**Monitoring Best Practices**
1. Establish **baselines** — track regular run durations so anomalies are detectable by contrast.
2. For semantic model refreshes, watch **retry counts** to separate transient network blips from true failures.
3. Use Spark performance metrics to detect resource bottlenecks (e.g., executor throttling).
4. Act on deviations from the baseline, not just on outright failures.

## Activator for Automated Monitoring Actions

**Core Concept**
Activator is Fabric's event-driven rules engine that evaluates streaming data and triggers automated actions when defined conditions are met — removing the need for manual alert monitoring.

**Monitor Hub vs. Activator**
- Monitor Hub is **retrospective** — investigate what happened after the fact.
- Activator is **proactive** — detect conditions in real time and respond automatically.

**Core Concepts**
- **Events:** Individual point-in-time observations in a stream (e.g., a temperature reading).
- **Objects:** Business entities being monitored (e.g., Package001, Freezer_B). Each object has a **unique identifier** field (e.g., PackageID).
- **Properties:** Attributes of an object updated dynamically as events flow in (e.g., CurrentTemperature).
- **Rules:** Conditions that, when met, trigger an action.

**Rule Configuration: Monitor Section**
- **Attribute:** The property column to watch (e.g., Temperature).
- **Summarization:** Smooth raw data before evaluating:
  - `Average` — smooths fluctuations
  - `Min/Max` — captures extremes
  - `Count` — tracks event frequency (detects dead sensors)
  - `Total` — accumulates values
- **Window size:** How much historical data to include (e.g., last 10 minutes).
- **Step size:** How frequently the rule recalculates (e.g., every 5 minutes).

**Rule Configuration: Condition Section**
| Condition Type | Use Case |
|---|---|
| Threshold | Value exceeds a limit (e.g., Temperature > 68°F) |
| Change detection | Detects sudden increases or decreases |
| Range monitoring | Entry or exit from a safe operating range |
| Missing data | No events received for X minutes (sensor failure detection) |

**Rule Configuration: Property Filter**
- Narrow which events are evaluated (e.g., only `City == "Seattle"` or `ProductType == "Medicine"`).
- Up to **three filters** can be combined.

**Action Types**
| Action | Best For |
|---|---|
| Email | Non-urgent, needs full context |
| Teams | Immediate team coordination |
| Power Automate | Multi-step workflows across external systems |
| Fabric item (pipeline/notebook) | Triggering data processing in response to an event |

## Exam Gotchas & Distinctions

- **"Workspace Viewers can see all Monitor Hub jobs"** — False. Users only see jobs for items they have explicit permissions to view.
- **"Monitor Hub retains logs indefinitely"** — False. **30 days** only. Export to Azure Log Analytics for long-term retention.
- **"Activator alerts only support simple numerical thresholds"** — False. Rules support threshold, change detection, range monitoring, missing data, and KQL-based logic.
- **"Every event matching a condition fires a separate alert"** — False. Activator uses **state management** — an alert fires on state *transition* (when condition becomes true), not on every matching event.
- **"Activator uses KQL queries to evaluate rules"** — False. Activator has a visual rule editor. KQL results can feed *into* Activator, but Activator's evaluation engine itself is not KQL.
- **"Monitor Hub replaces Activator"** — False. They serve different purposes: Monitor Hub = retrospective investigation; Activator = proactive automated response.
