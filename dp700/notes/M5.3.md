# Securing Data Access in Microsoft Fabric

Data access security in Fabric involves multiple overlapping layers. This module consolidates the full security model — OneLake security, workspace roles, item permissions, and item-specific security (RLS, CLS, DDM) — and clarifies which layer applies when.

---

## The Fabric Security Stack

```
Entra ID (Authentication)
    └── Fabric Tenant Settings (what's allowed globally)
          └── Workspace Roles (who can do what in a workspace)
                └── Item-Level Permissions (who can access specific items)
                      └── Object-Level Permissions (SQL GRANT/DENY)
                            └── Row/Column Filtering (views, RLS, DDM)
```

Each layer adds granularity. The **most restrictive** applicable rule wins.

---

## OneLake Security

**OneLake** is the underlying storage for all Fabric items. Access to OneLake data is controlled through the Fabric item permissions — you cannot access OneLake data directly without going through a Fabric item (lakehouse, warehouse, etc.).

### OneLake Path Structure
```
onelake://{workspace-name}/{item-name}.Lakehouse/Tables/{table}/
onelake://{workspace-name}/{item-name}.Lakehouse/Files/{path}/
```

### OneLake Access Permissions
When sharing a Fabric item (e.g., lakehouse), three OneLake-specific permissions can be granted:

| Permission | Scope |
|---|---|
| **ReadData** | Read Delta tables via the SQL Analytics Endpoint |
| **ReadAll** | Read all files in the lakehouse via OneLake API (includes Files/ and Tables/ raw files) |
| **Write** | Write to the lakehouse via OneLake API |

> **Exam Tip:** **ReadData** vs **ReadAll** is a critical distinction. ReadData gives access via the SQL endpoint (structured, governed). ReadAll gives access to the raw Parquet/Delta files directly via the OneLake API — bypassing any SQL-level filtering or views. Granting ReadAll to a user who shouldn't see all raw data is a security risk.

## Workspace Role Security Boundaries

| Role | Can Read Items | Can Modify Items | Can Share Items | Can Manage Members |
|---|---|---|---|---|
| Admin | ✅ | ✅ | ✅ | ✅ |
| Member | ✅ | ✅ | ✅ | ✅ (up to Member) |
| Contributor | ✅ | ✅ | ❌ | ❌ |
| Viewer | ✅ (read-only) | ❌ | ❌ | ❌ |

Workspace roles apply to **all items** in the workspace. You cannot use workspace roles to restrict access to specific items.

---

## Item-Level Sharing (Bypassing Workspace Roles)

Share specific Fabric items with users who are NOT workspace members:

```
Right-click Lakehouse → Manage Permissions → Share
→ Grant specific user:
    - ReadData (SQL endpoint access)
    - ReadAll (full OneLake file access)
    - Build (create reports from this item)
```

> **Exam Tip:** Item sharing is the solution when you need to give a user access to ONE lakehouse or warehouse without giving them access to everything else in the workspace. Adding them to the workspace as Viewer would expose ALL items.

## Row-Level Security (RLS)

RLS restricts which **rows** a user can see. Implementation depends on the item type:

### Semantic Model RLS (Power BI)
Define roles in the semantic model with DAX filter expressions:
```dax
// In semantic model: SalesRep role definition
[SalesRepEmail] = USERPRINCIPALNAME()
// Users in this role only see rows where SalesRepEmail = their email
```

Assign users or security groups to roles in the semantic model settings. This is the **primary RLS mechanism** for Power BI consumers.

### Lakehouse/Warehouse: No Native RLS
Neither Fabric Lakehouse nor Fabric Warehouse natively supports row-level security. Implement via:
1. **Views** with `USER_NAME()` or `SESSION_CONTEXT()` filters
2. **Separate tables/schemas** per user group
3. **Semantic model RLS** (if consumed through Power BI)

> **Exam Tip:** "How do you implement RLS for a Fabric Lakehouse?" → If users consume via Power BI: semantic model RLS. If users query directly via SQL endpoint: view-based filtering. Native SQL Server-style security policies are NOT available in Fabric Lakehouse or Warehouse.

## Column-Level Security (CLS)

### Warehouse
```sql
-- DENY a specific column
DENY SELECT ON dbo.DimEmployee (Salary) TO [analyst@company.com];
```

### Lakehouse
Use a view that excludes sensitive columns:
```sql
-- In Spark
spark.sql("""
CREATE VIEW IF NOT EXISTS silver_employee_public AS
SELECT EmployeeID, Name, Department, JobTitle
FROM silver_employees
""")
-- Share the view, restrict table access
```

### Semantic Model
Column-level filtering in the semantic model: remove the column from the model entirely, or use OLS (Object-Level Security):

Object-Level Security (OLS) in Power BI:
- Hides entire tables or columns from specific roles
- Users in the restricted role cannot see the column in reports or in DAX
- Configured via tabular model JSON or third-party tools (Tabular Editor)

## Dynamic Data Masking (DDM) — Warehouse

```sql
-- Mask email column
ALTER TABLE dbo.DimCustomer
ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()');

-- Mask partial credit card
ALTER TABLE dbo.Payments
ALTER COLUMN CardNumber ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)');

-- Default masking (0/null/XXX depending on type)
ALTER TABLE dbo.DimEmployee
ALTER COLUMN Salary ADD MASKED WITH (FUNCTION = 'default()');

-- Grant UNMASK to see real values
GRANT UNMASK ON dbo.DimCustomer TO [admin@company.com];
```

DDM masking functions:
| Function | Effect |
|---|---|
| `default()` | Numbers → 0, Strings → "xxxx", Dates → 01-01-1900 |
| `email()` | First char + domain placeholder: `aXXX@XXXX.com` |
| `partial(prefix, padding, suffix)` | Custom masking with literal portions visible |
| `random(from, to)` | Numbers: random value in range |

> **Exam Tip:** DDM is a **display-layer obfuscation**. It does NOT protect against users who export data and use workarounds. Users with UNMASK permission, or who can use aggregation/inference to reconstruct values, can bypass DDM. It reduces accidental exposure, not deliberate exfiltration.

## Private Links and Network Security

For enhanced network security, Fabric supports **Azure Private Link**:
- Access Fabric from a private VNet without traffic traversing the public internet
- Reduces exposure to public endpoint attacks
- Requires Azure VNet configuration and Fabric admin enablement

**Managed Virtual Network** (for Spark jobs):
- Spark clusters in Fabric can be configured to run within a managed VNet
- Enables Spark to access resources inside a private VNet (on-premises data, private Azure services)

## Comparing Security Mechanisms

| Mechanism | Granularity | Item Type | Who Configures |
|---|---|---|---|
| Workspace roles | All items in workspace | All | Workspace Admin |
| Item sharing | Specific item | All | Item owner / Workspace Member+ |
| SQL GRANT/DENY | Table/schema/column | Warehouse | Workspace Admin or SQL Admin |
| Views | Row + column level | Lakehouse, Warehouse | Data engineer |
| Semantic model RLS | Row level per user role | Power BI | Report developer / data modeler |
| OLS (Object-Level Security) | Table/column in semantic model | Power BI | Report developer / Tabular Editor |
| DDM | Column display masking | Warehouse | SQL Admin |
| Sensitivity labels | Item-level classification | All | Fabric Admin / Purview |

## Common Exam Traps

**"ReadAll permission is the same as ReadData"** — False. ReadData accesses the SQL endpoint (governed, structured). ReadAll accesses raw OneLake files directly — bypasses any SQL-level row/column filtering.

**"Native RLS works in Fabric Warehouse"** — False. Use semantic model RLS or view-based filtering.

**"DDM protects against data exfiltration"** — False. It masks display but doesn't prevent a determined user with appropriate access from inferring or reconstructing masked values.

**"OLS in Power BI blocks column access at the storage level"** — False. OLS hides columns from the model experience. Users with direct warehouse/lakehouse access can still read those columns via SQL or Spark.

**"Workspace Viewer sees all items but Contributor can restrict some items"** — False. Viewer sees all items; Contributors cannot restrict items from Viewers. Item-level restriction requires item sharing, not workspace role adjustments.
