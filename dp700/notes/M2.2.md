# Using Spark in a Fabric Lakehouse

This module covers the practical application of Spark within a Fabric Lakehouse context — reading, writing, and organising data with a focus on lakehouse-specific behaviours. Core Spark API concepts are covered in M1.3; this module focuses on lakehouse integration specifics.

---

## Lakehouse Spark Context

When a notebook is attached to a lakehouse, Spark has direct access to both storage areas:

- `Files/` → accessible as `spark.read.load("Files/...")` or `abfss://...`
- `Tables/` → accessible as managed tables via `spark.table("tablename")` or `spark.sql("SELECT...")`

The lakehouse provides a pre-configured **Spark catalog** backed by the lakehouse's internal metastore. Tables written to the catalog appear instantly in the lakehouse UI under "Tables".

---

## Writing to the Lakehouse Tables Section

```python
# Write a DataFrame as a managed Delta table
df.write.format("delta").saveAsTable("bronze_sales")
# → Stored at Tables/bronze_sales/ in the lakehouse

# Append new data
df.write.format("delta").mode("append").saveAsTable("bronze_sales")

# Overwrite
df.write.format("delta").mode("overwrite").saveAsTable("bronze_sales")
```

Tables written this way are **managed tables** — dropping the table also deletes the data.

---

## Writing to the Lakehouse Files Section

```python
# Write raw Parquet to Files/ (not a registered table)
df.write.mode("overwrite").parquet("Files/raw/sales_2024.parquet")

# Write Delta to Files/ (external table — not auto-registered)
df.write.format("delta").save("Files/delta/sales")
```

Data in `Files/` is not automatically registered as a Delta table in the catalog. To query it via SQL, you must either:
1. Move it to `Tables/` using `saveAsTable()`
2. Create an external table pointing to the path: `spark.catalog.createExternalTable("sales_ext", path="Files/delta/sales", source="delta")`

## Ingesting Files into the Lakehouse

### CSV
```python
df = spark.read.csv("Files/raw/orders.csv", header=True, inferSchema=True)
```

### Parquet
```python
df = spark.read.parquet("Files/raw/orders.parquet")
```

### JSON
```python
df = spark.read.json("Files/raw/events.json")
```

### Multiple files / wildcard
```python
df = spark.read.csv("Files/raw/orders_*.csv", header=True)
```

## Transforming and Staging Data (Bronze → Silver)

A typical lakehouse pattern:

```python
# Read from bronze (raw CSV)
bronze_df = spark.read.csv("Files/raw/sales.csv", header=True, inferSchema=True)

# Apply cleaning transformations
silver_df = (bronze_df
    .dropna(subset=["OrderID", "CustomerID"])
    .withColumn("OrderDate", bronze_df["OrderDate"].cast("date"))
    .filter(bronze_df["Quantity"] > 0)
)

# Write to silver layer as a managed Delta table
silver_df.write.format("delta").mode("overwrite").saveAsTable("silver_sales")
```

## Querying Lakehouse Tables with SQL in Notebooks

```sql
%%sql
SELECT CustomerID, SUM(Amount) AS TotalAmount
FROM silver_sales
GROUP BY CustomerID
ORDER BY TotalAmount DESC
LIMIT 10;
```

## Schema and Table Management

```python
# List tables in the current lakehouse
spark.catalog.listTables()

# Check if a table exists
spark.catalog.tableExists("silver_sales")

# Drop a managed table (also deletes data)
spark.sql("DROP TABLE IF EXISTS silver_sales")

# Show table schema
spark.sql("DESCRIBE silver_sales").show()
```

## Performance Considerations in the Lakehouse

### Small Files Problem
Frequent small writes (streaming, many small inserts) create many small Parquet files. Each file adds overhead at read time. Mitigate with:
- `OPTIMIZE` SQL command to compact files
- `spark.sql("OPTIMIZE silver_sales")` in notebooks

### Partitioning in the Lakehouse
```python
df.write.partitionBy("OrderYear", "OrderMonth").format("delta").saveAsTable("orders_partitioned")
```
Creates folder structure: `Tables/orders_partitioned/OrderYear=2024/OrderMonth=1/...`

Query performance improves when filtering on partition columns because Spark can skip irrelevant partitions entirely (**partition pruning**).

> **Exam Tip:** Partition on columns you **frequently filter by** with **low cardinality** (few distinct values). Date components (year, month) are ideal. Customer ID with millions of unique values would create millions of folders — a disaster.

### Caching
```python
df.cache()          # Cache in memory
df.persist()        # More options (MEMORY_AND_DISK, etc.)
df.unpersist()      # Release cache
```
Cache a DataFrame when you reference it multiple times in the same session to avoid recomputing it.

## Notebooks and Lakehouse Attachment

A notebook must be **attached to a lakehouse** to use the default catalog. A notebook can be attached to:
- **One default lakehouse** (provides the default database context)
- **Additional lakehouses** (accessible but not the default)

Attaching a lakehouse does **not** move data — it just configures the Spark session's catalog context.

## Common Exam Traps

**"Files written to Files/ are immediately queryable via SQL"** — False. They must be registered as tables (via `saveAsTable()` or `createExternalTable()`) before they appear in the SQL Analytics Endpoint.

**"All Spark tables are Delta by default in Fabric"** — Yes, Delta is the default. But a table written with `.parquet()` to `Files/` and then registered as an external table would be Parquet format. Delta is default for `saveAsTable()`.

**"Partitioning always helps performance"** — Only if you filter on the partition column and cardinality is appropriate. High-cardinality partition columns create millions of tiny folders.

**"Dropping a table always deletes the data"** — Only for **managed** tables. External tables retain their data files after the table is dropped.
