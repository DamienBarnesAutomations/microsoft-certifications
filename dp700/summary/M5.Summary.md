## Card 1: CI/CD with Git Integration and Deployment Pipelines

### What It Is

Git integration and deployment pipelines are the two mechanisms Fabric provides for managing content lifecycle from development through production. Git integration connects a workspace to a repository in GitHub or Azure DevOps for source control, while deployment pipelines move content between stage-based workspaces (Dev, Test, Production) in a structured release process. They can be used independently or together for a complete CI/CD approach.

### Key Details

#### Git Integration

Git integration operates at the workspace level, meaning a single workspace is connected to a single repository and branch at a time. Fabric supports both GitHub and Azure DevOps repositories. You can connect a workspace to any branch in the repo, and content items are stored as individual files in a structured folder layout. When you connect a workspace to Git, Fabric pulls the latest content from the connected branch and syncs local changes back via commit. Fabric supports multiple branching strategies: an isolated workspace approach lets you branch out an existing workspace to a new workspace for independent development, while client tools allow you to clone the repo locally, make changes, and push via pull request.

#### Deployment Pipelines

Deployment pipelines define a sequence of stages, typically two or three (Dev, Test, Production), where each stage is backed by a Fabric workspace. You assign workspaces to each stage, then use the pipeline UI to deploy content from one stage to the next. During deployment, Fabric clones content from the source stage and pastes it into the target stage. You can control which items deploy, configure deployment rules to swap connections (such as pointing to a production lakehouse instead of a development one), and set rules that persist across deployments. Deployment pipelines also support rules for replacing workspace references, semantic model connections, and data source credentials.

#### Combined Approach

When using Git integration and deployment pipelines together, only the Dev workspace is connected to Git. Developers commit changes to Git, then those changes flow into the Dev workspace. From there, the deployment pipeline promotes content through Test and Production. This separation ensures that Git serves as the source of truth for development, while the pipeline handles environment promotion.

#### Fabric REST APIs

Fabric provides REST APIs for both Git and deployment pipeline operations. The Git APIs allow you to programmatically commit changes, sync a workspace, and check status against the connected repository. The Deployment Pipeline APIs let you list pipelines, list stages, list items in a stage, and trigger deployments programmatically. These APIs are essential for automating CI/CD workflows and integrating Fabric into existing DevOps toolchains.

#### Branching Workflows

The isolated workspace branching approach creates a new workspace from an existing one, backed by a new branch, allowing parallel development without affecting the original workspace. Client tool branching lets developers clone the repository locally using standard Git tools, work on feature branches, push commits, and create pull requests for code review before merging into the main branch that Fabric tracks.

### Exam Gotchas

- Git integration is per-workspace, not per-item. You cannot connect individual items to Git independently.
- Deployment pipelines do not use Git. They are a separate Fabric-native promotion mechanism. Content moves via cloning, not via a repo.
- Deployment rules persist after deployment, meaning once you set a rule to swap a connection string, it stays in place for future deploys.
- Only the Dev workspace needs Git connectivity when using the combined approach. Test and Production workspaces receive content through the pipeline, not from Git.
- Fabric REST APIs require proper permissions on the workspace and pipeline. A Capacity Admin or Workspace Admin role is typically needed for pipeline operations.

## Card 2: Monitor Hub

### What It Is

The Monitor hub is a centralized visualization interface within Fabric that allows users to track and manage the status of activities across their Fabric items. It provides a single pane of glass for monitoring pipeline runs, dataflow refreshes, semantic model refreshes, Spark jobs, Eventstreams, and other item activities. The Monitor hub is the primary tool for identifying failures, reviewing historical runs, and troubleshooting operational issues.

### Key Details

#### Access and Visibility

You access the Monitor hub by selecting the Monitor icon in the Fabric navigation. What you see depends on your role. Regular users see only the activities and items they own or have access to. Fabric admins and tenant admins see all monitored activities across the entire tenant, giving them a complete operational picture.

#### Monitored Activities

The Monitor hub tracks a wide range of Fabric activities including Data Factory pipeline runs, Dataflow Gen2 refreshes, semantic model (dataset) refreshes, Spark job executions, Eventstreams operations, and other item-level activities. Each activity appears as a row in the monitoring view with its current status, start time, end time, and associated item details.

#### View Capabilities

The Monitor hub provides several view capabilities to help you find relevant information quickly. You can see the current status of each activity (Running, Completed, Failed, Cancelled). The view retains a 30-day history of activity runs, so you can review past executions. You can filter activities by status, activity type, time range, user who initiated the activity, and workspace. These filters can be combined to narrow down to specific operational concerns.

#### Drill-Down Actions

When you select an activity in the Monitor hub, you can perform several drill-down actions. You can open the item directly to investigate its configuration. You can retry a failed activity. You can view detailed logs and error messages for a specific run. You can also view the full history of that item to see patterns of success or failure over time.

#### Spark Monitoring

Spark job monitoring is particularly detailed in the Monitor hub. You can track Spark job progress, view executor and driver logs, monitor resource consumption, and see job-level details such as records processed and execution time. Spark monitoring works across items, meaning you can see Spark activity initiated by notebooks, data pipelines, or other Fabric items in a unified view.

#### Best Practices

Effective monitoring involves establishing what normal behavior looks like for your key activities. Once you understand normal run times, success rates, and patterns, you can quickly spot anomalies such as unusually long run times, unexpected failures, or changes in data volume. The Monitor hub helps you identify bottlenecks in your data pipelines and optimize performance over time. Regularly reviewing the Monitor hub is a recommended operational practice for Fabric environments.

### Exam Gotchas

- Users can only see their own items by default. They cannot see other users' activities unless they are a Fabric admin.
- The Monitor hub retains history for 30 days. Activities older than 30 days are no longer visible in the hub.
- Monitor hub filters are additive, meaning combining multiple filters narrows results further rather than broadening them.
- Spark monitoring details are available even when the Spark job was initiated indirectly through a pipeline or dataflow.
- The Monitor hub is for operational monitoring, not for auditing. Use Audit logs in the Admin portal for compliance and security auditing.

## Card 3: OneLake Security Roles

### What It Is

OneLake security roles are a role-based access control (RBAC) model that governs access to tables, folders, and files within a lakehouse at the data level. Security roles are enforced across all compute engines that access OneLake data, including Spark, SQL endpoints, and the OneLake APIs. This means a permission granted or denied through OneLake security applies regardless of which engine or tool a user employs to query the data.

### Key Details

#### When to Use OneLake Security Roles

OneLake security roles are specifically designed for scenarios where you need to restrict data access for users who have the Fabric Viewer role or Read-only item permissions. By default, these users do not have access to the underlying data in a lakehouse. OneLake security roles allow you to selectively grant or deny access to specific tables, folders, or columns without changing the user's Fabric role or item permissions. If a user already has a higher Fabric role such as Contributor or Admin, they typically have broader access that supersedes OneLake security restrictions.

#### Role Components

A OneLake security role consists of four components. The Data component specifies which tables, folders, or files the role applies to, allowing you to scope access to specific data assets. The Permission component defines the access level: Read allows users to read data but not modify it, while ReadWrite allows both reading and writing. The Members component lists the users, groups, or service principals assigned to the role. The Constraints component allows you to apply row-level or column-level filters, restricting which rows or columns a user can see within the scoped data.

#### DefaultReader Role

When you create a OneLake security role, Fabric automatically creates a DefaultReader role. This role is granted to any user who gains access to the lakehouse through sharing or other mechanisms. The DefaultReader role provides read access to all tables by default. If you want to restrict a user's data access, you must explicitly remove them from the DefaultReader role and assign them to a more restrictive custom role. This is a common oversight that leads to unintended data exposure.

#### Creation and Permissions

You create OneLake security roles from the lakehouse ribbon. Only users with the Admin or Member workspace role can create and manage OneLake security roles. Contributors and lower roles do not have permission to define data-level security. The roles are stored as part of the lakehouse metadata and are applied at query time by the compute engine.

#### Consistency Across Compute Engines

One of the key design principles of OneLake security roles is consistency across compute engines. Whether a user queries data through Spark (notebooks, jobs), SQL endpoint, Fabric data pipelines, or OneLake REST APIs, the same security roles are enforced. This eliminates the need to implement separate security mechanisms for each compute engine and ensures a unified security posture.

### Exam Gotchas

- OneLake security roles only affect users who already have limited Fabric permissions (Viewer or Read-only item). They do not override higher Fabric roles.
- The DefaultReader role is created automatically and grants broad read access. Failing to remove users from it is the most common security mistake.
- Column-level security via Constraints requires careful configuration. Test your roles to confirm that restricted columns are truly hidden from query results.
- OneLake security roles are per-lakehouse. You must configure them separately for each lakehouse in your environment.
- Security roles are not the same as workspace roles. Workspace roles control Fabric item-level access, while OneLake security roles control data-level access within a lakehouse.

## Card 4: Fabric Administration

### What It Is

Fabric administration is the set of controls, roles, and portals that govern the configuration, security, and operations of a Microsoft Fabric tenant. It encompasses a five-level hierarchy from tenant-wide settings down to individual items, a four-tier admin model where different administrators manage different scopes, and a centralized Admin portal for configuring governance policies, capacity, domains, users, and auditing.

### Key Details

#### Five-Level Hierarchy

Fabric organizes resources in a five-level hierarchy. At the top is the Tenant, which is the organizational boundary for all Fabric resources. Below that is Capacity, which represents the compute and storage resources allocated to run Fabric workloads. Domains sit within a capacity and provide logical groupings of workspaces. Workspaces contain items such as lakehouses, pipelines, reports, and semantic models. Items are the individual units of content that users create and interact with. Each level in the hierarchy has associated administration controls and settings.

#### Four-Tier Admin Model

Fabric uses a four-tier admin model to delegate administrative responsibilities. The Fabric admin (tenant admin) has full control over tenant-wide settings, tenant policies, and audit logs. The Capacity admin manages capacity-level settings including scaling, pausing, and resource allocation. The Domain admin manages domain-level settings such as delegated policies, item lifecycle management, and domain member assignments. The Workspace admin manages workspace-level settings including access permissions, Git integration, and item creation. Each tier operates within its defined scope and does not automatically grant access to higher tiers.

#### Admin Portal Sections

The Admin portal is the centralized interface for Fabric administration. It contains several key sections. Tenant settings hold governance policies that apply across the tenant, such as whether users can share content externally or create personal workspaces. Capacity settings allow capacity admins to manage compute resources, monitor utilization, and configure scaling. Domains provide logical groupings with delegated administration. Users shows all Fabric users in the tenant and their activity. Audit logs provide a searchable record of user actions for compliance and security investigation. Monitoring provides operational visibility across all Fabric activities.

#### Tenant Settings

Tenant settings are governance policies rather than security controls. They define what users can and cannot do across the Fabric tenant, such as enabling or disabling specific features, controlling sharing behavior, and managing data connectivity. Changes to tenant settings propagate within approximately 15 minutes across the tenant. It is important to understand that tenant settings govern behavior and capabilities, not data access or authentication.

#### Domains

Domains are a logical grouping mechanism for organizing workspaces and their associated resources. Domains do not control access. Access control remains at the workspace level. Domains support delegated administration, meaning a domain admin can manage domain-specific settings without being a Fabric admin. Domains can have subdomains for further hierarchical organization. Delegated settings allow domain admins to configure certain policies within their domain scope without affecting the broader tenant.

#### Capacity Management

Capacity is measured in Capacity Units (CUs), which represent the compute and memory resources available to run Fabric workloads. Scale up increases the CU size of an existing capacity for more power. Scale out adds additional capacity nodes for parallel workload processing. Pausing a capacity stops all workloads and stops billing, which is useful for development environments. The Metrics app provides detailed capacity utilization analytics, showing which workloads consume resources and identifying optimization opportunities.

#### Licensing

Fabric offers several licensing tiers. Fabric Free provides basic access to explore Fabric with limited capabilities. Power BI Pro allows sharing and collaboration on Power BI content with a per-user license. Power BI Premium Per User (PPU) provides advanced features including larger model sizes, AI capabilities, and paginated reports on a per-user basis. The F64 capacity threshold is significant because it enables Fabric Free users to view Power BI content shared to them, removing the need for every viewer to hold a Pro or PPU license.

#### Sharing Patterns

Fabric supports two primary sharing patterns. Workspace apps bundle multiple reports, dashboards, and other content into a single distributable package for large audiences who need consume-only access. Workspace roles (Admin, Member, Contributor, Viewer) provide collaborative access for teams who need to create, edit, and manage content together. Choosing the right pattern depends on whether the audience needs to consume or collaborate.

#### Audit Logs

Audit logs in the Admin portal provide a comprehensive, searchable record of user activities across the Fabric tenant. They capture actions such as content access, sharing, workspace changes, and administrative modifications. Audit logs are essential for compliance investigations, security monitoring, and operational troubleshooting. Logs are retained for a period defined by the tenant's Microsoft 365 compliance configuration.

#### Governance: Promoted vs Certified

Fabric distinguishes between two endorsement levels for content. Promoted content has been flagged as important or useful by the content owner or workspace admin, making it more visible in search results and content discovery. Certified content has been reviewed and validated by a designated certifier, typically a domain or tenant admin, confirming it meets organizational standards for accuracy and reliability. Certification implies a higher level of trust than promotion.

### Exam Gotchas

- Tenant settings are governance policies, not security controls. They do not prevent unauthorized data access; they control feature availability and sharing behavior.
- Domain admins do not automatically have workspace admin privileges. Domain administration and workspace administration are separate roles.
- The 15-minute propagation delay for tenant settings means changes are not instant. Do not expect immediate effect after modifying a tenant policy.
- The F64 capacity threshold is the minimum required for Free users to consume Power BI content. Below F64, all viewers need Pro or PPU licenses.
- Workspace roles control access to Fabric items, but OneLake security roles control access to data within items. These are separate security layers.
- Pausing a capacity stops all workloads. Any scheduled refreshes, pipelines, or jobs will not run until the capacity is resumed.
