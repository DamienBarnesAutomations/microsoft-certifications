## CI/CD: Git Integration and Deployment Pipelines

**Core Concept**
Fabric lifecycle management uses Git integration (GitHub/Azure DevOps) for version control and continuous integration, Fabric deployment pipelines for staged promotion (Dev → Test → Production), and Fabric REST APIs for automation — collectively enabling CI/CD for Fabric items.

**Technical Specifications**
- **Git integration (CI):** Workspace-level connection to GitHub or Azure DevOps repositories. Branch support enables isolated development. Sync workspace changes to Git (Changes) and pull Git commits into workspace (Updates). Git status column shows sync state per item. Source control icon shows change count.
- **Deployment pipelines (CD):** Create pipeline with 2-3 stages (Dev, Test, Production). Assign a workspace to each stage. Deploy content by cloning from one stage to another. Pipeline copies all workspace content into the target stage.
- **Combined Git + deployment pipelines:** Common approach: connect only the Development workspace to Git. Use Git for version control during development. Use deployment pipelines to promote content to Test and Production. Avoids Git synchronization conflicts across multiple stages.
- **Fabric REST APIs for CI/CD:**
  - Git APIs: Commit workspace changes to remote branch, update workspace with branch commits, get Git status.
  - Deployment pipeline APIs: List stage items, deploy stage content.
- **Branching workflow (isolated workspace):**
  1. Connect development workspace to main branch.
  2. From workspace, select "Branch out to new workspace" — creates new branch and dedicated workspace.
  3. Make changes in isolated workspace, commit to isolated branch.
  4. Create Pull Request in Git to merge isolated branch into main.
  5. Merge PR, open shared development workspace, sync changes from Git.
- **Branching workflow (client tools):**
  1. Connect development workspace to main branch.
  2. Clone repository locally (VS Code, Power BI Desktop).
  3. Make local changes, push to remote.
  4. Connect isolated branch to separate workspace for testing.
  5. Issue PR to merge into main branch.

**Architectural Logic**
CI/CD separates development from production to prevent breaking changes and enable collaboration. Git provides version history, branching, and pull request workflows for safe code integration. Deployment pipelines handle the infrastructure-level promotion of entire workspace contents between environments. REST APIs bridge the gap when automation outside the Fabric UI is needed (e.g., triggering deployments from external CI/CD systems). The recommended combined approach uses Git only on the Development workspace to avoid synchronization conflicts when deployment pipelines copy content across stages.

**Implementation Workflow**
1. Set up Git repository (GitHub or Azure DevOps).
2. Connect Fabric workspace to repository and branch from Workspace settings > Git integration.
3. Create deployment pipeline with stages.
4. Assign workspaces to each pipeline stage.
5. Develop in isolated branch/workspace, commit to Git.
6. Merge via PR to main branch.
7. Sync development workspace from Git.
8. Deploy to Test via deployment pipeline (clone from Dev).
9. Test and validate in Test workspace.
10. Deploy to Production via pipeline (clone from Test).

**Exam Gotchas & Distinctions**
- **Git integration is at workspace level:** The entire workspace connects to a repository/branch, not individual items.
- **Deployment pipeline copies ALL content:** Cloning from Dev to Test copies all workspace items. Cannot deploy individual items through the pipeline.
- **Only Development workspace connected to Git in combined approach:** Test and Production workspaces are managed solely through deployment pipelines. Connecting them to Git causes conflicts.
- **Branch out creates both new branch and new workspace:** The Fabric UI's "Branch out to new workspace" creates an isolated branch in Git and a dedicated workspace, both automatically.
- **REST APIs can commit and sync:** Git REST APIs allow programmatic commits and syncs without manual UI interaction.
- **CI = Git (version control, branching, PRs). CD = Deployment pipelines (staged promotion). CI/CD together + REST APIs = full automation.

## Monitoring Hub

**Core Concept**
The Monitor Hub is a centralized visualization tool that collects and aggregates execution data from Fabric activities (pipelines, dataflows, semantic model refreshes, Spark jobs, Eventstreams) into a single interface — providing job status, 30-day history, drill-down error investigation, and filterable views.

**Technical Specifications**
- **Access:** Monitor icon in Fabric navigation pane. Users see only items they have permission to view. Fabric admins see everything.
- **Monitored activities:** Data pipeline execution history, dataflow executions, datamart/semantic model refreshes, Spark job/notebook execution history and job details, Eventstream ingestion status and performance.
- **View capabilities:**
  - Status per activity: Running, Succeeded, Failed.
  - 30-day activity history for pattern analysis.
  - Filter by: status (running/succeeded/failed), item type, start time, submitting user, workspace/location.
  - Schedule failures view (preview): View and manage failure notifications for scheduled items in one place.
- **Drill-down actions (vary by activity type):**
  - Open the activity directly.
  - Retry a failed activity.
  - View activity details (customized per type: status, start/end time, duration, statistics).
  - View historical runs.
  - Hyperlinks to drill into execution details and error information.
- **Spark monitoring:** View Spark applications triggered from Notebooks, Spark Job Definitions, and Pipelines across items.
- **Best practices:** Continuously monitor ingestion/transformation/load processes. Collect and analyze data regularly to establish normal behavior parameters. Review logs/metrics to spot anomalies. Take action on deviations. Use monitoring data to identify bottlenecks for performance optimization.

**Architectural Logic**
The Monitor Hub solves the problem of fragmented monitoring across different Fabric item types. Instead of checking pipeline runs in Data Factory, notebook runs in Data Engineering, and refresh history in Power BI separately, the hub aggregates all activity metadata into one view. The 30-day retention provides trend analysis context. The filter-by-user capability is critical for support scenarios where a specific user's job failures need investigation.

**Implementation Workflow**
1. Open Monitor Hub from Fabric navigation pane.
2. Filter by status, item type, workspace, user, or time range to narrow scope.
3. Select an activity row, select ellipsis for actions (View detail, Retry, Open, View history).
4. Drill down into error details using hyperlinks in the detail view.
5. For recurring issues, use historical data to identify when the problem started.

**Exam Gotchas & Distinctions**
- **Monitor Hub is reactive, not proactive:** Shows what happened (status, errors, history). Proactive alerting requires Activator.
- **30-day retention:** Activity data in Monitor Hub is retained for 30 days. Beyond that, data is not available.
- **User-specific visibility:** Users only see activities for items they have permission to view. Admins see everything.
- **Schedule failures view is in preview:** The consolidated view of scheduled item failures is preview functionality.
- **Activity detail is type-specific:** The information available in the detail view varies depending on the activity type (pipeline vs. dataflow vs. Spark job).
- **Spark monitoring cross-item:** View Spark applications triggered from Notebooks, Spark Job Definitions, AND Pipelines — all in one place.

## OneLake Security Roles

**Core Concept**
OneLake security uses a role-based access control (RBAC) model that restricts access to specific tables or folders within a lakehouse — enforced consistently across all Fabric compute engines (Spark, SQL, and OneLake APIs) and designed to grant data access to users who have no data access through workspace roles (Viewers, Read-only item permission users).

**Technical Specifications**
- **When to use:** Users with Admin, Member, or Contributor workspace roles already have full read/write access to all OneLake data — OneLake security roles do NOT restrict their access. Use OneLake roles to grant specific data access to Viewer role users or users with only Read item permission, who have no OneLake data access by default.
- **Role components:**
  - **Data:** The specific tables or folders the role grants access to.
  - **Permission:** Read (view only) or ReadWrite (view and edit specific tables/folders without granting workspace write role).
  - **Members:** Users or groups assigned to the role.
  - **Constraints:** Optional row or column filters applied to the data within the role.
- **DefaultReader role:** Every new lakehouse automatically includes a DefaultReader role. When you share a lakehouse with the "Read all Apache Spark and subscribe to events" permission, the recipient is added to DefaultReader and gets read access to ALL data in the lakehouse. To restrict a user to only specific tables/folders, create a custom role with limited data scope AND remove the user from DefaultReader.
- **Creation:** From lakehouse ribbon > Manage OneLake security > New role. Set name, permission type (Read/ReadWrite), select tables/folders, save. After creation, edit to add members and constraints.
- **Creation permissions:** Only workspace Admin and Member roles can create or modify OneLake security roles.
- **Consistency:** OneLake security roles apply across ALL compute engines — Spark notebooks, SQL analytics endpoint, and OneLake APIs. T-SQL security (RLS/CLS/DDM) only applies to SQL endpoint queries.

**Architectural Logic**
OneLake security fills the gap between workspace-level access and SQL-level granular permissions. Workspace roles grant all-or-nothing access to lakehouse data. T-SQL permissions (RLS, CLS, DDM) only control what users see through the SQL analytics endpoint — they do not restrict Spark or OneLake API access. OneLake security applies consistently across all access methods, ensuring a user restricted from certain tables in the SQL endpoint cannot bypass the restriction by querying through Spark.

**Implementation Workflow**
1. Identify users who need restricted data access (Viewers or Read-only permission users).
2. Create OneLake security role specifying which tables/folders the role grants access to.
3. Set permission level (Read or ReadWrite).
4. Add members (users/groups).
5. Optionally apply row or column constraints.
6. Remove users from DefaultReader role if they were previously added through sharing.
7. Save role — restrictions apply across Spark, SQL, and OneLake APIs.

**Exam Gotchas & Distinctions**
- **OneLake security grants access, does not restrict:** Admin/Member/Contributor roles already have full access. OneLake security only adds access for users who would otherwise have none.
- **DefaultReader removal is critical:** Sharing a lakehouse adds the user to DefaultReader (full read access). If you then create a custom role granting limited access, the user still has full access through DefaultReader unless you explicitly remove them.
- **OneLake security vs. T-SQL security:** OneLake = consistent across all engines (Spark, SQL, APIs). T-SQL = SQL endpoint only. Enforce sensitive data restrictions at the OneLake level if access must be consistent regardless of query engine.
- **Constraints not available at role creation:** Must create the role first (select tables/folders), then edit to add row/column constraints.
- **ReadWrite permission:** Grants write access to specific tables/folders without requiring a workspace write role — useful for scenarios where users should edit data but not create new items.
- **Creation limited to Admin/Member:** Contributors and Viewers cannot create or modify OneLake security roles.

## Fabric Administration

**Core Concept**
Five-level platform hierarchy (Tenant → Capacity → Domain → Workspace → Item) with a four-tier admin delegation model (Fabric admin, Capacity admin, Domain admin, Workspace admin), managed through the Fabric admin portal for tenant settings, capacity management, domain governance, license assignment, and monitoring.

**Technical Specifications**
- **Hierarchy:**
  - **Tenant:** Entire Fabric environment aligned to Microsoft Entra ID directory.
  - **Capacity:** Dedicated compute/storage resource powering Fabric workloads.
  - **Domain:** Logical grouping of workspaces for governance boundary and policy delegation.
  - **Workspace:** Collaboration container for items.
  - **Item:** Individual data asset (lakehouse, warehouse, notebook, semantic model, report).
- **Admin roles and scope:**
  | Role | Scope | Responsibility |
  |---|---|---|
  | Fabric admin | Entire tenant | Tenant settings, manage capacities/domains, assign other admins |
  | Capacity admin | Specific capacity | Manage assigned workspaces, monitor capacity performance |
  | Domain admin | Specific domain | Manage workspaces within domain, enforce domain policies |
  | Workspace admin | Specific workspace | Control access, manage items, assign workspace permissions |
  - Fabric admin role listed as "Power BI Administrator" in Microsoft Entra ID.
- **Admin portal sections:**
  - **Tenant settings:** Platform-wide feature controls.
  - **Capacity settings:** View, create, manage capacities; assign workspaces to capacities.
  - **Domains:** Create domains, assign domain admins, organize workspaces by business function.
  - **Users:** Assign Fabric admin, capacity admin, domain admin roles.
  - **Audit logs:** User activity records across tenant — track who viewed/exported/shared/deleted content.
  - **Monitoring:** Usage and performance data.
- **Additional admin tools:** Microsoft 365 admin center (Fabric licenses), Microsoft Entra ID (identity/access), PowerShell cmdlets, REST APIs.
- **Tenant settings:**
  - Enable/disable features for: entire org, specific security groups, everyone except specific groups.
  - Changes propagate within 15 minutes.
  - Critical distinction: Tenant settings are **governance policies**, not security measures. Disabling Export to Excel removes the UI button but does not prevent data export via API or other tools. Real data security requires item permissions and sensitivity labels.
  - Key settings: Users can create Fabric items (main on/off), Export to Excel, Certification (controls who can certify items), external sharing, Copilot.
- **Domains:**
  - Logical grouping — domain assignment does NOT change item visibility or access control. Workspace roles and item permissions still control access.
  - Assignment methods: by workspace name (pattern matching — auto-assign workspaces containing "Finance") or by workspace admin (auto-assign workspaces whose admin is the Finance lead).
  - Subdomains: create nested governance boundaries (e.g., "Audit" subdomain under "Finance").
  - Domain admins can override delegated tenant settings for their domain.
  - Domain contributors: workspace admins with permission to assign their own workspaces to the domain.
  - Delegated settings: specific tenant settings the Fabric admin makes overridable at domain level (e.g., Certification, Default sensitivity label).
- **Capacity management:**
  - Capacity Units (CUs): all Fabric actions consume CUs. When consumption exceeds capacity limit, Fabric throttles background jobs.
  - Capacity Metrics app: visualize CU consumption, identify which workloads/workspaces consume most, detect throttling.
  - Scale up: increase F SKU size (e.g., F64 → F128) for more compute within same capacity.
  - Scale out: move some workspaces to a separate capacity to distribute load.
  - Pause capacity: stop all compute on a capacity (all content unavailable). Useful for dev/test capacities overnight/weekends.
  - Workspaces not assigned to a capacity fall back to shared capacity (limited, not for production).
- **Licensing:**
  - **Fabric Free:** Auto-assigned on first sign-in (if Fabric enabled). Can create non-Power BI Fabric items (lakehouses, notebooks, warehouses, pipelines) on F capacity. Cannot create Power BI items in shared workspaces.
  - **Power BI Pro:** Required to create and share Power BI reports/dashboards. On capacities < F64, also needed to VIEW Power BI content.
  - **Power BI Premium Per User (PPU):** Premium features per user. Does NOT provision a capacity. Cannot create non-Power BI Fabric items without F capacity.
  - **F64 threshold:** On F64+ capacities, Free license users CAN view Power BI reports/dashboards with Viewer workspace role or app. Below F64, viewing Power BI content requires Pro or PPU.
  - License assignment: from Microsoft 365 admin center (not Fabric admin portal). Group-based via Microsoft Entra ID security groups is recommended for scale.
- **Sharing patterns:**
  - **Workspace apps:** Publish read-only reports/dashboards to large audiences without granting workspace access. App consumers see finished content only, not work in progress.
  - **Workspace roles (Viewer):** Direct workspace access — user sees all items including work in progress. For collaboration teams, not large audiences.
  - External sharing: requires appropriate licenses or Microsoft Entra B2B. Controlled via Export and sharing tenant settings.
- **Audit logs:** Capture who viewed/exported reports, shared content externally, modified workspace permissions, deleted Fabric items. Searchable in admin portal by activity type, user, date range. Provides compliance evidence.
- **Governance:**
  - **Endorsement:**
    - **Promoted:** Item marked as quality/useful by workspace members (Contributor+). Badge in portal.
    - **Certified:** Formal review by authorized certifier (controlled via Certification tenant setting). Badge in portal.
  - **OneLake catalog Govern tab:** Governance snapshot of entire tenant. Shows sensitivity label coverage (%), endorsement coverage (% promoted/certified vs unendorsed), recommended actions.
  - **Admin monitoring workspace:** Dedicated workspace with Feature Usage and Adoption report + underlying semantic model. Shows which features users use, usage trends, most active users/departments. Strategic tool for adoption analysis.

**Architectural Logic**
The admin model follows a "centrally governed, decentrally managed" pattern. The Fabric admin sets tenant-wide policies and delegates operational management to domain admins (department-specific governance) and capacity admins (resource management). This prevents the Fabric admin from becoming a bottleneck while maintaining centralized visibility through audit logs and the Capacity Metrics app. Domains organize governance boundaries without interfering with the existing workspace role and item permission access control model — a workspace assigned to the Finance domain still requires explicit user permissions. The F64 threshold is a critical architectural design point: it determines whether Free users can view Power BI content, significantly impacting license cost.

**Implementation Workflow**
1. Enable Fabric in tenant settings (Users can create Fabric items).
2. Purchase and configure capacity (e.g., F64).
3. Assign Fabric admin role (listed as Power BI Administrator in Entra ID).
4. Create capacities and assign workspaces.
5. Create domains with domain admins. Delegate relevant tenant settings.
6. Configure tenant settings (export, sharing, certification, Copilot).
7. Assign licenses via M365 admin center (group-based).
8. Set up sharing patterns (workspace apps for consumers, workspace roles for collaborators).
9. Install Capacity Metrics app for ongoing CU monitoring.
10. Configure audit logging and set up regular governance review cadence.

**Exam Gotchas & Distinctions**
- **Tenant settings are NOT security:** Disabling Export to Excel removes the UI button but does not prevent data export through APIs or other tools. Real security requires item permissions and sensitivity labels.
- **Domains do NOT control access:** Moving a workspace into a Finance domain does not restrict access to Finance users. Access is still controlled by workspace roles and item permissions. Domains organize governance, not access.
- **F64 threshold changes license requirements:** On F64+, Free users can view Power BI content. Below F64, Pro or PPU is needed. This is the single biggest cost optimization lever.
- **Fabric admin = Power BI Administrator in Entra ID:** The role name in the Microsoft Entra ID admin center is different from what it's called in Fabric.
- **License assignment is M365 task, not Fabric:** Licenses are assigned in the Microsoft 365 admin center, not the Fabric admin portal.
- **Group-based licensing is recommended:** Assign licenses to Entra ID security groups rather than individuals for scalability.
- **Capacity pause makes all content unavailable:** Pausing a capacity stops all compute — all lakehouses, warehouses, notebooks, and reports become inaccessible until resumed.
- **Scale up vs scale out:** Scale up = increase SKU size (F64 → F128). Scale out = move workspaces to separate capacity. CHOOSE: scale up for uniform performance increase, scale out for workload isolation.
- **Capacity Metrics app must be installed:** Not pre-installed. Admin must install from AppSource within Fabric.
- **DefaultReader role is auto-created:** Every lakehouse gets DefaultReader. Users shared with "Read all Apache Spark" are added to it. Removing from DefaultReader is required for restricted OneLake security roles.
- **Audit logs for compliance:** Export to Excel, external share, permission changes, item deletions — all captured. Essential for compliance investigations.
- **Endorsement: Promoted vs Certified:** Promoted = self-certified by workspace members. Certified = formal review by authorized certifier (controlled via tenant setting).
- **Admin monitoring workspace is separate:** Not part of the admin portal. It's a standard Fabric workspace with prebuilt reports.
- **Domain assignment by workspace admin is recommended:** Pattern-based assignment (name matching) works initially but workspace admin assignment auto-assigns new workspaces as they're created by that admin.
