## Warehouse vs SQL Analytics Endpoint

**Core Concept**
Fabric provides two SQL-based items serving different purposes — a Warehouse with full read/write T-SQL capabilities (DDL, DML, MERGE, ACID) and a read-only SQL analytics endpoint attached to each Lakehouse — and choosing between them depends on whether DML operations are required.

**Technical Specifications**
| Capability | Warehouse | SQL analytics endpoint |
|---|---|---|
| Read data | Yes | Yes |
| Write data (INSERT, UPDATE, DELETE, MERGE) | Yes | No |
| Create tables (DDL) | Yes | No |
| Create views and stored procedures | Yes | Yes |
| Data source | Native warehouse tables in Delta format | Lakehouse Delta tables |

**Architectural Logic**
Use a Warehouse when you need full transactional T-SQL for dimensional modeling, ETL/ELT with DML, and MERGE-based upserts. Use the SQL analytics endpoint when you already have lakehouse Delta tables and only need read-only SQL access (querying, view creation, SQL security). The endpoint is auto-created for every lakehouse and provides the same SQL surface minus DDL/DML.

**Exam Gotchas & Distinctions**
- **SQL analytics endpoint cannot write:** Cannot INSERT, UPDATE, DELETE, or MERGE. Cannot CREATE TABLE or ALTER TABLE. Must use Spark, dataflows, or pipelines to write to Lakehouse tables.
- **Both support views and stored procedures:** The write limitation is on base tables only. Both can create views and stored procedures for abstraction and security.
- **Both support SQL security (RLS, CLS, DDM):** Security policies defined via T-SQL apply to both Warehouse and SQL analytics endpoint.

## Dimensional Modeling

**Core Concept**
Data warehouses organize data into fact tables (quantitative measures of business events) and dimension tables (descriptive attributes providing context), typically structured as a star schema (fact + directly related dimensions) or snowflake schema (normalized dimensions requiring multiple joins).

**Technical Specifications**
- **Fact tables:** Numerical measures (SalesAmount, Quantity). Large row counts. Foreign keys to dimension tables.
- **Dimension tables:** Descriptive attributes (CustomerName, Region, ProductCategory). Smaller row counts. Contain surrogate key (DW-generated integer, system-assigned) and alternate key (source-system business key like CustomerID, ProductCode).
- **Star schema:** Fact table relates directly to each dimension. Denormalized dimensions. Fewer joins, better query performance.
- **Snowflake schema:** Dimensions normalized into related tables (e.g., DimProduct references DimCategory and DimSupplier). Multiple joins required to reach some attributes. Less storage but more complex queries.
- **Surrogate vs. alternate keys:**
  - Surrogate key: Integer, auto-generated, system-assigned, no business meaning, maintains consistency across source system changes.
  - Alternate key: Natural/business key from source system, maintains traceability between warehouse and source.
  - Both needed — surrogate for warehouse consistency, alternate for source traceability and SCD matching.
- **Time dimension:** Special dimension with temporal attributes (year, quarter, month, day). Enables time-based aggregation.
- **Slowly Changing Dimensions (SCD):** Track how dimension attributes change over time.
  - **Type 0:** Attributes never change.
  - **Type 1:** Overwrite existing data — no history preserved.
  - **Type 2:** Add new record for each change — full history preserved. Mark old version as expired (IsActive = 'False', ValidTo = GETDATE()). New version becomes active (IsActive = 'True', ValidTo = '9999-12-31'). Requires source change detection mechanism (CDC, change tracking, triggers).
  - **Type 3:** History added as new column (limited history).
  - **Type 4:** Separate history dimension table.
  - **Type 5:** Hybrid for large dimensions where Type 2 is infeasible.
  - **Type 6:** Combination of Type 2 and Type 3.
- **Loading fact tables with SCD:** After dimension tables are populated, fact loading must look up the correct surrogate key version matching the event's timestamp. Pattern: `SELECT MAX(DateKey) FROM DimDate WHERE FullDateAlternateKey = stg.OrderDate` or similar surrogate key lookup joining on alternate key.
- **Staging tables:** Temporary holding area mirroring source data structure. Benefits: buffer between source and warehouse, minimizes load impact on warehouse performance, abstraction layer for transformation logic. Used with COPY INTO or pipelines before transforming into final dimensional model.
- **Scalar approximate count:** `APPROX_COUNT_DISTINCT(column)` uses HyperLogLog algorithm. Maximum 2% error rate with 97% probability. Significantly faster on large datasets. Use for exploration when precise count isn't required.

**Architectural Logic**
The dimensional model (star/snowflake) optimizes for analytical queries over transactional ones. Dimension denormalization (star) prioritizes query performance by minimizing joins at the cost of storage. Snowflake prioritizes storage efficiency and update consistency over query speed. SCD Type 2 is the most common approach for tracking historical changes — it preserves full history but increases dimension table size. Fact load ordering (dimensions first, then facts) ensures foreign key integrity. Staging protects production warehouse performance by isolating raw data load from transformation load.

**Implementation Workflow**
1. Design dimensional model: identify fact tables and dimension tables.
2. Create dimension tables with surrogate keys (INT IDENTITY) and alternate key columns.
3. Create staging tables matching source data structure.
4. Load staging data via COPY INTO, pipelines, or dataflows.
5. Load dimension tables: detect changes (CDC), insert new records, handle SCD logic (Type 1 overwrite or Type 2 versioning).
6. Load fact tables: join staged data to dimensions using alternate keys, select appropriate surrogate key version for SCD dimensions.
7. Create views and stored procedures for reusable query logic.

**Exam Gotchas & Distinctions**
- **Surrogate key is DW-internal:** Never expose surrogate keys to end users. They exist for warehouse consistency, not business meaning.
- **Alternate key is source-internal:** Always preserve the source system's business key for traceability and SCD matching.
- **Type 2 SCD requires change detection:** Without CDC or change tracking in the source system, you cannot determine what changed between loads.
- **Fact tables loaded after dimensions:** Foreign key integrity requires dimensions to exist before referencing facts.
- **Staging vs final tables:** Staging has source schema (raw, flat). Final has dimensional schema (normalized, keyed).
- **APPROX_COUNT_DISTINCT vs COUNT(DISTINCT):** Use APPROX for exploration/scoping (sub-second results at 2% error). Use COUNT(DISTINCT) for exact reporting.

## Fabric Warehouse Architecture

**Core Concept**
A Fabric data warehouse is a fully managed, enterprise-scale relational database built on OneLake with full transactional T-SQL capabilities (DDL, DML, MERGE), ACID compliance, automatic compute scaling independent of storage, and Delta format storage accessible by all Fabric workloads.

**Technical Specifications**
- **Storage:** All warehouse data stored in open Delta Parquet format on OneLake. Same data accessible by Lakehouse, Spark, Power BI without duplication.
- **Compute:** Scales automatically and independently from storage. No infrastructure to configure.
- **T-SQL support:** Full DDL (CREATE, ALTER, DROP), DML (INSERT, UPDATE, DELETE, MERGE), query capabilities — same engine as Azure SQL/SQL Server.
- **MERGE:** Supports upsert scenarios (INSERT + UPDATE + DELETE in single statement).
- **Cross-database querying:** Three-part naming (`database.schema.table`) to query across warehouses and lakehouses in the same workspace without copying data. All warehouses sharing the same workspace are on the same logical SQL server.
- **Table clones:** Zero-copy clones using `CREATE TABLE dbo.Employee AS CLONE OF dbo.EmployeeUSA`. Copies metadata only, references same underlying OneLake data files. Use cases: development/testing, pre-release snapshots, point-in-time historical preservation.
- **Tool connectivity:** SSMS, Azure Data Studio, any SQL client via TDS connections (Microsoft Entra ID authentication only — SQL authentication not supported). TCP port 1433 must be open. Copy SQL connection string from warehouse context menu in workspace.
- **Ingestion methods:**
  - **COPY INTO:** Bulk load from external Azure storage files (CSV, Parquet). Supports SAS or Storage Account Key for authentication. ERRORFILE for rejected rows (CSV only). Wildcards and multiple file locations from same storage account/container. Example:
    ```sql
    COPY INTO dbo.Region
    FROM 'https://storage.blob.core.windows.net/data/Region.csv'
    WITH (FILE_TYPE = 'CSV', CREDENTIAL = (IDENTITY = 'Shared Access Signature', SECRET = 'xxx'), FIRSTROW = 2)
    ```
  - **OPENROWSET:** Query files directly from external storage or OneLake without creating tables first. Ad hoc analysis or ingestion.
  - **CTAS (CREATE TABLE AS SELECT):** Create new table from SELECT query results. Useful for transforming and loading in one step.
  - **INSERT...SELECT:** Insert rows from one table into another (same or cross-database).
  - **Data pipelines:** Copy Data assistant with step-by-step wizard. Scheduleable. Connects to various source types.
  - **Dataflows Gen2:** Power Query experience with Copilot integration. Destinations: Azure SQL, Lakehouse, Kusto, Synapse, Warehouse. Update methods: Append (add rows) or Replace (truncate and reload).
  - **Cross-database 3-part queries:** Query lakehouse tables directly from warehouse — no data copy needed.
- **ETL process steps:** Data extraction (connect to source) → Data transformation (clean, deduplicate, validate, combine) → Data loading (into fact/dimension tables) → Post-load optimizations.
- **Full vs. incremental load:** Full load = truncate and reload all data (simpler, used for initial load or full refresh). Incremental load = apply changes since last update (preserves history, more complex, used for regular updates). Both can be combined.

**Architectural Logic**
The Fabric warehouse decouples compute from storage — queries consume compute resources that auto-scale independently of the underlying Delta Parquet files in OneLake. This means storage costs reflect only the Parquet files, while compute costs reflect only when queries run. Cross-database querying using 3-part naming eliminates data duplication between warehouses and lakehouses in the same workspace. Table clones provide instant point-in-time copies without storage overhead, enabling safe development and testing against production-sized data. The COPY INTO command enables bulk data loading directly from Azure storage without staging infrastructure.

**Implementation Workflow**
1. Create Warehouse in Fabric workspace (from create hub or within workspace).
2. Create tables using T-SQL CREATE TABLE with appropriate data types (INT for keys, NVARCHAR for text, DECIMAL for financial values).
3. Ingest data: COPY INTO (Azure storage files), pipelines (orchestrated), dataflows (Power Query), or cross-database queries.
4. Optionally use staging tables as buffer before loading final dimensional model.
5. Transform data using stored procedures, views, or CTAS.
6. Query using SQL query editor, visual query editor, or external tools (SSMS, ADS).
7. Create semantic models with Direct Lake mode for Power BI reporting.

**Exam Gotchas & Distinctions**
- **COPY INTO requires CREDENTIAL:** Must specify SAS or Storage Account Key for Azure storage access. ERRORFILE only supports CSV files.
- **Multiple file locations in COPY INTO:** Must be from same storage account and container. Comma-separated list.
- **All files must have same structure:** Same columns in same order matching target table.
- **Cross-database requires same workspace:** Three-part naming (`database.schema.table`) works only within the same Fabric workspace, not across workspaces.
- **Table clones are zero-copy:** No data duplication. Cloned table references same Parquet files. Deletion of cloned table does not affect source.
- **CTAS vs INSERT...SELECT:** CTAS creates new table; INSERT...SELECT adds rows to existing table.
- **Dataflow Gen2 update methods:** Append (add rows) vs Replace (truncate + reload). Does not support merge/upsert natively.
- **Warehouses in same workspace share logical SQL server:** Visible in SSMS object explorer when connected.
- **SSMS requires database name field:** Must explicitly enter warehouse name in connection properties. Leaving it blank causes connection failure even if authentication succeeds.
- **Entra ID only — no SQL auth:** SQL Server authentication (username/password) is not supported for Fabric warehouse connections.
- **Port 1433 must be open:** Network firewall must allow TCP 1433 for external tool connectivity.

## Querying the Warehouse

**Core Concept**
Query a Fabric warehouse using T-SQL (SQL query editor with IntelliSense and Copilot) or no-code visual query editor (drag-drop canvas with auto-generated T-SQL), supporting full analytical patterns including ranking functions, approximate counts, and window functions.

**Technical Specifications**
- **SQL query editor:** IntelliSense, code completion, syntax highlighting, client-side parsing, validation. New SQL query or template from Home menu or Queries node. Auto-saves to My queries folder. Results preview capped at 10,000 rows.
- **Results toolbar options:**
  - **Open in Excel:** Live connected query (not static download). Requires Enable Editing → Enable Content → authenticate in Excel.
  - **Explore this data (preview):** Side-by-side matrix and visual view for ad hoc exploration.
  - **Visualize results:** Creates Power BI visual directly from query results. Does NOT support queries with ORDER BY clause.
  - **Copy:** Copy with column names, results only, or column names only.
  - **Multiple result sets:** Results dropdown to navigate between tabs.
  - **Save as view / Save as table:** Requires schema and name selection.
- **Visual query editor:** Drag tables onto canvas. Right-click for Merge queries with join type and key column selection. View SQL button to inspect auto-generated T-SQL. Edit SQL script to open in SQL query editor. Results toolbar: Save as table, Save as view, Download Excel file, Visualize results.
- **Ranking functions with PARTITION BY:**
  - `ROW_NUMBER()`: Ordinal position within partition (1, 2, 3...). Ties get different numbers.
  - `RANK()`: Ranked position — ties share same rank, subsequent positions have gaps (1, 1, 3, 4...).
  - `DENSE_RANK()`: Ranked position — ties share same rank, no gaps (1, 1, 2, 3...).
  - `NTILE(N)`: Percentile grouping within partition (e.g., NTILE(4) = quartile 1-4).
- **Snowflake schema querying:** Requires multiple JOINs through the normalization chain. DimProduct → DimCategory needs two JOINs even if DimProduct columns aren't in SELECT.
- **SSMS connection details:**
  1. Copy SQL connection string from warehouse context menu.
  2. Paste into SSMS Server name field.
  3. Enter warehouse name in Database Name field (required — do not leave blank).
  4. Select Microsoft Entra authentication method.
  5. Port 1433 must be open.

**Architectural Logic**
The SQL query editor and visual query editor serve different audiences — T-SQL developers get IntelliSense, Copilot, and full syntax control; citizen developers get drag-drop with automatic query generation. Ranking functions enable complex analytical patterns (top-N per group, quartile analysis) in single queries without self-joins or subqueries. APPROX_COUNT_DISTINCT trades precision for speed using HyperLogLog — appropriate for data exploration where exact counts aren't needed.

**Implementation Workflow**
1. Open SQL query editor or New visual query from warehouse.
2. For SQL editor: Type or paste T-SQL query. Use Copilot (chat or quick actions) for assistance.
3. For visual editor: Drag tables to canvas, right-click to merge/join, select columns and aggregation.
4. Run query, review results (10K row cap), export or save as view/table.
5. Connect external tools (SSMS, ADS) via copied connection string.

**Exam Gotchas & Distinctions**
- **Visualize results does not support ORDER BY:** Queries with ORDER BY clause cannot use the Visualize results feature.
- **SSMS requires explicit database name:** Leaving the Database Name field blank causes connection failure. Must match warehouse name exactly.
- **Port 1433 requirement:** Network firewalls must permit outbound TCP 1433 for SSMS or ADS connectivity.
- **Entra ID authentication only:** No SQL Server authentication option.
- **Snowflake schema requires all join hops:** Even if intermediate dimension columns aren't in the final SELECT, all join relationships must be included in the FROM clause to traverse the normalization chain.
- **RANK vs DENSE_RANK:** RANK leaves gaps after ties; DENSE_RANK does not. Example: 3 tied for 1st → RANK gives 1,1,1,4; DENSE_RANK gives 1,1,1,2.
- **ROW_NUMBER is non-deterministic for ties:** Without a unique ORDER BY column, same tie values can get different row numbers between executions.
- **Results preview limited to 10K rows:** Downloaded/copied results may be larger; the display cap is 10,000 rows.
- **Queries auto-saved in My queries folder:** SQL query editor automatically saves work-in-progress queries.

## Data Modeling and Semantic Layer in the Warehouse

**Core Concept**
Preparing warehouse data for consumption involves cleaning up the model view (hiding staging/internal objects, renaming columns, adding descriptions), defining relationships (cardinality, cross-filter direction), standardizing access through views and DAX measures, and publishing semantic models using Direct Lake mode for Power BI reporting.

**Technical Specifications**
- **Model view actions:**
  - **Hide objects:** Staging tables, surrogate key columns, internal flags — objects that clutter the consumer field list.
  - **Rename columns:** Business-friendly names over technical abbreviations. Example: `CustRgn` → `Customer Region`.
  - **Add descriptions:** Context for what the data represents. Critical for Copilot and Fabric IQ — descriptive column names and descriptions improve natural language query accuracy.
- **Relationships:**
  - **Cardinality:** Typically many-to-one (fact-to-dimension).
  - **Cross-filter direction:** Single direction (dimension filters fact) — standard for star schema. Keeps filter behavior predictable and performant.
  - Without defined relationships, every consumer must write explicit JOIN logic. Relationships encode the connection once.
  - Data agents (Copilot, Fabric IQ) use relationships to generate accurate joins in NL-to-SQL.
- **Views:** Standardize access for T-SQL consumers. Encapsulate join logic, filters, column selection. Reference like a table. Serve as stable report sources — point reports at views rather than base tables.
- **DAX Measures:** Reusable calculations defined in the warehouse model view. Example: `Total Sales = SUM(SalesAmount)`. Single source of truth for metrics — update in one place, all consumers use the new definition.
- **Semantic model:** Created from warehouse using Direct Lake mode. Reads Delta Parquet files directly from OneLake — no import/refresh needed. Reports reflect latest warehouse data without scheduled refreshes.
- **Copilot benefits of modeling:** Well-named tables, descriptive columns, defined relationships, views, and measures all improve Copilot's ability to generate accurate T-SQL and NL responses.

**Architectural Logic**
Data modeling in the warehouse exists to bridge the gap between the technical schema (optimized for ETL) and the consumer schema (optimized for analysis). Hiding staging artifacts, renaming columns, and adding descriptions make the warehouse self-documenting. Relationships replace manual JOIN knowledge with encoded connections. Views standardize T-SQL access while measures standardize DAX calculations. The Direct Lake semantic model eliminates the import/refresh cycle — all consumers (Power BI, Copilot, data agents) read the same current data from OneLake Parquet files without duplication.

**Implementation Workflow**
1. In model view: hide staging tables, surrogate keys, and internal ETL columns.
2. Rename technical columns to business-friendly names. Add descriptions.
3. Define relationships between tables (many-to-one, single cross-filter direction).
4. Create views for common T-SQL query patterns.
5. Create DAX measures for standard business calculations.
6. Publish semantic model for Power BI reporting (Direct Lake mode).

**Exam Gotchas & Distinctions**
- **Hiding vs deleting:** Hiding removes from consumer view but does not drop the object. Object remains queryable via T-SQL.
- **Renaming in model view is cosmetic:** Does not change underlying T-SQL column name. Only affects the model view and downstream semantic model.
- **Direct Lake vs Import:** Direct Lake reads OneLake Parquet files directly — no refresh needed, but may have slower query on very complex models. Import mode copies data into Power BI memory — faster queries but requires scheduled refresh and duplicates storage.
- **Relationships inform Copilot/data agents:** Without defined relationships, NL-to-SQL tools cannot determine how tables connect and will produce incorrect joins.
- **Measures defined in warehouse model:** Can be consumed by Power BI without redefining there — becomes portable across reports.

## Copilot for Data Warehouse

**Core Concept**
AI-powered assistant integrated into the SQL query editor providing code completion (ghost text), chat-based natural language to T-SQL generation, and quick actions (Explain, Fix) — requiring F2/P1+ capacity, English prompts, and well-structured schema for best results.

**Technical Specifications**
- **Prerequisites:** Copilot enabled in tenant settings. Paid SKU (F2 or higher, or P-SKU) — trial SKUs not supported. Warehouse created in workspace.
- **Code completion:** Ghost text suggestions as you type. Accept with Tab. Accept next word with Ctrl+Right (Cmd+Right on macOS). Dismiss by continuing typing. Hover to preview alternatives. Enable/disable in warehouse Settings > Copilot pane. Status bar shows active/inactive.
- **Comments to guide Copilot:** Use `--` comments to describe intent, Copilot generates corresponding SQL. Example: `-- What is the distribution of trips by hour on working days?` generates appropriate query.
- **Copilot chat pane:** `/` commands:
  - `/generate-sql` — Generate T-SQL from natural language prompt.
  - `/explain` — Explain the query in the active tab.
  - `/fix` — Fix errors in the active tab. Optionally add context (e.g., `/fix using CTAS instead of ALTER TABLE`).
  - `/question` — Generate natural language response to prompt.
  - `/help` — Access Copilot documentation and guidance.
  - Session context retained across prompts — follow-up messages can reference earlier queries.
- **Quick actions (ribbon buttons):**
  - **Explain:** Adds summary comment at top and inline comments throughout the highlighted query section.
  - **Fix:** Auto-resolves syntax/logic errors. Only enabled after running a query that returned an error. Uses SQL error message as context.
- **Best practices:**
  - Descriptive table/column names in warehouse schema improve generated SQL accuracy.
  - Define relationships in model view for correct JOIN generation.
  - Use comments (`--`) at query top for extra context.
  - Specify columns, aggregations, and filters explicitly in prompts.
  - English prompts only for natural language to T-SQL.
  - Copilot handles typos and infers context from schema.

**Architectural Logic**
Copilot uses the warehouse schema (table names, column names, relationships, descriptions) as grounding context for T-SQL generation. The quality of generated queries correlates directly with schema quality — descriptive names and defined relationships produce accurate joins and filters. The multi-turn chat session context enables iterative refinement without re-stating full context.

**Implementation Workflow**
1. Ensure Copilot enabled in tenant and warehouse created.
2. Enable Show Copilot completions in warehouse settings.
3. Start typing in SQL editor for ghost text completions.
4. Use `--` comments to describe complex queries.
5. Open Copilot chat pane for NL-to-SQL with `/commands`.
6. Use Explain/Fix quick actions for debugging and comprehension.

**Exam Gotchas & Distinctions**
- **Fix button only activates after error:** Does not preemptively check queries. Must run the query first and get an error before Fix becomes available.
- **Trial SKUs do not support Copilot:** Requires F2+ or P1+. Free trial capacity (F64 trial) may have limitations.
- **English language only:** Natural language to T-SQL supports English prompts only.
- **Code completion requires explicit enable:** Not on by default in all environments. Check Settings > Copilot pane.
- **Copilot uses warehouse schema + query tab contents:** Generated SQL quality depends on schema quality.
- **Session context retained:** Follow-up prompts can reference earlier queries — no need to repeat full context every time.
- **Comments guide generation:** Writing descriptive comments at query top (`--`) improves Copilot output quality.

## Monitoring a Warehouse

**Core Concept**
Monitor warehouse activity through three mechanisms: the Fabric Capacity Metrics app (CU consumption trends and throttling detection), dynamic management views (real-time connections, sessions, requests), and query insights views (historical aggregated query performance with 30-day retention).

**Technical Specifications**
- **Fabric Capacity Metrics app:** Installed by admin. Filter to show only warehouse activity. Monitor CU consumption trends, identify throttling (indicating capacity is insufficient for workload). Optimize license based on observed usage patterns.
- **Capacity Units (CUs):** Each Fabric action consumes CUs. Data read/write in warehouse queries and underlying OneLake operations are significant CU consumers.
- **DMVs (real-time monitoring):**
  - `sys.dm_exec_connections`: Connection information (client IP, connection properties).
  - `sys.dm_exec_sessions`: Authenticated session information (login name, session ID).
  - `sys.dm_exec_requests`: Active request information (command, start time, elapsed time, status).
  - Example query: join all three DMVs to find active running requests ordered by elapsed time.
  - **KILL command:** Requires workspace Admin role to terminate long-running sessions. Members, Contributors, Viewers can only see their own results.
- **Query insights views (historical, 30-day retention):**
  - `queryinsights.exec_requests_history`: Each completed SQL request with start time, login, command.
  - `queryinsights.long_running_queries`: Queries by median execution time — includes `last_run_command`, `number_of_runs`, `median_total_elapsed_time_ms`, `last_run_start_time`.
  - `queryinsights.frequently_run_queries`: Queries by run count — includes `number_of_runs`, `number_of_successful_runs`, `number_of_failed_runs`.
  - **Latency:** Up to 15 minutes before queries appear in insight views.
  - **Parameterized dedup:** Queries with predicates are parameterized — `WHERE orderdate > '01/01/2023'` and `WHERE orderdate > '12/31/2021'` are considered the same command for aggregation purposes.

**Architectural Logic**
DMVs and query insights serve different monitoring timeframes. DMVs show what is happening right now — useful for identifying a runaway query. Query insights show what happened over the past 30 days — useful for identifying performance trends and optimization targets. The Capacity Metrics app connects CU consumption to specific activities, enabling cost optimization. The combination of real-time DMVs and historical insights creates a complete monitoring picture.

**Implementation Workflow**
1. Admin installs Capacity Metrics app to monitor CU consumption and throttling.
2. Query DMVs for real-time activity: `sys.dm_exec_requests` with `WHERE status = 'running'` sorted by elapsed time.
3. Query query insights for historical performance: `queryinsights.long_running_queries` sorted by median elapsed time to identify optimization candidates.
4. Use `queryinsights.frequently_run_queries` to identify most-used queries for performance tuning.
5. KILL long-running sessions (Admin only) if they consume excessive resources.

**Exam Gotchas & Distinctions**
- **DMVs vs query insights:** DMVs = real-time (current connections/sessions/requests). Query insights = historical (completed queries, 30-day retention, up to 15-min delay).
- **KILL requires Admin:** Only workspace Admins can terminate other users' sessions.
- **Query insights latency:** Up to 15 minutes — recent queries will not appear immediately.
- **30-day retention:** Query insights data is retained for 30 days. Historical data beyond 30 days is not available.
- **Parameterized dedup:** Queries with different date literals are treated as the same command for aggregation in `frequently_run_queries` and `long_running_queries`.
- **Capacity Metrics app must be installed:** Not pre-installed. Admin must install from AppSource within Fabric.
- **CUs are consumed by both compute and storage operations:** Warehouse queries consume CUs for compute; underlying Delta Parquet operations in OneLake also consume CUs.

## Warehouse Security

**Core Concept**
Multi-layered security: workspace roles (broad access control), item permissions (granular sharing), and T-SQL-based granular security (DDM, RLS, CLS, object-level permissions) — all enforced regardless of how data is accessed (SQL query editor, SSMS, SQL analytics endpoint, or Power BI).

**Technical Specifications**
- **Workspace roles:** Admin, Member, Contributor, Viewer — apply to all items in workspace.
- **Item permissions:** Read (connect via SQL analytics endpoint), ReadData (read data from any table/view), ReadAll (read raw Parquet files in OneLake). At minimum, Read permission required for SQL analytics endpoint connection.
- **Dynamic Data Masking (DDM):** Masks sensitive data in query results — underlying data in database unchanged. Applied per-column via ALTER TABLE:
  - `default()`: Full mask based on data type.
  - `email()`: First letter + "*.com" suffix. Only for email fields.
  - `partial(prefix, padding_string, suffix)`: Expose first N and last N characters with custom padding. `partial(0,"XXX-XXX-",4)` on phone numbers.
  - `random(low, high)`: Random number in range. Only for numeric/binary types.
  - Example: `ALTER TABLE Customers ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()')`
  - Unprivileged users with query permissions can potentially infer actual data — DDM should be part of a comprehensive security strategy (not standalone).
- **Row-Level Security (RLS):** Two-step implementation:
  1. **Filter predicate:** Inline table-valued function returning 1/0 based on condition (e.g., `WHERE @TenantName = USER_NAME() OR USER_NAME() = 'TenantAdmin'`). Uses `SCHEMABINDING`.
  2. **Security policy:** Binds predicate function to table: `CREATE SECURITY POLICY ... ADD FILTER PREDICATE function(column) ON table WITH (STATE = ON/OFF)`.
  - RLS blocks SELECT, UPDATE, DELETE on filtered rows. INSERT is not affected.
  - Transparency: User queries table normally, engine applies filter automatically.
  - Side-channel attack risk: Attackers may infer data through divide-by-zero errors or other exceptions in WHERE clauses.
  - Best practices: Separate schema for predicate functions, avoid type conversions, minimize joins/recursion in predicates.
- **Column-Level Security (CLS):** GRANT SELECT on entire table to role, then DENY SELECT on specific column. Example: `DENY SELECT ON dbo.Patients (MedicalHistory) TO Receptionist`.
  - CLS vs views comparison:
    | Aspect | CLS | Views |
    |---|---|---|
    | Granularity | Per-column per-role | Need separate views per permission set |
    | Maintenance | Auto-adapts to table structure | Need updates on schema changes |
    | Performance | Direct table access (efficient) | Potential overhead for complex views |
    | Transparency | User queries table directly | User must query different object |
    | Flexibility | Column access only | Can add row filtering (WHERE), calculated columns, transformations |
- **SQL granular permissions:** GRANT, REVOKE, DENY on tables and views (SELECT, INSERT, UPDATE, DELETE) and on functions/stored procedures (ALTER, CONTROL). DENY supersedes GRANT.
- **Principle of least privilege:** Users/applications should only have permissions needed for their task. Example: if app accesses data through stored procedures, grant only EXECUTE on procedures, not table SELECT.
- **Dynamic SQL:** Query built programmatically. Use `QUOTENAME()` to safely quote identifiers (prevents SQL injection). Use `sp_executesql` for parameterized execution. Example:
  ```sql
  CREATE PROCEDURE sp_TopTenRows @tableName NVARCHAR(128)
  AS
  DECLARE @query NVARCHAR(MAX) = N'SELECT TOP 10 * FROM ' + QUOTENAME(@tableName);
  EXEC sp_executesql @query;
  ```

**Architectural Logic**
Security is layered so that each layer addresses a different scope: workspace roles control who can access the workspace at all, item permissions control who can access a specific warehouse, and T-SQL granular security controls what data within the warehouse each user can see or modify. Security policies (DDM, RLS, CLS) are enforced at the query engine level — regardless of whether the user connects via SQL editor, SSMS, the SQL analytics endpoint, or Power BI. The DENY permission always overrides GRANT, providing a reliable way to enforce restrictions even when users belong to multiple roles.

**Implementation Workflow**
1. Assign users to workspace roles (Admin/Member/Contributor/Viewer) for broad access.
2. Grant item permissions (Read, ReadData, ReadAll) for granular warehouse sharing.
3. Apply DDM on sensitive columns: `ALTER TABLE ... ALTER COLUMN ... ADD MASKED WITH (FUNCTION = '...')`.
4. Implement RLS: create filter predicate function, then create security policy binding it to table.
5. Implement CLS: GRANT SELECT on table, DENY SELECT on sensitive columns.
6. Use GRANT/REVOKE/DENY for SQL granular permissions on tables, views, procedures, functions.
7. For dynamic SQL, always use QUOTENAME() and sp_executesql to prevent SQL injection.

**Exam Gotchas & Distinctions**
- **DDM does not change physical data:** Masking applies to query results only. Data in the Delta Parquet files remains unmasked. Users with ReadAll permission or direct OneLake access can bypass DDM.
- **DDM side-channel risk:** Unprivileged users may infer masked values through conditional logic (e.g., causing divide-by-zero if condition is met) — DDM is not a standalone security measure.
- **RLS requires both function + policy:** The inline table-valued function defines the predicate. The security policy binds it to a table. Both are required — neither alone enforces row filtering.
- **RLS INSERT is not affected:** RLS filter predicates apply to SELECT, UPDATE, DELETE. INSERT operations are not filtered by RLS.
- **DENY overrides GRANT:** If a user is granted a permission through one role and denied through another, DENY wins. Critical for security design.
- **CLS vs views choice:** CLS is simpler for column-only restrictions but cannot transform data or filter rows. Views are more flexible but require users to query a different object.
- **Separate schema for RLS objects:** Best practice to keep security functions and policies in their own schema (e.g., `Sec`).
- **Dynamic SQL requires QUOTENAME:** Without QUOTENAME, table/column names in dynamic SQL are vulnerable to SQL injection. `sp_executesql` provides parameterized execution for value parameters.
- **Security policies apply across all access methods:** RLS/CLS/DDM enforced regardless of whether user connects via SQL editor, SSMS, or SQL analytics endpoint. Same policies on warehouse and endpoint.
