## Card 1: Warehouse vs SQL Analytics Endpoint

### What It Is

Fabric provides two distinct T-SQL access layers for data in OneLake. The Warehouse is a fully managed relational database that supports full read-write T-SQL capabilities including DDL, DML, MERGE, and ACID transactions. The SQL Analytics Endpoint is a read-only T-SQL interface that allows you to query Lakehouse Delta tables without modifying them. Both endpoints support views, stored procedures, and SQL-based security, but they serve fundamentally different use cases.

### Key Details

#### Warehouse Capabilities
- Full DDL support: you can CREATE, ALTER, and DROP tables, schemas, and other objects directly in the warehouse.
- Full DML support: INSERT, UPDATE, DELETE, and MERGE statements are all available for data manipulation.
- ACID transactions ensure data integrity across concurrent operations, which is critical for reliable ETL pipelines.
- You can create stored procedures, user-defined functions, and views that encapsulate complex business logic.
- Supports cross-database querying using three-part naming within the same workspace, allowing you to join data across multiple warehouses and lakehouses.

#### SQL Analytics Endpoint Capabilities
- Read-only access to Delta tables stored in a Lakehouse, meaning you cannot run INSERT, UPDATE, DELETE, or MERGE against those tables.
- Full T-SQL query support including SELECT, JOIN, GROUP BY, window functions, CTEs, and stored procedures for read operations.
- Views and stored procedures can be created for read-only reporting and analytical queries.
- Useful when you want to provide a SQL interface over lakehouse data without exposing write capabilities to certain users.

#### Comparison of Capabilities

| Capability | Warehouse | SQL Analytics Endpoint |
|---|---|---|
| DDL (CREATE/ALTER/DROP) | Yes | No |
| DML (INSERT/UPDATE/DELETE) | Yes | No |
| MERGE | Yes | No |
| ACID Transactions | Yes | No |
| SELECT Queries | Yes | Yes |
| Views & Stored Procs | Yes (read-write) | Yes (read-only) |
| SQL Security | Yes | Yes |

#### When to Use Each
- Use a **Warehouse** when you need a traditional data warehouse with full write capabilities, ACID transactions, and ETL pipelines that modify data in place.
- Use a **SQL Analytics Endpoint** when you want a read-only SQL interface over your Lakehouse Delta tables for reporting and ad-hoc querying without risking accidental data modification.

### Exam Gotchas
- Do not confuse the SQL Analytics Endpoint with the Warehouse. The endpoint is read-only and cannot perform any DML or DDL operations.
- Both endpoints support stored procedures and views, but the write capabilities differ fundamentally.
- The SQL Analytics Endpoint is automatically created when you create a Lakehouse, but it is a separate object with its own connection string and permissions.

## Card 2: Dimensional Modeling

### What It Is

Dimensional modeling is a design technique used in data warehousing to organize data into structures that optimize analytical query performance. It involves two primary table types: fact tables that store measurable business events and dimension tables that store descriptive context. The most common layout is a star schema, which places a fact table at the center with directly related dimension tables around it.

### Key Details

#### Fact Tables
- Fact tables store numerical measures that represent business events such as sales amounts, order quantities, or transaction counts.
- They contain foreign keys that reference the primary keys of dimension tables, forming the relationships in the schema.
- Fact tables typically have the largest row counts in the warehouse because they record every individual business event.
- Additive measures can be summed across all dimensions, semi-additive measures can be summed across some but not all dimensions, and non-additive measures such as ratios cannot be summed meaningfully.

#### Dimension Tables
- Dimension tables store descriptive attributes that provide context for the facts, such as product names, customer demographics, or geographic regions.
- A surrogate key is an internally generated identifier, typically an auto-incrementing integer, used as the primary key in the dimension table.
- An alternate key is a business identifier such as a product SKU or customer account number that also uniquely identifies a record but is not used as the primary key.
- Dimension tables are typically much smaller than fact tables and contain far fewer rows.

#### Star Schema vs Snowflake Schema
- A star schema consists of a fact table directly connected to each dimension table with no further normalization. This denormalized structure minimizes the number of joins required for queries and improves read performance.
- A snowflake schema normalizes dimension tables into sub-dimension tables, reducing data redundancy but requiring multiple join hops to retrieve attributes from deeper levels of the hierarchy.
- Star schemas are generally preferred for data warehouses because they simplify queries and improve performance, while snowflake schemas are used when storage efficiency or strict normalization is required.

#### Slowly Changing Dimensions (SCD)
- SCD Type 0 retains the original value permanently and never applies any changes after the initial insert.
- SCD Type 1 overwrites the previous value with the new value, discarding all history.
- SCD Type 2 adds a new row whenever a tracked attribute changes, preserving full historical context by including effective date, expiry date, and a current flag.
- SCD Type 3 adds a new column to store the previous value, allowing limited history tracking.
- SCD Type 4 uses a separate history table to store changes while the main dimension table always contains the current state.
- SCD Type 5 combines Types 1 and 4, overwriting in the main table and appending changes to a history table.
- SCD Type 6 combines Types 1, 2, and 3 by maintaining a current row with an added column for the previous value while also creating new rows for each change.
- For the exam, SCD Type 2 is the most commonly tested because it preserves full history and requires careful management of effective dates and flags.

#### Time Dimension
- A time dimension is a specialized dimension table that provides a calendar-based breakdown of dates, including attributes such as day of week, month name, fiscal quarter, and holiday flags.
- It allows analysts to filter and group data by calendar periods without writing complex date calculations in every query.

#### Staging Tables
- Staging tables are temporary tables used during the ETL process to hold intermediate data before it is transformed and loaded into the final fact and dimension tables.
- They allow you to validate, clean, and reshape incoming data without modifying the production warehouse tables directly.

#### APPROX_COUNT_DISTINCT
- APPROX_COUNT_DISTINCT uses the HyperLogLog algorithm to estimate the number of distinct values in a column without scanning every row.
- It provides results with approximately two percent error, which is acceptable for large datasets where exact counts are computationally expensive.
- It is significantly faster than COUNT(DISTINCT ...) for very large tables because it avoids the overhead of maintaining a complete set of unique values.

### Exam Gotchas
- Star schema is generally preferred for query performance, while snowflake schema is preferred for storage normalization. Know when each is appropriate.
- SCD Type 2 creates new rows for every change, which increases row count but preserves full history. Always track effective and expiry dates.
- APPROX_COUNT_DISTINCT trades accuracy for performance. It is ideal for large datasets where a two percent error margin is acceptable.
- Staging tables are not part of the final schema. They exist only during the ETL process and should be dropped or truncated afterward.
- A fact table's grain defines what each row represents. Changing the grain changes the entire schema design.

## Card 3: Fabric Warehouse Architecture

### What It Is

A Fabric Warehouse is a fully managed relational database that runs on the Microsoft Fabric platform and stores all data in Delta format on OneLake. It provides auto-scaling compute that adjusts resources based on query demand, and it supports full T-SQL capabilities including DDL, DML, and MERGE operations. The warehouse abstracts the underlying infrastructure so you do not need to manage servers, storage, or scaling manually.

### Key Details

#### Storage and Compute
- All data in a Fabric Warehouse is stored in Delta format on OneLake, which means it is compatible with other Fabric engines such as Data Engineering and Data Science.
- Compute resources scale automatically based on query complexity and concurrent workload, eliminating the need for manual scaling decisions.
- The separation of storage and compute allows you to independently manage costs for each component.

#### Full T-SQL Support
- DDL operations such as CREATE TABLE, ALTER TABLE, and DROP TABLE are fully supported for schema management.
- DML operations including INSERT, UPDATE, DELETE, and MERGE are available for data manipulation.
- ACID transactions ensure that all operations are atomic, consistent, isolated, and durable, which is essential for reliable data pipelines.

#### Cross-Database Querying
- Cross-database queries use three-part naming in the format database.schema.table to reference objects across databases.
- This capability is limited to databases within the same workspace. You cannot query across databases in different workspaces using three-part naming.
- For cross-workspace scenarios, you need to use shortcuts or copy data between workspaces.

#### Table Clones
- Table clones create a zero-copy reference to an existing table using the CREATE TABLE ... CLONE command.
- The clone shares the same underlying Delta files as the original table, so no additional storage is consumed.
- Clones are metadata-only operations that complete almost instantly regardless of table size.
- Changes to the original table after cloning are not reflected in the clone, as the clone captures a point-in-time snapshot.

#### Tool Connectivity
- Fabric Warehouse supports connectivity from SQL Server Management Studio (SSMS), Azure Data Studio (ADS), and any tool that uses the Tabular Data Stream (TDS) protocol.
- Authentication requires Microsoft Entra ID. SQL authentication is not supported.
- The standard connection port is 1433, which is the default TDS port.

#### Ingestion Methods
- The COPY INTO statement is the primary method for loading data from external files into the warehouse. It supports authentication using CREDENTIAL objects for accessing storage accounts.
- OPENROWSET allows you to query external data sources directly without importing the data first, which is useful for ad-hoc exploration.
- CTAS (Create Table As Select) creates a new table based on the results of a SELECT statement, which is useful for transforming and loading data in a single operation.
- INSERT...SELECT loads data from an existing table into another table within the warehouse.
- Data Pipelines in Fabric provide orchestrated data movement and transformation workflows that can load data into the warehouse on a schedule.
- Dataflows Gen2 provide a low-code, visual approach to data transformation and loading.
- Cross-database queries allow you to pull data from other databases in the same workspace during the ingestion process.

#### ETL Process and Loading Patterns
- The ETL (Extract, Transform, Load) process in a warehouse typically involves extracting data from source systems, transforming it to match the target schema, and loading it into fact and dimension tables.
- A full load replaces all existing data in the target table with a complete copy of the source data, which is simpler but slower for large datasets.
- An incremental load only processes new or changed records since the last load, which is more efficient but requires tracking changes using timestamps, change data capture, or watermarks.

### Exam Gotchas
- Cross-database queries using three-part naming only work within the same workspace. Cross-workspace querying requires different approaches.
- Table clones are zero-copy and metadata-only. They do not duplicate data, but they capture a point-in-time snapshot.
- Entra ID is the only supported authentication method for Fabric Warehouse connections. SQL authentication is not available.
- The COPY INTO command requires CREDENTIAL objects for accessing external storage. You cannot use anonymous access for production scenarios.
- Full loads are simpler but less efficient than incremental loads. Know when each pattern is appropriate.

## Card 4: Querying the Warehouse

### What It Is

Fabric provides multiple interfaces for querying warehouse data, including a SQL query editor with IntelliSense and Copilot support, a visual query editor for drag-and-drop query building, and a results toolbar for exporting and visualizing query output. Additionally, ranking functions such as ROW_NUMBER, RANK, DENSE_RANK, and NTILE enable advanced analytical queries within T-SQL.

### Key Details

#### SQL Query Editor
- The SQL query editor in the Fabric portal provides IntelliSense for code completion, syntax highlighting, and error detection.
- Copilot integration allows you to generate queries using natural language descriptions and explain existing queries in plain language.
- A preview of up to ten thousand rows is available directly in the editor for quick data exploration without running a full query.
- You can save queries for reuse and share them with other workspace members.

#### Visual Query Editor
- The visual query editor provides a drag-and-drop interface for building queries without writing T-SQL manually.
- It automatically generates the corresponding T-SQL code as you add tables, select columns, and define join conditions.
- This interface is useful for users who are less familiar with SQL syntax but need to explore and analyze warehouse data.

#### Results Toolbar
- The results toolbar provides several actions for working with query output.
- You can open results directly in Excel for further analysis and formatting.
- The Explore data option allows you to drill into the result set interactively.
- The Visualize results option generates quick charts from the result set, but it does not support queries that use ORDER BY clauses.
- You can save query results as a new view or table for reuse and reference.

#### Ranking Functions
- ROW_NUMBER assigns a unique sequential integer to each row within a partition, starting at one for the first row. Rows with identical values receive different numbers.
- RANK assigns the same rank to rows with identical values, but it leaves gaps in the ranking sequence. For example, if two rows tie for rank two, the next row receives rank four.
- DENSE_RANK assigns the same rank to rows with identical values without leaving gaps. If two rows tie for rank two, the next row receives rank three.
- NTILE divides the result set into a specified number of roughly equal groups and assigns a group number to each row. For example, NTILE(4) splits the results into quartiles.

#### Snowflake Schema Querying
- Querying a snowflake schema requires joining through every hop in the normalized dimension hierarchy to retrieve attributes from sub-dimension tables.
- For example, if a product dimension is normalized into a category table and a subcategory table, you must join the fact table to the product dimension, then to the subcategory table, then to the category table.
- This adds complexity and can impact query performance compared to star schemas where dimensions are denormalized.

#### SSMS Connection
- Connecting to a Fabric Warehouse from SQL Server Management Studio requires specifying the database name in the connection dialog.
- The connection must use port 1433, which is the default TDS port for SQL Server connectivity.
- Authentication is handled exclusively through Microsoft Entra ID. You cannot use SQL Server authentication or Windows authentication.

### Exam Gotchas
- The Visualize results option in the results toolbar does not support queries with ORDER BY clauses. If your query includes ORDER BY, you must remove it before using this feature.
- RANK leaves gaps in the ranking sequence when there are ties, while DENSE_RANK does not. This distinction is commonly tested.
- ROW_NUMBER guarantees a unique number for every row even when values are identical, making it useful for deduplication scenarios.
- Snowflake schema queries require joining through every normalization hop. This can be complex and slow compared to star schema queries.
- SSMS connections require Entra ID authentication, port 1433, and a database name. SQL authentication is not supported.

## Card 5: Data Modeling and Semantic Layer

### What It Is

Data modeling in Fabric involves defining relationships, measures, and business-friendly metadata on top of your warehouse tables to create a semantic layer. This semantic layer, known as the semantic model, enables tools like Power BI to interpret your data through a consistent business lens. The model view in the Fabric portal provides a visual interface for managing these definitions, and Direct Lake mode allows Power BI reports to read Delta Parquet files directly from OneLake without requiring a separate refresh.

### Key Details

#### Model View Actions
- You can hide staging objects in the model view to declutter the interface and present only the tables and columns that matter for business reporting.
- Renaming columns to business-friendly names ensures that report consumers see meaningful labels such as "Total Revenue" instead of cryptic column names like "rev_amt_usd."
- Adding descriptions to tables and columns enables Copilot to generate more accurate and contextually relevant queries and explanations.

#### Relationships
- Relationships in the semantic model define how tables connect to each other, typically using a many-to-one cardinality where the many side is the fact table and the one side is the dimension table.
- The single cross-filter direction means that filters flow from the one side to the many side, which is the standard behavior for star schema models.
- Bidirectional cross-filtering is available but should be used sparingly because it can produce unexpected results and ambiguous filter propagation.

#### Views
- Views in the warehouse provide a stable, standardized T-SQL interface over underlying tables, allowing you to change the physical schema without breaking reports and queries that depend on the view.
- They serve as a consistent source for reports, ensuring that downstream consumers always query the same logical structure even as the underlying data model evolves.

#### DAX Measures
- DAX measures are reusable calculations defined in the semantic model that serve as a single source of truth for business metrics.
- Common measures include total revenue, year-over-year growth, and customer retention rates, all defined once and referenced across multiple reports.
- Defining measures in the semantic model rather than in individual reports ensures consistency and reduces duplication.

#### Semantic Model and Direct Lake Mode
- The semantic model in Fabric uses Direct Lake mode to read Delta Parquet files directly from OneLake.
- Direct Lake mode eliminates the need for a separate data refresh because the semantic model always reads the latest data from the Delta files.
- This approach combines the query performance of import mode with the real-time data availability of live connectivity, providing the best of both approaches.

#### Copilot Benefits of Modeling
- A well-defined semantic model with clear relationships, descriptions, and measures enables Copilot to generate more accurate queries and explanations.
- Copilot uses the model metadata to understand business context, which improves the quality of generated T-SQL and DAX expressions.
- Without a semantic model, Copilot must infer relationships and meanings from raw column names, which often produces less relevant results.

### Exam Gotchas
- The model view is where you define business-friendly names and descriptions. These definitions directly impact Copilot's ability to generate accurate queries.
- Direct Lake mode reads Delta files directly from OneLake and does not require a refresh. This is a key differentiator from import mode.
- Single cross-filter direction is the default and recommended setting. Bidirectional filtering should only be used when absolutely necessary.
- DAX measures defined in the semantic model serve as a single source of truth. Defining measures in individual reports leads to inconsistency.
- Hiding staging objects in the model view does not delete them. It only removes them from the visual interface.

## Card 6: Copilot for Data Warehouse

### What It Is

Copilot in Fabric Data Warehouse is an AI-powered assistant that helps you write, understand, and debug T-SQL queries using natural language. It provides code completion through ghost text suggestions, a chat pane for interactive assistance, and quick actions that explain or fix queries. Copilot retains session context, allowing you to ask follow-up questions without repeating prior information.

### Key Details

#### Prerequisites
- Copilot requires a Fabric capacity of F2 or higher to function. Free and trial capacities do not support Copilot.
- Copilot currently supports English only. Other languages are not supported for natural language interactions.
- Copilot must be enabled at the tenant level by a Fabric administrator. If it is not enabled, the features will not appear in the workspace.

#### Code Completion
- Copilot provides ghost text suggestions as you type T-SQL queries, predicting the rest of your code based on the context of your query and your schema.
- You can press Tab to accept the ghost text suggestion and continue editing, or you can ignore it and continue typing your own code.
- The suggestions are context-aware, meaning they consider your existing schema, table names, column names, and query structure.

#### Comments to Guide Copilot
- You can write natural language comments at the top of your query using the double-dash T-SQL comment syntax to guide Copilot's code generation.
- For example, writing a comment that describes the business logic you need will cause Copilot to generate a query that matches your description.
- The comments serve as instructions that Copilot interprets alongside your schema to produce relevant T-SQL code.

#### Chat Pane
- The chat pane provides an interactive interface where you can ask Copilot questions about your data and queries using natural language.
- The slash command generate-sql creates a new query based on your natural language description.
- The slash command explain analyzes an existing query and provides a plain language explanation of what each part of the code does.
- The slash command fix attempts to identify and correct errors in a query that has failed to execute.
- The slash command question allows you to ask general questions about your data warehouse, schema, or T-SQL concepts.
- The slash command help provides information about Copilot's available features and usage patterns.
- Copilot retains the context of your current session, so follow-up questions do not require you to re-explain prior interactions.

#### Quick Actions
- The Explain quick action adds inline comments to your existing query that describe what each section of the code accomplishes.
- The Fix quick action only activates after a query execution error. It analyzes the error message and suggests corrections to resolve the issue.
- Quick actions appear as contextual buttons near your query or error message, providing one-click access to common Copilot capabilities.

#### Best Practices
- Use descriptive schema and table names so that Copilot can better understand your data model and generate more accurate queries.
- Define clear relationships in your semantic model so that Copilot understands how tables connect and can generate correct join logic.
- Write clear, specific comments at the top of your queries to guide Copilot toward the exact business logic you need.
- Review Copilot-generated code carefully before executing it. AI-generated queries may contain logical errors or performance issues that require human judgment.

### Exam Gotchas
- Copilot requires F2 capacity or higher. It does not work on free or trial capacities.
- Copilot only supports English. Other languages are not supported for natural language interactions.
- Copilot must be enabled at the tenant level. It is not available by default in all environments.
- The Fix quick action only activates after a query error. It does not proactively suggest fixes for queries that have not yet been executed.
- Copilot retains session context, so you do not need to repeat prior information in follow-up questions.
- Ghost text suggestions are context-aware. They consider your schema, table names, and existing query structure.

## Card 7: Monitoring and Security

### What It Is

Monitoring in Fabric Warehouse involves tracking query performance, resource usage, and system health using Dynamic Management Views (DMVs), Query insights, and the Capacity Metrics app. Security in Fabric Warehouse encompasses workspace roles, item permissions, Dynamic Data Masking (DDM), Row-Level Security (RLS), Column-Level Security (CLS), and SQL granular permissions. Together, these capabilities ensure that you can observe system behavior and control access to sensitive data.

### Key Details

#### Dynamic Management Views (DMVs)
- DMVs provide real-time visibility into active connections, sessions, and requests executing on the warehouse.
- The sys.dm_exec_connections view returns information about established connections, including connection ID, authentication method, and encryption status.
- The sys.dm_exec_sessions view returns information about active sessions, including user identity, login time, and client interface.
- The sys.dm_exec_requests view returns information about currently executing queries, including query text, status, wait type, and resource consumption.
- To terminate a running query, you use the KILL command with the session ID. Only users with Admin permissions can execute the KILL command.

#### Query Insights
- Query insights provide historical performance data for queries executed on the warehouse, allowing you to identify slow queries and optimize performance.
- Historical data is retained for thirty days, after which it is automatically purged.
- There can be up to a fifteen-minute delay between query execution and the appearance of insights data, so real-time monitoring requires DMVs instead.
- Query insights perform parameterized deduplication, which groups similar queries that differ only in parameter values into a single entry to reduce noise and improve readability.

#### Capacity Metrics App
- The Capacity Metrics app provides a centralized dashboard for monitoring Fabric capacity usage across workspaces and items.
- It displays metrics such as CPU utilization, memory consumption, and query execution time for each item.
- This app is useful for identifying capacity bottlenecks and planning capacity upgrades.

#### Workspace Roles
- The Admin role has full control over the workspace, including the ability to manage permissions, settings, and all items.
- The Member role can manage workspace settings and content but cannot manage permissions for other users.
- The Contributor role can create, modify, and delete content within the workspace but cannot manage workspace settings.
- The Viewer role has read-only access to workspace content and cannot create or modify any items.

#### Item Permissions
- The Read permission allows a user to view an item but does not grant access to the underlying data.
- The ReadData permission allows a user to read the data within an item, such as querying tables in a warehouse.
- The ReadAll permission grants unrestricted read access to all data within an item, including all tables, views, and stored procedures.

#### Dynamic Data Masking (DDM)
- Dynamic Data Masking masks query results at the query layer, replacing sensitive values with masked output such as "XXXX" or random characters.
- DDM does not change the physical data stored in the warehouse. The original data remains intact and unmodified.
- There is a side-channel risk because the masking is applied at the application layer. Users with direct access to the underlying Delta files or with elevated permissions may be able to bypass the masking.
- DDM is configured on individual columns using the MASKED WITH clause in the CREATE TABLE or ALTER TABLE statement.

#### Row-Level Security (RLS)
- Row-Level Security restricts which rows a user can see in a table based on their identity or role membership.
- RLS is implemented in two steps: first, you define a filter predicate function that returns true for rows the user is allowed to see, and second, you apply a security policy to the table that invokes the filter predicate.
- INSERT statements are not affected by RLS. A user can insert any row regardless of the security policy, but they can only query rows that pass the filter predicate.
- RLS applies to SELECT, UPDATE, and DELETE operations but does not prevent INSERT operations.

#### Column-Level Security (CLS)
- Column-Level Security restricts access to specific columns in a table by first granting access to the table and then denying access to the sensitive columns.
- The GRANT statement provides access to the table or a subset of columns, and the DENY statement revokes access to specific columns, overriding the GRANT for those columns.
- Views can be used as an alternative to CLS by creating a view that exposes only the non-sensitive columns, but CLS provides direct column-level control without creating additional objects.

#### SQL Granular Permissions
- In SQL permission hierarchies, DENY always takes precedence over GRANT. If a user has both GRANT and DENY on the same object or column, the DENY wins.
- This means that even if a user is granted access through a role, an explicit DENY on a specific object or column will block their access.

#### Dynamic SQL and Security
- Dynamic SQL can introduce SQL injection vulnerabilities if user input is concatenated directly into query strings.
- The QUOTENAME function wraps identifiers in square brackets or quotes to prevent injection attacks by ensuring that user input is treated as a literal value rather than executable code.
- Always use parameterized queries or QUOTENAME when incorporating user input into dynamic SQL statements.

### Exam Gotchas
- DMVs provide real-time data, while Query insights provide historical data with up to a fifteen-minute delay. Know which to use for each scenario.
- Only users with Admin permissions can execute the KILL command to terminate running queries.
- DDM masks query results but does not modify physical data. There is a side-channel risk because the masking is applied at the application layer.
- RLS does not affect INSERT statements. A user can insert any row but can only query rows that pass the filter predicate.
- DENY always overrides GRANT in SQL permission hierarchies. This is a common exam scenario.
- Query insights retain data for thirty days and perform parameterized deduplication to group similar queries.
- Use QUOTENAME in dynamic SQL to prevent injection attacks by treating user input as literal values.
