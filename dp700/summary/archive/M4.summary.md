# M4.1.md

## Core Concept
Microsoft Fabric is a unified, end-to-end analytics platform that integrates data engineering, data warehousing, data science, real-time analytics, and business intelligence into a single SaaS environment built on OneLake.

## Technical Specifications
*   Unified Platform: Integrates various tools and services (Power BI, Azure Synapse Analytics, Azure Data Factory) into one SaaS product.
*   OneLake: Centralized, open-format data storage built on ADLS Gen2. Supports Delta, Parquet, CSV, JSON. Eliminates data silos by allowing compute engines to access data without movement/duplication. Uses Shortcuts for external data access.
*   Workspaces: Logical containers for organizing and managing data, reports, and assets. Provide separation of resources, access control, Git integration, and compute resource management.
*   Administration & Governance: Centralized in the Admin portal. Manages permissions, data sources, gateways, usage. OneLake catalog aids in governance (sensitivity labels, metadata, refresh status).
*   Collaboration: Facilitates teamwork by removing silos. Data engineers, analytics engineers, data analysts, data scientists, and low-code users can collaborate.
*   AI Capabilities: Data processed in Fabric is available for AI workloads (Copilot, data agents, Fabric IQ). Fabric IQ unifies data using ontologies for consistent business language. Foundry IQ accesses enterprise knowledge. Work IQ captures collaboration signals.
*   Copilot: Generative AI assistant across workloads for code completion/generation, data transformation guidance, report/insight generation.
*   Workloads: Data Engineering, Data Factory, Data Warehouse, Real-Time Intelligence, Industry Solutions, Data Science, Databases, IQ (preview), Power BI.

## Architectural Logic (The "Why")
Fabric simplifies analytics by providing a single, integrated platform, reducing complexity, governance gaps, and duplicated effort associated with separate tools. Centralizing data in OneLake ensures scalability, cost-effectiveness, and accessibility, while enabling AI workloads to leverage the same governed data as analytics. This unified approach fosters collaboration among different data roles.

## Implementation Workflow
1.  Enable Fabric for the organization (requires Fabric Admin, Power Platform Admin, or Global Admin).
2.  Create workspaces for collaboration and resource management.
3.  Configure workspace settings (license type, OneDrive access, ADLS Gen2 connection, Git integration, Spark settings).
4.  Manage workspace access using roles (admin, contributor, member, viewer) or item-level permissions.
5.  Use the OneLake catalog to discover and access data sources.
6.  Create items within workloads (e.g., lakehouses in Data Engineering, pipelines in Data Factory, reports in Power BI).
7.  Leverage AI capabilities like Copilot and Fabric IQ.

## Exam "Gotchas" & Distinctions
*   OneLake is the *storage layer* for Fabric; it's not a compute engine itself.
*   Distinguish between Fabric workloads (e.g., Data Engineering vs. Data Factory).
*   Understand that Fabric integrates capabilities from Azure Data Factory and Azure Synapse Analytics.
*   Recognize that AI capabilities (Copilot, Fabric IQ) are built upon the governed data prepared within Fabric.
*   Workspaces are key for organization, security, and collaboration.
*   Fabric supports a data mesh architecture with centralized governance.

# M4.2.md

## Core Concept
A data warehouse in Microsoft Fabric is a fully managed, enterprise-scale relational database built on OneLake, offering full T-SQL capabilities and integrating seamlessly with other Fabric workloads.

## Technical Specifications
*   Foundation: Built on OneLake, uses Delta format for data storage.
*   T-SQL Support: Full transactional capabilities (DDL/DML like CREATE, ALTER, DROP, INSERT, UPDATE, DELETE, MERGE). ACID compliant.
*   Dimensional Modeling: Supports star and snowflake schemas with Fact and Dimension tables. Fact tables contain quantitative data; Dimension tables provide descriptive attributes and keys (surrogate, alternate).
*   Slowly Changing Dimensions (SCD): Supports types 0-6, with Type 1 (overwrite) and Type 2 (add new records) being common. Tracks changes to dimension attributes over time.
*   Key Capabilities: Full T-SQL, fully managed, OneLake integration, cross-database querying (warehouse-to-lakehouse using 3-part naming), familiar tooling (SSMS, Azure Data Studio), Copilot assistance.
*   Warehouse vs. SQL Analytics Endpoint: Warehouse supports read/write T-SQL and table creation (DDL). SQL analytics endpoint provides read-only SQL access to Lakehouse Delta tables.
*   Ingestion: COPY INTO (bulk load from Azure storage), OPENROWSET (query external/OneLake files), Pipelines/Dataflows Gen2, cross-database queries (CTAS, INSERT...SELECT). Staging tables are common for ETL.
*   Table Clones: Zero-copy clones for development, testing, recovery, or historical snapshots.
*   Querying: SQL query editor (T-SQL, IntelliSense, Copilot), Visual query editor (no-code graphical interface). Client tools (SSMS, ADS) via TDS connection.
*   Modeling: Prepare tables (hide internal objects, rename columns, add descriptions), define relationships (cardinality, cross-filter direction), standardize access with Views and Measures. Create semantic models for Power BI (Direct Lake mode).
*   Security: Workspace roles, item permissions, granular SQL security (RLS, CLS, DDM).
*   Monitoring: Capacity Metrics app (CU usage, throttling), DMVs (`sys.dm_exec_requests`, etc.), Query Insights (historical query data, `queryinsights.*` views).

## Architectural Logic (The "Why")
Fabric Data Warehouse provides a structured, familiar SQL environment for enterprise analytics, leveraging OneLake's scalability and open format. It bridges the gap between traditional data warehouses and modern data lakes, supporting both traditional BI and AI workloads with integrated tools and security. Dimensional modeling ensures efficient analysis of business data.

## Implementation Workflow
1.  Create a data warehouse in a Fabric workspace.
2.  Design dimensional model (Fact & Dimension tables, consider SCD types).
3.  Ingest data using COPY INTO, Pipelines, Dataflows Gen2, or cross-database queries. Use staging tables.
4.  Create tables using T-SQL `CREATE TABLE` statements.
5.  Load data, often using `COPY INTO` or `INSERT...SELECT`.
6.  Query data using SQL query editor or Visual query editor.
7.  Transform data using Views and Stored Procedures.
8.  (Optional) Create table clones for development/testing.
9.  Model data (clean, rename, describe, define relationships, create views/measures).
10. Publish semantic models for Power BI (Direct Lake).
11. Implement security: Workspace roles, item permissions, granular SQL security (RLS, CLS, DDM).
12. Monitor capacity (Metrics app), activity (DMVs), and query performance (Query Insights).

## Exam "Gotchas" & Distinctions
*   Warehouse = Read/Write T-SQL, table creation. SQL analytics endpoint = Read-only SQL on Lakehouse data.
*   Data stored in Delta format on OneLake.
*   Key benefits: Full T-SQL, OneLake integration, cross-database queries, familiar tooling, Copilot.
*   Dimensional modeling (star/snowflake schemas) is crucial for performance.
*   SCD types are important for tracking changes in dimension data.
*   Security includes workspace roles, item permissions, and granular SQL controls (RLS, CLS, DDM).
*   Monitoring involves capacity metrics, DMVs, and query insights.

# M4.3.md

## Core Concept
Loading data into a Microsoft Fabric data warehouse involves strategies like staging data, using full or incremental loads, and leveraging tools like COPY statements, pipelines, Dataflows Gen2, and cross-database queries.

## Technical Specifications
*   ETL Process: Extract, Transform, Load. Ingestion moves raw data; Loading places transformed data into final tables.
*   Data Storage: Fabric warehouses store data in Delta Parquet format on OneLake.
*   Staging: Auxiliary objects (tables, procedures) used as temporary holding areas to simplify load operations.
*   Load Types:
    *   Full (Initial) Load: Populates warehouse for the first time. Truncates and reloads tables. Easier but longer duration.
    *   Incremental Load: Updates warehouse with changes since the last update. Preserves history, faster than full load, more complex to implement.
*   Keys: Surrogate keys (system-generated, internal to DW) and Business keys (natural/source system identifiers). Crucial for traceability and data integration.
*   Dimension Tables (SCD): Handle changes over time (Type 1, Type 2 most common). Type 2 adds new records for changes, keeping history. Requires change detection mechanisms (CDC, change tracking).
*   Fact Table Loading: Load after dimensions. Look up surrogate keys using business keys. Handle SCDs correctly to match fact events with correct dimension versions.
*   Pipelines: Cloud-based ETL/ELT service. Use Copy Data activity (wizard-driven ingestion from various sources) or Dataflows Gen2 (Power Query transformations). Can be scheduled.
*   T-SQL Loading: `COPY INTO` statement (bulk load from Azure storage - CSV, Parquet; supports SAS/SAK, error handling, multiple files, wildcards). `CREATE TABLE AS SELECT` (CTAS) and `INSERT...SELECT` for loading from other Fabric assets (warehouses, lakehouses) using three-part naming.
*   Dataflows Gen2: Import data, transform with Power Query (no-code), add destinations (Warehouse, Lakehouse, etc.), publish. Supports Copilot for transformations.

## Architectural Logic (The "Why")
Robust data loading strategies are fundamental for data warehouse success, ensuring timely and accurate analytics. Staging data, choosing appropriate load types (full vs. incremental), handling SCDs correctly, and using efficient loading methods (COPY, pipelines, cross-database queries) optimize performance, maintainability, and data quality.

## Implementation Workflow
1.  Design dimension and fact tables, considering keys and SCD types.
2.  Create staging tables if needed.
3.  Choose a loading method:
    *   Pipelines: Use Copy Data assistant for wizard-driven loads or Dataflows Gen2 for complex transformations. Schedule pipelines.
    *   T-SQL: Use `COPY INTO` for bulk loads from Azure storage. Use CTAS/INSERT...SELECT for cross-asset loads.
4.  Implement incremental load logic using change detection if necessary.
5.  Load dimension tables first, then fact tables, ensuring correct key lookups.
6.  Apply post-load optimizations as needed.
7.  Publish Dataflows Gen2 if used for ETL logic.

## Exam "Gotchas" & Distinctions
*   Distinguish between data ingestion and data loading.
*   Staging tables are temporary storage for ETL.
*   Full load vs. Incremental load: Understand trade-offs in complexity, duration, and history preservation.
*   Surrogate keys vs. Business keys: Purpose and use in DW.
*   SCD Types (especially Type 1 and Type 2) are critical for managing dimension changes.
*   Pipelines (orchestration, Copy Data, Dataflows) vs. T-SQL (`COPY INTO`, CTAS, INSERT...SELECT) for loading.
*   Three-part naming (`workspace.warehouse.table`) for cross-asset queries.

# M4.4.md

## Core Concept
Querying a Microsoft Fabric data warehouse involves using T-SQL with tools like the SQL query editor or Visual query editor, leveraging dimensional modeling concepts, and utilizing features like Copilot for assistance.

## Technical Specifications
*   Querying Tools: SQL query editor (T-SQL, IntelliSense, Copilot), Visual query editor (no-code graphical interface). Client tools (SSMS, Azure Data Studio) via TDS connection.
*   T-SQL Capabilities: SELECT, JOIN, aggregate functions (SUM, COUNT, AVG), window functions (ROW_NUMBER, RANK, DENSE_RANK, NTILE), APPROX_COUNT_DISTINCT.
*   Dimensional Modeling Queries: Aggregating measures by dimension attributes, joins across fact and dimension tables (star/snowflake schemas).
*   Ranking Functions: Partitioning data within groups and assigning ranks (ROW_NUMBER, RANK, DENSE_RANK, NTILE).
*   Approximate Counts: `APPROX_COUNT_DISTINCT` for faster, less precise counts on large datasets.
*   Views & Stored Procedures: Save reusable T-SQL logic for standardization and simplifying access. Views for query structure; Stored procedures for repeatable tasks.
*   Copilot Integration: Code completion, query generation from natural language (`/generate-sql`), query explanation (`/explain`), query fixing (`/fix`), general questions (`/question`). Requires specific capacity and tenant settings.
*   Query Results: Preview limited to 10,000 rows. Options to Open in Excel (live connection), Explore data (matrix/visual), Visualize results (basic chart), Copy.
*   Cross-Database Queries: Use three-part naming (`workspace.warehouse.table`) to query across warehouses/lakehouses within the same workspace.
*   Client Tool Connection: Use SQL connection string from Fabric workspace. Requires Microsoft Entra ID authentication. TCP port 1433 must be open.

## Architectural Logic (The "Why")
Effective querying is essential for extracting insights from the data warehouse. T-SQL provides a powerful and flexible language for complex analysis. Tools like Copilot, visual editors, and client integrations streamline the query development process, making data more accessible and actionable for users. Standardizing access with views and measures ensures consistency.

## Implementation Workflow
1.  Open the warehouse in Fabric.
2.  Use the SQL query editor or Visual query editor to write queries.
3.  Leverage T-SQL for filtering, joining, aggregating, and ranking data.
4.  Use `APPROX_COUNT_DISTINCT` for performance on large datasets where precision isn't critical.
5.  Create Views and Stored Procedures to encapsulate reusable logic.
6.  Utilize Copilot for code completion, generation, explanation, and fixing.
7.  Connect client tools (SSMS, ADS) using the provided SQL connection string and Microsoft Entra ID authentication.
8.  Explore query results using provided tools (Excel, Visualize, Copy).
9.  Use cross-database queries (three-part naming) to combine data from different Fabric assets.

## Exam "Gotchas" & Distinctions
*   Distinguish between SQL query editor (code-based) and Visual query editor (no-code).
*   Understand the use cases for ranking functions (ROW_NUMBER, RANK, DENSE_RANK, NTILE).
*   Know when to use `COUNT` vs. `APPROX_COUNT_DISTINCT`.
*   Copilot features (completion, chat, quick actions) require specific capacity and tenant enablement.
*   Results toolbar options: Open in Excel (live connection), Visualize results (basic chart), Explore data.
*   Cross-database queries use three-part naming. Client tools require Microsoft Entra ID authentication.

# M4.5.md

## Core Concept
Copilot in Microsoft Fabric's Data Warehouse enhances productivity by providing AI-powered code completion, natural language to SQL query generation, query explanation, error fixing, and conversational assistance directly within the SQL editor.

## Technical Specifications
*   Prerequisites: Supported Fabric capacity (F2/P1+), specific regions, enabled Copilot tenant switch, warehouse created.
*   Code Completion: Inline, context-aware T-SQL suggestions (ghost text). Accepts via Tab. Alternative suggestions available. Guided by comments (`--`).
*   Copilot Chat Pane: Natural language interaction. `/commands` for specific actions (`/generate-sql`, `/explain`, `/fix`, `/question`, `/help`). Retains conversation context.
*   Quick Actions: "Explain" (adds comments and summary) and "Fix" (resolves errors using query context). Available in the SQL editor ribbon.
*   Best Practices: Craft clear prompts, use expressive schema names, add comments for complex queries, provide context (schema, keys), use English for prompts.
*   Schema Awareness: Uses warehouse schema and metadata for relevant suggestions and query generation. Well-structured schemas improve accuracy.
*   Support: Currently English to T-SQL. Requires specific capacity SKUs (not trial).

## Architectural Logic (The "Why")
Copilot aims to accelerate SQL development and debugging, making data warehousing tasks more accessible and efficient. By understanding schema and user intent, it reduces repetitive coding, improves query accuracy, and aids in understanding complex SQL logic, thus boosting user productivity.

## Implementation Workflow
1.  Ensure prerequisites are met (capacity, tenant settings, permissions).
2.  Open a warehouse and a new SQL query.
3.  Enable Copilot settings if needed.
4.  Use code completion as you type (accept with Tab).
5.  Use comments (`--`) to guide suggestions.
6.  Open the Copilot chat pane to ask questions or use `/commands` for specific actions (e.g., `/generate-sql`, `/explain`, `/fix`).
7.  Use "Explain" and "Fix" quick actions from the editor ribbon.
8.  Follow best practices for prompt crafting and schema naming.

## Exam "Gotchas" & Distinctions
*   Copilot features require specific capacity SKUs (F2/P1+) and tenant enablement. Trial SKUs are NOT supported.
*   Code completion, chat, and quick actions are distinct ways to interact with Copilot.
*   `/commands` are used in the chat pane for specific actions.
*   "Explain" adds comments; "Fix" resolves errors automatically based on context.
*   Schema structure and naming conventions significantly impact Copilot's accuracy.
*   Currently supports English prompts for T-SQL generation.

# M4.6.md

## Core Concept
Monitoring a Microsoft Fabric data warehouse involves tracking capacity utilization (CUs), current activity via DMVs, and query performance using Query Insights.

## Technical Specifications
*   Capacity Monitoring: Microsoft Fabric Capacity Metrics app tracks CU consumption by workload (filter for warehouse activity). Helps manage costs and identify throttling.
*   Current Activity Monitoring (DMVs): System views providing real-time information. Key DMVs:
    *   `sys.dm_exec_connections`: Connection details.
    *   `sys.dm_exec_sessions`: Authenticated session details.
    *   `sys.dm_exec_requests`: Active request details (command, start time, elapsed time).
*   Query Monitoring (Query Insights): Historical, aggregated query data. Views include:
    *   `queryinsights.exec_requests_history`: Details of completed queries.
    *   `queryinsights.long_running_queries`: Query execution time metrics (median elapsed time).
    *   `queryinsights.frequently_run_queries`: Query usage frequency and success/failure counts.
*   Query Insights Notes: Data reflects with a delay (up to 15 mins). Queries with parameterized predicates are aggregated in Query Insights.
*   Query Optimization: Use DMVs (`sys.dm_exec_requests`) to identify long-running queries. Use Query Insights to find frequently run or slow queries for tuning.
*   Permissions: Workspace Admins can use `KILL` command on sessions.

## Architectural Logic (The "Why")
Monitoring is crucial for managing costs (CU usage), optimizing performance (identifying slow queries), ensuring resource availability (detecting throttling), and understanding usage patterns. This allows for proactive management and tuning of the data warehouse environment.

## Implementation Workflow
1.  Install and use the Microsoft Fabric Capacity Metrics app to monitor CU consumption and throttling.
2.  Query DMVs (`sys.dm_exec_connections`, `sys.dm_exec_sessions`, `sys.dm_exec_requests`) to view current activities and identify long-running queries.
3.  Query `queryinsights.*` views (`exec_requests_history`, `long_running_queries`, `frequently_run_queries`) to analyze historical query performance and usage.
4.  Identify slow or frequently run queries based on insights.
5.  Optimize identified queries for better performance and reduced CU consumption.
6.  (If necessary) Use `KILL` command (requires Workspace Admin) to terminate problematic sessions.

## Exam "Gotchas" & Distinctions
*   Capacity Metrics app is for CU usage and throttling.
*   DMVs provide *real-time* activity information.
*   Query Insights provides *historical* query data (with a delay).
*   `queryinsights.long_running_queries` and `queryinsights.frequently_run_queries` are key for performance tuning.
*   Parameterized queries are aggregated in Query Insights.
*   Workspace Admins have elevated privileges for `KILL` commands.

# M4.7.md

## Core Concept
Securing a Microsoft Fabric data warehouse involves multiple layers of protection, including workspace roles, item permissions, granular SQL permissions (RLS, CLS, DDM), and adhering to the principle of least privilege.

## Technical Specifications
*   Security Layers:
    *   Workspace Roles: Admin, Member, Contributor, Viewer for overall workspace access.
    *   Item Permissions: Share specific warehouses with Read, ReadData, ReadAll permissions.
    *   Granular SQL Security (T-SQL):
        *   Object-Level Security: Control access to specific tables, views, stored procedures.
        *   Row-Level Security (RLS): Filter rows based on user context (e.g., `WHERE TenantName = USER_NAME()`). Uses security predicates (filter functions) and security policies.
        *   Column-Level Security (CLS): Restrict access to specific columns. Can use `GRANT`/`DENY` on columns.
        *   Dynamic Data Masking (DDM): Obscures sensitive data in real-time query results without altering stored data. Masking types: default, email, custom text (partial), random. Applied via `ALTER TABLE ... ADD MASKED`.
*   Principle of Least Privilege: Grant only necessary permissions to users and applications. Applications should ideally interact via stored procedures or views with minimal direct table access.
*   Dynamic SQL: Use `sp_executesql` or `QUOTENAME` to safely build queries programmatically, preventing SQL injection.
*   Table and view permissions: SELECT, INSERT, UPDATE, DELETE. `DENY` permissions override `GRANT`.
*   Function and stored procedure permissions: ALTER, CONTROL.
*   Best Practices: Create separate schemas for predicate functions/policies. Avoid type conversions/excessive joins in RLS predicates. Test security changes in safe environments.

## Architectural Logic (The "Why")
Comprehensive security is vital for protecting sensitive data, ensuring compliance, and maintaining data integrity. Layered security controls (from workspace down to column/row level) provide flexibility to enforce appropriate access based on user roles and data sensitivity, while adhering to the principle of least privilege minimizes risk.

## Implementation Workflow
1.  Assign appropriate Workspace Roles to users.
2.  Configure Item Permissions for specific warehouse sharing.
3.  Use T-SQL to implement granular security:
    *   Create tables/views and apply `GRANT`/`DENY` for object-level security.
    *   Implement RLS: Create predicate function, security policy, and apply to tables.
    *   Implement CLS: `GRANT`/`DENY` SELECT on specific columns.
    *   Apply DDM: `ALTER TABLE ... ADD MASKED` for sensitive columns.
4.  Adhere to the principle of least privilege when assigning permissions.
5.  Use dynamic SQL cautiously with parameterization (`sp_executesql`, `QUOTENAME`).
6.  Review and audit permissions regularly.

## Exam "Gotchas" & Distinctions
*   DDM masks data in query results; it doesn't encrypt or change stored data.
*   RLS filters rows based on predicates; CLS restricts column visibility.
*   `DENY` permissions override `GRANT` permissions.
*   Workspace roles vs. Item permissions vs. Granular SQL permissions.
*   Principle of least privilege is a core security concept.
*   Dynamic SQL requires careful handling to prevent SQL injection.
