# M2.1.md

## Core Concept
Microsoft Fabric is a unified, end-to-end analytics platform that integrates data engineering, data warehousing, data science, real-time analytics, and business intelligence into a single SaaS environment built on OneLake.

## Technical Specifications
*   Unified Platform: Integrates various tools and services (Power BI, Azure Synapse Analytics, Azure Data Factory) into one SaaS product.
*   OneLake: Centralized, open-format data storage built on ADLS Gen2. Supports Delta, Parquet, CSV, JSON. Eliminates data silos by allowing compute engines to access data without movement/duplication. Uses Shortcuts for external data access.
*   Workspaces: Logical containers for organizing and managing data, reports, and assets. Provide separation of resources, access control, Git integration, and compute resource management.
*   Administration & Governance: Centralized in the Admin portal. Manages permissions, data sources, gateways, usage. OneLake catalog aids in governance (sensitivity labels, metadata, refresh status).
*   Collaboration: Facilitates teamwork by removing silos. Data engineers, analytics engineers, data analysts, data scientists, and low-code users can collaborate.
*   AI Capabilities: Data processed in Fabric is available for AI workloads (Copilot, data agents, Fabric IQ). Fabric IQ unifies data using ontologies for consistent business language. Foundry IQ accesses enterprise knowledge. Work IQ captures collaboration signals.
*   Copilot: Generative AI assistant across workloads for code completion/generation, data transformation guidance, report/insight generation.
*   Workloads: Data Engineering, Data Factory, Data Warehouse, Real-Time Intelligence, Industry Solutions, Data Science, Databases, IQ (preview), Power BI.

## Architectural Logic (The "Why")
Fabric simplifies analytics by providing a single, integrated platform, reducing complexity, governance gaps, and duplicated effort associated with separate tools. Centralizing data in OneLake ensures scalability, cost-effectiveness, and accessibility, while enabling AI workloads to leverage the same governed data as analytics. This unified approach fosters collaboration among different data roles.

## Implementation Workflow
1.  Enable Fabric for the organization (requires Fabric Admin, Power Platform Admin, or Global Admin).
2.  Create workspaces for collaboration and resource management.
3.  Configure workspace settings (license type, OneDrive access, ADLS Gen2 connection, Git integration, Spark settings).
4.  Manage workspace access using roles (admin, contributor, member, viewer) or item-level permissions.
5.  Use the OneLake catalog to discover and access data sources.
6.  Create items within workloads (e.g., lakehouses in Data Engineering, pipelines in Data Factory, reports in Power BI).
7.  Leverage AI capabilities like Copilot and Fabric IQ.

## Exam "Gotchas" & Distinctions
*   OneLake is the *storage layer* for Fabric; it's not a compute engine itself.
*   Distinguish between Fabric workloads (e.g., Data Engineering vs. Data Factory).
*   Understand that Fabric integrates capabilities from Azure Data Factory and Azure Synapse Analytics.
*   Recognize that AI capabilities (Copilot, Fabric IQ) are built upon the governed data prepared within Fabric.
*   Workspaces are key for organization, security, and collaboration.
*   Fabric supports a data mesh architecture with centralized governance.

# M2.2.md

## Core Concept
A lakehouse in Microsoft Fabric unifies the flexibility of a data lake with the analytical capabilities of a data warehouse, built on OneLake and using Delta Lake tables.

## Technical Specifications
*   Design: Organizes data into `Tables` (Delta Lake tables for structured, SQL-queryable data) and `Files` (raw/semi-structured data in native formats).
*   Delta Lake Tables: Store data in Delta format with ACID transactions, schema enforcement, time travel, efficient updates/deletes. Supports batch and streaming data. Stored in the `Tables` folder.
*   Files Folder: Stores raw data in native formats (CSV, JSON, Parquet, etc.). No schema enforcement, flexible for exploration.
*   Schemas: Enabled by default (e.g., `dbo`). Organize tables into logical groups; support schema-level permissions and cross-workspace queries (workspace.lakehouse.schema.table).
*   Access Modes: Lakehouse Explorer (manage data, upload files, create tables) and SQL Analytics Endpoint (read-only T-SQL queries, create views/functions, apply SQL security).
*   Ingestion Methods: Upload, Load to Table (no-code for CSV/Parquet), Dataflows Gen2, Notebooks (Spark), Data Factory pipelines (Copy data).
*   Shortcuts: Reference data in OneLake or external storage (ADLS Gen2, S3, Dataverse) without copying. Schema shortcuts map entire schemas.
*   Transformation Tools: Notebooks (PySpark, SQL, Scala), Dataflows Gen2 (Power Query), Pipelines (orchestration).
*   Analysis Tools: SQL Analytics Endpoint (T-SQL), Spark Notebooks (Spark SQL/PySpark), Power BI (Direct Lake mode via semantic models).
*   Security: Layered controls - workspace roles, item-level sharing, row/column-level security (SQL endpoint), schema-level permissions. Integrates with Microsoft Purview.
*   Foundation for Intelligent Analytics: Well-structured lakehouse data becomes the foundation that intelligent experiences across Microsoft Fabric depend on.

## Architectural Logic (The "Why")
Lakehouses address the limitations of traditional data lakes (lack of structure/performance) and data warehouses (difficulty with diverse data formats/scaling). They provide a unified platform for storing and analyzing all data types, enabling both traditional analytics and AI workloads. Organizing data into structured `Tables` and raw `Files`, combined with Delta Lake's reliability, ensures data quality and facilitates efficient querying.

## Implementation Workflow
1.  Create a lakehouse in a Fabric workspace.
2.  Organize data into `Tables` (Delta Lake) and `Files` folders.
3.  Ingest data using preferred methods (upload, Load to Table, Dataflows Gen2, Notebooks, Pipelines).
4.  Transform data using Notebooks, Dataflows Gen2, or Pipelines.
5.  Load transformed data into Delta tables.
6.  Query data via the SQL Analytics Endpoint (T-SQL) or Spark Notebooks (Spark SQL/PySpark).
7.  Connect Power BI to the SQL endpoint or create a semantic model for reporting (using Direct Lake mode).
8.  Implement security using workspace roles, item permissions, row/column-level security.
9.  Use shortcuts to integrate external or other OneLake data.

## Exam "Gotchas" & Distinctions
*   Lakehouse = Data Lake Flexibility + Data Warehouse Analytics.
*   Key components: OneLake storage, Delta Lake tables, Files, SQL Analytics Endpoint, Spark compute.
*   Distinguish between `Tables` folder (Delta, schema-enforced, SQL-queryable) and `Files` folder (raw, no schema).
*   Understand the role of Delta Lake (ACID, schema enforcement, time travel).
*   Direct Lake mode in Power BI connects directly to lakehouse data without importing.
*   Shortcuts allow data integration without duplication.

# M2.3.md

## Core Concept
Apache Spark in Microsoft Fabric provides a distributed processing framework for large-scale data analytics, integrated within the Fabric environment.

## Technical Specifications
*   Languages: Java, Scala, Spark R, Spark SQL, PySpark (Python).
*   Spark Pool: Cluster of compute nodes (head node, worker nodes with executors) for distributed processing.
*   Fabric Spark Pools: Starter pool (configurable default) and custom pools. Settings include Node Family (memory optimized), Autoscale, Dynamic Allocation.
*   Runtimes & Environments: Support multiple Spark runtimes (version of Spark, Delta Lake, Python). Custom environments can install specific libraries (PyPI) and configurations.
*   Native Execution Engine: Vectorized engine running Spark operations directly on lakehouse infrastructure (for Parquet/Delta files). Enable via `spark.native.enabled=true` and `spark.shuffle.manager=org.apache.spark.shuffle.sort.ColumnarShuffleManager`.
*   High Concurrency Mode: Shares Spark sessions across multiple users/processes for efficiency. Enable in workspace settings.
*   Automatic MLFlow Logging: Implicit logging of ML experiment activity.
*   Execution: Notebooks (interactive exploration), Spark Job Definitions (automated scripts).
*   DataFrames: Primary data structure for structured data (optimized for distributed processing).
*   Loading Data: Infer schema (`header=True`) or specify explicit schema (`StructType`).
*   Transformations: `select`, `where`, `groupBy`, `aggregrate`, `partitionBy`.
*   Saving Data: `write.mode("overwrite").parquet(...)`, `write.partitionBy(...).parquet(...)`. Delta format preferred.
*   Spark SQL: Query catalog objects (views, tables) using SQL expressions. `createOrReplaceTempView()`, `saveAsTable()`. Delta tables preferred. `spark.catalog.createExternalTable()`.
*   Visualization: Built-in notebook charts and Python graphics libraries (Matplotlib, Seaborn).

## Architectural Logic (The "Why")
Use Spark in Fabric for large-scale data processing, complex transformations, machine learning, and interactive data exploration where performance and scalability are critical. Leverage DataFrames and Spark SQL for structured data manipulation. Utilize notebooks for exploration and Spark Job Definitions for automated workflows. The native execution engine and high concurrency mode optimize performance and resource utilization.

## Implementation Workflow
1.  Create/Configure a Spark Pool (starter or custom) in workspace settings.
2.  Define/Select a Spark Runtime and Environment (including necessary libraries).
3.  (Optional) Enable Native Execution Engine and High Concurrency Mode.
4.  Use a Notebook or create a Spark Job Definition.
5.  Load data into a Spark DataFrame (`spark.read.load(...)`).
6.  Perform transformations using DataFrame API or Spark SQL.
7.  Save processed data (e.g., as Parquet or Delta tables).
8.  Visualize results using built-in charts or Python libraries.

## Exam "Gotchas" & Distinctions
*   Distinguish between DataFrames (distributed) and Pandas DataFrames (in-memory). Use `.toPandas()` for conversions.
*   Understand the difference between managed and external tables in the Spark catalog.
*   Know that Delta Lake format is preferred for tables in Fabric Spark.
*   Be aware of the performance benefits of the Native Execution Engine and partitioning.
*   Recognize that Spark pools and runtimes are configurable at the workspace level and can be restricted by administrators.
*   Understand that Spark jobs are for automated, scheduled tasks, while notebooks are for interactive exploration.

# M2.4.md

## Core Concept
Delta Lake tables in Microsoft Fabric lakehouses provide ACID transactions, schema enforcement, time travel, and efficient data manipulation capabilities, bringing relational database semantics to data lake processing.

## Technical Specifications
*   Format: Open-source storage layer over Parquet data files, with a `_delta_Log` folder containing transaction details (JSON format).
*   Benefits: Relational tables (CRUD operations), ACID transactions, data versioning/time travel, support for batch and streaming data, standard formats (Parquet), interoperability via SQL analytics endpoint.
*   Creation Methods:
    *   Saving DataFrame: `df.write.format("delta").saveAsTable("tablename")` (managed table).
    *   External Table: `df.write.format("delta").saveAsTable("externaltablename", path="Files/path")`. Data files stored in `Files` location.
    *   Metadata Creation: `DeltaTable.create(...)` API or `CREATE TABLE ... USING DELTA` SQL statement.
*   Managed vs. External Tables: Managed tables (default) have metadata and data managed together; deleting the table deletes data. External tables map metadata to a separate file location; deleting the table does not delete data.
*   Optimization:
    *   OptimizeWrite: Enabled by default; reduces small files by writing fewer, larger files. Configurable via `spark.microsoft.delta.optimizeWrite.enabled`.
    *   OPTIMIZE command: Consolidates small Parquet files into larger ones, improving performance. Can apply V-Order.
    *   V-Order: Optimizes Parquet files for faster reads in Fabric compute engines (Power BI, SQL, Spark) via Verti-Scan technology. Enabled by default, small write overhead.
    *   VACUUM command: Removes old data files older than a specified retention period (default 7 days) to save storage.
*   Partitioning: Organize data into subfolders (e.g., `year=2024`) to improve query performance via data skipping. Use when data is very large and partitions are few/large. Avoid for small data or high cardinality columns.
*   Working with Delta Tables in Spark:
    *   Spark SQL: `INSERT`, `UPDATE`, `DELETE`, `SELECT` statements via `spark.sql()` or `%%sql` magic.
    *   Delta API: `DeltaTable.forPath(...)` to modify data via API methods (`update`, `delete`).
*   Time Travel: Query previous versions using `versionAsOf` or `timestampAsOf` options when reading Delta tables. History available via `DESCRIBE HISTORY`.
*   Streaming: Delta tables can be used as sources or sinks for Spark Structured Streaming. Use `ignoreChanges` or `ignoreDeletes` options for updates/deletes. Requires `checkpointLocation` for recovery.

## Architectural Logic (The "Why")
Delta Lake tables provide the reliability and structure of relational databases within a data lake, enabling efficient and robust data processing for both batch and streaming scenarios. Optimizations like OptimizeWrite, OPTIMIZE, V-Order, VACUUM, and partitioning ensure performance and manage storage costs for large datasets. Time travel aids in auditing and recovery.

## Implementation Workflow
1.  Create tables using Spark (saving DataFrames, `DeltaTable.create()`, `CREATE TABLE` SQL) or through Power BI/Dataflows.
2.  Choose between managed (default) or external tables based on data lifecycle needs.
3.  Apply optimizations: Ensure OptimizeWrite is enabled, run OPTIMIZE and VACUUM periodically (manually or scheduled). Consider V-Order for read performance.
4.  Use partitioning strategically for large tables based on query patterns.
5.  Query/modify tables using Spark SQL or the Delta API.
6.  Leverage time travel for historical data access or recovery using `DESCRIBE HISTORY` and `versionAsOf`/`timestampAsOf`.
7.  Integrate with streaming data sources/sinks using Spark Structured Streaming.

## Exam "Gotchas" & Distinctions
*   Delta Lake brings RDBMS features (ACID, schema, time travel) to data lakes.
*   Managed vs. External tables: Deleting external table data requires separate action.
*   Optimizations: OptimizeWrite (write optimization), OPTIMIZE (file compaction), V-Order (read optimization), VACUUM (cleanup old files).
*   Partitioning: Improves read performance for large data, but can harm small data.
*   Time travel requires access to transaction logs and older Parquet files.
*   Streaming support via Spark Structured Streaming requires `checkpointLocation` and careful handling of updates/deletes.

# M2.5.md

## Core Concept
Dataflows Gen2 in Microsoft Fabric are cloud-based ETL tools for building and executing scalable data transformation processes with a visual interface.

## Technical Specifications
*   Supports a wide variety of data source connectors (relational databases, Excel, SharePoint, Salesforce, Spark, Fabric lakehouses).
*   Offers numerous data transformations: Filter/Sort rows, Pivot/Unpivot, Merge/Append queries, Split/Conditional split, Replace values/Remove duplicates, Add/Rename/Reorder/Delete columns, Rank/Percentage calculator, Choose Top N/Bottom N.
*   Data destinations: Lakehouse, Warehouse, SQL database (Fabric, Azure SQL DB, Azure Data Explorer, Azure Synapse Analytics).
*   Can be loaded into a new table, included in a data pipeline, or used as a data source by data analysts.
*   Can be horizontally partitioned for specialized semantic models.
*   Benefits: Consistent data, self-service access, performance optimization (extract once, reuse), simplified complexity, data quality, low-code interface.
*   Limitations: Not a replacement for a data warehouse, row-level security not supported, Fabric capacity workspace required.
*   Interface: Power Query Online (visual), Advanced editor (M code).

## Architectural Logic (The "Why")
Use Dataflows Gen2 for reusable ETL logic, reducing repeated data source connections and simplifying data preparation for downstream analytics. They are ideal for scenarios where data needs to be cleansed and transformed before landing in a destination or before being consumed by reporting tools. Use Data Pipelines for orchestration of Dataflows Gen2 or for ELT (Extract, Load, Transform) patterns where data is loaded first and then transformed.

## Implementation Workflow
1.  Create a Dataflow Gen2 in Data Factory, Power BI workspace, or lakehouse.
2.  Connect to the desired data source(s).
3.  Apply transformations using the Power Query Online interface (or M code).
4.  Optionally, configure a data destination (Lakehouse, Warehouse, etc.).
5.  Run manually, on a schedule, or as part of a data pipeline.
6.  (Optional) Make discoverable for Power BI Desktop connections.

## Exam "Gotchas" & Distinctions
*   Distinguish between Dataflows Gen2 (ETL, reusable logic, Power Query) and Data Pipelines (orchestration, activity sequencing).
*   Note that Dataflows Gen2 do NOT support row-level security.
*   Understand that Dataflows Gen2 can be a *source* for Data Pipelines, or Data Pipelines can *incorporate* Dataflow activities.
*   ELT vs. ETL: Dataflows Gen2 can be used for both, but their primary strength is in the transformation phase.

# M2.6.md

## Core Concept
Data pipelines in Microsoft Fabric orchestrate sequences of activities for data movement and processing, automating ETL/ELT processes.

## Technical Specifications
*   Core concepts: Activities (data transformation like Copy Data, Data Flow Gen2, Notebook, Stored procedure; control flow like branching, looping), Parameters (for reusability), Pipeline runs (track execution).
*   Copy Data Activity: For direct data transfer between sources and destinations without transformations, or for importing raw data for later transformation. Supports various sources and destinations including OneLake (lakehouse, warehouse, SQL DB).
*   Data Flow Activity: Encapsulates Dataflows Gen2 for transformations during data transfer.
*   Pipeline Templates: Predefined common scenarios for quick customization.
*   Run & Monitor: Validate, run interactively, schedule runs, view run history.

## Architectural Logic (The "Why")
Use pipelines to automate complex data ingestion and transformation workflows that involve multiple steps, conditional logic, or scheduled execution. They provide a visual way to manage data movement and processing, integrating various activities like data copying, data transformation (via Dataflows Gen2), and script execution (via Notebooks). Use Copy Data activity for simple, direct data movement or when transformations are handled later. Use Data Flow activity when complex transformations are needed *during* the pipeline's execution.

## Implementation Workflow
1.  Create a new pipeline in Microsoft Fabric.
2.  Add and configure activities (e.g., Copy Data, Data Flow Gen2, Notebook) on the pipeline canvas.
3.  Connect activities using control flow logic (success, failure, completion dependencies).
4.  (Optional) Parameterize the pipeline for reusability.
5.  Validate the pipeline configuration.
6.  Run interactively or schedule/trigger the pipeline.
7.  Monitor pipeline runs via the run history.

## Exam "Gotchas" & Distinctions
*   Distinguish between Copy Data activity (simple transfer) and Data Flow activity (complex transformations via Dataflows Gen2).
*   Understand that pipelines can *call* Dataflows Gen2.
*   Key use case: Automating ETL/ELT, especially when multiple steps or schedules are involved.
*   Familiarity with Azure Data Factory concepts is directly transferable.

# M2.7.md

## Core Concept
The medallion architecture organizes data in a Fabric lakehouse into logical layers (Bronze, Silver, Gold) to progressively refine data quality, ensuring reliability and efficient analysis.

## Technical Specifications
*   Layers:
    *   Bronze (Raw): Landing zone for all data types (structured, semi-structured, unstructured) in their original format. No changes made.
    *   Silver (Validated): Data is validated, cleansed, combined, and refined. Enforces data quality rules (remove nulls, deduplicate). Central repository, consistent format.
    *   Gold (Enriched): Data is further refined and modeled for specific business/analytics needs (aggregation, enrichment). Ready for downstream consumption (analytics, data science, reporting). Often modeled as a star schema.
*   Customization: Can include additional layers (e.g., "raw" before bronze, "platinum" for specific use cases). Flexible design.
*   Data Movement: Use Pipelines (orchestration), Dataflows Gen2 (transformation, low-code), or Notebooks (complex transformation, Spark/SQL/Scala).
*   Data Transformation vs. Orchestration: Transformation alters data structure/content (Dataflows, Notebooks). Orchestration manages sequences of processes (Pipelines).
*   Fabric Lakehouse Integration: Layers are implemented within a lakehouse using Delta tables. Gold layer can be a star schema. Data Warehouse can serve as a Gold layer.
*   Consumption: SQL Analytics Endpoint (querying Delta tables, views, functions, SQL security), Power BI (Direct Lake mode via semantic models).
*   Security & Management: Workspace/item-level permissions. Consider storing layers in separate workspaces. Minimize permissions (read-only for Bronze/Silver). Git integration for CI/CD.
*   CI/CD: Crucial for Gold layer to ensure high-quality, reliable data. Fabric Git integration supports version control, collaboration, automated deployments.

## Architectural Logic (The "Why")
The medallion architecture ensures data quality and reliability as data moves through progressive refinement stages. It provides structure for diverse data types, facilitates efficient analysis by preparing data for specific use cases (e.g., star schema for reporting), and enables better governance and security by organizing data logically. This pattern complements existing data models and allows customization.

## Implementation Workflow
1.  Create a Fabric lakehouse.
2.  Define layers (Bronze, Silver, Gold) and data flow paths.
3.  Ingest raw data into the Bronze layer (using Pipelines, Dataflows, Notebooks).
4.  Transform and cleanse data, loading into the Silver layer (using Dataflows or Notebooks).
5.  Model and enrich data for reporting/analytics, loading into the Gold layer (using Notebooks, SQL analytics endpoint).
6.  Enable consumption via SQL Analytics Endpoint or Power BI semantic models.
7.  Implement security controls at workspace, item, and potentially layer levels.
8.  Integrate CI/CD processes, especially for the Gold layer.

## Exam "Gotchas" & Distinctions
*   Bronze: Raw, original format. Silver: Cleaned, validated, consistent. Gold: Modeled, enriched, ready for reporting/AI.
*   Data transformation tools: Dataflows (low-code, Power Query), Notebooks (code-based, Spark/SQL). Data Orchestration tool: Pipelines.
*   Gold layer modeling: Often star schema. Can use Data Warehouse as Gold layer.
*   Security: Layered permissions are critical. Read-only recommended for Bronze/Silver.
*   CI/CD is most critical for the Gold layer.
*   The architecture is flexible and can be extended beyond three layers.
