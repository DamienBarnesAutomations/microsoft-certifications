# M1.1.md

## Core Concept
Dataflows Gen2 in Microsoft Fabric are cloud-based ETL tools for building and executing scalable data transformation processes with a visual interface.

## Technical Specifications
*   Supports a wide variety of data source connectors (relational databases, Excel, SharePoint, Salesforce, Spark, Fabric lakehouses).
*   Offers numerous data transformations: Filter/Sort rows, Pivot/Unpivot, Merge/Append queries, Split/Conditional split, Replace values/Remove duplicates, Add/Rename/Reorder/Delete columns, Rank/Percentage calculator, Choose Top N/Bottom N.
*   Data destinations: Lakehouse, Warehouse, SQL database (Fabric, Azure SQL DB, Azure Data Explorer, Azure Synapse Analytics).
*   Can be loaded into a new table, included in a data pipeline, or used as a data source by data analysts.
*   Can be horizontally partitioned for specialized semantic models.
*   Benefits: Consistent data, self-service access, performance optimization (extract once, reuse), simplified complexity, data quality, low-code interface.
*   Limitations: Not a replacement for a data warehouse, row-level security not supported, Fabric capacity workspace required.
*   Interface: Power Query Online (visual), Advanced editor (M code).

## Architectural Logic (The "Why")
Use Dataflows Gen2 for reusable ETL logic, reducing repeated data source connections and simplifying data preparation for downstream analytics. They are ideal for scenarios where data needs to be cleansed and transformed before landing in a destination or before being consumed by reporting tools. Use Data Pipelines for orchestration of Dataflows Gen2 or for ELT (Extract, Load, Transform) patterns where data is loaded first and then transformed.

## Implementation Workflow
1.  Create a Dataflow Gen2 in Data Factory, Power BI workspace, or lakehouse.
2.  Connect to the desired data source(s).
3.  Apply transformations using the Power Query Online interface (or M code).
4.  Optionally, configure a data destination (Lakehouse, Warehouse, etc.).
5.  Run manually, on a schedule, or as part of a data pipeline.
6.  (Optional) Make discoverable for Power BI Desktop connections.

## Exam "Gotchas" & Distinctions
*   Distinguish between Dataflows Gen2 (ETL, reusable logic, Power Query) and Data Pipelines (orchestration, activity sequencing).
*   Note that Dataflows Gen2 do NOT support row-level security.
*   Understand that Dataflows Gen2 can be a *source* for Data Pipelines, or Data Pipelines can *incorporate* Dataflow activities.
*   ELT vs. ETL: Dataflows Gen2 can be used for both, but their primary strength is in the transformation phase.

# M1.2.md

## Core Concept
Data pipelines in Microsoft Fabric orchestrate sequences of activities for data movement and processing, automating ETL/ELT processes.

## Technical Specifications
*   Core concepts: Activities (data transformation like Copy Data, Data Flow Gen2, Notebook, Stored procedure; control flow like branching, looping), Parameters (for reusability), Pipeline runs (track execution).
*   Copy Data Activity: For direct data transfer between sources and destinations without transformations, or for importing raw data for later transformation. Supports various sources and destinations including OneLake (lakehouse, warehouse, SQL DB).
*   Data Flow Activity: Encapsulates Dataflows Gen2 for transformations during data transfer.
*   Pipeline Templates: Predefined common scenarios for quick customization.
*   Run & Monitor: Validate, run interactively, schedule runs, view run history.

## Architectural Logic (The "Why")
Use pipelines to automate complex data ingestion and transformation workflows that involve multiple steps, conditional logic, or scheduled execution. They provide a visual way to manage data movement and processing, integrating various activities like data copying, data transformation (via Dataflows Gen2), and script execution (via Notebooks). Use Copy Data activity for simple, direct data movement or when transformations are handled later. Use Data Flow activity when complex transformations are needed *during* the pipeline's execution.

## Implementation Workflow
1.  Create a new pipeline in Microsoft Fabric.
2.  Add and configure activities (e.g., Copy Data, Data Flow Gen2, Notebook) on the pipeline canvas.
3.  Connect activities using control flow logic (success, failure, completion dependencies).
4.  (Optional) Parameterize the pipeline for reusability.
5.  Validate the pipeline configuration.
6.  Run interactively or schedule/trigger the pipeline.
7.  Monitor pipeline runs via the run history.

## Exam "Gotchas" & Distinctions
*   Distinguish between Copy Data activity (simple transfer) and Data Flow activity (complex transformations via Dataflows Gen2).
*   Understand that pipelines can *call* Dataflows Gen2.
*   Key use case: Automating ETL/ELT, especially when multiple steps or schedules are involved.
*   Familiarity with Azure Data Factory concepts is directly transferable.

# M1.3.md

## Core Concept
Apache Spark in Microsoft Fabric provides a distributed processing framework for large-scale data analytics, integrated within the Fabric environment.

## Technical Specifications
*   Languages: Java, Scala, Spark R, Spark SQL, PySpark (Python).
*   Spark Pool: Cluster of compute nodes (head node, worker nodes with executors) for distributed processing.
*   Fabric Spark Pools: Starter pool (configurable default) and custom pools. Settings include Node Family (memory optimized), Autoscale, Dynamic Allocation.
*   Runtimes & Environments: Support multiple Spark runtimes (version of Spark, Delta Lake, Python). Custom environments can install specific libraries (PyPI) and configurations.
*   Native Execution Engine: Vectorized engine running Spark operations directly on lakehouse infrastructure (for Parquet/Delta files). Enable via `spark.native.enabled=true` and `spark.shuffle.manager=org.apache.spark.shuffle.sort.ColumnarShuffleManager`.
*   High Concurrency Mode: Shares Spark sessions across multiple users/processes for efficiency. Enable in workspace settings.
*   Automatic MLFlow Logging: Implicit logging of ML experiment activity.
*   Execution: Notebooks (interactive exploration), Spark Job Definitions (automated scripts).
*   DataFrames: Primary data structure for structured data (optimized for distributed processing).
*   Loading Data: Infer schema (`header=True`) or specify explicit schema (`StructType`).
*   Transformations: `select`, `where`, `groupBy`, `aggregrate`, `partitionBy`.
*   Saving Data: `write.mode("overwrite").parquet(...)`, `write.partitionBy(...).parquet(...)`. Delta format preferred.
*   Spark SQL: Query catalog objects (views, tables) using SQL expressions. `createOrReplaceTempView()`, `saveAsTable()`. Delta tables preferred. `spark.catalog.createExternalTable()`.
*   Visualization: Built-in notebook charts and Python graphics libraries (Matplotlib, Seaborn).

## Architectural Logic (The "Why")
Use Spark in Fabric for large-scale data processing, complex transformations, machine learning, and interactive data exploration where performance and scalability are critical. Leverage DataFrames and Spark SQL for structured data manipulation. Utilize notebooks for exploration and Spark Job Definitions for automated workflows. The native execution engine and high concurrency mode optimize performance and resource utilization.

## Implementation Workflow
1.  Create/Configure a Spark Pool (starter or custom) in workspace settings.
2.  Define/Select a Spark Runtime and Environment (including necessary libraries).
3.  (Optional) Enable Native Execution Engine and High Concurrency Mode.
4.  Use a Notebook or create a Spark Job Definition.
5.  Load data into a Spark DataFrame (`spark.read.load(...)`).
6.  Perform transformations using DataFrame API or Spark SQL.
7.  Save processed data (e.g., as Parquet or Delta tables).
8.  Visualize results using built-in charts or Python libraries.

## Exam "Gotchas" & Distinctions
*   Distinguish between DataFrames (distributed) and Pandas DataFrames (in-memory). Use `.toPandas()` for conversions.
*   Understand the difference between managed and external tables in the Spark catalog.
*   Know that Delta Lake format is preferred for tables in Fabric Spark.
*   Be aware of the performance benefits of the Native Execution Engine and partitioning.
*   Recognize that Spark pools and runtimes are configurable at the workspace level and can be restricted by administrators.
*   Understand that Spark jobs are for automated, scheduled tasks, while notebooks are for interactive exploration.

# M1.4.md

## Core Concept
An Eventhouse in Microsoft Fabric provides a data store for real-time data, housing KQL databases optimized for continuous ingestion and analysis using Kusto Query Language (KQL).

## Technical Specifications
*   Eventhouse: Container for one or more KQL databases.
*   KQL Database: Automatically partitions data by ingestion time. Optimized for time-series, append-only data.
*   Data Ingestion Sources: Local files, Azure storage, Amazon S3, Azure Event Hubs, Fabric Eventstream, Real-Time hub, OneLake, Data Factory copy, Dataflows, Kafka, Flink, Kinesis, Pub/Sub.
*   Database Shortcuts: Query external KQL databases without copying data.
*   OneLake Availability: Enable for KQL databases/tables for Fabric ecosystem integration.
*   Querying: KQL (case-sensitive, pipeline approach with operators like `where`, `project`, `summarize`, `take`) or T-SQL in KQL querysets.
*   KQL Queryset: Workspace for running/saving/sharing KQL/T-SQL queries. Supports visualizations and Copilot for AI-assisted query generation.
*   Optimization Techniques: Filter data early and effectively (especially time-based), reduce columns early (`project`), optimize aggregations/joins (smaller table first), limit results during exploration.
*   Materialized Views: Precomputed aggregations that automatically update. Store precomputed part + delta. Combine at query time for instant, up-to-date results. Used for dashboards/reports on large datasets. Created using ` .create materialized-view ...`.
*   Stored Functions: Encapsulate reusable KQL query logic with parameters. Defined using `.create-or-alter function ...`.

## Architectural Logic (The "Why")
Use Eventhouses and KQL databases for ingesting and analyzing high-volume, continuous, real-time data streams where time is a critical dimension (time-series data). KQL's optimized query engine and automatic partitioning facilitate fast access to recent data. Materialized views and stored functions enhance query performance and reusability for dashboards and recurring analytical tasks.

## Implementation Workflow
1.  Create an Eventhouse in Microsoft Fabric.
2.  (Optional) Create additional KQL databases within the Eventhouse.
3.  Ingest data using supported sources (Eventstream, Azure Event Hubs, Kafka, etc.) or direct methods.
4.  Enable OneLake availability if cross-workload integration is needed.
5.  Query data using KQL or T-SQL in a KQL queryset.
6.  Implement optimization techniques (early filtering, column reduction).
7.  (Optional) Create Materialized Views for precomputed aggregations.
8.  (Optional) Create Stored Functions for reusable query logic.
9.  (Optional) Use Copilot for AI-assisted KQL query generation.
10. Visualize data using Real-Time Dashboards or queryset visualizations.

## Exam "Gotchas" & Distinctions
*   KQL is case-sensitive.
*   Distinguish between KQL databases (time-series, append-only, auto-partitioned) and traditional relational databases (updates, complex relationships).
*   Understand the performance benefits of Materialized Views for aggregations on large, streaming datasets.
*   Recognize that Stored Functions improve query reusability and consistency.
*   Eventhouses are containers for KQL databases.
*   Copilot in KQL querysets assists in generating KQL code.
