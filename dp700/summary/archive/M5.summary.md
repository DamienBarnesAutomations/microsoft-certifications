# M5.1.md

## Core Concept
Lifecycle management in Microsoft Fabric implements CI/CD through Git integration for version control and deployment pipelines for promoting content across environments.

## Technical Specifications
*   CI/CD Components:
    *   Git (Integration): Collaboration via branches, version control, incremental code changes, and history. Supports GitHub and Azure DevOps.
    *   Deployment Pipelines: Automates movement of content through stages (typically Development $\rightarrow$ Test $\rightarrow$ Production).
    *   Fabric REST APIs: Enables programmatic automation of commits, updates, and deployments.
*   Git Workflow:
    *   Integration occurs at the workspace level.
    *   Sync state is indicated by a Git status column in the workspace.
    *   Collaboration pattern: Develop in isolated workspaces/branches $\rightarrow$ Commit $\rightarrow$ Pull Request (PR) $\rightarrow$ Merge to main $\rightarrow$ Sync shared workspace.
*   Deployment Pipelines Workflow:
    *   Create pipeline $\rightarrow$ Define stages $\rightarrow$ Assign workspaces to stages.
    *   Promote content by cloning items from one stage to the next.
*   Hybrid Approach: Connect only the Development workspace to Git for version control, then use deployment pipelines to promote to Test and Production to avoid synchronization conflicts.

## Architectural Logic (The "Why")
CI/CD reduces bugs and code failures by ensuring changes are frequently integrated, validated, and tested in isolated environments before reaching production. Git provides the "safety net" for versioning and collaboration, while deployment pipelines provide the "conveyor belt" for structured release.

## Implementation Workflow
1.  Set up a Git repository (GitHub/Azure DevOps).
2.  Connect a Fabric workspace to the repository and select a branch.
3.  Develop changes in an isolated workspace/branch.
4.  Commit changes to the Git branch.
5.  Create a Pull Request to merge changes into the main branch.
6.  Sync the shared development workspace with the main branch.
7.  Create a deployment pipeline and assign workspaces to stages (Dev, Test, Prod).
8.  Deploy content between stages.
9.  (Optional) Automate using Fabric REST APIs for commits and deployments.

## Exam "Gotchas" & Distinctions
*   Distinguish between Continuous Integration (merging/validating code in Git) and Continuous Delivery (promoting code through stages via pipelines).
*   Git integration is at the *workspace* level.
*   The hybrid approach (Git for Dev $\rightarrow$ Pipelines for Test/Prod) is a recommended pattern to minimize sync conflicts.
*   REST APIs are used for *automation* of these processes.

# M5.2.md

## Core Concept
Monitoring in Microsoft Fabric is the process of collecting system metrics to ensure the health, reliability, and performance of data ingestion and transformation activities.

## Technical Specifications
*   Activities to Monitor:
    *   Data Pipelines: Success/failure, job history, error details.
    *   Dataflows: Start/end times, status, duration, table load activities.
    *   Semantic Model Refreshes: Status, retries (to identify transient issues).
    *   Spark Jobs/Notebooks: Progress, task execution, resource usage, logs.
    *   Eventstreams: Ingestion status, performance, streaming data flow.
*   Monitor Hub: Centralized visualization tool to view status of multiple activities across the tenant in one place. Provides activity details, historical runs, and error metadata.
*   Fabric Activator: Event-driven automation tool. Triggers actions (alerts, workflows, Fabric jobs) based on thresholds, patterns, or KQL query results in streaming data.
*   Best Practices: Track metrics to identify "normal" behavior, review logs regularly, resolve deviations quickly, and optimize bottlenecks.

## Architectural Logic (The "Why")
Continuous monitoring prevents system errors from affecting end-users by allowing engineers to identify and remediate issues (e.g., failed refreshes, slow Spark jobs) proactively. The Monitor Hub aggregates fragmented activity logs into a single pane of glass for operational efficiency.

## Implementation Workflow
1.  Open the Monitor Hub from the Fabric navigation pane.
2.  Filter activity by status, item type, time, user, or workspace.
3.  Select specific activities to view details, retry runs, or investigate error logs.
4.  Drill down into Spark application details for notebook/pipeline failures.
5.  Configure Activator rules to automate responses to critical event patterns or anomalies.

## Exam "Gotchas" & Distinctions
*   Monitor Hub is for *operational* monitoring (what failed and when).
*   Activator is for *real-time* automated response to data patterns.
*   Distinguish between monitoring the *process* (e.g., did the pipeline run?) and monitoring the *data* (e.g., is the temperature too high?).

# M5.3.md

## Core Concept
Fabric uses a layered security model (Authentication $\rightarrow$ Fabric Access $\rightarrow$ Data Security) to enforce the principle of least privilege across workspaces, items, and the underlying OneLake data.

## Technical Specifications
*   Security Layers:
    1.  Microsoft Entra ID: Authentication.
    2.  Fabric Access: General platform access.
    3.  Data Security: Specific action permissions on tables/files.
*   Data Security Controls:
    *   Workspace Roles: Admin, Member, Contributor, Viewer. Apply to *all* items in a workspace.
    *   Item Permissions: Shared for specific items (e.g., a single lakehouse). Granular permissions: Read, ReadAll SQL endpoint data, Read all Apache Spark/subscribe to events, Build reports.
    *   Compute Permissions: Engine-specific controls (SQL endpoint, semantic model).
    *   OneLake Security: RBAC roles for specific tables/folders. Permissions: Read, ReadWrite.
*   OneLake Security Roles: Consist of Data (tables/folders), Permissions, Members, and optional Constraints (row/column filters).
*   DefaultReader Role: Automatically granted to users with "Read all Apache Spark" permission. Must be removed to enforce custom restrictive roles.
*   Granular T-SQL Security: Row-Level Security (RLS), Column-Level Security (CLS), and Dynamic Data Masking (DDM).

## Architectural Logic (The "Why")
The multi-layer approach allows administrators to start with broad access (Workspace roles) and progressively refine it (Item permissions $\rightarrow$ OneLake roles $\rightarrow$ T-SQL security). This ensures users have exactly the access they need (least privilege) without over-provisioning. OneLake security is unique because it is enforced consistently across all compute engines (Spark, SQL, API).

## Implementation Workflow
1.  Assign a Workspace Role for broad collaboration.
2.  (Optional) Remove user from workspace and use Item Permissions for specific item access.
3.  Configure OneLake security roles to restrict access to specific tables/folders within a lakehouse.
4.  Remove user from the `DefaultReader` role if restrictive access is needed.
5.  Apply T-SQL granular security (RLS, CLS, DDM) for SQL analytics endpoint access.

## Exam "Gotchas" & Distinctions
*   Workspace roles (Admin/Member/Contributor) override OneLake security roles (they have full access).
*   Viewers have no OneLake data access by default; they need OneLake security roles.
*   Item permissions grant access to the *item*, but OneLake security roles grant access to the *data within the item*.
*   `DefaultReader` is a common "gotcha"—if not removed, custom restrictive roles are ignored.

# M5.4.md

## Core Concept
Fabric administration involves managing the platform hierarchy (Tenant $\rightarrow$ Capacity $\rightarrow$ Domain $\rightarrow$ Workspace $\rightarrow$ Item) and delegating responsibilities to ensure governed, performant, and secure usage.

## Technical Specifications
*   Admin Hierarchy:
    *   Tenant: Global settings, security policies, feature availability.
    *   Capacity: Compute/storage resources (F SKUs).
    *   Domain: Logical business groupings (e.g., Finance, Risk) for governance.
    *   Workspace: Collaboration containers for items.
    *   Items: Individual assets (Lakehouse, Warehouse, etc.).
*   Admin Roles:
    *   Fabric Admin: Tenant-wide control (Power BI Administrator in Entra ID).
    *   Capacity Admin: Manages specific capacity, monitors performance.
    *   Domain Admin: Manages workspaces in a domain, enforces domain policies.
    *   Workspace Admin: Manages access and items in a specific workspace.
*   Tenant Settings: Control feature availability (Enable/Disable, specific groups). Can be delegated to domain admins.
*   Domains: Organize governance. Use pattern matching or workspace admin assignment for automation.
*   Licensing:
    *   Capacity License: Shared compute (F SKU).
    *   Per-User Licenses: Fabric Free (non-Power BI items), Power BI Pro (creating/sharing reports), PPU.
    *   F64 Threshold: Users with "Free" licenses can view Power BI content if the workspace is on F64 or larger.
*   Monitoring/Governance:
    *   Monitor Hub: Operational job health.
    *   Admin Monitoring Workspace: Strategic adoption/usage reports.
    *   Capacity Metrics App: CU consumption, throttling, scaling.
    *   Audit Logs: Compliance and security tracking.
    *   Endorsement: Promoted (by contributors) vs. Certified (by authorized stewards).

## Architectural Logic (The "Why")
A tiered delegation model prevents the tenant admin from becoming a bottleneck. By delegating to capacity, domain, and workspace admins, the organization can scale governance and support locally while maintaining global guardrails via tenant settings.

## Implementation Workflow
1.  Configure Tenant Settings for feature availability and security.
2.  Provision and manage Capacity (assign workspaces, monitor CUs).
3.  Define Domains and assign Domain Admins to delegate governance.
4.  Assign User Licenses based on role (Free for viewers on F64+, Pro for creators).
5.  Establish a sharing pattern (Apps for consumers, Workspace roles for collaborators).
6.  Monitor health using the Monitoring Hub, Capacity Metrics app, and Audit logs.
7.  Enforce trust via the Endorsement (Promoted/Certified) process.

## Exam "Gotchas" & Distinctions
*   Tenant settings are governance policies, NOT security measures (export buttons may disappear, but API access might remain).
*   Domains organize governance, NOT access (moving a workspace to a domain doesn't change who can see the data).
*   The F64 capacity is the critical threshold for allowing "Free" users to view Power BI content.
*   Distinguish between the Monitor Hub (operational/failures) and Admin Monitoring Workspace (strategic/adoption).
