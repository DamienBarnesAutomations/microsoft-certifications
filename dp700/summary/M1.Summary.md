## Card 1: Dataflows Gen2

### What It Is
Dataflows Gen2 are cloud-based ETL tools built on Power Query Online. They allow you to extract data from multiple sources, apply transformations using a visual interface, and load the results into a Fabric destination such as a Lakehouse, Warehouse, or SQL Database. You can also load data into external targets like Azure SQL Database, Azure Data Explorer, and Azure Synapse Analytics. The dataflow preserves every transformation step you apply, which makes it easy to reuse and maintain your logic over time.

### When to Use It
Use a Dataflow Gen2 when you need to apply transformations during ingestion, such as filtering rows, cleansing data, merging multiple sources, or standardizing column names. Dataflows are well suited for teams that prefer a low-code interface over writing Spark notebooks. They work well when you want to create a reusable semantic model that data analysts can connect to through Power BI Desktop.

### ETL vs. ELT with Dataflows
In the ETL pattern, a single Dataflow Gen2 handles extraction, transformation, and loading in one step. You connect to the source, apply all transformations in Power Query Online, and land the data in the destination. In the ELT pattern, a Pipeline extracts and loads raw data into a destination like a Lakehouse first. Then a separate Dataflow Gen2 connects to that Lakehouse data and applies the transformations. The exam tests your ability to distinguish between these two patterns and know when each is appropriate.

### Destinations
Adding a destination to your dataflow is optional. A dataflow can exist without a configured destination and still serve as a logical data source for pipelines or for report developers connecting through Power BI Desktop. This is different from pipelines, where every Copy Data activity must have both a source and a destination.

### Sources
Dataflows Gen2 support a wide range of data sources, including cloud and on-premises relational databases, Excel and flat files, SharePoint, Salesforce, Spark, and Fabric lakehouses.

### Transformations Available
The Power Query Online interface provides many transformation options. You can filter and sort rows, pivot and unpivot columns, merge and append queries, split columns, replace values, remove duplicates, add or rename columns, calculate ranks and percentages, and select the top or bottom N rows.

### Power Query Online Interface
The ribbon contains source connectors, transformation tools, parameter management, and default data destination configuration. The Queries pane lists all data sources, which are called queries during editing and tables once loaded to a destination. You can duplicate a query, create a reference to another query, or disable the load for any query. The Diagram view provides a visual map of how queries connect and what transformations have been applied. The Data Preview pane shows a subset of the data so you can see the effect of each transformation. You can drag and drop columns to reorder them or right-click to filter directly in the preview. The Query Settings pane shows the list of Applied Steps, where each transformation is recorded as a step. Most steps have a gear icon that lets you modify the step, and you can right-click to rename, reorder, or delete steps. The Advanced Editor in this pane shows the M code that Power Query generates behind the scenes for every transformation.

### Horizontal Partitioning
A global dataflow can be created first, and then data analysts can create specialized dataflows that reference the global one. This allows different teams to work with subsets of the data without duplicating the extraction and transformation logic.

### Requirements and Limitations
Dataflows Gen2 require a Fabric capacity workspace. They do not support row-level security, and they are not a replacement for a data warehouse. The exam may test whether you understand these limitations.

### Execution Options
A dataflow can be run manually, on a refresh schedule, or as part of a pipeline activity. When you integrate a dataflow into a pipeline, you can chain it with other activities like stored procedures or notebooks.

### Exam Gotchas
In the Power Query interface, data sources are called queries during editing but become tables once loaded to a destination. A dataflow can exist without a destination and still provide output as a data source reference. Standalone dataflows are limited to their own refresh schedule, while pipeline integration enables complex dependencies, error handling, and sequential activities. Dataflows Gen2 do not work on Trial SKUs for all scenarios. Published dataflows can be used as data sources in Power BI Desktop if made discoverable, which reduces duplicate data preparation for report developers.

## Card 2: Data Pipelines

### What It Is
Data pipelines in Microsoft Fabric share the same architecture as Azure Data Factory. They define a sequence of activities on a visual canvas to automate ETL and ELT processes. Activities fall into two broad categories: data transformation activities and control flow activities. Data transformation activities include Copy Data, Dataflow Gen2, Notebook, Stored Procedure, and Delete Data. Control flow activities include ForEach, Until, If Condition, Set Variable, and Wait, which manage branching, looping, and variable handling within the pipeline.

### Copy Data Activity
The Copy Data activity moves data between a supported source and destination without applying any transformations. It uses a graphical configuration wizard and is optimized for high-performance raw data movement. You should use Copy Data when you need to move large volumes of data without transformation. If you need to transform data during ingestion, you should use a Dataflow Gen2 activity instead. Within OneLake, you can configure the destination to be a lakehouse, warehouse, SQL Database, or other supported target.

### Parameters
Parameters make pipelines reusable by allowing you to provide specific values each time the pipeline runs. For example, you might define a parameter for a folder name so the same pipeline can be used for different data sources. Parameters are defined in the pipeline settings and referenced within activities.

### Pipeline Runs
Each time a pipeline is executed, a unique run ID is generated. You can review run details to confirm success or investigate failures. Runs can be initiated on-demand through the Fabric user interface or scheduled to start at a specific frequency.

### Validation
Before running a pipeline, you should use the Validate option to check that the configuration is valid. This helps catch errors before execution.

### Templates
Microsoft Fabric provides predefined pipeline templates for common ingestion scenarios. You can access these templates from the Templates tile when creating a new pipeline. After selecting a template, you can customize the resulting activities on the canvas to fit your specific needs.

### Triggers
Pipelines can be triggered manually or on a schedule. When you use a pipeline to run a dataflow, you can have the data refreshed at specific intervals instead of having to manually run the dataflow each time.

### Architectural Logic
Pipelines separate execution logic from transformation logic. The pipeline handles sequencing, dependencies, scheduling, and error handling, while the individual activities handle the actual data processing. This separation allows each activity to be developed, tested, and versioned independently. You should use Copy Data over Dataflows Gen2 when moving large volumes of raw data without transformation, because Copy Data is optimized for speed and volume. You should use a Pipeline with a Dataflow activity when you need to orchestrate transformations followed by other steps. Control flow activities are appropriate when the pipeline must make decisions based on conditions, such as checking if a file exists before copying it.

### Exam Gotchas
Control flow activities and data transformation activities are separate categories with different purposes. Copy Data is optimized for raw data movement without transformations, and using it for transformation is an anti-pattern. Standalone dataflows have their own refresh schedule, while pipelines can wrap dataflows and add dependency management, sequential activity execution, and conditional logic. Templates are starting points that can be customized after creation. Each pipeline run generates a unique ID used for monitoring and troubleshooting. Fabric pipelines share the same architecture as Azure Data Factory, so familiarity with ADF transfers directly to Fabric.

## Card 3: Apache Spark in Fabric

### What It Is
Apache Spark in Microsoft Fabric is a distributed parallel processing framework that enables large-scale data analytics. It uses a divide-and-conquer approach by distributing work across multiple processing nodes in a cluster, which is called a Spark pool. A Spark pool consists of a head node that runs a driver program to coordinate distributed processing, and multiple worker nodes that run executor processes to perform the actual data processing tasks. Spark supports multiple languages including PySpark, Spark SQL, Scala, Spark R, and Java, though most data engineering and analytics workloads use a combination of PySpark and Spark SQL.

### Spark Pool Types
Microsoft Fabric provides a starter pool in each workspace by default. The starter pool enables Spark jobs to start quickly with minimal setup and configuration. You can configure the starter pool to optimize the nodes for your specific workload or cost constraints. In addition to the starter pool, you can create custom Spark pools with specific node configurations that support your particular data processing needs. If you create one or more custom pools, you can set one of them or the starter pool as the default pool for the workspace. The ability to customize Spark pool settings can be disabled by Fabric administrators at the Fabric capacity level.

### Configuration Settings
The node family determines the type of virtual machines used for the cluster nodes, and memory optimized nodes provide optimal performance in most cases. Autoscale controls whether nodes are automatically provisioned as needed and allows you to set the initial and maximum number of nodes. Dynamic allocation controls whether executor processes are dynamically allocated on the worker nodes based on data volumes. These two settings work together but are independent of each other.

### Runtimes and Environments
The Spark runtime determines the version of Apache Spark, Delta Lake, Python, and other core software components that are installed. An environment consists of a runtime plus custom public libraries from the Python Package Index, custom uploaded package files, Spark configuration properties, and resource files. You can define multiple environments to support a diverse range of data processing tasks. After creating a custom environment, you can set it as the default environment in the workspace settings. Environments ensure parity between development in notebooks and production in Spark jobs.

### Native Execution Engine
The native execution engine is a vectorized processing engine that runs Spark operations directly on lakehouse infrastructure. It can significantly improve performance when working with large datasets in Parquet or Delta file formats. To enable the native execution engine, you must set both spark.native.enabled to true and spark.shuffle.manager to org.apache.spark.shuffle.sort.ColumnarShuffleManager. You can enable these settings at the environment level or within an individual notebook using the %%configure magic. Setting only one of these two properties is insufficient.

### High Concurrency Mode
High concurrency mode allows multiple users to share Spark sessions while maintaining code isolation. When this mode is enabled, multiple notebooks can share the same Spark session, but each notebook maintains its own variable namespace so that variables in one notebook are not affected by code in another. High concurrency mode also applies to Spark jobs for non-interactive script execution. You can enable this mode in the Data Engineering and Science section of the workspace settings.

### Automatic MLFlow Logging
By default, Microsoft Fabric uses MLFlow to implicitly log machine learning experiment activity without requiring the data scientist to include explicit code. You can disable this functionality in the workspace settings if needed.

### Notebooks vs. Spark Job Definitions
Notebooks are interactive, cell-based tools that support Markdown content and executable code. They support multiple languages through magic commands such as %%pyspark, %%spark, %%sql, and %%r. Results are displayed under each cell, and built-in charting is available. Notebooks are best suited for exploration and development. Spark Job Definitions are script-based and support on-demand or scheduled execution. They allow you to specify a reference file containing function definitions and associate the job with a specific lakehouse. Spark Job Definitions are best suited for production automation where reliability, scheduling, and repeatability are required.

### Spark Sessions
A Spark session is initiated when you execute the first cell in a notebook. The session persists until it is stopped or times out from inactivity.

### Exam Gotchas
The driver runs on the head node and coordinates tasks, while executors run on worker nodes and process data. Candidates commonly confuse these two roles. The runtime is the base software version, while the environment is the runtime plus specific libraries and configurations. These are often conflated on the exam. You must set both native execution engine properties together for it to work. High concurrency mode shares compute resources but keeps variables isolated between notebooks. The starter pool is per workspace and custom pools must be explicitly created. Autoscale controls node count while dynamic allocation controls executor processes, and they are independent settings.

## Card 4: Spark Dataframes and Spark SQL

### What They Are
A Spark DataFrame is a distributed collection of data organized into named columns. It is built on Resilient Distributed Datasets but provides a higher-level API similar to Pandas DataFrames, optimized for distributed processing across a cluster. Spark SQL provides a SQL interface to query DataFrames and catalog objects, allowing data engineers and data analysts to work on the same data using their preferred language.

### Loading Data
You load data into a DataFrame using spark.read.load with a format parameter such as csv, parquet, or delta. For CSV files with column names in the first row, you specify header=True as an option.

### Schema Specification
You can let Spark infer the schema by scanning the data, which is slower and can result in type mismatches if the data contains unexpected values. Alternatively, you can specify an explicit schema using StructType and StructField from the pyspark.sql.types module. An explicit schema skips the data scan step, which improves loading performance and prevents type errors. The exam tests your understanding of this performance difference.

### DataFrame Operations
You can select a subset of columns using the select method or the shorthand syntax df["col1", "col2"]. You filter rows using the where method with Boolean conditions, and you can chain multiple conditions with the or operator. The filter method works identically to where. You aggregate data using groupBy followed by an aggregate function like count. The limit method returns the first n rows. You can chain methods together to perform a series of transformations that result in a new DataFrame.

### Saving Data
You save a DataFrame using the write method with a mode parameter. The overwrite mode replaces existing data and the append mode adds to existing data. You can save data as Parquet files or as managed Delta tables in the catalog using the saveAsTable method. Delta format is preferred in Microsoft Fabric because it supports ACID transactions, versioning through time travel, and streaming.

### Partitioning
Partitioning is an optimization technique that creates a folder hierarchy based on column values. When you write a DataFrame with partitionBy, the output creates folders in the format ColumnName=Value. Multi-column partitioning creates nested folder hierarchies. Partition pruning allows the engine to skip entire folders that do not match a query filter, which reduces disk I/O. When reading a specific partition by path, the partitioning column is omitted from the resulting DataFrame because all rows in that folder share the same value. Over-partitioning on high-cardinality columns creates too many small files and degrades performance, so you should partition only on columns that are frequently used in WHERE filters.

### Spark Catalog
The Spark catalog is a metastore that manages relational objects including views and tables. You create a temporary view using createOrReplaceTempView, and it is automatically deleted at the end of the session. Managed tables store both metadata and data in the Fabric-managed Tables location, and deleting a managed table also deletes its underlying data. External tables store metadata in the catalog but keep data in an external location such as the Files folder, and deleting an external table preserves the underlying data files.

### Spark SQL
You can query catalog objects using the Spark SQL API with spark.sql, which returns a DataFrame. In notebooks, you can use the %%sql magic to run SQL directly and display results automatically as a table. Both approaches query the same catalog objects.

### Visualization
Built-in charting in notebooks allows you to display DataFrame results as charts with customizable properties. For more control, you can use graphics libraries such as Matplotlib or Seaborn. Most Python visualization libraries require Pandas DataFrames, so you must convert Spark DataFrames using the toPandas method. This conversion pulls data to the driver node, so you should use it selectively on aggregated or subset data rather than on full datasets.

### Exam Gotchas
Inferred schemas require a data scan and are slower and error-prone, while explicit schemas skip the scan and are faster and type-safe. Deleting a managed table deletes the data, but deleting an external table preserves the data. Over-partitioning on high-cardinality columns degrades performance. Delta is the preferred format in Fabric. The %%sql magic auto-displays results while spark.sql returns a DataFrame that requires display or further processing. Matplotlib and similar libraries require toPandas conversion, which pulls data to the driver and should be used on aggregated data only.

## Card 5: Eventhouse and KQL

### What It Is
An Eventhouse is a container for one or more KQL databases that are optimized for high-volume, append-only time-series data. When you create an Eventhouse, a default KQL database is automatically created with the same name. KQL databases automatically partition data by ingestion time, which means recent data is quickly accessible without scanning all historical data. This design is ideal for immutable events that represent what happened at specific moments in time, such as IoT sensor readings, application logs, and clickstreams.

### Data Ingestion
You can ingest data into a KQL database from local files, Azure Storage, Amazon S3, Azure Event Hubs, Fabric Eventstream, Real-Time Hub, OneLake, Data Factory Copy, Dataflows, and connectors for Apache Kafka, Confluent Cloud Kafka, Apache Flink, MQTT, Amazon Kinesis, and Google Cloud Pub/Sub. The Get Data menu in the Eventhouse UI provides access to these ingestion methods.

### Database Shortcuts
Database shortcuts allow you to query data from external KQL databases in other Eventhouses or Azure Data Explorer without copying the data. The external data appears as if it were stored locally in your Eventhouse.

### OneLake Availability
You can enable OneLake availability for individual KQL databases or tables, making your data accessible throughout the Fabric ecosystem for cross-service integration with Power BI, Warehouse, Lakehouse, and other Fabric services.

### KQL Queryset
A KQL Queryset is a workspace for running and managing queries against KQL databases. It is automatically created with each KQL database and supports multiple query tabs, saved queries, and sharing. The KQL Queryset supports both KQL and T-SQL queries, though KQL provides richer time-series analysis capabilities.

### KQL Syntax
KQL uses a pipeline approach where data flows from one operation to the next using the pipe character. Think of it like a funnel where you start with the full dataset and each operator filters, rearranges, or summarizes the data before passing it to the next step. The order of operators matters because each step works on the results from the previous step. The simplest KQL query is just a table name, which returns all columns with a row limit determined by your query tool defaults.

### KQL is Case-Sensitive
KQL is strictly case-sensitive for table names, column names, function names, operators, keywords, and string values. All identifiers must match exactly. For example, TaxiTrips is different from taxitrips and from TAXITRIPS. This is a common source of query errors and an exam-relevant detail.

### Core KQL Operators
The where operator filters rows based on conditions, including time-based and value-based conditions. The project operator selects specific columns. The take operator returns a sample of rows for exploration. The summarize operator performs aggregations such as count, average, sum, min, and max, and you can group results using the by clause. The sort by operator orders results. The join operator combines tables. The limit operator restricts the number of results returned.

### KQL Optimization
Filter early to reduce the amount of data that subsequent operations need to process. Time-based filters are especially efficient because KQL databases index by ingestion time. Order your filters by how much data they eliminate, putting the most restrictive filter first. Reduce columns early by using project before where, summarize, or join. For joins, put the smaller table first because KQL processes the first table to match against the second table. Use take or limit for exploration instead of full table scans. The key principle is that performance is directly proportional to the amount of data processed.

### Materialized Views
Materialized views store precomputed aggregation results that automatically update as new data arrives. A materialized view consists of a materialized part containing historical aggregations and a delta containing new data since the last background update. At query time, the system combines both parts to give you fresh results. A background process periodically merges the delta into the materialized part. You create a materialized view using the .create materialized-view command with a summarize statement, and you query it like a regular table. Materialized views are useful when the same aggregation is run repeatedly because they trade storage for query speed.

### Stored Functions
Stored functions encapsulate KQL queries that accept parameters for reuse and consistency. You create a function using the .create-or-alter function command with parameters and a query body. You call the function like a table by passing values for the parameters. Stored functions are useful in environments where multiple people write queries and the same transformation or filtering logic must be applied consistently.

### Copilot for Real-Time Intelligence
When enabled by an administrator, Copilot provides AI-powered KQL code generation in the KQL Queryset. It opens as a side pane and generates KQL code based on natural language questions about your data.

### Exam Gotchas
KQL is case-sensitive for all identifiers, and failing to match exact casing is a common error. The pipeline concept in KQL means operations are sequential and order matters significantly. Materialized views store precomputed results and update incrementally, while standard views run the query every time with no stored results. Functions are reusable logic calculated at query time, while materialized views are reusable results that are precalculated and auto-updating. Time-based filtering using ago is indexed and therefore fast. Join order matters because KQL processes the first table to match against the second, so smaller table first is more efficient. When reading partitioned data via a direct folder path, the partitioning column is omitted from the result set. The KQL Queryset supports both KQL and T-SQL, though T-SQL is a subset of what KQL provides for time-series analysis. The Eventhouse is the container and KQL databases are inside it, and creating an Eventhouse auto-creates one KQL database while additional databases can be created within the same Eventhouse.
