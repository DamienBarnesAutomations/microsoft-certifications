## Dataflows Gen2

**Core Concept**
Dataflows Gen2 are cloud-based ETL tools using Power Query Online to ingest, transform, and load data into Fabric destinations (Lakehouse, Warehouse, SQL Database) or external targets (Azure SQL Database, Azure Data Explorer, Azure Synapse Analytics), with the dataflow preserving all transformation steps for reuse.

**Technical Specifications**
- **ETL vs. ELT pattern:**
  - **ETL:** Dataflow extracts from source, transforms, then loads to destination. Single dataflow handles full pipeline.
  - **ELT:** Pipeline extracts and loads raw data into destination first (e.g., Lakehouse), then a separate Dataflow Gen2 connects to that Lakehouse data to cleanse and transform it. Separates extraction from transformation.
- **Destinations:** Lakehouse, Warehouse, SQL Database (Fabric-native); also Azure SQL Database, Azure Data Explorer, Azure Synapse Analytics.
- **Adding a destination is optional** — dataflow can serve as a data source for data analysts connecting via Power BI Desktop or as a source for pipeline activities without materializing to a destination.
- **Sources:** Cloud/on-premises relational databases, Excel/flat files, SharePoint, Salesforce, Spark, Fabric lakehouses.
- **Transformations:** Filter/Sort, Pivot/Unpivot, Merge/Append, Split/Conditional split, Replace values/Remove duplicates, Add/Rename/Reorder/Delete columns, Rank/Percentage, Top/Bottom N.
- **Power Query Online interface components:**
  - **Ribbon:** Source connectors, transformation tools, parameter management, default data destination configuration
  - **Queries pane:** Lists data sources (called queries during editing, tables when loaded). Supports duplicate, reference, and disable-load per query
  - **Diagram view:** Visual map of query connections and applied transformations; toggle on/off
  - **Data Preview pane:** Subset of data showing transformation effects; interactive (drag-drop reorder columns, right-click filter)
  - **Query Settings pane:** Applied Steps — each transformation is a step; gear icon on most steps allows modification; right-click for rename, reorder, delete; Advanced Editor for M code viewing/editing
- **M code:** Every transformation generates M code behind the scenes; accessible via Advanced Editor in Query Settings pane
- **Horizontal partitioning:** A global dataflow can be created, then data analysts create specialized dataflows (referencing the global one) for specific needs
- **Requirements:** Fabric capacity workspace (no RLS support; not a replacement for a data warehouse)
- **Execution:** Manual, refresh schedule, or as a pipeline activity
- **Benefits:** Reusable ETL logic, consistent data (e.g., standard date dimension), self-service subsets, performance optimization (extract once for reuse), reduced data source complexity, low-code interface
- **Limitations:** No row-level security support, not a replacement for a data warehouse, requires Fabric capacity
- **Discoverability:** Make dataflow discoverable so data analysts connect through Power BI Desktop

**Architectural Logic**
Dataflows Gen2 decouple transformation logic from orchestration. The dataflow defines the "what" (transformations as Power Query M steps), while pipelines define the "when" and "how" (sequencing, dependencies, error handling). Use Dataflows Gen2 over raw Copy Data when transformations must be applied during ingestion (filtering, cleansing, merging multiple sources). Use Dataflows Gen2 over Notebooks when the team is comfortable with Power Query's low-code interface and transformations are straightforward. Use a Pipeline to wrap a Dataflow when additional orchestration is required (e.g., run a stored procedure or notebook after dataflow completes). Anti-pattern: using a Dataflow for complex algorithmic transformations that would be better handled by Spark notebooks, or using a standalone Dataflow when pipeline-level dependency management is needed.

**Implementation Workflow**
1. Create Dataflow Gen2 in Data Factory workload, Power BI workspace, or directly in a lakehouse.
2. Select data source from the ribbon (cloud/on-premises database, file, SharePoint, etc.).
3. Apply transformations using ribbon tools, right-click actions on Data Preview, or Power Query Online interface.
4. Configure data destination in Query Settings pane (optional — can skip if dataflow serves only as a source).
5. Publish dataflow.
6. Run manually, set a refresh schedule, or integrate into a Data Pipeline (add Dataflow Gen2 activity to pipeline canvas, link to specific dataflow, chain subsequent activities).

**Exam Gotchas & Distinctions**
- **ETL vs. ELT with Dataflows:** ETL = Dataflow does Extract, Transform, Load in one step. ELT = Pipeline loads raw data first, then Dataflow connects to the loaded data to transform. The exam tests understanding of when to use each pattern.
- **Queries vs. Tables:** In the Power Query interface, sources are called "queries"; once loaded to a destination, they become "tables."
- **Destination optional:** A dataflow can exist without a configured destination, serving purely as a logical data source for pipelines or Power BI Desktop. This differs from pipelines where every Copy Data activity must have a source and destination.
- **No destination ≠ no output:** Even without a destination, the dataflow's transformed output is accessible as a data source reference.
- **Dataflow alone vs. in a Pipeline:** Standalone dataflows are limited to their own refresh schedule; pipeline integration enables complex dependencies, error handling, and sequential activities across multiple tools.
- **Fabric capacity required:** Dataflows Gen2 do not work on Trial SKUs for all scenarios; Fabric capacity workspace requirement is explicit.
- **Power BI Desktop connection:** Published dataflows can be used as data sources in Power BI Desktop if made discoverable — reducing duplicate data preparation for report developers.

## Data Pipelines

**Core Concept**
Data pipelines in Fabric (sharing the same architecture as Azure Data Factory) define a sequence of activities — data transformation (Copy Data, Dataflow Gen2, Notebook, Stored procedure, Delete) and control flow (loops, conditionals, variables, parameters) — orchestrated on a visual canvas to automate ETL/ELT processes.

**Technical Specifications**
- **Activity categories:**
  - **Data transformation activities:** Copy Data, Dataflow Gen2, Notebook, Stored procedure, Delete data, and others
  - **Control flow activities:** ForEach, Until, If Condition, Set Variable, Wait, and others for implementing branching and looping logic
- **Copy Data activity:** High-performance movement between supported sources and destinations without transformations. Graphical configuration wizard. Use when raw data movement is required without transformation. Wide range of source connections supported. In OneLake: lakehouse, warehouse, SQL Database, and others.
- **Parameters:** Enable pipeline reusability — provide specific values per run (e.g., folder name). Defined in pipeline settings, referenced in activities.
- **Pipeline runs:** Each execution creates a unique run ID. Review run details for success/failure and specific settings used. Runs can be on-demand (interactive) or scheduled.
- **Validation:** Use Validate option to check configuration before running.
- **Run history:** Accessible from the pipeline canvas or pipeline item listing in workspace page.
- **Templates:** Predefined activity sequences for common ingestion scenarios. Access via Templates tile in new pipeline. Customize on canvas after creation.
- **Destinations:** Lakehouse, Warehouse, SQL Database (within OneLake/Fabric).
- **Triggers:** Manual or scheduled.

**Architectural Logic**
Pipelines decouple "execution logic" (sequencing, dependencies, scheduling) from "transformation logic" (which is handled by activities like Dataflows Gen2, Notebooks, or Stored procedures). This separation allows each activity to be developed, tested, and versioned independently. Use Copy Data over Dataflows Gen2 when moving large volumes of raw data without transformation — Copy Data is optimized for speed and volume. Use a Pipeline with a Dataflow activity when you need to orchestrate transformations followed by other steps (e.g., Dataflow → Stored procedure → Notebook). Use control flow activities when the pipeline must make decisions based on conditions (e.g., If Condition to check if a file exists before copying). Anti-pattern: using Copy Data for data transformation (use Dataflows or Notebooks instead), or using a standalone Dataflow when pipeline-level orchestration (dependencies across multiple activities) is required.

**Implementation Workflow**
1. Create a Pipeline in the Fabric workspace (Data Factory workload).
2. Drag activities from the activity library to the canvas (Copy Data, Dataflow, Notebook, etc.).
3. Connect activities based on outcome (Success, Failure, Completion) to define execution flow.
4. Define parameters in pipeline settings for reusability.
5. For Copy Data: use the graphical wizard to select source connection, destination, and column mapping.
6. For pipeline templates: select Templates tile, choose matching scenario, customize resulting activities.
7. Validate the pipeline configuration.
8. Run interactively or set a schedule.

**Exam Gotchas & Distinctions**
- **Control Flow vs. Data Transformation:** Control flow activities (ForEach, If Condition, Wait) manage the execution path of the pipeline itself. Data transformation activities (Copy Data, Dataflow, Notebook) move/change data. These are separate categories with different purposes.
- **Copy Data vs. Dataflow Gen2:** Copy Data is optimized for blind, high-speed raw data movement without transformations. Dataflow Gen2 is for low-code visual transformations during ingestion. Using Copy Data for transformation is an anti-pattern.
- **Pipeline vs. Dataflow scheduling:** Standalone dataflows have their own refresh schedule. Pipelines can wrap dataflows and add dependency management, sequential activity execution, and conditional logic.
- **Template vs. Custom Pipeline:** Templates are starting points for common scenarios; custom pipelines are built from scratch for unique requirements. Templates can be customized after creation.
- **Unique run ID:** Each pipeline run generates a unique ID used for monitoring and troubleshooting.
- **Fabric pipelines share ADF architecture:** Familiarity with Azure Data Factory directly transfers to Fabric pipelines — same concepts of activities, linked services, datasets, triggers, and parameters.

## Apache Spark in Fabric

**Core Concept**
Apache Spark in Microsoft Fabric provides distributed parallel processing via Spark pools (head node driver + worker node executors) for large-scale data analytics, supporting PySpark, Spark SQL, Scala, Spark R, and Java with configurable runtimes, environments, and optimizations (native execution engine, high concurrency mode).

**Technical Specifications**
- **Spark pool architecture:**
  - **Head node** — runs the driver program that coordinates distributed processing
  - **Worker nodes** — run executor processes that perform actual data processing tasks
  - "Divide and conquer" approach: data is distributed across worker nodes for parallel processing
- **Pool types:**
  - **Starter pool:** Default per workspace; enables quick Spark job startup with minimal setup
  - **Custom pools:** Created with specific node configurations for particular workload needs. Administrator can disable custom pool creation at Fabric capacity level.
- **Configuration settings:**
  - **Node Family:** Memory optimized (recommended for most workloads)
  - **Autoscale:** Automatic node provisioning as needed; configure initial and maximum nodes
  - **Dynamic allocation:** Dynamically allocate executor processes based on data volumes
  - Default pool setting: set starter pool or a custom pool as default for the workspace
  - Spark pool settings configured in Workspace Settings > Capacity settings > Data Engineering/Science Settings
- **Languages:** PySpark, Spark SQL, Scala, Spark R, Java. Most workloads use PyPython and Spark SQL in practice.
- **Runtimes and Environments:**
  - **Runtime:** Version of Apache Spark, Delta Lake, Python, and other core components
  - **Environment:** Runtime + custom public libraries (PyPI) + custom uploaded package files (.whl/.jar) + Spark config properties + resource files
  - Multiple environments can be defined for diverse processing tasks
  - After creating a custom environment, set it as default in workspace settings
  - Environments ensure parity between development (notebooks) and production (Spark jobs)
- **Native execution engine:**
  - Vectorized processing engine running Spark operations directly on lakehouse infrastructure
  - Improves performance significantly for Parquet/Delta file formats
  - Enable settings: `spark.native.enabled: true` and `spark.shuffle.manager: org.apache.spark.shuffle.sort.ColumnarShuffleManager`
  - Can be enabled at environment level (persistent) or notebook level via `%%configure` magic
- **High concurrency mode:**
  - Shares Spark sessions across multiple concurrent users or processes
  - Multiple users can run notebooks sharing the same session while maintaining code isolation (separate variable namespaces)
  - Also applicable to Spark jobs (non-interactive script execution)
  - Enable in workspace settings > Data Engineering/Science section
- **Automatic MLFlow logging:** Enabled by default; implicitly logs ML experiment activity without explicit code. Can be disabled in workspace settings.
- **Spark administration:** Admins manage Spark settings at Fabric capacity level, restricting/overriding workspace-level Spark settings.
- **Notebooks vs. Spark Job Definitions:**
  - **Notebooks:** Interactive, cell-based (Markdown + code). Supports multiple languages via magics (`%%pyspark`, `%%spark`, `%%sql`, `%%r`). Results displayed under each cell. Built-in charting. Use for exploration and development.
  - **Spark Job Definitions:** Script-based, on-demand or scheduled. Supports reference files (e.g., Python code files with function definitions) and lakehouse associations. Use for production automation.
- **Spark sessions:** Initiated on first cell execution; persist until stopped or timeout from inactivity.

**Architectural Logic**
Spark separates compute (pools) from storage (OneLake), enabling independent scaling of each. The distributed architecture uses a driver program (head node) to coordinate work across executor processes (worker nodes), handling task distribution and result collation transparently. The starter pool minimizes startup latency for ad-hoc workloads, while custom pools provide tailored configurations for specific processing needs. Use notebooks over Spark Job Definitions for iterative development and exploration (the "developer loop": experiment → see result → iterate). Use Spark Job Definitions over notebooks for production automation where reliability, scheduling, and repeatability are required. Use High Concurrency Mode when multiple users need to run Spark notebooks concurrently in the same workspace to reduce session startup resource waste. Use the Native Execution Engine when working with large Parquet/Delta datasets to bypass JVM overhead with vectorized processing. Anti-pattern: using notebooks for scheduled production data pipelines (use Spark Job Definitions or Pipeline-integrated notebook activities instead).

**Implementation Workflow**
1. **Configure Starter Pool** in Workspace Settings > Capacity settings > Data Engineering/Science Settings. Set Node Family (Memory optimized recommended), Autoscale (initial/max nodes), and Dynamic allocation.
2. **Create custom pools** (optional) in the same settings area with specific node configurations. Set one as default.
3. **Create Environment:** Name → select Spark runtime version → add PyPI libraries → upload custom .whl/.jar files → set Spark config properties → upload resource files → assign to notebook or Spark pool.
4. **Enable Native Execution Engine:** Set `spark.native.enabled: true` and `spark.shuffle.manager: org.apache.spark.shuffle.sort.ColumnarShuffleManager` at environment level or via `%%configure` in notebook.
5. **Enable High Concurrency Mode** in workspace settings if multiple concurrent users need shared sessions.
6. **Create Notebook** for interactive exploration: write code in cells (PySpark, Spark SQL, Scala, R), use `%%` magics to switch languages within a cell, run interactively.
7. **Create Spark Job Definition** for production automation: specify script, optional reference file, lakehouse association, and schedule.

**Exam Gotchas & Distinctions**
- **Driver vs. Executor:** The driver (head node) is the brain/coordinator that distributes tasks; executors (worker nodes) are the muscle that processes data. Common exam confusion point.
- **Runtime vs. Environment:** Runtime is the base software version (Spark, Delta Lake, Python). Environment is the runtime PLUS the specific libraries and configs needed for a project. Candidates often conflate the two.
- **Native Execution Engine settings:** Must set BOTH `spark.native.enabled` to true AND `spark.shuffle.manager` to the ColumnarShuffleManager. Setting only one is insufficient.
- **High Concurrency Mode isolation:** Session (compute resources) is shared, but state (variables, functions) remains isolated between notebooks. Shared session ≠ shared variables.
- **Notebooks vs. Spark Job Definitions:** Notebooks are for interactive dev exploration; Job Definitions are for automated production runs. Using notebooks for production scheduling is an anti-pattern.
- **Starter pool is per workspace:** One starter pool per workspace by default. Custom pools must be explicitly created.
- **Autoscale vs. Dynamic allocation:** Autoscale controls the number of nodes provisioned. Dynamic allocation controls how many executor processes run on those nodes. They work together but are independent settings.

## Spark Dataframes and Spark SQL

**Core Concept**
Spark Dataframes are distributed collections of data organized into named columns (built on RDDs but with a higher-level API), and Spark SQL provides a SQL interface to query them — together enabling large-scale data manipulation with explicit or inferred schemas, partitioning, and a catalog of managed/external tables and views.

**Technical Specifications**
- **Dataframe:** Primary structured data API in Spark. Built on RDDs (Resilient Distributed Datasets). Similar to Pandas Dataframes but optimized for distributed processing across a cluster.
- **Loading data:**
  - `spark.read.load()` with `format` parameter (e.g., 'csv', 'parquet', 'delta')
  - Common options: `header=True` for CSV with column names in first row
- **Schema specification:**
  - **Inferred:** Spark scans data to guess column types. Slower, error-prone (type mismatches possible).
  - **Explicit:** Manually defined via `StructType` and `StructField`. Faster (skips scan), prevents type mismatches.
  - Explicit schema example: `productSchema = StructType([StructField("ProductID", IntegerType()), StructField("ProductName", StringType())])`
  - Import from `pyspark.sql.types import *`
- **Dataframe operations (PySpark):**
  - `.select("col1", "col2")` — subset of columns; shorthand: `df["col1", "col2"]`
  - `.where((df["col1"] == value) | (df["col1"] == value2))` — filtering with Boolean conditions
  - `.filter()` — equivalent to `where()`
  - `.groupBy("col").count()` — aggregation
  - `.limit(n)` — first n rows
  - Method chaining: `.select().where().groupBy().count()`
- **Saving data:**
  - `.write.mode("overwrite").parquet("path")` — save as Parquet files
  - `.write.format("delta").saveAsTable("table_name")` — save as managed Delta table in catalog
  - Write modes: `overwrite` (replaces), `append` (adds to existing)
- **Partitioning:**
  - `.write.partitionBy("ColumnName").parquet("path")` — creates folder hierarchy (`ColumnName=Value/`)
  - Multi-column partitioning: creates nested folder hierarchy (e.g., `Year=2024/Month=01/`)
  - **Partition pruning:** Engine skips entire folders that don't match query filter, reducing disk I/O
  - **Reading partitioned data:** Load specific partition by path: `spark.read.parquet('path/ColumnName=Value')`. Partitioning columns are OMITTED from resulting dataframe (implicit in folder name).
  - Partitioning optimization benefit: eliminates unnecessary disk I/O for filtered queries
- **Spark catalog (metastore):** Manages relational objects — views (temporary) and tables (persistent)
  - **Temporary views:** `df.createOrReplaceTempView("view_name")`. Automatically deleted at end of session.
  - **Managed tables:** Stored in `Tables` location. Fabric manages both metadata and data. `df.write.format("delta").saveAsTable("table_name")`. Deleting table deletes underlying data.
  - **External tables:** Metadata in catalog, data in external location (e.g., `Files` folder). `spark.catalog.createExternalTable`. Deleting table preserves underlying data.
  - **Preferred format in Fabric:** Delta format (supports ACID transactions, versioning, streaming)
- **Spark SQL API:**
  - `spark.sql("SELECT ... FROM table WHERE ...")` — returns a dataframe
  - `%%sql` magic in notebooks — run SQL directly, results auto-displayed as table
  - SQL and PySpark can work interchangeably on the same catalog objects
- **Visualization in notebooks:**
  - Built-in charting: display dataframe results as chart, customize chart properties
  - Graphics libraries: Matplotlib (requires `.toPandas()` conversion), Seaborn, etc. for custom charts

**Architectural Logic**
The dataframe API provides a familiar tabular interface (like Pandas) but distributes operations across a cluster, handling partitioning, parallel execution, and fault tolerance transparently. Spark SQL bridges the gap between data engineers (PySpark) and data analysts (SQL) by allowing both to work on the same catalog objects. Managed vs. external tables provide flexibility: use managed tables when you want Fabric to handle the full lifecycle (create, update, delete), and external tables when you want the data to persist independently of the catalog metadata. Use explicit schemas over inferred schemas to prevent type errors and improve loading performance (Skips the data scan step). Use partitioning on large datasets (typically >1 TB) for columns frequently used in WHERE filters, but avoid over-partitioning on high-cardinality columns that creates too many small files. Use Delta format over Parquet for tables that need ACID transactions, versioning (time travel), and streaming support.

**Implementation Workflow**
1. Load data:
   ```python
   df = spark.read.load('path/file.csv', format='csv', schema=explicitSchema, header=True)
   ```
2. Inspect: `display(df.limit(10))`
3. Transform: chain `.select()`, `.where()`, `.groupBy()`, `.count()` as needed.
4. Create catalog views for SQL access: `df.createOrReplaceTempView("view_name")`
5. Create managed Delta table: `df.write.format("delta").saveAsTable("table_name")`
6. Partition large datasets: `df.write.partitionBy("Category").mode("overwrite").format("delta").saveAsTable("table_name")`
7. Query via Spark SQL: `spark.sql("SELECT ...")` or `%%sql` magic.
8. Export to Parquet: `df.write.mode("overwrite").parquet("path")`

**Exam Gotchas & Distinctions**
- **Inferred vs. Explicit schema:** Inferred requires Spark to scan data first (slower, risk of type mismatches). Explicit schema skips the scan (faster, type-safe). This performance difference is exam-relevant.
- **Managed vs. External tables:** Managed = Delete table deletes data. External = Delete table preserves data files. The exam tests this distinction.
- **Partitioning anti-pattern:** Over-partitioning (too many small files from high-cardinality columns) degrades performance. Partition columns used frequently in WHERE filters only.
- **Column omission in partitioned reads:** When reading a specific partition folder, the partitioning column is not included in the resulting dataframe (because all rows share the same value). Candidates often miss this.
- **Delta is the preferred format:** While Spark supports multiple formats, Microsoft Fabric strongly prefers Delta for its ACID, versioning, and streaming capabilities.
- **toPandas() conversion:** Matplotlib and most Python visualization libraries require Pandas DataFrames, not Spark DataFrames. Use `.toPandas()` to convert — this pulls data to the driver node, so use selectively on aggregated/subset data.
- **%%sql vs. spark.sql():** `%%sql` is a notebook magic that runs SQL directly and auto-displays results. `spark.sql()` returns a DataFrame that requires `display()` or further processing. Both query the same catalog.

## Eventhouse and KQL

**Core Concept**
An Eventhouse is a container for one or more KQL databases optimized for high-volume, append-only time-series data with automatic ingestion-time partitioning, supporting Kusto Query Language (KQL) and T-SQL for querying, with sub-second latency on recent data.

**Technical Specifications**
- **Eventhouse:** Container housing one or more KQL databases. Automatically creates a default KQL database with the same name.
- **KQL database characteristics:**
  - Automatically partitions data by ingestion time — recent data quickly accessible without scanning all historical data
  - Optimized for immutable, append-only events — data rarely updated or deleted because events represent what happened at specific moments
  - Time-series data model: timestamp is as important as the event value
  - Fundamentally different from relational databases (which focus on updates and relationships)
- **Data ingestion methods:**
  - Direct: Local files, Azure Storage, Amazon S3
  - Streaming: Azure Event Hubs, Fabric Eventstream, Real-Time Hub
  - Connectors: Apache Kafka, Confluent Cloud Kafka, Apache Flink, MQTT, Amazon Kinesis, Google Cloud Pub/Sub
  - Other: OneLake, Data Factory Copy, Dataflows
  - Get Data menu in Eventhouse UI
- **Database shortcuts:** Query data from external KQL databases in other Eventhouses or Azure Data Explorer without copying data — appears as if stored locally.
- **OneLake availability:** Enable per KQL database or table to make data accessible across Fabric (Power BI, Warehouse, Lakehouse, other services).
- **KQL Queryset:** Workspace for running and managing queries against KQL databases. Auto-created with each KQL database. Supports multiple query tabs, saved queries, sharing. Supports both KQL and T-SQL.
- **KQL syntax:**
  - Pipeline approach: pipe (`|`) operator passes data from one operation to the next ("funnel" — start with full dataset, incrementally reduce)
  - **Case-sensitive:** Everything — table names, column names, function names, operators, keywords, string values. `TaxiTrips` ≠ `taxitrips`.
  - Core operators:
    - `where` — filter rows (supports time-based, value-based conditions)
    - `project` — select columns
    - `take` — sample rows (exploration)
    - `summarize ... by ...` — aggregation (count, avg, sum, min, max, etc.)
    - `sort by` — ordering
    - `join` — combine tables
    - `limit` — limit results
  - Simplest query: `TableName` (returns all columns, row limit depends on tool defaults)
  - Time filtering: `where pickup_datetime > ago(30min)` — uses time index
- **KQL optimization:**
  - Filter early — especially time-based filters that leverage indexes
  - Order filters by elimination power — most-restrictive filter first
  - Reduce columns early — `project` before `where`, `summarize`, or `join`
  - Join order: smaller table first (KQL processes first table to match against second)
  - Use `take` or `limit` for exploration instead of full table scans
  - Key principle: performance is directly proportional to data processed
- **Materialized views:**
  - Precomputed aggregation results that auto-update as new data arrives
  - Two parts: **materialized part** (historical aggregations) + **delta** (new data since last background update)
  - At query time, system combines both parts for fresh results
  - Background process periodically merges delta into materialized part
  - Creation: `.create materialized-view ViewName on table TableName { TableName | summarize ... by ... }`
  - Query like a regular table: `ViewName | where ...`
- **Stored functions:**
  - Encapsulated KQL queries accepting parameters for reuse and consistency
  - Creation: `.create-or-alter function FunctionName(ParamName:ParamType) { query }`
  - Execution: called like a table — `FunctionName(value) | take 10`
- **Copilot for Real-Time Intelligence:** AI-powered KQL code generation in KQL Queryset when enabled by administrator. Opens as side pane.
- **Visualizations in KQL queryset:** Query results can be rendered as charts, tables, and other visual formats.

**Architectural Logic**
Eventhouse/KQL databases implement the "digital conveyor belt" pattern — events flow in continuously, get automatically organized by ingestion time, and are immediately available for analysis. The automatic time-based partitioning ensures that queries for recent data do not scan historical data, making sub-second latency achievable even on billions of rows. Use Eventhouse over Lakehouse when the data is streaming/append-only time-series (IoT sensor readings, application logs, clickstreams) and low-latency ingestion with time-window analysis is the primary requirement. Use materialized views over live queries when the same aggregation is run repeatedly — the materialized view trades storage for query speed by maintaining precomputed results updated by a background process. Use stored functions over inline queries when the same transformation/filtering logic must be applied consistently by multiple team members. Anti-pattern: using KQL databases for transactional workloads with frequent UPDATE/DELETE operations (use Warehouse instead), or using materialized views for ad-hoc queries that are run infrequently.

**Implementation Workflow**
1. Create an Eventhouse in a Fabric workspace (auto-creates default KQL database).
2. Ingest data via Get Data menu (Eventstream, direct connectors, files, or Data Factory).
3. (Optional) Enable OneLake availability for cross-service access.
4. (Optional) Create database shortcuts to external KQL databases or Azure Data Explorer.
5. Write KQL queries in the KQL Queryset:
   - `TableName | where condition | project columns | summarize ... by ... | take N`
6. Create materialized views for precomputed aggregations:
   ```
   .create materialized-view ViewName on table TableName { TableName | summarize ... by ... }
   ```
7. Create stored functions for reusable logic:
   ```
   .create-or-alter function FunctionName(Param:Type) { TableName | where condition | project ... }
   ```
8. Build Real-Time Dashboards (covered in M3) or set up Activator rules (covered in M3/M5).

**Exam Gotchas & Distinctions**
- **KQL case sensitivity:** KQL is strictly case-sensitive for ALL identifiers. `TaxiTrips` ≠ `taxitrips` ≠ `TAXITRIPS`. This is a common source of query errors and an exam-relevant detail.
- **Pipeline (funnel) concept:** KQL operations are sequential — each pipe `|` passes the result to the next operation. Order matters significantly. Unlike SQL subqueries, KQL processes left-to-right, top-to-bottom.
- **Materialized View vs. Standard View:** Standard views run the query every time (no storage, always live). Materialized views store precomputed results and update incrementally (faster query, periodic freshness). The exam tests this distinction.
- **Function vs. Materialized View:** Functions are reusable logic (calculated at query time). Materialized views are reusable results (precalculated, auto-updating). Different use cases.
- **Time-based filtering is free (indexed):** KQL databases index by ingestion time, making `ago()` filters especially efficient compared to filters on non-time columns.
- **Join order matters:** KQL processes the first (left) table to match against the second (right). Smaller table first = less data to process. Opposite of some SQL join engines.
- **Partitioning columns omitted in path reads:** When reading partitioned data via direct folder path, the partitioning column is not in the resulting KQL result set — analogous to Spark's behavior.
- **KQL vs. T-SQL support:** KQL Queryset supports both KQL (pipeline-based, time-series optimized) and T-SQL (familiar relational syntax). KQL provides richer time-series analysis. T-SQL is a subset.
- **Eventhouse vs. KQL database:** Eventhouse is the container; KQL databases are inside it. Creating an Eventhouse auto-creates one KQL database. Additional KQL databases can be created within the same Eventhouse.
