## Card 1: Real-Time Intelligence Overview

### What It Is

Real-Time Intelligence in Microsoft Fabric is an integrated set of components designed to ingest, process, analyze, and visualize streaming data as it arrives. It provides a unified experience for working with data in motion, from raw event ingestion through to actionable dashboards and automated responses. Rather than waiting for batch processing cycles, Real-Time Intelligence lets you react to events within seconds or even milliseconds.

### Key Details

#### Events vs Streams

An event is a single, discrete record representing something that happened at a specific point in time, such as a sensor reading, a transaction, or an error log entry. A stream is an ordered sequence of events flowing from a source over time. Understanding this distinction matters because Eventstreams processes streams as continuous flows while individual events are what you query and analyze in Eventhouse and KQL databases.

#### Real-Time Hub

The Real-Time Hub serves as a central catalog for all data-in-motion across your Fabric environment. It organizes data sources into four categories: data sources (your own streams and event hubs), Azure sources (connections to Azure Event Hubs, IoT Hub, and Service Bus), Fabric events (activities happening within Fabric itself such as pipeline runs or notebook executions), and Azure events (Azure Monitor alerts and Azure Service Bus messages). The hub gives you a single place to discover, manage, and connect to streaming data regardless of where it originates.

#### Core Components

Eventstreams is the visual, no-code engine for capturing, transforming, and routing streaming data to various destinations. Eventhouse is the high-performance analytics engine built on Kusto technology that stores and queries event data using KQL. KQL Queryset provides an interactive workspace for writing and executing KQL queries against Eventhouse databases. Real-Time Dashboards deliver live visual monitoring with auto-refreshing tiles powered by KQL queries. Activator is the event detection and rules engine that monitors streaming data and triggers automated actions when conditions are met.

#### Copilot for Real-Time Intelligence

Copilot assists with real-time tasks by generating KQL queries from natural language descriptions, suggesting transformations in Eventstreams, and helping you build dashboard tiles. It can summarize data patterns and recommend optimizations for your streaming pipelines and queries.

#### Common Use Cases

Real-Time Intelligence supports scenarios such as delivery tracking where you monitor package locations and ETAs in real time, equipment monitoring on manufacturing floors to detect anomalies before failures occur, fraud detection that flags suspicious transactions as they happen, website performance monitoring that tracks page load times and error rates, and system health monitoring that alerts on infrastructure degradation across your environment.

### Exam Gotchas

- Real-Time Intelligence is not a single service but a collection of integrated Fabric components working together.
- The Real-Time Hub is distinct from Eventstreams; the hub is a catalog while Eventstreams is the processing engine.
- Events and streams are not interchangeable terms in exam questions; an event is one record, a stream is a sequence.
- Copilot can assist with KQL query generation but you still need to understand KQL fundamentals for the exam.
- Activator is not a replacement for Azure Monitor alerts; it is a Fabric-native alternative with its own rule model.

## Card 2: Eventstream

### What It Is

Eventstream is a visual, no-code engine within Microsoft Fabric that provides a drag-and-drop canvas for capturing, transforming, and routing streaming data. It allows you to build complex event processing pipelines without writing code, connecting various sources to destinations through a graphical interface that shows data flow in real time.

### Key Details

#### Sources

Microsoft sources include Azure Event Hubs for high-throughput event ingestion, Azure IoT Hub for device-to-cloud communication, Azure Service Bus for enterprise messaging, and Change Data Capture (CDC) for capturing database changes in real time. Azure event sources include Azure Blob Storage for file-based events. Fabric events capture internal Fabric activities such as pipeline runs and monitoring events. External sources support Apache Kafka, Google Cloud Pub/Sub, and MQTT protocols for connecting to third-party streaming platforms.

#### Transformations

Filter lets you remove events that do not meet specified criteria, keeping only relevant data flowing downstream. Manage fields allows you to add, remove, or rename columns to shape event data into the structure you need. Aggregate performs calculations such as count, sum, average, min, or max over grouped data. Group by with tumbling windows divides the event stream into fixed-size, non-overlapping time intervals for aggregation, while sliding windows create overlapping intervals for smoother trend analysis. Union combines multiple streams into a single output stream. Join merges data from two or more streams based on matching conditions. Expand takes a column containing JSON or arrays and flattens it into multiple rows or columns.

#### Destinations

Eventhouse and KQL databases receive transformed events for high-performance analytics and querying. Lakehouse and Delta tables store events in the OneLake Delta format for use with SQL analytics and Spark processing. Derived streams create copies of the processed stream for content-based routing, allowing you to split a single source into multiple downstream paths based on event attributes. Fabric Activator sends events to the Activator service for automated rule-based monitoring and alerting. Custom endpoints deliver events to external systems via HTTP POST or other configured protocols.

#### Canvas Workflow

The Eventstream canvas follows a left-to-right flow starting with source connectors on the left, transformation nodes in the middle, and destination connectors on the right. You drag components from the toolbox onto the canvas, connect them with lines to define data flow, and configure each node through property panels. The canvas updates in real time to show sample data flowing through the pipeline, helping you validate your design before publishing.

### Exam Gotchas

- Eventstreams supports both Microsoft-native sources (Event Hubs, IoT Hub, Service Bus) and external sources (Kafka, Pub/Sub, MQTT).
- Derived streams are not the same as destinations; they create intermediate branches for routing logic.
- Tumbling windows never overlap while sliding windows do; this distinction affects aggregation results.
- CDC sources capture row-level changes from databases but require appropriate database permissions and configuration.
- The canvas shows sample data during design but actual throughput depends on source configuration and processing complexity.
- You cannot use custom SQL transformations in Eventstreams; all transformations are visual and pre-built.

## Card 3: Eventhouse and KQL Databases

### What It Is

Eventhouse is a high-performance analytics engine in Microsoft Fabric designed for storing and querying massive volumes of event data. It uses Kusto Query Language (KQL) for analysis and provides automatic ingestion-time partitioning with an append-only, immutable storage model that ensures data integrity and enables high-speed queries across billions of events.

### Key Details

#### Architecture and Storage

Eventhouse automatically partitions data at ingestion time based on time ranges, distributing events across storage nodes for parallel query execution. The append-only model means events cannot be modified or deleted after ingestion, ensuring data integrity and supporting compliance requirements. Each Eventhouse can contain multiple KQL databases, and each database stores its own tables, functions, and materialized views independently.

#### KQL Syntax Fundamentals

KQL uses a pipeline approach where each operator transforms its input and passes results to the next operator in the chain. The pipe character separates operators, and results flow from top to bottom through the query. KQL is case-sensitive for everything including table names, column names, function names, and string literals, so `MyTable` and `mytable` are different identifiers. Unlike T-SQL, KQL does not use semicolons to terminate statements and does not have UPDATE or DELETE operations since the storage is append-only.

#### Core KQL Operators

Take returns a specified number of arbitrary rows from the result set without any ordering guarantee, useful for quick data sampling. Where filters rows based on a boolean condition, and placing it early in a query improves performance by reducing the dataset before subsequent operators. Project selects, renames, or creates specific columns, limiting the columns returned and reducing memory usage. Summarize performs aggregations such as count, sum, avg, min, max, and distinct over grouped data. Sort by orders the result set by one or more columns in ascending or descending direction. Join combines rows from two tables based on a matching condition, with common types including inner, left, right, and full joins. Limit is a performance-friendly alternative to take that returns a specified number of rows after all other processing.

#### Query Optimization

Filter early using the time index column to leverage Eventhouse partitioning and skip irrelevant time ranges. Reduce columns early by using project to eliminate unnecessary fields before aggregation or join operations. When writing joins, place the smaller table first so that the join operation uses less memory. Limit aggregation results by adding take or limit at the end of complex queries to prevent excessive memory consumption during testing and development.

#### Materialized Views

Materialized views provide precomputed aggregations that are continuously updated as new data arrives. They consist of two parts: the materialized part containing precomputed results for historical data and the delta part holding newly arrived data that has not yet been incorporated. Queries against materialized views always return the current, up-to-date result by combining both parts transparently. Common use cases include maintaining running counts, distinct value tracking, and time-windowed aggregations without reprocessing raw data.

#### Stored Functions

Stored functions are reusable, parameterized KQL queries saved within a database. They accept input parameters and return query results, allowing you to encapsulate complex logic and call it from other queries or dashboards with different parameter values. This promotes code reuse and consistency across multiple query contexts.

#### T-SQL Support

Eventhouse supports a subset of T-SQL syntax, allowing you to write queries using familiar SQL constructs for basic operations. However, not all T-SQL features are available, and KQL provides additional capabilities specifically optimized for event analytics such as time-series functions and advanced parsing operators.

#### OneLake Integration and Database Shortcuts

KQL databases in Eventhouse store their data in OneLake automatically, making the data accessible to other Fabric workloads including Spark notebooks and SQL analytics. Database shortcuts allow you to create references to other KQL databases, enabling cross-database queries without data duplication.

#### KQL Queryset

KQL Queryset provides an interactive workspace for writing, executing, and managing KQL queries against Eventhouse databases. It supports query results visualization, parameterized queries, and the ability to pin query results to Real-Time Dashboards for live monitoring.

### Exam Gotchas

- KQL is case-sensitive for all identifiers; a misspelled table or column name will fail silently or return errors.
- KQL does not support UPDATE or DELETE operations; the append-only model is immutable.
- The pipe operator in KQL passes results between operators; order matters and affects both performance and correctness.
- Materialized views always return current data by combining precomputed and delta parts transparently.
- T-SQL support in Eventhouse is a subset; do not assume all T-SQL features are available.
- Filter placement early in a query leverages time partitioning and dramatically improves performance.
- In KQL joins, the smaller table should come first for optimal memory usage, unlike SQL optimizer behavior.
- Stored functions accept parameters but do not support complex control flow like stored procedures in SQL.

## Card 4: Real-Time Dashboards

### What It Is

Real-Time Dashboards are visual monitoring interfaces in Microsoft Fabric that display live data from KQL queries with automatic refresh capabilities. They consist of configurable tiles that run KQL queries against Eventhouse databases, presenting results in charts, tables, and other visualizations that update at regular intervals without manual intervention.

### Key Details

#### Structure

Dashboards are organized into pages, where each page contains one or more tiles arranged in a grid layout. Each tile runs its own KQL query against an Eventhouse database and displays the results in a configured visualization type. Pages allow you to group related monitoring views together, such as separating system health metrics from business performance indicators within the same dashboard.

#### Authorization Model

Pass-through identity means the tile query runs using the viewer's own credentials, so each user sees only the data they have permission to access. Editor identity means the tile query runs using the dashboard editor's credentials, so all viewers see the same data regardless of their individual permissions. You choose the authorization model when creating each tile, and it affects both security and data consistency for viewers.

#### Tile Configuration

Each tile displays results from a KQL query and supports interactive features including drill-down capabilities that let viewers click through to see underlying data details. Visualization types include time charts, bar charts, pie charts, tables, cards, and other formats appropriate for the query results. Tiles can be resized and repositioned on the page grid to create custom monitoring layouts.

#### Parameters

Parameters are user-driven filters prefixed with an underscore character that appear as interactive controls at the top of the dashboard. Viewers can change parameter values to filter all tiles that reference those parameters, enabling dynamic exploration of the data without modifying queries. Parameters are defined once at the dashboard level and can be referenced by multiple tiles throughout the dashboard.

#### Auto Refresh

Dashboard editors set the default refresh rate that determines how often tile queries re-execute against the database. Viewers can adjust the refresh rate for their own session, choosing faster or slower updates based on their monitoring needs. The minimum refresh rate is limited by system constraints, and extremely frequent refreshes may impact query performance and resource consumption.

#### Base Queries

Base queries are shared query definitions stored at the dashboard level that individual tiles can reference by name instead of duplicating the full query text. They use variable names to parameterize common logic, allowing multiple tiles to reuse the same underlying query with different visualization configurations. This approach reduces maintenance overhead when query logic changes, since you update the base query once rather than modifying every tile that uses similar logic.

### Exam Gotchas

- Pass-through identity enforces row-level security based on the viewer's permissions, while editor identity shows all data to everyone.
- Parameters must be prefixed with an underscore to function as dashboard-level controls.
- Base queries reduce duplication but each tile still defines its own visualization independently.
- Auto refresh rates are set by editors as defaults, but viewers can override them for their own sessions.
- The minimum refresh rate is a system limit, not configurable per dashboard or per tile.
- Drill-down on tiles requires that the underlying KQL query returns the necessary detail columns.
- Dashboard pages are independent; parameters on one page do not automatically affect tiles on other pages.

## Card 5: Activator

### What It Is

Activator is an event detection and automated rules engine within Microsoft Fabric that monitors streaming data and triggers actions when specified conditions are met. It provides a no-code interface for defining monitoring rules across your streaming pipelines, dashboards, and other data sources without writing custom alerting logic.

### Key Details

#### Core Object Model

Events represent the incoming data records that Activator monitors, originating from Eventstreams, dashboards, or other Fabric data sources. Objects are the logical entities you want to monitor, such as a specific sensor, device, transaction stream, or website endpoint. Properties are the numeric or string attributes on objects that you track and evaluate against conditions, such as temperature values, response times, or error counts. Rules define the conditions that trigger actions when property values change in specified ways.

#### Rule Definition Structure

The Monitor section of a rule specifies which attribute to watch and how to aggregate it, using a time window and step size to define the evaluation period. The window determines how much historical data to consider, while the step size controls how frequently the rule checks for condition changes. The Condition section defines the actual trigger logic, supporting threshold comparisons (value exceeds or falls below a limit), change detection (value increases or decreases by a specified amount), range checks (value enters or leaves a defined band), missing data detection (no events received within an expected period), and occurrence behavior (how many times a condition must be true before triggering). Property filters allow you to add up to three conditions that must all be satisfied before the rule fires, enabling compound monitoring logic.

#### Actions

Email actions send notification messages to specified recipients when rules trigger, including configurable subject lines and body content with dynamic values from the event data. Teams actions post messages to designated Teams channels, enabling team-wide visibility into monitoring alerts. Power Automate actions invoke custom workflows that can perform complex operations such as updating external systems, creating tickets, or orchestrating multi-step responses. Fabric item actions can start or stop other Fabric items like pipelines or notebooks, enabling automated remediation workflows.

#### Alternative Alerting Methods

Dashboard alerts provide simpler alerting directly from Real-Time Dashboard tiles by defining threshold conditions on displayed metrics without leaving the dashboard interface. System event alerts monitor Fabric system events such as pipeline failures or capacity changes, triggering notifications based on platform-level conditions. Query alerts execute KQL queries on a schedule and trigger when results match specified criteria, offering a flexible alternative to the full Activator rule model for straightforward monitoring scenarios. All three alternatives use the same underlying Activator engine but present simplified interfaces for common use cases.

### Exam Gotchas

- Activator rules evaluate conditions within defined time windows; the window and step size directly affect how quickly anomalies are detected.
- Property filters support up to three conditions that must all be satisfied, not up to three rules per property.
- Missing data detection requires that you know the expected event frequency; otherwise you cannot distinguish slow data from lost data.
- Dashboard alerts, system event alerts, and query alerts all use the Activator engine but with different simplified interfaces.
- Fabric item actions can start or stop other Fabric items, enabling automated remediation beyond simple notifications.
- The Monitor section requires both an attribute to watch and a summarization method with window and step size.
- Rules trigger actions each time the condition transitions from false to true, not continuously while the condition remains true.
