# M3.Summary.md

## Real-Time Intelligence Platform Overview

**Core Concept**
Real-Time Intelligence is an integrated set of Fabric components (Eventstreams, Eventhouse/KQL databases, Real-Time Hub, KQL Querysets, Real-Time Dashboards, Activator) that ingest, process, store, analyze, and act on streaming data within seconds to minutes of event occurrence — contrasting with traditional batch analytics that processes historical snapshots on scheduled intervals.

**Technical Specifications**
- **Events vs. Streams:** An event is a single digital record of something that happened at a specific moment (website click, sensor reading, stock price change). A stream is an ordered sequence of events, typically ordered by event time. Streams are the delivery mechanism carrying events from source to processing destination.
- **Real-Time Hub:** Central catalog for discovering and managing all data-in-motion across the organization. Access via the Real-Time icon in the Fabric menu bar. Categories:
  - **Data sources:** Browse/connect to available streaming sources.
  - **Azure sources:** Discover/configure Azure streaming sources (IoT Hub, Service Bus, Azure Data Explorer DB, etc.).
  - **Fabric events:** Subscribe to system-generated events — job status changes, file/folder actions in OneLake, workspace item changes.
  - **Azure events:** Subscribe to Azure service system events (Blob Storage actions, etc.) for triggering automated responses.
  - From the hub, navigate directly to eventstreams or KQL databases for deeper analysis. Build Activator rules from discovered streams.
- **Components:**
  - **Eventstreams:** Capture streaming data from various sources, apply real-time transformations (filter, enrich, aggregate) as data flows, route to destinations.
  - **Eventhouse:** Container for KQL databases optimized for time-series, high-velocity data. Integrates with OneLake for cross-workload access.
  - **KQL Queryset:** Workspace for running/managing KQL or T-SQL queries against KQL databases. Save queries, organize multiple tabs, share with others, create visualizations from query results.
  - **Real-Time Dashboards:** Connect to KQL databases, refresh automatically as new data arrives. Tiles with KQL-based visualizations. Interactive drill-down and filtering.
  - **Activator:** Event detection and rules engine. Monitors streaming data against user-defined conditions. Actions: email, Teams, Power Automate, Fabric notebooks/pipelines.
- **Copilot for Real-Time Intelligence:** AI-based KQL query generation. Opens as side pane in KQL Queryset. Requires admin enablement (F2+ capacity).
- **Use cases:** Delivery tracking (vehicle location monitoring), equipment monitoring (temperature anomaly prevention), fraud detection (immediate purchase pattern analysis), website performance (page load monitoring), system health (application error tracking).

**Architectural Logic**
Real-Time Intelligence is designed for latency-sensitive workloads where data value decreases rapidly with time. Unlike batch pipelines that process on schedules, RTI operates on continuous data flows. Each component handles a specific stage — capture (Eventstreams/Hub), store (Eventhouse), analyze (KQL), visualize (Dashboards), act (Activator). The system uses append-only immutable events as its core data model because time-series events represent what actually happened at specific moments and cannot be changed retroactively.

**Implementation Workflow**
1. Discover streaming data via Real-Time Hub or create an Eventstream with a source connector.
2. Apply optional transformations (filter, aggregate, enrich) in the Eventstream.
3. Route processed data to Eventhouse (KQL database), Lakehouse, Activator, or custom endpoint.
4. Query stored data using KQL or T-SQL in KQL Queryset.
5. Build Real-Time Dashboards connected to KQL databases for monitoring.
6. Configure Activator rules for automated alerting and actions.

**Exam Gotchas & Distinctions**
- **Event vs. Stream:** Each event is a single record; a stream is the ordered sequence of events over time. The stream is the delivery mechanism.
- **Batch vs. Real-Time:** Batch processing = scheduled intervals, historical snapshots. Real-Time Intelligence = continuous flows, data actively in motion.
- **Real-Time Hub is a catalog, not storage:** It's for discovering and managing data-in-motion, not for storing streaming data.
- **Copilot generates KQL code:** It does not automatically apply transformations or create dashboards — it helps write the query code.
- **Fabric events scope:** Workspace item changes, OneLake file/folder actions, job status changes — these are system-generated events you can subscribe to, not data events.

## Eventstream

**Core Concept**
A visual no-code engine (drag-and-drop canvas) that captures events from streaming data sources, applies optional in-flight transformations, and routes processed data to one or more destinations — the primary ingestion pipeline for Real-Time Intelligence.

**Technical Specifications**
- **Sources:**
  - **Microsoft sources:** Azure Event Hubs, Azure IoT Hub, Azure Service Bus, Change Data Capture (CDC) from database services.
  - **Azure events:** Azure Blob Storage events.
  - **Fabric events:** Workspace item changes, OneLake data store changes, Fabric job events.
  - **External sources:** Apache Kafka, Google Cloud Pub/Sub, MQTT (Message Queuing Telemetry Transport, in preview).
- **Transformations (applied in-flight during stream processing):**
  - **Filter:** Keep only events matching field-value conditions (e.g., `temperature > 80`, `status = "error"`). Eliminates unwanted data before further processing.
  - **Manage fields:** Add, remove, rename fields, change data types, add calculated fields. Use for data cleansing and schema alignment.
  - **Aggregate:** Calculate Sum, Minimum, Maximum, or Average every time a new event occurs over a period of time. Rename calculated columns, filter based on other dimensions. Multiple aggregations in one transformation.
  - **Group by:** Calculate aggregations over time windows. Supports tumbling windows (fixed non-overlapping intervals) and sliding windows (overlapping intervals). Examples: hourly sales totals, daily temperature averages.
  - **Union:** Connect two or more nodes, combine events with shared fields (same name and data type) into one table. Fields that don't match are dropped.
  - **Join:** Combine data from two streams based on a matching condition between them.
  - **Expand:** Array transformation — creates a new row for each value within an array.
- **Destinations:**
  - **Eventhouse (KQL database):** Store in KQL database for KQL/T-SQL querying and dashboarding.
  - **Lakehouse:** Convert real-time events to Delta Lake format, store in designated lakehouse tables. Enables cross-workload analytics.
  - **Derived stream:** Transformed subset of the original stream for content-based routing. Example: filter high-temperature IoT sensor data to Activator while routing hourly averages to KQL database. Derived streams can be further routed to multiple destinations.
  - **Fabric Activator:** Direct connection to event detection engine. Data reaches threshold → Activator triggers email, Teams, Power Automate, or Fabric item actions.
  - **Custom endpoint:** Route to external system or custom application outside Fabric.
  - Multiple destinations can be attached simultaneously without collisions.
- **Canvas workflow:** Sources → optional transformations → one or more destinations. Each node is a drag-and-drop component.

**Architectural Logic**
Eventstreams serve as the ingestion and transformation layer before data reaches storage. The drag-and-drop canvas enables real-time ETL without code. Content-based routing (via derived streams) lets different subsets of the same stream go to different destinations — critical when the same raw data serves multiple use cases (alerting + analytics + archival). Multiple destinations on the same stream means you can store raw and transformed data simultaneously without duplication.

**Implementation Workflow**
1. Create Eventstream in Fabric workspace.
2. Add source (new or from Real-Time Hub).
3. Apply optional transformations on canvas (filter, manage fields, aggregate, group by, union, join, expand).
4. Add one or more destinations.
5. (Optional) Create derived streams between transformations and destinations for content-based routing.
6. Start eventstream — data flows from source through transformations to destinations.

**Exam Gotchas & Distinctions**
- **Eventstream transformations vs. KQL Update Policies:** Eventstream transformations happen in-flight during stream processing, before data reaches storage. KQL Update Policies run after data is written to a KQL database table. Choosing between them depends on where in the pipeline the transformation is needed.
- **Derived streams are destinations that become sources:** They are configured as destinations but can then be used as input to further transformations or destinations.
- **Union drops non-matching fields:** Only fields with the same name and data type across streams are included in the output.
- **Aggregate vs. Group by:** Aggregate calculates per-event (every new event triggers recalculation). Group by calculates over time windows (tumbling or sliding).
- **Multiple destinations are independent:** One destination failure does not affect other destinations in the same eventstream.
- **Lakehouse destination converts to Delta:** Real-time events stored in Lakehouse are converted to Delta Lake format — enabling Spark and SQL analytics queries.

## Eventhouse and KQL Databases

**Core Concept**
An Eventhouse is a container that houses one or more KQL databases, each optimized for storing and analyzing high-velocity, append-only time-series data. Data is automatically partitioned by ingestion time, making recent data quickly accessible while historical data remains available for trend analysis.

**Technical Specifications**
- **Architecture:** Automatic partitioning by ingestion time. Time-series data is immutable (events represent what happened at a specific moment and cannot be changed). Append-only pattern — new events continuously added, updates/deletes are rare.
- **KQL (Kusto Query Language):** Pipeline-based language using pipe (`|`) to flow data from one operator to the next. Case-sensitive for everything: table names, column names, function names, operators, keywords, string values (e.g., `TaxiTrips` ≠ `taxitrips`).
- **Basic KQL operators:**
  - **`take N`:** Return first N rows. Used for sampling without scanning full table.
  - **`where condition`:** Filter rows. Effective early filtering reduces data for subsequent operations.
  - **`project col1, col2`:** Select/rename specific columns. Reduces resource usage especially on wide tables.
  - **`summarize agg() by group`:** Aggregate data. `count()`, `avg()`, `sum()`, `min()`, `max()`.
  - **`order by col` / `sort by col`:** Sort results.
  - **`limit N`:** Limit results (useful after summarize for exploration).
- **Query optimization principles:**
  - **Filter early and effectively:** Put filters that eliminate most data first. Time-based filtering is most effective because KQL databases use time indexes. Example: `where pickup_datetime > ago(30min)` before other operations.
  - **Reduce columns early:** Project only needed columns before filtering or aggregating.
  - **Smaller table first in joins:** KQL processes the first table to match with the second — fewer rows to process improves performance.
  - **Limit aggregation results:** Use `limit` after summarize during exploration to avoid processing full result sets.
- **Time-based filter syntax:** `where pickup_datetime > ago(30min)`, `where ingestion_time() between (ago(30min) .. now())`. The `ago()` function is optimized for time-index lookup.
- **Materialized views:** Precomputed aggregation results that automatically update as new data arrives.
  - **Architecture:** Consists of a materialized part (precomputed results from already-processed data) and a delta (new data since last background update). At query time, both parts are combined automatically for fresh results. Background process periodically moves delta data into materialized part.
  - **Creation:** `.create materialized-view ViewName on table SourceTable { SourceTable | summarize agg() by group }`
  - **Querying:** Materialized views are queried like regular tables: `ViewName | where condition`
  - Always returns current data regardless of when background materialization last ran.
- **Stored functions:** Encapsulate query logic as reusable parameterized functions.
  - **Creation:** `.create-or-alter function FunctionName(param:type) { query }`
  - **Usage:** Called like a table: `FunctionName(value) | take 10`
  - Useful for ensuring consistent calculations across team members.
- **T-SQL support:** Subset of T-SQL for users familiar with SQL syntax. Example: `SELECT TOP 10 * FROM stock;`
- **OneLake availability:** Can be enabled per KQL database or table. Makes data accessible to Power BI, Warehouse, Lakehouse, and other Fabric services for cross-workload integration.
- **Database shortcuts:** Query data from external KQL databases or Azure Data Explorer databases as if local — no data copying.
- **KQL Queryset:** Workspace for running/managing queries. Save queries, organize tabs, share with others. Create visualizations (charts, tables) directly from query results.
- **Copilot for Real-Time Intelligence:** Generate KQL code from natural language questions. Opens as side pane in queryset.
- **Management commands:** Update policies (auto-transform incoming data to different tables), materialized views (precalculated aggregations), stored functions (reusable query logic).

**Architectural Logic**
KQL databases are optimized for the unique characteristics of time-series data — immutable, append-only, timestamp-centric. Automatic ingestion-time partitioning means recent data is isolated from historical data, so queries for current conditions only scan relevant partitions rather than the full dataset. The pipeline (pipe) syntax of KQL mirrors this funnel approach: start with the full dataset, then progressively filter, project, and aggregate. Materialized views solve the problem of recalculating aggregations over billions of rows on every query by maintaining precomputed results that update incrementally. The materialized + delta architecture ensures queries always see current data without waiting for background processing. Use stored functions when the same filtering or transformation logic is needed across multiple queries — they standardize calculations and reduce duplication.

**Implementation Workflow**
1. Create Eventhouse in Fabric workspace (default KQL database created with same name).
2. Ingest data: Eventstream, direct connectors (local files, Azure storage, Amazon S3, Event Hubs, Kafka, etc.), or Get Data option in KQL database.
3. Explore data in KQL Queryset using `table | take 10` for sampling.
4. Write optimized queries: filter early (time filter first), reduce columns (`project`), place smaller table first in joins.
5. Create materialized view for common aggregations: `.create materialized-view Name on table T { T | summarize ... by ... }`
6. Create stored functions for reusable logic: `.create-or-alter function Name(param:type) { query }`
7. Enable OneLake availability for cross-workload access if needed.
8. Create database shortcuts to external KQL databases.

**Exam Gotchas & Distinctions**
- **KQL is case-sensitive:** Table names, column names, function names, keywords, string values all must match case exactly. This is a common source of query errors.
- **`take N` vs. `limit N`:** `take` returns first N rows from wherever the query engine reaches first (non-deterministic). `limit` specifies a hard limit on result set size. Both useful but different behavior.
- **Filter order matters:** Put the filter that eliminates the most data first in the `where` chain. Time filters first because they leverage the time index.
- **Smaller table first in joins:** KQL processes the first (left) table to match against the second (right). Always put the smaller table first.
- **Materialized views always return current data:** The delta part ensures query-time freshness even if background materialization hasn't run yet. Do not assume materialized views are stale between updates.
- **Materialized vs. regular view:** A regular view is just a saved query — no performance benefit. A materialized view stores precomputed results and updates incrementally.
- **Stored functions vs. views:** Functions support parameters. Views do not. Use functions when you need variable values in the query logic.
- **Database shortcuts vs. OneLake availability:** Shortcuts query external KQL databases without copying. OneLake availability exposes local KQL data to other Fabric workloads (Power BI, Warehouse, Lakehouse). They serve opposite directions.
- **Update policies vs. Eventstream transformations:** Update policies transform data after it lands in the KQL database. Eventstream transformations happen before data reaches storage. Same end goal (data transformation), different pipeline stage.
- **T-SQL is a subset:** Not all T-SQL features are available. KQL is the primary query language for Eventhouses.

## Real-Time Dashboards

**Core Concept**
A visual monitoring interface composed of tiles, each displaying a KQL query result that refreshes automatically as new data arrives in the connected KQL database — purpose-built for continuous data tracking rather than historical snapshot reporting.

**Technical Specifications**
- **Structure:** One or more tiles per dashboard. Each tile contains a KQL query result displayed as a visualization (chart, map, table, etc.). Multiple pages organize related tiles.
- **Data source:** KQL database in an Eventhouse. Created from workspace or directly from a KQL Queryset.
- **Authorization for data source:**
  - **Pass-through identity:** Each viewer accesses data using their own permissions.
  - **Dashboard editor's identity:** All viewers access data using the dashboard creator's permissions.
- **Tiles:** Each tile displays results of a KQL query. Initially renders as a table. Edit to select visualization type (bar chart, line chart, map, etc.). Interactive: drill into data, filter, aggregate, change visualization type.
- **Pages:** Default single page. Add pages as containers for related tiles — organize by data source or subject area.
- **Parameters:** User-driven filters. Created with a variable name (prefixed with `_` like `_selected_neighbourhoods`). Values based on specific text or query results. Reference in tile KQL queries using underscore prefix. Example:
  ```kql
  bikes
  | where (isempty(_selected_neighbourhoods) or Neighbourhood in (_selected_neighbourhoods))
  ```
- **Auto refresh:** Dashboard editors set a default refresh rate. Viewers can adjust rate during their session. Editors can set a minimum refresh rate to prevent excessive refresh requests.
- **Base queries:** Shared query definitions reusable across multiple tiles. Defined in dashboard's Base queries menu with a variable name (e.g., `_base_bike_data`). Tile-specific queries reference the base query by variable name. Avoids duplicating logic. Example base query:
  ```kql
  bikes | where ingestion_time() between (ago(30min) .. now())
  | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
  ```
  Tile query referencing it:
  ```kql
  _base_bike_data
  | project Neighbourhood, latest_observation, No_Bikes, No_Empty_Docks
  | order by Neighbourhood asc
  ```
- **Text tiles:** Provide additional information/context on the dashboard.

**Architectural Logic**
Real-Time Dashboards differ from Power BI reports in their data refresh model. Dashboards connect directly to KQL databases and refresh tiles continuously as new data arrives — there is no scheduled import or refresh configuration. Base queries improve maintainability by centralizing common data retrieval logic; changing one base query updates all tiles that reference it. Parameters enable audience-specific filtering without duplicating dashboards. The authorization model (pass-through vs. editor identity) controls whether the dashboard respects individual user permissions or uses a single shared access identity.

**Implementation Workflow**
1. Create Real-Time Dashboard in workspace or from KQL Queryset.
2. Connect to a KQL database as data source.
3. Configure data source authorization (pass-through or editor identity).
4. Add tiles with KQL queries. Test queries in the tile editor.
5. Edit tile visualizations (chart type, formatting).
6. (Optional) Create additional pages for organization.
7. (Optional) Define base queries for shared data logic.
8. (Optional) Add parameters with underscore-prefixed variable names.
9. Configure auto refresh (default rate and minimum rate).
10. Publish dashboard for viewers.

**Exam Gotchas & Distinctions**
- **Base queries vs. individual tile queries:** Base queries are defined at dashboard level with a variable name. Tile-specific queries are standalone within each tile. A base query is shared, a tile query is not.
- **Parameter underscore prefix:** Parameters must be referenced in KQL queries with `_` prefix (e.g., `_selected_neighbourhoods`). The underscore is part of the variable name, not the parameter definition.
- **Pass-through vs. editor identity:** Pass-through = user's own permissions. Editor identity = everyone uses the creator's permissions. Critical access control distinction.
- **Auto refresh minimum rate:** Editors set a floor, viewers can only increase the interval (not go below the minimum). Prevents excessive data source queries.
- **Tiles render as tables initially:** Visualizations are configured after tile creation. The initial display is always tabular.
- **Dashboard vs. Power BI:** Real-Time Dashboards connect directly to KQL databases and auto-refresh. Power BI can also query KQL databases but uses a different model (DirectQuery/Import).

## Activator

**Core Concept**
Activator is Fabric's event detection and rules engine within Real-Time Intelligence — it continuously monitors streaming data against user-defined conditions and triggers automated actions (email, Teams, Power Automate, Fabric item actions) when conditions are met, turning passive monitoring into active response.

**Technical Specifications**
- **Core object model:**
  - **Events:** Individual data records flowing in from data sources.
  - **Objects:** Real-world entities being monitored (Package001, SensorA, Customer123). Created by selecting a unique identifier field from event data (e.g., `PackageId`, `DeviceID`). New unique IDs automatically create new objects.
  - **Properties:** Data attributes of objects that are monitored (Temperature, DeliveryState, HoursInTransit). Updated continuously as new events arrive.
  - **Rules:** Conditions evaluated against property values, triggering actions when met.
- **Rule definition:**
  - **Monitor section:**
    - **Attribute:** The specific property to watch (e.g., Temperature).
    - **Summarization:** Controls noise reduction. Options: Average (smooth outliers), Minimum/Maximum (catch extremes), Count (track reading frequency, useful for sensor failure detection), Total (sum values).
    - **Timing settings:**
      - **Window size:** How much historical data to include in the summarization (e.g., 10 minutes of temperature readings).
      - **Step size:** How often to recalculate (e.g., every 5 minutes). Window size and step size can differ.
  - **Condition section:**
    - **Threshold monitoring:** Trigger when value crosses a numeric boundary (Temperature > 68°F).
    - **Change detection:** Trigger when value trends increase/decrease above baseline.
    - **Range monitoring:** Track entry/exit from safe zones.
    - **Missing data:** Trigger when no new events for a specified duration (sensor failure detection).
    - **Value:** The numeric threshold.
    - **Occurrence behavior:** "Every time" for immediate alerts vs. "When it has been true for" to identify persistent problems (e.g., stays high for 15 minutes).
  - **Property filter section:** Narrow which events are evaluated. Up to three filter conditions combined. Examples: `ColdChainType equals "medicine"`, `City equals "Seattle"`, `Temperature > 68°F`.
- **Actions:**
  - **Email:** Detailed notification for review within hours/days. Recipient gets comprehensive context.
  - **Teams:** Immediate message to channel or individual. Best for quick responses and team coordination.
  - **Power Automate:** Multi-step business process automation across different systems (e.g., create ticket, update CRM, notify manager).
  - **Fabric item actions:** Execute data pipelines or notebooks. Best for further data processing and advanced analysis in response to conditions.
- **Alternative approaches (same Activator engine):**
  - **Dashboard alerts:** Created directly from Real-Time Dashboard visualizations.
  - **System event alerts:** Monitor Fabric workspace activities and OneLake file operations.
  - **Query alerts:** Created from KQL Queryset results and visualizations.
  - These alternatives do not require the full business objects model — they use the engine differently for simpler scenarios.

**Architectural Logic**
Activator's business object model enables stateful monitoring of individual entities rather than stateless stream-level checks. Instead of asking "does any row have Temperature > 68°F?", you ask "does Package001 maintain Temperature > 68°F over a sustained period?" — this requires tracking per-object state across multiple events. The summarization layer (window size + step size) distinguishes transient spikes from sustained problems, which is critical for avoiding alert fatigue. The property filter section focuses rules on relevant subsets of objects, reducing unnecessary evaluations. The alternative approaches (dashboard/system/query alerts) provide simpler paths to Activator's engine for users who don't need the full object model.

**Implementation Workflow**
1. Configure Activator as a destination in an Eventstream.
2. Create business objects: select unique identifier field (object), select properties to monitor.
3. Define rule:
   a. Choose attribute (property to watch) and configure summarization (window size, step size, aggregation type).
   b. Set condition (threshold, change detection, range monitoring, or missing data) with value and occurrence behavior.
   c. Apply property filter (up to three conditions) to narrow scope.
4. Configure action: email, Teams, Power Automate, or Fabric item.
5. Save and enable rule — Activator continuously evaluates and triggers actions.
6. (Alternative) Create alerts directly from Dashboard tiles, KQL Queryset results, or system events without business objects.

**Exam Gotchas & Distinctions**
- **Business Objects vs. Simple Alerts:** Business objects track state per-entity (e.g., each package's current temperature). Simple alerts (dashboard/query/system) check condition against any row in the stream. Business objects are for entity-centric monitoring; simple alerts are for stream-level conditions.
- **Window size vs. Step size:** Window = how far back to look. Step = how often to recalculate. They can differ. Example: window 10 min, step 5 min means you get an updated average every 5 minutes based on the last 10 minutes of data.
- **Summarization prevents alert fatigue:** Raw temperature spikes may be noise. Average over 10-minute windows catches sustained problems while ignoring brief fluctuations.
- **Missing data detection:** Useful for detecting sensor failures, not just threshold violations. Configure "No new events for more than N minutes" as a condition.
- **Up to three property filters:** Combine to create precise targeting (e.g., cold chain + Seattle + high priority).
- **"Every time" vs. "When it has been true for":** "Every time" fires on each qualifying event. "When it has been true for" waits for sustained condition over time period.
- **Fabric item actions execute Notebooks/Pipelines:** Enables automated data processing loops without human intervention.
- **Power Automate for cross-system workflows:** Use when action involves multiple systems (email + CRM update + ticket creation), not just a single notification.
- **Alternative alerts use same engine:** Dashboard alerts, query alerts, and system event alerts all use the Activator engine but skip the business object model setup.
