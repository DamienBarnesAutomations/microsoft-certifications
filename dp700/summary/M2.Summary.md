# M2.Summary.md

## Microsoft Fabric Platform and Lakehouse

**Core Concept**
Microsoft Fabric is a unified SaaS analytics platform where all data is stored in a single open format (Delta-Parquet) in OneLake (built on ADLS Gen2), accessible by all compute engines without data movement, with lakehouses providing structured Tables (Delta, SQL-queryable, ACID) and raw Files (any format, no schema enforcement).

**Technical Specifications**
- **OneLake:** Built on ADLS Gen2. Single logical lake across regions and clouds without moving/duplicating data. Supports formats: Delta, Parquet, CSV, JSON. Tabular data written in Delta-Parquet by all analytical engines.
- **Shortcuts:** References to files/storage in OneLake or external sources (ADLS Gen2, Amazon S3, Dataverse). No data copying — ensures consistency. OneLake manages source permissions (uses your identity for authorization). Schema shortcuts: map entire schema to a folder of Delta tables in another lakehouse or ADLS Gen2 — referenced tables appear as local tables within the schema.
- **Workspaces:** Logical containers for organizing items. Configure: License type, OneDrive access, ADLS Gen2 Storage connection, Git integration, Spark workload settings. Four roles: Admin, Member, Contributor, Viewer (apply to all items). Data lineage view available.
- **Admin portal:** Centralized. Manage groups/permissions, configure data sources/gateways, monitor usage/performance, access admin APIs/SDKs. Fabric can be enabled for entire org or specific security groups. Roles: Fabric Admin, Power Platform Admin, Global Admin.
- **OneLake catalog:** Searchable discovery. Only see items shared with you. Filter by workspace/domain/keyword/item type. Shows sensitivity labels, item metadata, refresh status.
- **Fabric workloads:** Data Engineering, Data Factory, Data Warehouse, Real-Time Intelligence, Data Science, Databases, Industry Solutions, IQ (preview), Power BI.
- **Fabric IQ (preview):** One of three IQ workloads. Fabric IQ = ontologies/graphs/semantic models for OneLake data. Foundry IQ = enterprise knowledge across Azure/SharePoint/web. Work IQ = M365 collaboration signals. Data agents connect to ontology as source for NL-queries.
- **Copilot:** Enabled by default across all workloads. Admins disable in Admin portal > Tenant settings. Capabilities: code completion/generation in notebooks, SQL generation, KQL translation, Power BI report generation, data transformation guidance in Data Factory.
- **Lakehouse structure:**
  - **Tables folder:** Delta Lake tables — support SQL queries through SQL analytics endpoint, enforce schemas, ACID transactions, Power BI access, automatic optimization/maintenance.
  - **Files folder:** Raw/semi-structured data in native format (CSV, JSON, Parquet, images, documents). No schema enforcement, no direct SQL queries. Staging area before transformation into Tables.
  - SQL analytics endpoint created automatically (read-only T-SQL, supports views, functions, SQL security — RLS, CLS).
  - Schemas enabled by default (dbo auto-created). Organize tables by business domain. Support schema-level permissions and four-part namespace: `workspace.lakehouse.schema.table`.
- **Lakehouse access modes:**
  - **Lakehouse explorer:** Manage tables/files/folders, upload files, create tables, add reference lakehouses (browse multiple lakehouses side by side)
  - **SQL analytics endpoint:** Read-only T-SQL queries against Delta tables. Create views, functions, apply SQL security. Cannot modify underlying data.
- **Ingestion methods:** Upload (local files/folders), Load to Table (no-code for CSV/Parquet; append or overwrite), Dataflows Gen2 (Power Query), Notebooks (Spark), Data Factory pipelines (Copy activity), Shortcuts.
- **Power BI integration:** Direct Lake mode — reads Delta Parquet files directly from OneLake without import/refresh. Default for lakehouse semantic models. Fast query performance with current data.

**Architectural Logic**
Fabric eliminates the traditional tradeoff between data lakes (flexible/cheap but no ACID) and data warehouses (structured/fast but expensive for diverse data). Lakehouses bridge this by bringing Delta Lake (ACID, schema enforcement, time travel) directly to OneLake storage. The Tables/Files separation lets you maintain raw source data for compliance/reprocessing (Files) alongside structured analytics tables (Tables). Use shortcuts over data ingestion when data already exists in supported cloud storage (ADLS S3 Dataverse) to avoid duplication. Use Direct Lake mode over Import mode for Fabric-native data to eliminate scheduled refresh while maintaining fast query performance. Use item permissions over workspace roles when a user only needs access to specific items rather than the entire workspace.

**Implementation Workflow**
1. Enable Fabric in Admin portal > Tenant settings (org-wide or per security group).
2. Create workspace; configure license type, Git integration, Spark settings.
3. Create lakehouse: Tables (for structured Delta) + Files (for raw staging) + SQL analytics endpoint (auto-created).
4. Ingest data: upload, Load to Table (CSV/Parquet only, no-code), shortcuts, pipelines, dataflows, or notebooks.
5. Transform: notebooks (Spark SQL/PySpark) for complex logic, Dataflows Gen2 for low-code Power Query transformations.
6. Query via SQL analytics endpoint (read-only T-SQL) for ad-hoc analysis.
7. Create Power BI semantic model on lakehouse (Direct Lake mode default).
8. Set permissions: workspace roles for broad collaboration, item permissions for granular access.

**Exam Gotchas & Distinctions**
- **Tables vs. Files:** Only Tables data is available via SQL analytics endpoint. Files require Spark processing first.
- **SQL analytics endpoint is read-only:** Cannot INSERT/UPDATE/DELETE/MERGE. Must use Spark notebooks, dataflows, or pipelines for writes.
- **Load to Table supports CSV and Parquet only:** No-code ingestion limited to these formats. Other formats need notebooks or dataflows.
- **Lakehouse explorer vs. SQL endpoint:** Explorer is for management/Spark access; SQL endpoint is for read-only T-SQL queries.
- **Shortcuts use caller identity:** When accessing data through a shortcut to another OneLake location, OneLake uses YOUR identity to authorize access — not a service identity.
- **Schema shortcuts vs. individual shortcuts:** Schema shortcuts map entire Delta table schemas from external sources — all referenced tables appear as local.
- **SaaS vs. PaaS:** Fabric is SaaS — no need to manually create ADLS Gen2 accounts. Underlying Azure resource management is abstracted.
- **Fabric IQ vs. Foundry IQ vs. Work IQ:** Fabric IQ = analytics data/ontologies; Foundry IQ = enterprise knowledge across Azure/SharePoint/web; Work IQ = M365 collaboration signals.
- **Copilot capacity requirement:** Requires F2 or higher (or P1+). Free trial SKUs not supported for all Copilot features.

## Delta Lake

**Core Concept**
Delta Lake is an open-source storage layer on top of Parquet that brings ACID transactions, schema enforcement, time travel, and batch/streaming unification to data lakes — each Delta table consists of Parquet data files plus a `_delta_log` folder of JSON transaction logs.

**Technical Specifications**
- **Architecture:** Parquet data files + `_delta_log` folder with JSON transaction logs tracking every change.
- **ACID transactions:** Atomicity, Consistency, Isolation, Durability with serializable isolation for concurrent operations.
- **Schema enforcement:** Validates data written matches table schema; prevents corrupt data writes.
- **Time travel:** Transaction log enables querying previous versions via `versionAsOf` or `timestampAsOf` options. View history with `DESCRIBE HISTORY table_name` (shows version, timestamp, operation, operationParameters). History also available for external tables by specifying folder path.
- **CRUD support:** SELECT, INSERT, UPDATE, DELETE operations supported (unlike raw Parquet which is immutable).
- **OptimizeWrite (enabled by default):** Reduces small file problem by writing fewer larger files during writes. Can be disabled/enabled at Spark session level: `spark.conf.set("spark.microsoft.delta.optimizeWrite.enabled", True/False)`. Also settable in Table Properties and for individual write commands.
- **OPTIMIZE:** Maintenance command consolidating small Parquet files into fewer larger files — better compression, efficient data distribution across nodes. Run via Lakehouse Explorer > Maintenance > Run OPTIMIZE command.
- **V-Order:** When run with OPTIMIZE, applies special sorting, row group distribution, dictionary encoding, and compression on Parquet files.
  - V-Order is enabled by default in Fabric and applied as data is written
  - Incurs ~15% overhead on write times
  - Enables faster reads: Power BI/SQL engines use Microsoft Verti-Scan technology for maximum benefit; Spark and other engines get ~10% faster reads (up to 50%)
  - 100% compliant with open-source Parquet format — all Parquet engines can read V-Ordered files
  - Not beneficial for write-intensive staging data (data read only once or twice)
- **VACUUM:** Removes old Parquet data files not referenced in transaction log and older than retention period. Does NOT remove transaction logs.
  - Default retention period: 7 days (168 hours)
  - System prevents shorter retention period
  - After VACUUM, cannot time travel back earlier than retention period
  - Run ad-hoc or scheduled via Fabric notebooks. Also via Lakehouse Explorer > Maintenance > Run VACUUM command.
  - SQL syntax: `VACUUM schema.table RETAIN 168 HOURS`
  - VACUUM commits to Delta transaction log — view previous runs with `DESCRIBE HISTORY`
- **Managed vs. External tables:**
  - **Managed:** `df.write.format("delta").saveAsTable("table_name")`. Fabric manages metadata AND data files. Data stored in `Tables` location. Deleting table deletes underlying data.
  - **External:** `df.write.format("delta").saveAsTable("table_name", path="Files/path")`. Metadata in metastore, data in custom location (e.g., `Files` folder or fully qualified ADLS path). Deleting table preserves data files.
  - Create managed tables via Spark SQL: `CREATE TABLE ... USING DELTA`
  - Create external tables via Spark SQL: `CREATE TABLE ... USING DELTA LOCATION 'Files/mydata'` (schema determined by Parquet files at location)
  - Auto-discovery: Saving DataFrame in Delta format to `Tables` location auto-creates table metadata in metastore
- **DeltaTableBuilder API:** Create tables programmatically: `DeltaTable.create(spark).tableName("t").addColumn("c", "INT").execute()`
- **DeltaTable API (for file-level operations):** Create `DeltaTable.forPath(spark, delta_path)` to work with Delta format files directly. Supports `update()`, `delete()`, `merge()` operations.
- **Time travel options:**
  - `spark.read.format("delta").option("versionAsOf", 0).load(delta_path)`
  - `spark.read.format("delta").option("timestampAsOf", '2022-01-01').load(delta_path)`
- **Partitioning:**
  - `df.write.format("delta").partitionBy("Column").saveAsTable("table_name")`
  - Creates folder hierarchy: `Category=Bike Racks/`, `Category=Road Bikes/`
  - Enables partition pruning (data skipping) — skip irrelevant folders
  - Do NOT partition: small data volumes, high-cardinality columns (too many partitions), multiple levels (nested partitions)
  - Partitions are fixed layout — don't adapt to different query patterns
- **Spark Structured Streaming with Delta:**
  - Delta tables as streaming source: `spark.readStream.format("delta").option("ignoreChanges", "true").table("table_name")`
  - Only append operations can be included in stream. Specify `ignoreChanges` or `ignoreDeletes` for source Delta tables with updates/deletes.
  - Delta tables as streaming sink: `transformed_df.writeStream.format("delta").option("checkpointLocation", path).start(sink_path)`
  - `checkpointLocation` tracks stream state for failure recovery
  - Stop stream with `.stop()` to avoid unnecessary processing costs

**Architectural Logic**
Delta Lake solves the "small file problem" and data corruption risks inherent in raw Parquet lakes. The transaction log (JSON files in `_delta_log`) makes Parquet files reliable — every write, update, or delete creates a new Parquet file and records it in the log, enabling ACID transactions and time travel. OptimizeWrite and OPTIMIZE address the small file problem that arises from this immutable-file pattern. V-Order specifically optimizes reads for Fabric's Verti-Scan engine (Power BI, SQL), making the write-vs-read tradeoff explicit: ~15% slower writes for dramatically faster reads. Use managed tables for most analytics scenarios where Fabric controls the full lifecycle. Use external tables when data must persist independently of the catalog metadata (e.g., data shared across systems). Use VACUUM retention period based on data change frequency and time travel requirements — the default 7 days balances storage cost with historical query capability. Use Delta tables as streaming sources when you need near-real-time processing of ingested data; use them as streaming sinks when you need to persist processed streaming results.

**Implementation Workflow**
1. Create managed Delta table: `df.write.format("delta").saveAsTable("table_name")`
2. Create external Delta table: `df.write.format("delta").saveAsTable("table_name", path="Files/path")`
3. Create table from scratch (DeltaTableBuilder): `DeltaTable.create(spark).tableName("t").addColumn("c", "INT").execute()`
4. Create table via Spark SQL: `CREATE TABLE t (c INT) USING DELTA` or with `LOCATION` for external.
5. Run OPTIMIZE: Lakehouse Explorer > Maintenance > Run OPTIMIZE (optionally with V-Order). Or in notebook: `OPTIMIZE table_name`.
6. Run VACUUM: Maintenance > Run VACUUM with retention threshold. Or: `VACUUM schema.table RETAIN 168 HOURS`.
7. Time travel query: `spark.read.format("delta").option("versionAsOf", 0).load(path)` or with `timestampAsOf`.
8. Streaming: `df.writeStream.format("delta").option("checkpointLocation", checkpointPath).start(sinkPath)`

**Exam Gotchas & Distinctions**
- **OptimizeWrite enabled by default:** Reduces small files during writes. Disable only for specific write-intensive scenarios. Must set at Spark session level or table property.
- **V-Order ~15% write overhead:** This tradeoff (slower writes for faster reads) is exam-relevant. Disable for staging data written once/read once.
- **VACUUM default 7 days:** Minimum retention enforced by system; cannot go below 7 days (168 hours). After VACUUM, time travel before retention period is broken.
- **VACUUM removes files, not transaction logs:** Transaction logs remain — you can see history of VACUUM operations via DESCRIBE HISTORY, but the actual data files are gone.
- **Managed vs. External table deletion:** Managed = delete table deletes Parquet files. External = delete table preserves files. Critical exam distinction.
- **Streaming Delta source requires ignoreChanges/ignoreDeletes:** Without these options, modifications to source Delta table (updates/deletes) cause streaming errors. Only appends are safe by default.
- **Checkpoint location required for streaming:** Tracks processing state for failure recovery. Without it, stream restart must reprocess all data.
- **Auto-discovery for Tables location:** Saving Delta files to the `Tables` folder auto-creates table metadata — no explicit `CREATE TABLE` needed.
- **Partitioning anti-pattern:** High-cardinality partition columns create too many small files. Partition columns should have a reasonable number of distinct values.
- **DESCRIBE HISTORY shows all operations:** CREATE TABLE, WRITE, UPDATE, DELETE, VACUUM — all logged with version numbers.
- **DeltaTable API for file paths:** When working with Delta files outside the catalog (not registered tables), use `DeltaTable.forPath()` for update/delete/merge operations.

## Medallion Architecture

**Core Concept**
The medallion architecture organizes lakehouse data into Bronze (raw/unaltered landing zone), Silver (validated/cleansed/consistent format), and Gold (enriched/star schema/business-level aggregates) layers — a multi-hop design pattern that incrementally improves data quality as data moves through each layer.

**Technical Specifications**
- **Bronze layer (Raw):** Landing zone for all data in original format (structured, semi-structured, unstructured). No changes made to data. "Source of truth" for raw data.
- **Silver layer (Validated):** Combine/merge data, enforce validation rules (remove nulls, deduplicate), store in consistent format. Central repository accessible by multiple teams. Data is clean enough for further refinement but not yet modeled for specific use cases.
- **Gold layer (Enriched):** Further refinement aligned to specific business/analytics needs. Aggregations to specific granularity (daily, hourly), enrichment with external information, dimensional modeling (star schema). Multiple Gold layers possible for different audiences (Finance Gold, Sales Gold, Data Science Gold).
- **Custom layers:** Additional layers possible — e.g., "Raw" layer before Bronze for specific format landing, "Platinum" for further enriched data. Architecture is flexible.
- **Transformation vs. Orchestration:**
  - **Data transformation:** Altering structure/content of data. Tools: Dataflows Gen2 (smaller models, simple transformations), Notebooks (larger models, complex transformations, can save as managed Delta tables)
  - **Data orchestration:** Coordination/management of multiple processes. Tool: Pipelines (schedule, trigger, sequence across layers)
- **Layer flow decisions:**
  - Bronze: Pipelines, dataflows, notebooks
  - Silver: Dataflows or notebooks (focus on data quality/consistency, not modeling)
  - Gold: Notebooks, SQL analytics endpoint, or semantic model
- **Gold layer options:**
  - Model as star schema (dimensional model with facts and dimensions)
  - Can use Data Warehouse as Gold layer
  - Connect to Gold Delta table via SQL analytics endpoint, model with SQL for reporting
  - Connect via Power BI Direct Lake mode to SQL analytics endpoint
- **Security considerations:**
  - Different layers in different workspaces for improved security and capacity management
  - Gold: restrict to read-only. Apply minimal permissions.
  - Silver: decide if users can build upon it.
  - Bronze: restrict to read-only for compliance.
- **CI/CD considerations:**
  - Git integration in Fabric: back up, version, revert, collaborate with branches
  - CI/CD critical at Gold layer: ensures high-quality, validated, reliable data for consumption
  - Automated deployments, data quality checks, monitoring, security measures

**Architectural Logic**
The medallion architecture prevents "data swamps" by forcing incremental quality improvement through defined layers. Each layer has a specific purpose and quality level, making data reliable for downstream consumers. Bronze preserves the original data unchanged (compliance, reprocessing). Silver provides organization-wide clean data in consistent format. Gold models data for specific business consumption (star schema, aggregations). The multi-hop approach means data can move between layers as needed. Use separate workspaces for different layers when security isolation is required — Bronze in a restricted workspace, Gold in a workspace accessible to report consumers. Use a Data Warehouse as the Gold layer when you need full T-SQL DML (INSERT/UPDATE/DELETE/MERGE) for dimensional modeling. The architecture complements other data organization methods rather than replacing them — it is a framework for data cleaning, not a data architecture or model itself.

**Implementation Workflow**
1. **Design:** Determine layers needed (Bronze/Silver/Gold minimum; optional extra layers).
2. **Create lakehouse(s):** Single lakehouse for all layers, or separate lakehouses/workspaces per layer.
3. **Bronze:** Ingest raw data using pipelines, dataflows, or notebooks. Store unaltered in original format.
4. **Silver:** Use notebooks or Dataflows Gen2 to cleanse (remove nulls, deduplicate, merge). Write to Silver Delta tables in consistent format. Validate data quality.
5. **Gold:** Transform Silver data into dimensional model (star schema with facts/dimensions). Aggregate to required granularity. Enrich with external data. Write to Gold Delta tables.
6. **Consume:** Connect Power BI (Direct Lake), SQL analytics endpoint, or Data Warehouse to Gold layer for reporting and AI consumption.
7. **Orchestrate:** Use pipelines to schedule movement across layers with dependency management and error handling.
8. **Secure:** Apply workspace roles and item permissions per layer. Restrict Bronze to read-only for data engineers. Restrict Gold to read-only for report consumers.

**Exam Gotchas & Distinctions**
- **Transformation vs. Orchestration:** Transformation changes the data (Dataflows, Notebooks). Orchestration manages the sequence (Pipelines). The exam tests knowing which tool fits which role.
- **Multiple Gold layers:** Organizations can have multiple Gold layers for different domains (Finance, Sales, Data Science) — each tailored to specific analytical needs.
- **Gold layer as Data Warehouse:** A Fabric Warehouse can serve as the Gold layer when full T-SQL capabilities are needed for dimensional modeling.
- **Layer separation in workspaces:** Storing Bronze in a separate workspace from Gold provides both security isolation and capacity management benefits.
- **Medallion complements, doesn't replace:** The medallion architecture works alongside existing data models and methods — it's a data cleaning framework, not a wholesale replacement.
- **Direct Lake on Gold:** Power BI connecting to Gold Delta tables via Direct Lake provides fast query performance without scheduled refresh — the same data feeds both reports and AI agents.
- **CI/CD at Gold layer:** Because Gold is the consumption layer, version control and automated deployment are most critical here to ensure downstream consumers always get validated, reliable data.
