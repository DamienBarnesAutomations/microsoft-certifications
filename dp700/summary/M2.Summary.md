## Card 1: Microsoft Fabric Platform and Lakehouse

### What It Is

Microsoft Fabric is a unified SaaS analytics platform that brings together data engineering, data warehousing, data science, real-time analytics, and business intelligence into a single, integrated environment. At its core is OneLake, a single logical lake that serves as the organizational data foundation, built on Azure Data Lake Storage Gen2 and using Delta-Parquet as its default format. Fabric workspaces provide the organizational boundary where data and resources live, and each workspace assigns one of four roles to users: Admin, Member, Contributor, or Viewer. The platform is governed through an Admin portal and discoverable through the OneLake catalog, which indexes data across the organization.

### Key Details

**Fabric Workloads:**
Fabric offers several specialized workloads that each address a different analytical need. Data Engineering provides Spark-based lakehouse development, Data Factory handles data movement and orchestration, Data Warehouse delivers traditional T-SQL analytics, Real-Time Intelligence processes streaming data, and Data Science supports model training and experimentation. Databases provide relational transactional capabilities, and IQ (currently in preview) offers AI-powered analytics. Power BI remains the primary reporting and visualization workload. Copilot is available across workloads to assist with code generation, natural language queries, and content creation.

**Fabric IQ (Preview):**
Fabric IQ includes three distinct workloads designed to bring AI-driven insights into the Fabric ecosystem. These workloads focus on intelligent data discovery, automated insights, and natural language interaction with data assets.

**OneLake and Shortcuts:**
OneLake is built on top of Azure Data Lake Storage Gen2 and provides a single logical lake for the entire organization. It stores data in Delta-Parquet format by default, enabling efficient analytical queries. Shortcuts are references to data stored elsewhere that do not copy the data into OneLake, allowing users to access external data without duplication. Schema shortcuts extend this concept to reference schema-level objects from other sources.

**Lakehouse Structure:**
A Lakehouse in Fabric contains two primary folders. The Tables folder holds Delta Lake tables that support SQL queries, ACID transactions, and direct Power BI connectivity. The Files folder holds raw data in its original format, such as CSV, JSON, or Parquet, which can be explored and transformed as needed.

**SQL Analytics Endpoint:**
When a Lakehouse is created, Fabric automatically provisions a SQL analytics endpoint. This endpoint provides read-only T-SQL access to the Delta tables in the Lakehouse, allowing users to query data using familiar SQL syntax without modifying the underlying files.

**Schemas:**
Schemas are enabled by default in Fabric Lakehouses. The dbo schema is automatically created when a Lakehouse is provisioned. Fabric uses a four-part namespace that includes the workspace, Lakehouse, schema, and table, which provides logical organization and access control for data assets.

**Ingestion Methods:**
Fabric provides multiple ways to bring data into a Lakehouse. Upload and Load to Table support direct file ingestion for CSV and Parquet files. Dataflows Gen2 offer a visual, low-code transformation experience. Notebooks provide Spark-based programmatic ingestion. Pipelines orchestrate complex data movement workflows. Shortcuts enable zero-copy access to external data without ingestion.

**Power BI Direct Lake Mode:**
Direct Lake mode allows Power BI to query Lakehouse data directly without importing it into a Power BI dataset. This provides near-real-time reporting on live data in the Lakehouse while reducing data duplication.

### Exam Gotchas

- OneLake is built on ADLS Gen2, not Blob Storage, and it uses Delta-Parquet as the default format.
- Load to Table only works for CSV and Parquet files; other formats require Notebooks or Dataflows.
- Schemas are enabled by default, and the dbo schema is automatically created, which is a detail frequently tested.
- The SQL analytics endpoint is read-only; you cannot run DML or DDL through it.
- Shortcuts reference data without copying it, which is different from ingesting data into the Lakehouse.
- Fabric workspaces have only four roles: Admin, Member, Contributor, and Viewer; there is no "Owner" role.

## Card 2: Delta Lake

### What It Is

Delta Lake is an open-source storage layer that brings reliability and ACID transaction support to data lakes. It stores data in Parquet files and maintains a transaction log in the `_delta_log` folder, which records every change made to the table. This architecture enables features like schema enforcement, time travel, and reliable concurrent access that traditional data lake formats do not provide.

### Key Details

**Architecture:**
Delta Lake consists of Parquet data files that contain the actual table data and a `_delta_log` directory containing JSON files that record every transaction performed on the table. Each JSON entry in the transaction log represents a committed change, such as adding or removing a file. This log is the source of truth for the current state of the table and enables features like time travel and rollbacks.

**ACID Transactions:**
Delta Lake supports full ACID transactions, meaning that every operation is atomic, consistent, isolated, and durable. This ensures that concurrent readers and writers do not corrupt the table and that partial writes are never visible to other users.

**Schema Enforcement:**
Delta Lake enforces schema on write, meaning that if you attempt to write data with a schema that does not match the existing table, the operation will fail. This prevents data corruption caused by schema drift and ensures data quality at the storage layer.

**Time Travel:**
Delta Lake maintains a complete history of every version of the table through its transaction log. You can query any historical version using the `versionAsOf` or `timestampAsOf` methods in Spark, or by using the `DESCRIBE HISTORY` command to see the full change log. This capability is essential for auditing, debugging, and recovering from accidental data modifications.

**CRUD Support:**
Delta Lake supports full create, read, update, and delete operations on tables. This makes it suitable for both analytical workloads and scenarios that require frequent data modifications, such as slowly changing dimensions or record-level updates.

**OptimizeWrite:**
OptimizeWrite is enabled by default in Fabric and reduces the number of small files written during data operations. By coalescing writes, it improves downstream query performance and reduces storage overhead. This is particularly important for streaming workloads that can generate many small files.

**OPTIMIZE:**
The OPTIMIZE command consolidates small Parquet files into larger ones, which improves query performance by reducing the number of files that need to be read. Running OPTIMIZE regularly is a best practice for tables that receive frequent small writes.

**V-Order:**
V-Order is a write-time optimization that is enabled by default in Fabric. It adds approximately 15% overhead during writes but significantly accelerates read performance for Power BI and SQL queries through a technique called Verti-Scan. V-Order is fully Parquet compliant, meaning that V-Ordered files can still be read by any Parquet-compatible tool, though the performance benefit is only realized by Fabric engines.

**VACUUM:**
The VACUUM command removes old Parquet files that are no longer referenced by the current version of the transaction log. By default, VACUUM retains files for 7 days, after which they are eligible for deletion. After VACUUM runs, time travel to versions older than the retention period is no longer possible because the underlying files have been removed. Importantly, VACUUM only removes data files, not transaction log entries.

**Managed vs External Tables:**
A managed table in Fabric means that the metadata and data files are both managed by the Lakehouse. When you delete a managed table, both the metadata and the underlying data files are deleted. An external table references files that exist outside the Lakehouse's managed storage. When you delete an external table, only the metadata is removed, and the original data files are preserved.

**DeltaTableBuilder API:**
The DeltaTableBuilder API provides a programmatic way to create and modify Delta tables using a fluent builder pattern in Spark. It supports operations like creating tables with specific schemas, adding columns, and setting table properties.

**DeltaTable API:**
The DeltaTable API provides direct access to Delta table file paths and metadata. It is useful for scenarios that require inspecting the physical layout of a table or performing operations at the file level.

**Partitioning:**
Partitioning organizes data into subdirectories based on column values, which enables partition pruning during queries. Partition pruning eliminates the need to scan all data files when a query filters on the partition column. However, partitioning is an anti-pattern for high-cardinality columns because it generates too many small files, which degrades performance.

**Spark Structured Streaming with Delta:**
Spark Structured Streaming supports Delta Lake as both a source and a sink. When reading from a Delta table as a streaming source, you can set `ignoreChanges` or `ignoreDeletes` to control how the stream handles updates and deletes in the source table. When writing to a Delta table as a streaming sink, you must specify a `checkpointLocation` to enable fault-tolerant exactly-once processing.

### Exam Gotchas

- VACUUM removes old data files, not transaction logs; transaction logs are never deleted by VACUUM.
- Time travel is only possible within the VACUUM retention period; once files are vacuumed, those historical versions are gone.
- V-Order adds write overhead (~15%) but the read benefit is only realized by Fabric engines (Power BI, SQL endpoint); third-party Parquet readers still work but do not get the Verti-Scan benefit.
- Managed tables delete data when dropped; external tables do not. This is a critical distinction for exam questions about data retention.
- High-cardinality columns should not be used for partitioning because they create too many small files.
- OptimizeWrite is enabled by default, which is a common exam detail.
- When using Delta as a streaming sink, a checkpointLocation is mandatory.

## Card 3: Medallion Architecture

### What It Is

The Medallion Architecture is a multi-layer data architecture pattern used in Microsoft Fabric to organize data as it moves from raw ingestion through cleansing and enrichment to business-ready consumption. It uses three named layers—Bronze, Silver, and Gold—each serving a distinct purpose in the data lifecycle. The architecture provides a structured approach to data quality, governance, and performance by separating raw data storage from validated data and from final business-consumable datasets.

### Key Details

**Bronze Layer:**
The Bronze layer is the raw, unaltered landing zone for incoming data. Data in Bronze is stored exactly as it arrives from the source systems, with no transformations applied. It serves as the single source of truth for all historical data and provides an immutable archive that can be referenced for auditing, debugging, or reprocessing. Bronze tables are typically stored as external tables or in the Files folder of a Lakehouse.

**Silver Layer:**
The Silver layer contains data that has been validated, cleansed, and brought into a consistent format. It serves as the central repository of curated data that has undergone quality checks and standardization. Data in Silver is typically deduplicated, null-handled, type-cast, and enriched with basic business logic. This layer is the foundation for all downstream analytical consumption.

**Gold Layer:**
The Gold layer contains enriched, business-ready data organized into star schemas, summary tables, or other aggregated structures optimized for reporting and analytics. Gold layer data is typically consumed directly by Power BI, SQL analytics endpoints, or other reporting tools. An organization can maintain multiple Gold layers for different business domains, such as finance, sales, or operations, each tailored to specific analytical needs.

**Custom Layers:**
While the Medallion Architecture prescribes three layers, organizations are free to add custom layers as needed. For example, an organization might add a "Platinum" layer for highly aggregated executive dashboards or a "Staging" layer for pre-processing before Bronze. The key principle is that each layer adds value through transformation while maintaining clear separation of concerns.

**Transformation vs Orchestration:**
In Fabric, transformation and orchestration are handled by different workloads. Dataflows Gen2 and Notebooks are used for data transformation—applying business logic, cleansing, and enriching data as it moves between layers. Pipelines are used for orchestration—scheduling and coordinating the movement and transformation of data across the architecture. Understanding which workload handles which responsibility is important for both architecture design and exam questions.

**Layer Flow Decisions:**
Data typically flows from Bronze to Silver to Gold, but the architecture allows for flexibility. Some datasets may skip a layer if no additional transformation is needed, while others may pass through multiple transformations within a single layer. The key decision is ensuring that each layer adds measurable value and that the overall flow is maintainable and auditable.

**Gold Layer Options:**
Gold layer data can be materialized in several ways depending on the consumption pattern. Star schema tables in a Lakehouse provide optimized structures for Power BI reporting. A Data Warehouse can serve as the Gold layer for organizations that prefer T-SQL-based analytics. The SQL analytics endpoint provides read-only SQL access to Lakehouse Gold tables. Power BI Direct Lake mode enables direct querying of Gold layer data without import, reducing data duplication.

**Security Considerations:**
The Medallion Architecture supports granular security by allowing different layers to reside in different workspaces with different access permissions. Bronze layer data can be made read-only for compliance purposes, ensuring that raw source data is never modified. Silver layer data can be restricted to data engineers who manage transformations. Gold layer data can be made read-only for consumers, preventing accidental modifications to business-critical datasets.

**CI/CD Considerations:**
Continuous integration and continuous deployment become critical at the Gold layer because changes to Gold layer definitions directly impact business reporting. Version control, automated testing, and deployment pipelines should be established for Gold layer transformations and schema definitions. Bronze and Silver layers are less sensitive to CI/CD because they represent intermediate states, but Gold layer reliability is paramount.

### Exam Gotchas

- Bronze is raw and unaltered; it is the source of truth, not a staging area for transformations.
- Silver is the central repository of cleansed and validated data; it is not simply " Bronze minus errors."
- Multiple Gold layers are explicitly supported for different business domains; this is not an anti-pattern.
- Dataflows Gen2 and Notebooks handle transformation; Pipelines handle orchestration—do not confuse the two.
- Gold layer read-only access is a security best practice that is frequently tested.
- Bronze layer read-only for compliance is an important governance consideration.
- CI/CD is most critical at the Gold layer because it directly affects business reporting.

## Card 4: Warehouse vs SQL Analytics Endpoint

### What It Is

A Warehouse in Microsoft Fabric is a full T-SQL analytics endpoint that provides read-write access to data using Data Definition Language (DDL), Data Manipulation Language (DML), and transaction control statements like MERGE. It supports complete ACID transactions and is designed for enterprise data warehousing workloads. The SQL analytics endpoint, by contrast, is a read-only T-SQL interface that is automatically provisioned when a Lakehouse is created. It provides SQL query access to the Delta tables stored in the Lakehouse but does not support write operations.

### Key Details

**Warehouse Capabilities:**
A Fabric Warehouse provides full read-write T-SQL capabilities, including DDL statements for creating and modifying tables, DML statements for inserting, updating, and deleting data, and the MERGE statement for upsert operations. It supports complete ACID transactions, which means all changes are atomic and consistent. Warehouses are designed for traditional data warehousing scenarios where centralized, governed, high-performance SQL analytics are required.

**SQL Analytics Endpoint Capabilities:**
The SQL analytics endpoint is a read-only T-SQL interface that is automatically created alongside each Lakehouse. It allows users to query Delta tables using familiar SQL syntax, create views, and define stored procedures. However, it does not support DDL or DML operations, meaning you cannot create tables, insert data, or modify existing data through this endpoint.

**Comparison:**
A Warehouse is a standalone, fully managed T-SQL endpoint with full read-write capabilities, while the SQL analytics endpoint is a read-only interface layered on top of a Lakehouse. A Warehouse stores its own data independently, whereas the SQL analytics endpoint reads from Delta tables managed by the Lakehouse. Both support views, stored procedures, and SQL-based security, but only the Warehouse supports transactions and data modification.

**When to Use a Warehouse:**
Use a Warehouse when you need full T-SQL capabilities for data warehousing workloads, including DDL, DML, and MERGE operations. It is appropriate when the data architecture requires a centralized, governed repository with enterprise-grade transaction support and when the primary consumers are SQL analysts and report builders who need write access.

**When to Use the SQL Analytics Endpoint:**
Use the SQL analytics endpoint when you need read-only SQL access to Lakehouse data without duplicating it into a separate warehouse. It is appropriate when the Lakehouse already contains well-structured Delta tables and when the primary consumption pattern is query-based rather than write-based.

**Shared Capabilities:**
Both the Warehouse and the SQL analytics endpoint support creating views, defining stored procedures, and implementing SQL-based security through row-level security and column-level security. Both provide T-SQL syntax compatibility, making it easy for SQL-proficient users to work with either option.

### Exam Gotchas

- The SQL analytics endpoint is read-only; you cannot run INSERT, UPDATE, DELETE, CREATE TABLE, or MERGE through it.
- A Warehouse is a standalone resource, while the SQL analytics endpoint is automatically associated with a Lakehouse.
- Both support views and stored procedures, but only the Warehouse supports write operations through those objects.
- The SQL analytics endpoint reads directly from Delta tables in the Lakehouse, so changes to the Lakehouse are immediately visible.
- A Warehouse stores its own data independently and does not share storage with a Lakehouse.
- Both support row-level and column-level security for access control.
