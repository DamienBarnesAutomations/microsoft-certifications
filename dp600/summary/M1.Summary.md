# M1.Summary.md

## Microsoft Fabric (End-to-End Analytics Platform)

**Core Concept**
Microsoft Fabric is a unified SaaS analytics platform where all data is stored in a single open format (Delta-Parquet) in OneLake, accessible by all compute engines (Data Engineering, Warehouse, Data Factory, Power BI, Real-Time Intelligence, Data Science, Databases, Industry Solutions, IQ) without data movement.

**Technical Specifications**
- **OneLake foundation:** Built on ADLS Gen2; all engines write in Delta-Parquet format; open formats (Delta, Parquet, CSV, JSON) supported
- **Workspaces:** Logical containers for organizing items; support licensing type, OneDrive access, ADLS Gen2 connection, Git integration (bidirectional with Azure DevOps/GitHub), Spark workload settings; four roles: Admin, Member, Contributor, Viewer
- **Workspace settings:** License type, OneDrive access, ADLS Gen2 storage connection, Git integration, Spark workload settings
- **Admin portal:** Manage groups/permissions, configure data sources/gateways, monitor usage/performance, access admin APIs/SDKs; enable Fabric for entire org or specific security groups
- **OneLake catalog:** Searchable discovery across tenant; shows metadata: name, type, owner, last refresh, workspace, sensitivity labels, endorsement status; permission-based visibility (users only see shared items); filter by workspace/domain/keyword/item type
- **Domains:** Group data by business area; used for organization and governance
- **Data mesh support:** Decentralized data ownership with centralized governance; no direct Azure resource access needed
- **Copilot:** Enabled by default for all workloads; administratively disable per tenant or capacity; generates code, SQL, KQL, DAX, reports; explains and fixes code
- **Fabric IQ (preview):** One of three IQ workloads (Fabric IQ, Foundry IQ, Work IQ). Fabric IQ models business data via ontologies, semantic models, and graphs. Foundry IQ connects structured/unstructured data across Azure, SharePoint, OneLake, web. Work IQ captures collaboration signals from documents, meetings, chats, workflows.
- **Data agents:** Conversational Q&A across lakehouses, warehouses, semantic models, ontologies; use NL2SQL, NL2DAX, NL2KQL
- **Data lineage:** Visual view of data flow and dependencies across workspace items

**Architectural Logic**
Fabric solves the problem of fragmented analytics tooling (separate data lakes, warehouses, ETL tools, BI platforms) by unifying all compute engines on a single open-format data lake (OneLake). This eliminates data duplication, reduces governance gaps, and ensures the same governed data powers both reports and AI workloads. The SaaS model eliminates infrastructure management. Workspaces provide logical isolation and access control, while OneLake provides physical unification—a "single logical lake" across regions and clouds.

**Implementation Workflow**
1. **Enable:** Fabric Admin enables Fabric in Admin portal > Tenant settings (org-wide or per security group).
2. **Create workspace:** Create a workspace; configure license type, Git integration, Spark settings.
3. **Create items:** Create lakehouses, warehouses, semantic models, notebooks, pipelines as needed per workload.
4. **Ingest & govern:** Ingest data via pipelines/dataflows/mirroring; apply sensitivity labels, endorsement, descriptions.
5. **Collaborate:** Assign workspace roles (Admin/Member/Contributor/Viewer); use item-level permissions for granular access.
6. **Consume with AI:** Copilot available across all workloads; data agents for natural language querying.

**Exam Gotchas & Distinctions**
- **OneLake vs. separate storage:** Unlike traditional environments where each tool (Spark, SQL, Power BI) has its own storage, OneLake is a single logical lake. All engines read/write the same data without duplication.
- **Workspace roles vs. item permissions:** Workspace roles (Admin/Member/Contributor/Viewer) apply to all items in a workspace. Item permissions allow per-item sharing for granular control. A Viewer with no item permissions sees items listed but has zero data access by default.
- **Fabric IQ vs. Foundry IQ vs. Work IQ:** Fabric IQ = business data/ontologies in OneLake; Foundry IQ = enterprise knowledge across Azure/SharePoint/web; Work IQ = collaboration signals from M365.
- **Copilot capacity requirement:** F2 or higher (or P1+); Trial SKUs not supported for Copilot in notebooks and Dataflows.
- **Enabling Fabric:** Requires Fabric Admin, Power Platform Admin, or Global Admin role.
- **Data mesh support:** Fabric supports decentralized ownership with centralized governance—know this for the exam.

## OneLake

**Core Concept**
OneLake is the tenant-wide, single-logical-lake storage layer built into every Fabric environment, automatically available with no setup, eliminating data silos by providing a single copy of data accessible to all Fabric workloads.

**Technical Specifications**
- **Storage foundation:** Azure Data Lake Storage Gen2 (ADLS Gen2)
- **Default table format:** Delta Lake (open Parquet files with transaction log); also supports Parquet, CSV, JSON
- **Tenant-wide:** Automatically provisioned when Fabric is enabled; no separate setup
- **Single source of truth:** All workloads read/write the same underlying files; updates visible immediately
- **OneLake catalog:** Searchable inventory across tenant; metadata: name, type, owner, last refresh, workspace, sensitivity labels, endorsement (Promoted/Certified/Master data); permission-based visibility; filter by keyword/item type/workspace/domain
- **Shortcuts:** References to external/internal data without copying. Sources: other OneLake locations, ADLS Gen2, Amazon S3, Dataverse. Cross-workspace collaboration supported. Schema shortcuts map entire schema to Delta tables in another lakehouse or ADLS Gen2. OneLake manages source permissions—user's identity used for authorization. Not suitable when a stable snapshot is required, network latency impacts performance, or compliance requires physically separate copies.
- **Ingestion methods:**
  - **Mirroring:** Continuous replication from SQL Server, Azure SQL DB, Azure Cosmos DB, Snowflake—changes reflected automatically
  - **Pipelines:** Data Factory orchestration with copy activities
  - **Dataflows:** Power Query-based ETL (Gen2)
  - **Streaming:** Eventstream-based continuous ingestion from IoT, app logs, clickstream
  - **Direct upload:** Upload files directly through Fabric UI
- **Real-Time Hub:** Centralized catalog for discovering streaming data (eventstreams, KQL tables) and Azure/Fabric events. Contents: Data sources (Microsoft/external/Kafka/Google Cloud Pub/Sub/MQTT), Azure sources (IoT Hub, Service Bus, Event Hubs, Data Explorer), Fabric events (workspace item changes, OneLake file operations), Azure events (Blob Storage events)
- **Purview integration:** OneLake integrates with Microsoft Purview for data governance—classification, sensitivity labels, lineage

**Architectural Logic**
OneLake implements a "single copy" architecture that eliminates the traditional problem of data silos. In traditional environments, each team maintains its own copy of data for its tools, creating inconsistency and storage waste. OneLake provides a unified storage layer that all compute engines access directly. When data changes, everyone sees the updated version immediately. Shortcuts extend this by providing access to external data without copying, while maintaining data consistency. For AI workloads, the OpenLake catalog powers Copilot's data discovery—the same catalog users browse is what AI uses to find relevant data.

**Implementation Workflow**
1. **Discovery:** Open OneLake catalog; search by name, workspace, domain, or tag; filter by type, endorsement, sensitivity label.
2. **Connect:**
   - For existing data: Create shortcuts (OneLake, ADLS, S3, Dataverse)
   - For new data: Use ingestion (Mirroring, Pipelines, Dataflows, Streaming, Upload)
3. **Validate:** Preview data via SQL analytics endpoint (read-only T-SQL) before building on it.
4. **Consume:** Create semantic models (Power BI Direct Lake), query via Spark notebooks, or discover streaming data via Real-Time Hub.

**Exam Gotchas & Distinctions**
- **Shortcuts vs. copying:** Shortcuts provide access without data duplication and maintain consistency with source. Not suitable for point-in-time snapshots, high-latency connections, or compliance-mandated physical separation.
- **OneLake Catalog vs. Real-Time Hub:** OneLake catalog is for batch/stored data (lakehouses, warehouses, semantic models); Real-Time Hub is for data-in-motion (eventstreams, KQL tables).
- **Delta format default:** Analytical engines write in Delta-Parquet format automatically. Not all file formats in OneLake are Delta—only managed tables.
- **Permission-based visibility:** The OneLake catalog respects access permissions—different users see different catalogs. If you can't find an item, you don't have access.
- **Schema shortcuts:** Map an entire schema of Delta tables from another lakehouse or ADLS Gen2, making them appear as local tables—different from individual shortcuts.
- **Mirroring is continuous, not batch:** Changes in source are automatically reflected in OneLake with no manual refresh.
- **Labels on export:** Sensitivity labels are preserved on export to Excel, PDF, PowerPoint, .pbix but NOT on CSV or TXT (Fabric shows a warning).

## Lakehouse

**Core Concept**
A lakehouse in Fabric combines flexible data lake storage with data warehouse analytical capabilities, storing structured, semi-structured, and unstructured data in OneLake with both Apache Spark (read/write) and a read-only SQL analytics endpoint.

**Technical Specifications**
- **Storage areas:**
  - **Tables:** Managed Delta Lake tables with schema enforcement, ACID transactions, SQL-queryable via SQL analytics endpoint; auto-optimized and maintained
  - **Files:** Raw/semi-structured files in native format (CSV, JSON, Parquet, images, documents); no schema enforcement; no direct SQL querying
- **Delta Lake:** Open-source storage layer providing ACID transactions, schema enforcement, time travel (query previous versions/rollback), efficient updates/deletes; consists of Parquet data files + transaction log
- **Access modes:**
  - **Lakehouse Explorer:** Manage tables, files, folders; add reference lakehouses for side-by-side browsing
  - **SQL analytics endpoint:** Read-only T-SQL queries against Delta tables; supports views, functions, SQL security (RLS, CLS), but cannot modify data
- **Schemas:** Enabled by default; `dbo` created automatically; organize tables by business domain; support schema-level permissions and four-part namespace queries (`workspace.lakehouse.schema.table`)
- **Ingestion methods:** Upload (local files/folders), Load to Table (no-code for CSV/Parquet; append or overwrite), Dataflows Gen2 (Power Query), Notebooks (Spark), Data Factory pipelines (Copy activity), Shortcuts (OneLake, ADLS, S3, Dataverse)
- **Compute:**
  - Spark notebooks (PySpark, Spark SQL, Scala, R) for read/write
  - SQL analytics endpoint for read-only T-SQL
  - Power BI Direct Lake (reads Delta files directly with no import/refresh)
- **Security:** Workspace roles, item-level sharing; SQL analytics endpoint supports RLS and CLS; OneLake security roles for granular table/folder access
- **Four-part namespace:** `workspace.lakehouse.schema.table` for cross-workspace queries

**Architectural Logic**
The lakehouse solves the "two-tier" problem where organizations maintained both a data lake (for scale, flexibility, low cost) and a data warehouse (for ACID, schema, query performance). By bringing Delta Lake (ACID, schema enforcement, time travel) directly to the data lake storage, the lakehouse eliminates the need to manage separate systems for raw exploration and structured analytics. Data engineers use Spark notebooks for complex transformations; analysts query the same data via SQL endpoint or Power BI Direct Lake—no data movement needed. Use a lakehouse when you need to handle mixed data formats, evolving schemas, medallion architecture, or Python/Spark-based data science. Do not use for heavy multi-table transactional updates (use warehouse), real-time streaming (use eventhouse), or when strict schema-on-write governance is required.

**Implementation Workflow**
1. Create a lakehouse in a Fabric workspace (schemas enabled by default).
2. Ingest data into `Files` (staging) or `Tables` (managed Delta) via upload, Load to Table, notebooks, dataflows, pipelines, or shortcuts.
3. Transform data using notebooks (Spark SQL/PySpark) or Dataflows Gen2 (Power Query) to create curated Delta tables.
4. Query via SQL analytics endpoint (T-SQL) for validation/analysis; connect Power BI via Direct Lake for reporting.
5. Apply security: workspace roles for collaboration; RLS/CLS on SQL endpoint; OneLake security roles for granular access.

**Exam Gotchas & Distinctions**
- **Tables vs. Files:** Tables are Delta-formatted, SQL-queryable, schema-enforced. Files are raw, any format, no schema, no SQL access. Common exam confusion point.
- **SQL analytics endpoint is read-only:** No INSERT/UPDATE/DELETE/MERGE. Only SELECT, views, functions, and SQL security configuration.
- **Load to Table no-code:** Only supports Parquet and CSV files. Other formats require notebooks or dataflows.
- **Schemas in lakehouse:** Enabled by default; enables four-part naming for cross-workspace queries.
- **Delta Lake time travel:** Transaction log enables querying previous versions and rollback—but VACUUM removes old files and breaks time travel.
- **Direct Lake:** Power BI reads Delta files directly from OneLake without scheduled refresh. If a query exceeds memory/resource thresholds, falls back to DirectQuery (configurable—allow or disallow fallback in semantic model settings).
- **Cross-workspace queries:** Use four-part naming (`workspace.lakehouse.schema.table`), not just three-part.

## Data Warehouse

**Core Concept**
A Fabric data warehouse is a fully managed, enterprise-scale relational database built on Delta format in OneLake, providing full read-write T-SQL (DDL and DML) with multi-table ACID compliance for structured analytical workloads.

**Technical Specifications**
- **Storage:** Open Delta format on OneLake—accessible by other Fabric workloads without duplication
- **T-SQL capabilities:** Full DDL (CREATE, ALTER, DROP) and DML (INSERT, UPDATE, DELETE, MERGE) with multi-table ACID compliance
- **Ingestion methods:**
  - `COPY INTO`: Bulk load from files (CSV, Parquet) in Azure storage or OneLake
  - `OPENROWSET`: Query files from external storage without creating tables first
  - Pipelines and Dataflows: Orchestrated movement and transformation
  - Cross-database queries: Query lakehouse tables via three-part naming (`database.schema.table`) without copying
- **Managed:** No infrastructure to configure; compute scales automatically and independently from storage
- **Tooling support:** SQL query editor (IntelliSense, code completion, syntax highlighting), Visual Query Editor (drag-and-drop, generates T-SQL behind the scenes), SSMS, Azure Data Studio, any SQL client via TDS connections
- **Copilot:** Generate SQL from natural language, code completion, explain/fix existing queries
- **Cross-database queries:** Three-part naming to join warehouse tables with lakehouse tables in a single query
- **Table clones:** `CREATE TABLE AS CLONE OF` creates zero-copy reference at a point in time; only changed data consumes new storage; useful for dev/testing, data recovery, preserving snapshots for historical reporting
- **Staging pattern:** Land raw data in staging tables via COPY INTO/pipelines, then transform (INSERT/SELECT) into dimensional model with surrogate key lookups
- **Fact/dimension modeling:** Surrogate keys (warehouse-generated integers via IDENTITY), alternate keys (source system natural keys for traceability), star schema (fact directly to dimensions) or snowflake schema (normalized dimensions)
- **Security:** Workspace roles, item permissions (Read, ReadData, ReadAll), granular SQL security (object-level, RLS, CLS, Dynamic Data Masking via T-SQL DCL)
- **Monitoring:** Query Insights (30-day retention) via system views: `queryinsights.exec_requests_history`, `queryinsights.long_running_queries`, `queryinsights.exec_sessions_history`; DMVs for real-time monitoring (`sys.dm_exec_requests`)
- **Warehouse vs. SQL analytics endpoint table:**
  - Read data: Both Yes
  - Write data (INSERT/UPDATE/DELETE/MERGE): Warehouse Yes, Endpoint No
  - Create tables (DDL): Warehouse Yes, Endpoint No
  - Views/stored procedures: Both Yes
  - Data source: Warehouse = native tables; Endpoint = lakehouse Delta tables

**Architectural Logic**
The warehouse bridges traditional relational data warehousing with modern data lake architecture by storing all data in Delta format on OneLake while providing the full T-SQL surface that SQL professionals expect. Unlike the lakehouse (read-only SQL endpoint), the warehouse supports full DDL/DML, enabling transactional ETL patterns—MERGE for upserts, CTAS for one-time materializations, stored procedures for recurring transformations. Use warehouse over lakehouse when the workload requires multi-table ACID transactions, slowly changing dimension updates, or a SQL-first team that needs full DDL/DML. Use warehouse over eventhouse for structured BI and star schema dimensional modeling.

**Implementation Workflow**
1. Create a warehouse in a Fabric workspace (from create hub or within workspace).
2. Ingest data into staging tables via COPY INTO, pipelines, or cross-database queries.
3. Create dimensional model: dimension tables (surrogate keys via IDENTITY) + fact tables.
4. Load dimensions via INSERT...SELECT (initial) or MERGE (SCD Type 1); load facts by joining staging to dimensions for surrogate key resolution.
5. Create views and stored procedures for reusable logic.
6. Apply security (workspace roles, item permissions, SQL granular).
7. Connect Power BI via Direct Lake for reporting.

**Exam Gotchas & Distinctions**
- **Warehouse vs. lakehouse SQL analytics endpoint:** Both support Direct Lake for Power BI. Warehouse = full read-write T-SQL. Lakehouse endpoint = read-only.
- **No foreign key enforcement:** Fabric warehouse does NOT enforce FK constraints. Referential integrity depends entirely on ETL logic. This is different from traditional SQL Server/Azure SQL DB.
- **Table clones are zero-copy:** Only changed data consumes new storage. Not the same as full copies (SELECT INTO duplicates all data).
- **Query Insights retention:** 30 days. Uses specific system views for historical analysis.
- **KILL command:** Only workspace Admins can terminate sessions. Members/Contributors/Viewers can only see their own queries.
- **Visual Query Editor:** Generates T-SQL behind the scenes—useful for drag-and-drop query building, but switch to SQL query editor for complex logic.
- **Cross-database three-part naming:** `warehouse.schema.table` or `lakehouse.schema.table`—works across warehouses and lakehouse SQL analytics endpoints.

## Real-Time Intelligence

**Core Concept**
Real-Time Intelligence in Fabric provides an integrated suite (Eventstreams, Eventhouses, Real-Time Hub, KQL Querysets, Real-Time Dashboards, Activator) to ingest, process, store, query, visualize, and act on streaming data with minimal latency.

**Technical Specifications**
- **Eventstreams:** Continuous data flows from sources (Azure Event Hubs, IoT Hub, Service Bus, CDC feeds, Kafka, Google Cloud Pub/Sub, MQTT (preview), Fabric events, Azure Blob Storage events). Support real-time transformations (filter, manage fields, aggregate, group by, expand, join, SQL code) as data flows through. Destinations: KQL database in Eventhouse, Lakehouse, derived stream, Activator, custom endpoint.
- **Eventhouse:** Workspace of KQL databases sharing capacity and resources. KQL databases store time-series/event-based data with automatic indexing and partitioning by ingestion time. Columnar store with compression. Schema-on-write with dynamic fields for semi-structured data. Append-optimized—not designed for UPDATE/DELETE.
- **KQL (Kusto Query Language):** Designed for time-series analysis on large volumes of structured/semi-structured/unstructured data. Same language used in Azure Data Explorer, Azure Monitor Log Analytics, Microsoft Sentinel. Supports a T-SQL subset. Built-in operators: `take`, `where`, `summarize`, `project`, `make-series`, `series_decompose_anomalies`, `series_decompose_forecast`.
- **KQL Queryset:** Workspace for running/managing queries against KQL databases; supports multiple tabs, saved queries, sharing; also supports T-SQL queries alongside KQL.
- **Real-Time Dashboards:** Connect directly to KQL databases; auto-refresh as new data arrives; composed of tiles each based on a KQL query; interactive (drill into data, filter, change visualization type).
- **Activator:** Monitors streaming data against user-defined rules and thresholds. Four core concepts: Events (each record), Objects (business entities represented by event data), Properties (fields mapped to object state), Rules (conditions triggering actions). Actions: notifications, Power Automate workflows, Fabric data pipelines, notebooks.
- **Real-Time Hub:** Central catalog for streaming data discovery. Categories: Data sources (Browse/connect to streaming sources), Azure sources (IoT Hub, Service Bus, Event Hubs, Data Explorer), Fabric events (workspace item changes, OneLake file operations), Azure events (Blob Storage events). Preview data, set alerts (Activator), create eventstreams, query KQL tables, create Real-Time Dashboards.
- **Direct ingestion to KQL database:** Via local files, Azure storage, Amazon S3, Azure Event Hubs, OneLake, and more. Update policies transform data after it lands in the database (different from Eventstream transformations that happen during stream processing).
- **Management commands:** Update policies (auto-transform incoming data), materialized views (precalculate summaries), stored functions (reusable query logic).
- **Power BI integration:** Can create Power BI reports from KQL database data (DirectQuery, not Direct Lake).

**Architectural Logic**
Real-Time Intelligence solves the problem that traditional batch-oriented stores (lakehouse, warehouse) cannot handle streaming data with sub-second latency. Eventstreams capture and transform data in motion; Eventhouses store it with automatic time-based partitioning for fast retrieval; Activator enables event-driven automation. The architecture is event-driven rather than batch-scheduled. Use Eventhouses over lakehouses when data arrives continuously (streaming), needs to be queryable within seconds, and involves time-window analysis. Use Eventhouses over warehouses when the ingestion pattern is append-only streaming rather than batch transactional loads. The Real-Time Hub provides the discovery layer for streaming data, analogous to what the OneLake Catalog provides for batch data.

**Implementation Workflow**
1. **Discover:** Open Real-Time Hub to find existing eventstreams or KQL tables.
2. **Ingest:** Create an Eventstream or directly ingest data into a KQL database.
3. **Transform:** Apply real-time transformations within the Eventstream (filter, aggregate, join) or use update policies in the KQL database.
4. **Store:** Route processed data to an Eventhouse KQL database for indexed storage.
5. **Query:** Use KQL Queryset (KQL or T-SQL) for analysis.
6. **Visualize:** Create Real-Time Dashboards (auto-refreshing) or Power BI reports.
7. **Act:** Configure Activator rules to trigger notifications, workflows, or data pipelines based on conditions.

**Exam Gotchas & Distinctions**
- **Eventstreams vs. KQL update policies:** Eventstream transformations happen *during* stream processing (before data reaches destination). Update policies happen *after* data lands in a KQL database. Different stages.
- **Real-Time Hub vs. OneLake Catalog:** Real-Time Hub = streaming/event data in motion; OneLake Catalog = batch/stored data at rest.
- **DirectQuery, not Direct Lake:** Power BI connects to Eventhouses via DirectQuery, not Direct Lake, because the columnar format is not Delta/Parquet.
- **Append-only:** Eventhouse is append-optimized, not designed for UPDATE/DELETE. If exam scenario requires modifying individual records, warehouse/lakehouse is the right choice.
- **Always-On option:** Available for critical monitoring systems that can't tolerate startup latency. Must be explicitly enabled. Adds cost.
- **Activator vs. Power Automate:** Activator is Fabric-native for real-time event conditions; can trigger Power Automate flows for downstream actions.
- **KQL syntax:** Pipe-based (`|`) operator chaining. `Table | take 10` is equivalent to `SELECT TOP 10 * FROM Table`.
