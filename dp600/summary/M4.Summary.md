## AI-Ready Semantic Layer

**Core Concept**
Preparing a semantic model for AI consumption involves grounding AI tools like Copilot and data agents with clear naming, thorough documentation (descriptions within 200 characters), linguistic synonyms/relationships, and explicit Prep for AI configuration (AI data schema, AI instructions, verified answers) so that retrieval-augmented generation (RAG) produces accurate natural-language answers.

**Technical Specifications**
- **Grounding:** Contextual information — table names, column names, relationships, measure definitions, descriptions (truncated to first 200 characters in DAX query view), linguistic schema, data categories — that AI retrieves before generating a response.
- **RAG process:**
  1. User submits a prompt (written question or button selection).
  2. Copilot preprocesses the prompt by collecting grounding data from the semantic model schema, linguistic schema, descriptions, and other metadata.
  3. Copilot sends the augmented prompt and grounding data to Azure OpenAI.
  4. Azure OpenAI generates a response.
  5. Copilot postprocesses the response (applies responsible AI filters) and returns output.
- **Copilot is nondeterministic:** Same input may produce different responses; preparation reduces ambiguity but cannot guarantee identical output.
- **What AI consumes from the semantic model:**
  - Table names — identifies available business entities
  - Column names — maps user questions to specific data fields
  - Relationships — understands how tables connect for correct joins
  - Measure definitions — identifies calculated metrics (Total Sales, Profit Margin)
  - Descriptions — business context for tables, columns, measures
  - Data types and format strings — how to display/interpret values
  - Linguistic schema — synonyms and relationships for varied user terminology
  - Data category — geographic, URL, or image data for appropriate handling
  - Hidden columns/measures and tables marked as private are **excluded** from Copilot
- **Schema reduction:** Copilot restricts context to what's most relevant to the user's question; models with fewer, well-organized tables make this more effective.
- **Model complexity issues:**
  - Duplicate field names across tables (e.g., `Name` in both Customer and Store) — Copilot may choose the wrong one
  - Complex DAX patterns — harder for AI to interpret and explain correctly
  - Implicit measures — Copilot may create its own aggregations for columns without explicit measures, which may not match business logic
  - Currency conversion tables, disconnected tables (field parameters), calculation groups can produce unexpected results
- **Gold layer design principles:**
  - One entity per table (Customers, Products, Sales)
  - Star schema structure — dimension tables describe entities, fact tables capture events
  - Business-friendly table names — use `Sales Transactions` instead of `fact_sales_v2`
- **Column naming best practices:**
  - Full words: `Customer Name` instead of `CustNm` or `cust_name`
  - Specific: `Order Date` instead of `Date` when multiple date columns exist
  - Units: `Revenue (USD)` or `Weight (kg)`
  - Avoid prefixes like `dim_` or `fact_`
  - Consistency across tables (e.g., always `Product Name` not `ProductTitle`)
- **Measure naming best practices:**
  - Describe the calculation: `Total Sales` is clear; `TS` is not
  - Include scope: `YTD Revenue` or `Sales (last 12 months)`
  - Avoid duplicate names across measures and columns
- **Descriptions for AI consumption:**
  - Table descriptions: what the table represents and what records it contains
  - Column descriptions: what values the column holds and business rules
  - Measure descriptions: business logic, inclusions, exclusions
  - Copilot in Power BI Desktop can generate measure descriptions automatically (review and revise)
  - **First 200 characters are all used for grounding** — put most important context first
- **Simplify for AI — hide these fields:**
  - Surrogate key columns (ProductKey, CustomerID) when a natural key or name column exists
  - ETL metadata columns (LoadDate, BatchID, SourceSystem)
  - Deprecated or unused columns
- **Keep visible for AI:**
  - Business-facing columns users reference in questions
  - Measures representing key business metrics
  - Date table columns for time intelligence
- **Linguistic modeling**
  - Configured via Q&A Setup in Power BI Desktop (Modeling ribbon)
  - **Synonyms:** Map alternate terms to fields (e.g., "Revenue" has synonyms Sales, Turnover, Income)
  - **Linguistic relationships:** Define verbs connecting entities ("Customers purchase Products", "Stores are located in Regions")
  - **Field exclusion:** Disable specific fields from Q&A/Copilot via "Include in Q&A" checkbox in Synonyms view
  - Requires Q&A to be enabled: File > Options and settings > Options > Data Load > Turn on Q&A
  - Copilot can suggest synonyms automatically
  - Requires ongoing maintenance as model/business terminology evolves
- **Prep for AI features** (Power BI Desktop: Home ribbon > Prep data for AI; Power BI service: semantic model > Prep data for AI):
  1. **AI data schema** — controls which tables/columns are visible to AI (complements hiding in the model itself; provides an additional layer of control specifically for AI consumption)
  2. **AI instructions** — free-form text explaining business terminology, rules, data scope, preferred measures. Do not repeat information already in descriptions/column names.
  3. **Verified answers** — predefined visuals for specific trigger phrases. Start with top 5-10 most common business questions. Ensures consistent responses for high-frequency or critical questions.
- All Prep for AI updates save to the semantic model (not individual reports), apply everywhere the semantic model is used, and can be managed through Git integration or deployment pipelines. After deploying through these channels, refresh the model in the Power BI service to sync updates.
- **Approved for Copilot:** Setting in Power BI service (Settings > Approved for Copilot) that:
  - Removes friction treatments (warning banners) from Copilot answers
  - Reports built on an approved model also inherit the status
  - Marking a model as Approved for Copilot is a commitment — prepare and test thoroughly first
- **Intelligence layers (semantic model to ontology connection):**
  - **Fabric IQ:** Business semantics within Fabric — ontology, data agents, operations agents
  - **Foundry IQ:** AI apps/agents in Microsoft Foundry — shared context and knowledge endpoints
  - **Work IQ:** Intelligence into M365 experiences (Copilot, Teams, Excel)
- **Validate AI readiness:**
  - **Copilot pane** in Power BI Desktop with skill picker (Answer questions about the data, Analyze report visuals, Create new report pages)
  - **HCAAT** ("How Copilot arrived at this") included in answers — shows what fields and filters Copilot used
  - **Download diagnostics** from Copilot pane menu — detailed info on grounding data and processing steps
  - **Add to page** — add Copilot-generated visual to canvas for direct inspection
  - Close and reopen Copilot pane to reflect updates from Prep for AI changes
- **AI readiness checklist:**
  - Tables have clear, business-friendly names representing entities
  - Columns have descriptive full-word names (no abbreviations)
  - Key measures have descriptions explaining business logic, inclusions, exclusions
  - Technical fields (surrogate keys, ETL columns) are hidden
  - Verified answers created for most common business questions
  - AI instructions document business context, terminology, data scope
  - Linguistic modeling includes relevant synonyms and relationships
  - Model is tested with Copilot and produces accurate, consistent responses
  - Model is marked as Approved for Copilot in the Power BI service

**Architectural Logic**
AI tools have no inherent business knowledge — they rely entirely on grounding data (schema, descriptions, synonyms, AI instructions) retrieved during the RAG preprocessing step. The quality of AI output is directly tied to grounding data quality because Azure OpenAI generates responses using only the context provided. The semantic model sits at the critical junction between data engineering (upstream ingestion/transformation) and AI consumption (downstream Copilot/data agents). Use Prep for AI features over model-level hiding when you need AI-specific visibility control separate from report-level visibility. Use linguistic modeling (synonyms and relationships) alongside AI instructions: linguistic modeling handles precise field-level terminology mapping, while AI instructions provide broad business context and rules. Verified answers override AI generation entirely for specific queries — use them where consistency is critical and the answer is stable, not where the business question or answer changes frequently.

**Implementation Workflow**
1. **Design gold layer:** Entity-oriented tables, star schema, business-friendly naming.
2. **Document:** Write clear table/column/measure descriptions with key context in first 200 characters. Use Copilot in Desktop to generate descriptions, then review.
3. **Simplify:** Hide technical columns (surrogate keys, ETL metadata) from the model.
4. **Configure Prep for AI:** Set AI data schema (hide technical fields from AI), write AI instructions (business rules, terminology, scope, preferred measures), create verified answers for top 5-10 common questions.
5. **Linguistic modeling:** Add synonyms and linguistic relationships via Q&A Setup (Modeling ribbon).
6. **Validate:** Test with Copilot pane in Desktop (close/reopen after each Prep for AI update). Use HCAAT and Download diagnostics to troubleshoot incorrect responses.
7. **Iterate:** Log questions that produce incorrect answers; add verified answers, update descriptions, adjust instructions, refine synonyms.
8. **Mark approved:** Set Approved for Copilot in Power BI service after thorough testing.

**Exam Gotchas & Distinctions**
- **Grounding vs. ontology:** Grounding is per-model context (descriptions, synonyms, AI instructions); ontology is the organization-wide shared business vocabulary (Fabric IQ).
- **Hidden fields:** Hiding a field in the model removes it from AI consideration entirely — both columns AND tables. The AI data schema in Prep for AI adds a separate AI-specific visibility layer.
- **Verified answers vs. AI instructions:** Verified answers are predefined visual responses to specific trigger phrases (bypass AI generation). AI instructions provide broad business context for interpreting questions.
- **First 200 characters truncation:** Descriptions are truncated at 200 characters for grounding — put the most important context first. This is specific to the DAX query view experience.
- **Implicit measures:** Copilot may aggregate a column without an explicit measure — the aggregation may not match intended business logic. Always create explicit measures for fields users will query.
- **Schema reduction:** Copilot tries to limit context to relevant fields; a model with many technical columns forces more assumptions. Fewer, cleaner tables = more accurate AI.
- **Copilot nondeterministic:** Same prompt can produce different responses. Preparation reduces ambiguity but can't guarantee identical output.
- **Fabric IQ vs. Foundry IQ vs. Work IQ:** Fabric IQ = Fabric ontologies/data agents; Foundry IQ = enterprise knowledge across Azure/SharePoint/web; Work IQ = M365 collaboration signals.
- **Approved for Copilot vs. endorsement:** Endorsement guides discovery/trust ranking; Approved for Copilot is an explicit governance gate that removes friction treatments in Copilot.
- **Prep for AI saves to semantic model:** All Prep for AI changes persist on the semantic model (not reports) and sync via Git/deployment pipelines — but require a model refresh in the service to take effect after deployment pipeline sync.

## Fabric IQ (Ontology)

**Core Concept**
Fabric IQ is a workload in Microsoft Fabric that creates ontologies — organization-wide, machine-understandable vocabularies of business concepts (entity types, properties, relationships) bound to OneLake data sources (lakehouse tables for static data, eventhouse streams for time-series data), enabling natural language queries through data agents and visual graph traversal through Graph in Microsoft Fabric.

**Technical Specifications**
- **Fabric IQ workload:** Sits alongside Data Engineering, Data Factory, Data Science, Data Warehouse, Real-Time Intelligence, and Power BI. Currently in preview.
- **Ontology item:** Fabric artifact containing entity types (business concepts), properties (characteristics), relationship types (connections), and data bindings (links to OneLake sources).
- **Build-bind-query workflow:**
  1. **Build:** Define entity types, properties, and relationship types (business vocabulary).
  2. **Bind:** Connect ontology definitions to lakehouse tables (static data) and eventhouse streams (time-series data) by mapping source columns to entity properties.
  3. **Query:** Use Graph (GQL), Query Builder (filter/explore without SQL), or data agents (natural language) against business concepts.
- **Entity type components:**
  - **Name:** Business-friendly name people use in conversation. 1-26 characters, alphanumeric/hyphens/underscores, start and end with alphanumeric. Choose names that make sense when spoken aloud (e.g., "Hospital contains Department").
  - **Properties:** Name (specific like `HospitalName` rather than generic `Name`), Data type (string, integer), Property type (Static — infrequently changing attributes; Time series — continuously arriving observations like vital signs).
  - **Key:** One or more properties that uniquely identify entity instances. Only string or integer properties. Required before binding — without a key, the system cannot create instances from source data.
- **Relationship types:**
  - Named, directional connections between two different entity types (e.g., "Hospital contains Department", "Room has Patient").
  - Direction matters: define based on how users ask questions (source → target direction).
  - Source and target entity types must be different.
  - Definitions establish *possible* connections; data bindings populate *actual* connections using source table keys.
- **Data binding:**
  - Maps ontology properties to actual source columns. Without bindings, the ontology has structure but no data.
  - **Static bindings:** Connect to lakehouse tables for infrequently changing data (hospital names, department locations, patient demographics).
  - **Time series bindings:** Connect to eventhouse tables for streaming, timestamped observations (heart rate, oxygen saturation, temperature).
  - **Dual-binding pattern:** An entity can have both static and time series bindings. Example: VitalSignEquipment has static attributes (EquipmentType, PatientId bound to lakehouse) and time series measurements (HeartRate, OxygenSaturation bound to eventhouse with Timestamp).
  - Static binding **must be configured first** in dual-binding — time-series data needs to attach to existing entity instances.
  - The static property in a time series binding is the linking key column (e.g., EquipmentId connecting readings to equipment entities), not a new static binding.
- **Relationship bindings:** Configure source data (table containing keys for both entity types), map source columns to entity type keys. Each row with values in both columns creates one relationship instance. The same table can serve as source for multiple relationships if it contains the necessary keys.
- **Preview experience:** Entity type overview shows: relationship graph (visual map of connections), property charts (distribution of property values), entity instances table (actual instances populated from bound data). Refresh browser 1-2 minutes after binding if "Updating your ontology" message appears.
- **Two creation paths:**
  1. **Generate from Power BI semantic model:** Select an existing Direct Lake semantic model. Creates entity types from tables, properties from columns (data types preserved), relationship types from model relationships, and data bindings automatically (Direct Lake with inbound public access only). Faster start but may produce technical names needing refinement.
  2. **Build from OneLake data:** Manual creation with full control from scratch. Clean business vocabulary from the start, but more upfront design work. Choose when no semantic model exists, models are optimized for reporting rather than vocabulary, or full control is desired.
- **Semantic model mode support for ontology generation:**

| Feature | Import mode | Direct Lake mode | DirectQuery mode |
|---|---|---|---|
| Entity type definitions | Supported | Supported | Supported |
| Property definitions | Supported | Supported | Supported |
| Relationship definitions | Supported | Supported | Supported |
| Data bindings to sources | Not supported | Supported (with inbound public access) | Not supported |
| Querying bound data | Not supported | Supported (without measures and calculated columns) | Not supported |

- **Verification tasks after generation:**
  - Rename technical table names to business-friendly names (e.g., `factsales` → `SaleEvent`)
  - Confirm properties mapped correctly
  - Verify entity type keys (some may not import automatically)
  - Confirm data bindings point to correct source tables
  - Name relationship types with business vocabulary
  - Bind relationship types to source data columns
  - Add time series bindings manually (not created during generation)
  - Handle multi-key scenarios manually (composite keys may need manual configuration)
- **Data agents:** Conversational Q&A powered by Azure OpenAI Assistant APIs. Configure with up to five data sources (lakehouses, warehouses, KQL databases, Power BI semantic models, or ontologies) in any combination. Generates SQL for lakehouses/warehouses, DAX for semantic models, KQL for KQL databases. Uses ontology business vocabulary for ontology sources. Enhanced by data agent instructions and example queries. Enforces read-only access and security protocols. Publish to M365 Copilot or integrate with Microsoft Copilot Studio.
- **Graph in Microsoft Fabric:** Native graph storage and compute using labeled property graph model (nodes = entities, edges = relationships with labels and properties). Queried via GQL (international standard). Automatically created from ontology entity types and relationships. Operates directly on OneLake without data duplication or ETL. Scale-out architecture handles large graph structures.

**Architectural Logic**
Fabric IQ separates business meaning from physical data structures. The ontology defines what a "Patient" is and how it relates to "Departments" without requiring knowledge of table schemas or column names. Data binding maps these conceptual definitions to actual OneLake sources without moving or duplicating data — the ontology creates a semantic layer that references existing data. This enables federated queries across lakehouse (static) and eventhouse (time-series) data using consistent business vocabulary. The build-bind-query pattern ensures that business concepts remain stable even when underlying storage changes. Use manual ontology creation from OneLake when you need complete control over business vocabulary from the start (no cleanup of autogenerated technical names). Use generation from Direct Lake semantic model when an existing well-structured model exists and you want to save setup time — but expect to refine entity names, keys, and add time series bindings. Use Graph (GQL) over Query Builder when analysis involves multi-hop relationship traversal ("Which patients are in departments within this hospital?"). Use data agents over Graph when the user needs natural language Q&A rather than visual exploration.

**Implementation Workflow**
1. **Create ontology:** + New item in Fabric workspace → Ontology (preview). Name with numbers, letters, underscores (no spaces or dashes).
2. **Choose approach:** Generate from Direct Lake semantic model or build manually from OneLake.
3. **If generating:**
   a. Open published semantic model in Fabric.
   b. Select Generate Ontology from ribbon.
   c. Choose target workspace and name.
   d. After creation, review entity type names (rename technical to business-friendly), verify keys, confirm data bindings, name relationships, bind relationship source data.
   e. Add time series bindings for streaming entity types.
4. **If building manually:**
   a. Select Add entity type from ribbon. Enter business-friendly name.
   b. Add properties: name, data type (string/integer), property type (static or time series).
   c. Configure entity type key (string or integer property) — required before binding.
   d. Repeat for each business concept.
   e. Add relationship types: select source entity on canvas → Add relationship type → choose target entity, name the relationship directionally.
5. **Bind static data:** Select entity type → Bindings tab → Add data to entity type → choose lakehouse from OneLake catalog → select table → map source columns to properties → configure key.
6. **Bind time series data:** Select entity type → Add data to entity type → choose eventhouse → select table → choose Timeseries binding type → specify Timestamp column → separate properties into Static (linking key) and Timeseries (measured values). Static binding must exist first.
7. **Configure relationship bindings:** Open relationship type → Source data → select workspace/lakehouse/table containing keys for both entity types → map source columns to entity type keys.
8. **Preview:** Select entity type → Entity type overview from ribbon → verify relationship graph, property charts, entity instances.

**Exam Gotchas & Distinctions**
- **Ontology vs. semantic model:** Semantic models serve specific reporting domains; ontologies standardize concepts organization-wide and are consumed by AI agents and graph traversal. Semantic models are the starting point for ontology generation but serve different purposes.
- **Generation vs. manual creation:** Generation is faster but produces technical names needing refinement. Manual builds produce clean business vocabulary from the start but require more upfront design.
- **Direct Lake required for full generation:** Data bindings are only created automatically when the semantic model uses Direct Lake mode with inbound public access enabled. Import and DirectQuery modes support entity type/relationship generation but NOT data bindings.
- **Static binding first in dual-binding:** Time-series data needs existing entity instances to attach to. The linking key (e.g., EquipmentId in the time series properties) must reference instances created by the static binding.
- **Entity key requirement:** Keys are required before binding; use string or integer properties only. Without a key, the system cannot create instances from source data.
- **Data binding does not copy data:** Bindings create a semantic layer referencing existing OneLake data — no data movement or duplication.
- **Property name constraints:** 1-26 characters, only alphanumeric/hyphens/underscores, start and end with alphanumeric.
- **Relationship binding vs. definition:** Definitions establish possible connections; bindings populate actual connections using source table keys. A relationship type without a binding exists as a definition but cannot be queried.
- **Ontology naming:** Use numbers, letters, underscores only (no spaces or dashes) in the ontology item name itself. Entity type names can be more natural business-language names.
- **Fabric IQ tenant settings:** Fabric administrator must enable certain tenant settings before ontology items can be created.
- **Preview refresh:** After binding, the preview may show "Updating your ontology" for 1-2 minutes — refresh browser to display results.
- **Graph auto-creation:** A managed graph is automatically created from ontology entity types and relationships — no separate setup needed. Queried using GQL.
- **Data agent limits:** Up to five data sources per agent (any combination of lakehouses, warehouses, KQL databases, semantic models, ontologies).
- **GQL vs. Query Builder:** GQL is for complex multi-hop graph traversal; Query Builder is for filtering and exploring entity instances without writing queries.
