## DAX Calculations

**Core Concept**
DAX (Data Analysis Expressions) is a formula language in Power BI semantic models for creating calculated tables, calculated columns, and measures—three calculation types with distinct evaluation behavior, storage characteristics, and use cases.

**Technical Specifications**
- **Calculated Tables:** DAX formula returning a table object. Use cases: duplicate a table for role-playing dimensions (e.g., `Ship Date = 'Date'`), create date tables (`CALENDARAUTO(6)` generates complete years spanning model data; `CALENDAR(start, end)` for explicit range), enable what-if analysis. Duplicate tables recalculated when source table refreshes; increase storage size; require custom column configuration after creation (rename, sort, hide).
- **Mark as Date Table:** Required for time intelligence functions. Validates: unique values, no nulls, contiguous dates, same timestamp across Date/Time values. You must either use a custom date table or the built-in auto date/time feature (limited, not customizable).
- **Calculated Columns:** DAX formula returning a scalar per row, evaluated in row context. Use `RELATED()` for lookups across relationships (faster than `LOOKUPVALUE` which performs table scan). Use `RELATEDTABLE()` for many-side values. Increase storage in Import mode (stores value per row). Prefer Power Query computed columns (better compression, loaded before DAX evaluation) or measures (no storage). Best when: formula depends on summarized model data, or requires DAX-specific functions (RELATED, parent-child hierarchy functions).
- **Row context:** Current row during calculated column evaluation. Only applies to the current table—use RELATED/RELATEDTABLE/LOOKUPVALUE for values from other tables.
- **Implicit Measures:** Automatic column summarization via Summarization property (Sum, Average, Count, DistinctCount, Min, Max, StdDev, Variance, Median for numerics; First/Last/Count for text; Earliest/Latest/Count for dates). Default summarization differs by data type: numeric numeric default = Sum, but rates (like Unit Price) default to Average. Report authors can override—risk of misleading aggregations. Implicit only works for single-column aggregation; complex logic requires explicit measures.
- **Explicit Measures:** DAX formulas evaluated at query time using filter context; do not store values. Simple measures aggregate one column (`SUM(Sales[Amount])`). Compound measures reference other measures (`[Revenue] - [Cost]`). Key difference from calculated columns: evaluated in filter context (not row context), no storage, more efficient for large models.
- **Quick Measures:** Built-in DAX generator for common patterns (division, YTD, etc.); generates DAX automatically.
- **Iterator Functions (X-functions):** `SUMX`, `AVERAGEX`, `COUNTX`, `MINX`, `MAXX`, `RANKX`. Require: a table (model table or table expression) + an expression returning a scalar per row. Evaluate expression row-by-row using row context, then aggregate. `SUM(Col)` is internally converted to `SUMX(Table, Col)`—same performance. Use `VALUES()` for different grain levels: `AVERAGEX(VALUES('Sales Order'[Sales Order]), [Revenue])` averages per order rather than per line item.
- **RANKX:** `RANKX(ALL('Product'[Product]), [Quantity], , , DENSE)`—ALL removes filters for ranking across all products; use DENSE to avoid gaps after ties. Use `HASONEVALUE` to avoid ranking totals: `IF(HASONEVALUE('Product'[Product]), RANKX(...))`.
- **Formatting:** Set formatting (decimals, data type, home table) immediately after creating a measure.
- **Storage comparison table:**
  - Calculated Columns: Evaluate at refresh via row context; store value per row (Import mode); increase model size; can filter/group. Best for new fields for slicing/relationships.
  - Measures: Evaluate at query time via filter context; no storage; efficient. Best for dynamic calculations based on filters.

**Architectural Logic**
DAX provides a layered calculation architecture: calculated tables add structural data (duplicate dimensions, date tables), calculated columns add row-level attributes (fiscal periods, derived values), and measures define dynamic aggregations. This separation keeps the model efficient—measures don't store data, while calculated columns/tables do. The key design principle: prefer measures over calculated columns whenever possible (smaller model, faster refresh). Use calculated columns only when the column is needed for relationships, filtering, or when the formula requires DAX-specific functions like RELATED.

**DAX / M Notes**
- `SUM(T[Col])` is shorthand for `SUMX(T, T[Col])` with identical performance.
- `RELATED()` leverages existing relationships (fast); `LOOKUPVALUE()` performs table scan (slow). Use RELATED whenever a relationship exists.
- `CALENDARAUTO(n)` where `n` = last month of fiscal year (e.g., 6 for June year-end). Scans all date columns to determine range. Generates complete years.
- `FORMAT(date, "yyyy mmm, dd")` for user-defined date formatting.
- Iterator performance scales with table row count. An iterator over 100 million rows is expensive.
- `COUNTROWS(FILTER(...))` is expensive. Prefer `CALCULATE(COUNTROWS(Table), Condition)`.

**Implementation Workflow**
1. **Calculated Tables:** DAX → returns table → configure relationships, rename columns, set sort order, hide intermediate columns.
2. **Calculated Columns:** DAX → evaluated row-by-row at refresh → stores result per row.
3. **Explicit Measures:** DAX → evaluated at query time using filter context → no storage → set formatting immediately.
4. **Quick Measures:** Use built-in generator for common patterns; review generated DAX.

**Exam Gotchas & Distinctions**
- **Calculated Columns vs. Measures:** Calculated columns store values (increase model size, evaluated at refresh). Measures are computed at query time (no storage). The most common DAX confusion on the exam.
- **RELATED vs. LOOKUPVALUE:** RELATED uses existing relationships (index-based, fast). LOOKUPVALUE scans the table (expensive). Always prefer RELATED.
- **SUM vs. SUMX:** Identical for single-column aggregation. `SUM(T[Col])` is syntactic sugar for `SUMX(T, T[Col])`.
- **Implicit vs. Explicit Measures:** Implicit measures are automatic but can be misused (e.g., summing unit prices). Explicit measures enforce correct business logic.
- **Row context vs. Filter context:** Calculated columns use row context (current row). Measures use filter context (current filters from visuals). Understanding this distinction is critical for the exam.
- **VALUES for grain control:** Use `VALUES(Table[Col])` to get unique values—essential for calculating averages at higher grain levels.
- **RANKX and ALL:** Without ALL, RANKX only ranks visible items (filter context). ALL removes filters for global ranking. Use HASONEVALUE to blank the total row.

## Semantic Models for Scale (Storage Modes)

**Core Concept**
Storage mode choice (Direct Lake, Import, DirectQuery, or Composite) determines query performance, data freshness, available Fabric features, and model size limits in a semantic model, with Direct Lake as the default for Fabric-native workloads.

**Technical Specifications**
- **Direct Lake (default for Fabric):** Reads Delta tables from OneLake into memory on demand. No scheduled refresh needed—reflects changes automatically when Delta tables update. Combines Import-level speed with DirectQuery-level freshness.
  - Connection paths: OneLake tables (directly to Delta tables in lakehouse/warehouse) or SQL analytics endpoint (enables views, cross-source joins, SQL RLS).
  - **Fallback behavior:** Complex DAX, memory limits, or unsupported operations trigger fallback to DirectQuery (queries run against SQL analytics endpoint). Configurable: Allow fallback (query succeeds but may be slower) or Disallow fallback (query returns error). Start with allowed, monitor, optimize to reduce frequency.
  - Automatically enables Large Semantic Model Storage Format (removes 10-GB limit) and is a prerequisite for query scaleout and XMLA endpoint read/write.
  - Aggregations: Often not needed—columnar engine handles large volumes efficiently. Add only when query patterns confirm need.
  - **OneLake Integration:** Direct Lake tables are already in OneLake; Import mode tables can be exported to OneLake as Delta tables (measures and calculation groups cannot be exported).
- **Import Mode:** Copies data into compressed in-memory format. Fastest query performance. Data freshness depends on refresh schedule. Best for non-Fabric sources, maximum query speed, or when features not yet in Direct Lake are needed. Connect to views, include only necessary columns, use appropriate data types to reduce model size. Enable Large Semantic Model Storage Format manually for models >10 GB.
- **DirectQuery Mode:** Sends queries to source at query time—no data stored. Suitable for real-time data, very large external datasets, or governance requirements that data stay at source. Performance depends on source speed and network latency.
- **Composite Mode:** Mixes storage modes per table in the same model. Enables many-to-many relationships across sources. Use for hybrid scenarios: Direct Lake fact tables + Import reference tables, or cross-source analysis.
- **Large Semantic Model Storage Format:** Removes 10-GB upload limit. Required for XMLA read/write and query scaleout. Automatically enabled for Direct Lake; must be enabled manually for Import/DirectQuery. Maximum size = Fabric capacity size or admin-set limit.
- **XMLA Endpoint:** Read-only by default; capacity admin can enable read/write. Connection string: `powerbi://api.powerbi.com/v1.0/[tenant]/[workspace]`. Enables external tools (Tabular Editor, DAX Studio, ALM Toolkit).
- **Query Scaleout:** Distributes read queries across read-only replicas. Brief delay between primary model refresh and replica synchronization. Requires Large Semantic Model Storage Format.
- **Storage mode decision table:**
  - Direct Lake: OneLake; Fast; Near real-time; Fabric-native workloads
  - Import: In-model cache; Fastest; Refresh-dependent; Non-Fabric sources, max performance
  - DirectQuery: Source system; Depends on source; Near real-time; Real-time, very large external data
  - Composite: Mixed; Varies; Mixed; Cross-source, hybrid

**Architectural Logic**
Direct Lake is the cornerstone of Fabric's scalable semantic model architecture. It avoids both the staleness of Import (requires refresh) and the latency of DirectQuery (depends on source query speed) by reading Delta files directly from OneLake. The tradeoff is fallback risk: certain DAX patterns or query complexity can trigger DirectQuery fallback, changing performance characteristics. The Large Model Format, XMLA endpoint, and Query Scaleout are interdependent—you typically enable them together for enterprise-scale models. Use Direct Lake as the default; move to other modes only when specific requirements (non-Fabric source, real-time, governance) demand it.

**Implementation Workflow**
1. **Choose storage mode:** Start Direct Lake for Fabric-native data. Use Import for non-Fabric sources needing max speed. Use DirectQuery for real-time external data.
2. **Configure large model format:** Enable manually for Import/DirectQuery models >10 GB; automatic for Direct Lake.
3. **Enable XMLA endpoint (if needed):** Set to read/write for external tool access.
4. **Enable Query Scaleout (if needed):** For high-concurrency workloads.
5. **Set Direct Lake fallback:** Default allowed; disallow only when all query patterns stay within Direct Lake limits.
6. **Configure OneLake Integration (if needed):** Export Import tables to Delta for downstream Fabric consumption.

**Exam Gotchas & Distinctions**
- **Direct Lake vs. DirectQuery:** Direct Lake reads columnar Parquet directly (fast, no refresh). DirectQuery translates to source SQL (depends on source). Both support fallback behavior.
- **Direct Lake fallback is configurable:** "Allowed" (slower but succeeds) vs. "Disallowed" (error). The exam expects you to know this setting exists and when to use each.
- **Large Model Format prerequisite:** Required for XMLA read/write AND Query Scaleout. Both depend on it. Direct Lake auto-enables it.
- **OneLake Integration only exports Import tables:** Direct Lake tables are already natively in OneLake. Measures, calculation groups, and DirectQuery tables cannot be exported.
- **Query Scaleout sync delay:** Brief delay between primary refresh and replica sync—important for exams discussing data freshness vs. concurrency.
- **Composite mode enables many-to-many across sources:** Only way to combine Direct Lake + Import tables with relationships.

## Semantic Model Star Schema Design

**Core Concept**
Star schema design in semantic models organizes fact tables (measures) and dimension tables (context) with single-direction one-to-many relationships for clean filter propagation, performant queries, and reliable AI consumption.

**Technical Specifications**
- **Relationship types:**
  - **One-to-many:** Standard star schema pattern; dimension (one side) filters fact table (many side). Use single-direction filtering from dimension to fact.
  - **Many-to-many:** Requires a bridge table that holds unique key combinations; bridge has one-to-many relationships to both sides.
  - **Cross-source:** Fact from lakehouse related to dimension from warehouse—uses composite model capabilities; each side resolved independently.
- **Filter direction:** Single-direction (dimension → fact) is the standard. Bi-directional filtering necessary for many-to-many or when dimension must be filtered by fact values; use sparingly—degrades performance and creates unexpected behavior.
- **Referential integrity:** Assume Referential Integrity setting tells engine to use INNER joins instead of LEFT OUTER joins—improves Direct Lake/DirectQuery performance. Enable only when confident every FK has a matching PK in dimension. Violations cause unmatched rows to silently disappear.
- **Inactive relationships + USERELATIONSHIP:** Only one active relationship between two tables. Activate inactive relationship in DAX: `CALCULATE(SUM(Sales[Amount]), USERELATIONSHIP(Sales[ShipDate], 'Date'[Date]))`.
- **Snowflake handling in semantic models:**
  - **Flatten into star:** Combine normalized dimension tables into single denormalized table via Power Query merges, SQL joins, or notebook transformations. Preferred for most scenarios—simpler filter paths, better AI consumption.
  - **Preserve snowflake:** Only when hierarchy has many levels creating dozens of redundant columns, multiple fact tables share subdimensions, or RLS must be applied at a specific hierarchy level. Each relationship must use single-direction filtering from outermost table toward fact.
- **Composite model cross-source scenarios:** Fact tables in lakehouse + dimensions in warehouse; real-time eventhouse + historical lakehouse; reference data from external (Import) + Fabric-native facts (Direct Lake). Configure storage mode per table independently.

**Architectural Logic**
A well-designed star schema gives both Power BI and AI tools (Copilot, data agents) clear filter paths from dimensions to facts. Single-direction filtering keeps behavior predictable and performant. The relationship design decision is the semantic model equivalent of foreign keys in a database—but with cardinality and cross-filter direction as additional dimensions. The key principle: dimension tables filter fact tables, not the other way around. Use active relationships for the primary analytical path; use USERELATIONSHIP for alternative paths (e.g., ship date vs. order date) without cluttering the model with duplicate dimensions.

**Implementation Workflow**
1. Design star schema: central fact table(s) with related dimension tables.
2. Configure relationships: one-to-many, single-direction from dimension to fact.
3. Set referential integrity: enable only when data quality guarantees FK-PK match.
4. For snowflake sources: flatten into star schema at data preparation stage (Power Query/SQL/notebooks).
5. For cross-source scenarios: use composite mode with per-table storage mode configuration.
6. For multiple date relationships: make one active, use USERELATIONSHIP in DAX for alternates.
7. For many-to-many: create bridge table with one-to-many to both sides.

**Exam Gotchas & Distinctions**
- **Referential Integrity setting:** INNER vs. LEFT OUTER join behavior. Violations cause silent data loss. The exam expects understanding of this tradeoff.
- **USERELATIONSHIP is a CALCULATE modifier:** Only works within CALCULATE or CALCULATETABLE. Cannot be used standalone in a measure.
- **Snowflake flattening is preferred:** Most exam scenarios should flatten snowflake into star schema. Preserve only when there's a specific reason (shared subdimensions, RLS at hierarchy level).
- **Bi-directional filtering is expensive:** Use only when necessary. Overuse causes ambiguous filter paths and performance degradation.
- **Cross-source relationship behavior:** Each side resolved independently—performance depends on both sources.

## Semantic Model Performance Optimization

**Core Concept**
Semantic model performance optimization follows a systematic diagnose-fix-verify workflow using Performance Analyzer to identify bottlenecks, then targets DAX optimization, cardinality reduction, aggregation implementation, and visual simplification.

**Technical Specifications**
- **Performance Analyzer:** Built into Power BI Desktop and service (edit mode > View > Performance Analyzer). Breaks visual load time into: DAX query, Visual display, Direct query, Other. Run after clearing visual cache. Export slow DAX queries via "Copy query" or "Run in DAX query view" (not available in web—copy and paste manually).
- **DAX Optimization Techniques:**
  - **Variables (VAR/RETURN):** Eliminate repeated expression evaluations. A PARALLELPERIOD reference evaluated twice = double the work. VAR evaluates once, reuses. Also improves readability and debugging (temporarily RETURN a variable to inspect intermediate values).
  - **FILTER vs. column predicate:** `CALCULATE([Sales], Sales[Amount] > 1000)` is faster than `CALCULATE([Sales], FILTER(Sales, Sales[Amount] > 1000))`. FILTER iterates every row; column predicate uses internal optimizations.
  - **KEEPFILTERS:** Preserves existing filter context instead of replacing it. Use when adding a filter condition without overriding slicer/visual filters.
  - **Iterator costs:** `SUMX`, `AVERAGEX`, etc. process every row. Performance scales linearly with row count. Use non-iterator equivalents (SUM, AVERAGE) when possible.
  - **Expensive patterns to avoid:** `COUNTROWS(FILTER(...))` on large tables (use CALCULATE+COUNTROWS instead); nested CALCULATE with complex filters (break into component measures); mixing aggregation grains (use VAR to evaluate totals once and reuse).
  - **Move calculations upstream:** Power Query computed columns compress better than DAX calculated columns. Source-level (SQL view) calculations use database engine optimization. DAX calculated columns evaluated after all Power Query tables finish loading—increases refresh time.
- **DAX Studio:** Free external tool connecting via XMLA. Server Timings separates Formula Engine (FE) vs. Storage Engine (SE) time. Query Plan shows logical/physical plans. Model metrics shows cardinality, compression stats.
- **Cardinality Reduction:**
  - Remove unused columns (vertical filtering).
  - Reduce time precision: datetime → date (millions of unique values → thousands).
  - Bucket continuous values (ages → age bands).
  - Remove unnecessary rows (horizontal filtering—load only needed history).
  - Optimize data types: numeric (value encoding—efficient) vs. text (hash encoding—less efficient). Remove text prefixes from codes.
  - Prefer Power Query computed columns over DAX calculated columns (better VertiPaq compression).
  - Tradeoff: granularity vs. performance—use composite model (Import for summary, DirectQuery for detail) when both needed.
- **Aggregations:**
  - **User-defined:** Manually create summary table at higher grain, map via Manage Aggregations (Sum, Count, Min, Max, GroupBy). Aggregation table uses Import; detail table uses DirectQuery. Requires composite model. Hide aggregation table from report authors.
  - **Automatic:** Machine learning based on query log (7 days of data). Power BI automatically creates/updates/removes aggregation tables. Requirements: Premium/Fabric capacity, DirectQuery mode for aggregated tables, supported sources (Azure SQL, Synapse, Databricks, Snowflake). Enable in model settings. Both user-defined and automatic can coexist.
  - **Monitor effectiveness:** Refresh history shows cache memory; Azure Log Analytics for hit rate analysis.
  - **Complementing Direct Lake:** Start without aggregations; add only when measurement shows need.
- **Best Practice Analyzer (BPA):** 60+ rules across Performance, DAX Expressions, Error Prevention, Maintenance, Formatting. Available via sample notebooks in Fabric service or Tabular Editor (external tool). Run after building/significantly changing a model.
- **Visual design best practices:** ≤8 visuals per page; reduce measures/data points per visual; use drillthrough/tooltips to distribute load.
- **DirectQuery troubleshooting:** Verify query folding; work with DBAs for source indexes; consider mixed storage modes for summary + detail.

**Architectural Logic**
Performance optimization follows a "measure, fix, verify" workflow because guessing at bottlenecks wastes effort. The VertiPaq engine compresses data column-by-column, so high-cardinality columns and complex filter patterns are the primary bottlenecks. DAX optimization (variables, avoiding FILTER on large tables) addresses calculation cost. Cardinality reduction reduces storage and scan cost. Aggregations trade detail for speed—precomputed summaries serve the 80% of common queries. The key architectural insight: Import model performance depends on model size (cardinality) and DAX efficiency; Direct Lake performance depends on Delta file structure and DAX complexity; DirectQuery depends on source speed and query folding.

**Implementation Workflow**
1. **Diagnose:** Open Performance Analyzer, clear cache, capture timings, identify slowest visual and bottleneck category.
2. **Isolate:** Copy DAX query → run in DAX query view or DAX Studio. Check FE vs. SE time, query plan.
3. **Fix DAX:** Use variables, replace FILTER with column predicates, avoid expensive iterators, break complex measures into components.
4. **Reduce cardinality:** Remove unused columns, reduce datetime precision, bucket, filter, optimize data types.
5. **Implement aggregations:** For large fact tables with common summary-level queries—user-defined or automatic.
6. **Verify:** Remeasure with Performance Analyzer to confirm improvement. Document baselines before/after.

**Exam Gotchas & Distinctions**
- **Performance Analyzer vs. DAX Studio:** PA identifies which visual is slow in a report; DAX Studio provides engine-level diagnostics (FE vs. SE time, query plan). Both are needed for complete diagnosis.
- **FILTER dimension tables, not fact tables:** In RLS and measures, filtering dimension tables propagates efficiently to fact tables via relationships. Filtering fact tables directly is more expensive.
- **Query folding for DirectQuery:** Verify transformations push back to source. Broken folding forces local processing—exam-important distinction.
- **Cardinality tradeoff documentation:** High cardinality is not always bad—business requirements may need it. The exam tests whether you know when and why to reduce it.
- **User-defined aggregations require composite model:** Aggregation = Import, detail = DirectQuery. Both tables need matching relationships to the same dimension tables.
- **Aggregations and Direct Lake:** Start without them; add only when measurement shows need. Direct Lake is already fast.
- **V-Order:** Write-time optimization for read-heavy workloads. Disabled by default in new workspaces. Enable at session level in Spark: `SET spark.sql.parquet.vorder.default=TRUE`.

## Semantic Model Security (RLS and OLS)

**Core Concept**
Row-level security (RLS) restricts which rows a user sees via DAX filter expressions on dimension tables; object-level security (OLS) hides entire tables or columns from specific roles, configured via external tools like Tabular Editor.

**Technical Specifications**
- **RLS implementation:**
  - **Static:** Hardcoded filter (`[Region] = "West"`). Simple but doesn't scale—each partition needs new role/rule; requires republish.
  - **Dynamic (recommended):** Uses `USERPRINCIPALNAME()` to match user identity against model data. Single role works for all users—adding/removing users is a data change, not a model change.
  - **Security table pattern:** Dedicated table mapping users to data partitions. Uses `CONTAINS(SecurityTable, SecurityTable[UserEmail], USERPRINCIPALNAME(), SecurityTable[Region], [Region])`. Centralized management, multi-value assignments, data-driven updates.
  - **Filter dimension tables (not fact tables):** Relationships propagate dimension filters to fact tables efficiently (fewer rows to evaluate).
  - **USERNAME() vs. USERPRINCIPALNAME():** `USERNAME()` returns `DOMAIN\username` in Desktop, `user@domain.com` in service. `USERPRINCIPALNAME()` returns `user@domain.com` consistently. Use USERPRINCIPALNAME() for consistency across environments.
  - **DirectQuery with SSO:** If source supports SSO, database can enforce its own RLS—no roles needed in semantic model.
  - **Role with FALSE():** Blocks access to all rows in a specific table—useful when users should see aggregated data but not detail-level records.
  - **No rules on a role = all data:** A role with no filter expressions provides full access to all rows.
  - **Multiple role membership:** Filters are additive (union). User sees data permitted by any role.
- **OLS implementation:**
  - **Cannot configure in Power BI Desktop natively—requires Tabular Editor** (external tool, connect via XMLA or local Desktop instance).
  - **Permission values:** `None` (object hidden—metadata and data invisible) or `Read` (visible—default).
  - **Measure restriction:** Measures can't be hidden directly, but a measure referencing a secured object is automatically restricted.
  - **Relationship dependency:** You cannot secure a table if it breaks a relationship chain (A→B→C: B cannot be secured, but individual columns in B can be).
  - **Feature limitations:** Models with OLS don't support Quick Insights, Smart Narrative visuals, or Excel Data Types gallery.
  - **Error experience:** Queries on secured objects display "field can't be found"—potentially confusing for consumers.
  - **Workspace role override:** OLS applies only to Viewers. Admin/Member/Contributor bypass OLS.
  - **OLS applied to Copilot/data agents:** Secured columns aren't accessible through natural language queries.
- **Testing roles:**
  - **Desktop:** Modeling > View as → select role; for dynamic RLS, enter test email in "Other user" field. Stop viewing to return.
  - **Service:** Semantic model > More options > Security > Test as role.
  - Verify: permitted data visible, restricted data hidden, aggregations reflect filtered data, OLS objects show appropriate errors. Test with multiple emails including edge cases (user not in security table).
- **Role membership:** Assign in Power BI service (semantic model > Security). Supported: individual users, Microsoft Entra security groups, distribution groups, service principals. NOT supported: Microsoft 365 groups. Prefer security groups over individual users (delegated management, consistent access).
- **Workspace role interaction with RLS:** Viewers are subject to RLS. Admin/Member/Contributor bypass RLS—they see all data. Workspace role assignment critical: don't grant edit-level roles to users needing data-level security.

**Architectural Logic**
RLS and OLS serve different security dimensions. RLS filters rows (who sees which records), OLS restricts table/column visibility (who sees which schema elements). Both apply to all consumption paths—Power BI reports, paginated reports, Copilot chat, Fabric data agents. The layered approach (workspace roles → item permissions → T-SQL/RLS/OLS → OneLake security) follows least privilege: start broad, narrow to specific tables/rows/columns. Dynamic RLS with USERPRINCIPALNAME() is the recommended pattern because it decouples security from model maintenance—user access is a data change, not a model redeployment.

**Implementation Workflow**
1. **Create roles:** In Power BI Desktop > Modeling > Manage roles.
2. **Define RLS filters:** Use DAX on dimension tables; `USERPRINCIPALNAME()` for dynamic security.
3. **Optional security table:** Create table mapping users to partitions; use CONTAINS in RLS filter.
4. **Configure OLS (optional):** Use Tabular Editor → Role → Table Permissions → set `None` for tables/columns to hide.
5. **Test:** View as (Desktop), Test as role (service); test multiple user identities.
6. **Assign members:** In Power BI service > Security; use security groups for scalable management.

**Exam Gotchas & Distinctions**
- **RLS vs. OLS:** RLS filters rows; OLS hides entire tables or columns. RLS uses DAX in Power BI Desktop; OLS requires Tabular Editor.
- **USERNAME() vs. USERPRINCIPALNAME():** USERNAME() returns different formats in Desktop vs. service. USERPRINCIPALNAME() is consistent—always use it.
- **Workspace role bypass:** Admin/Member/Contributor see ALL data regardless of RLS/OLS. Only Viewers are restricted. Critical exam point.
- **Multiple role membership:** Filters are additive (union). A user in two roles sees data from both.
- **Security group support:** Microsoft Entra groups supported; Microsoft 365 groups NOT supported for role membership.
- **OLS and break relationship chain:** Securing a table that is an intermediate in a relationship chain is not allowed. You must keep it accessible but can hide individual columns.
- **Role with no rules = full access:** Common mistake—creating a role but forgetting to add filter rules means the role sees all data.

## Semantic Model Development Lifecycle

**Core Concept**
Managing the semantic model lifecycle in Fabric involves four stages—Develop (reusable assets, version control), Validate (XMLA/SemPy), Deploy (deployment pipelines), Monitor (refresh, monitoring), following a defined process from authoring to production operations.

**Technical Specifications**
- **Reusable Assets:**
  - **Shared semantic model:** Centralized business metrics, relationships, calculations; reports connect via DirectQuery to the semantic model. Single source of truth—update once, every connected report reflects change. Endorsed shared models are preferred data sources for AI agents.
  - **Power BI template (.pbit):** Captures complete report structure (pages, visuals, queries, parameters) without data. Prompts for parameter values and credentials on open. Supports parameter types: Text (server/database names), Boolean (conditional logic), Date (default ranges). Small file size, easy distribution.
  - **Data source file (.pbids):** Preserves only connection info; opens Desktop with connection preconfigured.
- **Version Control:**
  - **Power BI Project (.pbip):** Saves report + model as plain text files (TMDL for semantic model, .pbir JSON for report). Diff-friendly, mergeable. `/.gitignore` auto-generated to exclude cache/settings. Enable: File > Options > Preview features > Power BI Project (.pbip). In preview.
  - **Fabric Git Integration:** Bidirectional sync between workspace and Azure DevOps/GitHub repository. Supports many item types (notebooks, pipelines, lakehouses, warehouses). Workflow: commit changes → sync; update workspace from repo; branch switching for dev/testing; conflict resolution when same item changed in both.
  - **Combined workflow:** Local .pbip development → commit to Git → code review via pull requests → workspace sync.
- **XMLA Endpoint & SemPy:**
  - **Connection string:** `powerbi://api.powerbi.com/v1.0/[tenant]/[workspace]`
  - **SemPy (sempy.fabric):** Python library included in Fabric Runtime 1.2+. Functions: `list_tables()`, `list_columns()`, `list_measures()`, `list_relationships()`, `list_relationship_violations()`, `evaluate_measure()`, `evaluate_dax()`, `read_table()`. Used in Fabric notebooks.
  - **Validation:** Relationship violations (orphan keys), measure testing (compare against known values), data quality (null checks, duplicate keys), BPA (60+ rules).
  - **External tools:** DAX Studio (interactive queries, server timings), Tabular Editor (visual model editing, BPA), ALM Toolkit (schema compare).
  - **Read-only vs. read-write:** XMLA default is read-only. Capacity admin can enable read-write for model deployment, scripted operations, external tool modifications.
  - **Prerequisite:** Large semantic model storage format required for XMLA read/write.
- **Deployment Pipelines:**
  - **Default stages:** Development → Test → Production. Customizable (2-10 stages).
  - **Workspace assignment:** Each stage maps to a separate workspace (must be Fabric/Premium capacity).
  - **Deployment rules:** Data source rules (server, database, connection path) and parameter rules (override values per stage). Configure before first deployment. Rules only apply during pipeline deployment—don't change source item.
  - **Comparison view:** Orange = differs; green = identical; "new" indicator = exists only in source stage. Selective deployment (some items can stay in development while others promoted).
  - **Automation via REST API:** CI/CD integration, scheduled deployments, pre-deployment validation scripts.
  - **Git vs. Pipelines:** Git = version control/collaboration (what changed, who approved). Pipelines = stage promotion (is the right content in the right environment with correct configuration).
- **Monitor:**
  - **Scheduled refresh:** Configure frequency (daily/weekly), times, failure notifications. On-premises requires data gateway. Schedule during off-peak hours.
  - **Pipeline-based refresh:** Data Factory pipeline with semantic model refresh activity. Enables sequential dependencies (lakehouse refresh → transform → model refresh → notification). Conditional logic to skip on upstream failure.
  - **Monitoring Hub:** Status of all running/recent activities. Verify scheduled refreshes, investigate failures, identify performance trends.
  - **Refresh history:** Shows status, duration, type (scheduled/on-demand/pipeline) per model.
  - **Lineage view:** Visual map of data flow from sources through models to reports. Use for troubleshooting data freshness issues.

**Architectural Logic**
The lifecycle follows a Develop → Validate → Deploy → Monitor workflow that addresses common problems at scale. Reusable assets (shared models, templates, .pbids) establish consistency. .pbip projects with TMDL text files make semantic model changes reviewable through Git (diff-friendly, mergeable). SemPy provides programmatic validation (relationship violations, measure testing, data quality) that can be automated in notebooks—run before every deployment. Deployment pipelines with environment-specific rules handle configuration differences between dev/test/prod. The key architectural insight: XMLA is the unification layer—SemPy in notebooks, DAX Studio, Tabular Editor, and ALM Toolkit all connect through the same XMLA endpoint.

**Implementation Workflow**
1. **Develop:** Create shared semantic models, .pbit templates, .pbids files. Save as .pbip project. Use Git integration for version control.
2. **Validate:** Use SemPy (notebook) or BPA to check relationships, measures, data quality. Use DAX Studio for interactive query testing.
3. **Deploy:** Create deployment pipeline (Dev→Test→Prod). Configure deployment rules (data source, parameters). Promote selectively. Optionally automate via REST API.
4. **Monitor:** Set up scheduled refresh (or pipeline-based). Monitor via Monitoring Hub and refresh history. Use lineage view for troubleshooting.

**Exam Gotchas & Distinctions**
- **.pbip vs. .pbix:** .pbip stores as TMDL text files (diff-friendly, mergeable, supports batch editing via scripts). .pbix is binary—no diff, no merge.
- **Git Integration vs. Deployment Pipelines:** Git is for version control/collaboration (tracking changes, branching, PRs). Deployment Pipelines are for environment promotion (moving content from dev to test to prod with config rules). They complement each other.
- **SemPy vs. External Tools:** SemPy provides automated/scriptable validation in notebooks (repeatable, can be run in CI/CD). Tabular Editor/DAX Studio provide interactive real-time analysis.
- **TMDL files:** Each table, measure, relationship = separate readable text file. This enables scripted batch updates and meaningful code reviews.
- **Deployment rules configure BEFORE first deploy:** Rules only apply during pipeline deployment; updating after initial setup requires redeploy.
- **XMLA endpoint must be enabled:** If disabled, SemPy and external tools cannot connect. Verify in capacity admin portal.
- **TMDL language:** Tabular Model Definition Language—the text-based format used in .pbip projects. Not the same as TMSL (Tabular Model Scripting Language).
