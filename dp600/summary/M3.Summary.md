## Card 1: DAX Calculations & Model Components

### What It Is
Semantic models are enhanced through three types of DAX (Data Analysis Expressions) calculations: **Calculated Tables**, **Calculated Columns**, and **Measures**. These allow for the creation of sophisticated logic, from adding new dimensions to performing complex, dynamic aggregations.

### Calculation Types
- **Calculated Tables:** These are created with DAX formulas that return a table object. They are useful for duplicating existing tables to handle multiple relationships (e.g., creating a "Ship Date" table from a "Date" table) or for generating specialized tables like date tables using `CALENDARAUTO`.
- **Calculated Columns:** These add a new column to an existing table, with the formula evaluated in **row context** during data refresh. While useful for adding attributes like "Fiscal Year," they increase model size and should be used sparingly in favor of Power Query or measures.
- **Measures:** These are dynamic aggregations evaluated in **filter context** at query time. Measures do not store values in the model, making them highly efficient for large datasets. They are the primary tool for business metrics like "Total Revenue" or "Profit Margin."
- **Iterator Functions:** Functions like `SUMX`, `AVERAGEX`, and `RANKX` evaluate an expression row-by-row over a specified table. They are essential for complex calculations that require row-level logic before aggregation.

### Key Concepts
- **Row Context vs. Filter Context:** Calculated columns operate in row context (the current row), while measures operate in filter context (the set of rows currently filtered by slicers or visuals).
- **Relationship Handling:** In complex models, measures can use the `USERELATIONSHIP` function to activate inactive relationships, allowing a single dimension (like Date) to support multiple roles (like Order Date and Ship Date).

### Exam Gotchas
- **Measure Efficiency:** Measures are more efficient than calculated columns because they do not consume storage and are computed only when needed.
- **Iterators:** Use iterators when you need to perform a calculation on each row (e.g., `Quantity * UnitPrice`) before aggregating the result.
- **Calculated Tables:** These are useful for creating role-playing dimensions to solve multiple relationship challenges.

## Card 2: Designing for Scale & Storage Modes

### What It Is
Designing for scale involves making strategic decisions about how data flows into the model and how it is structured to support growing volumes of data and increasing numbers of concurrent users.

### Storage Modes
The choice of storage mode directly impacts query performance, data freshness, and feature availability:
- **Direct Lake (Default):** The premier mode for Fabric. It reads Delta tables directly from OneLake into memory, combining the extreme speed of Import mode with the near real-time freshness of DirectQuery. It automatically enables the Large Semantic Model storage format.
- **Import Mode:** Copies data into an in-memory cache. This is the fastest mode for query performance but is limited by the need for scheduled refreshes and the 10GB upload limit (unless the Large Model format is enabled).
- **DirectQuery:** Sends queries directly to the source at query time. It is best for real-time requirements or massive datasets that cannot be imported, but it can suffer from higher latency due to query round-trips.
- **Composite Mode:** Combines multiple modes within a single model (e.g., Import for dimensions and Direct Lake for facts) to balance performance and freshness.

### Star Schema & Relationships
A well-designed star schema is fundamental to performance. Relationships should connect dimension tables to fact tables using a one-to-many pattern, with filters flowing from the dimension to the fact. For complex models, designers must manage inactive relationships using `USERELATIONSHIP` and handle many-to-many scenarios using bridge tables.

### Scaling Settings
To support large-scale environments, several advanced settings can be configured:
- **Large Semantic Model Storage Format:** Removes the 10GB limit and is required for XMLA access and Query Scaleout.
- **XMLA Endpoint:** Enables connection via external tools like Tabular Editor and DAX Studio.
- **Query Scaleout:** Distributes read queries across read-only replicas to handle high concurrency.
- **Direct Lake Fallback:** Determines whether queries that cannot run in Direct Lake mode should automatically fall back to DirectQuery or return an error.

### Exam Gotchas
- **Direct Lake is the default:** In Fabric, start with Direct Lake and only move to other modes if specific requirements (like non-Fabric sources) necessitate it.
- **Relationship direction:** Standard star schemas use single-direction filtering from dimension to fact to ensure predictable performance.
- **Fallback behavior:** In production, you may choose to "Disallow Fallback" to enforce consistent performance, even if it means some queries return errors.
- **OneLake Integration:** Enabling this allows downstream Fabric items (like notebooks) to consume the semantic model data directly as Delta tables.

## Card 3: Performance Optimization

### What It Is
Optimization involves diagnosing bottlenecks and applying targeted fixes to ensure reports and AI-powered experiences (Copilot, Agents) remain responsive.

### Diagnostic Tools
- **Performance Analyzer:** A built-in tool used to measure how long each visual takes to load. It breaks down timing into categories: **DAX query**, **Visual display**, **DirectQuery**, and **Other**.
- **DAX Studio:** A powerful external tool that provides engine-level diagnostics, such as **Server Timings** (separating formula and storage engine time) and **Query Plans**.
- **Best Practice Analyzer (BPA):** A tool (available in Fabric via notebooks or in Tabular Editor) that scans the model against dozens of rules to catch structural and performance issues.

### Optimization Strategies
- **DAX Tuning:** Improve performance by using **Variables (VAR)** to avoid repeated evaluations, replacing expensive `FILTER(Table, ...)` with simple column predicates, and avoiding unnecessary nested `CALCULATE` calls.
- **Reducing Cardinality:** Lowering the number of unique values in a column (e.g., truncating a timestamp to a date) significantly improves VertiPaq compression and query speed.
- **Aggregations:** Implement summary tables (Aggregations) to store precomputed totals. The engine can then automatically route common queries to these fast, in-memory tables instead of scanning massive detail tables.

### Troubleshooting Workflow
A systematic approach is required:
1. **Identify:** Use Performance Analyzer to find the slowest visuals and identify the bottleneck category (e.g., high DAX time).
2. **Isolate:** Copy the problematic DAX query and run it in DAX Query View or DAX Studio to verify if the issue is in the query itself.
3. **Fix & Verify:** Apply optimizations (e.g., reducing cardinality or adding an aggregation) and re-measure to confirm improvement.

### Exam Gotchas
- **The "Small File" Problem:** In Direct Lake, a large number of small files can degrade performance; use `OPTIMIZE` in Spark to compact them.
- **Cardinality is Key:** High-cardinality columns (like GUIDs or high-precision timestamps) are major contributors to slow models and high memory usage.
- **Aggregations are Transparent:** When correctly configured, the engine automatically uses aggregations, so users don's need to know they exist.
- **Variables save time:** Using `VAR` in DAX can often cut execution time in half by preventing the engine from recalculating the same expression multiple times.

## Card 4: Semantic Model Security

### What It Is
Semantic model security controls which data users can see when they query a model. Implementing security ensures that data visibility is restricted to only authorized users, protecting sensitive information across all consumption paths.

### Row-Level Security (RLS)
RLS restricts *which rows* are visible based on DAX filter expressions.
- **Static RLS:** Uses hardcoded filter expressions (e.g., `[Region] = "Midwest"`). This is simple but does not scale as the number of partitions grows.
- **Dynamic RLS:** Uses the `USERPRINCIPALNAME()` function to evaluate the signed-in user's identity against a column in the model. This is the recommended approach for scalable, automated security.
- **Security Table Pattern:** For complex scenarios, a dedicated security table can map users to various data partitions (e.g., regions or departments), enabling centralized and data-driven management.
- **Implementation Best Practice:** Apply RLS to dimension tables rather than fact tables, as model relationships efficiently propagate these filters to related fact data.

### Object-Level Security (OLS)
OLS restricts access to *specific tables or columns*. When an object is secured with OLS, it and its metadata are completely hidden from unauthorized users.
- **Configuration:** OLS cannot be configured natively in Power BI Desktop and must be implemented using external tools like **Tabular Editor**.
- **Use Cases:** Protecting personally identifiable information (PII), sensitive financial data, or internal development tables.
- **Limitations:** OLS applies only to users with **Viewer** permissions; users with Admin, Member, or Contributor roles bypass OLS.

### Testing and Management
- **Testing:** Use the **View as** feature in Power BI Desktop or the Power BI service to preview reports as if assigned to specific roles.
- **Role Membership:** Manage role assignments in the Power BI service. It is highly recommended to map roles to **Microsoft Entra security groups** rather than individual users for scalable and delegated management.
- **AI Security:** Properly configured RLS and OLS ensure that Copilot and Fabric data agents only access and surface authorized data.

### Exam Gotchas
- **RLS is Additive:** If a user is assigned to multiple roles, they see the **union** of all rows permitted by those roles.
- **Workspace Roles vs. RLS:** Workspace roles (Admin, Member, Contributor) bypass RLS entirely. Only users with Viewer permissions are subject to RLS.
- **OLS and Metadata:** When an object is secured with OLS, it is completely invisible to unauthorized users, including its metadata.
- **Relationship Integrity:** When implementing RLS, ensure that relationship chains are not broken, as this can cause unintended data visibility.

## Card 5: Development Lifecycle Management

### What It Is
Lifecycle management (LCM) provides a structured process—**Develop $\rightarrow$ Validate $\rightarrow$ Deploy $\rightarrow$ Monitor**—to manage semantic models from creation to production.

### Develop
- **Reusable Assets:** Use Shared Semantic Models (one model, many reports) and Power BI Templates (`.pbit`) to ensure consistency.
- **Version Control:** Use Power BI Desktop Projects (`.pbip`) to save models as readable text (TMDL) for Git integration. This allows for effective collaboration and code reviews.

### Validate
- **Programmatic Validation:** Use the XMLA endpoint and **SemPy** in Fabric notebooks to automate the inspection of model metadata, validation of relationships, and testing of DAX calculations.
- **External Tools:** Leverage tools like **Tabular Editor** (for Best Practice Analyzer) and **DAX Studio** to conduct deep structural and performance audits before deployment.

### Deploy
- **Deployment Pipelines:** Promote content through defined stages (e.g., Dev $\rightarrow$ Test $\rightarrow$ Prod) using Fabric deployment pipelines.
- **Deployment Rules:** Use rules to automatically adjust configurations during promotion, such as updating data source connections or overriding parameter values for different environments.

### Monitor
- **Scheduled Refresh:** Ensure data freshness by configuring refresh schedules and setting up failure notifications.
- **Monitoring Hub:** Use the Fabric Monitoring Hub to track workspace activity, refresh history, and identify potential performance trends.

### Exam Gotchas
- **Git vs. Pipelines:** Git is for tracking *what* changed and facilitating collaboration, while Deployment Pipelines are for managing *where* content is deployed across environments.
- **SemPy Advantage:** SemPy allows for automated, repeatable validation in notebooks, which is more scalable than manual checks.
- **Deployment Rules Timing:** Always configure deployment rules *before* the first deployment to ensure environments are correctly configured upon promotion.
