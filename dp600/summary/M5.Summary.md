# M5.Summary.md

## Fabric Security Model

**Core Concept**
Microsoft Fabric's layered security model evaluates access sequentially across Microsoft Entra ID, Fabric access, and data security — the data security layer has four controls (workspace roles, item permissions, compute permissions, OneLake security) that narrow from workspace-wide to per-table/folder, implementing the principle of least privilege.

**Technical Specifications**
- **Three levels of access evaluation (sequential):**
  1. Microsoft Entra ID authentication — checks if the user can authenticate
  2. Fabric access — checks if the user can access Fabric
  3. Data security — checks if the user can perform the requested action on a table or file
- **Four primary access controls at the data security level (from broadest to narrowest):**
  1. **Workspace roles** — apply to all items in a workspace
  2. **Item permissions** — apply to a single item (shared individually)
  3. **Compute/granular permissions** — T-SQL DCL (GRANT, DENY, REVOKE) within a specific engine
  4. **OneLake security** — RBAC within an item (specific tables/folders)
- **Workspace roles (4):**
  - **Admin:** Create, view, modify, share, manage all content and data; manage permissions
  - **Member:** Create, view, modify, share all content and data (no permission management)
  - **Contributor:** Create, view, modify all content and data (no share or permission management)
  - **Viewer:** View all content in the workspace but CANNOT modify it. See items listed but have NO access to underlying OneLake data by default.
  - Workspace roles can be assigned to individuals, security groups, Microsoft 365 groups, and distribution lists.
- **Item permissions (lakehouse sharing example):**
  - Read permission is always granted when sharing — lets recipient see item's metadata and associated reports, but NO data access to SQL or OneLake
  - Additional permissions:

| Permission | What it allows |
|---|---|
| Read all SQL endpoint data | Read data from SQL analytics endpoint using T-SQL |
| Read all Apache Spark and subscribe to events | Read lakehouse data through Apache Spark and OneLake APIs. Also adds recipient to DefaultReader OneLake security role |
| Build reports on the default semantic model | Create Power BI reports on the default semantic model |

  - Both data-access permissions above grant access to ALL data in the lakehouse by default — use OneLake security roles to restrict further
- **Compute/granular permissions (T-SQL DCL):**
  - `GRANT` — gives permission
  - `DENY` — denies permission; always supersedes GRANT
  - `REVOKE` — removes a previously granted/denied permission
  - Supported for: `SELECT`, `INSERT`, `UPDATE`, `DELETE` on tables, views, functions, stored procedures
  - Also supports RLS (row-level security), CLS (column-level security), and Dynamic Data Masking
- **OneLake security roles (RBAC within a lakehouse item):**
  - Four components:
    - **Data** — which tables or folders the role grants access to
    - **Permission** — Read (view data) or ReadWrite (view and edit data without a workspace write role)
    - **Members** — users or groups assigned to the role
    - **Constraints** — optional row or column filters applied to data in the role
  - Enforced consistently across ALL Fabric compute engines: Spark, SQL, OneLake APIs
  - Only workspace Admin and Member roles can create or modify OneLake security roles
  - Admin/Member/Contributor workspace roles **bypass** OneLake security roles — they already have full read/write access to all OneLake data. OneLake security only restricts Viewers and Read-permission users.
  - **DefaultReader role:** Every lakehouse has an auto-created DefaultReader role. Users granted "Read all Apache Spark" item permission are automatically added to it. When restricting a user to a custom role, also remove them from DefaultReader — otherwise they retain full read access through the default role.
- **Configuration:**
  - Workspace role: Workspace > Manage access > enter user > select role > Add
  - Item permissions: Item ellipsis (...) > Manage permissions > share with user > select permissions
  - OneLake security: Lakehouse lake view > Manage OneLake security from ribbon > New role > name, permission type, select tables/folders > save > edit to add members and constraints

**Architectural Logic**
The layered model follows the principle of least privilege by starting broad (workspace role for collaboration) and narrowing as needed (item permissions for specific items, compute permissions for engine-specific control, OneLake security for within-item table/folder access). Each layer is independently configurable but works additively — access is the intersection of what the workspace role, item permissions, compute permissions, and OneLake security give. Because Admin/Member/Contributor bypass OneLake security, use workspace roles for broad collaboration and OneLake security specifically for restricting Viewers and Read-permission users who should only see subsets of data. Use item permissions over workspace roles when a user only needs access to one or two items, not the entire workspace.

**Implementation Workflow**
1. **Assign workspace role** for broad collaboration (Admin/Member/Contributor/Viewer).
2. **Refine with item permissions** — share individual items with Read + additional data permissions when a user needs limited access.
3. **Apply granular permissions** — T-SQL DCL (GRANT/DENY/REVOKE) for SQL endpoint access; OneLake security roles for Spark/API access to restrict to specific tables/folders. Remove users from DefaultReader when adding to custom restricted roles.
4. **Validate** — users with only Viewer role see items but cannot access data until OneLake security roles grant table/folder access.

**Exam Gotchas & Distinctions**
- **Viewer role and OneLake data:** Viewers see items listed but have NO underlying OneLake data access by default. Use OneLake security roles to grant data access to viewers.
- **DefaultReader:** Automatically created in every lakehouse. Adding Read all Apache Spark permission auto-adds recipient to DefaultReader. ALWAYS remove from DefaultReader before adding to a custom restricted role — otherwise the user retains full read access through DefaultReader.
- **Admin/Member/Contributor bypass OneLake security:** OneLake security roles only restrict Viewers and Read-permission users. If a workspace Admin needs restricted access, they cannot be restricted via OneLake security — must remove from Admin role.
- **Read permission alone does not grant data access:** Read item permission only shows metadata. Users need Read all SQL endpoint data OR Read all Apache Spark to access actual data.
- **OneLake security is cross-engine:** Enforced consistently across Spark, SQL, and OneLake APIs — not engine-specific like T-SQL permissions.
- **DENY supersedes GRANT:** If a user is in a role with GRANT and another with DENY on the same permission, DENY wins.

## Data Warehouse Security

**Core Concept**
Fabric data warehouse provides four T-SQL-based data protection features — Dynamic Data Masking (masks at query time), Row-Level Security (filters rows via security predicates), Column-Level Security (hides columns via GRANT/DENY), and SQL granular permissions (SELECT/INSERT/UPDATE/DELETE) — all enforced at the SQL engine level.

**Technical Specifications**
- **Dynamic Data Masking (DDM):** Masks column values in query results without altering stored data.

| Masking Function | Syntax | Behavior | Limitations |
|---|---|---|---|
| Default | `default()` | Full mask based on data type | Completely hides data |
| Email | `email()` | Exposes first letter + constant `".com"` suffix | Only applicable to email fields |
| Custom Text | `partial(prefix_padding, padding_string, suffix_padding)` | Exposes first N and last N characters with custom padding in middle | Not suitable for numeric, date, time data types |
| Random | `random(low, high)` | Replaces numeric/binary value with random number in range | Only applicable to numeric and binary data types |

  - Applied at column level using `ALTER TABLE ... ALTER COLUMN ADD MASKED WITH (FUNCTION = '...')`
  - Example: `ALTER TABLE Customers ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()')`
  - Unprivileged users with query permissions CAN infer actual data (DDM does not physically obfuscate stored data)
  - DDM should be part of a comprehensive strategy including proper object-level security and minimal required permissions
  - The data in the database is not changed — masking rules apply to query results only
- **Row-Level Security (RLS):** Filters rows at query time based on group membership or execution context.
  - Two-step implementation:
    1. Create an inline table-valued function (security predicate) that returns a table with one column; the predicate evaluates `WHERE @column = USER_NAME()` or similar condition
    2. Create a security policy that applies the predicate to a target table using `ADD FILTER PREDICATE`
  - Predicate function created with `WITH SCHEMABINDING`
  - Security policy syntax: `CREATE SECURITY POLICY [schema].[name] ADD FILTER PREDICATE [schema].[function]([column]) ON [schema].[table] WITH (STATE = ON)`
  - Disable with `ALTER SECURITY POLICY ... WITH (STATE = OFF)`
  - DML impact:
    - SELECT: Cannot view filtered rows
    - UPDATE: Cannot update filtered rows
    - DELETE: Cannot delete filtered rows
    - INSERT: Not applicable
  - **Side-channel attack risk:** Attackers can infer data through crafted WHERE clauses (e.g., divide-by-zero errors that reveal whether a condition is true)
  - Best practices: create separate schema for predicate functions/policies, avoid type conversions in predicates, avoid excessive table joins and recursion in predicates
- **Column-Level Security (CLS):** Restricts column access at query time.
  - Implementation pattern:
    1. `GRANT SELECT ON [table] TO [role]` (grants access to all columns)
    2. `DENY SELECT ON [table]([column]) TO [role]` (denies specific column)
  - Example: `DENY SELECT ON dbo.Patients (MedicalHistory) TO Receptionist`
  - CLS vs. Views comparison:
    - CLS: More granular (per-column per-role), automatically adapts to table structure changes, more efficient, transparent to users (query same table)
    - Views: Less granular (must create separate views for different permissions), need updates when table structure changes, can introduce performance overhead, users query different object, can provide row-level security AND transform data
- **SQL granular permissions (DCL):**
  - Fundamental DML permissions: `SELECT`, `INSERT`, `UPDATE`, `DELETE`
  - Object permissions (for functions and stored procedures): `ALTER`, `CONTROL`
  - Applied via `GRANT`, `DENY`, `REVOKE`
  - `DENY` always supersedes `GRANT` when a user has both
  - Dynamic SQL: T-SQL statements built programmatically using `sp_executesql`; always use `QUOTENAME()` to prevent SQL injection

**Architectural Logic**
All four features (DDM, RLS, CLS, granular permissions) are enforced at the SQL engine level and operate transparently — queries return masked/filtered/hidden data without application changes. This makes them suitable for securing existing applications that cannot be rewritten. Use DDM when the requirement is to obscure but still indicate the type of data (e.g., showing an email format without revealing the full address). Use RLS when different users should see different rows based on identity (e.g., tenant isolation, departmental data access). Use CLS when specific columns are too sensitive for certain roles (e.g., MedicalHistory for receptionists). Use views over CLS when you also need row-level filtering and data transformation in the same object. Use Dynamic SQL when you need to parameterize object names in queries — but always parameterize inputs to prevent SQL injection.

**Implementation Workflow**
1. **DDM:** `ALTER TABLE [table] ALTER COLUMN [column] ADD MASKED WITH (FUNCTION = '[function]')`
2. **RLS:** a. Create filter predicate function: `CREATE FUNCTION [schema].[name](@param AS type) RETURNS TABLE WITH SCHEMABINDING AS RETURN SELECT 1 AS result WHERE @param = USER_NAME()` b. Create security policy: `CREATE SECURITY POLICY [schema].[name] ADD FILTER PREDICATE [schema].[function]([column]) ON [schema].[table]`
3. **CLS:** `GRANT SELECT ON [table] TO [role]` → `DENY SELECT ON [table]([column]) TO [role]`
4. **Granular permissions:** `GRANT/DENY/REVOKE [SELECT|INSERT|UPDATE|DELETE|ALTER|CONTROL] ON [object] TO [user/role]`
5. **Dynamic SQL:** Use `sp_executesql` with `QUOTENAME()` for safe object name parameterization

**Exam Gotchas & Distinctions**
- **DDM does not change stored data:** It only masks query results. Users with query permissions can infer actual data through inference attacks.
- **RLS side-channel attacks:** Risk of information leakage through crafted WHERE clauses that cause exceptions. The exam expects awareness of this vulnerability.
- **DENY supersedes GRANT:** If a user inherits GRANT through one role and DENY through another, DENY wins. This is a fundamental T-SQL security rule.
- **CLS vs. Views:** CLS is transparent (users query the same table), more granular, more efficient, and auto-adapts to table changes. Views are more flexible (can combine row filtering, column filtering, and data transformation in one object). The exam tests this distinction.
- **SECURITY POLICY with STATE = ON/OFF:** Policy must be ON for RLS to be active. Altering to OFF disables RLS — all users see all rows.
- **Schema binding in predicates:** RLS predicate functions must be created WITH SCHEMABINDING.
- **INSERT not affected by filter predicates:** Filter predicates do not apply to INSERT operations — only SELECT, UPDATE, DELETE.

## Microsoft Purview (Fabric Governance)

**Core Concept**
Microsoft Purview provides advanced cross-platform data governance — Data Map (scan/catalog metadata), Unified Catalog (searchable asset inventory), Information Protection (sensitivity labels and IRM), Data Loss Prevention (policies blocking/alerting on sensitive data movement), and Audit (activity logging) — extending beyond Fabric's built-in governance capabilities through a registered connection between the Fabric tenant and Microsoft Purview.

**Technical Specifications**
- **Built-in Fabric governance capabilities (no Purview license required):**
  - **Admin Portal:** Tenant settings, capacities, domains
  - **Domains:** Group data by business area (Sales, Finance, Operations)
  - **Workspaces:** Group items by team or department
  - **Capacities:** Limit compute resource usage for all Fabric workloads
  - **Metadata scanning:** Extract names, identities, sensitivities, endorsements from data lakes for governance analysis
  - **Data tags:** Sensitivity labels and data retention tags
  - **Workspace roles:** Define authorized users
  - **Data-level controls:** Granular restrictions at table, row, column level
  - **Certifications:** Fabric is compliant with HIPAA BAA, ISO/IEC 27017, ISO/IEC 27018, ISO/IEC 27001, ISO/IEC 27701
  - **OneLake data hub:** Data discovery
  - **Endorsement:** Promoted, Certified, Master data
  - **Data lineage:** Visual understanding of data flow between items
  - **Monitoring Hub:** Centralized view of Fabric activities (users see only items they have permission to; shows activity, not detailed query content)
  - **Capacity Metrics App:** Insights into Fabric usage and resource consumption
- **Purview pillars:** Data Governance, Data Security, Risk and Compliance
- **Purview tools (require Purview license + Fabric tenant registration):**
  - **Data Map:** Scans all data assets across hybrid/on-premises/multicloud environments; captures metadata; identifies sensitive data; built-in scanning and classification system keeps Data Map updated
  - **Unified Catalog:** Searchable catalog of scanned data; search/browse datasets, view metadata, lineage, classification, sensitivity labels; users can annotate datasets with tags; supports self-service access requests through access policies
  - **Information Protection:** Classify, label, and protect sensitive data with customizable sensitivity labels; labels follow data across emails, documents, cloud storage; policies enforce access controls and encryption via Information Rights Management (IRM); train classifiers to auto-detect records (e.g., patient records)
  - **Data Loss Prevention (DLP):** Automatically detect, monitor, and control sharing/movement of sensitive data; administrators customize rules to block, restrict, or alert on sensitive data transfers
  - **Audit:** Automated logging of user/admin activities (creating files, accessing Fabric items) in the Purview audit log; critical for investigating policy changes or unauthorized access
- **Purview hub connection process:**
  1. In Purview, register Fabric tenant as a data source from Data Map icon.
  2. Select Fabric as data source.
  3. Configure authentication in Microsoft Entra ID (e.g., managed identity of Purview account).
  4. Create a scan in Purview using the Fabric data source.
  5. Once connected, Purview hub appears in Fabric settings.
- **Purview hub in Fabric:** Displays reports and insights about Fabric items. Acts as a centralized gateway between Fabric and Purview. Default tabs: Overview, Sensitivity labels, Endorsement, Domains, Items explorer. Overview page provides high-level tenant data estate insights. Take a tour button provides introduction.

**Architectural Logic**
Purview sits outside Fabric as a cross-platform governance layer. It connects to Fabric via a registered tenant connection and scanning process — Purview does not access Fabric data continuously; it scans metadata on a schedule to populate the Data Map and Unified Catalog. The Purview hub in Fabric is the integration point: it surfaces Purview's governance findings (sensitivity label coverage, endorsement status, domain distribution) within the Fabric UI without requiring users to leave Fabric. Use Purview over built-in Fabric governance when the organization needs cross-platform data estate visibility (scan on-premises, other clouds, other SaaS alongside Fabric), DLP policies for sensitive data movement, advanced auditing, or Information Rights Management encryption.

**Implementation Workflow**
1. **Register Fabric tenant:** In Purview Portal > Data Map > register data source > select Fabric.
2. **Configure authentication:** In Microsoft Entra ID, set up managed identity or other authentication for Purview.
3. **Create scan:** In Purview, create a scan using the Fabric data source to capture metadata.
4. **Access Purview hub:** In Fabric settings > Microsoft Purview hub to view governance reports and insights.
5. **Apply Purview tools:** Configure Information Protection (sensitivity labels, classifiers), DLP policies, Audit logging as needed.

**Exam Gotchas & Distinctions**
- **Fabric built-in vs. Purview:** Built-in features work without extra licensing and cover basic governance (domains, workspaces, endorsement, data lineage, monitoring). Purview adds cross-platform scanning, Data Map/Unified Catalog, DLP, IRM encryption, advanced audit. The exam may ask which capabilities require Purview versus what Fabric provides natively.
- **Purview hub is a gateway:** It does not replace Purview Portal — it surfaces Purview governance data inside Fabric. Advanced configurations (scan creation, DLP policies, label definitions) happen in Purview Portal.
- **Connection must be registered in Purview first:** The Purview hub in Fabric only appears after registering the Fabric tenant in Purview's Data Map and creating a scan.
- **Fabric compliance certifications:** HIPAA BAA, ISO/IEC 27017, 27018, 27001, 27701 — know these for the exam.

## Analytics Data Governance (Sensitivity Labels, Endorsement, and AI Governance)

**Core Concept**
Governing analytics data in Fabric involves sensitivity labels (classification with downstream inheritance), endorsement (Promoted/Certified/Master data trust signals), documentation (descriptions, tags, lineage, domains), and AI-specific governance (Approved for Copilot gate, endorsement-prioritized AI agent data selection) — all aggregated in the OneLake catalog.

**Technical Specifications**
- **Sensitivity labels** (from Microsoft Purview Information Protection — requires Purview licensing and admin configuration):
  - Metadata tags (Public, General, Confidential, Highly Confidential) classifying data sensitivity
  - Appears visually on Fabric items in the portal
  - Can enforce access control through Purview protection policies (users outside permitted security groups cannot access)
  - **Travels with data on export** through supported paths: Excel, PDF, PowerPoint, .pbix files
  - **NOT preserved on CSV or TXT** exports — Fabric displays a warning
  - Works across ALL Fabric item types: lakehouses, warehouses, semantic models, reports, notebooks, pipelines
  - **Downstream inheritance:** Labels applied at source (lakehouse) propagate automatically: lakehouse → SQL analytics endpoint → semantic model → report. Labeling a single source item can protect the entire downstream chain.
  - **Default labeling:** New items auto-receive a baseline label if no label is applied during creation
  - **Mandatory labeling:** When enabled, users cannot save Power BI items without applying a label (limited support for non-Power BI Fabric items)
  - **Inheritance upon creation:** New items created from labeled parents inherit the parent's label
  - **Inheritance from data sources:** Power BI semantic models inherit labels from labeled data sources
  - If the organization does not use Purview, alternative classification: workspace naming conventions, item descriptions, tags
- **Endorsement levels:**
  - **Promoted:** Any user with write permissions can promote an item. Signals team-level trust. Low-friction, no admin involvement.
  - **Certified:** Organization-authorized reviewer verifies quality standards. Fabric admin specifies who can certify (can delegate to domain administrators). Reserve for production assets feeding business-critical decisions.
  - **Master data:** Only users specified by Fabric admin can apply. Applies ONLY to data items (lakehouses, semantic models) — not reports, notebooks, pipelines. Signals single source of truth for core reference data (product catalogs, customer master lists, financial hierarchies).
  - Nearly all Fabric and Power BI items support endorsement (Promoted/Certified): lakehouses, warehouses, semantic models, reports, notebooks, pipelines, dataflows. **Exception: Power BI dashboards do NOT support endorsement.**
  - Absence of endorsement communicates the item is personal, experimental, or not yet reviewed.
  - Endorsement determines which data Copilot and AI agents treat as trustworthy — certified/promoted semantic models are prioritized over unendorsed items.
- **Tags:** Configurable text labels defined by Fabric administrator. Data owners apply tags for categorization beyond endorsement/sensitivity (e.g., by business domain: Sales, Finance, HR; or refresh frequency: Daily, Weekly). Searchable and filterable in OneLake catalog.
- **Documentation practices:**
  - **Item descriptions:** Added to every item; appear in OneLake catalog for evaluation without opening
  - **Data lineage:** Visualize data flow from source to destination; understand dependencies
  - **Impact analysis:** Before changing an item, identify downstream items that would be affected
  - **Domain assignment:** Assign items to Fabric domains (Sales, Finance, Operations) for context in OneLake catalog
- **OneLake catalog:**
  - **Explore tab:** Browse and filter items by domain, item type, endorsement, keyword
  - **Govern tab:** View governance posture for owned data; recommendations to improve (add descriptions, apply sensitivity labels)
  - **Secure tab:** Manage security centrally — view and edit workspace roles and OneLake security roles
  - Also embedded in Microsoft Teams, Microsoft Excel, Microsoft Copilot Studio
- **AI consumption governance:**
  - **Sensitivity labels define boundaries:** AI agents respect access controls enforced by sensitivity label protection policies
  - **Endorsement signals trust:** When multiple sources can answer a question, endorsement determines priority. Certified > Promoted > Unendorsed
  - **Descriptions and documentation provide context:** AI agents use item descriptions and column names to understand what data represents
  - **Approved for Copilot** (separate from endorsement):
    - Marked in semantic model settings in Power BI service
    - Removes friction treatments (disclaimers/warnings) from Copilot answers
    - Reports built on an approved model inherit the status
    - Workspace administrators can configure workspace to show only Approved for Copilot items in standalone Copilot experience
    - Changes can take **up to 24 hours to fully reflect** across all reports (most appear within an hour)
    - Must use Prep for AI features first (AI data schema, AI instructions, verified answers) before marking as approved
  - **Prep for AI** (from Home ribbon in Desktop or semantic model page in service):
    - AI data schema: define focused subset of tables/columns/measures for Copilot
    - AI instructions: provide natural language business context, rules, terminology
    - Verified answers: associate specific visuals with trigger phrases for known questions
  - **Fabric IQ ontology:** Endorsement, classification, and documentation ensure the ontology connects to trustworthy data. Data agents use endorsement/sensitivity metadata to determine appropriate sources.
  - **Operations agents (preview):** In Real-Time Intelligence, monitor eventhouse streams against rules. Well-governed source data ensures rules and actions are based on trustworthy data.

**Architectural Logic**
Governance signals (sensitivity labels, endorsement, documentation) flow from source items downstream through inheritance. The OneLake catalog aggregates these signals into a single searchable/governable surface. AI agents process these signals programmatically — they cannot "know" which data is trustworthy or sensitive without explicit metadata. Sensitivity labels provide the access boundary (AI respects Purview protection policies). Endorsement provides trust ranking (AI prioritizes certified over unendorsed). Descriptions provide semantic context (AI uses them to understand what data represents). This means governance is not separate from AI strategy — the same classification and documentation that helps human users find data is what enables AI to produce accurate, safe responses. Use "Promoted" for team-level AI use and "Certified" for organization-wide AI consumption. Apply sensitivity labels to ALL items containing personal, financial, or regulated data — AI automatically respects these guardrails.

**Implementation Workflow**
1. **Classify:** Apply sensitivity labels to source lakehouses/warehouses (propagation handles downstream items). Enable default labeling so new items always have a baseline. Use mandatory labeling for Power BI items if possible.
2. **Endorse:** Team members promote tested items. Domain-authorized reviewers certify production assets. Admin-designated users apply Master data to authoritative source-of-truth items.
3. **Document:** Add descriptions to all items. Assign domains. Apply tags for business categorization.
4. **Set AI governance:** Configure Prep for AI features (AI data schema, AI instructions, verified answers) on semantic models. Mark as Approved for Copilot after thorough testing.
5. **Monitor:** Use OneLake catalog Govern tab to track governance coverage (items lacking labels, descriptions, endorsement). Use recommendations to close gaps.
6. **Use in OneLake catalog:** Before starting new projects, search for existing certified or master data items to reuse, reducing duplication.

**Exam Gotchas & Distinctions**
- **Label propagation vs. manual labeling:** One label on a lakehouse propagates downstream through the entire chain (lakehouse → SQL endpoint → semantic model → reports). The exam tests understanding that you do not need to label each item individually.
- **Approved for Copilot vs. endorsement:** Endorsement guides discovery and AI prioritization. Approved for Copilot is a formal governance gate that removes friction in the Copilot experience. Both are needed — they serve different purposes.
- **Master data vs. Certified:** Certified signals quality/trustworthiness. Master data signals the authoritative single source of truth (e.g., product catalog, customer master). Master data only applies to data items (lakehouses, semantic models — not reports/notebooks/pipelines).
- **Labels not preserved on CSV/TXT:** Sensitivity labels and protections travel with Excel, PDF, PowerPoint, .pbix exports but NOT CSV or TXT — Fabric shows a warning.
- **Endorsement exception:** Power BI dashboards do NOT support endorsement. All other Fabric items do.
- **Mandatory labeling limited scope:** Works for Power BI items to prevent saving unlabeled. Support for non-Power BI Fabric items is limited.
- **Approved for Copilot propagation:** Reports inherit the status from their semantic model. Changes take up to 24 hours (most within 1 hour) — not instant.
- **OneLake catalog Govern tab:** Contains recommended actions — use it proactively to identify governance gaps before they affect AI quality.
- **AI agent prioritization:** Certified semantic models > Promoted > Unendorsed. If an AI agent produces unexpected results, check whether it is using the correct endorsed source.
