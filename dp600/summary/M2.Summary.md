## Card 1: Analytical Data Store Options

### What It Is
Microsoft Fabric provides three primary analytical data stores: the Lakehouse, the Warehouse, and the Eventhouse. While all three are built on the OneLake foundation and support open formats like Delta and Parquet, they are optimized for different data patterns, query languages, and workload requirements.

### Comparing the Stores
- **Lakehouse:** This is the most versatile option, designed for flexible analytics and data engineering. It supports structured, semi-structured, and unstructured data. The primary development tool is Apache Spark (Python, Scala, SQL, R), and it supports batch ingestion via Spark notebooks, pipelines, and dataflows. It provides a dual-access model: read/write access via Spark and read-only T-SQL access through the SQL analytics endpoint.
- **Warehouse:** This is optimized for structured analytics and enterprise BI reporting. It provides full transactional T-SQL capabilities, including complete DDL and DML support (such as `MERGE`). The primary development tool is T-SQL, and it is the preferred choice for SQL-first teams building star schemas and dimensional models.
- **Eventhouse:** This is purpose-built for real-time analytics on streaming and time-series data. It handles high-volume, append-heavy workloads with minimal latency. The primary development tool is Kusto Query Language (KQL), and it is ideal for monitoring telemetry, logs, and IoT sensor data.

### Decision Framework
When choosing a data store, consider several key factors. The **data format** (structured vs. unstructured) and **write pattern** (transactional vs. streaming) are critical. **Query language preference** (T-SQL vs. Spark vs. KQL) and the **team's existing skill set** also play a major role. Finally, the **workload type**—whether it is batch analytics, exploratory data science, or real-time monitoring—will ultimately determine the best fit.

### AI Readiness
Each store supports different AI scenarios. The Lakehouse is the natural home for machine learning training and feature stores, especially when using Spark. The Warehouse provides the structured, governed data that Copilot and data agents rely on for answering natural language questions. The Eventhouse enables real-time AI scoring and anomaly detection on live, streaming event data.

### Exam Gotchas
- **OneLake Integration:** All three stores write to OneLake, meaning data can be accessed across workloads via shortcuts or cross-database queries without duplication.
- **Lakehouse SQL Access:** The SQL analytics endpoint on a lakehouse is strictly read-only for T-SQL users.
- **Warehouse Transactions:** Only the Warehouse provides full multi-table ACID transaction support through T-SQL.
- **Eventhouse Optimization:** The Eventhouse is optimized for append-only streaming and is not intended for frequent `UPDATE` or `DELETE` operations.
- **Workload Overlap:** Many real-world solutions use multiple stores together (e.g., a Lakehouse for staging and a Warehouse for curated BI).

## Card 2: Dimensional Modeling

### What It Is
Dimensional modeling organizes analytical data into **fact tables** (numeric measures of business events) and **dimension tables** (descriptive attributes providing context). This separation makes data intuitive for analysts and optimized for query engines.

### Schema Types
- **Star Schema:** Central fact table with dimension tables radiating outward. Fewer joins, faster queries, recommended for most analytics and Power BI semantic models. Denormalized dimensions add minor storage redundancy but vastly simplify queries.
- **Snowflake Schema:** Normalized dimensions split into related sub-tables (e.g., product → subcategory → category). Use when dimensions are extremely large or you need hierarchies at different grains. More joins = more complex queries.

### Fact Table Design
- **Define the grain first** — what one row represents (e.g., one row per sales order line). Grain determines which dimension keys and measures belong.
- **Three types:** Transaction (one row per event), Periodic Snapshot (regular interval summary), Accumulating Snapshot (tracks process milestones).
- **Measures:** Additive (summable across all dimensions), Semi-additive (not across time), Non-additive (store underlying values instead).
- **Factless fact tables** capture occurrences without numeric measures (e.g., attendance).

### Dimension Table Design
- Use **surrogate keys** (autogenerated integers) instead of natural keys to insulate from source changes and support SCD tracking.
- **Denormalize** dimension attributes for performance — store category name directly in product dimension rather than a separate table.
- **Conformed dimensions** are shared across multiple fact tables (e.g., a single date dimension used by sales, inventory, and purchasing facts).
- **Role-playing dimensions** reference the same physical table multiple times in one fact table (e.g., Order Date, Ship Date, Delivery Date all using Dim_Date).
- **Junk dimensions** consolidate many small, low-cardinality attributes (flags, status values) into one table.

### Slowly Changing Dimensions (SCD)
- **Type 0:** Retain original — never change (e.g., date of birth).
- **Type 1:** Overwrite — no history kept (corrections, history not needed).
- **Type 2:** Add new row — full history with start/end dates and current flag. Most common for attributes where historical accuracy matters.
- **Type 3:** Add new column — tracks only current vs. previous value.
- **Type 6:** Hybrid of Type 1, 2, and 3 — full history plus current value on every row.

### AI Readiness
Star schemas are the foundation for Power BI semantic models and Copilot. The Fabric IQ ontology maps directly to dimensional model concepts: entity types → dimensions, properties → attributes, relationships → key-based connections.

### Exam Gotchas
- **Grain first:** Always define the grain before picking dimensions and measures.
- **Surrogate keys preferred:** Insulate from source system key changes and enable SCD Type 2.
- **SCD Type 2 columns:** Start date, end date, is_current flag are the standard implementation.
- **Star over snowflake:** Star is recommended for most Fabric workloads — simpler queries, better Power BI performance.
- **No FK enforcement:** Fabric warehouses don't enforce foreign key constraints; use naming conventions and loading logic instead.

## Card 3: Dataflows Gen2 (Low-Code Transformation)

### What It Is
Dataflows Gen2 provide a **Power Query-based, low-code ETL** experience in Microsoft Fabric. Transformations are built visually in the Power Query Online editor, recorded as applied steps, and run on managed Fabric compute. Ideal for teams comfortable with Power Query in Excel or Power BI Desktop.

### Key Capabilities
- Connects to 300+ data sources (cloud/on-prem databases, files, SaaS, Fabric items).
- 300+ visual transformations (filter, merge, pivot, aggregate, group by).
- Loads to lakehouses (Delta tables), warehouses, SQL databases, ADLS Gen2, Azure Data Explorer, Snowflake, and more.
- **Update methods:** Replace (full snapshot), Append (incremental rows), Incremental refresh (time-windowed buckets, significantly reduces refresh time).
- **Copilot for Dataflow Gen2:** Generate transformations via natural language prompts ("Remove rows where Status is null", "Add column for profit = Revenue - Cost").

### Common Transformations
| Type | Purpose |
|------|---------|
| Filter rows | Remove rows not meeting criteria |
| Select/remove columns | Keep only needed columns |
| Change data types | Set correct types for analysis |
| Split/Merge columns | Reshape column values |
| Pivot/Unpivot | Convert rows ↔ columns |
| Group by | Aggregate by one or more columns |
| Merge queries | Join two queries (like SQL JOIN) |
| Append queries | Stack rows (like SQL UNION) |

### M Language
Every visual transformation generates M code behind the scenes. Direct M editing useful for: custom functions, parameterized queries, error handling (`try...otherwise`), and advanced logic not supported visually.

### Performance Optimization
- **Modern Query Evaluator:** Enabled by default, provides faster refreshes and better resource utilization.
- **Query Folding:** Pushes transformations to the data source for execution (ideal = full folding). Check by right-clicking a step → View Native Query. Folding-friendly steps: filters, column selects, sorts, group bys, merges from same source. Folding breakers: custom M columns, pivots, merges across sources.
- **Filter and select columns early** — reduces data volume for downstream steps.
- **Disable unnecessary loads** — staging/reference queries don't need to load to destinations.
- **Preview-only steps** — run during authoring but excluded from production refresh.
- **Staging dataflows** — separate extraction from transformation for independent schedules and reusability.

### Exam Gotchas
- **Low-code ≠ no-code:** Power Query interface, but M language is available for advanced logic.
- **Query folding:** Know what breaks it (custom columns, pivots) and what doesn't (filters, selects, group bys).
- **Incremental refresh:** Supported for lakehouse, warehouse, and Azure SQL Database destinations only.
- **A destination is optional** — a dataflow can run without one and be consumed by pipelines or Power BI directly.
- **Dataflows vs. notebooks:** Dataflows for simple-to-moderate/low-code preference; notebooks for complex logic/large-scale/Spark.

## Card 4: Notebooks (Spark Transformation)

### What It Is
Fabric notebooks provide an interactive, code-based environment running on **Apache Spark**. Supports PySpark (Python), Spark SQL, Scala, and R. Cells execute independently, results appear inline — ideal for iterative development and complex transformations.

### When to Use Notebooks vs. Dataflows
| Factor | Notebooks | Dataflows Gen2 |
|--------|-----------|----------------|
| Complexity | Complex logic, custom functions | Simple to moderate |
| Interface | Code-based (SQL, Python) | Visual, low-code |
| Scale | Large datasets (Spark distributed) | Smaller to mid-size |
| Flexibility | Full programming language | Prebuilt transformations |

### Data Shaping & Cleaning
Core transformation patterns (both Spark SQL and PySpark):
- **Remove duplicates:** `SELECT DISTINCT` or `ROW_NUMBER() OVER (PARTITION BY ...)`
- **Handle nulls:** `COALESCE(region, 'Unknown')` or drop rows with `WHERE customer_id IS NOT NULL`
- **Filter rows:** `WHERE year(order_date) = 2024 AND amount > 0`
- **Select/rename columns:** Consistent naming conventions help Copilot and AI tools.
- **Add calculated columns:** `quantity * unit_price AS line_total`
- **Conditional columns:** `CASE WHEN ... THEN ... END AS value_tier`
- **Convert data types:** `CAST(amount AS DECIMAL(10,2))`

### Combining & Aggregating Data
- **Joins:** INNER, LEFT, RIGHT, FULL OUTER, CROSS — standard SQL join types.
- **Aggregations:** `GROUP BY` with `COUNT`, `SUM`, `AVG`; `HAVING` to filter groups.
- **Window functions:** `ROW_NUMBER()`, `RANK()`, `LAG()`, `LEAD()`, running `SUM()` — keep all rows while computing values across related rows.
- **CTEs:** `WITH ... AS (...)` breaks complex queries into named steps; in PySpark, chain DataFrame operations.
- **Pivot:** Transform rows to columns for cross-tabulation; specifying values improves performance.

### Writing Delta Tables
- **Write modes:** `CREATE OR REPLACE TABLE` (overwrite) or `INSERT INTO` (append).
- **Partitioning:** Use for tables >1 TB; target ≥1 GB per partition; common partition columns: year, month, region. Avoid over-partitioning on high-cardinality columns.
- **File sizing:** Target 128 MB – 1 GB per Parquet file. Optimize Write (default) consolidates small files. Run `OPTIMIZE` and `VACUUM` for maintenance.
- **Delta features:** ACID transactions, schema enforcement, V-Order (optimization for read-heavy workloads, disabled by default).

### Exam Gotchas
- **Default lakehouse:** Pinning a default lakehouse sets the Hive metastore context — tables are referenced by name without full paths.
- **Magic commands:** `%%sql` switches to Spark SQL within a PySpark notebook.
- **Optimize Write is on by default** — helps prevent small file problems.
- **V-Order is off by default** — must be enabled at the session level.
- **Partitioning guidelines:** Only partition tables >1 TB; avoid high-cardinality partition columns.

## Card 5: T-SQL Transformation

### What It Is
T-SQL in Fabric Warehouse provides full read-write capabilities for data transformation — `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE TABLE AS SELECT` (CTAS). The lakehouse SQL analytics endpoint is **read-only** for T-SQL.

### Core Transformations
- **Filter & shape:** `WHERE`, `CASE`, `COALESCE`/`ISNULL`, `CAST`/`CONVERT` for type conversions.
- **Joins & aggregations:** `INNER JOIN`, `GROUP BY`, `HAVING` to filter groups.
- **Window functions:** `ROW_NUMBER()`, `RANK()`, `LAG()`, `LEAD()`, `SUM() OVER (...)` — analytical calculations without collapsing rows.
- **CTEs:** Named subqueries (`WITH ... AS (...)`) for step-by-step transformations.

### Views
- **Reusable named SELECT statements** that always reflect current source data.
- Benefits: reusability, abstraction (hide complex joins), security (restrict columns/rows).
- Use `ALTER VIEW` to modify. Organize into schemas (e.g., `gold`, `reporting`).
- **Views vs. tables:** Views = always fresh, no storage cost, best for simple/moderate aggregations. Tables = precomputed, faster for performance-critical dashboards.

### Stored Procedures
- Named blocks of T-SQL supporting **write operations, parameters, multi-step logic, and error handling** (`TRY...CATCH`).
- **Loading patterns:** Full refresh (delete + reload), Incremental load (watermark column), Merge/Upsert (`MERGE` statement for inserts + updates in one operation).
- **Pipeline integration:** Data Factory pipelines can call stored procedures as activities on a schedule.

### Dimensional Table Implementation
- **Create dimension tables** with `IDENTITY` surrogate keys, SCD Type 2 columns (effective_date, end_date, is_current).
- **Create fact tables** with foreign keys to dimension tables and numeric measures.
- **Load dimensions:** Initial `INSERT...SELECT`, updates via `MERGE` (Type 1) or expire + insert (Type 2).
- **Load facts:** Join staging data to dimension tables on surrogate keys, filtering `is_current = 1`.
- **Table clones:** `CREATE TABLE ... AS CLONE OF ...` — zero-copy reference for development/testing without duplicating storage.

### Exam Gotchas
- **Lakehouse SQL endpoint is read-only** — only warehouses support write operations via T-SQL.
- **No FK enforcement:** Fabric warehouses don't enforce foreign key constraints; maintain referential integrity through loading logic.
- **CTAS** is for one-time materialization; stored procedures are preferred for recurring transformations.
- **Table clones are zero-copy** — they share underlying data files until modified, making them efficient for dev/test.
- **Visual Query Editor** generates T-SQL behind the scenes; can switch to View SQL at any time.
