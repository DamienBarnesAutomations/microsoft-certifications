# M2.Summary.md

## Lakehouse

**Core Concept**
A Fabric lakehouse combines data lake scalability with data warehouse query capabilities, storing structured, semi-structured, and unstructured data in OneLake and offering both Apache Spark (read/write) and a read-only SQL analytics endpoint.

**Technical Specifications**
- **Areas:** `Tables` (managed Delta tables) and `Files` (unstructured/non-Delta data like JSON, Parquet exports, images, documents). Placing data in `Tables` auto-validates, extracts metadata, and registers the table in the Hive metastore—no manual `CREATE TABLE` needed.
- **Access paths:**
  - Spark (Python, Scala, SQL, R) for read/write
  - SQL analytics endpoint for read-only T-SQL queries
- **Storage format:** Delta Lake (Parquet with transaction log)
- **Schema management:** Schema-on-read with optional enforcement through Delta
- **Transaction support:** Single-table ACID through Delta Lake only; no multi-table transactions
- **Write support:** Spark notebooks, pipelines, dataflows, Spark job definitions
- **Read support:** Spark + T-SQL via SQL analytics endpoint; Power BI via Direct Lake mode
- **Data types:** Structured, semi-structured (JSON, Parquet), unstructured (images, documents)
- **AI integration:** Spark MLlib, scikit-learn run natively; Semantic Link (SemPy) bridges Power BI semantic models and lakehouse data; vector embeddings stored as Delta tables for RAG/ similarity search; `Files` area stores documents/images for generative AI pipelines
- **Limitations:** Batch or micro-batch only (not real-time streaming); no full DDL/DML on SQL analytics endpoint (read-only); no multi-table ACID transactions

**Architectural Logic**
The lakehouse solves the problem of having separate data lakes (for data science) and data warehouses (for BI) that require data duplication. By using Delta format on OneLake and providing both Spark and SQL access to the same copy, it enables data engineers to transform data with notebooks and analysts to query the same data with T-SQL or Power BI Direct Lake—without moving data. Use lakehouse over warehouse when data includes unstructured formats, schemas are evolving, or the team works in Python/Spark. Use lakehouse over eventhouse when data arrives in batches, not streams. Anti-pattern: using the lakehouse for heavy transactional UPDATE/DELETE patterns across multiple tables (use warehouse instead).

**Implementation Workflow**
1. Create a lakehouse in a Fabric workspace.
2. Ingest data into `Tables` (managed Delta) or `Files` (unstructured) via pipelines, dataflows, or Spark notebooks.
3. Transform data using notebooks (PySpark/Spark SQL/Scala/R) and register results as Delta tables.
4. Expose curated tables to analysts via the SQL analytics endpoint or Power BI Direct Lake.

**Exam Gotchas & Distinctions**
- **SQL analytics endpoint is read-only:** Candidates often assume the lakehouse supports full T-SQL writes. It does not. For DDL/DML must use a warehouse.
- **Single-table vs. multi-table ACID:** Lakehouse provides single-table ACID via Delta; warehouse provides multi-table ACID via T-SQL. This distinction matters for workloads requiring referential integrity across tables.
- **Direct Lake on lakehouse:** Power BI reads Delta files directly from OneLake with no import or refresh needed—but falls back to DirectQuery if the query exceeds memory/resource thresholds.
- **Auto-registration:** Files placed in `Tables` are automatically registered as Delta tables; files placed in `Files` are not—they must be read via Spark with explicit schema.

## Warehouse

**Core Concept**
A Fabric warehouse is an enterprise-scale relational data store built on Delta format in OneLake, providing full read-write T-SQL with multi-table ACID transactions for structured, governed analytical workloads.

**Technical Specifications**
- **Storage format:** Delta (Parquet with transaction log) on OneLake
- **Schema management:** Schema-on-write with enforced data types
- **Transaction support:** Full multi-table ACID (multiple tables commit or roll back together)
- **Write support:** T-SQL (INSERT, UPDATE, DELETE, MERGE, COPY INTO, CTAS), pipelines, dataflows
- **Read support:** T-SQL (SELECT, views, stored procedures, functions); Power BI via Direct Lake
- **Data types:** Structured only (tabular)
- **No capacity management:** Fabric handles scaling automatically with no knobs to turn
- **Tooling support:** SQL Server Management Studio (SSMS), VS Code with MSSQL extension, Visual Query Editor (drag-and-drop with auto-generated T-SQL)
- **DDL:** CREATE TABLE, ALTER TABLE, views, stored procedures, functions, schemas
- **DML:** INSERT, UPDATE, DELETE, MERGE with full transactional consistency
- **Cross-database queries:** Three-part naming (`warehouse.schema.table` / `lakehouse.schema.table`) to join across warehouses and lakehouse SQL analytics endpoints
- **AI integration:** Structured, governed dimensional models serve as the foundation for Copilot in Power BI (generates DAX against warehouse star schemas) and data agents (translate natural language to T-SQL)
- **No foreign key enforcement:** Fabric warehouses do not enforce foreign key constraints; rely on naming conventions and loading logic for referential integrity

**Architectural Logic**
The warehouse provides a "schema-on-write" environment prioritizing data quality and governance. Unlike the lakehouse's flexible schema-on-read, the warehouse validates data types and constraints at load time, catching errors early. Use warehouse over lakehouse when the workload requires multi-table ACID transactions, slowly changing dimension updates, or a SQL-first team that needs full DDL/DML. The warehouse serves as the curated serving layer in a medallion architecture—data flows from lakehouse through the warehouse for dimensional modeling and BI consumption. Anti-pattern: using the warehouse for unstructured data, real-time streaming, or Spark-based ML workloads.

**Implementation Workflow**
1. Create a warehouse in a Fabric workspace.
2. Ingest structured data into staging tables via T-SQL, pipelines, or dataflows.
3. Transform using T-SQL queries (joins, aggregations, window functions, CTEs).
4. Persist results using CTAS or stored procedures into dimensional tables (fact + dimension).
5. Expose to Power BI via Direct Lake or views for semantic modeling.

**Exam Gotchas & Distinctions**
- **Warehouse vs. lakehouse SQL analytics endpoint:** The warehouse is read-write; the lakehouse endpoint is read-only. Both support Direct Lake for Power BI.
- **No foreign key enforcement:** Unlike SQL Server or Azure SQL Database, Fabric warehouse does not enforce FK constraints. This can lead to orphaned fact rows if dimension loading fails. The exam expects you to know this.
- **Direct Lake:** Warehouse supports Direct Lake (reads Delta files directly) with no scheduled import refresh. Falls back to DirectQuery when query resource limits are exceeded.
- **COPY INTO:** Available in warehouse for high-speed ingestion from files in ADLS Gen2 or OneLake.

## Eventhouse

**Core Concept**
An eventhouse is a real-time analytics store in Fabric, using Kusto Query Language (KQL) and built on a workspace of KQL databases, optimized for streaming ingestion, time-series data, and high-volume event-based workloads.

**Technical Specifications**
- **Architecture:** A workspace of KQL databases sharing capacity and resources
- **Data types:** Time-series, event-based, semi-structured (JSON, text), structured
- **Primary query language:** Kusto Query Language (KQL); also supports a subset of T-SQL
- **Write support:** Streaming ingestion, batch ingestion, Eventstream, SDKs, Kafka, Logstash, dataflows
- **Read support:** KQL, T-SQL (subset), Power BI via DirectQuery (not Direct Lake)
- **Storage format:** Columnar store with automatic indexing and compression
- **Schema management:** Schema-on-write with dynamic fields for semi-structured data
- **Transaction support:** Append-optimized; not designed for UPDATE/DELETE operations
- **Partitioning:** Automatic time-based partitioning and indexing by ingestion time
- **Always-On option:** Available for time-sensitive systems that cannot tolerate startup latency; stays available continuously and scales via autoscale
- **AI integration:** Built-in KQL ML functions: `series_decompose_anomalies` for anomaly detection, `series_decompose_forecast` for time-series forecasting, `make-series` for time-series analysis; real-time scoring pipelines via Eventstream
- **High-volume ingestion:** Optimized for millions of events per day; queryable within seconds

**Architectural Logic**
The eventhouse solves the problem of real-time analytics on streaming data—a gap in batch-oriented stores like the lakehouse and warehouse. Its automatic time-based partitioning and columnar storage with built-in indexing enable sub-second queries on append-heavy event data. Use eventhouse over lakehouse/warehouse when data arrives continuously, needs to be queryable within seconds, and involves time-window analysis. Use eventhouse over lakehouse when the ingestion pattern is append-only streaming rather than batch. Anti-pattern: using the eventhouse for traditional star schema modeling (it is optimized for flat, denormalized event data), heavy UPDATE/DELETE patterns, or Spark-based data engineering.

**Implementation Workflow**
1. Create an eventhouse in a Fabric workspace.
2. Ingest streaming data via Eventstream, SDKs, Kafka, or batch ingestion into a KQL database.
3. Query and analyze using KQL (time-series operators, anomaly detection, pattern matching).
4. Build Real-Time Dashboards using KQL for live monitoring.
5. Route aged data to OneLake for access by other Fabric workloads (lakehouse/warehouse).

**Exam Gotchas & Distinctions**
- **Power BI connection:** Eventhouse uses DirectQuery (not Direct Lake) because the columnar format is not Delta/Parquet-based in the same way.
- **Append-only:** The eventhouse is not designed for UPDATE/DELETE. If the exam scenario requires modifying individual records, warehouse or lakehouse is the right choice.
- **KQL vs. T-SQL:** KQL provides the richest analytics experience for time-series; T-SQL subset is available but limited.
- **Always-On:** Must be explicitly enabled; adds cost but eliminates cold-start latency for critical monitoring.
- **Dynamic fields:** Schema-on-write with dynamic fields means you can ingest semi-structured data without defining every column upfront, but the core schema is enforced at write time.

## Dimensional Modeling

**Core Concept**
Dimensional modeling organizes data into fact tables (numeric measures of business events) and dimension tables (descriptive attributes), prioritizing query performance and user comprehension over storage normalization.

**Technical Specifications**
- **Fact tables** contain:
  - Dimension keys (foreign keys referencing dimension tables)
  - Measures (numeric, aggregatable values)
  - Attributes / degenerate dimensions (e.g., order number, tracking code—descriptive but no separate dimension table)
- **Fact table types:**
  - **Transaction:** One row per business event; measures are additive across all dimensions; row is fully known on insert and does not change (except corrections)
  - **Periodic Snapshot:** State at regular intervals; measures are semi-additive (summable across most dimensions but NOT across time)
  - **Accumulating Snapshot:** Tracks a process through milestones; has multiple date dimension keys (one per milestone); row is created at process start and updated as milestones complete; includes duration measures between milestones
- **Factless fact tables:** Capture occurrences without numeric measures (e.g., student attendance, promotion coverage); analyzed by counting rows
- **Aggregate fact tables:** Precomputed summaries at higher granularity/lower dimensionality; purpose is to accelerate commonly run queries; can be used through DirectQuery storage mode in Power BI
- **Measure types:**
  - **Additive:** Summable across all dimensions (revenue, quantity, cost)
  - **Semi-additive:** Summable across some dimensions but not time (account balance, inventory level)
  - **Non-additive:** Cannot be summed meaningfully (unit price, temperature, ratio)
- **Grain:** Defines what one fact row represents. Always define grain **before** identifying dimensions and measures. Grain that is too high-level loses detail; grain that is too detailed increases storage without analytical value.
- **Dimension tables** contain:
  - Surrogate key (system-generated integer, primary key)
  - Natural key / business key (source system identifier)
  - Dimension attributes (columns used for filtering, grouping, labeling)
- **Date dimension exception:** Surrogate key typically uses `YYYYMMDD` integer format (both meaningful and efficient)
- **Naming conventions:** `f_` or `Fact_` prefix for fact tables; `d_` or `Dim_` prefix for dimension tables
- **Schema organization:** Use schemas (`dim`, `fact`, `staging`, `gold`, `reporting`) to separate objects by role

**Architectural Logic**
Dimensional modeling solves the problem that normalized transactional schemas are inefficient for analytical queries (too many joins, unintuitive for business users). The star schema denormalizes dimensions so that queries need only one join per dimension, matching how users naturally ask questions ("Sales by Region by Month"). The tradeoff is storage redundancy from denormalization, but the storage cost is negligible compared to query performance gains. Use star schema over snowflake for most analytics workloads—only consider snowflake when a dimension is extremely large, shared hierarchies exist across different grain levels, or storage costs outweigh query performance needs.

**DAX / M Notes**
*Not applicable to this module.*

**Implementation Workflow**
1. **Define grain:** Determine what one fact row represents (e.g., one row per sales order line item).
2. **Identify dimensions and measures:** Listen for "by" in stakeholder requirements ("sales by region by product by month" reveals dimensions and attributes).
3. **Design schema:** Prefer star schema; use snowflake only when justified by storage cost or shared hierarchies at different grain levels.
4. **Denormalize dimensions:** Flatten hierarchies into single dimension tables; store category name on every product row rather than referencing a separate category table.
5. **Assign surrogate keys:** Use `IDENTITY(1,1)` auto-incrementing integers for dimension surrogate keys.
6. **Create fact table:** Include dimension keys + measures at the defined grain.

**Exam Gotchas & Distinctions**
- **Grain-first rule:** The most common design error is identifying dimensions/measures before defining the grain. The grain determines which dimension keys and measures belong in the table.
- **Star vs. snowflake for Power BI:** Snowflake dimensions require a view to flatten joins back together because Power BI hierarchies need columns from a single table.
- **Degenerate dimensions:** Attributes stored directly in the fact table (order number, tracking code) are not separate dimension tables—candidates often create unnecessary dimension tables for these.
- **Semi-additive measures:** Candidates often assume all measures are additive. Inventory levels and account balances cannot be summed across time.
- **Surrogate vs. natural key:** Surrogate keys insulate the warehouse from source system changes and enable SCD Type 2 tracking; natural keys come from source systems and may change or be reused.
- **Foreign keys not enforced:** Fabric warehouse does not enforce FK constraints; referential integrity depends on loading logic.

## Slowly Changing Dimensions (SCD)

**Core Concept**
SCD patterns define how dimension tables respond when source system attribute values change, balancing historical accuracy against implementation complexity.

**Technical Specifications**
- **Type 0 (Retain original):** Never allows changes. Use for fixed reference data (date of birth, original credit score at time of application).
- **Type 1 (Overwrite):** Replaces the old value with the new value; no history maintained. Use for error corrections or when historical accuracy does not matter. Caution: overwriting a salesperson's region reassigns all historical sales to the new region.
- **Type 2 (Add new row):** Inserts a new row for each change; maintains full version history. Requires additional columns:
  - `start_date` (when this version became effective)
  - `end_date` (when superseded; current rows use far-future date like `9999-12-31`)
  - `is_current` flag (identifies active version for fact table lookups)
  - ETL: expire existing current row (`end_date = today`, `is_current = 0`), then insert new row with new surrogate key, `start_date = today`, `is_current = 1`. Essential when analyzing past context (e.g., "sales by the region the salesperson was assigned to at the time of the sale").
- **Type 3 (Add new column):** Stores current and previous value in separate columns (e.g., `CurrentSalesRegion` and `PreviousSalesRegion`). Tracks only the most recent change; loses all intermediate changes.
- **Type 6 (Hybrid):** Combines Type 1, Type 2, and Type 3. Maintains full version history (Type 2) while storing current value on every row (Type 1 overwrite on specific column) and previous value (Type 3). Every row for a dimension member must be updated when current value changes—adds significant ETL complexity.
- **Selection guide:**
  - Fixed reference data → Type 0
  - Corrections, history not needed → Type 1
  - Full historical accuracy required → Type 2
  - Current vs. previous comparison only → Type 3
  - Current + historical context on every row → Type 6
- **Tradeoffs:**
  - **Storage:** Type 2 dimensions grow over time; plan for increased storage
  - **Query complexity:** Type 2 requires matching on effective dates or using `is_current` flag in joins
  - **ETL complexity:** Type 2 and Type 6 require sophisticated change-detection logic, row expiration, and version insertion

**Architectural Logic**
SCD patterns resolve the conflict between transactional systems (which overwrite data) and analytical systems (which must describe the past accurately). Without an SCD strategy, overwriting a customer's region would retroactively change all historical analysis. Type 2 is the most common for audit-critical attributes because it preserves the context that existed at the time of each fact event. The tradeoff is complexity: every Type 2 attribute requires surrogate keys that change between versions, making fact-to-dimension joins dependent on effective date ranges.

**Implementation Workflow**
1. Identify which dimension attributes require historical tracking and which do not.
2. For Type 1 attributes: use MERGE to overwrite existing rows in place.
3. For Type 2 attributes: implement ETL that sets `end_date` and `is_current = 0` on the existing row, then inserts a new row with a new surrogate key and `start_date = today`.
4. For fact table loads against Type 2 dimensions: join on `is_current = 1` (current view) or on effective date range (`fact.order_date BETWEEN dim.start_date AND dim.end_date`) for point-in-time accuracy.

**Exam Gotchas & Distinctions**
- **Type 2 fact loading nuance:** Joining on `is_current = 1` gives the current attribute values for all historical facts. For historical accuracy, join on effective date range instead. The exam expects you to understand the difference.
- **Don't apply Type 2 to every attribute:** Only track history on attributes where the business requires historical analysis. Use Type 1 for the rest to keep the dimension manageable.
- **Type 1 + Type 2 on the same dimension:** A dimension can mix SCD types—some attributes overwritten (Type 1), others versioned (Type 2). The implementation must handle both within the same table.
- **Surrogate key replacement:** When a Type 2 change occurs, the surrogate key changes. All fact rows referencing the old surrogate key still point to the correct historical version.

## Dataflows Gen2

**Core Concept**
Dataflows Gen2 provide a cloud-based, low-code Power Query ETL experience in Fabric for connecting, transforming, and loading data into lakehouses, warehouses, and other destinations without writing code.

**Technical Specifications**
- **Interface:** Power Query Online (visual, no-code/low-code)
- **Destinations:**
  - Fabric Lakehouse (Delta tables or files: CSV, Parquet, Excel (Preview))
  - Fabric Warehouse (schema-aware, supports writing into specific schemas)
  - Azure SQL Database
  - Fabric SQL database
  - ADLS Gen2
  - Azure Data Explorer / KQL databases (Append only)
  - Snowflake
  - SharePoint Files (delimited text or Excel)
  - No destination required—dataflow can serve as a data source for pipelines or Power BI
- **Update methods:**
  - **Replace:** Drops and recreates destination on every refresh
  - **Append:** Adds new rows to existing data (only method supported by KQL/Azure Data Explorer)
  - **Incremental refresh:** Refreshes only new/changed data using a DateTime column, dividing data into configurable time-range buckets. Supported: Lakehouse, Warehouse, Azure SQL Database. Significantly reduces refresh time for large/frequently updated datasets.
- **Capabilities:**
  - Connect to hundreds of data sources (cloud + on-premises via gateway)
  - 300+ built-in transformations
  - AutoSave and background publishing (validation runs in background with parallel query validations)
  - Schedule and automate (manual, scheduled with parameter support, or pipeline orchestration)
  - Email alerts for failed scheduled refreshes
  - Copilot for Dataflow Gen2 (natural language prompts generate transformations; requires F2 or higher, not supported on Trial SKUs)
  - Environment portability: Fabric Variable Libraries and relative references for CI/CD lifecycle management
- **M language:** Every visual transformation generates M code behind the scenes. Access via Advanced Editor. Direct M coding useful for: custom functions, parameterized queries, error handling (`try...otherwise`), advanced logic the visual interface does not support.
- **Export query results:** To CSV or Excel from the query editor for validation and debugging
- **Performance features:**
  - **Modern Query Evaluator:** Enabled by default; improves refresh times for multi-step shaping pipelines (joins, group-bys, type conversions, complex expressions); no configuration needed
  - **Query folding:** Pushes M steps to source as native queries (e.g., SQL). Three outcomes:
    - Full folding (ideal): all transformations pushed to source
    - Partial folding: some pushed, some local
    - No folding: all processing local (avoid for large datasets)
  - **Check folding:** Right-click step in Applied Steps → "View Native Query" available = step folds; grayed out = folding broken at this step
  - **Steps that typically fold:** Filter rows (WHERE), Select/remove columns, Sort (ORDER BY), Group by (GROUP BY), Merge queries same source (JOIN), Change data types (CAST), Rename columns
  - **Steps that break folding:** Custom columns with complex M, Pivot/unpivot, Merge from different sources, `Table.Buffer`, some M-specific text transformations
  - **Preview-only steps:** Mark steps that run during authoring/preview but excluded from refresh (right-click → "Enable only in previews"). Use for sampling, safer experimentation, debugging.
- **Performance best practices:** Filter early, select columns early, disable unnecessary loads (right-click → deselect "Enable load"), use staging dataflows (separate extraction from transformation), parameterize for reuse, use Monitoring Hub and refresh history to track performance

**Architectural Logic**
Dataflows Gen2 democratize data preparation by extending Power Query skills (common in Excel/Power BI) to enterprise-scale cloud ETL. The separation of transformation logic (Power Query M) from execution engine (managed Fabric compute) makes transformations repeatable, auditable, and reusable across multiple destinations. Use dataflows over notebooks when the team is comfortable with Power Query but not Spark/T-SQL, and transformations are simple to moderate (the "80% case"). Use dataflows over notebooks when the same transformed data must go to multiple destinations. Use notebooks over dataflows for complex algorithmic logic, large-scale distributed processing, or full T-SQL DML patterns.

**DAX / M Notes**
- M is a functional, case-sensitive language. Every Power Query step generates M code.
- Custom functions in M follow the pattern: `(inputText as text) as text => Text.Upper(Text.Trim(inputText))`
- Common transformations: Filter rows, Select/remove columns, Change data types, Split columns, Merge columns, Pivot/Unpivot, Group by, Add calculated columns, Merge queries (JOIN), Append queries (UNION)
- Data quality: Handle nulls (Replace Values), Remove Duplicates, Trim whitespace, Standardize text (Capitalize Each Word, UPPERCASE, lowercase), Remove/Replace Errors

**Implementation Workflow**
1. Navigate to Fabric workspace → + New item → Dataflow Gen2.
2. Select Get Data to connect to source (cloud database, on-premises via gateway, flat file, web service, other Fabric item).
3. Apply transformations visually in Power Query Online editor (ribbon, right-click, or Copilot natural language prompts).
4. Configure destination and update method (Replace, Append, or Incremental Refresh).
5. Publish dataflow; set schedule or integrate into pipeline for orchestration.

**Exam Gotchas & Distinctions**
- **Dataflows Gen1 (Power BI) vs. Gen2 (Fabric):** Gen1 is legacy Power BI dataflows with internal storage only; Gen2 supports multiple external destinations (lakehouse, warehouse, ADLS Gen2, Azure SQL, Snowflake, etc.) and Copilot.
- **Copilot requirement:** F2 or higher capacity (or P1+); Trial SKUs not supported.
- **KQL / Azure Data Explorer destination:** Append only—Replace and Incremental Refresh are not supported.
- **Incremental Refresh vs. Append:** Incremental Refresh uses a DateTime window to update specific segments; Append blindly adds all new rows to existing data.
- **Query folding check:** Folding breaks at a step and all subsequent steps run locally. Order of transformations matters—place folding-friendly steps early.
- **Preview-only steps:** Excluded from production refresh—key for the exam to know they are not the same as "disabled" steps.
- **No destination is valid:** A dataflow can run without a configured destination, serving as a logical data source for pipelines or Power BI.

## Notebooks

**Core Concept**
Fabric notebooks are interactive, web-based coding environments powered by Apache Spark for scalable, code-first data transformation using PySpark (Python), Spark SQL, Scala, or R.

**Technical Specifications**
- **Languages:** PySpark, Spark SQL, Scala, R
- **Magic commands:** `%%sql`, `%%scala`, `%%r` to switch language within a cell regardless of notebook default
- **Spark session:** Starts automatically on first cell execution; persists until stopped or times out from inactivity; all cells share the same session (variables, temp views, DataFrames accessible across cells)
- **Lakehouse attachment:** Pin a default lakehouse → tables and files accessible in explorer; sets Hive metastore context so tables queryable by name without full path
- **Cells:** Code or markdown; run individually or sequentially; output appears below each cell
- **Data stores accessible:**
  - Lakehouse: Pin as default; query Delta tables by name
  - Warehouse: Cross-database queries via three-part naming (`warehouse.schema.table`)
  - KQL database: Spark connector for Kusto
  - External sources: Spark connectors (JDBC, Azure Blob, ADLS, REST APIs)
- **Development patterns:**
  - Interactive development (write → run → inspect → refine)
  - Parameterized notebooks (designate a parameters cell; calling process injects values)
  - Pipeline integration (notebook activity in Data Factory pipeline; pass parameters; chain with other activities)
- **Copilot:** Natural language to Spark SQL/PySpark code generation; requires F2 or higher
- **Delta table features:**
  - ACID transactions: writes either fully succeed or fully roll back
  - Schema enforcement: rejects writes with mismatched column names or data types
  - OPTIMIZE: compacts small files into larger ones
  - VACUUM: removes unreferenced old files to reclaim storage
  - V-Order: write-time Parquet optimization for read-heavy workloads; disabled by default; enable with `SET spark.sql.parquet.vorder.default=TRUE`
  - Optimize Write: enabled by default; consolidates small files during writes
- **Partitioning guidelines:**
  - Benefit when table exceeds 1 TB and queries frequently filter on partition column
  - Target partition size: at least 1 GB per partition
  - Avoid over-partitioning on high-cardinality columns (creates too many small files)
  - Common partition columns: year, month, region
  - Skip partitioning entirely for tables under 1 TB
- **File sizing:** Target 128 MB to 1 GB per file
- **Write modes:**
  - `overwrite` / `CREATE OR REPLACE TABLE`: Replaces entire table (careful—destructive)
  - `append` / `INSERT INTO`: Adds new rows to existing table

**Architectural Logic**
Notebooks solve the problem of complex, large-scale data transformation that low-code tools cannot handle. By providing the full Apache Spark engine with multiple language support, notebooks enable data engineers and data scientists to implement custom logic—joins, window functions, conditional branching, ML training—on datasets larger than what a single machine can process. Use notebooks over Dataflows Gen2 when transformations require complex joins, window functions, conditional logic, ML libraries, or when datasets are large enough to benefit from distributed Spark processing. Use notebooks over T-SQL when the workload involves Python ecosystems (scikit-learn, pandas), unstructured data processing, or iterative ML experimentation.

**Implementation Workflow**
1. Create a notebook in a Fabric workspace.
2. Attach a default lakehouse (tables queryable by name).
3. Read data into DataFrame or temp view.
4. Apply transformations (filter, clean, join, aggregate, window functions) using Spark SQL or PySpark.
5. Write results as partitioned Delta tables using `CREATE OR REPLACE TABLE` or `INSERT INTO`.
6. Optionally run OPTIMIZE and VACUUM for maintenance.

**Exam Gotchas & Distinctions**
- **Notebooks vs. Dataflows Gen2:** Notebooks are code-based, handle complex logic and large datasets; Dataflows are visual/low-code, handle simple-to-moderate transformations. The exam may ask which fits a given skill set and complexity level.
- **Spark session sharing:** Variables and temp views created in one cell are available in subsequent cells—important when debugging and for multi-cell pipelines.
- **Lakehouse attachment vs. full path:** With a default lakehouse pinned, reference tables by name; without it, you must use the full path.
- **Partitioning thresholds:** Partition only when table > 1 TB; target ≥1 GB per partition. Over-partitioning creates small files that degrade performance.
- **V-Order disabled by default:** Candidates often assume V-Order is on. It is not in new workspaces; must be explicitly enabled at session level.
- **OPTIMIZE vs. VACUUM:** OPTIMIZE compacts files but keeps all historical versions; VACUUM physically deletes old files beyond a retention threshold. VACUUM can break time-travel queries.

## T-SQL Transformations

**Core Concept**
T-SQL in a Fabric warehouse provides a full read-write, multi-table ACID transactional environment for transforming structured relational data using DDL, DML, views, stored procedures, and dimensional table patterns.

**Technical Specifications**
- **Capabilities:** Full DDL (CREATE, ALTER, DROP) and DML (INSERT, UPDATE, DELETE, MERGE) with multi-table ACID compliance
- **Key commands:**
  - **CTAS (CREATE TABLE AS SELECT):** Creates and populates a new table in one statement; useful for one-time materializations
  - **MERGE:** Inserts new rows and updates existing ones in a single atomic operation; ideal for dimension table upserts
  - **COPY INTO:** High-speed ingestion from files in ADLS Gen2 or OneLake
- **Views:**
  - Named SELECT statement stored as a database object; no data storage—always reflects current source state
  - Benefits: Reusability (update in one place), abstraction (hide joins/calculations), security (expose only specific columns/rows)
  - Common patterns: Transformation views (business rules/calculations), Aggregation views (summaries at specific grain), Denormalized views (flatten joins for reporting tools)
  - Use ALTER VIEW to modify existing definition
- **Stored procedures:**
  - Named block of T-SQL stored in the warehouse; supports write operations (INSERT/UPDATE/DELETE), parameters, multi-step logic, error handling (TRY...CATCH)
  - Naming convention: `usp_` prefix to distinguish user procedures from system procedures
- **Loading patterns:**
  - **Full refresh:** Delete all rows and reload entire table; simplest pattern; good for small to medium tables
  - **Incremental load:** Process only new/changed data since last run using a watermark column (e.g., `modified_date`, row version)
  - **Merge (upsert):** Single MERGE statement handles inserts and updates; especially useful for dimension tables
- **Table clones:** `CREATE TABLE table_name AS CLONE OF source_table;` Zero-copy reference at a point in time; only changed data consumes new storage; ideal for dev/testing and creating rollback points before risky transformations
- **Custom schemas:** Organize objects into schemas like `gold`, `dim`, `fact`, `staging`, `reporting`
- **Visual Query Editor:** Drag-and-drop interface within warehouse; generates T-SQL behind the scenes; switch to View SQL to see generated query; save output as view or table
- **External tools:** Connect via T-SQL connection string to SSMS or VS Code with MSSQL extension
- **No foreign key enforcement:** Fabric warehouse does not enforce FK constraints; rely on naming conventions and ETL logic for referential integrity

**Architectural Logic**
T-SQL in the warehouse provides the transactional integrity and governance that dimensional modeling requires. Stored procedures and views encapsulate transformation logic into reusable, parameterizable, and automatable components. Use T-SQL transformations over notebooks when the team is SQL-first and the transformation pattern involves DML operations, transactional consistency across multiple tables, or scheduled incremental refreshes. Use T-SQL over Dataflows Gen2 when transformations require stored procedures, complex joins, DML operations, or parameterized recurring refreshes. Anti-pattern: using T-SQL for unstructured data, Python ecosystem ML workloads, or operations that need Spark's distributed processing.

**Implementation Workflow**
1. Load raw data into staging tables via COPY INTO, pipelines, or dataflows.
2. Transform data using T-SQL queries (filter, join, aggregate, window functions, CTEs).
3. Create views (`CREATE VIEW`) to encapsulate reusable logic without storing data.
4. Create stored procedures (`CREATE PROCEDURE`) for parameterized, repeatable transformation automation.
5. Implement dimensional tables: dimension tables with surrogate keys (`IDENTITY(1,1)`) and fact tables with foreign keys referencing dimension keys.
6. Load dimension tables (MERGE for Type 1; expire/insert for Type 2).
7. Load fact tables by joining staging data to dimension tables to resolve surrogate keys.
8. Orchestrate stored procedures via Data Factory pipelines for scheduled refreshes.

**Exam Gotchas & Distinctions**
- **Warehouse vs. lakehouse SQL analytics endpoint:** The warehouse supports full read-write T-SQL; the lakehouse endpoint is read-only. Both support Power BI Direct Lake.
- **Views vs. Tables:** Views are virtual (always current, no storage cost, performance depends on query complexity); Tables are materialized (faster for frequent/expensive queries, consume storage, require refresh).
- **Views vs. Stored Procedures:** Views are read-only SELECT; stored procedures support writes, parameters, multi-step logic, and error handling.
- **Stored Procedures vs. CTAS:** CTAS is for one-time table creation; stored procedures handle recurring, parameterized refreshes.
- **No FK enforcement:** Unlike traditional SQL Server, Fabric warehouse does not enforce foreign keys. Fact-to-dimension integrity depends entirely on the ETL process.
- **Table clones vs. full copies:** Clones are zero-copy at creation (share underlying data files); only changed data consumes new storage. A full copy (`SELECT INTO`) duplicates all data immediately.
- **MERGE for Type 1 dimensions:** Single atomic operation handles both new and updated records. For Type 2, MERGE alone is insufficient—must expire old row and insert new row with different surrogate key.
- **Is_current = 1 in fact loading:** Gives current attribute values but not historically accurate; for historical accuracy, join on effective date range.
